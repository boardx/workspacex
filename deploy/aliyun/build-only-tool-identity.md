# Reviewed tools for a frozen application build

`workspacex-cn-build-candidate --build-only <root-private-binding.json> <applicationSHA> <release> <attempt>` is an explicit artifact lane. The three-argument legacy entry retains its dynamic preactivate gate. Neither lane promotes main-cn here. This extends merged #5168 static bootstrap semantics without changing the frozen application.

The independently reviewed tool commit must be installed by an authorized operator in `/opt/workspacex-cn/release-tools/<toolSHA>` with clean HEAD and root-owned, non-writable ancestors/files. Before any new installation, review/approve exact files and hashes. The binding is an EXCL root:root 0600 JSON file with `schemaVersion:1`, `mode:"build-only"`, `applicationRevision`, `toolRevision`, `toolRoot`, `release`, `attemptId`, and `filesSha256` for exactly the `FILES` paths enumerated by `cn-build-tool-identity.py`. This list includes the loader itself. Every installed entry in that closure must equal its tool Git object and listed hash; the validator must also equal its exact tool object. No unchecked alternate tool directory or caller-provided executable is accepted.

The binding also contains `applicationSource:{path:"/var/lib/workspacex-cn/build-sources/<applicationSHA>.git",ref:"refs/heads/candidate",treeSha,inventorySha256}`. Prepare that dedicated root-private, complete bare cache from the already verified source artifact before invoking this lane; do not change the shared mirror's moving main. The loader checks exact candidate ref/commit/tree, hashes its recursive Git tree inventory, runs full fsck, and rejects alternates/promisor config/packs. The build fetches only this offline ref; the ordinary lane retains its existing origin/main source gate. Existing ancestry checking remains. Collector reuses this bound cache rather than asserting current shared main equals an older frozen candidate.

Application checkout/source cache, offline dependencies, config and stable secrets retain existing prebuild checks. The tool collector uses the frozen application's actual compatibility CLI with `--static` in the application cwd; it never copies application modules or claims production schema/permission/seed readiness. Tool collector/evidence/probe and validator bytes come from the independent reviewed tool identity, rather than the application SHA. Source revision in images/manifest remains the application SHA.

Publisher performs actual immutable registry inspections for all six services. After publishing, the explicit lane re-reads manifest, seal, and original prebuild evidence, verifies exact application/release/attempt and static-only facts, requires a fresh prebuild TTL and the actually held canonical FD9 lock, repeats six registry digest inspections, and creates EXCL root600 `build-only.sealed.json` alongside prebuild receipts. It binds application/tool revisions, all tool hashes, binding/prebuild/manifest/seal hashes, and immutable image references. `ready`, `prepared`, and `productionActivated` remain false. Registry failure or any changed tool/seal/static fact prevents this receipt.

This receipt is not accepted by deploy preparation or activation. Existing preactivate dynamic schema/permission and real production bootstrap gates remain unchanged; a source-static receipt cannot substitute for them. No migration, provisioning, service activation, traffic change, or production SQL is added by this change.

Local verification includes identity, source-cache, closure, drift, receipt and maintenance input-substitution negative fixtures, the canonical preflight validator suite and Bash syntax checks. Exact commands, source hashes and results are recorded in the review evidence rather than treated as a fixed test count here. Local verification uses Python stdlib synthetic fixtures and shell syntax checks, not production credentials or a live build. Full CI and authorized exact tool installation are required before cloud use; this PR alone does not retrofit an already installed 9b25 toolchain.

The loader validates every Git metadata directory/file before invoking Git, rejects external Git directories, symlinks and config includes, and disables fsmonitor/hooks explicitly. Receipt admission re-executes the exact bound tool validator and compares its complete result with `prebuild.validated.json`; no subset of bootstrap fields substitutes for that gate.

Receipt publication uses a private temporary file, file fsync, an exclusive atomic hard link and directory fsync. An existing final receipt is never replaced. On post-link failure, only a final inode matching the owned temporary inode is removed, followed by directory fsync. Unproven cleanup emits `RECEIPT_CLEANUP_UNPROVEN` and actual final-existence readback. An existing root-private receipt with identical bytes is verified and directory-fsynced for idempotent reuse; different bytes are rejected. A killed process may leave its UUID temporary file, which requires ownership/inode proof before cleanup.

Ordinary build/deploy now admit through the fixed root-owned maintenance helper immediately after acquiring canonical release FD9, before checkout, prepare, activation or rollback/config restoration calls. CLI create/clear/admit require the same fixed root-private lock inode on FD9, rejection of a second flock, and a successful nonblocking flock on the inherited description; an unrelated process holding the lock cannot substitute. The helper checks its bytes against fixed `/etc/workspacex-cn/trusted-tool-binding.json` (root600, exact toolRevision and hold module hash). This profile and the helper require separately approved exact installation. Missing trusted helper/profile and unknown or held maintenance states fail closed; an absent or cleared hold permits ordinary admission. No caller override is exposed. The tool closure includes the hold module and must be refrozen to the final reviewed commit. This admission guard is not an application writer fence or database recovery adapter.

The `FILES` payload package is not a complete trusted Git tool checkout. Installation also requires a separately reviewed full Git object/bundle closure and root0700 tool clone without hardlinks/alternates/includes/gitfiles/promisor, exact tool HEAD, full fsck and source hash verification. The local producer does not establish these prerequisites.

Operational dynamic preactivate uses a **separate** schema1 `mode=operational-preactivate` binding at `/etc/workspacex-cn/operational-bindings/<app>/<attempt>/preactivate.json`, and explicit collector/verifier `--operational`. It binds exact app/tool/full FILES, source cache closure, release/attempt, baselineRevision, manifestSha256, sealSha256 and prebuildSha256. The loader revalidates the complete prior prebuild validator result, fixed canonical hold admission, and baseline from the live API compose label. Collector repeats baseline identity and retains the original target-image static smoke, real production-network read-only compatibility transaction, schema/permission/seed gates, prior lineage and TTL. This mode never changes build-only authorization and creates no migration or activation permit.

Remaining production blocker: those compatibility probes do not prove the complete exact migration ledger is applied across all three databases. The migration-completion producer is implemented as a fact-only verifier; the production recovery and activation adapters remain unimplemented, so this operational identity bridge alone is not permission to migrate or publish. A maintenance parent holding canonical FD9 cannot invoke ordinary deploy (which reopens/flocks FD9) and cannot bypass ordinary held-state rejection. A separate approved maintenance adapter must consume verified inherited FD9, exact held identity, independently verified migration-completion and recovery permits, then invoke a bounded activation implementation without ordinary lock reopening. Wrong inherited FD, absent recovery/migration evidence and ordinary held admission must reject. No such adapter is added here, and the current CLI provides no maintenance activation path.

Deploy consumes the bridge only through explicit `workspacex-cn-deploy --operational [--prepare|--rollback|--verify-active] <app> <attempt>`. The ordinary invocation keeps its legacy preactivate validator selection. No environment variable enables operational authorization and no missing-binding fallback is allowed in explicit mode. Ordinary held-state admission still rejects both modes; this flag is not the missing maintenance adapter.

The reviewed migration-completion verifier is exposed by root-only `node --import tsx <reviewed-tool-root>/packages/cloud-deploy/src/cn-migration-completion-cli.ts <sourceSHA> <attempt>`. It reads only the fixed root600 input `/etc/workspacex-cn/migration-completion-inputs/<source>/<attempt>.json`, requires safe parents, nofollow, one link, bounded stable bytes, binds raw input hash, and directly recomputes the original and completed migration plans against the fixed candidate checkout. Exact production-source identity, full provider envelope, independent SQL count/checksums and strict one-hour TTL come from the existing verifier. Its output is a fact-only witness and explicitly does not authorize production mutation. Both verifier and CLI bytes are part of the tool-source closure; a trusted tool checkout's exact dependency closure must also be independently prepared before invocation. This CLI is not a recovery proof or the still-missing maintenance activation adapter.

Before the completion CLI executes the identity helper, it verifies the fixed root700 single-link helper bytes against the external fixed root600 trusted-tool profile. The helper's `--completion-checkout` is fact-only: it reuses full reviewed tool/source-cache binding, canonical inherited FD9 verification, root/nofollow Git metadata trust, exact HEAD/full fsck and every tracked regular source blob's actual Git SHA and stable inode. Gitfiles, alternate/partial objects, include/filter configuration, writable metadata, source symlinks/hardlinks and changed bytes reject before migrator import. Git environment is sanitized again for the plan verifier's child Git calls. This does not admit ordinary releases through a held maintenance state and grants no mutation permission. A full trusted dependency closure and successful privileged CLI invocation remain separate deployment prerequisites.

## Reviewed installation and maintenance admission

The installation producer and transaction consumer use `profileTransactionsV1` for the fixed trusted-tool profile. Target and mode are derived from the reviewed Git consumer, and content binds the exact tool revision and `FILES` hashes. Fresh inventory, provider output and request identity are hash-bound inputs; missing tool commit or complete offline Git artifact rejects. Profile creation participates in the same journal and compensation as executable installation. It is not an independent write after the transaction.

Fresh installation verifies inventory against the current clock and records `admittedAt` inside the protected manifest binding and journal. Reviewed recovery first verifies the exact journal hash and matching protected binding, then verifies all current manifest, Git, payload and target checks. It validates the original inventory at the stored admission time; no caller-supplied recovery clock is accepted. Missing, altered or future admission time rejects. A foreign inode is not overwritten, even if its bytes match.

Explicit maintenance preactivate uses `--maintenance` and a fixed maintenance binding. It requires the inherited canonical FD9, exact held identity, a reviewed recovery verifier matching the tool Git object, and replay of protected recovery evidence. Evidence, profile, verifier, binding and source bytes are checked again after replay, including file identity. The ordinary release path still rejects a maintenance hold. This entry provides no migration or activation authority.

The basic trusted-tool profile does not automatically supply the additional maintenance recovery verifier binding. The production recovery verifier, complete backup-time object evidence, all-writer fencing and actual three-database recovery/activation adapters must be implemented and verified before maintenance can proceed. Local fixtures cannot establish those production facts.
