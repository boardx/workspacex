# Comment body file storage

Comment thread metadata remains in `whiteboard_comment_threads.payload`, including author/mentions, anchors, status and revision. `comments[].body` exists only in a verified immutable ObjectStore body map. PostgreSQL stores `body_object_key/body_hash/body_bytes`. Idempotency responses, which also contain historical comment text, move into immutable response blobs with `response_object_key/response_hash/response_bytes`; their old `response` is NULL after migration. Audit events contain no text and are unchanged.

Every list/dispatch/capture obtains fresh board ACL and the board row lock before disclosure or migration. ObjectStore put-once and readback size/MIME/digest checks precede PG pointer publication. An outer transaction failure leaves the original legacy row intact; any unreferenced file is handled by existing grace-period GC. Both current bodies and replay receipts are GC roots protected by the existing purge fence. A missing/corrupt pointed file fails closed and never falls back to an old plaintext copy.

Migration `20260927205000_whiteboard_comment_bodies.sql` is additive. Authorized board access and backup capture migrate all legacy thread bodies and replay responses for that board under its lock. An operator can invoke `migrateLegacyInTransaction` inside a tenant transaction with a principal authorized for that board. It is resumable and does not require two facts to be written. No production database backfill was run in this change; untouched/archived boards can still contain legacy payloads until a permitted migration is performed.

Rollback means rolling back a failed transaction or operating a version with this dual-format reader. A pre-pointer application binary cannot read migrated rows and is not a safe deployment rollback target. Do not repopulate legacy plaintext alongside pointers. Preserve the additive schema and this reader when rolling back unrelated application behavior.

Body schema is `{version:1,bodies:{commentUUID:body}}`; no board identity is embedded. Capacity follows existing `WHITEBOARD_COLLABORATION_LIMITS` (comment characters, comments per thread and bounded checkpoint bytes), not a new independent ceiling. Backup types and strict schemas live in `application/whiteboard/comment-backup-contract.ts`; metadata rejects embedded body fields. `captureBackupInTransaction` returns descriptors after verified legacy conversion. `restoreBackupInTransaction` requires a fresh empty target owned by the principal and verified target-scoped copies, rewrites boardId in thread/comment metadata, and publishes refs. Archived-object threads remain captured; their original object IDs need not still exist in a restored live snapshot. Active anchors should be checked against the snapshot by the backup service.

Object deletion/undo changes only metadata status/revision/archivedAt and must keep them aligned between indexed columns and JSON metadata. Those transitions do not rewrite the body map.
