# PROP-PROJECT-LIFECYCLE-E2E-001 — 「走完一遍」的定义：项目生命周期闭环验收标准

状态：待人类裁决
提出：2026-08-12（dev-project，人类 2026-08-12 直接下达「建立一个标准」）
实测基线：`origin/main@42f0ca21`（提案初版基线 `0d556167`；rebase 时按新 main 重核，见第 3 节表下更正）
相关：CLR（`core-loop-readiness-standard.md`，本提案设计成它的第五条 track）、#991（蓝本闭环 backlog）、#470（去 mock epic）、ADR-023

## 1. 一句话

人类要的闭环是「**新建项目蓝本 → 套用它建项目 → 把这个项目走完**」，但**今天没有任何文档定义「走完」是什么**——
CLR 的 R1–R10 管的是 chat 能力闭环（注册/agent/skill/模板/会话/录音），**项目生命周期那条没人定义过**。
定义不写死，做完也没人能判断算不算完成。本提案就是那个定义。

## 2. 为什么不另起一套评分卡

CLR 正文第 9 行逐字写着「**它不是第四套评分卡**」。本仓已因「同一事实声明在两处」漂移过五次。
所以本提案**不建立独立标准**，而是定义 CLR 的**第五条 track：P（项目生命周期可达性）**，
判据格式、评分方法、四道机械门（G1–G4）**全部沿用 CLR 既有的那套**，一条不改。

⚠ **本提案不改** `PASS_THRESHOLD`。

聚合公式按裁决（2026-08-12，第 6 节裁项 ①）改为：

```
CLR = min( R , P , mean(B, V-D, V-P) )     达标 ⟺ CLR ≥ PASS_THRESHOLD(=9)
```

**track P 与 R 同级充当天花板**，不进 `mean`。理由：人类的原话就是「把整个项目走完一遍」，
它是北极星的**直接度量**；放进 `mean` 会被三个 chat 指标稀释成不可见。

⚠ **落地时 `core-loop-readiness.ts` 才是这条公式的单一事实源**（CLR 正文第 61 行逐字规定：
「要改权重或改合成方式，改那个文件，不要在别处再写一份」）。本节这段话是**说明**，不是实现；
两处不一致时以代码为准。

### 预期后果：总分会骤降到 P 的水平

今天 P = 1/11 ⇒ 一旦并入，CLR 会从当前值掉到 **≈1**。

**这是如实，不是倒退。** 掉下去的那些分本来就建立在「项目生命周期没被度量」的空白之上。
CLR 正文第 148 行已有同款条款：「**CLR = 0 是事实，不是故障，不该把 CI 打红**」——
`--strict` 只对记录自相矛盾退非 0，分数低不退。指挥板需同步一句解释，
否则看板上的骤降会被读成「系统坏了」而不是「定义变诚实了」。

### 三条判分纪律（沿用 track R）

1. **吃种子的运行不作数**——必须空库、靠界面自己走到。
2. **「后端有端点」不给分**——判据是**用户在界面上走得到**。P1–P10 的后端契约全部已签核、
   应用层 32 个纯用例全部写好，但**零控制器、零表**，所以一分不给。
3. **未评分记 0，不记「未知」**（G1）。

### 评分操作规程（三条，都是踩出来的）

这三条不是设计出来的，是 2026-08-12 更正 P 分数时**当场踩到才写下的**。coord-main 裁定
把它们作为 track P 的正式条款（同日）。

**规程 1 —— 判「在不在 main 上」只能读内容，不能读 PR 状态，也不能读 SHA 血统。**

squash 合并会让 `git merge-base --is-ancestor <本地commit> origin/main` **假阴**（PR 明明合了，
血统检查说没有）。本次实测：#1038 已 MERGED，但本地 commit 不是 `origin/main` 的祖先。
正确做法是读 main 上的**内容**：

```bash
git show origin/main:phases/<phase>/feature_list.json | jq -r '.features[]|select(.id=="F164")|.status'
git show origin/main:apps/web/components/projects/projects-screen.tsx | grep -c archiveProject
```

**规程 2 —— 评分必须声明它所基于的 main SHA，并与 G2 联动。**

分数是**某个 SHA 上的事实**，不是永久属性。评分记录必须写明 `origin/main@<sha>`；
该 SHA 之后 `watch` 路径有改动 ⇒ 按 G2 分数过期记 0。本提案第 5 行的「实测基线」就是这个字段。

**规程 3 —— 分数变动要留更正痕迹，并禁止引用分数行本身。**

任何引用 track P 分数的文档/看板/评论，都必须**回到当时的 main 重核**，不得引用本文件某一行
——那一行写下来就不会再变，而 main 会变。这正是 `static-trace-vs-live-fact.md` 那条
「痕迹写得越诚实越具体，读起来越像权威」的直接应用：**一份不声明失效条件的分数表，
它自己就会变成新的静态痕迹陷阱。**

## 4. 可执行形态：`project-lifecycle.spec.ts`

本标准的机械载体是**一个** e2e 规格，跑在 `core-loop-empty-db`（不吃种子）那个 project 上，
**十一步一条链，前一步的产出是后一步的输入**——中间任何一步断掉，后面全部失败，这正是要的效果。

```
注册管理员 → P1 建蓝本 → P2 改环节 → P3 设档位 → P4 发布版本
   → P5 预览 → P6 建项目(带 blueprintVersionId) → P7 断言六类落库
   → P8 筹备页计数一致 → P9 推进环节 → P10 成员变更 → P11 归档转只读
```

### 为什么现在不把这个文件放进仓库

因为它今天**必然全红**（P1 就走不到）。本仓刚因「标了 passing 其实走不通」栽过
（#991 记录的七条蓝本 feature，evidence 只覆盖领域层）。放一个 `test.skip` 的骨架是同类问题：
**跳过的测试和通过的测试在 CI 摘要里长得一样。**

⇒ **落地时机**：#991 的 BP-09 完成后，作为 **BP-10** 一次性写入并要求全绿。
在那之前，track P 的分数由**人工照第 3 节表格逐项核**（与 track R 允许「devapp 上手工走一遍」同规格）。

### 反证要求（沿用本仓门控纪律）

`project-lifecycle.spec.ts` 落地时**必须同时带反证**：把 P6 的 `blueprintVersionId` 改成 `null`
（即不套蓝本），P7 的六类断言**必须变红**。否则无法区分「蓝本真的驱动了初始化」与
「项目自己长出了默认数据」——这正是 F23 当年只用纯函数单测所以看不出来的那个盲区。

## 6. 三件裁决（已裁，2026-08-12）

裁决人：**coord-main**，依人类 2026-08-11 的全权授权代裁。**人类可随时推翻任何一条。**

### ① track P 进 `min`，不进 `mean` —— 已裁

```
CLR = min( R , P , mean(B, V-D, V-P) )
```

裁决理由（逐字）：人类的原话就是「把整个项目走完一遍」，**它是北极星的直接度量，
放 mean 会被三个 chat 指标稀释成不可见**。

配套要求：总分骤降到 P 的水平是**如实而不是倒退**，提案内写明（见第 2 节末），
**指挥板同步解释**——否则看板骤降会被读成「系统坏了」。

### ② P4「试跑」移出第一版 —— 已裁

不在 track P 第一版里造新门，对齐 #991 的 createProject 单门裁决：
**「用已发布蓝本成功建出项目」（现 P6）就是这一段的验收**，试跑（applyBlueprint 预演）
留给 BP 后续批次。

⇒ 原 P4 删除、后续维编号前移、原 P5 的「未试跑时被拒」子句撤销，track P 由 12 维变 **11 维**。
（`KNOWN_CONTRACT_GAPS.T7`「什么算已试跑无出处」因此在第一版里**不必先解决**。）

### ③ 评分人 = 独立评分线 —— 已裁

照 `rev-uiux` 模式派**独立会话**按 exact SHA 评分，**实现者不自评**。

⇒ 对本提案作者的直接约束：**dev-project 不评自己做的 P 条目**（如现在的 P11 归档）。
这与 CLR 既有的 G3（`scored_by ≠ implemented_by`）是同一条，不是新规则。
