# PROP-PROJECT-LIFECYCLE-E2E-001 — 「走完一遍」的定义：项目生命周期闭环验收标准

状态：待人类裁决
提出：2026-08-12（dev-project，人类 2026-08-12 直接下达「建立一个标准」）
实测基线：`origin/main@42f0ca21`（提案初版基线 `0d556167`；rebase 时按新 main 重核，见第 3 节表下更正）
相关：CLR（`core-loop-readiness-standard.md`，本提案设计成它的第五条 track）、#991（蓝本闭环 backlog）、#470（去 mock epic）、ADR-023

## 1. 一句话

人类要的闭环是「**新建项目蓝本 → 套用它建项目 → 把这个项目走完**」，但**今天没有任何文档定义「走完」是什么**——
CLR 的 R1–R10 管的是 chat 能力闭环（注册/agent/skill/模板/会话/录音），**项目生命周期那条没人定义过**。
定义不写死，做完也没人能判断算不算完成。本提案就是那个定义。

## 2. 为什么不另起一套评分卡

CLR 正文第 9 行逐字写着「**它不是第四套评分卡**」。本仓已因「同一事实声明在两处」漂移过五次。
所以本提案**不建立独立标准**，而是定义 CLR 的**第五条 track：P（项目生命周期可达性）**，
判据格式、评分方法、四道机械门（G1–G4）**全部沿用 CLR 既有的那套**，一条不改。

⚠ **本提案不改** `PASS_THRESHOLD`，**不改**聚合公式 `CLR = min(R, mean(B, V-D, V-P))`。
track P 怎么并进那个公式（是进 `min` 还是进 `mean`），是**人类裁决项**，见第 6 节。
在裁决前，track P 只作为**独立记录**存在，不参与 CLR 合成。

## 3. track P 判据（P1–P12）

判据与 track R 同构：**把种子脚本给的前置数据全部拿掉，一个刚注册的真实管理员能不能靠产品自己的界面走到这一步。**
每维 **0 或 1 分，没有 0.5**。

| # | 维度 | 给 1 分的判据（界面动作 → 真实端点 → 可验事实） | 今天 |
|---|---|---|---|
| **P1** | 建蓝本 | 后台「项目蓝本」界面上新建一个蓝本 → `POST /blueprints` → 刷新后它还在（DB 有行，不是前端 state） | ✗ |
| **P2** | 编设计环节 | 打开设计器改任一设计环节 → `PUT /blueprints/:id/design-facets/:key` → 完成度分子 +1 且刷新后保持；分母来自定义表（禁止硬编码 15/16） | ✗ |
| **P3** | 设时长档位 | 选一个时长档位 → `PUT /blueprints/:id/duration-tier` → 议程环节数随档位变，刷新后保持 | ✗ |
| **P4** | 试跑 | 对蓝本发起一次试跑 → `POST /blueprints/:id/trial-runs` → 蓝本被标记为「已试跑」 | ✗ |
| **P5** | 发布版本 | 点发布 → `POST /blueprints/:id/versions` → 产出一个不可变版本号；**未试跑时这一步被拒**（AC3a 门真的会咬） | ✗ |
| **P6** | 套用前预览 | 建项目向导里选中该蓝本 → `GET /blueprints/:id/initialization-preview` → 预览的六类计数与 P8 实际写入**逐项相等** | ✗ |
| **P7** | 用蓝本建项目 | 向导提交 → `POST /projects`（`blueprintVersionId` = P5 那个版本）→ 跳转到新项目 | ✗ |
| **P8** | 六类初始化真落库 | P7 之后：议程环节 / 分组 / 角色分工 / 会前任务 / 材料清单 / 画布与产出物 六类**按蓝本写进 DB**，事务性（不留半成品），幂等（双击只建一个） | ✗ |
| **P9** | 项目筹备可读 | 打开项目筹备页 → `GET /projects/:projectId/prep` → 四子标签计数与 P8 实际条目数一致；不套蓝本的空项目显示**真实空态**，不生成示例数据 | ✗ |
| **P10** | 推进议程环节 | 在现场协作界面推进一个环节 → `project.advanceAgendaSegment`（该状态的**唯一**写操作）→ 刷新后状态保持 | ✗ |
| **P11** | 成员管理 | 加成员 / 改角色 / 移除 → 三个真实端点 → 变更**下一次请求即生效** | ✗ |
| **P12** | 归档退役 | 列表 ⋯ 菜单归档 → `POST /projects/:id/archive` → 项目转只读（写被拒、读仍可用），可解归档 | **✓** |

### 三条判分纪律（沿用 track R）

1. **吃种子的运行不作数**——必须空库、靠界面自己走到。
2. **「后端有端点」不给分**——判据是**用户在界面上走得到**。P1–P11 的后端契约全部已签核、
   应用层 32 个纯用例全部写好，但**零控制器、零表**，所以一分不给。
3. **未评分记 0，不记「未知」**（G1）。

## 4. 可执行形态：`project-lifecycle.spec.ts`

本标准的机械载体是**一个** e2e 规格，跑在 `core-loop-empty-db`（不吃种子）那个 project 上，
**十二步一条链，前一步的产出是后一步的输入**——中间任何一步断掉，后面全部失败，这正是要的效果。

```
注册管理员 → P1 建蓝本 → P2 改环节 → P3 设档位 → P4 试跑 → P5 发布
   → P6 预览 → P7 建项目(带 blueprintVersionId) → P8 断言六类落库
   → P9 筹备页计数一致 → P10 推进环节 → P11 成员变更 → P12 归档转只读
```

### 为什么现在不把这个文件放进仓库

因为它今天**必然全红**（P1 就走不到）。本仓刚因「标了 passing 其实走不通」栽过
（#991 记录的七条蓝本 feature，evidence 只覆盖领域层）。放一个 `test.skip` 的骨架是同类问题：
**跳过的测试和通过的测试在 CI 摘要里长得一样。**

⇒ **落地时机**：#991 的 BP-09 完成后，作为 **BP-10** 一次性写入并要求全绿。
在那之前，track P 的分数由**人工照第 3 节表格逐项核**（与 track R 允许「devapp 上手工走一遍」同规格）。

### 反证要求（沿用本仓门控纪律）

`project-lifecycle.spec.ts` 落地时**必须同时带反证**：把 P7 的 `blueprintVersionId` 改成 `null`
（即不套蓝本），P8 的六类断言**必须变红**。否则无法区分「蓝本真的驱动了初始化」与
「项目自己长出了默认数据」——这正是 F23 当年只用纯函数单测所以看不出来的那个盲区。

## 6. 需要人类裁的三件

1. **track P 怎么并进 CLR 公式**：进 `min`（与 R 同级当天花板，即「项目走不完，整体不达标」），
   还是进 `mean`（与 B/V 同级参与平均）？
   **我的建议：进 `min`。** 理由与 R 同构——项目生命周期是这个产品的主干，走不完时
   chat 体验再好也不构成「可用」。但这会立刻把 CLR 拉到 ≤1，**这是事实不是故障**（CLR 自己第 148 行
   写过「CLR = 0 是事实，不该把 CI 打红」）。
2. **P4「试跑」是否第一版必要**：`KNOWN_CONTRACT_GAPS.T7` 指出「什么算已试跑」无出处；
   若第一版砍掉试跑门，P4 与 P5 的「未试跑被拒」子句一并撤，track P 变 11 维。
3. **P 的授权评分人**：建议 `rev-e2e`（与 R 同）。
