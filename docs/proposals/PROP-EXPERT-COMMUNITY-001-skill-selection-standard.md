# PROP-EXPERT-COMMUNITY-001 附录 C — 技能入选标准：研究方法、维度与判据

> 状态：**提案 v1**（2026-09-24），待人类评审。通过后结论回流为现行标准。
> 主文档：`PROP-EXPERT-COMMUNITY-001.md`。本附录回答一个问题：**什么样的 skill 有资格进入 WorkSpaceX 的工作生态，以及它该排在哪一波**。
>
> 单一事实源分工（同一事实只写一处）：
> - **维度 id、权重、门槛、层级阈值** → `evals/skill-selection/rubric.json`（唯一数值来源；本文不写任何权重数字）
> - **来源包的健康度事实**（维护者、星数、提交、许可）→ `evals/skill-selection/packages.json`
> - **逐 skill 评分与证据** → `evals/skill-selection/scores/*.jsonl`
> - **排名、层级、能力拉动、敏感性与一致性** → 由 `evals/skill-selection/score.mjs` 生成的 `evals/skill-selection/REPORT.md`
> - 本文只定义**维度含义、打分锚点、研究流程与判定规则**。

---

## 1. 为什么需要这套标准

主方案 §6 的"直接 / 改写 / 参考"是逐包的审阅结论，有三个缺陷：

1. **不可比**：法务 skill 和营销 skill 各自说"好"，没法放在一张表里排序。
2. **不可复核**：结论写在散文里，换一个人看可能得出不同判断，无从度量分歧。
3. **混了两个问题**："值不值得要"和"现在能不能跑"是两回事——一个高价值但依赖 Python 沙箱的 skill，不应该因为今天跑不了就被判低分，它应该**拉动**我们去建 Python 沙箱。

所以本标准把判断拆成三层：**硬门（能不能进）→ 价值分 V（值不值得要）→ 就绪分 R（哪一波做）**，并用两道机械检查验证标准本身：评审员一致性、权重敏感性。

## 2. 研究流程（六个阶段）

| 阶段 | 做什么 | 谁 / 怎么做 | 产出 | 证据等级 |
|---|---|---|---|---|
| ① 普查 | 列出候选包里的每个 skill，去掉 vendored 副本 | 脚本（git ls-tree） | 候选清单 | — |
| ② 硬门 | 许可、安全、实质、合规四道门 | 自动检查 + 评审员复核 | gates 字段 | E2 |
| ③ 静态深审 | 读 SKILL.md 全文（必要时读 references / scripts），按 §4 锚点逐维打分，每维附一句证据 | 评审员（人或 agent），**每维必须附证据，无证据的分数无效** | scores/*.jsonl | E2 / E3 |
| ④ 标准自检 | 独立第二评审员对分层抽样重评；权重 ±20% 扰动 | `score.mjs` | 一致性、敏感性报告 | — |
| ⑤ 实测评测 | 对 A 层候选跑 evals：有 / 无 skill 基线对照、触发 eval、注入反例 | 平台评测 runner（主方案 C12） | 测得的质量分替换静态 Q 分 | E4 |
| ⑥ 专家签核与复评 | 领域专家试用；上游变动或线上评分下跌时复评 | 人 | 已验证徽章 | E4 + 人 |

**证据等级**：E1 只看了元数据；E2 读了 SKILL.md 全文；E3 另读了 references / scripts；E4 跑过评测。
**判定约束**：进入 A 层至少要 E2；获得"已验证"徽章必须 E4。

本轮（2026-09-24）完成 ①–④；⑤⑥ 依赖评测 runner 与专家，排在主方案 W1 之后。

## 3. 硬门（任何一道不过 = 不入选）

| 门 | 判据 | 结果取值 |
|---|---|---|
| **G1 许可** | 许可在 `rubric.json` 白名单内（对应主方案 D-EC5）；Proprietary、禁止商用、Commons Clause、无 LICENSE 一律拒 | pass / fail |
| **G2 安全** | 无凭据跨服务外传；无未经审批的破坏性或外发写操作；无未披露的联网 / 遥测；不把外部内容当指令执行 | pass / fixable（改写时可修）/ fail |
| **G3 实质** | 不是空壳（有具体步骤、模板或判据，不是只罗列问题）；不依赖专有 skill 且无替代；脚本若声称处理用户数据，必须真能接收用户输入（不是只跑内置样例） | pass / fixable / fail |
| **G4 合规** | 不冒充真实人物；法律、税务、医疗、投资等受监管领域有（或可补）免责声明与"非专业意见"边界；对人打分类 skill 有公平性约束 | pass / fixable / fail |

`fixable` 不挡入选，但改写工作量计入 R2。

## 4. 价值分 V：值不值得进入生态

V 由四组共十个维度组成，每维 0–5 分，按 `rubric.json` 的权重加权后折算为 0–100。四组对应主方案 §1 的判断：**我们的差异化在团队协作、组织上下文与可信赖，而不是 skill 数量**，所以战略契合的权重最高。

### S 战略契合 —— 它是否让 WorkSpaceX 更像 WorkSpaceX

| 维度 | 0 | 1 | 3 | 5 |
|---|---|---|---|---|
| **S1 协作闭环**：产出是否进入团队协作对象（项目、产出物、知识库、会议、任务）并在角色间流转 | 纯个人一次性问答，产出不被他人使用 | 产出是个人草稿 | 产出是团队会复用的产出物（周报、规格、审阅意见） | 读写团队对象（会议转录、项目、知识库、任务），天然在角色之间交接 |
| **S2 组织大脑复利**：是否消费或沉淀可复用的组织上下文，越用越好 | 不用任何上下文 | 每次让用户重新说明背景 | 读组织档案 / playbook / 规范 | 生成并维护受治理的组织资产（playbook、术语表、指标口径、品牌规范），有修订闭环 |
| **S3 可组合性**：能被多少个专家智能体或角色复用 | 只服务一个小众角色的罕见任务 | 单一角色 | 是某个专家智能体的核心积木 | 横向通用，≥3 个角色或专家智能体会用 |

### U 用户价值 —— 用户会不会真的反复用它

| 维度 | 0 | 1 | 3 | 5 |
|---|---|---|---|---|
| **U1 使用频率**（目标用户做这件事的频率） | 每年或更少 | 每季度 | 每两周 | 每天 |
| **U2 单次价值**（节省时间 × 决策分量） | 5 分钟以内的琐事 | 省 15 分钟的一般事务 | 约 1 小时的专业工作 | 数小时、高分量（法律、财务、投资决策或对外交付） |
| **U3 目标客群覆盖**：与我们的 ICP（中国知识型团队、投资机构、产品与研究团队、专业服务团队）的相关度 | 与 ICP 无关（例如美国个人报税） | 边缘客群 | 某一 ICP 细分的核心工作 | 多个 ICP 细分的核心工作 |

U2=2、U1=4 这类中间值允许，按与相邻锚点的接近程度取整数。

### Q 内容质量 —— 它本身写得好不好

| 维度 | 0 | 1 | 3 | 5 |
|---|---|---|---|---|
| **Q1 专业深度** | 常识复述 | 通用框架罗列 | 有领域框架与典型边界情况 | 专家级：细分立场、反例、边界情况与取舍都写清楚（例：责任上限拆成四种立场） |
| **Q2 可操作性与输出契约** | 只有目标没有步骤 | 有步骤无模板 | 步骤 + 模板 + 明确的输出格式 | 另有决策树、降级路径与分支处理 |
| **Q3 护栏** | 无 | 仅一句免责 | 来源标注、缺数据不编造、写操作确认 | 系统化：来源标签由工具结果决定、外部内容当数据、多道审批不合并、严重度下限 |
| **Q4 可测试性** | 无法判断输出对错 | 有自检清单 | 有 evals 或产物校验脚本 | evals 含断言 + 基线对照或确定性评分器 |

### H 来源健康 —— 上游靠不靠得住（包级事实，见 `packages.json`）

| 维度 | 0 | 1 | 3 | 5 |
|---|---|---|---|---|
| **H1 维护** | 已归档或超过 6 个月无提交 | 个人维护、偶尔提交 | 小团队或公司、每月有提交 | 官方厂商、每周有提交、有 CI |
| **H2 采用证据**（去刷量） | 星数与提交数严重背离（刷星或引流嫌疑） | 小众 | 有独立第三方评测或教程 | 厂商公布的装机数据，或多个独立来源的采用报道 |

H 由包级事实统一给分，避免同一个包里的 skill 被不同评审员打出不同的来源分。

## 5. 就绪分 R：哪一波做（不影响是否入选）

| 维度 | 0 | 1 | 3 | 5 |
|---|---|---|---|---|
| **R1 依赖就绪** | 依赖路线图外的能力 | 依赖 W3 运行时（Python 沙箱、Office 公式重算、SQL、调度器、浏览器） | 依赖 W2 连接器（邮件、日历、项目跟踪、CRM、组织档案） | 今天能跑：上传文件、对话、产出物、网页检索 |
| **R2 适配成本** | 需要重写 | 结构保留，正文大改 | 替换占位符、规则上移到平台 | 只改 frontmatter |
| **R3 本地化成本** | 核心逻辑依附美国法、GAAP、税制，中国场景不可用 | 大量美国法内容需重写 | 示例偏美国，概念通用 | 与法域无关 |

## 6. 判定规则

### 6.1 层级（阈值见 `rubric.json`）

| 层 | 条件 | 处置 |
|---|---|---|
| **A 核心入选** | 四门全过（允许 fixable），V ≥ A 阈值 | 导入生态；按 R 排波次；进入评测阶段 ⑤ |
| **B 候选** | V 介于 B、A 阈值之间 | 以"实验"身份进社区注册表；评测证明基线提升后才能升 A |
| **C 参考** | V 介于 C、B 阈值之间 | 不导入，只抽取结构或做法 |
| **D 不采用** | V 低于 C 阈值，或任一门 fail | 记录理由 |

### 6.2 波次（仅对 A、B 层）

| R | 波次 |
|---|---|
| R ≥ W1 阈值且 R1 = 5 | W1（零连接器即可上线） |
| R1 = 3 | W2 |
| R1 ≤ 1 | W3 |

### 6.3 同职去重（执行"同一事实只写一处"）

每个 skill 标注一个标准化的**职能族**（例如"竞品分析""风险矩阵""会议纪要"）。`score.mjs` 列出**跨来源包**的同族 A、B 层 skill，作为候选合并组：

- 族内 V 最高者标为建议的**规范版本**；
- 是否真重复由人工确认。同族不等于重复：NDA 审阅和 SaaS 合同审阅同属"合同审阅"族，但各有专门判据，应当并存；
- 确认重复的，其余版本只作为规范版本的补充材料，不单独上架。

### 6.4 能力拉动（让价值驱动路线图）

对每项尚未具备的平台能力 c，计算**拉动值**：被 c 挡住的 A、B 层 skill 的 V 之和。按拉动值降序，就是能力建设的优先级。这让主方案 §8 的路线图由数据决定，而不是由直觉决定。

### 6.5 评测后的修正（阶段 ⑤ 之后）

- 用测得的**基线提升**（有 skill 与无 skill 的通过率之差，单位百分点）替换静态 Q4；
- 提升低于 `rubric.json` 的最低阈值：即使静态分高，也降为 B 层。理由：finance_skills 实测只提升 7.9 个百分点，证明静态审阅会高估价值。

## 7. 标准自身怎么验证

| 检查 | 方法 | 合格线（`rubric.json`） | 不合格怎么办 |
|---|---|---|---|
| **评审员一致性** | 分层抽样，由独立第二评审员盲评；计算每维平均绝对差与层级一致率 | 每维平均绝对差 ≤ 阈值；层级一致率 ≥ 阈值 | 分歧最大的维度补锚点示例后重评 |
| **权重敏感性** | 每组权重分别 ±20%，重新分层 | 层级变化的 skill 比例 ≤ 阈值 | 说明结论依赖权重拍板，需人类确认权重 |
| **证据完整性** | 每个分数必须附证据字段 | 缺证据的行 = 0 | 退回重评 |

## 8. 评分记录格式

`scores/*.jsonl`，每行一个 skill：

```json
{
  "id": "kwp/sales/call-prep",
  "package": "anthropics/knowledge-work-plugins",
  "path": "sales/skills/call-prep/SKILL.md",
  "domain": "sales",
  "job_family": "会前准备",
  "one_liner": "客户会议前汇总账户背景、参会人与议程建议",
  "gates": { "G1": "pass", "G2": "pass", "G3": "pass", "G4": "pass", "note": "" },
  "scores": { "S1": 4, "S2": 3, "S3": 3, "U1": 4, "U2": 3, "U3": 4, "Q1": 3, "Q2": 4, "Q3": 4, "Q4": 1, "R1": 3, "R2": 3, "R3": 4 },
  "evidence": { "S1": "读 CRM + 日历 + 会议转录，产出会前简报供团队共享", "...": "..." },
  "capabilities": ["upload", "connector:crm", "connector:calendar", "connector:transcript"],
  "experts": ["sales"],
  "recommendation": "rewrite",
  "evidence_level": "E2",
  "confidence": "med"
}
```

H1、H2 不写在行里，由 `score.mjs` 按 `package` 从 `packages.json` 合并。

能力取值（固定枚举，定义见 `rubric.json`）：`upload`、`artifact`、`web`、`connector:crm`、`connector:email`、`connector:calendar`、`connector:chat`、`connector:docs`、`connector:pm`、`connector:transcript`、`connector:warehouse`、`connector:other`、`profile`、`python`、`office_gen`、`sql`、`scheduler`、`browser`、`subagent`。
