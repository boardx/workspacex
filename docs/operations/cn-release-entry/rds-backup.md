# Fixed RDS snapshot adapter

This adapter is locally tested, not installed or cloud accepted. It does not grant permissions.

Official contract: [RDS DescribeBackupTasks](https://help.aliyun.com/zh/rds/developer-reference/api-rds-2014-08-15-describebackuptasks) supports PostgreSQL. The request specifies the exact DBInstanceId and the CreateBackup response's BackupJobId. A Finished task returns its BackupId. [Official Python SDK request model](https://github.com/aliyun/aliyun-openapi-python-sdk/blob/master/aliyun-python-sdk-rds/aliyunsdkrds/request/v20140815/DescribeBackupTasksRequest.py) confirms POST, API version 2014-08-15 and the BackupJobId parameter. These public sources were checked 2026-10-11; no authenticated cloud request was made.

The adapter requires one exact task with matching numeric job ID, Manual mode and BackupStatus Finished, then finds that exact BackupId in all DescribeBackups pages. It also requires a successful manual full snapshot, MetaStatus OK and a current-epoch time bound. A nearby successful snapshot is never a substitute. Failed, pending, missing, duplicate or malformed task results cannot authorize switching. A backup is not an isolated restore acceptance.

## Interface

`cn-release-rds-backup.py preflight|action|observe RELEASE_APPROVAL_SHA256`

Fixed approval: `/etc/workspacex-cn/release-approvals/<SHA>.json`, kind `cn-fixed-release-approval-v1`, standard target and seven-field identity. The `rds` object contains:

- `dbInstanceId`: `pgm-uf6rg214cp381l49`
- `roleName`: `WorkspacexCnProductionEcsRole`
- `principalArn`: exact STS observed session principal
- `sdkRoot`: `/usr/local/lib/workspacex-cn/rds-sdk` (new approved installation required)
- `sdkManifestSha256`: SHA256 of fixed root-private `/etc/workspacex-cn/rds-sdk-manifest.json` (at most 1 MiB). Its exact `{kind:"cn-rds-sdk-manifest-v1",sdkRoot,filesSha256}` schema contains the complete installed relative-file-to-SHA256 map. All files and safe parent permissions are verified; extras, symlinks and inline `sdkFiles` are rejected. The release approval remains bounded to 64 KiB.
- `adapterSha256`, `holdHelperSha256`
- `permissionEvidence`: `{path, sha256}` for a root-owned independently approved capability receipt

Permission receipt kind is `cn-approved-rds-capability-v1`; exact account `1177216024653153`, region `cn-shanghai`, DB and role above; ordered actions `rds:CreateBackup`, `rds:DescribeBackups`, `rds:DescribeBackupTasks`; `approved:true` and actual `observedAt` no older than one hour. It is not generated by this adapter. A successful read does not prove CreateBackup permission.

Only these three permissions are proposed, on `acs:rds:cn-shanghai:1177216024653153:dbinstance/pgm-uf6rg214cp381l49`. They are currently missing and have not been configured by this work.

Before any consume/hold action the driver calls `preflight(approval)`: verify approved capability and complete SDK, existing IMDSv2 role plus exact STS principal, and actual read access to both Describe APIs. Action calls preflight again before creating an intent.

Inputs under `/var/lib/workspacex-cn/release-generated/<SHA>/rds-backup/`:

- `inputs/stop.json`: original sessions evidence with knownFiveStopped, zero otherDatabaseClientSessions, same holdGeneration, finishedAt within ten minutes for action.
- `inputs/hold.json`: actual held object with same source and attempt.
- `rds-request.json`: `{identity: <same seven fields>, inputHashes: {stop: <raw SHA>, hold: <raw SHA>}}`.

The router creates these root-owned private files and directory. Action uses exclusive fsynced `intent.json`; any existing intent blocks another CreateBackup, including unknown network outcomes. Original dispatch, task observations and every backup page are retained privately. Action polls only DescribeBackupTasks, every five seconds within its deadline and reader budget; no network or mutation retry is automatic. The action reader is bounded by the lesser of 1200 seconds and the original approval/release deadline remaining; the independent observer remains capped at 120 seconds. Timeout requires explicit observation/reconciliation, never another CreateBackup.

Action stdout is the normalized original `backup-receipt.json` bytes. Observe independently rereads exact task and backup, compares stable identity/status to that receipt, and returns the unchanged receipt bytes. If action died before saving this receipt, observe currently blocks; recovery of that partial-write case must be separately reviewed, not auto-replayed.

`verify(raw, manifest, previous, mode, releaseSHA)` pins the root approval and its adapter hash, checks stage `rds-backup`, previous receipt, the six core manifest identity fields and `authorizationEvidenceSha256 == releaseSHA`. The fixed root request binds all seven approval identity fields, including publicationAttemptId; it then executes the fixed read-only observer CLI. Only matching original bytes after successful independent reads produce `externalWritesTerminal:true`. It does not infer restored business availability.

## Local validation

`python3 -B -m unittest discover -s tests -p test_cn_release_rds_backup.py`

Fixtures cover lost Create response, immutable intent, input tamper, expired stop, exact job mapping, wrong job, unrelated successful snapshot, pending/failed task, missing BackupId, multi-page byte preservation, bounded read polling, deadline expiry, capability failure and independent verifier identity/output checks. These are offline tests, not successful real SDK signing or cloud backup acceptance.

Provider compatibility: DescribeBackups preflight uses supported PageSize 30; collection uses 100. Counts accept bounded decimal strings and integers but reject booleans, negatives and inconsistent page/row totals. EndTime is rounded to the next minute so a just-completed backup is not omitted. The lower time bound uses the documented provider timestamp precision (minute or second); exact task-to-backup association remains mandatory.
