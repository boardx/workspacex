# Persistent CN release continuation (#5623)

This increment provides a durable host executor and reusable, parameterized continuation generators. It is **not yet the complete one-request production release**. It does not install anything, grant permissions, or claim that the current production release completed. The existing production operator remains the only mutation owner until the exact code, cgroup capability, observers and authorization closure are reviewed and installed.

The follow-up [fixed request driver](fixed-driver.md) connects root-derived packages and the A4 held-health / separately approved A5 clear / A6 public-business sequence. It remains subject to exact installation and full-chain validation; the older finalize contract below is preserved for its original consumers.

## Failure and supervision contract

1. Status is read-only; it cannot create an attempt or claim the global owner. Capability/expiry/prior-receipt failures happen before mutation intent.
2. The controller serializes all attempts. Existing commands still acquire the **canonical release.lock themselves**; holding that lock around them would deadlock. The controller lock does not replace canonical hold admission in legacy entrypoints.
3. An exclusive intent and its parent directory are fsynced before execution. Child `setsid` sends READY; the parent confirms the session, attaches it to the fixed cgroup, fsyncs the process record, then releases the execution gate. Parent death before this handshake cannot release a later mutation.
4. Production requires a preinstalled root-controlled **Linux cgroup v2** subtree at `/sys/fs/cgroup/workspacex-cn-continuation`, including `cgroup.kill`. Each operation uses its own child cgroup. Ordinary daemonization/setsid cannot escape that kill domain. Trusted actions must not manipulate cgroup membership. No CLI option disables this requirement.
5. Kill and join only establish local termination. Docker/RDS/OSS may already have accepted work. Every successful forward action also needs an independent observer whose reviewed verifier explicitly establishes `externalWritesTerminal: true`. Reconciliation uses that same mandatory condition. Unknown results retain the intent and block new writes; no automatic retry or rollback.
6. Recovery is separately approved with scope `runtime-only-reviewed-recovery` and `recoveryOf` pointing to the original request. It requires original local execution terminal plus a fresh independent observer proving safe recovery. Its final verifier must establish all of `baselineBusinessAccepted`, `holdCleared`, `externalWritesTerminal`. A recovery receipt never becomes a normal forward receipt.
7. Partial evidence/receipt writes, missing process records, different package hashes and changed attempt identities fail closed. A malformed final receipt cannot release another attempt. Recovery authorization cannot be inferred from an expired normal request.

The CLI accepts exactly `MODE REQUEST_SHA256 ATTEMPT`, from the fixed installed pathname, and verifies its own bytes against a protected installation seal. `advance`, `reconcile`, `status`, `recover`, and `reconcile-recovery` are explicit operations. Only the root installer can create the protected request and verifier package. `action.sh`/`verify.py` supplied by `ghrunner` do not confer authority.

## One approval versus stage packages

The stage package executor is the foundation, not the desired permanent manual procedure. The intended owner of package creation is a fixed, approved root generator that derives each next stage from the original release authorization and actual preceding receipts. Users should not have to approve unchanged scope at every step.

The current generator adapters parameterize acquire/publication, four normal runtime phases and final status/clear. Their CLI authority comes only from protected approvals. `cn-release-derived-approval.py` now derives approvals for the four runtime phases from one protected exact release delegation and hash-bound validated journal; it verifies the actual materializer before publishing. The root journal projector now derives four-phase readiness from the full immutable entry chain. Acquire/finalize/recovery derivation and the full-chain driver are not yet connected; until a whole-chain generator and trusted live receipt/observer producers are connected and tested, missing stages must block admission. Do not substitute a runner-generated `hasApproval: true`, arbitrary verifier or handmade business receipt.

## Scenarios and mandatory gates

| Scenario | Reused route | What cannot be skipped |
|---|---|---|
| Hotfix, no schema diff | Same exact-source runtime-only route with scheduling priority | Startup side effects disclosure, actual preceding receipts, current-epoch backup, terminal observers and business acceptance |
| No schema diff, ordinary release | Consume → canonical publish → hold → exact stop → session observation → host/RDS backup → switch → held health → separately approved A5 clear → A6 six journeys and stable public observation | Empty SQL diff is not proof of no writes: API startup cleanup/seed/task recovery remain relevant |
| Prepared candidate | Reuse already admitted exact artifacts and receipts, still verify freshness and source/baseline identity | Never reset the original requestedAt to hide build or waiting time; report activation duration separately |
| Cold release | Include producer plan, five parallel jobs and final collection before transfer | Build/collect, authentication, transfer, waiting and failures all count toward calendar lead time |
| Schema/data migration | Existing seven-step A0–A6 route | This runtime-only binder rejects it; backup, isolated restore, migration/readback and separate writer approval remain mandatory |
| Recovery/rollback | Original identity plus fresh, separately scoped authorization and actual terminal observations | Budget expiry must not prevent safety recovery; it must not restart the successful-release timer either |

## 30-minute budget and authentication readiness

`requestedAt` and `deadlineAt` are immutable release identity fields across every stage, process restart and receipt. The interval is at most 30 minutes. Normal stage expiry cannot exceed that deadline; the supervisor uses the remaining time. Receipts report full elapsed time and switch/activation elapsed time separately. Crossing the budget means a failed timing target, not permission to remove validation. Fresh recovery has its own bounded safety window while retaining the original requestedAt and over-budget measurement.

Before expensive build/transfer, readiness must include an **actual successful OIDC/STS read-only exchange** for the exact GitHub environment/role/audience, usable exact object policy, live Shanghai runner, installed closure/cgroup support and RDS backup/read capability. Static trust JSON, token presence, prior-day success or `OTHER` alone are not enough. Fixed error stage/status/public category and bounded unknown-code fingerprint must survive redaction so failure does not require speculative IAM changes and repeated full CI cycles. This readiness integration is not completed by the stage transport; absent fresh evidence remains a release blocker.

One real build sample is available: GitHub run **38146134231**, created **2026-10-11T14:10:50Z**, final collect completed **14:18:10Z**: **440 seconds / 7m20s**, including collect (**113s**). Parallel job durations: plan 21s, API 164s, Web 290s, sandbox 296s, Agent 83s, Postgres 122s. The seven original ZIPs total **3,825,900,817 bytes**. This measures only the build segment, not cloud transfer or release. The continuing user-request calendar has already exceeded 30 minutes and is a failed sample; diagnosis/approval/CI time must not be subtracted to relabel it successful.

The original publication contract requires at least 20 minutes remaining. Therefore a cold pipeline must finish build, authentication and initial transfer before the first ten minutes to fit a 30-minute request window. This is a concrete bottleneck to measure and optimize; this patch does not silently lower that existing contract.

## Verification and installation boundary

Run the focused suites:

```bash
python3 -I -B -m unittest discover -s tests -p 'test_cn_release_entry.py' -v
python3 -I -B -m unittest discover -s tests -p 'test_cn_release_continuation_*.py' -v

```

Entry tests use real forked processes, parent death, persistent journals, timeouts and fresh-process reconciliation. Their disposable fixture disables the Linux kill domain only through an imported-library seam; production has no such switch. They are **not** a real Linux cgroup acceptance test. `tests/cn_release_cgroup_linux.py` is a separate required CI step: it creates one exclusive temporary root-owned subtree, exercises a real setsid descendant and timeout, verifies no late write, and removes only that subtree. Capability absence exits nonzero; it is not a skipped passing test. Its actual CI result must be recorded before claiming Linux supervision verified. Template integration exercises real canonical seven-ZIP verification and original materializers, but does not run production Docker/RDS or public business journeys.

Generate a non-executing install proposal with `scripts/cn-release-orchestrate.py installation-plan --probe <actual-readonly-probe.json>`. It names exact new entry hash, root paths/modes, installation seal, one narrow sudo rule and cgroup requirement. Unknown old state is marked unverified, never guessed absent. The final installation must CAS actual old state, preserve recoverable prior bytes, validate sudo syntax, check the complete tool closure and prove cgroup cleanup with a setsid descendant. No bootstrap, sudo edit or IAM change is performed by this PR.

Production blockers still include the exact approved installation, Linux cgroup test, root derivation wiring for the whole chain, independently implemented terminal/business observers, live auth/permissions, and a real release with measured public acceptance. The task must remain open until these are delivered; this code is not evidence that production is available.

### Persistent observation chain (follow-up)

Normal forward/reconcile receipts additionally bind the exact independent observer bytes with `terminalObservationSha256`; `.terminal-observation.json` preserves those bytes separately from action stdout. Read-only status and an idempotent completed call verify both stored evidence files before returning completed. The root journal projector validates every intermediate stage, its protected package, process terminal evidence, original action and observer hashes, and approved stage verifier before projecting business phases for approval derivation.

A crash after immutable evidence is written but before its receipt can leave a partial completion. If fresh reconciliation produces different bytes (for example a new observation timestamp), the entry preserves the original evidence and blocks with `EVIDENCE_CHANGED` or `TERMINAL_OBSERVATION_CHANGED`. It does not overwrite history or replay the action. This case still requires a separately reviewed repair/recovery transaction; automatic recovery of arbitrary partial evidence is not implemented. The failure-injection test records this limitation explicitly.

The projector also binds dynamic inputs to the exact verified stage output bytes, and binds authorization/template/migration inputs to the once-approved hashes and release identity. It refuses unrelated hand-prepared input files. Backup actions emit a summary rather than the full backup-result bytes required by the binder. The fixed `cn-release-runtime-readback.py` now verifies the actual result, manifest, configuration backup and tar hashes under the canonical lock and checks the live hold before/after. The journal consumes its exact independently observed result bytes for `hostBackup` and pins every stage observer. Production still needs the reviewed stage package/approval generator to wire that observer; installing the projector alone does not execute a release.
