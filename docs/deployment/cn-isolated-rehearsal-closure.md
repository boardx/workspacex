# Target-bound isolated rehearsal entrypoint

This entrypoint performs no instance purchase and cannot activate production. The coordinator must supply an approved, already created isolated provider instance and reviewed root-private execution manifest. `pgm-uf6rg214cp381l49` is always rejected as a target. Missing stage inputs fail preflight, rather than becoming a successful receipt.

```sh
python3 .harness/scripts/vm/isolated_rehearsal.py ROOT_MANIFEST_PATH EXACT_MANIFEST_SHA256 --preflight
python3 .harness/scripts/vm/isolated_rehearsal.py ROOT_MANIFEST_PATH EXACT_MANIFEST_SHA256
```

The manifest binds attempt UUID, provider ID, actual creation UTC, actual endpoint and IPv4/hash, frozen source manifest path/hash, and candidate SHA. Default TLS is `verify-full`; a disabled-TLS exception additionally requires independent approval and new target-specific provider evidence, and the Aliyun adapter checks current provider SSL state again. No old target, password, TLS exception, backup checksum or candidate source is silently inherited.

Stages run in order: provider attestation → cleanup registration and exact template readback → create-once isolated account/readback → three-database preparation and CMS restoration → three before proofs → main migrations → canonical Python setup → canvas audit → three after proofs → encrypted snapshot → recovery verification → exact deletion/NotFound → cleanup registration removal. Provider observation repeats before each SQL-bearing stage. Deletion starts with five minutes reserved and OOS starts at creation +115 minutes; the maximum authorized use is two hours. OOS independently remains the deadline backstop on host failure.

Each mutating stage writes an fsynced private intent before invocation and a create-once receipt afterward. Unknown account/OOS results reconcile only through readback. Unknown restore or migration results stop and preserve the intent; they are never submitted again automatically. Root-private independent credentials are generated once with mode0600, never taken from production and never passed on command lines. Stage stderr and raw provider errors are suppressed; only bounded receipts are accepted. Adapter process groups receive SIGTERM then bounded SIGKILL on timeout; restoration and SQL/snapshot supervisors clean only containers and networks carrying their unique ownership labels.

The runnable Aliyun adapter reuses round-one IMDSv2 and signed RPC, but parameterizes the isolated target. OOS `GetExecutionTemplate` is used to compare the actual template structure with the exact target/deadline/role, not merely rely on an execution ID: [official API](https://www.alibabacloud.com/help/en/oos/developer-reference/api-oos-2019-06-01-getexecutiontemplate). Only exact structured `InvalidDBInstanceId.NotFound` is accepted for RDS deletion; permission/network errors remain failures.

The CMS restore adapter verifies client image ID/architecture, API client source label, backup receipt and ciphertext hashes, recipient certificate/key match, target-owned network, actual TCP peer, empty target database, source database owners/ACL/locale and all three databases. It streams decryption into pg_restore without writing a plaintext archive. Actual memberships are checked absent before temporary SET grants; after restoration only the exact grants created by this attempt are revoked with their observed grantor/flags, then a fresh provider observation and original-archive COPY/sequence fidelity proof are produced for every database. It reuses the reviewed round-one target-account/bootstrap and target-restore/database-preparation patterns; original scratchpad scripts are not installed or rewritten by this change.

## Manifest preparation and remaining gates

Every stage entry has a trusted script path, exact SHA256 and bounded timeout, and consumes stdin `{binding,secret,operation,previousReceipts,providerObservation}`. Imported modules are explicit hash-bound siblings copied into the same private executable snapshot. `previousReceipts` supplies hash references to actual earlier producers, including dynamic restore `baselineProofRefs`; no unknown future proof hash is hand-filled into a frozen manifest. It must produce `{accepted,targetInstanceId,attemptId,candidateSha}`; restore/before/after/snapshot/recovery additionally cover exactly workspacex, workspacex_agent and workspacex_memory. These are real producers, never handmade replacement receipts. Root must install/review all conservation, migration, canonical setup, canvas, snapshot and recovery adapters and bind them to the frozen source before preflight can pass. A single root-private stage manifest uses `stages` for every operation and binds attempt/target/candidate. The canonical migration engine verifies all actual image SQL bytes against a frozen inventory, derives pending work from the real restored ledger, and calls the actual migrator twice with `force:false`. Canvas SQL is transactionally replayed and rolled back; its hash covers the final expanded migration bytes. Snapshot streams three database dumps directly into CMS ciphertext. Recovery verifies CMS integrity, archive table rows and sequence values against the still-isolated databases using the reviewed digest-only streaming engine; it does not restore over a live database.

The restore manifest also supplies immutable three-backup receipt/ciphertext references, client/API images, exact database helper, `tls.ca={path,sha256}` and recipient certificate/private-key references and an independently verified fresh read-only source database-spec receipt. Cleanup IAM role/policy installation is a coordinator prerequisite. The manifest binds exact attempt-specific names and canonical trust/policy hashes. Before OOS registration the adapter reads the actual OOS-only trust, exact single-clone delete policy and exclusive attachment. After verified instance NotFound and OOS cancellation terminal, it detaches and removes only that policy and role; actual GetRole/GetPolicy NotFound is required before acceptance. Other temporary account/bootstrap policies must be removed by the coordinator and retained in the canonical cleanup receipt. The adapter never provisions broad IAM permissions or passes a GitHub administrator token.

Prepared scripts and fake-provider tests do not establish release readiness. Actual provider/peer attestation, restoration fidelity, fresh source/ledger plan, canonical setup, three-database conservation, encrypted recovery, deletion and IAM cleanup receipts are mandatory. No source/pending migration count is inferred from an old ledger.

Verification: `python3 -m unittest discover -s .harness/scripts/vm -p isolated_rehearsal_test.py`; the Vitest wrapper includes all isolated Python suites and portable Node negative cases in repository CI. Counterexamples exercise a real Node validator and real local subprocess timeout, besides deterministic provider failures. No tests purchase an instance or connect to a database.

Prepared unit fixtures initially used the real300s deletion readback default for an intentionally missing fake response. That fixture defect was corrected to explicit zero test budgets and dedicated first-false/then-true polling tests; production deletion retains its independent300s bounded budget. Local tests are not actual rehearsal readiness.

## One-shot input assembly

The coordinator binds an approved created target to a reviewed stage template through `isolated_rehearsal_prepare.py REQUEST_PATH REQUEST_SHA256 PRIVATE_OUTPUT_DIRECTORY`. Request JSON supplies `binding`, a hash-bound `stageTemplate` and `reviewedModules:{basename:{path,sha256}}`. The builder derives transitive module maps from actual verified Python AST imports and writes both manifests create-once as root0600. A previous target/attempt template is rejected; failed validation removes only files created by this invocation. The request contains no passwords; isolated credentials are generated later after actual OOS readback. The outer binding includes every explicit executable module map; `preflight` checks transitive `isolated_*` imports against those copied bytes. It reads and hashes all nested stage references, final SQL/law plans, canonical setup resources, backup receipts and streaming ciphertext checksums. It rejects draft plans, old candidate image declarations, a missing source resource or a public-readable CMS key. This check performs no cloud call or SQL. Its successful result is `preparedInputClosure`, not provider or release acceptance.

The root input builder must obtain actual immutable candidate API and Python images, source-built metadata and fresh protected canonical receipts before marking the template prepared. A candidate API image can be prebuilt without activating services. The image's actual OCI revision is checked again by each live supervisor. Historical fixture JSON is never substituted for those inputs. Both migrate and canvas plan use `sourceSqlInventory:[{name,sha256}]` and `canonicalMigratorSha256`; they must equal the conservation plan's full SQL map. All stages share `stageManifest.stages`; snapshot, recovery and restore fidelity share the exact same recipient key path.

Before purchase, verify the target-neutral template's source, images, complete reviewed transformation laws, three encrypted backups, source database/role spec, canonical resource closure, install file hashes and dedicated cleanup IAM template are already available. After creation, bind only actual provider ID/time/endpoint/peer and attempt, never an old clone identity. Register and read back OOS before account creation/SQL. A final frozen source change invalidates all candidate-bound inputs and requires rebuilding that input set; no count-only patch is permitted.

Before clone purchase, the same builder accepts `REQUEST_PATH REQUEST_SHA256 --review-template`. It checks a target-neutral frozen template and all referenced bytes/transitive modules without creating manifests or inventing an instance ID. Its result deliberately says only `reviewedInputBytesAvailable`, `targetBindingRequired:true`, `liveAccepted:false`. This is one pre-purchase input check, not authorization to buy a clone, an assertion that runtime images exist, or SQL conservation acceptance. The coordinator separately verifies actual local image/provenance inventory and IAM installation.

Offline semantic admission reuses the actual hashed database helper's validation, the authoritative canonical plan factory and JavaScript JSON serialization for reviewed law body hashes. It checks all five canonical sources and the real source/extractor/runtime JSON contents, derives both secondary database plans again and requires exact bytes, checks CMS key/certificate pairing with OpenSSL and compares every recipient, and binds canvas SQL/migration bytes before any cloud write. Node and OpenSSL are local tool prerequisites; Node's resolved executable/ancestor ownership is checked. Provider, OCI metadata, live roles/peers, archive SQL data fidelity and cleanup remain actual runtime gates and cannot be inferred from offline tests.
