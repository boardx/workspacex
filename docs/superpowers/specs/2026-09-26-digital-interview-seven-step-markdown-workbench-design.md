# 数字访谈七步 Markdown 工作台设计

**日期：** 2026-09-26  
**状态：** 待人工审阅  
**范围：** `apps/web/app/itv`、`apps/web/components/itv`、数字访谈 API 与 `packages/contracts`。

## 目标

把当前“主题、专家、问题、访谈、报告”五步访谈页重组为图片所示的七步工作台：需求导入、AI 分析、专家选择、专家提纲、开始访谈、汇总报告，并从访谈列表进入。

每个 AI 生成步骤都必须产生一个人可读、可复制、可导出的 Markdown 产物。用户既能在当前步骤审阅和确认它，也能在最终报告中回溯它的版本、生成状态和来源边界。

## 非目标

- 不把 Markdown 作为专家、问题、回答或证据 ID 的唯一数据源。
- 不删除现有真实受访者证据、人工审批、失败恢复和 Word/PDF 导出能力。
- 不改变数字专家为模拟研究样本、不能替代真人访谈的产品边界。

## 用户流程与界面

### 0. 访谈列表

列表页保留现有搜索、状态与历史能力，卡片改为显示当前进度、研究主题、样本数量、模拟/真人证据比例、最近的 Markdown 产物更新时间。主操作是“继续访谈”或“查看报告”；新建操作进入步骤 1。

### 1. 导入需求

用户通过文本、粘贴内容或已有附件输入研究背景与目标。输入区旁展示可接受的材料类型、材料边界与隐私提示。提交后形成 `需求说明.md`；未上传文件时，文本也会形成同样的 Markdown 文档。用户必须确认需求说明后才能触发 AI 分析。

### 2. 确认分析

页面采用原型中的四宫格：研究目标、建议访谈方向、目标人群、预期产出。左侧为可编辑的 `研究分析.md` 预览，右侧以可操作摘要呈现对应条目。确认会锁定该分析版本并生成候选专家，不确认则以新版本重新生成，旧版本仍可查看。

### 3. 选择专家

双栏布局：专家库支持搜索、筛选与查看完整画像；已选区显示角色覆盖、重复角色提示与样本缺口。模型推荐的理由以 `专家建议.md` 呈现，每一位候选专家仍使用稳定的 `expertId` 供后续提纲、访谈和引用使用。

### 4. 专家提纲

左侧是已选专家，右侧是按专家分组的可折叠访谈提纲。AI 生成的提纲保存为 `访谈提纲.md`；用户可修改、增加问题或删除问题。确认时保存结构化问题版本，同时保存与其对应的 Markdown 版本。

### 5. 开始访谈

显示当前专家、已完成问题数、访谈状态、关键记录和切换专家动作。每一个回答继续保存结构化事实（专家 ID、问题 ID、回答、时间），并追加到 `访谈记录.md`。进行中、部分完成、失败与恢复均必须可见；失败后的重试只能补齐未完成段，不覆盖已保存回答。

### 6. 汇总报告

报告首页按原型展示关键指标、模拟与真人证据覆盖、关键洞察、风险提示和建议行动。主体为 `访谈报告.md`，支持逐条回到原始回答；Word/PDF 导出必须包含完整 Markdown 内容、证据边界和生成时间。证据不足时仍可生成探索性报告，但不能显示为已批准的决策结论。

顶部进度条始终显示 1–6 的当前状态、可安全返回的已完成步骤与需要确认的草稿步骤。桌面端优先采用原型的工作台布局；窄屏下切换为纵向步骤导航，不丢失关键操作。

## 数据与 API 契约

新增单一的“步骤产物”模型，避免在每一个业务对象上重复定义 Markdown 字段：

```ts
type DigitalInterviewArtifact = {
  artifactId: string;
  step: "intake" | "analysis" | "experts" | "outline" | "runs" | "report";
  title: string;
  markdown: string;
  version: number;
  status: "draft" | "confirmed" | "generating" | "failed" | "completed";
  generatedAt: string | null;
  failure: { code: string; retryable: boolean } | null;
  evidenceMode: "simulated" | "participant" | "mixed";
};
```

`DigitalInterviewWorkflowView` 返回按步骤索引的产物清单，以及当前结构化实体：专家、问题、访谈回答和报告发现。API 对每次生成、确认或重试都返回更新后的工作流视图，因此前端不会依赖临时本地 Markdown。

AI 返回内容的约束是“结构化结果 + 规范 Markdown 产物”而不是让前端从 Markdown 解析业务事实：

- 结构化结果确保稳定的对象标识、权限检查、版本冲突检测和原始回答引用；
- Markdown 是用户可见的研究文档、导出源和版本审阅对象；
- 模型调用失败时，已完成的 Markdown 片段、状态及重试入口必须被持久化；
- 下游重生成创建新产物版本，不能静默覆盖已确认版本。

## 组件边界

- `digital-interview-workbench.tsx`：页面外壳、七步导航、当前步骤状态和未保存变更保护。
- `digital-interview-artifact-panel.tsx`：统一渲染 Markdown、版本状态、复制、导出与失败重试。
- `digital-interview-intake-step.tsx`、`analysis-step.tsx`、`expert-selection-step.tsx`、`outline-step.tsx`、`run-step.tsx`、`report-step.tsx`：各步骤的领域交互。
- 保留 `interview-report-markdown.tsx` 为 Markdown 渲染的唯一实现，避免出现第二套解析和样式规则。

现有巨型流程组件将按这些职责拆分；所有关键操作都保留稳定的 `data-testid`。

## 错误、可用性与证据边界

- 生成中显示骨架、阶段名和可安全离开的说明；禁止只显示无限 loading。
- 失败状态显示可理解原因、是否可重试、已保存内容以及下一步操作。
- 每个编辑中的 Markdown 草稿在切换步骤或离开前均使用现有未保存更改确认机制。
- 焦点顺序与键盘操作覆盖步骤导航、专家搜索、问题编辑、生成、重试和导出。
- 模拟证据必须在每个 Markdown 产物和最终导出中明确标示；报告批准能力继续由真实受访者证据规则决定。

## 验收与验证

1. 新建访谈可从需求输入走完七步，并在每个 AI 步骤看到对应 Markdown 产物。
2. AI 重新生成创建新版本，确认过的版本及其结构化对象仍可回看。
3. 专家、问题、回答和报告可在 Markdown 与原始结构化事实之间双向定位。
4. 报告生成中断后刷新页面，已生成 Markdown 与重试状态保持；重试不清除完成内容。
5. 模拟研究不具备真人证据时，报告与导出显示探索性/待验证边界，审批仍被阻止。
6. 单元与 UI 测试覆盖七步导航、确认、重试、版本和导出；完整浏览器 E2E 覆盖从需求到报告的主路径。
