# ADR-112：本地版的存储与同步——不用 Yjs 当存储层

- 状态：已决定（2026-09-23）
- 起因：人类问「能不能用 Yjs 来做 local 的存储，这样联网之后就能把内容同步上去」
- 决定人：本 ADR 的结论由 agent 依据实测与公开资料给出，人类可推翻

## 决定

**不用 Yjs 作为本地版的存储层。** 本地版继续用 PGlite。

Yjs 在本仓只有一个合理位置：**真正的协作文档内容**——富文本正文、画布几何、评论草稿
这类「多人同时编辑同一块自由内容」的字段。做法是关系行仍存 PGlite（id、owner、org、
权限、外键），行里放一个指向 Y.Doc 的引用，**一行一个 Y.Doc**，由 PGlite 那侧的 RLS
决定是否下发该 doc 的令牌。这样 Yjs 的「文档级授权」粒度恰好和「一行」对齐。

「联网后同步」是另一个问题，**不靠换存储引擎解决**，见下面第三节。

## 为什么不行（判据，不是偏好）

本地版的库是**完整关系型 schema**，实测数字：

| 项 | 数量 |
|---|---|
| 迁移文件 | 267 |
| 表 | 246 |
| 启用 RLS 的表 | 177 |
| 外键 | 518 |

对着这四个数字，Yjs 有三条硬伤：

1. **行级授权在 Y.Doc 内部原理上做不到。** Yjs 官方 FAQ 自己写着权限无法在一个 YDoc
   内部切分，要不同权限就得拆成多个 YDoc。而 RLS 是**行级**授权、Y.Doc 的授权粒度是
   **整篇文档**。177 张 RLS 表要保住语义，就得按（租户 × 表 × 行策略）切 Y.Doc——
   而同一份 FAQ 又警告不要一次加载成百上千个 YDoc。两条约束直接对撞。
   <https://docs.yjs.dev/api/faq>
2. **没有 schema、没有索引、没有联表、没有聚合。** 518 个外键的引用完整性要在应用层
   手写重建，而 CRDT 的并发语义恰恰会制造悬空引用：一端删父行、另一端加子行，
   两边都「合并成功」。<https://rxdb.info/articles/alternatives/yjs-alternative.html>
3. **更新日志不会自己消失。** `Y.mergeUpdates` 不回收已删内容，GC 只在装载进 Y.Doc 时
   发生；而要做版本快照就必须关 GC。社区实测过一份未 GC 的大文档，开 GC 应用耗时
   38 秒、关 GC 1.6 秒。<https://github.com/yjs/yjs/issues/541>
   <https://docs.yjs.dev/api/document-updates>

换句话说：PGlite 已经免费给了 SQL、外键、RLS 和 267 个迁移。换成 Yjs 是把这四样全丢掉
再手写回来，而其中 RLS 那一条**写不回来**。

## 「联网后同步」该怎么走

先把问题拆成两问，不要一次要全部。

| 方案 | 2026-09 现状 | 对本仓是否可用 |
|---|---|---|
| ElectricSQL | **只做读路径**，写路径要自己实现。2026-08-11 加入 Databricks，Electric Cloud 正在关停。**PGlite 与 Electric 同属一家，现同属 Databricks** | 只读同步可用；要自托管 |
| PowerSync | Postgres ↔ 本地 SQLite，Sync Rules 同时充当授权边界，是最接近 RLS 语义的机制，**支持离线写** | 可用，但本地要从 PGlite 换成 SQLite——对 267 个 PG 迁移是重大工程 |
| Zero（Rocicorp） | 1.0 于 2026-06 发布，用现有 PG schema，但**明确不支持离线写** | **出局**：本地版的全部意义就是离线 |
| Triplit | 2025-10 被 Supabase 收购，站点已停放 | 不押注 |
| cr-sqlite / vlcn | 表级 CRDT 的 SQLite 扩展，周边维护停在 2024-10 | 要换掉整个本地引擎 |
| Automerge | 与 Yjs 同类，关系型问题一个没解决 | 同 Yjs |
| PG 逻辑复制 | 面向常在线多主集群，不面向「笔记本关机三天」；**PGlite 不是完整 PG 服务端，当不了复制节点** | 不可用 |
| **导出 / 导入 + 冲突由人解决** | 最土最稳 | **建议的第一步** |

**建议的第一步是导出/导入**，理由有三：它立刻消除「切到在线只是打开个网页」这个事实
缺口；它不赌任何一家正在被收购的公司；它让我们先拿到真实的冲突分布，再决定要不要上
同步引擎。等真实数据证明冲突频繁且人工解决不了，再考虑 PowerSync。

## 如果以后真的要做同步，这些坑先记下

- **绝不要用 wall clock 做 LWW**：离线端时钟漂移会静默吞写入，要用 HLC / Lamport。
- **租户隔离必须是同步的分桶边界**，不能同步完再过滤——否则未授权数据已经落到对方磁盘。
- **schema 迁移是最痛的点**：离线端可能停在 N-5 版本，同步协议必须版本化。
- **首次同步不能全量**：246 张表全量首同步不可接受，必须按租户 + 时间窗做部分复制。
- **端到端加密与服务端同步相互矛盾**：服务端加密就无法做服务端授权校验与分片过滤，
  二选一，别两边都承诺。
- **CRDT 只在「变更可表达为静态 JSON 操作」时成立**：需要人判断才能正确合并的状态
  （审批、结算、库存扣减），CRDT 会自动收敛到一个没人想要的结果，这比报错更糟。

## 诚实的边界

- 没有查到一手的「我们把 CRDT 用在关系型业务数据上然后后悔了」的工程复盘。上面第 2 条
  的依据是论证性材料，不是事故报告。
- 官方 FAQ 说体积「很少成为实际问题」，而社区实测帖反复出现大文档的性能悬崖。两者都对：
  官方说的是人手输入的文本，我们要装的是业务表。这正是边界所在。
