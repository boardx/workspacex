# ADR-107: harness 控制平面代码量精简 —— H3A 冻结 + pr-queue/merge-gate 合并 + doctor 框架收敛

- 状态: Proposed（需人类/coord-main 确认后转 Accepted；本 ADR 本身不改任何代码，
  执行拆为独立 issue，一个 issue 一个 PR，逐条过 CI）
- 适用层：方法论（可移植）
- 日期: 2026-08-17

## 背景

人类看到"全项目约 44 万行代码，`.harness/` 控制平面本身接近 3 万行"这个数字后，
指出这个量级"太复杂了"，要求一个完整的精简方案。

**实测拆解 `.harness/scripts/` 约 3 万行的构成**（不是猜测，逐项查过）：

| 板块 | 行数 | 真实使用情况 |
|---|---:|---|
| H3A 治理机器（task-assignment / workflow-event / review-decision / domain / role-authorization / role-freeze / graph 相关文件） | **5,366 行**（约占 18%） | `.harness/tasks/` **0** 个实例、`.harness/reviews/` **0** 个、`.harness/events/` 仅 2 个、`.harness/domains/` 仅 1 个 |
| 19 个独立 `lint-*` doctor 脚本 | 数千行，散在 19 个文件 | 每次 `verify:base` 都跑，各自重复一套 CLI 接线 + 日志格式样板 |
| `pr-queue.ts` + `merge-gate.ts` | 345 + 151 = 496 行 | **本会话亲历的真实重复**：2026-08-16 一天内为同一套"独立 approve + verdict label + Closes #N"判据，在两个文件里同步改了三轮（PR #1442/#1463/#1477），每次都要同时改两处、写两份测试 |

最大的单一发现：**H3A 那套治理机器为一个还没有真正跑起来的流程（Epic E3 任务分配）提前建了一整座工厂**——5,366 行代码，生产里几乎没有真实数据支撑（0/0/2/1 个实例）。这不是"代码写多了"的泛泛问题，是可以指名道姓的具体板块。

## 决策

**分三阶段，不做一次性大重构**——每阶段独立评审、独立验证，任一阶段可以单独暂停而不影响其余阶段：

### 阶段一：冻结 H3A（风险最低，收益最快，优先做）

不删除代码（Epic E3 未来可能真的要用），但把 H3A 相关的 7 个 lint doctor
（`task-assignment-doctor` / `workflow-event-doctor` / `review-decision-doctor` /
`domains-doctor` / `role-authorization-doctor` / `role-freeze-doctor` /
`graph-authority-doctor`）从 `verify:base:raw` 的强制链条里摘出，改成按需
手动跑（`pnpm harness <name> doctor`）的独立命令，不再是每次全量验证都背负
的固定成本。

**验收标准**：
- 摘除后 `verify:base:raw`/`verify:harness:raw` 仍然覆盖所有"有真实实例"的检查
  （即当前唯一有 2 个实例的 `workflow-event-doctor`，需要单独评估是否保留在
  强制链里，还是随其余六个一起摘出——由执行 issue 决定，不在本 ADR 预先拍板）。
- 每个被摘除的 doctor 命令本身完全保留、可独立运行、文档说明"何时该手动跑"。
- 反证：验证 Epic E3 真的开始产生 `.harness/tasks/` 实例时，摘除不会阻止随时
  把对应 doctor 重新接回强制链——摘除是可逆操作，写清楚怎么接回去。

### 阶段二 a：合并 `pr-queue.ts` + `merge-gate.ts`

两者本会话已证明高度重合（同一套判据的两份实现，`merge-gate.ts` 部分代码
直接 `import` 自 `pr-queue.ts`）。合并为一个模块，`merge-gate` CLI 变成对
`pr-queue` 判定结果的一层"只看这一个 PR、退出码语义"的薄包装，而不是重新
实现一遍规则。

**验收标准**：
- 合并后两处（原 CLI `harness pr-queue --pr N` 与 `harness merge-gate --pr N`）
  的输出结论对同一个 PR 必须完全一致——这本来就是本会话 PR #1463/#1477 强调
  过的目标，合并后应该是结构性保证，不再需要"改一处记得改另一处"的纪律。
- 现有 46+31 个测试用例（`merge-gate.test.ts` + `pr-queue.test.ts`）合并后
  不丢失任何一条反证覆盖，允许合并成一个测试文件。

### 阶段二 b：19 个 lint-doctor 抽共享框架

不改变任何一条检查的判断逻辑，只抽取重复的 CLI 接线（`ghJson`/`log.ok`/
`log.err` 之类的样板）成一个共享的 "doctor runner" 工具函数。

**验收标准**：
- 抽取前后每个 doctor 的输出文案、退出码、检查逻辑完全不变（这是纯重构，
  不是功能改动）——用抽取前的输出快照做回归比对。
- 优先做体量最大的几个（`lint-ui-material.mjs` 481 行、`lint-verification-can-fail.mjs`
  417 行、`lint-third-artifact.mjs` 349 行），不要求一次性覆盖全部 19 个。

### 阶段三：文档债务收敛

配合阶段一二的代码改动，顺手清理已发现但未处理的文档漂移（ADR-009→ADR-017
在十几份文档里未同步、"同一事实两处声明"的残留），不单独再开一轮扫描——
借着改代码的机会顺手修文档，比单独立一个"扫文档"的项目更有效率。

## 后果

**正面：**
- 阶段一预计能把日常 `verify:base` 的强制检查面减少约 18%（5,366 / 约 30,000
  行对应的检查逻辑），降低验证成本与新读者的心智负担。
- 阶段二 a 消除一个本会话实测确认过的、真实发生过的维护双份成本。
- 阶段二 b 降低"新增第 20 个 doctor"时的边际成本（复用框架而不是复制一份
  样板），间接放慢未来的行数增长速度。

**负面 / 需注意：**
- 阶段一的"冻结"本质是一个产品/架构方向判断（要不要为 Epic E3 保留现成能力）
  ——**本 ADR 不替人类拍这个板**，只提出"如果要冻结，冻结到什么程度、怎么
  验收、怎么可逆"这套机械操作方案；是否执行、执行到哪一步，由人类/coord-main
  在 Accepted 时或各执行 issue 里逐条确认。
- 阶段二 a 合并两个模块时，如果判据逻辑本身有分歧（目前测试用例显示一致，
  但历史上可能因为"改一处忘另一处"已经产生过细微不一致），合并过程本身就是
  一次强制对齐，需要对每一处不一致做显式取舍记录，不能悄悄选一边。
- 阶段二 b 如果发现"共享框架"强行套用后反而让某个 doctor 的特殊逻辑变得更难
  读，应该允许该 doctor 不套用框架、保留独立实现——不追求 100% 覆盖率本身
  就是目标的一部分。
- 三个阶段都不改变任何检查的判断标准（阶段一是"要不要跑"，阶段二是"怎么实现"，
  不是"判定条件变宽变严"）——如果执行过程中发现某个阶段顺带想调整判断逻辑，
  应该拆成单独的 issue，不要混进"精简"这个范畴，避免审查者分不清"这行改动
  是纯重构还是行为变了"。

**对架构平面的影响：**
- `.harness/instructions/testing-standards.md`（如果提到 19 个 doctor 全量清单）
  与 `coding-standards.md` 需要同步阶段一的"强制链 vs 按需手动"新分类，避免
  又一次"文档说全部强制、代码已经不是"的漂移。

## 备选方案（考虑过，否决）

- **一次性大重构，一个 PR 改完三个阶段**：否决。三个阶段的风险等级、决策归属
  （阶段一需要人类拍板，阶段二纯技术重构）完全不同，混在一起会让 review 无法
  区分"这行改动是不是应该更谨慎地看"。
- **直接删除 H3A 代码而不是冻结**：否决。0/0/2/1 个实例不等于"确定不会用"，
  可能只是 Epic E3 还没到那个阶段；删除是不可逆操作，冻结（摘出强制链但保留
  代码+命令）在几乎不增加维护成本的前提下保留了可逆性。
- **维持现状不动**：否决。5,366 行"为未跑起来的流程建工厂"和两份重复的 review
  判据都是本会话实测确认的真实成本，不是主观感觉。
