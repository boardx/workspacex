# ADR 020: 阶段设计签核 —— UI 之外，契约与架构也必须先经人类确认

- 状态: Accepted
- 适用层：方法论（可移植：随模板打包）
- 日期: 2026-07-28
- 扩展：**ADR-003**（UI 先行确认关卡）。ADR-003 仍然有效，本 ADR 把签核对象从「一件」扩成「四件」。

## 背景

ADR-003 解决了一个真问题：feature_list 在任何人看到真实界面之前就被定成权威，
`user_visible_behavior` 只能凭文字想象界面。它引入了 UI 先行关卡。

2026-07-28，18 个业务屏建成、225 个 feature 生成之后，人类指出了 ADR-003 覆盖不到的一层：

> 有 Use Case，加上用户界面，应该还不够去确认整个设计。

这不是感觉，是**已经发生的事实**。在建界面的过程中，下列**后端契约**被顺手创造出来了，
而它们从未作为契约被评审过：

| 事实上的后端契约 | 现在住在哪 | 谁在依赖它 |
|---|---|---|
| 机密数据的模型路由规则（D-U1「全程本地」） | `apps/web/lib/mock/chat.ts` 的 `modelPolicyViolation` | 后端 gateway 的拦截规则 |
| 组织类型与模型策略（`OrgKind` / `ModelPolicy`） | `apps/web/lib/identity.ts` | 整个权限与隔离模型 |
| 丢弃原因七类枚举（D-U4） | `apps/web/lib/omission-reason.ts` | `omissions[].reason` 的线上格式 |
| 撤回链五步与两级 SLA（D-13/D-15/D-19） | `apps/web/lib/withdrawal-flow.ts` | 对受访者的合规承诺 |

**它们是在画界面时产生的，不是在设计后端时产生的。** 界面能跑通不等于契约成立——
mock 是手写的，它对自己永远自洽。

更直接的证据：刚生成的 225 个 feature，其 `verification` 引用的**全部是尚不存在的测试文件**。
738 点的验收标准现在悬在空中；它们要落地，前提正是「核心数据结构 + 接口 + API 契约」。

### 为什么不是简单地「把签核对象换成整个 phase」

人类的初步想法是「整个 phase 签核」。方向对，但**粒度会出问题**：

- phase-01 是 50 份 UC / 115 个 feature / 373 点。一次签完前端 + 后台 + 架构，
  评审者读到第 30 份 UC 时已经疲劳，而第 45 份里的契约缺陷要等整批返工。
- 与 harness 的「一次只做一个 feature」纪律冲突：一个不可分割的巨型门让中间态无处安放。
- 阻塞面过大：蓝本设计器的契约没定，不该拖住访谈模块开工。

## 决策

### 一、签核对象从「UI 一件」扩成「四件套」

`has_ui` 阶段进入 `new-sprint` 之前，必须签核**契约束（contract bundle）**，每束四件：

| # | 产出物 | 洋葱层 | 回答什么问题 |
|---|---|---|---|
| ① | **领域模型**：实体、值对象、**不变量** | 最内层 | 这个域里什么是永远为真的 |
| ② | **用例接口**：application service 的输入/输出端口 | 中层 | 外界能对这个域做什么 |
| ③ | **API 契约**：对外 HTTP 面，含错误语义与权限前置 | 外层 | 前端能调什么、失败长什么样 |
| ④ | **UC 覆盖证明**：UC 的 R12 → API 操作 → 前端消费点 | 横切 | 这些接口真的够跑通业务吗 |

**UI 不被替代，它是第 ④ 件的一部分**——「前端消费点」就是已建成的界面。
ADR-003 的 `ui-signoff.md` 继续存在，成为契约束签核的一个组成项。

### 二、两级粒度：契约束签核 + 阶段一致性复核

- **契约束**按**能力域**切（如「身份与权限」「Artifact 与文件」「Context Pack」
  「能力配置平面」「撤回与留存」）。每束独立签核、独立解锁其覆盖的 feature。
- **阶段级只保留一道「一致性复核」**：检查各束之间的**交叉约束**有没有互相打架。
  典型交叉约束：权限沿数据链路传播（跨 5 个束）、撤回级联（跨 4 个模块）、
  同一事实在多束中的表述（枚举、SLA、估点）。

⇒ 一个 feature 可以开工，当且仅当：**它所属的契约束已签 ∧ 阶段一致性复核已通过**。

### 三、后台采用整洁架构（洋葱），且**依赖方向由脚本强制**

```
     ┌───────────────────────────────────────┐
     │  interface   控制器 / DTO / 路由       │  → 依赖内层
     │  ┌─────────────────────────────────┐  │
     │  │  application  用例 / 端口        │  │  → 依赖内层
     │  │  ┌───────────────────────────┐  │  │
     │  │  │  domain  实体 / 不变量     │  │  │  → 不依赖任何人
     │  │  └───────────────────────────┘  │  │
     │  └─────────────────────────────────┘  │
     │  infrastructure  PG / S3 / 模型网关     │  → 实现 application 的端口
     └───────────────────────────────────────┘
```

⚠ **洋葱架构的全部价值在「依赖只能指向内层」这一条，而这条可以机械检查。**
只分目录不查依赖方向 = 四层文件夹 + 零收益。故本 ADR 强制配套 `lint-arch-deps`。
`infrastructure` 是特例：它**实现** `application` 定义的端口，依赖方向仍指向内（依赖倒置）。

### 四、API 契约单一事实源，且 **mock 必须由契约生成**

```
  zod schema（唯一事实源）
     ├─→ 后端 DTO + 运行时校验（NestJS ValidationPipe）
     ├─→ 前端 client 类型
     ├─→ OpenAPI（对外文档 + 契约 diff 门控）
     └─→ 前端 mock 数据          ←── 这条是关键
```

**为什么 mock 必须从契约生成**：本项目已经**五次**撞到同一种失效模式——
同一事实声明在两处必然漂移（设计 token、字号档位、丢弃原因枚举、撤回链 SLA、估点）。
现在 18 个屏的 mock 是手写的，它与未来的 API 是第六次。
让 mock 从契约生成后，**前端自动成为契约的第一个消费者：契约错了，界面当场就崩**，
而不是等到联调。

## 门控（三道新的机械检查）

| 门控 | 检查什么 | 失败意味着 |
|---|---|---|
| `lint-arch-deps` | 依赖只能指向内层；`domain` 不 import 任何外层 | 洋葱破了，退化成四层文件夹 |
| `lint-contract-source` | mock 由契约生成（带生成标记且与 schema 一致）；不存在手写的第二份类型 | 第六次漂移 |
| `verify-uc-coverage` | 每个 UC 的 R12 → 至少一个 API 操作 → 至少一个前端消费点 | 有 UC 跑不通，或有接口没人要 |

加上既有的七道（typecheck / lint-design / lint-dead-controls / lint-omission-reason /
lint-withdrawal-flow / check-token-contrast / verify-ui-states）与 `validate-fl`，
构成设计阶段的完整门控面。

**`new-sprint` 的拒绝条件扩展**：`has_ui` 阶段除 `ui-signoff.md: confirmed` 外，
还需该 feature 所属契约束的 `design-signoff.md: confirmed`，且阶段一致性复核通过。

## 后果

**正面**
- 后端契约在被实现之前先被评审，而不是从 mock 里考古出来。
- 225 个 feature 的 verification 从「引用不存在的测试文件」变成「引用契约定义的操作」。
- 洋葱的依赖纪律可机械保证，不靠自觉。
- mock 与 API 不会漂移，前端是契约的活测试。

**代价（要说清楚）**
- **开工时间往后推。** 每个契约束的四件套是真实工作量。
- 增加三道门控，CI 变慢。
- 契约变更成本上升（这是有意的：契约就该难改）。

**为什么代价可接受**：现在 mock 里已埋了至少 4 处事实上的后端契约。直接开工的话，
它们会被 115 个 feature **各自实现一遍**，联调时发现四套不一致——那时的返工代价
远大于现在把契约先定下来。

**试点范围**：先在 **phase-00 共享内核**（17 个 feature）跑通全流程。
它体量小，而横切契约恰好全在那里（Artifact 模型、Context Pack、两层权限、组织配置）。
跑通后再套用到 phase-01 的 115 个 feature。

## 与既有 ADR 的关系

- **ADR-003** 继续有效。UI 先行关卡成为四件套中第 ④ 件的组成部分，不被替代。
- **ADR-012**（审计链加固）：契约束签核记录沿用同一套证据纪律。
- **ADR-018**（spec_ref 闭环）：UC 覆盖矩阵是 spec_ref 闭环在契约层的延伸——
  从「feature 指回 UC」扩展到「UC 的验收线索指向 API 操作与前端消费点」。
