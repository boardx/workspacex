# 组织大脑：三级记忆与决策支持体验

日期：2026-10-01。本文件是待讨论的产品设计与验收目标，不表示全部能力已实现。当前事实与本轮截图见 `evidence/kg-user-acceptance/2026-10-01/`；真实模型质量须另行验收。

## 以一次决定作为验收单位

用户的问题是“现在应不应该做这个决定，依据是什么，还缺什么”，而不仅是“助手记不记得”。组织大脑应把聊天产生的事实、个人承诺和项目证据带到同一次决策中，并让用户能核查、纠正和撤回。

层级与部署模式是两个独立维度：会话、个人、项目各自在云端组织和 local 组织下验收。local 组织目前只有所有者，项目协作的其他成员旅程适用于云端；local 的项目仍须可组织自己的长期工作。组织层作为跨项目治理的延伸，不能代替本轮三级验收。

| 层级 | 用户问题 | 应保留的内容 | 使用与边界 | 必须提供的操作 |
|---|---|---|---|---|
| 当前 chat session | 我们刚讨论到哪里？为什么改口？ | 当前讨论、候选方案、尚未证实的假设、决定及原话 | 同一会话；私人或项目会话的可见范围必须明确 | 查看来源、确认/纠正、标矛盾、忘掉、选择长期保留 |
| 个人（跨 sessions） | 我以前承诺过什么？这符合我的目标吗？ | 本人确认的长期事实、偏好、目标、决定、待办及来源会话 | 默认仅本人；可用于新会话；不能把私人背景自动变成项目公共知识 | 找到历史来源、更新、忘掉、分享前预览项目成员、撤回 |
| 项目 | 团队现在依据哪些证据？谁拍板？哪些事项尚未确定？ | 获授权的项目事实、证据、假设、冲突、决定、理由、责任人与时限 | 项目成员及角色控制；同一成员的私人召回必须与项目共有材料区分 | 证据溯源、确认/采纳、解决冲突、决策沿革、撤回共享、形成行动 |

自动“记下”与用户“确认”必须可区分。自动复制到个人的决定不能显示成用户已确认的组织事实。个人新会话能召回一条历史事实，也不代表这条事实已经存在于长期记忆管理页；必须分别检查可见层级与实际来源。

## 贯穿流程：是否扩大首发范围

1. **会话记录**：用户说“王芳拍板首发只做安卓版，因为客户司机主要用安卓”。系统展示决定、理由、拍板人和原话；若对象或理由不确定，应允许纠正。该步验收对象是正确记录，不要求用户理解 AGE。
2. **个人连续性**：数日后新会话问“我们为什么先做安卓，我还需要补什么？”系统找回本人先前决定和承诺，标明历史日期与来源。不把“我猜用户偏好安卓”当作团队认可事实。
3. **进入项目**：用户选择把这条决定分享到真实项目，确认前看到哪些人能看到。项目大脑显示共享来源、确认状态及当前有效性；另一项目成员的新会话能使用它，非成员不能使用。
4. **决策准备**：在项目问“现在要不要增加 iOS 首发？”系统先列当前目标、预算/工期约束、已有用户证据、矛盾和缺失材料。缺少 iOS 用户占比或新增成本时明确说缺少，不自行补数。AGE 支持人—决定—理由—证据—后续变化的关系；pgvector 帮助找到措辞不同但相关的证据。两者的价值由决策材料的正确性证明。
5. **提供选择**：至少比较“维持安卓首发”和“扩大到 iOS”的收益、成本、风险与适用条件；推荐须引用支持理由，并区分事实、推断与假设。用户可以点开来源，发现旧预算后纠正，再询问时使用新预算。
6. **人做决定**：用户确认选项、理由、责任人和截止时间。只有这一步产生团队决定；系统建议本身不自动成为已拍板的结论。新的决定链接到被取代的旧决定，同时保留沿革。
7. **行动与回看**：创建实际待办或关联已有任务，新会话能追踪执行。撤回分享后项目公共记忆不再使用副本；个人原件仍在。随后评价结果是否支持当时假设。

## 用户可见的决策输出

建议用一份可展开的“决策准备”卡，而非默认给用户整幅知识图：

- **当前问题与范围**：项目、组织模式、参与者、资料截止时间。
- **已经知道**：预算、目标、约束、当前决定；每项带来源、日期、确认状态。
- **还不知道/有冲突**：缺失材料及它会影响哪个选项；提供“补充证据”或“请某人确认”的实际入口。
- **可选方案**：收益、成本、风险、前置条件、依据。证据不足时仍可比较，但明确无法定论。
- **建议与不确定性**：推荐理由、关键假设、哪些新信息可能改变建议；无需展示算法分数来假装可靠。
- **确认与行动**：选择方案、记录拍板者/理由、指定负责人/时限，再创建或关联任务；可回看与修订。

来源上区分“当前对话”“我的历史”“项目共有”。分享前的个人材料只给本人用于思考；若决定要在项目中公开，用户需选择哪些依据一并公开。项目成员不得通过答案、来源抽屉或后续抽取得到别人未分享的个人原话。

## 三级 × 两模式端到端验收矩阵

| ID | 完整用户旅程 | 硬验收 |
|---|---|---|
| D01 | 两模式：聊决定→查看会话记忆→点来源→纠正→当轮重问 | 决定/理由/拍板人正确；来源原话对应；纠正后不复活旧值 |
| D02 | 两模式：自动记下或显式长期保留→个人大脑→刷新→新会话问 | 明确保留方式与确认状态；管理页能找到；跨会话引用正确，原来源可访问 |
| D03 | 两模式：真实新建项目→分享个人条目→预览范围→项目大脑→项目新会话 | 项目条目及共享来源可见；项目回答可引用；不能只证明写 API 成功 |
| D04 | 云端：成员/非成员各开新会话；分享→撤回→成员再次问 | 分享前不可见，分享后成员可见，非成员始终不可见；撤回后副本不再召回，个人原件仍在 |
| D05 | 两模式：项目会话产生新决定→开另一项目会话提问→个人会话提问 | 项目层的归属、引用和个人层的差异符合说明；会话条目不冒充项目已确认决定 |
| D06 | 两模式：同一决策问题用 AGE+vector 和 vector-only 对照 | 正确引用及决策材料覆盖率更好；报告真实模型、真实嵌入、语料/题量，不用是否显示“关联”标签代替价值 |
| D07 | 两模式：项目提一个证据不足的选择问题→补材料→再次比较 | 至少2选项；事实、假设、推断区分；推荐依据全部可核查；缺失数据不捏造 |
| D08 | 两模式：确认建议→记录理由/拍板者→建立责任人与时限→刷新/新会话追问 | 人的确认形成决定；有实际可追踪任务；不是只显示“已安排” |
| D09 | 两模式：预算或决定变更→决策准备更新→新会话重问 | 当前有效知识正确；被取代内容明确；后续比较和建议用新值，来源对应 |
| D10 | 两模式：AGE/pgvector各故障→决策问题→恢复重问 | 可以完成回答；说明哪部分检索缺失及影响；不足时不做无依据确定结论；恢复后两路可用 |

2026-10-01 修复复验：D01–D03 的主要系统路径已复验；D04 已通过通用和研讨型项目的成员/非成员、分享前后及撤回流程，并补验两种组织的忘掉原件与撤销恢复。D05 的项目原生晋升及其与个人层的差异尚未完成本轮专项。D06–D09 的自然语言决策质量仍需真实模型，当前模型域名被环境代理阻止，不能判通过。D10 已在独占数据库注入 AGE、pgvector 和两者同时故障并验证恢复，建议可靠性仍需真实模型。

修复结果、原始测试报告和逐步截图见 `evidence/kg-user-acceptance/2026-10-01/remediation/`。这些技术路径成绩不代表完整“方案比较→人确认→创建真实任务→跟踪结果”已验收。

## 推进顺序

先解决来源精准、层级导航与关系图可读性，确保用户能辨认当前有效事实。其次完成会话→个人→项目的可见流转与撤回闭环。再用真实模型评测完整决策准备、方案比较、人工确认和任务跟踪。最后扩展到跨项目的组织层治理。每个阶段都保留截图和失败记录，不以现有技术能力推导用户流程已经可用。
