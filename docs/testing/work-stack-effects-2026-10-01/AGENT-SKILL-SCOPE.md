# Selected digital human skill scope (#4869; PR #4892)

The old run snapshot resolver appended arbitrary thread-mounted skill versions to a selected agent's pins and gave an explicitly selected empty-pin role the organization's skill pool. This contradicted the user's new requirement that selected digital humans expose and execute only their mounted skills.

New explicit selections freeze `skill_scope=agent_pins`; acceptance rejects thread mounts outside the published agent version's exact version IDs, including another version of the same skill. Empty role pins stay empty. Before skill content/model execution, claim reads the frozen agent version pins and execution rejects an out-of-scope run snapshot. It reports the existing SKILL_VERSION_UNAVAILABLE terminal code, logging the distinct scope violation detail.

The general assistant keeps the previous organization/default/thread-mount behavior. General admission comes only from server selection: the resolved ID must match the server's default, and a user explicitly selecting even that ID gets role scope. Client `env-default` text alone cannot turn an arbitrary role into general scope. The queue freezes explicit selection provenance and checks the server default again at dispatch. New acceptance and queue idempotency also reject a changed selection scope for the same request ID. Existing runs have NULL scope and retain their immutable historical snapshots; old queue rows with unknown selection provenance default to strict role scope. No claim is made that historical runs were retrospectively constrained. Other acceptance callers (REST, scheduling, plan/artifact launches, carry-over) provide an actual agent ID and default to explicit scope.

Member profile returns exact `{skillId,versionId}` published pins, including older versions, through the same tenant/visibility checks. It also returns strict `pendingSkillBindings` from the frozen version. Pending authored capabilities are informational, never added to executable pins. The pending frozen column migration/official pack authoring belongs to the separate pack subtask; this adapter depends on that migration being integrated. Pending/Authored schemas are single-source contracts in agent-role.ts.

Evidence: restoring the old resolver, executor and profile use case produced four failures (explicit empty pin fallback, unmounted/alternate-version acceptance, execution validation, and exact profile pins). After the fix, four target files passed 41 tests. Later tests additionally cover adapter SQL tenant/platform bounds, pending capability separation, and the shared default-selection predicate. These are pure/application/controlled-adapter checks, not PostgreSQL isolation evidence.

New real PostgreSQL regressions in runtime-profile-claim.test.ts cover actual message repository acceptance, all scope claim values, and tampered role snapshots rejected before content/model execution. They have not been run by this subtask; integration will execute them. Architecture and permission-path lint passed during development. An initial API typecheck found two integration errors (bridge error export and error disposition); both were corrected, but that failed run is not counted as final typecheck validation. Integration's normal checks cover the final tree.
