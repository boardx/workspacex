## 1. 已确认目标与范围

人类确认：Devapp 自动部署；中国生产自动准备，批准后上线。
提交后的标准验证、部署、验收、证据收集由流水线推进。产品失败不自动豁免。
稳定发布的验收是既有核心旅程通过、真实运行版本一致、失败恢复可证明，
不能承诺所有未知回归绝不发生，也不能用 healthz 或 CI success 替代业务验收。
这轮不引入新产品界面、不增加开发 Agent 数量，不将中国生产改为免批准发布。

## 3. 方案选择

推荐：增量改造现有可信部署链，增加隔离候选、回归验收和事件衔接。
仅自动派发旧脚本能减少人工，但不解决原地构建及恢复缺口；
全面迁移部署平台会扩大范围并重复已有中国生产控制协议，暂不选。

## 4. Devapp 发布事务

主路径：main exact SHA 门禁通过 → 创建候选 → 隔离构建 → 启动候选 →
候选业务验收 → 复核 baseline/锁 → 兼容迁移与任务 drain → 切换入口 →
公网业务验收 → 稳定观察 → available。

1. 构建和依赖安装不得写入活动版本目录，不得变更旧版静态资源。
   优先保留现有运行拓扑，用独立 release 目录和服务端口隔离候选；
   容器与 systemd 服务的完整映射须在实施计划中逐项明确。
2. 候选运行与生产数据分离；候选测试使用隔离库及专属测试账号和对象前缀。
   真正环境切换前的数据库操作只能走现有受控入口。
3. 不同环境的 NEXT_PUBLIC 构建参数进入制品身份。
   只有源码、依赖、平台和构建参数一致才能复用相同制品，不能宣称所有环境共用同一 Web 字节。
4. 切换前记录旧入口、旧制品、配置引用及实际服务身份；保留旧版完整静态资源，
   使切换前已打开的浏览器仍可读取旧 chunk。保留期需覆盖会话与回退窗口。
5. 运行中的 Agent/SSE/WS 应有有界 drain；超时保持旧服务，不强杀业务任务。
6. 切换或公网验收失败自动恢复旧入口和完整运行版本，再验收旧版浏览器旅程。
   恢复未证明即事故终态，不继续新候选，也不自动清理恢复所需制品。
7. 构建与验证可并行；环境变更与切流使用同一锁。候选淘汰只发生在写操作前，
   不取消已开始的迁移/切流事务；共享 Devapp 的真实验收与其他部署也必须互斥。

## 5. 数据兼容性

每项迁移与补种都必须分类。普通自动通道只接收已证明新旧应用兼容的扩展变化，
使用可重入操作和版本账本。破坏性、未知、不可逆数据变换转维护通道，不自动切流。
应用回滚不代表数据回滚；自动回退必须证明旧应用能读取迁移后的数据。
没有兼容证明时保持旧版，不能自动执行 down migration 或恢复整个数据库覆盖新写入。

## 6. 中国生产自动准备与一次准入

Devapp exact-source 真实运行验收完成后，协调器冻结 source、attempt 和生产 baseline，
串接现有候选构建、运输及 prepare；不创建第二套 receipt 或 privileged writer。
先验证完整链的兼容能力、已有环境审批与可信入口，避免同时派发两种构建路径。
prepare 不切流；准备完成后显示证据绑定的候选并进入既有生产批准点。
人工批准只授权该候选及 baseline；批准后动态复验 TTL、锁、基线和证据。
过期或漂移返回 NOT_READY，重新准备并重新绑定批准，不能在批准后悄悄换 SHA。
沿用现有 production-cn-promotion / production-cn 的治理，需验证真实环境配置
是否造成重复人工审批；代码中的 environment 声明不证明实际审批数量。
稳定密钥、配置持久化和数据库备份继续遵守原有生产规则。

## 7. 既有功能回归契约

发布前建立版本化清单，逐条绑定当前真实测试入口和证据，不临时复制断言到 workflow。
至少覆盖登录及组织隔离、项目列表/打开、聊天发送/流式/历史、工具与文件产物、
白板保存及重开；本次变更相关领域再追加完整回归。
确定性回归验证业务协议；影响 Agent/Skill/模型路由的版本还要求已有真实模型旅程。
用例只能操作自己的数据，并保留任务/文件归属和版本身份。
缺失、跳过、超时或产品失败都阻止候选晋级。

## 8. 失败反证与真实验收

| 场景 | 必须观察到的结果 |
|---|---|
| 构建或候选回归失败 | 活动入口、进程和静态资源未变，旧旅程继续通过 |
| 新旧应用不兼容的迁移 | 切换前拒绝，数据库无未授权变化 |
| drain 超时或锁冲突 | 保持旧版本，不重复派发 writer |
| 切换后浏览器业务失败 | 自动恢复旧运行版本，旧浏览器旅程通过 |
| 回滚失败或远端操作状态未知 | 事故终态，保留证据和锁，不盲目重试写操作 |
| baseline/CAS/TTL 变化 | 拒绝晋级，要求重建对应准备证据 |
| 准备完成但无人批准 | 中国生产运行体和入口不变 |
| 批准后正常激活 | 公网核心旅程通过，实际运行身份等于批准候选 |
| 两个 main 提交连续到达 | 事务串行，旧事件不能让运行版本倒退 |
| 切换前已打开的浏览器 | 旧 chunk 可读取，连接按 drain 策略结束或恢复 |

先在隔离环境执行故障注入，再做 Devapp 真实切换/恢复演练；
生产启用以实际环境治理、主机能力和一次批准发布演练为前提。
本地 fixture 测试不能替代主机安装证明、公网浏览器或数据库兼容验收。

## 9. 实施切片与交付

按依赖顺序一项一个 issue/PR：

1. 固定核心回归清单、证据协议、候选状态及失败反证。
2. Devapp 独立 release 构建、候选运行及可信入口安装演练。
3. Devapp 切换、drain、兼容准入和完整自动恢复，完成真实故障演练。
4. 接通 exact-source Devapp 验收到中国生产自动准备，验证幂等及未知状态处理。
5. 验证现有生产批准与激活闭环，完成真实一次批准上线/恢复演练后启用。

每片先定义可执行 verification，再实施；不跳过现有基础验证、独立 review 和 CI。
记录提交、门禁、构建、准备、批准、切流、可用与恢复各时间点，区分排队/执行时长。
性能目标待真实样本评估，不通过削减原有业务覆盖来达标。
