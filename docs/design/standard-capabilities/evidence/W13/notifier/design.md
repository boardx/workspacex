# W13 scheduler notification receipt adapter

Audit of `origin/main` d30ac48e8 and the peer worktree found existing `TaskNotifications`, `useTaskNotifications`, and `reconcileTaskNotices`. They project visible ThreadCard status changes and keep observed/read cursors in browser localStorage. They expose no durable server-side publisher. The existing inbox aggregates feedback, system exceptions and design projects, rather than arbitrary task notices.

Reuse `standard_schedules` as the only failure fact source. A schedule fails terminally with `failure_code` and `last_occurrence_id`; this adapter adds only accepted/read receipt timestamps. No notification payload copy, new inbox table, email fallback, main-run state or synthetic failed thread is introduced.

`PgScheduleNotifications` implements both `ScheduledRunNotifier` and `ScheduleNotifications`. Internal publish matches org, recipient, schedule, occurrence, code and failed status. It returns durablyAccepted only after the transaction commits. Repeated and concurrent calls preserve the first accepted timestamp. The scheduler's existing pending receipt/retry path remains unchanged.

Authenticated GET `/schedule-notifications` returns a bounded, paginated unread list. POST `/schedule-notifications/read` takes only `{factId}` and persists an idempotent read timestamp. Both read current org membership and bind current principal's org and user. No instruction, thread title or link is disclosed: a notice remains a fixed failure fact even if its source thread became private/inaccessible. Removed org members receive no list or ack authority. Stable server read receipts survive browser/process restart; the UI must not replace this with local optimistic success.

Implemented shared composition (root-owned hunks): one `PgScheduleNotifications(db, identity)` instance bound to both `SCHEDULE_NOTIFICATIONS` and `SCHEDULED_RUN_NOTIFIER`; add `ScheduleNotificationsController`. The scheduler still requires explicit enablement and its official provider setup. The existing TaskNotifications surface now consumes the independent unread source with two fixed labels: “定时任务已停止：访问权限已撤销” / “定时任务未能执行”. Polling, authentication and tenant switching use the existing apiRequest path. The UI removes a notice only after a successful HTTP acknowledgment; errors remain visible/retryable. Do not navigate an inaccessible source thread or clear all notices through a made-up local receipt.

Validation: contract tests include strict no-content/no-recipient fields and bounded pages. PostgreSQL tests prove exact publishing identity, lost-reply retry, concurrent/read idempotency, adapter restart and actual membership deletion; HTTP tests use the real controller with an explicit test principal injector. They are controller/DB tests, not evidence of the final production auth/DI/UI composition. Initial HTTP failure (a literal boolean mistakenly used as a Zod field) is retained and fixed with `z.literal(true)` plus a direct contract parser regression.


Final added verification: `schedule-notifications-delivery.test.ts` loads the exact production KernelModule provider definitions into Nest, verifies both public/internal tokens resolve to the same PgScheduleNotifications, then runs an actual pg-boss due job through ScheduledChatRunGateway/acceptHumanMessage against an archived thread. It observes the resulting persisted failure, notification_pending=false, HTTP unread fact, HTTP ack, and a recreated adapter's empty unread list. It asserts zero model calls, zero accepted chat messages and zero executor kicks. This 1/1 integration passed and its wrapper cleaned. The original controller/PG group passed 3/3 in root's 58-test merge regression. UI component tests (3 new + 2 preserved) passed 5/5, and contracts passed 2/2. These are real local DB/HTTP + jsdom UI tests, not a claim of a deployed browser screenshot or production rollout.

Final Web typecheck: `pnpm --filter web typecheck` exited 0. Root pre-push caught an unknown JSON assignment in the delivery test; it now uses the shared ScheduleNotificationListOutput parser, rather than a type assertion. No second API compiler was launched.
