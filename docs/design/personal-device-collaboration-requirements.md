> 架构决策见 `docs/adr/ADR-113-personal-device-pairing-and-runner-protocol.md`（Proposed）。

## 1. 一句话

**手机是遥控器和收件箱，电脑是干活的机器。** 用户在手机上看、问、派、批；
在自己那台性能好的电脑上真正执行；将来也可以选择在云端 VPC 执行。

这是 WorkSpaceX 的一种协作方式：**同一个人的多台设备之间的协作**。
它和「多人协作」互补——结果可以再从这里分享给别人。

## 2. 角色与设备

| 名词 | 含义 |
|---|---|
| 桌面实例 | 用户电脑上的本地版 WorkSpaceX（`apps/desktop` + `packages/local-runtime`），有本地模型、本地数据 |
| 手机端 | 手机 App（H5 起步）或**微信小程序**，只有精简界面，不存业务数据 |
| 中继 | 我们运营的转发服务，只看到密文和设备 ID |
| Runner | 能执行任务的地方。第一个是桌面实例，将来是云 VPC |

## 3. 用户故事

### US-1 配对（一次性）
作为用户，我在电脑上打开「手机连接」，屏幕出现二维码；我用手机 App 或微信扫一扫，
手机上显示「已连接：我的电脑（名称）」。
- 二维码 5 分钟过期，只能用一次。
- 电脑上能看到已配对设备列表（设备名、首次配对时间、最近活跃），可以逐台吊销。
- 关掉「手机连接」开关 = 吊销全部设备、断开中继。

### US-2 随时看
我在外面，用手机查看电脑上的对话、项目、运行中的 agent 与产出物。
- 电脑在线时实时；网络切换（Wi-Fi ↔ 4G）后自动续上，不丢事件（复用 `lastKnownSeq` 重放）。
- 电脑离线时，手机明确显示「电脑离线，上次在线 xx」，不显示过期数据冒充最新。

### US-3 在手机上继续对话
我在手机上对某个对话追问，电脑上的本地模型回答，手机流式显示。

### US-4 派任务（核心）
我在手机上写「把这周的访谈录音整理成报告」，选择执行位置「我的电脑」，提交。
- 电脑在线：立即开始，手机能看进度。
- 电脑离线：任务进入待执行（密文存中继信箱，默认保留 72 小时），电脑开机后自动领取；
  超时未领取，手机收到「未执行」通知，而不是静默消失。
- 任务完成：手机收到一条**不含内容**的通知「任务已完成」，点开后经隧道读结果。

### US-5 审批
电脑上的 agent 跑到需要人确认的一步（发送邮件、覆盖文件、调用付费工具……），
我的手机收到「需要你审批」，看摘要后点同意或拒绝，agent 继续或停止。

### US-6 分享给别人
我把一份结果分享到微信群（小程序卡片）或发给同事。
- 这是数据**离开本人**：沿用现有「人发起 + 有审计」的导出路径，界面上明确提示。

### US-7（将来）选择在云上执行
派任务时执行位置可选「云端（组织的 VPC）」。
- 本地组织的任务选云端 = 数据离开本人设备，**每次**弹出授权说明，记入审计。
- 云 Runner 与桌面遵守同一套 Runner 协议（ADR-113 D5）。

## 4. 非功能要求

| 项 | 要求 |
|---|---|
| 安全 | 端到端加密；中继看不到内容与 URL 路径；桌面不开入站端口；本地服务仍只绑回环 |
| 授权 | 手机令牌按设备发放、可限权（只读 / 可派任务 / 可审批）、可单独吊销 |
| 延迟 | 审批往返（点击 → 桌面收到）在正常 4G 下 p95 ≤ 2 秒（待实测后定） |
| 可用性 | 中继不可用时，桌面功能完全不受影响（中继不是桌面的必需依赖） |
| 数据边界 | 手机端不落业务数据（仅缓存当前屏）；推送载荷不含内容 |
| 地域 | 国内用户的中继部署在境内、已备案域名；微信 openid / unionid 存境内 |

## 5. 分期

| 期 | 范围 | 验收（端到端可复现） |
|---|---|---|
| **P0** | ADR-113 签核；identity 束 `no-shared-storage` 措辞重签；Runner 协议与中继帧协议写成契约 | 人类签核 |
| **P1** | 桌面隧道客户端、扫码配对、设备管理、中继（境内）、手机 H5：US-1/2/3/5 | 手机在 4G 下驱动家里电脑完成一次 agent run 并完成一次审批 |
| **P2** | 离线派任务（密文信箱）、推送、令牌限权：US-4 | 电脑关机时派任务 → 开机后自动执行 → 手机收到完成通知 |
| **P3** | 微信小程序、微信登录绑定、订阅消息、卡片分享：US-6 | 在小程序里走完 P1 + P2 的闭环 |
| **P4** | 云 VPC Runner、逐次授权：US-7 | 同一任务可选电脑或云端执行，本地组织选云端时有授权与审计记录 |

## 6. 客户端技术取向（待定，列候选）

- 抽共享包（暂名 `packages/remote-client`）：隧道、加密、调用封装，类型复用 `packages/contracts` 的 zod schema。
- 界面：一套代码同时出小程序和 H5/App 的框架（Taro 或 uni-app，二选一待评估）；
  只做精简界面——任务列表、对话、审批、结果查看，不移植整套 web。
- 小程序的加密能力有限，需要纯 JS 实现（例如 tweetnacl），性能待实测。

## 7. 微信小程序专项

| 事项 | 已知 | 待核实 |
|---|---|---|
| 网络 | 只能连后台配置的 HTTPS/WSS 白名单域名，需已备案 → 中继必须境内部署 | 单个小程序并发 WSS 连接数上限对长连接体验的影响 |
| 登录 | `wx.login` 取 code → 服务端换 openid / unionid → 绑定 WorkSpaceX 账号 | 账号体系是否要支持「只有微信、没有邮箱」的用户 |
| 通知 | 订阅消息：用户在派任务时授权一次，完成时推一次，正好对应「一个任务一次通知」 | 长期订阅的类目资格 |
| 分享 | 小程序卡片可发到群聊，作为结果分享入口 | — |
| 主体资质 | 需企业主体与对应服务类目 | 适合本产品的类目 |
| 内容安全 | 用户可见的生成内容可能需要内容安全检测 | 与端到端加密是否冲突（见 ADR-113「我们什么情况下会改主意」） |
| 生成式 AI 合规 | — | 模型跑在用户自己电脑上、平台只转发密文时，是否仍需算法 / 生成式 AI 备案 |

## 8. 开放问题（需人类拍板）

1. **是否接受 ADR-113 D1**：`personal-local` 的边界从「本机」扩为「本人已配对的设备」。
   不接受则本需求只能做局域网直连，且国内小程序方案不成立。
2. 中继信箱的默认保留时长（72 小时是提案值）和条数上限。
3. 手机端是否需要离线只读缓存（例如最近 10 份产出物），还是坚持「不落业务数据」。
4. 小程序和 App 的先后顺序：国内市场是否直接从小程序起步、跳过 H5。
5. 云 VPC Runner 的归属：只做「组织自己的 VPC」，还是也提供我们托管的共享 Runner。

## 9. 与已有决策的关系

- **ADR-112**：本方案不做同步，中继只传输，所以不触碰「端到端加密与服务端同步二选一」——我们选了加密。
- **`super-instance-design.md` §3**：桌面与云 Runner 都只主动连出，与联邦层原则一致；
  中继属于产品交付面，不属于内部运营平面。
- **`architecture.md` 可移植性硬约束**：中继写成普通 Node 服务；Cloudflare DO 版本只是海外的可选实现。
