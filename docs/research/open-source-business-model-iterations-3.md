# 开源方案 — 第三轮十次迭代（第 21–30 轮）

> 前两轮见 `-iterations.md`（1–10 轮，产出 v11/v12）与 `-iterations-2.md`（11–20 轮，产出 v22）。

> 并遵仓库铁律：**没有脚本的规范视为未落地**，所以本轮必须产出至少一道真的会红的门控。

## 第 21 轮 · v22 的缺口清单本身有错

v22 结尾列了 5 个缺口。逐个实测，**两个是错的，一个半对**。

| # | 问题 | 实测 | 改法 |
|---|---|---|---|
| 201 | 「MAAU 格式规范不存在」**错了**。SKILL.md 的 frontmatter 已经是事实清单：`name` / `description` / `capability_id` / `version` | `skills/standard-methods/maau-canvas/SKILL.md` 带 `capability_id: WX-S021`、`version: 3.0.0` | 缺的不是格式，是**对外公布的契约**。工作量从「设计」降为「固化并公布」 |

| 205 | 缺口之间没有依赖顺序 | — | 格式契约是发布路径的前置；导出是退出自由的前置 |
| 206 | 没说明每个缺口**不补会怎样** | — | 每条写清后果，优先级才有依据 |
| 207 | 「没有一条承诺是机械检查的」——但仓库已有 **23 个 lint 门控**的现成模式 | `ls .harness/scripts/lint-*.mjs` = 23 | 照抄既有形状即可，这不是难题，是一直没做 |
| 208 | 缺口只列产品侧，没列**组织侧**：社区经理、安全响应人一个都还不存在 | — | 补组织缺口，它决定产品缺口能不能被补上 |
| 209 | 没区分「H1 必须补」与「可以带着缺口发布」 | — | 分开，否则发布日永远到不了 |
| 210 | 「最小可行完整解」5 件事没有排期与负责人，仍是清单不是计划 | — | 转成 90 天计划（第 27 轮） |

## 第 22 轮 · MAAU 契约：把缺口①变成规范

**实测 18 个 skill 的清单完整度，发现一个结构性问题。**

| 群体 | 数量 | 有身份（`capability_id` + `version`） | 有 LICENSE |
|---|---|---|---|
| 自研 skill | 13 | **有** | **多数无**（13 个里 5 个有） |
| 外来 skill | 5 | **无** | **有**（5 个里 4 个有） |
| 合计 | 18 | 缺 5 | 缺 8 |

**清单的两半分裂在两批人身上，没有一个 skill 两样俱全。**
自研的声明了身份不声明许可；外来的声明了许可不声明身份。
而商业边界恰恰需要**两样同时有**——否则回答不了「这一个 MAAU 是开源的还是付费的」。

| # | 问题 | 改法 |
|---|---|---|
| 211 | 必填字段没有定义 | 定为 `name` / `description` / `capability_id` / `version` / `license` / `content_class` |
| 212 | **`license` 不是清单字段**，只作为同目录文件存在，机器读不到归属 | 升为 frontmatter 必填，与 LICENSE 文件互相印证 |
| 213 | 没有 `content_class` 区分运行时与内容 | 新增枚举：`runtime` / `content-open` / `content-paid` |
| 214 | `capability_id` 的命名空间没有为第三方留位 | `WX-S*` 保留给官方，第三方用 `<vendor>-*` |
| 215 | `version` 没有 SemVer 政策 | 改内容升 minor，改判据或接口升 major，写成公布的承诺 |
| 216 | 没有兼容性 diff 门控 | 清单变更纳入契约 diff，破坏性变更必须升 major |
| 217 | 没有废弃政策 | 定义 deprecated 标记与最短保留期 |
| 218 | 沙箱资源契约未公开：能否联网、内存、超时 | 写进清单的 `runtime_requirements` |
| 219 | 没有来源与签名字段，第三方 MAAU 无法验真 | 加 `provenance` 与签名 |
| 220 | 私有 MAAU 没有位置 | 加 `visibility`：`public` / `org` / `private` |

## 第 23 轮 · 发布与分发路径（缺口②）

| # | 问题 | 改法 |

| 221 | 发布没有状态机，作者不知道自己处在哪一步 | 草稿 → 提交 → 审核 → 上架 → 弃用，状态对作者可见 |

| 225 | 没有回滚：新版本坏了退不回去 | 一键回退到上一版本 |
| 226 | 组织私有源没有设计 | 私有 registry，与公开市场同一格式 |
| 227 | 发现与搜索没有设计，18 个就已过载，上千个无法用 | 按场景与角色分类，不是平铺 |
| 228 | 没有信任信号，用户无法判断敢不敢装 | 显示来源、签名、安装量、评测分 |

## 第 26 轮 · 把承诺变成机械检查（缺口⑤）

仓库已有 23 个 lint 门控，形状现成。**承诺不带门控就只是一句话。**

| # | 承诺 | 能否机械检查 | 门控设计 |
|---|---|---|---|
| 251 | 每个 MAAU 都声明许可与身份 | **能** | `lint-maau-manifest`：必填字段 + LICENSE 文件互相印证（本轮已实现） |
| 252 | 契约包不依赖 MAAU 内容包 | **能** | 扩展 `lint-arch-deps` 或新增边界检查 |
| 253 | OSS 不依赖 EE | 能 | `lint-ee-boundary`（v12 已提，仍未建） |
| 254 | 依赖许可证全部已知 | 能 | `oss-dependency-inventory --strict`（已建） |
| 255 | 历史无明文凭据 | 能 | `oss-secret-scan --strict`（已建，需完整 clone） |
| 256 | 本地零出网 | 能 | 拔网 e2e，断言出网计数为 0 |
| 257 | 第一个价值时刻有埋点 | 能 | 检查事件定义存在且被触发 |
| 258 | 每类角色的体验有主、有判据、有度量 | 能 | 体验承诺登记表 + 字段完整性门控 |
| 259 | 响应 SLA 达成率 | **不能机械阻断**，但能统计 | 自动统计 + 公开看板，越线开 issue |
| 260 | 退出自由 | 部分 | 导出命令必须存在且 e2e 跑通；「不断供」靠合同不靠脚本 |

**本轮实现了 251**，其余登记在案。一次做一道，比列十道都不做强。

| # | 问题 | 改法 |
|---|---|---|

## 第 30 轮 · 事前验尸：这方案会怎么失败

假设 18 个月后失败了，回头看最可能的原因。

| # | 死法 | 早期信号 | 预防 |
|---|---|---|---|
| 291 | **维护者先走**，不是没人用 | 每周投入时长持续上升，未分诊 issue 积压 | 维护者体验是一级约束；承诺不到就不承诺 |
| 292 | 开源了但没人部署 | 首月部署数低于两位数 | 定位与品类词先验证；0→1 体验优先 |
| 293 | 部署了但没到第一个价值时刻 | 安装量远大于价值时刻数 | 示例项目 + 引导收敛 |
| 294 | EE 切线反复移动，社区信任崩塌 | 社区对新功能归属的抗议 | 切线只进不退，写成承诺并公开 |
| 295 | 行业内容被照抄，差异化消失 | 竞品出现相似方法论 | 靠评测集与数据积累，不靠保密 |
| 296 | 被超级应用分发碾压 | 客户说「飞书自带的够了」 | 打它们进不去的场景 |
| 297 | 合规事故：敏感数据随仓库或日志泄露 | 扫描有遗漏项 | 全历史扫描 + 发布前 dry-run |
| 298 | 沙箱逃逸导致安全事件 | 逃逸报告 | 沙箱加固列 P1；SECURITY.md 已落地 |
| 299 | 战线过长：12 类角色都想照顾，一类都没做好 | H1 承诺项全部半成品 | **只承诺 5 类半**，其余明说不做 |
| 300 | 方案本身没被执行，留在文档里 | 三个月后仓库没有对应 issue | 批准即转 feature 清单，没有 issue 的方案等于不存在 |
