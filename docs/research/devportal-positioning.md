# devportal 结构研究与定位设计

> 2026-09-23 · 研究稿，待人类决策。
> 起因：开源方案 v22/v32 两次把 devportal 当作 MAAU 市场的基础设施来评估。
> 本文实测其结构后发现**那个前提是错的**，并给出定位建议。
> 结论会改动 `open-source-business-model.md` 的两处措辞与一条归属。

---

## 0. 一句话

**devportal 不是「开发者门户」，它是协调平面的人类可读窗口。**
名字误导了此前所有关于它的讨论——包括我自己在方案里写的两句话。
它天然属于 v32.1 新划的第三类归属「不交付 · 内部运营平面」，
但它同时装着一层归属相反的公开层，这是必须解决的结构性张力。

---

## 1. 实测结构

13944 行、131 个文件、18 个页面路由、20+ 个 BFF API 路由。

### 1.1 数据源：零连接产品

| 检查 | 结果 |
|---|---|
| 环境变量 | 全部是 `COORD_*`：`COORD_GATEWAY_URL`、`COORD_API_TOKEN`、`COORD_ADMIN_TOKEN`、`COORD_DISPATCH_TOKEN`、`COORD_BROKER_TOKEN`… |
| 是否连 `apps/api`（产品 API） | **零命中**。没有 `KERNEL_*`、没有 `/api/v1`、不 import 产品包 |
| BFF 路由 | `api/coord/*`、`api/portal/*`、`api/p30/*`——全部指向协调平面 |

**它和产品没有任何数据往来。** 这一条是后面所有结论的基础。

### 1.2 模块知识库自己的定位（权威）

`.agents/skills/mod-devportal/SKILL.md` 写得很清楚：

> develop.boardx.us 的**协作平面**：面向工程师/agent 的项目页、个人主页与平台管理页
> （coord-brain/dispatcher 可视化），是 mod-coord-platform 状态的**人类可读窗口**，
> **本身不持有协调状态**。

并列了一条不变量：

> **只读窗口，不是权威**：BFF 路由是协调平面状态的转发/聚合层，不应绕过 DO/协议直接写协调状态。
> 发现门户需要「改状态」而不只是「看状态」时，说明这个能力该加在 coord-platform 那边。

### 1.3 三层结构，其中一层归属相反

| 层 | 路由 | 身份 | 数据 | 天然归属 |
|---|---|---|---|---|
| **公开层** | `/explore`、`/projects/:slug`、`/u/:handle`、`/a/:handle/:agent` | **零身份**（有机械门控强制） | mock，未接后端 | **对外**：产品/生态 |
| **协作层** | `/`、`/p/:slug/{pulse,work,talk,people,coord,settings}`、`/me`、`/onboard` | Cloudflare Access | 真实 coord 数据 | 内部运营平面 |
| **平台层** | `/platform/coord-brain`、`/platform/dispatcher` | Access + 管理员 | coord 管理 | 内部运营平面 |

### 1.4 身份层做得很扎实，值得记一笔

- `lib/access.ts` **验签而不是只信 header**，注释点明原因：`*.pages.dev` 直连不经过 Access，
  攻击者可手工伪造 `Cf-Access-Authenticated-User-Email`。用 JWKS 验 RS256。
- 公开层的「零身份」不是靠自觉：`tests/public-layer-static.test.ts` 从四个公开入口出发
  **递归收集 import 链**，逐文件断言不出现身份读取面（禁 `lib/access`、`lib/session`、
  `next/headers`、`cookies()`、`headers()`、任何 `cf-access`）。**实测该门控在跑且通过。**

这是本仓「没有脚本的规范视为未落地」那条铁律的正面样本。

## 2. 核心张力：公开层写了，但对外不存在

两件事都为真，合起来产生一个空洞：

1. **代码层面**：公开层零身份，门控强制，`/u/:handle` 注释写「贡献事实默认公开」，
   `/a/:handle/:agent` 写「分身页默认全公开（软件资产无隐私权）」。
2. **部署层面**：整域由 Cloudflare Access 保护，而且**这一条有 CI 断言**，不是注释里的说法。
   `apps/devportal/README.md` 的冒烟标准写着：

   > `develop.boardx.us` → **302**（Access 门禁在前）；`*.pages.dev` 直连 API → 401（验签拒绝无凭据请求）。
   >
   > 域名绑定：Pages → devportal → Custom domains → develop.boardx.us；**Access 应用作用于该主机名**。

整域门禁之下，**公众到不了公开层**：访问根域先吃 302 跳登录。
写了四个页面、配了机械门控、声明了公开语义，而实际可见性为零。

⚠ 注意这里的证据强度差别。「公开层零身份」有机械门控在跑，是**动态事实**；
「公开层对外可见」从来没有任何断言，只存在于页面注释里，是**静态痕迹**。
两者被当作同一件事对待了。

⚠ 这不是我新发现的问题——模块知识库里有一个**没填的占位符**正指着它：

> `<公开面/未登录可达的门户页面清单——待核实，任何改动过一遍未授权视角>`

问题被记下来了，一直没解决。这正是本仓「静态痕迹 ≠ 动态事实」要防的形状：
代码注释说「默认公开」是写下来就不再变的痕迹，域级门禁才是会变的事实。

## 3. 这推翻了开源方案里的两句话

| 方案原文 | 实测 | 应改为 |
|---|---|---|
| v12：「devportal 与 skill-sandbox 高度契合，市场基础设施已具备一半」 | 错。devportal 零连接产品，是协调平面窗口 | 市场基础设施与 devportal 无关 |
| v22/v32：「devportal 18 个页面没有发布路径，所以市场要从零建」 | 结论对，理由错 | **不是 devportal 缺了发布路径，是 devportal 根本不是市场** |

措辞要改，因为「缺发布路径」暗示补一个页面就行，而真实情况是市场是另一件东西，
需要另外的受众、数据源与可见性模型。

**唯一的例外值得注意**：`/a/:handle/:agent`（agent 数字分身页）已经在做
「公开展示一个 agent 资产」这件事。它是未来 MAAU 市场最接近的雏形——
如果要建市场，从这里长出来比从零开始近。

## 4. 定位设计

### 4.1 主张

**devportal 的协作层与平台层划进「不交付 · 内部运营平面」，与协调平面同归属。**

理由三条：

1. **数据上它就是协调平面的前端**，零连接产品，模块知识库自称「只读窗口」。
2. **它已经在 Cloudflare 上**（Pages + edge runtime + Access），与协调平面同一朵云。
   v32.1 已把协调平面划进内部运营平面，前端跟着走是一致的。
3. **受众是我们自己和我们的 agent**，不是客户。

### 4.2 公开层要单独处置

它与上面两层在**归属、受众、可见性、数据源**四件事上都相反，不该共享一个域与一道门禁。

| 方案 | 做法 | 代价 | 评价 |
|---|---|---|---|
| **A 拆域** | 协作层+平台层留 `develop.boardx.us`（整域 Access）；公开层迁独立公开域，无 Access | 一次域名与部署拆分 | **建议**。四个页面的设计意图明确，门控已就绪，只差一个能被访问的域 |
| B 砍掉 | 删除公开层四个页面 | 浪费已有的设计与门控 | 除非确定不做对外面 |
| C 维持 | 一个域，公开层永远到不了公众 | 零成本，但留一个永久空洞 | **不可接受**：它让「默认公开」这句话长期为假 |

选 A 还有一个额外收益：公开层是**产品/生态**归属，拆出去之后，
devportal 剩下的部分归属干净，不再横跨两类。

### 4.3 演进方向：现在不要插件化

模块知识库提到对照 Backstage 的插件模式。**现阶段不建议**：
Backstage 的插件化解决的是「多个互不相干的数据源要进同一个门户」，
而 devportal 今天只有一个数据源（协调平面）。
插件框架在只有一个插件时是纯成本。触发条件写清楚：
**当出现第二个与协调平面无关的数据源时再评估**。

## 5. 建议的改动

1. `open-source-business-model.md` 的两处措辞（见第 3 节）。
2. 归属表「不交付 · 内部运营平面」一行补入 devportal 的协作层与平台层。
3. 新增决策 **D13：公开层拆域还是砍掉**。
4. 模块知识库那个占位符，用第 1.3 节的三层表填上。

## 6. 尚未核实

- **公开层迁出后的域名与 ICP 备案**：对外公开域在中国的备案要求，未查。
- **Access 的 bypass 规则**：仓库里**没有任何 Access 策略声明**（grep 无命中），
  策略只存在于 Cloudflare Zero Trust 控制台。CI 冒烟断言根域 302 说明整域确实有门禁，
  但**是否已为 `/explore` 等路径单独配了 bypass，仓库里看不出来**。
  若已配，第 2 节的张力即不存在——请以控制台为准核对一次。
- **`CF_ACCESS_AUD` 未启用**：README 记载部署用的 API token 无 Access 读权限，
  aud 校验待人类提供后在 `wrangler.toml` 取消注释。未配置时只验 issuer 与签名，
  同团队域下的其他 Access 应用签发的 JWT 可能通过。这是**独立于定位的一个安全待办**，
  顺带记在这里。
