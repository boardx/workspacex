# 超级实例（Super Instance）结构设计

> 2026-09-23 · 研究稿，待人类决策。
> 起因：D14 的答案不是「用」或「不用」，而是**既是也不是**——
> 它首先是一个 WorkspaceX 实例（所以是 dogfooding），
> 同时是产品栈之上的一个扩展，跑在边缘，并连接到所有客户实例。
> 本文把这句话拆成可实现的结构，并标出它和已定边界打架的地方。

---

## 0. 先把「既是也不是」拆开

这句话之所以不自相矛盾，是因为它说的是**三层不同的东西**，之前被压成了一个问题：

| 层 | 是什么 | 在哪 | 开源？ |
|---|---|---|---|
| ① **产品本体** | 一个货真价实的 WorkspaceX 实例，跑我们自己这个组织。**平台大脑用的就是产品的组织大脑能力**（同一套本体表），只是装的对象多了所有客户实例 | 可移植层（任何能跑 PG 的地方） | 开源那部分就是开源的 |
| ② **运营扩展** | 装在①上的闭源扩展：车队视图、事故面板、GTM、CRM 看板、发布控制台 | 与①同栈（扩展不是另一个系统） | **闭源，不交付** |
| ③ **边缘呈现与联邦** | Workers / DO / Pages：汇聚、路由、缓存、定时、对外呈现 | **Cloudflare** | 闭源，不交付 |

**所以三句话都成立**：它基于我们自己的产品（①）；它是产品栈上的扩展（②）；它在 Cloudflare（③）。
此前我把这三件当成一件来回答，才会得出「用了就不在 Cloudflare」这种二选一。

⚠ **本文推翻 v32.5 的 D14 结论**（「不 dogfooding」）。那个结论建立在一个错误前提上：
以为「用自家产品」与「在 Cloudflare」互斥。它们不互斥——**前提是分清哪一层在哪**。

---

## 1. 为什么不能整个搬上 Cloudflare（这条是硬约束，不是偏好）

`architecture.md` 只有一条硬约束：**禁止把业务逻辑绑死在单一云的专有原语上**。
`knowledge-ontology.md` 把它具体化为：

> canonical 永远是 Postgres 关系表，图和向量都是可重建的投影——**这让整套东西保持可移植**

组织大脑要的是 `ontology_objects` / `ontology_edges` / `context_nodes` / `ontology_actions`
四张 PG 表 + pgvector + Apache AGE。**Cloudflare 上没有这三样**：Durable Object 的 SQLite
不是 PG，没有 pgvector，没有 openCypher。

把①搬上去 = 用专有原语重写 canonical = 违反唯一硬约束，并且让我们自己的实例
和卖给客户的实例**跑在两套不同的东西上**——那就不再是 dogfooding 了，
是「做了一个像我们产品的别的东西」。

**结论：① 留可移植层，③ 在边缘。**
这不是妥协——本体架构自己就说图与向量是「可重建的投影」，
**边缘承载的一切都是投影**，正好落在它已经画好的那条线上。

---

## 2. 「超级实例」的正确定义

不是「能看到所有客户数据的那个实例」。是：

> **把每一个客户实例当作一等实体，建模进自己组织大脑的那个实例。**

已有的本体模型不用改就能装下它——只是多一类对象和几条边：

```
客户组织 ──has_instance──▶ 客户实例 ──running──▶ 版次/版本
                              │
                              ├──emitted──▶ 健康信号 / 错误指纹
                              ├──enabled──▶ 能力开关 ──defined_by──▶ 技能包
                              ├──raised──▶ 事故 ──caused_by──▶ 发布 ──contains──▶ PR ──verified_by──▶ 证据
                              └──in_stage──▶ 商机阶段
```

右半边（发布 / PR / 证据 / ADR）**已经在图里了**——那正是平台大脑。
接上左半边，两者在**同一张图**上。

这一步是整个设计的价值所在，也是「为什么我们自己必须用自己的产品」的硬答案：

> 运营要回答的问题天然是**图问题**，不是检索问题。
> 「这个客户装的是哪版 → 那版有哪个已知缺陷 → 是哪个 PR 引入的 → 谁决定的 → 证据在哪 → 还有哪些客户中招」
> ——这是一条 6 跳路径，每一跳都是**边**。

`knowledge-ontology.md` 写着「纯向量 RAG 对组织本体这种强关系数据会丢关键结构
（谁决定的、被什么取代、证据在哪是边，不是文本相似度）」。运营正是这种数据。

**销售问答因此反转了**：不再需要解释「为什么我们自己不用」，
而是可以说「**我们用得比任何客户都重——我们用它管所有客户**」。

## 3. 联邦层：连到所有客户实例（新东西，最需要设计）

仓库现状（实测，注意不要多读）：`cloud-deploy` 能按 `projectName` provision **彼此独立的具名部署**
（八阶段 preflight → secrets → migrate → bootstrap → readiness → business-probe，各带 compose / nginx /
TLS / 备份 / 密钥）。**这是「一客户一实例」所需的机制，但不等于今天已经这么用**——
现有调用面向我们自己的生产。设计按「客户各有实例」推进时，这是要新接的那一段，不是已有事实。
跨**组织**已有平台级（`platform-members`：平台超管看所有组织）；
跨**实例**目前**不存在**。这是要新建的部分。

### 3.1 方向：出站上报，不是入站抓取

**运营面没有任何对客户实例的读权限。** 客户实例主动 push 到边缘收集端点。

理由不是洁癖，是三条各自独立成立的：

1. **信任**：自托管客户之所以自托管，就是为了「你进不来」。一个能反向读实例的控制面，
   把自托管降级成「托管，但机器是我买的」。开源叙事当场崩掉。
2. **爆破半径**：边缘被攻破时，攻击者拿到的是已上报的聚合，不是一把能读遍所有客户库的钥匙。
3. **网络现实**：客户实例多在内网 / VPC，本来就不可入站。

这条已有先例：`AGENTS.md` 的运营纪律写着「**不能让生产反过来依赖运营面**」——
方向纪律本来就是单向的，这里只是把它延伸到跨实例。

### 3.2 传什么：信号，不是内容

| 上报 | 不上报 |
|---|---|
| 实例的不可逆 ID、版次（`DeploymentEdition`）、版本、部署形态 | 任何客户内容：会话、文档、画布、产出物、组织大脑里的材料 |
| 健康：可用性、延迟分位、队列深度、磁盘水位 | 任何自然人信息：成员姓名、邮箱、头像 |
| 用量**计数**：run 数、token 聚合、技能包命中次数、座席数 | 用量**明细**：谁在什么时候跑了什么 |
| 错误**指纹**：堆栈哈希 + 错误码 + 版本，不带参数 | 错误**现场**：请求体、参数、日志原文 |
| 能力开关状态、迁移版本号 | 密钥、令牌、连接串 |

判据一句话：**能不能从上报里重建出客户的一句话？能就不许传。**

### 3.3 `personal-local` 一行都不上报

`identity.ts` 已经定死：`kind = "personal-local"` 的组织是「数据不出本机」的产品承诺，
「对任何他人不可见，**包括平台运营**」，连 `listPlatformMembers` 都不列它们。

联邦层必须**继承**这条，不是重新决定一次。它在上报端就要被排除，
而不是在边缘过滤——排除发生在数据离开客户机器之前。

### 3.4 同意不能坍缩成一个布尔

`consent-item.ts` 是全仓唯一事实源，它的核心论断是：四项同意管四件不同的事、
**下游出口互不相同**，所以不能合并成一个「同意/不同意」。

跨实例上报是同一个形状的问题。**照抄那个结构**，而不是发明一个 `telemetry: true`：

| 项 | 不给的后果 |
|---|---|
| `health` | 我们看不到这个实例是否活着 ⇒ 不承诺主动发现故障 |
| `usage` | 无用量计数 ⇒ 计价只能靠合同约定，不能按量 |
| `diagnostics` | 无错误指纹 ⇒ 报障时要客户自己捞日志 |
| `benchmark` | 不进跨客户对标基线 ⇒ 也拿不到「你比同行慢在哪」这类回馈 |

四项独立，逐项可撤。**每一项都要有一个客户看得见的开关，和一句「关了会失去什么」。**

### 3.5 边缘存的都是投影

边缘（DO / KV / D1）持有的每一样东西都必须能从客户上报 + 可移植层重建。
边缘数据**丢光是可恢复事件，不是数据丢失**。

这不是额外纪律——本体架构自己的话：「图和向量都是可重建的投影」。
边缘只是第三种投影。

## 4. 扩展怎么接：用已有的 seam，不 fork

「在产品栈上拓展」如果做成 fork 一份代码，半年后两边就漂了。仓库里已有的扩展面：

| seam | 现状 | 运营扩展怎么用 |
|---|---|---|
| **技能包**（`capability_id`、`SKILL.md`、`skill-sandbox`） | 运行时围绕它建 | 运营能力做成**闭源技能包**：车队巡检、事故归因、GTM 归因 |
| **签名分发**（`SkillStarterPack` / `UnsignedSkillStarterPack`、`coord-gateway/signature.ts`） | 已有签名与导入 | 闭源包走同一条签名通道，不另开后门 |
| **纯函数 + DO 宿主**（`coord-brain`：零 IO、零 Workers 依赖、可任意环境单测） | 已落地 | 联邦判定逻辑照此办理：规则是纯函数包，边缘只是宿主 |
| **版次契约**（`DeploymentEdition`） | 已是单源 | 加一个版次值来标记「这是运营实例」，而不是到处 `if (isOps)` |

`coord-brain` 这个先例特别值钱：它证明了**业务判定可以完全不碰 Cloudflare 原语**，
DO 只做取快照、调函数、写结果。联邦层照抄这个形状，硬约束就不会再被碰。

## 5. 四种死法（写在前面，不是事后复盘）

| 死法 | 怎么发生 | 现在就挡住 |
|---|---|---|
| **超级实例变成客户的单点** | 运营面下线，客户实例跟着不可用 | 联邦最终一致、可离线；客户实例**不得**有任何指向运营面的必需依赖。加门控：扫客户侧代码不许出现运营面地址 |
| **「运营客户数据」被照字面实现** | 有人把客户内容同步上来做"全局洞察" | §3.2 的判据进门控：上报 schema 做白名单，新增字段要过评审 |
| **个人信息随上报出境** | 上报里带了成员邮箱 | 上报 schema 字段级检查人名/邮箱/电话形态即红（v32.3 已列，仍未建） |
| **边缘成为跨客户高价值目标** | 一次边缘失陷 = 所有客户的运营画像 | 边缘只存投影与不可逆 ID；跨客户对标只出分位，不出可指认的单点 |

## 6. 与已定边界的关系：一处冲突，必须先答

v32.5 刚定的三层边界里有一条：**受托于客户的数据不能上边缘。**

而「用来运营我们将来所有客户数据的一个东西」这句话，照字面读是**要把客户数据集中上来**。
这两条不能同时成立。

本文按**前者**设计——运营的是**客户实例的运行事实**，不是**客户的内容**。
理由在 §3.1：反过来做会摧毁自托管与开源叙事的前提，那是整个商业模式的地基。

**如果本意确实是后者**（集中客户内容做跨客户分析），那不是一个架构选项，
是一次**商业模式换道**：从「你的数据在你那」换成「你的数据在我这」。
它会同时推翻开源方案的归属表、数据边界、以及对自托管客户的全部承诺——
需要作为一条独立决策重新走一遍，不能夹带在结构设计里通过。

→ **新增决策 D16：联邦层运营的是运行事实，还是客户内容。**

## 7. 分期（每期都能独立停下来）

| 期 | 做什么 | 停在这里也成立吗 |
|---|---|---|
| **S1** | ① 立起来：一个真实 WorkspaceX 实例跑我们自己的组织，现有的 ADR / 方法论 / 经验迁进它的本体表，平台大脑从这里起步 | 成立。dogfooding 已经发生，联邦一行没写 |
| **S2** | 上报契约定稿：schema + 四项同意 + `personal-local` 排除 + 字段白名单门控 | 成立。有契约无实现，但契约是公开承诺 |
| **S3** | 客户实例侧上报器（出站、可关、可看见传了什么） | 成立。数据上来了，边缘还没有 |
| **S4** | 边缘收集与投影：Workers 收、DO 聚合、Pages 呈现车队 | 成立。这是第一个看得见的运营价值 |
| **S5** | 客户实例进组织大脑成为一等实体，接上 6 跳路径检索 | 这一步才兑现 §2 的价值 |
| **S6** | 运营扩展技能包化：巡检、归因、GTM | — |

**S1 和 S2 不依赖任何未决决策，可立即并行。** S3 之后都要等 D16。

---

## 8. 一句话总结

> 平台大脑**用的就是**我们自己产品的组织大脑能力（是）；
> 运营能力是产品栈上的闭源扩展，不是另一个系统（是）；
> 边缘承载的是它的投影与联邦入口，不是它的 canonical（不是）；
> 联邦联的是**客户实例的运行事实**，不是**客户的内容**（这条待 D16 确认）。
