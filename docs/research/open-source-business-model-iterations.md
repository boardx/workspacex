# 开源商业模式方案 — 十轮迭代记录

> 配套文档：`open-source-business-model.md`（v11，已吸收本文全部改进）。
> 规则：每轮找出 10 个问题并给出改法。问题尽量锚定仓库真实事实，标注出处；
> 找不到出处的判断标注「假设」。本文是**过程记录**，不是权威结论；权威在主文档。

| 轮次 | 主题 | 致命级发现 |
|---|---|---|
| 1 | 事实与证据 | 方案建立在未核实的产物上（通用 compose 不存在） |
| 2 | 法律与合规 | git 历史未做凭据扫描就谈公开仓库 |
| 3 | 财务模型 | 没有单位经济模型，免费层可能亏穿 |
| 4 | 竞争与定位 | 通篇讲怎么切分，没讲为什么有人选它 |
| 5 | 社区与治理 | harness 流程对外部贡献者是劝退级门槛 |
| 6 | 技术执行 | 内部过程文档与证据在同一个仓库里，公开前必须清洗 |
| 7 | 决策表 | 决策表默认了结论，没有「不开源」对照项 |
| 8 | 路线与度量 | 退出判据不可机械检查，违反项目自己的铁律 |
| 9 | 风险 | 最大风险「开源后无人问津」没被正面处理 |
| 10 | 可执行性 | 读完不知道下一步做什么 |

---

## 第 1 轮 · 事实与证据

方案里的每一句断言，能不能在仓库里找到出处。

| # | 问题 | 证据 | 改法 |
|---|---|---|---|
| 1 | 宣称发 Apache-2.0，但全仓**没有任何 package.json 带 `license` 字段**，2160 个已解析依赖没有许可证清单，无法确认可否再分发 | `grep '"license"' apps/*/package.json packages/*/package.json` 无输出；`pnpm-lock.yaml` 2160 条 `resolution:` | P0 增加「依赖许可证盘点 + SBOM 生成 + `lint-license-compat` 门控」，作为开源的**前置条件**而非附属 |
| 2 | `@firecrawl/anydoc` 等第三方包可能不可随产品再分发 | `apps/skill-sandbox/package.json` | 依赖三分类：可随源码分发 / 需替换 / 改为运行时按需下载；逐个给结论 |
| 3 | 方案完全没提这是**中国部署优先**的项目 | `deploy/` 下只有 `aliyun`；CI 有 `deploy-cn-production.yml`、`prepare-cn-release.yml` | 开源策略拆成中国与海外双轨，社区、渠道、合规各自成节 |
| 4 | 263 个源文件硬编码 `workspacex`，品牌与代码强耦合 | `grep -ril workspacex apps packages` = 263 个文件 | 提取品牌常量；评估白标成本；在商标政策里写明 fork 须改名 |
| 5 | 退出判据写「docker compose 一键起」，但仓库里**没有通用 compose**，只有阿里云部署脚本 | `deploy/aliyun` | 把「造出通用 compose」列为 P2 的工作项，不是判据前提 |
| 6 | 断言 phase-16/17 行业 agent 可闭源，但没核实它们与核心的耦合度 | 未勘探 | 先做可分离性勘探，再承诺闭源；耦合太深就只能先开源或先解耦 |
| 7 | 「17 个 skill / 20 个模板 / 45 个工具」抄自提案文档，是**静态痕迹不是动态事实** | 违反 `AGENTS.md` 的 static-trace-vs-live-fact 铁律 | 改为脚本机械清点，数字带生成时间 |
| 8 | 座席价、6-12 个月冷启动期等数字没有任何出处 | — | 全部标注「假设」，并给出验证方法与验证时间点 |
| 9 | 现有 CI 的 real-model evidence workflow 依赖真实模型 key，开源后外部贡献者的 CI 跑不了 | `real-model-chat-evidence.yml` 等 6 个 workflow | 公开 CI 默认走回环模型 lane；真实模型 lane 仅内部触发 |
| 10 | 没有任何基线指标，无法判断任何阶段是否成功 | — | 开源前先测一次基线：部署数、贡献者、issue 响应时间、客户数 |

## 第 2 轮 · 法律与合规

| # | 问题 | 改法 |
|---|---|---|
| 11 | 商标未定策略，而品牌名深嵌代码 | 制定商标政策：代码 Apache-2.0，名称与 logo 保留；fork 须改名 |
| 12 | 无 CLA/DCO，历史提交的版权归属不清 | 开源前做 provenance 审计：所有历史作者是否可授权 |
| 13 | **只检查 HEAD 不够**，凭据可能在 git 历史里 | 全历史 secret 扫描（gitleaks/trufflehog）+ 必要时重写历史或从干净仓重新发布 |
| 14 | 专利策略未定，Apache-2.0 自带专利授权与反诉终止条款 | 明确接受，并在决策表标注不可逆 |
| 15 | 出口管制与制裁合规（中美双向）未评估 | 法务确认分发管辖；加密相关代码单独看 |
| 16 | 中国 ICP 备案、数据出境、个人信息保护法对托管云形态的约束未提 | 中国云与海外云分别列合规清单 |
| 17 | **D6 选 DCO 与「将来可能改许可证」互相矛盾** | 明说取舍：DCO 摩擦小但放弃改许可证的权利；要保留就必须 CLA |
| 18 | GitLab 模式下 EE 源码公开可见但不可用，许可措辞与执行手段未定 | EE 目录单独 LICENSE，文件头声明，CI 校验，并接受只能防君子 |
| 19 | 第三方 Skill 造成损失时的责任归属未定 | 市场条款 + 责任限制 + 审核标准，上线前定 |
| 20 | 金融客户的 AI 输出合规（免责、留痕、可解释）没进 EE 功能清单 | 加入 EE：输出留痕、引用强制、审计导出 |

## 第 3 轮 · 财务模型

| # | 问题 | 改法 |
|---|---|---|
| 21 | 没有单位经济模型，不知道一个活跃用户每月烧多少推理成本 | 建最小模型：每用户月均 token × 单价 = 变动成本，对照定价 |
| 22 | Cloud Free 有真实推理成本，免费层可能亏穿 | 明确配额、超限降级到小模型、而不是直接断服务 |
| 23 | 定价梯度缺「从免费到付费的转化墙」 | 定义具体的墙：第二个组织成员、云端深度研究次数、数据保留期 |
| 24 | 没有现金流时间线，P0-P5 约 8-10 个 sprint 期间靠什么活未说 | 加一条：实施与定制收入承担前 12 个月现金流 |
| 25 | 「不要变成外包公司」没有可执行阈值 | 设硬阈值：实施收入占比超过 60% 触发复盘 |
| 26 | Skill 市场抽成比例未定，平台自营与第三方的冲突规则未定 | 定抽成区间，并承诺自营 skill 与第三方同等排序规则 |
| 27 | 企业年费与实施费分账、续费率假设缺失 | 列出假设值并标注为待验证 |
| 28 | 没有止损条件 | 写明：12 个月后自助付费为零则回退到纯服务模式或闭源 |
| 29 | 同一张价格表在中国与海外都不对 | 双市场分别定价，货币与支付通道分开 |
| 30 | 开源本身的成本（社区运营、issue 响应、安全响应）未计入 | 加一行人力预算：至少 0.5 FTE 社区 + 0.2 FTE 安全响应 |

## 第 4 轮 · 竞争与定位

| # | 问题 | 改法 |
|---|---|---|
| 31 | 未做竞品对位，Dify/Coze/FastGPT/OpenWebUI 已占「开源 AI 应用平台」心智 | 加竞品表，明确我们不是通用 agent 平台 |
| 32 | 通篇讲怎么切分，没讲**为什么有人选它** | 补定位句：以证据为中心的研究与投研工作台，不是 chatbot 搭建器 |
| 33 | Context Engine 是最强差异点，却只在护城河里一句带过 | 提升为定位核心：不可变原件 + 血缘 + 可引用片段，别家没有 |
| 34 | 与上游模型厂商的关系未定：伙伴还是被替代 | 明确定位在模型之上的工作流层，适配器保证可换 |
| 35 | 中国开源获客路径与 GitHub star 逻辑不同，方案只有一条路 | 双渠道：GitHub/HN 海外，Gitee/掘金/公众号/线下沙龙国内 |
| 36 | 垂直选择（投研/IC/投后）未验证市场规模与获客可行性 | 先做 5 家目标客户访谈，再决定 D4 |
| 37 | 没有回答「为什么不会被大模型厂商内建功能吃掉」 | 答案是数据与合规的归属：私有证据库与审计留痕不会交给模型厂 |
| 38 | harness 作为第二产品与主产品争夺同一批工程资源 | 明确 harness 只做「顺手开源」，不投入专职资源，除非主产品站稳 |
| 39 | 没有「谁会 fork 我们、fork 之后怎么办」的推演 | 加对抗推演：最可能的 fork 诱因是 EE 切线移动 |
| 40 | 没有定义品类名，用户搜什么词能找到你 | 定品类词，它决定 README 第一行与所有渠道文案 |

## 第 5 轮 · 社区与治理

| # | 问题 | 改法 |
|---|---|---|
| 41 | 治理模型未定（BDFL / 技术委员会 / 基金会），企业客户会问 | 起步 BDFL + 公开决策记录（ADR 已有），写进 GOVERNANCE.md |
| 42 | **harness 流程对外部贡献者是劝退级门槛**（必须有 issue、进 sprint、过 verify） | 设外部贡献快车道：小改动只需 PR + CI 绿，不走 sprint |
| 43 | 文档主要是中文，双语策略与维护成本未定 | 英文只维护入口层（README/CONTRIBUTING/契约文档），深层容忍中文 |
| 44 | 开源项目需要公开 roadmap，但 `phases/` 是内部节奏 | 定映射规则：公开 roadmap 只露 phase 目标与季度，不露内部 feature |
| 45 | 无 SECURITY.md、无 CVE 流程、无披露时限 | P0 就写，这是企业客户的硬门槛 |
| 46 | 发版与兼容性承诺（SemVer、LTS、破坏性变更政策）缺失 | 契约单源正好让 API 兼容性可机械 diff，把它做成发布门控 |
| 47 | 社区与公司边界未定：谁能 merge，EE 团队与 OSS 团队关系 | 写明合并权归属与利益冲突处理 |
| 48 | 「开源但不接 PR」是反感点，却没有对应的 SLA | 承诺首次响应时间，并公开达成率 |
| 49 | 行为准则与争议处理缺失 | CODE_OF_CONDUCT.md，标准模板即可 |
| 50 | **agent 生成的 PR 在开源社区的标识与接受度未定**，这是新问题 | 公开披露 agent 参与度，PR 标注生成来源，人类维护者负最终责任 |

## 第 6 轮 · 技术执行可行性

| # | 问题 | 改法 |
|---|---|---|
| 51 | `ee/` 与现有 `lint-arch-deps` 的关系未定：EE 也守洋葱分层吗 | 守。EE 是 infrastructure/interface 的扩展，同样禁止反向依赖 |
| 52 | 许可证校验可被绕过（删掉校验即可） | 明确威胁模型：防君子不防小人，靠合同而非技术 |
| 53 | 多租户是 EE，但 RLS 在 OSS 的 PG 层，边界切不干净 | OSS 保留单租户 RLS 基座，EE 只加租户路由与配额 |
| 54 | 计量事件要不要在 OSS 版发出（隐私）未定 | OSS 版默认不发，遥测 opt-in，代码里可见可审计 |
| 55 | **内部 evidence/、phases/、docs/reports/ 含大量内部过程与可能的客户信息** | 公开前做仓库清洗计划，HEAD 与历史都要洗 |
| 56 | 开源仓与内部仓的同步机制未设计 | 单向：内部为源，定期推公开仓；避免双向 merge 地狱 |
| 57 | 桌面版的模型权重分发（许可与体积）未评估 | 不打包权重，首次启动按需拉取；评估权重许可 |
| 58 | skill-sandbox 依赖容器与 `network:none`，Windows 桌面能否成立未验证 | 桌面版先降级为受限执行，或要求本机 Docker |
| 59 | 依赖 Cloudflare 的部分让自托管者被迫绑云 | 邮件等能力抽成适配器，提供 SMTP 默认实现 |
| 60 | 证据体系依赖真实模型 key，外部 CI 跑不了 | 公开 CI 默认回环模型；真实模型 lane 内部触发 |

| # | 问题 | 改法 |
|---|---|---|

| 82 | **最大风险是「开源后无人问津」，方案没正面处理** | 列为头号风险，并配采用率的早期信号与应对 |
| 83 | 竞争对手照抄行业 Skill 接口并自建 | 接受；靠评测集与数据积累而不是接口保密 |
| 84 | 开源后攻击面公开，而 skill-sandbox 执行模型生成的代码 | 安全响应流程与沙箱加固列为 P1 |
| 85 | 2160 个依赖的供应链风险，开源后成为攻击目标 | 依赖锁定、自动更新、SBOM、签名发布 |
| 86 | 关键人风险：单一决策者兼单一维护者 | 至少两名有合并权的维护者，写进治理文档 |
| 87 | 社区分叉风险的触发条件未识别 | 最常见诱因是 EE 切线移动，承诺切线只进不退 |
| 88 | 中美双边政策风险对「开源 + 云」组合的影响 | 双轨部署与双轨社区，降低单边依赖 |
| 89 | 模型供应商成本波动未对冲 | 适配层已解决技术替换，商业上加成本上浮的定价条款 |
| 90 | agent 生成代码在开源社区可能被质疑质量 | 用证据体系正面回应：每个 feature 带可复现验证 |

## 第 10 轮 · 可执行性与文档本身

| # | 问题 | 改法 |
|---|---|---|
| 91 | 读完不知道下一步做什么 | 文档第一屏给「今天就能做的三件事」 |
| 92 | 只有抽象阶段，没有 90 天计划 | 加 90 天计划 |
| 93 | 决策与证据混在一起，决策者要翻全文 | 加一页纸摘要节 |
| 94 | 没区分「零成本、低风险、现在就能做」的动作 | 单列无悔动作：license 字段、SECURITY.md、SBOM、依赖盘点，不等决策 |
| 95 | 文档事实与仓库事实会漂移，违反「同一事实不得声明在两处」 | OSS/EE 归属表落到 `PROJECT.md`，本文只引用；加脚本核对 |
| 96 | 没有把方案转成 issue/feature 的路径，而项目规则要求开发在 GitHub 可见 | 明确：批准后按阶段开 issue，一 issue 一 PR |
| 97 | 缺术语表 | 加 OSS / EE / open core / source-available 的精确定义 |
| 98 | 假设与事实未分离标注 | 全文事实带出处，假设带标签与验证方法 |
| 99 | 没有版本与变更记录 | 加版本号与本迭代记录的链接 |
| 100 | 结论过于确定，缺「什么证据下我会改变主意」 | 加证伪条件节 |
