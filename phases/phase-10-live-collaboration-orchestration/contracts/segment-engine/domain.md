# `segment-engine` — 不变量

1. **环节状态只有一个事实来源**：`listAgendaSegments`/`advanceAgendaSegment`（F963 已接）。
   （怎么断言：对比主持台全场视图与任一分组视图渲染出的环节标题/序号/剩余轮次字段，逐字节相等；
   出现不一致即视为编排层建了第二份副本，判失败。）
2. **只有引导师能推进环节**（F119 已限定，本束不改变这条，只在编排层复用）。
   （怎么断言：以组长/组员/观察者身份调用 `advanceAgendaSegment`，断言被拒绝，不是 200。）
3. **倒计时字段在真正接入前不得渲染编造数值**：占位必须带明确的"待补契约"视觉标记（`＊`），
   不得渲染一个看起来像真实倒计时的数字。（怎么断言：`getSegmentCountdown` 端口未落地期间，
   状态条组件源码里倒计时展示分支必须能追踪到明确的 mock/占位标记，不是硬编码的动态数字。）
4. **"第X组需介入" pill 同理，无判据来源期间不得渲染**：只能展示占位或完全不展示，
   不得基于任何猜测规则（如"该组消息量低于阈值"）自造判据冒充真实告警。
   （怎么断言：审查该 pill 的渲染条件，确认其数据来源可追溯到一个已签核的契约字段，
   而不是编排层自己算出来的启发式规则。）

## [待定] 未决项（不阻塞开工，需人类在签核时一并给答案）

- `getSegmentCountdown` 最终应该长在 phase-01 议程契约里（扩展 `listAgendaSegments` 返回形状），
  还是本束新开一个独立只读端口——两种方案对前端状态管理的复杂度不同，需要架构层面拍板。
- 倒计时的"重置"时机（环节推进后立即重置 vs 服务端下一次轮询才反映）目前 requirements 只说
  "环节推进后立即重置"，具体是靠 WebSocket 推送还是前端轮询，未定。
