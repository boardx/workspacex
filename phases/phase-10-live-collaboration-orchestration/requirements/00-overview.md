# 原始需求 — Phase 10 现场协作编排（总览）

> 这是一份**大白话需求**，给 requirement-author 读的输入，不是权威。权威是同目录生成出的 `../feature_list.json`。

## 为什么要单独立一个 phase（不是塞进 phase-01 或 phase-02）

- 人类在 2026-08-20 的会话里明确要求：把「项目 → 现场协作」Tab 的开发**从 phase-01 挪出来**，新建一个 phase 承接，并且**先做完整规划再开始开发**。
- 排查发现这块从来没有被真正 spec 过：
  - `phases/phase-01-run-a-project/requirements/06-itv/uc-6-4-现场记录与-ai-副驾驶.md` 反复强调「项目 → 现场协作主持台（引导师视角、四组并行、广播、介入建议）**是另一个屏、另一个用例**，不是 UC-6.4 的原型依据」——即承认存在但从未落成一份 UC 文档。
  - `phases/requirements/DECISIONS-FINAL.md` D-41、`DECISIONS-DELTA.md` 同样只是"提醒不要混淆"，没有给出这个屏自己的规格。
  - 唯一落地的代码/feature 是 `phases/phase-01-run-a-project/feature_list.json` 里的 **F963（已 passing）**：把主持台状态条接了真实的 `listAgendaSegments`/`advanceAgendaSegment`，并把"四组并行"整块降级为诚实空态（因为素材充足度、现场介入标记等字段在仓库里找不到任何契约出处）。这正是当前生产环境里能看到的样子（黑条 `NO_PROJECT_ROLE` 错误 + "画布/转写接线未完成，暂不可用"）。
- 同时，这个 Tab 需要聚合的能力散落在**已经存在或已规划**的多个 phase 里：
  - phase-00 共享内核：Segment/Anchor/角色 RLS。
  - phase-01：议程环节引擎（`listAgendaSegments`/`advanceAgendaSegment`，F90/F102/F119/F148/F963 已 passing）、画布（canvas 束，F100-F107 已签核）、转录（recording 束，F69-F79 已签核）、与 AI 的对话（08-chat）。
  - phase-02：知识图谱节点/关系/决策树领域模型（F11/F15/F16）、看板（F02）、下一步可开展的工作（F17）、批量确认写回（F18）——**目前整个 phase-02 状态是 `not_started`，`contracts/` 只签了 survey 一个束**。
  - phase-06/07/08/09：深度研究、用户访谈、转录、问卷（含"现场投票"F07）——2026-08-20 之前已从 phase-02 拆出，各自独立维护，`depends_on: ["00"]`。
- **本 phase 的范围因此被刻意收窄为"编排层"**：不重新定义知识图谱/看板/问卷/研究/访谈/转录各自的领域模型（那些各自的 phase 是单一事实源），只做：
  1. 现场协作 Tab 的**视角切换器**（主持台·全场 vs 分组）与**角色可见性**（引导师/组长/组员/观察者）。
  2. 议程环节引擎在现场的**呈现与推进控制**（在 F963 已完成的真实状态条基础上，把"四组并行"从空态升级为真实卡片——但只有当画布/转录束真正给出仓储实现后才能这么做，见下面的硬前置）。
  3. **分组签到**（链接/二维码/成员到场状态）——这是全新领域，之前完全没有 spec。
  4. **分组视角的五模块侧栏**（与 AI 的对话 / 用户访谈 / 深度研究 / 问卷 / 本组图谱）——每个模块本身的领域逻辑分别属于 08-chat（phase-01）、phase-07、phase-06、phase-09、phase-02（知识图谱），本 phase 只做"哪个分组在哪个环节能看到哪些模块的哪些卡片、卡片怎么路由到各自模块"的编排与路由。
  5. **主持台·全场三视图**：看板聚合（消费 phase-02 F02 的领域数据）、知识图谱决策推演聚合（消费 phase-02 F11/F15/F16/F17 的领域数据）、分组签到聚合。

## 角色与视角模型（大白话）

四个角色：**引导师（Facilitator，人类或 AI 代理）**、**组长**、**组员**、**观察者**。

- 引导师：唯一能看到"主持台·全场"视角的角色；同时可以切到任意一个分组视角查看/介入（原型原文"同一个界面，你有全部权限：四组对话、原始转写、切环节与介入"）；唯一能推进议程环节（`advanceAgendaSegment`，F119 已限定）。
- 组长：只能看自己所在分组的视角；能代表本组做"批量确认与写回"（对应 phase-02 F18，跨 phase 依赖，不在本 phase 重做）。
- 组员：只能看自己所在分组视角，可读写自己有权限的模块卡片（如新建对话、参与问卷）。
- 观察者：只读；具体能看到哪个粒度（全场只读 vs 分组只读）需要在契约设计阶段裁定，本文档不预判。

视角切换器有两档：
1. **主持台·全场**：三个子视图——看板 / 知识图谱·决策推演 / 分组与签到。
2. **分组·N组·当前议题（可带状态后缀，如"推演中""缺1人""需介入"）**：五个模块侧栏——与AI的对话 / 用户访谈 / 深度研究 / 问卷 / 本组图谱。

## R1 环节引擎的现场呈现（复用已有能力，不重造）

黑色常驻状态条：`环节 N/M · 环节名A→环节名B · 剩余倒计时` + 告警 pill（"第X组需介入"）+ `+5分钟` `下一环节` 按钮。这条状态条 F963 已经把标题/序号/推进动作接了真实数据；本 phase 要补的是：
- 倒计时（`listAgendaSegments` 目前只给 `{title, state}`，没有剩余时长字段——如果要倒计时，需要先跟 phase-01 议程束确认要不要补这个字段，本 phase 不能自己编一个假的服务端字段）。
- "第X组需介入"这类告警的判定依据（目前全仓无来源，同 F963 处置纪律）。
- 组长/组员/观察者视角下这条状态条的降级展示（F963 已删除的 `ROLE_OWN_GROUP`/`ROLE_SEES_ALL_RAW` 需要重新设计，不是简单复原旧 mock）。
