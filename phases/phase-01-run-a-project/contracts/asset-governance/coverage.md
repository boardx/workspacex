## 🔴 本文现在不是覆盖证明，是**覆盖缺口清单**

按 `verify-uc-coverage` 的两个方向：

- **UC → API**：某条验收线索找不到对应 API ⇒ **接口不够，业务跑不通**
- **API → UC**：某个 API 操作没有任何 UC 要它 ⇒ **接口是多余的，或有 UC 没写**

**本束现在两个方向都不成立**，原因**不是材料没写完**：

| 阻塞 | 后果 |
|---|---|
| **Q-0 未裁**（本域三件事与已拍板的 D-06 正面冲突） | `usecases.md` 第二节那 **10 个端口是否存在都未定**。给它们做覆盖映射 = 给一个可能整体不存在的范围做证明 |
| **feature 未生成** | `covers: []`。覆盖证明的粒度是 feature，没有 feature 就没有可映射的对象 |
| **Q-1b 未裁** | 「六种资产共用治理字段」这条核心不变量的适用范围未定（代码侧现状 3/6）。它决定 `SetAssetGovernance` 是一个端口还是六个 |
| **Q-12 未裁** | 「数据总览」的屏内容归 phase-01 还是 phase-03 未定 ⇒ `uc-23-8` 的覆盖边界未定 |

按本仓纪律（`contracts/project/design-signoff.md` 的先例），
**宁可让缺口有名字、会在每次 `doctor` 里出现，也不要为了消红填一张假的映射表。**

## 二、依赖 Q-0 的部分：**不做映射**（并说明为什么）

`uc-23-1` / `uc-23-2` / `uc-23-5` / `uc-23-7` 共 **55 条** R12 线索
（14 + 15 + 14 + 12），全部落在 `usecases.md` 第二节那 10 个端口上。

**本文刻意不为它们出映射表。** 理由：

> 给一组「是否存在都未定」的端口做覆盖证明，产出的是一张**看起来已经论证过的表**。
> 本仓有过完全同形的事故——「编了一个数值制造出已算过的假象」。
> 一张假的覆盖表比一个有名字的缺口糟得多：缺口会在每次 `doctor` 里出现，假表不会。

Q-0 裁决后：
- 裁 **A（整体进 phase-1）** ⇒ 补齐这 55 条的映射，本文改为完整覆盖表。
- 裁 **B（整体推 phase-2）** ⇒ 这 55 条随 UC 移出 phase-01，本文只保留第一节。
- 裁 **C（推荐：拆）** ⇒ 保留 `uc-23-3/4/6/8`（56 条）＋ 一条子裁决决定
  `uc-23-1` 的三条非外部路径与 `DetectUsageCrystallizationCandidates` 的去向。
