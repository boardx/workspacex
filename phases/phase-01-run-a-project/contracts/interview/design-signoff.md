# 契约束 `interview` 设计签核

覆盖 feature：**F80–F99**（20 件 / **68 点**，phase-01 全量 111 件中最大的一束）
依据 UC：`06-itv/uc-6-0` ~ `uc-6-7` **共八份**
（Studio 列表与范围 · 新建访谈模板 · 研究设计 · 受访者授权 · 现场记录与 AI 副驾驶 ·
回流成洞察 · 受访者自助门户 · 访谈对象表）

## 这个束为什么是这个边界

按**能力域**切，判据是「**这些东西的不变量互相依赖吗**」。八份 UC 被一条链串起来：
`对象表 → 模板 → 研究设计 → 授权 → 现场 → 回流 → 门户`，而**同意位**这一个值对象
同时是其中**五份** UC 的硬约束输入（采集门 / 输入门 / 归纳过滤 / 回流过滤 / 门户改选择）。
拆开会立刻出现「A 束签了，B 束签的时候发现 A 的不变量不够用」——例如把「受访者授权」单列成束，
那么「现场不得开始」「副驾驶取不到片段」「归纳跳过该人」三条断言就分散到三个束里各判一次，
**这正是 O-05 明令禁止的「出口遮盖」的组织形态版本**。

⚠ 68 点 / 20 feature 是一个**很大的束**。若人类判断评审负荷过重，可考虑的切法是
`interview-core`（F80–F85 F90–F92 F97–F99）+ `interview-consent`（F86–F89 F93 F95 F96），
**但必须接受同意位的不变量跨两束**——本文不推荐，理由如上。

## ③ API 契约 —— 对外形状与错误码对不对

**本束有对外 HTTP 面。** 第 ③ 件的落点是：

```
packages/contracts/src/interview.ts        ← 尚未创建
```

⚠ **本轮只是骨架，这个文件还不存在。** 它是**签核通过后、开工时的第一件产出**，
且必须先于任何前端 mock —— 因为：

> `apps/web/lib/mock/interview.ts` 与 `apps/web/lib/mock/entry.ts` **都是手写 mock**，
> 而它们对「受访者同意的四项是哪四项」给出了**两个互不相同、且都与 UC-6.3 不一致**的答案。
> `contract-design.md` 硬规则第 2 条「不许手写 mock」防的就是这件事，**而它已经发生了**（见下）。

### 签核前请重点确认

- [ ] **`ConsentKey` 枚举的封闭性**：`{record, transcript, ai_analysis, attribution}`，新增须走 ADR。
      断言写法必须是**集合断言 + 未声明值被拒**，⚠ **不要写 `toHaveLength(4)`**
      （那会让一个经 ADR 评审的正当新增被自己的测试拦下，E-4 的教训）。
- [ ] **响应体也要被契约校验**（`contract-design.md` 硬规则第 6 条）。本束尤其是：
      「受访者端响应体**不含**任何 AI 建议字段」（I-34）与「令牌失效时响应体**不含**任何访谈内容」（uc-6-6/V9）——
      这两条都是**关于「不该有什么」的断言**，请求侧的 ValidationPipe 一个都管不到。
- [ ] **错误码与别束的一致性**：`REQUIRES_PINNED` 与 artifact 束**同码同义**（D-30）。
      同一种失败在不同束里必须是同一个错误码 —— 这正是阶段一致性复核要查的四条之一。
- [ ] **不要在契约里重新声明阈值**：5（普遍性断言）· 8（跨组织聚合）· 0.45（相关度）· 240 秒 · 2 条/分钟 ·
      180 天（材料保留期）**全部是别处的单源**。O-16 原话是「全仓不出现第二个聚合门槛值」。

## ⚠ 必须先裁的三件事（不裁则本束多数 feature 无法验收）

### 1. 「授权 N/4」的四项，仓库里有**三个互相冲突的版本**

| 出处 | 四项内容 |
|---|---|
| **UC-6.3**（人类 2026-07-27 拍板，写在 UC 开头并明说旧版「**是错的**」） | 录音 / 转成文字稿 / **交给 AI 分析** / 报告中署名与职务 |
| `apps/web/lib/mock/interview.ts` 的 `AUTHORIZATION.items`（＝ ui-preview 的 **S-09**） | 录音 / 转文字稿 / **引述** / **内部复用** |
| `apps/web/lib/mock/entry.ts` 的 `SESSION.grants` 与 `/consent` 屏 | 录音 / 转文字稿 / 实名引用 —— **只有三项** |

**最危险的不是不一致，是「交给 AI 分析」这一项在已建成的界面里根本不存在**，
而 **O-05 的全部合规约束都挂在它上面**：不进副驾驶输入、不进归纳、不进回流自动填充、
per-speaker 前置过滤（F93）。这一项不落地，F86 F87 F88 F93 F95 F99 全部无法验收。

⇒ 收敛为单一事实源 `packages/contracts/src/interview.ts` 的 `ConsentKey`，两份 mock 从契约生成。
**这是本仓「同一事实声明在多处」的第六次复现，且已经漂移了。**

### 2. **场景角色**（研究员 / 受访者 / 观察员 / 记录 agent）不在 `ProjectRole` 四值里

现有实现另开了 `?view=` 预览轴（ui-preview **S-03**），但它**在生产构建下不可达**，是预览不是权限。
本束**八份 UC 各有一条 V-权限态**要求按这些角色做**服务端**断言 —— 没有角色本体就没有断言。
与 **S-02**（合规负责人缺位，动摇了 O-03）是同一个问题的两面，请**合并裁决**。

### 3. `verify-uc-coverage.ts` 对本束 5/8 份 UC **是空转的**

门控用 `^-\s*(V\d+)` 抓 R12，不认加粗写法 `- **V1（…`。
本束 8 份 UC 里 **uc-6-0 / uc-6-3 / uc-6-4 / uc-6-6 / uc-6-7** 都是加粗写法 ⇒ 门控报「R12 共 0 条」⇒
**107 条验收线索中的 69 条（64%）当前不受任何机械保护**，coverage 表里一条不写也照样绿。

⚠ 同一个脚本在**读表格**时专门加了容忍加粗的分支，注释还写着「本脚本第二版就因此误报 web-kernel 漏 10 条」——
**一侧修了，另一侧没修。** 这是门控缺陷不是 UC 缺陷；本文件已把 107 条**全部**列进 `coverage.md`。
修法：`^-\s*\*{0,2}(V\d+)`。⚠ **修完必须立刻造一次反证**（故意删掉 coverage 表某一行，确认门控转红），
否则又是一次「全绿但空转」—— 本仓已经发生过九次。

## 确认动作

并填 `confirmed_by` / `confirmed_at`（**ISO 8601，且不得晚于当下**）。

⚠ **这是人的动作，不是 agent 的**（ADR-023 决策五：`status` 是整条签核链唯一的信任根，
由 `.github/CODEOWNERS` + CI 保护）。在此之前 `new-sprint` 与 `claim` 都会拒绝把 F80–F99 开进 sprint。
签核之后还需 **阶段一致性复核**（`phases/phase-01-run-a-project/design-coherence.md`，
其 `covers_bundles:` 必须包含 `interview`）通过，feature 才可开工。
