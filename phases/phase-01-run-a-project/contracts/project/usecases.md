## 三、失败模式（已签核的部分 + 待裁的部分）

### 已在契约里、本束必须同码同义引用

| 失败码 | 语义 | 状态 |
|---|---|---|
| `NO_PROJECT_ROLE` | 无项目角色 —— **正常状态不是异常** | 已定 |
| `PROJECT_ROLE_INSUFFICIENT` | 有角色但该角色不含此动作 | 已定 |
| `ADMIN_NOT_SUPERUSER` | 管理员越过项目层读内容（`purpose != "audit"` 时） | 已定 |
| `STEP_CLOSED` | 目标环节已关闭，拒绝绑定 | ⚠ **契约里有，今天不可评估** → Q-2① / Q-8 |
| `STEP_REJECTS_ARTIFACT_TYPE` | 目标环节不接受该来源类型 | ⚠ **同上** → Q-2③ / Q-8 |
| `AUTH_SERVICE_UNAVAILABLE` | 判定服务不可用 —— **一律拒绝，不得降级放行** | 已定 |

### 本束将新增的失败码（形状待裁，此处只登记「会有」）

- 创建项目相关：待裁决 → **Q-1**
- 归档 / 解档相关：待裁决 → **Q-5**（若裁「不做生命周期」则一个都不会有）
- 父子项目相关（环、跨组织、深度超限）：待裁决 → **Q-12**（仅在裁 E 时才存在）

⚠ **不要预先把这些码写进 `packages/contracts/src/project.ts`。** 一个不会被任何路径抛出的
错误码读起来像覆盖，而它什么都没覆盖——这正是 `0008-f06-binding-modes.sql:29-31` 记下的形状：
*a check that cannot fail is worse than an absent one, because it reads as coverage.*

### 三条**必须双向**的反证断言（单向会全绿）

- **V4 / V5（两个失败码）**：构造 closed 环节 → 断言 `STEP_CLOSED`；**再**构造 open 环节 →
  断言成功。只有前者时，「永远返回 `STEP_CLOSED`」的实现也会全绿。
- **V8（临时提权按流程节点失效）**：以**正常结束 / 提前结束 / 跳过 / 合并**四种方式各终结一次，
  断言四种均立即失效；**再**断言环节仍进行时该权限**有效**——
  只有单向断言时，一个「从不授权」的实现也会全绿。
- **V15（不存在的路由）**：若 Q-9 裁「不提供删除」，断言 `DELETE /projects/*` **不在路由表里**。
  理由逐字照抄 N-5：「**『没有』这件事本身没人会去验**，某天有人为别的需求加上，
  不会有任何东西报警。」
