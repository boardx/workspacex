# 契约束 `chat` 设计签核

覆盖 feature：**F108 F109 F110 F111 F112 F113 F114 F115**（合计 **24 点**）
依据 UC：`08-chat/uc-8-1 对话卡片列表` · `uc-8-2 全屏对话窗口` · `uc-8-3 对话产出落地` ·
`uc-8-4 预设对话下发` · `uc-8-5 对话可见性规则`

## 这个束为什么这样切

按**能力域**切：这八件的不变量互相依赖，拆开会立刻出现「A 束签了，B 束签的时候发现 A 的不变量不够用」。

- **可见性（F108）是其余七件的地基**：uc-8-1/8-2/8-3/8-4 的 R5 全部逐字写着
  「本 UC 只调用 UC-8.5 的判定结果，不重复定义」。可见性若单独成束，
  列表过滤、观察者降级、草稿仅创建者可见、预设下发范围校验四处会各自长出一份角色语义——
  **这正是本仓最高发的「同一事实声明在两处」**。
- **批准卡（F112）依赖工具调用链（F111）的血缘落点**：批准卡的「调用链」一项就是
  `provenance_events` 的一段投影，两者共用同一份 append-only 事件流。
- **产出落地（F114）依赖消息与引用（F111/F113）**：出处回链 = 对话 id + 消息 id + 引用清单，
  引用不可定位则不得定版。
- **预设（F115）是 F110 + F108 的实例化**：预设实例继承 uc-8-2 全部规则，
  下发校验调用 uc-8-5 的可见性判定。

## ② 用例 —— 用例接口与失败模式穷举对不对

材料：本束 [`usecases.md`](./usecases.md)（27 个用例，失败模式逐条穷举）。
支撑：[`domain.md`](./domain.md)（33 条不变量，每条附一行「怎么断言」）。

### 签核前请重点确认

- [ ] **观察者降级是「服务端不下发」，不是「前端隐藏」**（uc-8-5 R3 步骤 6、V3）。
      `usecases.md` 的 `getThreadDetail` 对观察者返回的是**投影后的响应体**——
      原始转写字段、私聊消息、写能力标记**不在响应体里**，不是置成 `disabled: true`。
      ⚠ 这条最容易被「前端已经不渲染了」糊弄过去，验收必须是 API 层断言。
- [ ] **管理员的越权断言方向被 O-04 反转过**。管理员读项目层对话内容应当
      **返回内容 + 一条审计事件**，**不是 403**（uc-8-5 R5 / V4，早期稿本的「一律不可读」已撤回）。
      写测试的人若照旧稿写 `expect(403)`，会写出一个**断言错误方向的绿灯**。
- [ ] **「组长能看本组组员私聊」是反直觉的，且尚未定告知方式**（uc-8-5 R7、R10 [待确认]）。
      契约上它是硬规则；产品上它是隐私承诺问题。**是否要对组员显式告知、告知在哪、文案是什么**，
      本轮没有依据，`domain.md` 记为 `[待定]`。
- [ ] **批准闸门的失败模式**：并发批准（V17）、超时过期（V4/E1e）、预算耗尽转「等待输入」（V4b）、
      改参生成新卡而非就地改写（V2）、`[不用了]` 后动作永不执行（V2）。
      **「暂停 → 披露 → 人选 → 转后台」四段缺一不可**，这是产品的信任核心（uc-8-2 R11 明写它必须独立验收）。
- [ ] **主动发言取不到来源时的行为是「不发言」，不是「发一条空来源消息」**（uc-8-2 V6）。
      契约上它意味着 `proactiveSpeak` 有一个**正常返回但不产生消息**的出口，不是错误。
- [ ] **产出落地不自建机制**（D-38）。三模式绑定、快照不可变、引用资格门控全部委托
      phase-00 `artifact` 束的 `bindToProjectStep` / `pinVersion` / `referenceForDownstream`。
      要签的是：**对话侧只做入口与出处回链**，没有第二套版本机制。

## ③ API 契约 —— 对外形状与错误码对不对

**本束有对外 HTTP 面。** 第 ③ 件的落点是：

```
packages/contracts/src/chat.ts        ← 尚未创建
```

⚠ **本轮只产出骨架（本目录 5 份 markdown），`chat.ts` 尚不存在。**
它是**签核通过后、F108 开工时的第一件产出**——先写 zod 单源，再由它生成
后端 DTO / 前端 client 类型 / OpenAPI / **前端 mock**（`.harness/instructions/contract-design.md` §一）。

⚠ **现在 `apps/web/lib/mock/chat.ts` 是手写的**，且里面已经住着五个**事实上的后端契约函数**：
`dataScopeConstraint` / `modelPolicyViolation` / `isModelSelectable` / `modelLine` / `budgetLine`。
它们从未作为契约被评审——这正是 ADR-020 立论举的那类例子。
`chat.ts` 落地时这份 mock 必须改为**从契约生成**，手写副本收敛掉。

### 签核前请重点确认

- [ ] **🔴 `含机密 ⇒ 整轮走本地` 还是 `机密走本地、云端并存承接非机密`——两个口径，必须二选一。**
      - `feature_list.json` F112 与 D-U1 写的是「**含机密⇒整轮走本地**，不是分流，
        后端 gateway 按同一规则拦截」；
      - `ui-preview/README.md` **S-01** 白纸黑字说原型**字面矛盾**（同时印「gpt-5.2 ＋ 本地 qwen3-32b」
        和「含机密，仅本地模型」），而**实现取的口径是「机密只路由本地、云端可并存承接非机密」**，
        故 `modelPolicyViolation()` 只在「有机密但无任何本地模型」时报违规。
      - **两者会做出两个不同的 gateway。** 这条不是文案问题，是拦截规则。
      - ⚠ **这是跨束交叉约束**：`agent-runtime`（模型网关 / model registry）束会写同一条。
        **两边都指向本条裁决，不各自定义一份口径。** 详见 `domain.md` I-20 与「跨束交叉约束」节。
- [ ] **「高影响动作」的判定表缺失**（uc-8-2 R10 [待确认] / O-26）。
      已裁决的只有原则（「R1/R2/R3 按操作类型自动推导，外发邮件恒 R3、读公开资料恒 R1，
      任务模板可覆盖」），**完整映射表没有**。契约上批准卡「不自行定义风险等级，只呈现判定结果」，
      所以这张表是**别人的输入**，本束缺它就无法穷举「哪些调用会停下来」。
- [ ] **错误码语义跨束一致**。本束的 `REQUIRES_PINNED` / `SNAPSHOT_IMMUTABLE` / `ARTIFACT_NOT_FOUND`
      必须与 phase-00 `artifact` 束**同码同义**，不得在 `chat.ts` 里另起一份名字。
      同理 `NO_PROJECT_ROLE` / `CROSS_GROUP_DENIED` 与 `identity` 束。
- [ ] **响应体也要被契约校验**（`contract-design.md` §五-6）。
      本束的观察者投影是**减字段**——若只校验请求体，服务端多下发一个 `rawTranscript`
      **不会有任何门控变红**，因为前端类型也从同一份契约生成。
      观察者路径必须有 `out.safeParse()` 的**反向断言**（证明 schema 确实会拒绝多余字段）。
- [ ] **token 折算金额的单价与汇率来源**（uc-8-2 R10 [待确认]）：取自 model registry 已定，
      但**是否按组织可配**没有答案。`budgetLine` 现在读的是 mock 常量。

## 确认动作

人类逐节核对上面三节后，把 frontmatter 的 `status` 改为 `confirmed`，
并填 `confirmed_by` / `confirmed_at`（ISO 8601，**不得晚于签核当下**）。

⚠ **这是人的动作，不是 agent 的。** agent 不得代劳，该字段受 CODEOWNERS + CI 保护
（ADR-023 决策五）。在此之前 `new-sprint` 与 `claim` 都会拒绝把 F108–F115 开进 sprint。

⚠ 另需注意：**第 ① 件（UI）目前只覆盖 F114 / F115 两件。**
`ui-preview/chat/` 已有 18 张真实截图（`/chat/landing` 9 张 + `/chat/preset` 9 张），
但 **`/chat` 主屏零张**，F108 F109 F110 F111 F112 F113 的界面材料是空的，
缺口逐条记名在 `ui.md` 第四节 G-01 ～ G-23。

若在 `/chat` 主屏仍无截图的状态下把 `status` 一次性签成 `confirmed`，
等于把 ADR-003 想防的事对这六个 feature 再犯一次
（「feature_list 在任何人看到真实界面之前就被定成权威」）。
**要么先补画 `/chat` 主屏截图，要么在签核时显式接受「这六件不看图就签」并留下书面理由**——
但不要让缺口以「已经有 18 张图了」的方式被数字掩盖。
