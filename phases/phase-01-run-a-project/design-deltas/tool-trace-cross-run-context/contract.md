## §0 背景（实测，见 uc-8-10 §0）

`agent_run_steps` 表（`kind='tool_call'`）已经记录 `tool_name`/`tool_args_summary`/
`tool_result_summary`/`planning_note`（各 ≤1000 字符），数据已采集、已持久化，只是从未被
下一轮 run 的历史组装（`pg-agent-run-repository.ts:519` 的 `readThreadHistory`）读取过——
跨 run 时这部分信息只存在于审计快照里，不进入驱动下一轮生成的上下文。

## §1 R4 五个待设计问题的裁定（人类 2026-08-16 决策）

### ① 范围窗口
**裁定：最近 N 轮 run 的 tool_call，N 默认取 3。**
- 支持：单轮直接追问（"你刚才查到的"）与跨十轮的慢任务都能覆盖到，不像"只读上一次 run"
  那样在第 2 轮之后立刻断链。
- 代价（已知晓、接受）：预算占用比"只读上一次"更大，需要靠 §2 的裁剪顺序 + 去重兜底。
- N=3 是初始默认值，不是永久锁死——后续如证明覆盖不足或预算吃紧，可在不重新走本 delta
  签核的前提下由实现者按运维数据小幅调参（±1），调整超出此范围需回到本 delta 重签。

### ② 与 L1/L2/L3 的预算优先级
**裁定：排在 L2（持久摘要）之后、L3（文件检索）之前。** 预算紧张时的裁剪顺序（从先保留到
先被裁）：**L1 > L2 > 工具轨迹 > L3**。
- 支持：L1/L2 是「这条线程实际说了什么」的直接记录，信息密度最高，永远优先；工具轨迹是
  "上一步做过什么"的辅助信息，重要但不如原文/摘要基础；L3 是主动检索来的补充材料，预算
  紧张时最先让路。
- 去重规则（避免与 L1 重复）：若某轮 run 仍落在 L1 的近端窗口内，**跳过该轮的工具轨迹**
  （因为 L1 原文已包含触发该次工具调用的用户消息与最终回复文字，信息更完整）；只在该轮
  run 已滚出 L1 窗口、只剩 L2 摘要覆盖时，才为其补上工具轨迹伪消息。

### ③ 个人线程是否适用
**裁定：适用，一视同仁。** 工具调用轨迹的读取范围严格限定 `thread_id == 本线程`，是本线程
自己产生的数据，不属于跨范围检索，与 F156 delta 的硬边界 `cross_scope_retrieval_requests
== 0` 不冲突——个人线程与项目线程使用同一条回喂路径，不额外分叉。

### ④ 降级/可审计
**裁定：复用 F157 `agent_run_context` 快照结构，新增一个来源字段（如
`toolTraceSources: { runIds: string[], stepCount: number }` 或等价结构，具体字段名由实现者
在不引入第二套记录方式的前提下决定），不另建新表/新的审计记录路径**——同一事实不得声明
在两处。

### ⑤ 失败模式
**裁定：`agent_run_steps` 读取失败时，降级为跳过这一类来源、不阻断 run**，与 L2 摘要读取
失败的既有降级策略一致；快照里如实记录"本次因读取失败跳过了工具轨迹来源"，不伪造成"本来
就没有"。

## §2 边界（本 delta 明确不做的事）

- 不改 `ModelCallInput`/`ModelCallPort` 契约——工具轨迹仍以 `role+content` 形态的伪消息注入
  `history`，同 L1/L2/L3 的既有边界。
- 不改 `agent_run_steps` 表结构、不新增列——数据已经在那里，本 delta 只加一条读取+组装路径。
- 不改变 F156 delta 已签的召回边界。
