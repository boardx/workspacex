# 验收口径 · 工具调用轨迹跨 run 回喂上下文

规范以 [`contract.md`](./contract.md) 为准。以下是 F190（原 F185，重编号见 design-signoff.md）的验收改写口径（真栈反证，不伪造）。

## V1（跨 run 可见）——上一轮的工具调用对下一轮可见
- 构造：同一线程内，第一轮 run 触发至少一次 `tool_call` step（有 `tool_name`/
  `tool_args_summary`/`tool_result_summary`）；第二轮 run 就该结果发问，且不在第二轮的
  用户消息里逐字复述第一轮的工具结果。
- 断言：第二轮 `ModelCallInput.history` 包含一条源自第一轮工具调用的伪消息，内容含
  `tool_name` 与 `tool_result_summary` 的关键信息。
- 反证：把回喂路径去掉，第二轮 history 里不出现任何工具轨迹，本断言当场红。

## V2（范围窗口 N=3）——超出窗口的轮次不回喂
- 构造：同一线程连续 4 轮 run，第 1 轮触发 tool_call，第 2-4 轮不触发。
- 在第 5 轮 run 时检查 history。
- 断言：第 1 轮（已超出「最近 3 轮」窗口）的工具轨迹**不再**出现在第 5 轮的 history 里。

## V3（与 L1 去重）——仍在 L1 窗口内的轮次不重复注入
- 构造：某轮 run 触发 tool_call，且该轮距当前 run 足够近，仍落在 L1 近端原文窗口内。
- 断言：该轮的工具轨迹**不**作为独立伪消息注入（避免与 L1 原文重复）；该轮工具调用的信息
  只经由 L1 原文可见。

## V4（预算裁剪顺序）——预算紧张时 L1/L2 优先于工具轨迹，工具轨迹优先于 L3
- 构造：人为压低单次 run 的上下文预算，使其不足以同时容纳 L1+L2+工具轨迹+L3 全部候选。
- 断言：裁剪顺序为 L3 先裁、工具轨迹次之，L1/L2 最后才裁；`agent_run_context` 的
  `omissions`（若既有结构支持）或等价字段记录被裁掉的工具轨迹来源，不静默丢弃不留痕。

## V5（个人线程适用，不破 F156 边界）
- 构造：个人线程（无项目）内两轮 run，第一轮触发 tool_call。
- 断言：第二轮能看到第一轮的工具轨迹（本线程范围内，适用）；同时
  `cross_scope_retrieval_requests == 0` 仍成立（F156 delta 硬边界不受影响）。

## V6（可审计）——F157 快照记录工具轨迹来源
- 断言：某次 run 的 `agent_run_context` 快照里能读出"这次喂了几条工具轨迹、来自哪几次
  run"，字段复用 F157 既有快照结构追加，不存在第二套记录方式。

## V7（失败降级，不阻断 run）
- 构造：模拟 `agent_run_steps` 读取失败（如查询超时/异常）。
- 断言：run 本身不失败、正常产出回复；快照如实记录"本次因读取失败跳过了工具轨迹来源"，
  不伪造成"本来就没有工具轨迹"。
