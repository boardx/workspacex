# 🔴 Q-1 项目怎么创建？只能套蓝本，还是可以空白新建？

> **推荐：C（一条创建路径 + 蓝本可选参数）** —— 创建事务只有一处（identity.ts:602-605 的教训），
> 且「没有蓝本」是能被表达出来的正常值而非一个假蓝本。
> 🔗 上游：**Q-12**（若项目有类型，须补答两类项目是否都套蓝本）。

## 现状
- 契约里**只有蓝本一条路**：项目唯一的出生路径是
  `phases/phase-01-run-a-project/requirements/02-tpl/uc-2-2-套用蓝本新建项目.md`，
  即套蓝本的副产品。
- 「谁能创建」已有答案：组织角色 `lead`（项目负责人）——
  `phases/phase-00-shared-kernel/requirements/00-core/uc-0-3-角色本体与两层权限模型.md:99`
  逐字写着「创建与管理项目」。
- 空白新建**已被提出但标记为未确认**：uc-2-2 的 `A4`（`:174-175`）
  ——「**[设计]** 不套蓝本直接新建空项目：允许，但项目筹备页四子标签均为空态，
  不得伪造默认结构；此后可否补套蓝本见 R10 [待确认]」。
  `[设计]` 按该文件口径 `:11` 的定义就是「**需人类确认**」。
- 同文件 `:418` 另留一条 `[待确认]`：「空项目能否事后补套蓝本——若能，已有内容如何与默认值合并」。

## 候选

| | 方案 | 优点 | 缺点 / 风险 |
|---|---|---|---|
| **A** | **只能套蓝本**（含一个官方「空白蓝本」） | 创建路径唯一；六类初始化的事务写入（uc-2-2 E2「要么全成功要么整体回滚」）只需实现一次；项目必有 `blueprint_version_id`，`来自后台 vN` 的快照语义处处成立 | 「空白蓝本」是一个语义上的空壳，会诱导实现者给它塞默认值——那正是 uc-2-2 `V15` 要禁的「不生成示例分组或示例议程」；且后台需要维护一个谁都不该编辑的特殊蓝本 |
| **B** | **两条路径**：套蓝本 / 空白新建 | 贴合原型 A4；空项目是真实存在的低准备度形态（uc-2-2 `A2`/`:170-171` 举了原型实例「准备度 15% · 未邀请」） | 两条创建路径 = 两处要各自不出错。phase-00 已因同型问题写下纪律：`getLocalOrg` 明确**不创建**任何东西，「若这里也能创建，那就有了两条创建路径，而 I-2 要靠两处各自不出错」（`packages/contracts/src/identity.ts:602-605`） |
| **C** | **一条创建路径 + 蓝本可选参数**（`createProject(blueprintVersionId?: string \| null)`） | 只有一处创建事务；空白 = 传 null，六类初始化跳过而非写空值；与 D-17「artifact 的 projectId 可空」是同一种表达法 | 需要明确「未套蓝本」在项目上的表示（null 还是哨兵值）；补套蓝本仍需单独回答 |

## 我的推荐
**C**。理由不是"折中"，是它同时满足两条已有纪律：创建路径唯一（identity.ts:602-605 的教训），
且"没有蓝本"是一个能被表达出来的**正常值**而不是一个假蓝本
（同 `Artifact.projectId` 可空的处理法，`packages/contracts/src/artifact.ts:126-130`）。

## 连带必须一起答的
1. 空项目能否**事后补套蓝本**？若能，已有内容如何合并（覆盖 / 只填空缺 / 拒绝）？
   （uc-2-2 `:418` 已列为 `[待确认]`，本域不重复提问，只标记它阻塞 `uc-00-1`）
2. 组织角色 `lead` 之外，`admin` 能否创建项目？
   ⚠ 注意 `admin` 已被 D-18 定为「不是超级用户」
   （`phases/phase-01-run-a-project/requirements/01-auth/uc-1-4-角色可见性判定.md:131`），
   「能创建」与「能读内容」是两件事，但把它们混在一起是常见错误。
3. 创建者是否自动获得项目角色？uc-1-4 `:132` 说项目负责人「通常同时持有引导师，
   但两者是**独立授予**的」——「通常」不是规则。

## 待答 ①：环节实例是不是一张独立表？

| | 方案 | 优点 | 缺点 / 风险 |
|---|---|---|---|
| **A** | 独立 `agenda_stages` 表，`artifact_bindings.step_id` 加外键 | `STEP_CLOSED`/`STEP_REJECTS_ARTIFACT_TYPE` 立刻可判；孤儿绑定不可能存在；文件浏览器按环节分组有真实来源 | 要给 0008 补一次外键迁移（已有数据的 `step_id` 必须先有对应行）；phase-00 的绑定测试需要建环节夹具 |

## 待答 ②：状态集合与迁移规则

已知的约束点：需要能表达「进行中」「已结束」（`环节 3 结束`）、

| | 方案 | 优点 | 缺点 / 风险 |
|---|---|---|---|
| **A** | 三态 `pending → active → closed`，另加 `skipped`（终态） | 最小闭集；`STEP_CLOSED` 判据显然（`closed`/`skipped`）；「唯一驱动源」= 恰好一个 `active` | 「合并」表达不了（uc-1-4:99 明确要求合并也触发失效）——需要额外记「被并入哪个环节」 |

| **C** | 不建状态机，只记 `startedAt/endedAt` 时间戳 | 简单 | ⚠ **与 uc-1-4:98 正面冲突**：那里逐字写「失效条件是**流程节点**…**不是时间点**」。**不建议** |

**推荐**：环节持有一个 `acceptedSources: ArtifactSource[]`，**默认全接受**（空数组 = 不限制），

## 我的推荐
**A**，且**如果**产品确认「一场访谈确实要同时归属两者」，则**升级为 B**（不是跳到 C）。

理由三条：
1. **`kind` 作为一等字段而非两条代码路径**，在本仓已有先例并已 passing（组织的
   `organization` / `personal-local` 共用一张表与一套 RLS，`.../identity/domain.md:22-23`）。
2. **C 会撞已签闭集**：`acl_bindings.object_kind` 加第四种是签核动作，代价与收益不成比例。
3. **A → B 是加法不是重做**：先有 `kind`，再按需加第二个可空外键，
   两步都不推翻前一步。反过来（先 C 再合并）是返工。

⚠ **无论选哪个，请一并裁决三件事**，否则 F80 仍然做不下去：
1. **两级归属的可见性是交集还是并集？**

2. **「项目类型」影响不影响议程环节的定义？**（研究项目有没有议程环节？）
   ——它决定 Q-2 的环节实体要不要对某类项目可选。
3. **项目列表要不要按类型分区？** → 与 Q-6① 的两段式返回一并答。
