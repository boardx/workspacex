# 原始需求（细化）— UC-8.6 对话文件上传（附件）

> 所属：阶段一 · 能跑完一场项目 / M8 Chat
> 来源：`docs/proposals/PROP-CHAT-FILE-UPLOAD-001.md`（V9 设计 + §6 三件签核材料）
> + `phases/phase-01-run-a-project/contracts/chat-file-upload/design-signoff.md`（人类 2026-08-11「yes to all」确认参数=硬边界）。
> 人类 2026-08-11 亲口点名「期间要有文件上传的支持，上传各种文件」。

> 口径（四标记）：本 UC **无 `[原型]` 依据**——`components/chat/` 全域 grep `type="file"`/dropzone/attachment **零命中**（PROP §1 实测 origin/main）。
> 本 UC 的行为全部为 **[Backlog]**（proposal 文档要求）+ **[设计]**（反推补全），其**参数已由人类在束级 `design-signoff.md` 逐字签核**（confirmed，2026-08-11），故可开工；UI 尚未建，验收锚 API 层。
> 元数据：优先级 **P1**；估点 **10**；建议迭代 **迭代 4 · 能推演**（V9-a 上传骨架先行，V9-b 进 context 随 L3）。
>
> **[人类已签核 2026-08-11 · chat-file-upload 束]** 参数逐字为硬边界，实现者不得「优化」：
> 单文件 **25 MB**；MIME 白名单 **PDF / `text/plain`·`text/markdown` / 图片 `image/png`·`image/jpeg`·`image/webp` / Office `…wordprocessingml.document`·`…spreadsheetml.sheet`·`…presentationml.presentation` / `text/csv`**；
> 每消息附件数上限 **10**；保留策略 **随线程删除**（FK `ON DELETE CASCADE`，无独立生命周期）；
> 分期 **V9-a（上传+存储+预览）先行 / V9-b（文件内容进模型）随 chat-context-engine 束 L3 检索层**。

## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-8.6 / 对话文件上传（附件）
- **Actor**：**引导师**、**组长**、**组员**（有线程写能力者）；**观察者**（只读，不可传）。
- **目标**：用户在对话里给自己有写权的线程上传各种文件（文档/图片/表格），附件随消息落库、刷新仍在、随线程删除而级联清除；后续（V9-b）文件内容经检索层进模型上下文。
- **本用例结果**：一条消息可挂 1–10 个白名单类型、≤25MB 的附件；附件走服务端对象存储（复用 22-files 域存储，不新造）；无真实后端前不渲染假上传 UI。
- **系统边界**：新表 `chat_message_attachments`；上传端点 `POST /chat/threads/:threadId/attachments`（multipart）；`createMessage` 挂附件；`listMessages` 回读附件；composer 附件 UI；（V9-b）抽取管线 + 进 L3。
- **核心数据对象**：附件（id / org_id / message_id / storage_ref / filename / mime / bytes / extracted_ref / created_at）、消息、线程、线程写能力判定。

## R2 前置条件 / 触发条件

- **前置条件**：
  - 用户已建立可校验身份，且对目标线程持有**写能力**（`capabilitiesFor` / `resolveVisibility`，与 land-as-artifact 同一条写权规则）。
  - 目标线程存在且未被删除；对象存储能力（复用 22-files 域）可用，或界面明确显示不可用。
- **触发条件**：
  - [Backlog] 用户在 composer 点 📎 或把文件拖入输入区。
  - 系统携带当前组织、线程、角色标识进入上传流程。

## R3 主流程（编号步骤）

1. **用户操作**：在 composer 点 📎 选择文件，或把文件拖入输入区（拖入时高亮）。
   **系统响应**：[设计] 前端就地做**类型/大小/数量**预校验（软提示），但**权威校验在服务端**（R7）。
2. **用户操作**：确认上传。
   **系统响应**：调 `POST /chat/threads/:threadId/attachments`（multipart）。服务端**逐条强制校验**：actor 对该线程有写能力；`bytes ≤ 25MB`；`mime ∈ 白名单`；该线程已挂附件数 `< 10`。任一不满足返回明确错误码，**不静默丢弃**。
3. **系统处理**：校验通过则把文件写入对象存储（`storage_ref`），在 `chat_message_attachments` 落一行（`extracted_ref` 恒 `null`，V9-a 不抽取），返回 `{ attachmentId, filename, mime, bytes }`。
4. **用户操作**：连同消息发送——`createMessage` 带 `attachmentIds: string[]`。
   **系统响应**：服务端校验这些 id 属于该线程、且未挂到别的消息，落库 `message_id`；否则拒绝。
5. **系统响应**：`listMessages` 每条消息回读 `attachments: {id,filename,mime,bytes}[]`；刷新页面附件仍在。
6. **系统收口**：记录操作者/时间/对象/结果；composer 附件预览条显示文件名+类型图标+大小+✕移除。

## R4 备选流程与异常流程

- **备选**：A1 选中后发送前可逐个移除附件（✕）；移除仅去掉待发引用，不产生孤儿存储。
- **异常**：
  - E1（超限）大小>25MB / 非白名单 MIME / 该线程附件数已达 10 → 服务端拒绝，返回明确错误码，前端就地提示，**不静默丢弃、不伪装成功**。
  - E2（无写权）观察者或无写能力者上传被服务端拒（与 land-as-artifact 同一写权规则），返回权限错误。
  - E3（上传中断/超时）保留用户已选文件与输入，明确失败原因，允许安全重试；失败不得呈现为成功。
  - E4（发消息时附件不合法）`attachmentIds` 含不属于该线程或已挂别的消息的 id → 拒绝整条发送。

## R5 权限与可见性

- **写能力**：只有对该线程有写能力的 Actor 可上传并挂附件；**观察者不可传**。
- **可见性**：附件可见性沿用消息可见性（同 `acl_bindings` / `resolveVisibility`，见 UC-8.5）；文件浏览器（22-files）不是权限旁路。
- 所有权限判断在服务端执行；隐藏入口只是界面表现，不构成安全控制。

## R6 后置条件 / 不包含

- **正常后置**：附件持久存于对象存储 + `chat_message_attachments`；随消息可读；**随线程删除级联清除**（FK CASCADE）。
- **失败后置**：不创建「看似成功」的附件记录；无孤儿存储；失败进可观测日志。
- **不包含**：
  - V9-a **不含**「文件内容进模型」——那是 V9-b（R10 依赖 chat-context-engine 束 L3 层）。
  - 抽取器（PDF/OCR/表格）选型、多模态直传策略（本 UC 只到 `extracted_ref` 这一层）。
  - 独立于线程的附件生命周期（无独立保留期，随线程删）。

## R7 业务规则（不随实现变化的硬性约束 · 逐条来自 signoff，不得优化）

- [已签核] **单文件 ≤ 25 MB**——服务端强制，超限拒绝。
- [已签核] **MIME 白名单（保守起步）**：`application/pdf` / `text/plain` / `text/markdown` / `image/png` / `image/jpeg` / `image/webp` / `application/vnd.openxmlformats-officedocument.wordprocessingml.document` / `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` / `application/vnd.openxmlformats-officedocument.presentationml.presentation` / `text/csv`。白名单外一律拒。
- [已签核] **每消息附件数 ≤ 10**——服务端强制。
- [已签核] **保留策略 = 随线程删除**：`message_id`/`org_id` FK `ON DELETE CASCADE`；删除线程 → 附件行随消息级联删除，无独立生命周期。
- [设计] **写权规则复用**：上传与挂附件复用线程写能力判定（`capabilitiesFor` / `resolveVisibility`），与 land-as-artifact 同一条规则，不另立。
- [设计] **无真实后端不做假 UI**（本仓红线）：前端不做本地假预览充当上传成功；UI 与后端同批落地。
- [设计 · V9-b] `extracted_ref` 在 V9-a 恒 `null`；V9-b 抽取文本/OCR 后写入，作为进 **L3 检索召回层**的引用（`ModelCallInput`/`ModelCallPort` 不动，文件内容以检索片段进 history）。
- 任何上传、挂载、级联删除动作记录审计事件。

## R8 界面线索

- **前端入口**：[设计] composer 左侧 📎 按钮 + 拖拽区（拖文件到输入区高亮）；选中/拖入后在输入框上方显示附件预览条（文件名 + 类型图标 + 大小 + ✕ 移除）。
- **测试锚点（签核命名，V9-a UI 落地时创建）**：`chat-attachment-input` / `chat-attachment-chip-<id>` / `chat-attachment-remove-<id>`。
- **必须呈现的状态**：默认态、选中/拖入态、上传中（进度）、超限校验失败态（就地报错）、依赖失败态（存储不可用）、无权限态、成功态。
- **UI sign-off**：三件材料（UI/用例/API 契约）已在束级 `design-signoff.md` 由人类确认（confirmed 2026-08-11）。

## R9 非功能约束

- [设计] 上传 >1 秒显示进度；大文件不阻塞输入。
- 传输与静态加密、组织隔离（`org_id`）、AI 读取（V9-b）留痕。

## R10 已知约束 / 依赖

- **内部依赖**：UC-8.2（全屏对话窗口 composer）、UC-8.5（可见性判定）、22-files（对象存储，复用不新造）。
- **跨束依赖（V9-b）**：`chat-context-engine` 束的 **L3 检索召回层**（`uc-8-7` R4）——文件内容经抽取后进 L3，是 context engine 的第一个大客户。V9-b feature 依赖 V10 的 L3 接线 feature。
- **契约（ADR-020 单源）**：`packages/contracts/src/chat.ts` 加附件形状 + `uploadAttachment` 操作 + `createMessage`/`listMessages` 扩展；新 migration 建 `chat_message_attachments`。
- **[已裁决 O-01]** 审计留痕不可删；其余附件读材料保留期（默认 180 天），但 signoff 明确附件**随线程删**，不单独走保留期。

## R11 切分提示（给 requirement-author）

- **建议切法**：① 附件数据模型 + 上传端点（新表 + `POST .../attachments` + 服务端 25MB/MIME/≤10/写权四校验）→ ② 挂消息 + 回读 + 级联删除（`createMessage` 带 attachmentIds、`listMessages` 返回 attachments、FK CASCADE）→ ③ composer 附件 UI（📎/拖拽/预览条/移除/超限就地报错）→ ④【V9-b】抽取管线 + 进 L3 检索召回。
- **分期硬边界**：①②③ = V9-a（可先落地，不进 context，不占 execute-run.ts 串行窗口）；④ = V9-b（依赖 chat-context-engine 束 L3）。①②③ 与 ④ 必须是不同 feature 条目。
- **不重复实现**：对象存储复用 22-files，不新造；L3 检索复用 context-pack 引擎（`uc-8-7`），不重写。
- **优先级/依赖**：P1；共 10 点；在 UC-8.2 composer 之后；V9-b 在 `uc-8-7` L3 feature 之后。

## R12 AI Ready 验收线索

以下行为应可由 API 层自动化测试断言。**门控类断言全部在 API 层**，不依赖界面禁用。

- **V1（成功态 · UC1）**：作者对有写权线程上传一个 24MB、白名单类型文件 → 返回 `attachmentId`；`createMessage` 带该 id → `listMessages` 该消息 `attachments` 含此附件；重读（模拟刷新）仍在。
- **V2（超限拒绝 · UC3）**：分别上传 26MB / 非白名单 MIME（如 `application/x-msdownload`）/ 该线程第 11 个附件 → **三者都被服务端拒**，返回明确错误码，`chat_message_attachments` 行数**不增**。
- **V3（写权门 · UC2）**：观察者（无写能力）调上传端点 → 被拒（权限错误），无附件落库。
- **V4（级联删除 · UC4）**：给线程挂附件后删除线程 → `chat_message_attachments` 中该线程附件行数归 0（FK CASCADE），且对象存储引用不再被消息引用。
- **V5（挂载合法性 · E4）**：`createMessage` 带一个属于别的线程 / 已挂别的消息的 `attachmentId` → 整条发送被拒。
- **V6（composer UI · V9-a）**：composer 渲染 `chat-attachment-input`，选文件后出现 `chat-attachment-chip-<id>`，点 `chat-attachment-remove-<id>` 移除；超限就地报错不静默丢弃（web 组件测试）。
- **V7（V9-b · 本期不做）**：附件抽取文本进 L3 检索——`extracted_ref` 落库后，对含项目上下文的线程发问时该文件片段可被 L3 召回；个人对话零召回。
