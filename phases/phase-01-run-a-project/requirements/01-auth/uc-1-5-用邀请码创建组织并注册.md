# 原始需求（细化）— UC-1.5 用邀请码创建组织并注册

> 所属：阶段一 · 能跑完一场项目 / M1 登录管理
> 来源：`WorkspaceX Standalone.html` 登录页底部「还没有账号？**创建组织 · 需要 14 位邀请码**」；
> 说明页「已定下的四条规则」第 4 条：「**注册：邀请码或邀请链接**。只能被邀请入组织，两种入口：
> **14 位邀请码**、带组织与角色的一次性链接。」；后台「远洋咨询 · 组织 ID org_8f21」。
> **补写缘由**：原 8 份 M1/M2 用例中没有任何「创建组织 / 成为正式成员」流程，
> 按原文档做完迭代 1，系统里产生不出第一个组织与第一个人，无法端到端演示。

> 口径（四标记）：**[原型]** ＝ `WorkspaceX Standalone.html` **运行态实际存在**的行为（有界面可查，依据 scratchpad 的 proto-01~10 抽取档案）；**[Backlog]** ＝ `Backlog Use Case.html` 的**文档要求**（原型未必实现）；**[设计]** ＝ 依据前两者反推补全，**需人类确认**；**[待确认]** ＝ 不应由实现者自行决定。
> 元数据：优先级 **P0**；估点 **8**（原 5，2026-07-28 上调）；建议迭代 **迭代 1 · 能进场**。
> **估点变更说明**：O-12 裁定 `user ↔ organization` 为**一对多**，本用例须支持
> 「已有账号用新邀请码创建第二个组织」这条分支（不新建账号、只新建组织并授管理员），
> 并接入**顶部组织切换器**；O-29 另新增**邀请码 90 天有效期 + 批次追溯 + 吊销**
> 与**组织停用（只读 + 仅管理员可导出 + 留存期后销毁）**两条链路。
>
> **[人类已拍板 2026-07-27]** 认证方式采用**邮箱 + 密码**，注册时做**邮箱验证**；
> **不做邮箱验证码（OTP）登录**。本文按此口径书写。

## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-1.5 / 用邀请码创建组织并注册
- **Actor**：**组织创建者**（注册后即成为该组织首个管理员）、**平台运营方**（邀请码签发方）
- **目标**：[原型] 产品是**邀请制**的——不能自助开户。持有 14 位邀请码的人可以创建一个新组织，
  同时完成自己的账号注册，并成为该组织的第一个管理员。
- **本用例结果**：系统中新增一个组织（含组织 ID）与一个已验证邮箱的管理员账号，
  该用户登录后进入自己的空组织，可以开始邀请成员（UC-1.6）。
- **系统边界**：邀请码校验与核销、账号注册、邮箱验证、密码设置、组织创建、首个管理员授予。
- **核心数据对象**：平台邀请码、账号、邮箱验证令牌、组织、组织成员、角色。

## R2 前置条件 / 触发条件

- **前置条件**：
  - 用户持有一枚有效、未被核销的 14 位邀请码。
  - 用户的工作邮箱尚未被任何账号占用（若已占用走 A2）。
- **触发条件**：
  - [原型] 用户在登录页点击「还没有账号？创建组织 · 需要 14 位邀请码」。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

1. **用户操作**：输入 14 位邀请码。**系统响应**：校验邀请码格式、是否存在、是否在有效期内、
   是否已被核销；校验失败时按 E1/E2 处理，**不提示"码不存在"与"码已用过"之间的差别**（防枚举）。
2. **用户操作**：填写工作邮箱、姓名、设置密码。**系统响应**：校验邮箱格式与唯一性、
   密码强度符合策略；**此时不创建可用账号**，仅创建待验证注册记录。
3. **系统处理**：向该邮箱发送**验证链接**（非验证码）。界面提示「验证邮件已发送至 …，
   请在 24 小时内点击链接完成注册」，并提供「重发」入口（带频率限制）。
4. **用户操作**：点击邮件中的验证链接。**系统响应**：校验令牌有效性与时效；通过后激活账号、
   标记邮箱已验证。
5. **用户操作**：填写组织名称（及可选的组织简称）。**系统响应**：创建组织并分配组织 ID
   （[原型] 形如 `org_8f21`），把当前用户加入该组织并授予**管理员**角色，
   **核销**该邀请码使其不可再用。
6. **系统收口**：校验 AC1「一枚邀请码只能创建一个组织」；记录操作者、时间、邀请码、
   新组织 ID 与结果进审计。
7. **系统收口**：校验 AC2「注册完成后用户直接处于已登录态，落在自己的空组织首页」；
   刷新组织成员列表与配额初始值。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[原型] **另一条注册路径**——用户收到的是「带组织与角色的一次性链接」而非邀请码，
    则不创建组织，直接加入已有组织，走 **UC-1.6**。
  - A2：[设计] 邮箱已存在账号时，不新建账号，改为提示「该邮箱已注册，请登录后使用邀请码创建组织」，
    登录后可继续第 5 步。
  - A3：[设计] 用户完成第 4 步但未完成第 5 步就离开——账号已可用但无组织归属；
    再次登录时强制回到「创建组织」步骤，邀请码保持未核销。
- **异常流程**：
  - E1：[设计] 邀请码无效、过期或已核销时统一提示「邀请码不可用」，不区分原因；
    连续失败达阈值后对该 IP/会话限速。
  - E2：[设计] 邀请码在第 1 步校验通过、第 5 步核销时被他人抢先核销——以核销成功者为准，
    另一方明确失败并保留已注册的账号（无组织，走 A3）。
  - E3：[设计] 验证链接过期（超 24 小时）或已使用时，提供重新发送入口；
    注册记录保留不丢失已填信息。
  - E4：[设计] 请求超时、网络中断或依赖（邮件服务）不可用时，保留用户当前输入与最后成功状态，
    明确失败原因并提供安全重试；**邮件发送失败必须显式提示，不得静默成功**。
  - E5：[设计] 组织名称重复不阻断（不同组织可同名，以组织 ID 区分），
    但同一创建者下重名时提示确认。

## R5 权限与可见性

- **未登录访客**：可访问注册入口并提交邀请码；除自己的注册进度外不可读取任何数据。
- **组织创建者**：注册完成后为该组织**管理员**，可邀请成员、配置组织设置；
  其权限严格限于本组织，不得跨组织。
- **平台运营方**：签发与吊销邀请码；[已裁决 O-29] 其在产品内是否有对应界面。
  **裁决（O-29 ①）**：**phase-1 不做邀请码管理界面**——平台运营方**线下签发**。
  理由：原型无此屏，做了也无法验收。产品侧只需提供**服务端接口 + 运维脚本**入库邀请码，
  并保证核销、吊销、审计三条链路可用。管理界面留待有真实运营需求时再补。
- **其它角色**：本用例不涉及。
- 接口不得返回越权数据，不能只依赖前端隐藏；邀请码校验必须在服务端执行。

## R6 后置条件 / 不包含

- **正常后置条件**：
  - 新组织与首个管理员账号存在且可用，邮箱已验证，邀请码已核销。
  - [设计验收] AC1：一枚邀请码只能成功创建一个组织；重复使用被拒绝。
  - [设计验收] AC2：注册完成即处于已登录态，落在自己的空组织首页。
  - [设计验收] AC3：邮箱未验证前账号不可登录、不可被邀请进任何项目。
- **失败后置条件**：
  - 不创建「看似成功」的组织或账号；未完成的注册保留为待验证记录并可重试；
    失败事件进入可观测日志。
- **不包含**：
  - 自助注册（无邀请码即可开户）——[原型] 明确「只能被邀请入组织」。
  - 企业 SSO、社交账号登录（见 UC-1.1 的范围裁决）。
  - 计费账号、订阅与付费开通。
  - 邀请码的签发后台（属平台运营侧，不在本产品阶段一范围）。

## R7 业务规则（不随具体实现变化的硬性约束）

- [原型] **注册只能通过邀请**：14 位邀请码（创建新组织）或带组织与角色的一次性链接（加入已有组织）。
- [设计] **一码一组织**：邀请码核销后不可再用；核销必须与组织创建在同一事务内完成。
- [人类已拍板] **认证方式为邮箱 + 密码**；注册时通过**邮箱验证链接**确认邮箱所有权；
  **不使用邮箱验证码（OTP）**。
- [设计] **邮箱未验证的账号不可登录**，也不能被加入任何组织或项目。
- [设计] 验证链接有效期 24 小时，一次性使用；重发有频率限制。
- [设计] 邀请码校验失败不区分「不存在」与「已使用」，防止枚举。
- 所有权限判断必须在服务端执行；隐藏入口只是界面表现，不构成安全控制。
- 创建组织、核销邀请码、授予管理员角色都必须记录审计事件。

## R8 界面线索

- **前端入口**：[原型] 登录页底部「还没有账号？**创建组织 · 需要 14 位邀请码**」。
- **信息架构**：注册是登录页的分支流程，完成后直接进入组织首页。
- **推荐交互**：
  - [设计] 分步向导：邀请码 → 账号信息 → 邮箱验证 → 组织信息；每步可返回，已填内容不丢。
  - [设计] 14 位邀请码输入框应支持粘贴自动分段，明确显示已输入位数。
  - [设计] 邮箱验证等待页需提供「重发」与「换个邮箱」两个出口。
- **必须呈现的状态**：
  - 默认态、加载态、校验失败态、依赖失败态（邮件服务不可用）、成功态。
  - 邮箱验证等待态需明确告知下一步与超时时长。
- **原型参考**：
  - `phases/requirements/WorkspaceX Standalone.html` — 登录页
- **UI sign-off**：**原型确认缺失**（与 UC-1.6 的激活落地页同一判定，两份措辞已统一）——
  原型对注册链路只有登录页底部的一行文字「还没有账号？创建组织 · 需要 14 位邀请码」，
  **四个步骤的屏一个都没有**。这**不是「未探明」**：底部演示场景切换条的 11 项
  （说明 / 登录 / 对话 / 项目 / 画布 / Studio / 大脑 / 任务 / 后台 / 组员入口 / 移动端）
  **已完整枚举，其中没有任何注册场景**，登录页本身也已逐元素抽取。
  ⚠ 同时注意**原型自身矛盾**：说明页的「已完成的屏」清单却自称
  「登录/注册（邮箱·社交·SSO·邀请码入组织）」已完成——自述与运行态不符。
  实现前需先补原型并由产品/设计确认。

## R9 非功能约束

- **性能/规模预期**：
  - [设计] 邀请码校验与注册提交应在 1 秒内给出可感知反馈；邮件发送异步但需明确回执状态。
- **安全/隐私/合规**：
  - 密码必须加盐哈希存储，永不明文记录或回显；传输强制 HTTPS。
  - 邀请码、验证令牌均为高熵随机值，不可预测；验证令牌一次性且服务端可吊销。
  - [已裁决 O-28] 密码强度策略与是否强制二次验证。
    **裁决（O-28 ①②）**：**长度 ≥12 字符、不强制字符类组合、必须查弱口令库、不强制定期更换**
    （NIST 现行取向）；**phase-1 不做 MFA**，phase-2 回归。
    本用例的注册表单与 UC-1.1 的登录/重置**共用同一份策略实现**，不得各写一套。
  - [已裁决 O-28] **邮箱验证链接有效期 24 小时、一次性**；重发 **60 秒冷却 / 每日 5 次**。
    统一表见 `uc-1-1` R10。
- **兼容与降级要求**：
  - 响应式 Web；移动端可完成全流程。
  - 邮件服务不可用时明确失败，不得让用户以为注册已成功。

## R10 已知约束 / 依赖

- **内部依赖**：无（本用例与 UC-1.1 共同构成身份根，其它模块都依赖它们）。
- **被依赖**：UC-1.6 组织成员邀请、UC-1.1 登录、以及全部需要组织上下文的模块。
- **跨模块契约**：账号、组织、组织成员、角色必须使用统一标识。
- **[已裁决 O-29]** **14 位邀请码由谁签发、如何送达、有无有效期与批次管理**——
  这曾是本用例最关键的未决项，不决定则无法产生第一枚可用邀请码。
  **裁决（O-29 ①）**：
  - **签发方 = 平台运营方，线下签发**（销售/开通流程中人工发放），
    **phase-1 不做产品内管理界面**（原型无此屏，做了无法验收）。
  - **邀请码一次性、有效期 90 天**；过期即不可用，需重新签发。
  - **送达**走线下渠道（邮件/合同附件），产品侧不承诺送达。
  - **批次管理**：phase-1 只需 `batch_id` 字段用于追溯与批量吊销，不做批次界面。
  - 服务端必须提供：入库、核销（原子）、吊销、审计四条能力，且**核销与组织创建同事务**
    （对应 R11 的「一码一组织」并发验收）。
- **[已裁决 O-12]** 一个人能否创建/归属多个组织（对照 UC-17.4「同一人在两组织是两套权限」）。
  **裁决（O-12）**：**能**——`user` ↔ `organization` 是**一对多**，
  一个账号可**创建**多个组织、也可**归属**多个组织，用**顶部组织切换器**切换；
  切换时清空全部项目级上下文、权限按当前组织重新求值。
  对本用例的直接影响：**已有账号再次使用一枚新邀请码创建第二个组织是合法路径**，
  不得因「该邮箱已注册」而拒绝；此时**不新建账号**，只新建组织并把该账号设为其管理员
  （否则会出现同邮箱多账号，与 UC-1.1「同一人登录进的是同一账号」冲突）。
  另：**团队为单一归属**（组织内一人一队），跨组织互不影响。
- **[已裁决 O-29]** 组织删除/注销路径与其数据归属。
  **裁决（O-29 ③）**：phase-1 提供的是**停用**而非删除——
  组织停用后**数据保留至留存期届满再销毁**（留存期参数见 O-01），
  **停用期间仅管理员可导出**，其余成员登录后为只读（对应 UC-1.1 R4 A1 的只读降级）。
  硬删除不在 phase-1 范围，且任何删除都必须先经导出与留存期两道关卡。
- **[已裁决 O-28]** 密码策略、找回密码流程（属 UC-1.1 范围但需一并定稿）。
  **裁决（O-28）**：密码 ≥12 位 + 查弱口令库 + 不强制字符类 + 不强制定期更换；
  找回密码链接 1 小时一次性、「密码已修改」通知强制。详见 `uc-1-1` R4 A2 与 R10 统一表。

## R11 切分提示（给 requirement-author）

- 建议先拆「邀请码模型与校验 → 账号注册与密码 → 邮箱验证链接 → 组织创建与首管理员授予 →
  注册向导 UI → 审计 → 自动化验收」。
- 「一码一组织」的事务性（第 5 步核销与创建原子）应单独成 feature 并有并发验收。
- **优先级 / 先后依赖**：P0；5 点；迭代 1；**必须先于 UC-1.6 与所有需要组织上下文的 feature**。

## R12 AI Ready 验收线索

- V1（成功态）：AC1 —— 同一邀请码连续两次走完流程，第一次成功创建组织，第二次被拒绝。
- V2（成功态）：AC2 —— 完成邮箱验证与组织创建后，接口返回已登录会话且组织 ID 非空。
- V3（成功态）：AC3 —— 邮箱未验证的账号尝试登录被拒绝；尝试将其加入项目被拒绝。
- V4（权限态）：新建组织的管理员访问另一组织的任何资源均被拒绝并记录审计。
- V5（空态）：新组织首页显示真实空态与「邀请成员」下一步，不生成示例数据。
- V6（依赖失败）：模拟邮件服务不可用，界面明确失败并保留已填信息，不产生可用账号。
- V7（并发态）：两个会话同时用同一邀请码创建组织，只有一个成功，另一个收到明确失败。
- V8（审计态）：创建组织、核销邀请码、授予管理员三个事件均可按操作者、时间、对象检索。
- V9（安全态）：邀请码校验失败时，「不存在」与「已核销」返回完全相同的响应；
  连续失败触发限速。
- V10（多组织 · O-12）：[设计] 已归属 A 组织的账号用一枚新邀请码走完创建流程——
  断言：① **不新建账号**（账号表记录数不变），② 新组织创建成功且该账号为其管理员，
  ③ 顶部组织切换器出现两个可选组织，④ 切到 B 组织后请求 A 组织资源被拒。
