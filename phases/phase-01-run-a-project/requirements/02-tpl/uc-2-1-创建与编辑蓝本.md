## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-2.1 / 创建与编辑蓝本
- **Actor**：**方法负责人**（蓝本维护者，主 Actor）、**引导师**（可读、可复制、可提回改动，见 UC-2.3）
- **目标**：[原型] 把一次成功项目的骨架沉淀成可复用的蓝本：**设计配置项**分五组填完，
  套用后一次性初始化整场项目。原型原话：**「蓝本管骨架与默认值，不管具体内容。
  套用后引导师可逐场覆盖，改动只影响那一场。」**
- **本用例结果**：[原型] 方法负责人在**蓝本设计器**里把各项设计配置配到可发布状态，
  经「预览参与者视图」与「试跑一场」验证后发布出新版本（如 v4 → v5），
  该版本进入蓝本库可被新建项目套用（UC-2.2）；已开过的项目锁在自己的版本上（UC-2.4）。
- **系统边界**：后台蓝本库列表、**蓝本设计器（设计配置项 + 时长档位 + 形式与语言 + 模型策略 +
  配额与降级）**、预览与试跑、版本发布与归档、「套用后会初始化什么」一览的生成。
  **不含**：各配置项打开后的具体子编辑器（议程编辑器、材料准备、会前任务等，见 R10 未探明清单）。
- **核心数据对象**：蓝本、蓝本版本、**设计配置项（项数固定、由定义表驱动，各带完成标记与计数）**、
  **时长档位**、**议程环节表（随档位变化）**、形式与语言设置、模型策略、配额与降级策略、
  初始化清单（六类）、项目蓝本快照、回提建议。

## R2 前置条件 / 触发条件

- **前置条件**：
  - 用户已建立可校验的正式或临时身份，且拥有目标组织、项目、小组或资源的访问权。
  - 目标资源存在且未被删除/冻结；依赖能力“登录管理（谁能编辑与发布蓝本）”可用，或界面能明确显示其不可用状态。
  - 若动作涉及个人数据、录音、原始材料或跨范围读取，相应授权与留存策略已生效。
- **触发条件**：
  - [原型] 方法负责人在 `后台 → 项目蓝本` 列表页点某一行的 **`[编辑设计 →]`**，
    或点 **`[＋ 新建蓝本]`**（新建方式三选一，见 R4/A0）。
  - 系统从 **蓝本设计器** 进入本流程，并携带当前组织、蓝本 ID、当前版本与角色标识。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

### 3.0 设计器外壳（进入即见）

[原型] 顶部固定呈现：

```
← ｜ HMW 定题项目 · 蓝本设计
v4 已发布 · 用过 12 次 · 改动生成 v5，已开过的项目锁在自己的版本上
草稿自动保存 · 14:52
[预览参与者视图] [试跑一场] [发布 v5]
```

- **版本语义提示句必须原样呈现**：「**改动生成 v5，已开过的项目锁在自己的版本上**」——
  这是用户敢改蓝本的前提，不是装饰文案（版本机制细节见 UC-2.4）。
- **草稿自动保存**并显示最后保存时刻（原型：`草稿自动保存 · 14:52`）；不设「保存」按钮。
- 三个动作按钮的语义：`[预览参与者视图]` 只读预览、`[试跑一场]` 是**发布前置条件**、
  `[发布 v5]` 版本号由系统按当前已发布版本 +1 推导并显示在按钮上。

1. **方法负责人操作**：选**时长档位**（第 2 项设计配置「流程 Agenda」的上位选择）。

   | 档位 | 半场数 | **议程环节数** | 增量内容 |
   |---|---|---|---|
   | 半天 | 1 个半场 | **7 环节** | 只到收敛，不做原型 |
   | 一天 | 2 个半场 | **11 环节** | 加商业模式草稿 |
   | **两天（默认）** | 4 个半场 | **14 环节** | 加原型与用户测试 |
   | 三天 | 6 个半场 | **19 环节** | 加迭代与落地计划 |

   3–4 个环节，这是人能保持专注的上限；跨半场的休息与交接是流程的一部分，不是空隙——
   多天项目的成败通常取决于『隔夜之后怎么接上』。」**

   ⚠ 这道门槛**与原型直接冲突**：蓝本列表里 `商业模式共创 15/16`、`假设风暴（快版）12/16`、

   「必填项完成才能发布」出自 `Backlog Use Case.html`，且原型**从未标出哪几项必填**。
   **② [原型] 已试跑过一场**（原型证据：列表页「客户访谈复盘 **草稿**：『试跑一场后才能发布』」）。
   通过后生成 v5、[设计] 旧版归档（见 UC-2.4），并写审计。
   ⚠「发布新版本时旧版自动归档」的原文在**画布模板**那一屏，**蓝本侧没有这句**，属跨对象挪用，
   故标 [设计]。

10. **系统收口**：校验 AC1「**每一项设计配置都能编辑并有完成度标记，
    完成度分母 ＝ 已定义的配置项总数**」；记录操作者、时间、对象、结果与来源，
    刷新蓝本列表页的完成度与状态。
11. **系统收口**：校验 AC2「改动生成新版本，**已开过的项目锁在自己的版本上**」；
    记录版本差异（改了哪几项设计配置）供 UC-2.4 展示。
12. **系统收口**：校验 AC3「未试跑不得发布」与 AC4「换档位后议程环节表与第 2 项计数一致」。

  - A0：[原型] **新建蓝本三选一**（`[＋ 新建蓝本]` 入口）：**从空白开始 / 套用已有蓝本 /

    素材直接抓成蓝本。」→ 反向生成需把源项目的实际用料**映射回各项设计配置**，
    未能映射的项留空并计入完成度缺口。
  - A1：[Backlog] **换时长档位**：可选议程环节自动增删，**必留议程环节只压缩时间**
    （出自 Backlog；原型只有「环节表随之变化」）。
    [设计] 已填的环节内容不得静默丢弃——被移除的可选环节应可撤销或提示「切回该档位可恢复」
    （**回滚语义原型与 Backlog 均无**，纯反推）。
  - A2：[原型] **选「全线上」**：自动追加「破冰」「举手排队」两个议程环节，并标明来源为形式设置；
    切回「混合/线下」时应对称移除并提示。
  - A3：[设计] **配置项留空发布**：非必填项可留空（原型存在 `15/16`、`13/16`、`12/16`、`9/16` 等
    未配满仍已发布的蓝本），只有**必填项**未完成才阻断发布。
    [已裁决 O-18 ⑤] **「必填」由配置项定义表的 `required` 布尔列驱动**，
    不在代码里枚举；判定语句恒为「存在 `required = true` 且未完成的项即阻断」。
    清单内容仍待人类给出（见 R10），但**不阻断实现与验收**。
  - A4：[原型] 蓝本处于草稿态（从未发布）时，列表页只显示完成度与「试跑一场后才能发布」，
    不显示版本号。
- **异常流程**：
  - E1：[Backlog] **必填的设计配置项没完成不能发布**（原型反证：`15/16`、`12/16`、`9/16`
    的蓝本仍处「已发布」或可发布状态），侧栏用完成度（`n/N`）标出缺口，
    并可点击直达未完成项。失败不得被呈现为成功。
  - E2：[原型] **未试跑就点发布**：明确拒绝并提示「试跑一场后才能发布」，
    提供 `[试跑一场]` 直达入口，不产生版本号。
  - E3：[设计] 请求超时、网络中断或依赖不可用时，保留用户当前输入与最后成功数据（草稿自动保存的
    最后时刻必须真实），明确失败原因，并提供安全重试；**不得把「未保存」显示成「已自动保存」**。
  - E4：[设计] 同一蓝本被两名方法负责人并发编辑时不得静默覆盖；提示版本已变化，
    允许刷新、对比或重新提交；冲突粒度按**单个设计配置项**判定，不要整份蓝本锁死。
  - E5：[设计] 权限在操作过程中被撤回时立即终止后续写操作；已完成步骤按审计规则保留，
    未提交输入留在本地草稿并提示重新授权。
  - E6：[设计] 发布过程中断（生成 v5 与旧版归档之间失败）：两步必须同事务，
    不得出现「新版已生成但旧版仍为当前版」或反之的中间态。

## R7 业务规则（不随具体实现变化的硬性约束）

**术语与结构**
- [人类已拍板 D-03] **「设计配置项（16 或 15）」「N 个议程环节」「9 个方法环节」是三个不同的概念**，
  代码、接口字段、UI 文案、测试断言中**不得互相替代**，也不得统称「环节」。
- [原型] **设计配置项数固定、分五组**，运行时不可由用户增删项数；只能改各项的内容与完成状态。
  完成度以 `n/分母` 表示，是蓝本列表页与设计器侧栏的**同一个数**。
  **分母 ＝ 已定义的配置项总数，由配置项定义表驱动，不得在代码里硬编码 16 或 15**
  （原型标注 16、实际枚举 15，尚待产品确认，见头部 ⚠ 与 R10）。
- [原型] **议程环节数由时长档位决定**：半天 7 / 一天 11 / 两天（默认）14 / 三天 19；
  档位以**半场（半天）**为单位，一个半场约 3–3.5 小时、3–4 个议程环节。

**编辑与档位**
- [Backlog] 时长档位改变时**可选议程环节自动增删，必留议程环节只压缩时间**——
  原型只写「套用时先选档，环节表随之变化」，**没有可选/必留之分，也没有压缩时间的说法**。
- [原型] 形式选「全线上」**自动追加**「破冰」「举手排队」两个议程环节。
- [原型] **草稿自动保存**；显示的最后保存时刻必须真实，不得在保存失败时仍显示已保存。

**发布门槛与版本**
- [Backlog] **必填的设计配置项没完成不能发布**，侧栏用完成度标出来
  （**与原型冲突**：原型有 `15/16`、`12/16`、`9/16` 的已发布蓝本，且从未标注哪几项必填）。
- [原型] **试跑一场后才能发布**（列表页「客户访谈复盘 草稿：试跑一场后才能发布」）。
  [设计] 「必填完成」与「已试跑」是**两道并列的**发布门槛、缺一不可——**只有第二道有原型依据**，
  第一道见上条，两道并列的说法本身是本文的组合。
- [原型] **改动生成 v(n+1)，已开过的项目锁在自己的版本上**（快照绑定，详见 UC-2.4）。
- [设计] 发布新版时**旧版归档**——该句原文属**画布模板**屏（「发布新版本时旧版自动归档」），
  蓝本侧无此表述，属跨对象挪用，需人类确认蓝本是否沿用同一策略。
- [原型] **蓝本管骨架与默认值，不管具体内容**；套用后引导师的改动**只影响那一场，不回写蓝本**，
  要沉淀必须走 UC-2.3 的复盘「提交回蓝本」。

**模型与配额**
- [原型] 模型策略按场景分派而非全局单选：现场 sonnet-4.6（低延迟）/ 会后整理 opus-4.6（质量）/
  **机密材料仅本地 qwen3**。
- [原型] **「机密材料仅本地」是隐私硬路由，优先级高于配额降级**：达配额阈值时不得把机密材料
  切到非本地模型（对齐 proto-03「含客户机密 → 禁止降级」）。
- [原型] 单场 token 预算（默认 3.5M）达 **90% 自动降级到便宜模型并在对话里提示，不硬停**；
  理由：「现场卡住比多花钱贵。」降级必须**可见**，不得静默。

**通用**
- AC1：每一项设计配置都能编辑并有完成度标记，完成度分母 ＝ 已定义的配置项总数。
- AC2：改动生成新版本，已开过的项目锁在自己的版本上。
- AI/Agent 生成的候选内容必须标识为机器产出，展示可追溯来源；来源不足时不得伪造结论。
- AI/Agent 的写回、覆盖、发布或高影响工具调用必须遵守原型中的批准点；未经确认只保留为草稿或候选。
- 所有权限判断必须在服务端执行；隐藏入口只是界面表现，不构成安全控制。
- 任何覆盖、删除、撤销、签署、发布、写回或停用动作都必须记录审计事件，并显示动作影响范围。

  **本条的性质已由「待裁决」改判为「待补抽取」——它不再阻断 AC1、也不阻断开工**，
  因为 AC1 已定稿为「分母 ＝ 已定义的配置项总数」，实现由**配置项定义表驱动**
  （见下一条 O-18 ⑤），**禁止硬编码 16 或 15**，因此无论第 16 项最终有没有都不返工。
  仍然禁止：由实现者自行补一项，或直接把结构改成 15 项。
- **[已裁决 O-02]** **「蓝本」与项目设置里的「工作流模板」是不是同一个东西**——
  证据：蓝本列表 `HMW 定题项目 · 已发布 v4 · 7 环节·3.5h`，
  项目设置 → 工作流编排的模板库 `客户共创（3 小时）· 7 环节`，
  **结构高度相似但命名不同**；项目侧显示「设计思维标准五步 · 已套用 · **来自后台 v2**」，
  也带后台版本号。三种可能：① 同一实体的两个入口 ② 两层 ③ 两套独立体系。
  **裁决（O-02）：② 两层结构。**
  - **蓝本 ⊃ 工作流模板**：工作流模板 ≈ 蓝本**第 2 项「流程 Agenda」 ＋ 第 13 项「Skill 绑定」**
    在**项目侧的投影**，不是独立于蓝本的第二套体系。
  - 依据：原型两处都带**后台版本号**（`来自后台 v2`），说明项目侧是后台对象的投影而非独立对象。
  - **28 环节 vs 18 环节的解释**：**蓝本含全部档位的环节，项目套用后只实例化所选档位的环节**——
    因此无需判定原型数据错误，两个数字可以同时为真。
  - **连带裁定**：UC-2.2 的 `[另存为组织模板]` 产出的是**工作流模板**（不是新蓝本），
    与 **UC-2.3「提回蓝本」是两条不同路径**，不是重复功能：
    前者沉淀「这套议程 + Skill 绑定好用」，后者把改动回灌到蓝本的全部 16 项配置。
  - 对本用例的直接影响：第 2 项「流程 Agenda」与第 13 项「Skill 绑定」必须能被**单独投影**
    为工作流模板，故二者的数据结构需可独立序列化；`agenda_segment_id` 的持有方为
    **蓝本侧的议程环节定义**，项目实例引用它（D-03a 字段契约据此落定）。
  见 UC-2.2 / UC-2.3 / UC-2.4 同条。
- **[已裁决 O-18 ⑤]** **哪些设计配置项是「必填」**——发布门槛依赖这份必填清单，但原型只显示完成度，
  未标出哪几项必填（反证：`9/16`、`12/16` 的蓝本也已发布或可发布）。
  **裁决（O-18 ⑤）**：**清单本身无依据，仍需人类给出**；
  但**实现方式已定**：做成**配置项定义表的一个 `required` 布尔列**
  （与 O-07 的分母同用一张表）。这样「哪些必填」变成**数据而非代码**，
  清单日后怎么改都不改代码、不返工。
  发布门槛的判定语句固定为「**存在 `required = true` 且未完成的配置项 → 阻断发布**」，
  与具体是哪几项无关，**verification 可立即写**（见 R12）。
  **剩余待人类给出的只有那份清单的内容，不再是实现方式。**
- **[已裁决 O-03]** **「协同引导师」是不是第五种项目角色**——证据见上表第 4 项。
  **裁决（O-03）：不是——它是引导师的多实例**（一场可有多名引导师、权限相同，
  一名为主持人持最终确认权）。因此第 4 项「角色与权限」的可配角色集**恒为 4 角色**，
  与原型显示的「4 角色」一致，RBAC 表不扩行。归口 UC-0.3，本用例承接结果。
- **[待确认]** **「试跑一场」的完成判定**——是「创建试跑实例」即算，还是需跑完/需产出？
  试跑数据是否可删、是否计入配额。
- **[待确认]** 时长档位是否可自定义到任意半场数（`[＋ 档位]` 的边界），
  以及自定义档位下议程环节数的推导规则。
- **[待确认]** 单场 token 预算 3.5M 与 90% 降级阈值是否**项目级可覆盖**，
  与 proto-03「组织级 90% / 成员级 85% / Agent 级」三级阈值如何取舍
  （原型说明为「三级中最先触发的一条生效」）。
- **[已裁决 O-34]** 容量基线（保守值，来自一场线下工作坊的物理上限）：单项目在场 **60 人**（8–10 组 × 6 人 + 引导师团队）、组织并发项目 **20**、单场音频 **8 小时**、单项目材料 **5 GB**、历史 **3 年 × 200 项目**。⚠ **无本项目实测依据，需产品确认**；确认前各 UC **不写性能类 AC**，不阻塞开工
- **[已裁决 O-33]** 通知平面**单点定义在 `.harness/instructions/` 的通知规范**，各 UC 只引用不重复定义。默认：产品内通知**必选**；邮件**默认开启可关**；短信仅用于现场进场验证码；免打扰**默认关闭**（B 端工具，静默会误事）；到期提醒 **09:00 用户时区**；催办冷却 **4 小时**；组员**可以**催同组同伴；**「今天」一律按用户时区**

## R11 切分提示（给 requirement-author）

- 本用例估点 **21**，**必须拆成多个 feature**，建议切法：
  1. **蓝本与版本领域模型 + 权限**（蓝本、版本、**配置项定义表驱动的槽位**、完成度派生）
  2. **设计器外壳**（版本条、草稿自动保存、三动作按钮、完成度侧栏与目录导航）
  3. **时长档位与议程环节表联动**（四档 + 增删规则 + 必留项压缩时间 + `[＋ 档位]`）
  4. **形式与语言**（含「全线上」自动加两个议程环节的对称增删）
  5. **模型策略 + 配额与降级**（含「机密仅本地不可降级」硬路由）
  6. **「套用后会初始化什么」六类一览的生成**（与 UC-2.2 共用同一份契约）
  7. **预览参与者视图 / 试跑一场**
  8. **发布门槛与版本生成**（必填完成 ∧ 已试跑；事务性；审计）
  9. **新建三入口**（空白 / 套用已有 / 从历史项目反向生成）
  10. 审计与自动化验收
- **各配置项的面板不在本轮切分内**（待二级 sign-off），
  但 1、2 必须把「面板可插拔 + 每项独立完成度上报」的契约留出来。
- **优先级 / 先后依赖**：P0；**21 点**；迭代 1 · 能进场；先满足登录管理与角色。
- 对 P0 必做链路优先实现成功态、权限态与数据闭环，异常态不得延期到上线后。

## R12 AI Ready 验收线索

以下行为应可由自动化测试、接口断言或可复现人工步骤验证：

- V1（成功态 · AC1）：接口返回的设计配置项**与配置项定义表的条目数一致**且分组为五组；
  逐项写入后完成度从 `0/N` 单调递增到 `N/N`（**N 取自定义表，不硬编码**）；
  侧栏显示值与接口派生值一致。**断言必须写成参数化的 N**，
  这样第 16 项的裁决落地后不需要改测试。
- V1b（成功态 · AC1）：断言已枚举的 **15 项**（主题与背景 / 流程 Agenda / 分组规则 /
  角色与权限 / 问卷 / 访谈与对象 / 会前任务 / 场地与形式 / 项目材料 / 分组打印素材 /
  组内能力 / Agent 编排 / Skill 绑定 / 输出物 / 报告模板）**全部存在且可编辑**，
  分组归属与 R3 表一致。
- V2（成功态 · AC1）：构造完成度分别为 `9/N`、`12/N`、`13/N`、`15/N`、`N/N` 的蓝本，
  蓝本列表页对应行显示同一数值（原型列表真实取值以 16 为分母；
  [已裁决 O-07] 断言中的分母一律取自配置项定义表，不写死 16 或 15）。
- V3（成功态 · AC4）：依次选四档，断言议程环节数为 **7 / 11 / 14 / 19**，
  且第 2 项「流程 Agenda」的计数与之相等；默认档位为**两天**。
- V4（成功态 · AC4，**[Backlog] 口径**）：档位由「两天」切到「半天」后再切回，
  **必留议程环节保留且只被压缩时间**，可选环节被移除后可恢复；已填内容无静默丢失。
  ⚠ 增删规则出自 Backlog、回滚语义为反推；原型只说「环节表随之变化」，**待人类确认后再定稿**。
- V5（成功态）：形式选「全线上」后议程环节表**新增「破冰」「举手排队」两项**且标注来源；
  切回「混合」后对称移除。
- V6（成功态 · **AC3b**）：[已裁决 O-18 ⑤] 在配置项定义表中把任一项的 `required` 置为 `true`
  并留空该项，点 `[发布]` 被拒，错误指向该项且完成度侧栏高亮；补齐后可发布；
  把该项 `required` 改回 `false` 后即使留空也可发布。
  **断言写成「由 `required` 列驱动」而非「第 N 项必填」**——这样必填清单日后怎么定都不改测试，
  也自然解释了原型中 `15/16`/`12/16`/`9/16` 仍可发布（那些缺的项 `required = false`）。
- V7（成功态 · **AC3a，[原型] 口径**）：**未试跑的草稿点 `[发布]` 被拒**，
  提示「试跑一场后才能发布」；执行 `[试跑一场]` 后同一草稿可发布。
- V8（成功态 · AC2）：v4 蓝本改动后发布得到 v5；
  **在 v4 期间已创建的项目其蓝本版本字段仍为 v4**（不随发布漂移）——这是快照绑定的可执行断言。
- V9（成功态 · AC5）：改动任一设计配置项后，「套用后会初始化什么」六类一览随之变化；
  用同一蓝本走 UC-2.2 套用，实际写入项与该一览**逐项对得上**（跨用例断言）。
- V10（模型策略）：三条策略分别落到现场 / 会后整理 / 机密材料三类调用；
  **机密材料在配额达 90% 时仍走本地 qwen3，不被降级**。
- V11（配额与降级）：模拟用量达单场预算 90%，断言**自动切换到便宜模型 + 对话内出现提示 +
  会话未被中断**（不硬停）。
- V12（草稿自动保存）：改动后不点任何保存按钮，刷新页面内容仍在，
  且显示的最后保存时刻与实际写入时间一致；模拟保存失败时**不得**显示「已自动保存」。
- V13（新建三入口）：三种新建方式各建一份蓝本；
  「从已办过的项目反向生成」的结果中，源项目用过的问卷/画布/素材能对应到具体的设计配置项，
  未能映射的项留空并计入完成度缺口。
- V14（权限态）：逐一使用 方法负责人、引导师、观察者、未授权用户访问；

- V15（空态）：新建蓝本显示 `0/N` 真实空态与下一步，不生成示例配置。
- V16（依赖失败）：模拟网络/外部依赖失败，输入和最近成功数据保留，错误可解释且可重试。
- V17（并发态）：两名方法负责人同时改**不同**设计配置项互不覆盖；
  改**同一项**时提示版本已变化并可对比，无静默覆盖。
- V18（事务态）：注入发布中途失败，断言不产生「已生成新版但旧版仍为当前版」的中间态，
  且版本号无缺号。
- V19（审计态）：发布、换档位、改模型策略、改配额阈值、删除/复制蓝本均可按操作者、时间、
  对象和结果检索；越权尝试也有安全审计记录。
