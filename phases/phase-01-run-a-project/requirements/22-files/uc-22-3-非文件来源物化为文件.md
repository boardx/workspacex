# 原始需求（细化）— UC-22.3 非文件来源物化为文件

> 所属：阶段一 · 能跑完一场项目 / M22 项目文件
> 来源：**人类新需求（2026-07-28）**「**能保存成文件的数据，尽量保存成文件，
> 可以在这文件浏览器看到。**」——这一句就是本 UC 的全部立身之本。
> 架构依据 `docs/architecture/context-engine.md` **第 2.0 节第 2 条**
> 「**非文件来源必须物化为文件**：问卷 → `responses.csv` + `schema.json`；
> 对话 → `messages.jsonl`；访谈 → 音频 + `transcript.jsonl` + `notes.md`；
> 工作坊 → 音频 + `transcript.jsonl` + 白板照片；深度研究 → 网页快照 + `citations.json`；
> AI 生成 → 内容文件 + `provenance.json`」，与 **2.1 节**「非文件来源也必须生成开放、
> 可归档的 evidence bundle（JSONL / JSON / CSV / 音频 / 图片），**不能只活在某张业务表里**」。
> **[原型] 侧的间接证据**：对话右栏五标签之一「**材料 12**」——
> 对话界面里能数出 12 份材料，说明对话与材料是同一个池子；
> 蓝本第 9 项「项目材料 9 件」与项目筹备「9 已入库材料」计数一致。
> **补写缘由**：原型的问卷、访谈、工作坊、对话、画布各自有自己的界面与数据，
> **彼此之间和「材料」之间没有任何显式的转换关系**。若不把物化写成硬契约，
> file-first 就只剩一句口号：客户要「把材料交给我」时，问卷回收和对话记录交不出来。

> 口径（四标记）：**[原型]** ＝ `WorkspaceX Standalone.html` **运行态实际存在**的行为（有界面可查，依据 scratchpad 的 proto-01~10 抽取档案）；**[Backlog]** ＝ `Backlog Use Case.html` 的**文档要求**（原型未必实现）；**[设计]** ＝ 依据前两者反推补全，**需人类确认**；**[待确认]** ＝ 不应由实现者自行决定。
> 元数据：优先级 **P0**；估点 **13**；建议迭代 **迭代 2 · 材料入库**。
>
> ⚠ 本 UC **几乎全部是 `[设计]`**。原型证明的只有「材料是一个统一的池子且有计数」；
> **七种来源的具体文件清单、文件格式、同步时机全部来自架构文档**，标 `[设计]`。

## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-22.3 / 非文件来源物化为文件
- **Actor**：**系统**（物化是自动的，不是用户点「导出」触发的）；
  **项目负责人 / 引导师 / 组长 / 观察者**是消费方；**agent** 是其中一类生产方。
- **目标**：[设计] 让「不是文件的东西」也变成文件——
  一场问卷、一段对话、一次访谈、一张画布，用户都能在文件浏览器里**看到它、下载它**，
  而不是被告知「那个在系统里，导不出来」。
- **本用例结果**：每个非文件业务对象在产生或变更时，**同步**生成/更新对应的
  `artifact` + `artifact_version`；这些文件在 UC-22.1 浏览器中与上传文件**并列可见**、
  可下载、可批量导出；其内容经 UC-22.2 的同一条链路进入检索。
- **系统边界**：七类来源的物化规则、文件粒度、格式契约、同步时机、
  更新与版本推进、AI 生成物的溯源与标记。
  **不含**浏览与下载（UC-22.1）、上传与摄取链路本身（UC-22.2）、
  删除传播（UC-22.4）、各业务模块自身的功能（12-survey / 06-itv / 05-rec / 08-chat / 07-canvas）。
- **核心数据对象**：`artifacts`（`source_type` ∈ 八类）、`artifact_versions`、
  `derived_representations`、`provenance_events`、各业务对象的 ID（作为 `source_ref`）。

## R2 前置条件 / 触发条件

- **前置条件**：
  - UC-22.2 的摄取链路可用（物化产物**复用同一条链路**，不另建）。
  - 对应业务模块已产生数据（问卷已回收 / 对话已发生 / 访谈已录 / 画布已保存 …）。
- **触发条件**（[设计]，**全部是系统事件驱动，不是用户点导出**）：
  - `survey.response.submitted` / `survey.closed` → 问卷物化
  - `conversation.message.appended`（**去抖后**）/ `conversation.closed` → 对话物化
  - `interview.session.ended` / `transcript.finalized` → 访谈物化
  - `workshop.recording.stopped` / `whiteboard.photo.uploaded` → 工作坊物化
  - `research.run.completed` → 深度研究物化
  - `canvas.saved` → 画布物化
  - `generation.completed`（agent / AI 产出）→ AI 生成物化

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

1. **系统处理**：接收业务事件，解析出 `project_id`、`source_type`、`source_ref`
   （业务对象 ID）、可见性范围、`agenda_segment_id`（若业务对象绑定了议程环节）。

2. **系统处理**：按 `source_type` 查**物化清单**，确定这次要产出/更新哪几个文件。
   **七类来源的物化清单（[设计]，这是本 UC 的核心契约）**：

   | 来源 | `source_type` | 必须产出的文件 | 文件粒度 |
   |---|---|---|---|
   | **问卷** | `survey` | `responses.csv`（一行一份回收，含受访者标识/提交时间/逐题答案）<br>`schema.json`（问卷版本、题号、题干、题型、选项、跳转逻辑） | **一份问卷版本一组文件** |
   | **对话** | `conversation` | `messages.jsonl`（每行一条消息：`message_id` / `role` / `author` / `ts` / `reply_to` / `content` / `tool_calls` / `attachments`） | 🔴 **以会话为文件粒度**——一整段对话一个文件，**不是每条消息一个文件** |
   | **访谈** | `interview` | 音频原件（原格式）<br>`transcript.jsonl`（speaker / 起止时间码 / 文本 / 置信度）<br>`notes.md`（研究笔记） | **一场访谈一组文件** |
   | **工作坊** | `workshop` | 音频原件（多路则多份）<br>`transcript.jsonl`（**diarization** speaker、时间码、议题、决定、**反对意见**、行动项）<br>白板照片（原图 + EXIF） | **一场工作坊一组文件** |
   | **深度研究** | `research` | 网页快照（每个来源一份，保留原始 HTML/PDF）<br>`citations.json`（URL / 访问时间 / 作者 / 发布日期 / 引用锚点） | **一次 research run 一组文件** |
   | **画布** | `canvas` | **mermaid 源码 `.md`**（D-08：mermaid 是 R10 硬约束）<br>布局快照（图片或结构化布局 JSON） | **一张画布一组文件** |
   | **AI 生成** | `generated` | 内容文件（`.md` / `.csv` / 图片，按产出类型）<br>`provenance.json`（**prompt / model / model_version / run_id / 输入 Context Pack ID / 生成时间 / 触发者**） | **一次生成一组文件** |

3. **系统处理**：生成文件内容。**必须保留结构，不许拼成一段纯文本**
   （沿用 UC-22.2 R3 第 8 步的模态结构表）。
   [设计] 所有 JSONL 文件**每行一个独立 JSON 对象**，字段名稳定，
   新增字段向后兼容，**删除或改名字段属破坏性变更**（见 R7 命名契约）。

4. **系统处理**：判断是**新建**还是**更新**——
   - 该 `source_ref` 首次物化 → 新建 `artifact`（`source_type` + `source_ref` 唯一）。
   - 已存在且内容变化 → **新增 `artifact_version`**（旧版仍可下载，UC-22.4）。
   - 已存在且内容未变（`content_hash` 相同）→ **不新增版本**，只更新
     `provenance_events` 的最后核对时间。

5. **系统处理**：把产出的文件送入 **UC-22.2 的同一条摄取链路**
   （`RECEIVED → … → READY`），继承该业务对象的**可见性范围与机密标记**。
   [设计] 🔴 **可见性取来源的最严格结果**——若一场对话中包含了机密材料的引用，
   其 `messages.jsonl` 至少与该材料同级敏感（架构第五节「交集生成内容取所有来源权限的
   最严格结果，避免摘要造成越权信息洗白」）。

6. **系统处理（AI 生成专属）**：为 `generated` 类产物打上 **`synthesized` 标记**，
   写入 `provenance.json`，并在 `segments` 上标注生成属性。
   [设计] 🔴 **生成内容不得在下一次检索中伪装成一手证据**——
   检索侧必须能按 `evidencePolicy: "primary-only"` 把它们排除
   （架构第四节 QueryContext）；这与 16-persona / D-25「虚拟结论不能作为强洞察、
   不进决策依据」是**同一条约束的两端**，且必须**服务端强制**，不只是视觉标记。

7. **系统处理**：写 `provenance_events`——记录「这个文件是由哪个业务对象、
   在什么事件下、用哪个物化器版本生成的」，形成可回溯链路。

8. **系统收口**：校验 AC1「**每一个非文件来源的业务对象，在文件浏览器中都有对应的、
   可下载的文件**」——不存在只活在业务表里的上下文。

9. **系统收口**：校验 AC2「**物化是同步契约不是事后导出**」——
   业务对象产生/变更后，其文件版本在约定时限内已存在（见 R9），
   **不需要用户点任何「导出」按钮**。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[设计] **对话的去抖物化**——每条消息都物化会产生海量小版本，
    因此对话按「**去抖窗口 + 会话结束**」两个时机物化：
    窗口内合并，会话结束时强制落一版终版。
    这是架构第 2.0 节「代价与边界」第 2 条的直接落地：
    「高频小对象不单独成文件——以会话/场次为文件粒度，`messages.jsonl` 一个文件承载整段，
    Segment 仍精确到消息，靠 anchor 定位」。
  - A2：[设计] **问卷仍在回收中**——`responses.csv` 按批次追加为**新版本**
    （v1 = 前 30 份，v2 = 前 78 份…），问卷关闭时落终版并标记 `final`。
    `schema.json` 只在问卷版本变更时推新版。
  - A3：[设计] **画布的双产出**——mermaid 源码是**权威可 diff 的形式**，
    布局快照是**人看的形式**；两者同版本号联动。
    验收优先用 **round-trip 断言**（D-08：mermaid 源码 → 渲染 → 再解析 ≡ 原源码）。
  - A4：[设计] **访谈/工作坊的转录尚未完成**——音频先物化（原件优先，
    与 UC-22.2 E5 同原则），`transcript.jsonl` 作为**派生物**后到（UC-22.4）。
    浏览器中该组显示「音频已入库，转录生成中」。
  - A5：[设计] **深度研究的网页快照抓取失败**——`citations.json` 仍产出并
    在对应条目上标 `snapshot_failed`；**不因为一个来源抓不到就整场不物化**。
  - A6：[设计] **手工触发重新物化**——物化器升版后，有权者可对历史业务对象
    批量重跑物化，产出**新版本**，**不修改旧版本**（沿用 UC-22.2 A5）。

- **异常流程**：
  - E1：[设计] **物化失败**（业务数据结构异常、序列化错误）——
    业务对象**不受影响**（物化失败不能阻断业务），但产生一条
    **可见的物化失败记录**，出现在文件浏览器对应位置，标「物化失败，内容未入库」，
    出口：重试 / 查看错误详情。🔴 **不得静默失败**——静默失败会导致
    「用户以为都在文件里了，实际交付时才发现缺」。
  - E2：[设计] **业务对象被删除但文件已生成**——走 UC-22.4 的删除传播，
    两端必须一致；不允许出现「对话已删、`messages.jsonl` 还在浏览器里」。
  - E3：[设计] **可见性冲突**——业务对象的可见性与其引用材料的可见性不一致时，
    **取最严格结果**并记录该决策；若无法判定，**fail-closed**（按最严处理）。
  - E4：[设计] **物化产物过大**（如一场 8 小时工作坊的 transcript）——
    仍产出单文件（保持粒度契约），但下载走分片；
    [待确认] 是否设上限并在超限时分卷。
  - E5：[设计] **物化风暴**（大量业务事件同时触发）——
    物化任务进入与 UC-22.2 同一个持久队列，有背压与优先级；
    积压超阈值时给出可见告警，**不丢事件**。
  - E6：[设计] **AI 生成物缺少 `provenance.json`**（如生成器未上报 prompt/model）——
    **拒绝物化为 `READY`**，停在 `REVIEW_PENDING` 并标「溯源信息缺失」。
    没有溯源的生成内容不允许进入检索——这是 R7 的硬约束。

## R5 权限与可见性

- **继承原则**：物化文件的可见性**完全继承**其业务对象的可见性范围，
  并与其引用来源取**最严格结果**。物化**不是**放宽权限的通道。
- **项目负责人 / 引导师**：可见本项目全部物化文件；可触发重新物化。
- **组长 / 组员**：本组的画布、本组的对话、本组的分组材料——按业务对象的原可见性。
- **观察者**：只见**已发布且已脱敏**的物化文件；
  🔴 特别注意：原始 `messages.jsonl` 与 `transcript.jsonl` **默认不对观察者可见**
  （逐字记录含大量未脱敏内容），除非经脱敏处理并发布。
- **外部受访者**：其访谈的音频与转录，本人可通过 06-itv/UC-6.6 自助门户取得副本
  （[原型] 受访者「可要一份自己的副本」）；**不进入本项目文件浏览器的访客视图**。
- **agent**：只读消费物化文件；写入仅限 `generated` 类且强制带溯源。
- **硬约束**：物化过程本身在**系统身份**下运行，但产出物的 ACL 由业务对象决定，
  **不得因为是系统生成就获得更宽的可见性**。

## R6 后置条件 / 不包含

- **正常后置条件**：
  - 每个非文件业务对象在文件浏览器中有对应的、可下载的文件组。
  - 物化文件与上传文件在浏览器中**平权呈现**（同一棵树、同样的下载与导出能力）。
  - [设计验收] AC1：**零个**非文件来源的业务对象缺少对应文件（见 V1）。
  - [设计验收] AC2：物化是**同步契约**——业务对象变更后 N 秒内文件版本已更新，
    无需人工导出。
  - [设计验收] AC3：`generated` 类产物 **100%** 带 `synthesized` 标记与 `provenance.json`，
    且在 `evidencePolicy: "primary-only"` 检索下**零召回**。
- **失败后置条件**：
  - 物化失败**不阻断业务**，但必须产生可见的失败记录与重试出口。
  - 缺溯源的生成物不得进入 `READY`。
- **不包含**：
  - 各业务模块自身的功能（问卷设计、访谈进行、画布编辑…）。
  - 用户手动的「导出报告为 PDF」——那是 13-deliv 的交付物，不是证据平面的物化。
  - 跨项目的物化聚合（phase-3）。
  - 把每条消息物化为独立文件（**明确排除**，见 R7）。

## R7 业务规则（不随具体实现变化的硬性约束）

- 🔴 [设计｜架构 2.0.2] **非文件来源必须物化为文件**。清单见 R3 第 2 步的七行表，
  **该表是契约，实现不得少产出任何一个文件**。
- 🔴 [设计] **物化是同步契约，不是事后导出**。业务对象产生即生成/更新对应文件版本；
  **不得**做成「用户点导出才生成」——那样文件浏览器里就永远是残缺的，
  file-first 的「可下载是交付前提」立不住。
- 🔴 [设计｜架构 2.0 代价与边界 2] **高频小对象不单独成文件**：
  对话**以会话为文件粒度**，`messages.jsonl` 一个文件承载整段；
  **Segment 仍精确到消息**，靠 anchor 定位。同理，访谈/工作坊以**场次**为粒度。
- 🔴 [设计｜架构 3 + D-25 + 16-persona] **生成内容醒目标记为 `synthesized`，
  不得在下一次检索中伪装成一手证据**。必须**服务端强制**（`evidencePolicy` 生效），
  不只是界面上一个角标。
- [设计] **AI 生成物无 `provenance.json` 不得进入 `READY`**。
  `provenance.json` 至少含：prompt、model、model_version、run_id、
  输入 Context Pack ID、生成时间、触发者。
- [设计｜架构 2.1] 物化产物必须是**开放、可归档的格式**（JSONL / JSON / CSV / 音频 / 图片）；
  **不得**用私有二进制格式或需要本产品才能打开的格式——
  「对象存储里那棵树本身就是一份可离线打开的完整交付物」。
- [设计｜D-08] **画布物化以 mermaid 源码为权威形式**；布局快照是辅助。
  验收优先用 round-trip 断言。ReactFlow 相关产物降为 `[建议]`，不进契约。
- [设计｜架构 2.0.100] **文件名与目录结构是契约**——
  `responses.csv` / `schema.json` / `messages.jsonl` / `transcript.jsonl` /
  `notes.md` / `citations.json` / `provenance.json` **这七个文件名是固定的**，
  改名走迁移（与 UC-22.1 R7 同一条约束）。
- [设计｜架构 5] **交集生成内容取所有来源权限的最严格结果**，
  避免摘要造成越权信息洗白。
- [设计] **物化失败不阻断业务，但必须可见**。静默失败是本 UC 最危险的缺陷模式。
- [设计｜D-03a] 物化文件绑定的环节字段**只能是 `agenda_segment_id`**；
  **禁止**写入 `design_facet_id` 或 `method_stage_id`。

## R8 界面线索

- **前端入口**：本 UC **主要没有独立界面**——它的界面就是 UC-22.1 的文件浏览器。
  用户看到的是：问卷/访谈/工作坊/研究/对话/画布/AI 生成六个来源节点里
  **真的有文件**，而不是空的。
- **必须有界面的三处**：
  1. [设计] **业务对象侧的「已入库」角标**——在问卷详情、访谈详情、对话右栏、
     画布工具栏上显示「已入库 N 个文件」+ 跳转到文件浏览器对应位置的链接。
     [原型] 对话右栏的「**材料 12**」标签是这个角标的现成落点。
  2. [设计] **物化失败的可见记录**——出现在文件浏览器对应位置与业务对象侧，

## R9 非功能约束

- **性能/规模预期**：
  - [设计] **物化时限**（AC2 的可验收基线）：
    问卷提交 → `responses.csv` 更新 ≤ **60s**；
    对话去抖窗口 ≤ **5 分钟**，会话结束 → 终版 ≤ **60s**；
    画布保存 → mermaid 源码 ≤ **30s**；
    研究 run 完成 → 快照与 `citations.json` ≤ **5 分钟**；
    音频停止录制 → 音频原件入库 ≤ **5 分钟**（转录另计，属派生物）。
    ⚠ 这五个数是 `[设计]` 提议，需人类确认（见 R10）。
  - [设计] 物化任务与上传摄取**共用持久队列**，但**优先级低于用户主动上传**
    （用户在等的事优先）。
- **安全/隐私/合规**：
  - 逐字记录类文件（`messages.jsonl` / `transcript.jsonl`）默认**不对观察者可见**。
  - 受访者撤回同意后，其对应的物化文件走 UC-22.4 删除传播（17-gov/UC-17.2 五步）。
  - `provenance.json` 中的 prompt **可能含客户机密**——
    其可见性取该次生成的输入材料的最严格结果，**不得默认全场可见**。
  - PII 检出对物化文件同样生效（O-39 五类最小集）。
- **兼容与降级要求**：
  - 物化器升版必须**向后兼容**已有文件的读取；
    字段只增不删，破坏性变更走 R7 的迁移流程。
  - 物化服务不可用时，事件进入队列等待，**不丢失**；业务侧不受影响。

## R12 AI Ready 验收线索

- V1（🔴 file-first 总闸·可执行）：在一个演示项目中产生**每一类**业务对象各一个
  （1 场问卷回收 3 份、1 段 10 条消息的对话、1 场访谈、1 场工作坊、1 次研究 run、
  1 张画布、1 次 AI 生成），然后对**每一个** `source_ref` 调
  `GET /projects/:id/artifacts?source_ref=...`，断言 ① 返回非空；
  ② 返回的文件名集合**等于** R3 第 2 步契约表中该行列出的文件名集合；
  ③ 每个文件 `GET .../download` 返回 200 且哈希一致。
  **断言缺文件数为 0。**
- V2（对话粒度·可执行）：一段 50 条消息的会话物化后，断言
  ① `source_type=conversation` 且该 `source_ref` 下 **`messages.jsonl` 文件数 == 1**
  （不是 50）；② 该文件行数 == 50；
  ③ `segments` 中该会话的行数 == 50 且每行的 `anchor.messageId` 唯一非空。
  这一条同时验证「文件粒度是会话」与「Segment 精确到消息」。
- V3（同步契约·可执行）：提交一份新的问卷回收，
  轮询 `responses.csv` 的最新版本，断言在**约定时限内**（R10 待确认的秒数）
  行数增加了 1，**且全程未调用任何导出接口**。
  对对话、画布各做一次同样的断言。
- V4（画布 round-trip·可执行·D-08）：创建一张含 3 种节点类型的画布 → 物化 →
  取 mermaid 源码 `.md` → 重新解析导入为画布 → 再次物化 →
  断言两次的 mermaid 源码**逐字符相等**（或规范化后相等）。
- V5（🔴 生成物不伪装·可执行）：产生 1 个 AI 生成 artifact 与 1 个上传 artifact，
  内容语义相近。以 `evidencePolicy: "primary-only"` 调 `POST /context/search`，
  断言 ① 返回中**不含**该 `generated` artifact 的任何 segment；
  ② 以 `"all"` 调用时含它且每项带 `synthesized: true`；
  ③ 把请求中的 `evidencePolicy` 篡改为客户端伪造值时，服务端仍按最严策略执行
  （**服务端强制**，不信任客户端）。
- V6（溯源完整·可执行）：对每一个 `source_type == "generated"` 的 artifact，
  断言存在同组的 `provenance.json`，且其 JSON 含全部七个必填键
  （prompt / model / model_version / run_id / context_pack_id / generated_at / triggered_by）。
  **断言缺溯源的生成物数量为 0**；再人为构造一个缺 `model` 的生成事件，
  断言其状态停在 `REVIEW_PENDING` 而非 `READY`。
- V7（权限最严·可执行）：一段对话引用了一份标记为机密的材料，
  断言其 `messages.jsonl` 的敏感级 **≥** 该材料的敏感级；
  以只能看该对话但看不到那份材料的会话请求 `messages.jsonl`，断言被拒。
- V8（结构保留·可执行）：工作坊 `transcript.jsonl` 每行断言含
  `speaker` / `start_ms` / `end_ms` / `text` 四个必填键；
  含「反对意见」标注的行其 `tags` 含 `objection`。
  问卷 `schema.json` 断言含题号、题型、选项，且题号能与 `responses.csv` 列头一一对应。
- V9（物化失败可见·可执行）：注入一个序列化错误让某次物化失败，断言
  ① 业务对象仍正常可用；② 文件浏览器对应位置出现「物化失败」记录；
  ③ 该记录带原因与重试入口；④ **不存在**"业务对象存在但浏览器里什么都没有"的静默态。
- V10（幂等·可执行）：对同一 `source_ref` 连续触发两次物化事件且业务数据未变，
  断言 `artifact_versions` **不新增**（`content_hash` 相同），
  只新增一条 `provenance_events`。
- V11（观察者态）：以观察者会话请求 `messages.jsonl` 与 `transcript.jsonl`，
  断言默认返回 404（与不存在同响应）；经脱敏并发布后可见。
- V12（字段契约·可执行）：断言物化文件的表中**不存在** `design_facet_id`
  与 `method_stage_id` 列，环节绑定字段名严格为 `agenda_segment_id`（D-03a）。
