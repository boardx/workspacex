## 一、模块职责

**一句话**：给这个项目的**全部上下文**一个唯一的、可浏览的、可下载的物理形态。

本模块是 Context Engine **证据平面的用户界面**。它不产生新的存储，
它把 `artifacts / artifact_versions` **投影**成用户能打开、能下载、能交付的一棵树。

它要同时成立三件事：
1. **能上传** —— 用户交进来的材料有一条可见、可解释、可重试的入库链路。
2. **能看到** —— 不只是上传的文件，问卷、访谈、工作坊、对话、画布、AI 生成
   **全部物化成文件**，在同一棵树里并列。
3. **能下载 / 能真删** —— 客户与合规方要的是「把材料交给我」；
   撤回时「删除后文件浏览器里那份必须真的消失」是可演示的验收面。

**为什么值得付这个代价**（架构 2.0 原文四条）：
可下载是交付前提 · 撤回与删除要能演示 · 排查「AI 为什么这么答」时能直接打开那个文件 ·
对象存储里那棵树本身就是一份可离线打开的完整交付物。

| **UC-22.4** | 版本、派生物与删除传播 | P0 | **8** | 原件永不覆盖 + 派生物独立可见 + **六类级联失效** + 两级 SLA |
| | | | **47** | |

**依赖关系（同迭代交付才能端到端验收）**：

```
UC-22.2 上传与摄取 ──┐
                     ├──> UC-22.1 文件浏览器（可见性落点）
UC-22.3 物化    ─────┘          │
      （复用 22.2 的摄取链路）    │
                                 v
                          UC-22.4 版本与删除
                     （浏览器是删除的验收面）
```

- **22.2 必须先于 22.3**：物化产物复用同一条摄取链路，不另建入库路径。
- **22.1 必须与 22.3 同迭代**：否则「能在文件浏览器看到」无法验收。
- **22.4 依赖前三者**：删除的验收断言（`GET .../download` 返回 404）落在 22.1 的接口上。

## 五、原型状况：**确认缺失**，需补画

**原型在本模块只提供两样东西**：

1. **项目 → 项目筹备 → 材料准备**屏——但它**不是文件浏览器**，
   是**环节维度的材料要求表**（列：环节 / 形式 / 负责人 / 材料要求 / 推演模板），
   副标题「每个环节要用到的材料与推演模板 · 缺料的环节现场会空转」。
   它回答「这个环节需要什么材料」，**不回答「我们有哪些文件」**。
   屏上有 `[上传材料]` 与 `[让 AI 补齐缺料]` 两个按钮，
   计数「9 已入库材料 ｜ 2 环节缺料 ｜ 6 推演模板已绑定」。
2. **三处计数钩子**：蓝本第 9 项「项目材料 9 件」、第 10 项「分组打印素材 4 件」、
   对话右栏五标签之一「材料 12」。**都只有数字，都没有下钻目标。**

⚠ **缺失状态判定：原型确认缺失（不是「未探明」，也不是「原型待补」中的未知）。**
判定依据：**项目工作台的 7 个标签**与**项目设置的 6 个子标签**均已完整抽取
（`proto-05-deep-layer.md` / `proto-08-project-settings.md`），
其中**没有任何文件浏览 / 目录树 / 批量下载 / 版本列表 / 删除确认的界面**。
这是**枚举完毕后确认不存在**，与「某个屏还没点进去」性质不同。

**四份 UC 的 R8 均已标注「原型确认缺失，实现前必须先补画原型并由产品/设计确认」。**
需要补画的屏至少七个：
① 文件浏览器主屏（树+列表+预览三栏）② 上传弹层 ③ 摄取进度抽屉（九态）
④ `REVIEW_PENDING` 审核界面 ⑤ 版本列表下钻 ⑥ 删除确认（含影响面预览）
⑦ 待删除队列（合规角色）。

## 六、本模块最需要人类裁决的三条

见各 UC 的 R10。三条 `[待确认]` 按阻塞程度排序：

1. **🔴 `[待确认]` 观察者是否有下载权，以及含机密标记文件的搜索命中片段是否展示**
   （UC-22.1 R10）。前者直接定义客户交付边界——「只读」是否包含「可把文件带走」；
   后者是 O-17「材料级粒度」的直接后果：展示则片段脱离了「整份走本地模型」的路由约束，
   不展示则搜索对机密材料等于失效。**这是权限语义与合规边界，不应由实现者决定。**
2. **🔴 `[待确认]` 七类来源的物化时限具体数值**（UC-22.3 R10，R9 已给出提议：
   问卷 60s / 对话去抖 5min + 终版 60s / 画布 30s / 研究 5min / 音频 5min）。
   没有这五个数，AC2「物化是同步契约」的验收断言写不出来，
   「有多同步」也就成了各人各解——而这正是 file-first 与「事后导出」的分界线。
3. **🔴 `[待确认]` 能否删除单个中间版本，以及删除在宽限期内是否可撤销**（UC-22.4 R10）。
   前者涉及证据链完整性（若 v2 曾被某条 Claim 引用，删掉它等于让那条 Claim 悬空）；
   后者是误删刚需与对受访者「已删除」承诺之间的直接冲突。
   两条都必须由**合规 + 产品**共同拍板。

**次一级但同样阻塞开工**（写在各 UC 的 R10）：
UC-22.2 的**文件大小/批量/解压炸弹五个上限数值**与**类型白名单**
（尤其 `.html` / `.svg` 是否允许，直接决定预览渲染的安全设计）。

## 七、发现的契约冲突与风险

**未发现与既有模块的口径冲突。** 本模块是新增模块，与现有 20 个模块的接触面均为
「本模块消费其定义」或「本模块提供其落点」，无相互矛盾的既有裁决。

但记录三条**必须由 `requirement-author` 在生成 `feature_list.json` 时处理的事项**：

1. **⚠ 估点可能重复计入**：D-13 已把 UC-17.2 的最小切片（待删除队列 + 退出检索 +
   报告段落标失效 + 回执）**前置进 phase-1，+8 点**。
   UC-22.4 的 8 点与这 8 点在**实现上是同一批工作**（同一套待删除队列、同一套级联失效）。
   两处必须核对，**不要重复计入 phase-1 总点数**。
   本索引报出的 47 点是**模块视角**的完整估点，未做去重。
2. **⚠ 六类级联失效依赖外部模块提供失效接口**：
   pgvector（embedding）、FTS/Segment、`ontology_edges`（09-kg）、
   缓存与 `context_packs`（00-core）、报告段落标记（13-deliv / 14-brain）。
   **任一模块不提供失效接口，UC-22.4 的 AC2 就无法达成**——
   这是本模块最大的外部风险，需在排期上确保这些接口先于 UC-22.4 就绪。
3. **⚠ 上游模块不得自建入库路径**：05-rec / 06-itv / 12-survey / 08-chat / 07-canvas
   必须复用 UC-22.2 的摄取链路。若各自建一条私有入库路径，
   幂等键与权限传播就会有多套实现，file-first 的一致性立刻瓦解。
   建议在各上游模块的 R10「跨模块契约」中回写这一条。
