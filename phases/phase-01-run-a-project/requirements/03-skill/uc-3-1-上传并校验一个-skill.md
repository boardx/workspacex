# 原始需求（细化）— UC-3.1 上传并校验一个 Skill

> 所属：阶段一 · 能跑完一场项目 / M3 上传 Skill
> 来源：`Backlog Use Case.html` 的 UC-3.1；UI 线索来自 `WorkspaceX Standalone.html`；
> **运行态原型**：后台 → AI 能力 → **Skill 库与市场（86 个已启用 · 3 个待审核）**——
> `[导入 Skill]` `[＋ 新建 Skill]`、列表列「来源标记 / 调用次数 / 满意度 / 文件数」、
> 待审核条目「Jobs-to-be-done 访谈法 —— 高琳 18 分钟前从 Codex 社区导入，安全扫描通过，
> 等待方法论审核 ｜ 来源 Codex 社区 · 4 个文件 `[批准发布]` `[查看内容]`」；
> 大脑 → 晋升队列候选 2「批准并推给全员 …… 并**在 Skill 库里生成一条可调用的 skill**」。

> 口径（四标记）：**[原型]** ＝ `WorkspaceX Standalone.html` **运行态实际存在**的行为（有界面可查，依据 scratchpad 的 proto-01~10 抽取档案）；**[Backlog]** ＝ `Backlog Use Case.html` 的**文档要求**（原型未必实现）；**[设计]** ＝ 依据前两者反推补全，**需人类确认**；**[待确认]** ＝ 不应由实现者自行决定。
> 元数据：优先级 **P0**；估点 **8**（原 5，因双重门禁 + 三种来源 + 元数据面上调）；
> 建议迭代 **迭代 2 · 能挂能力**。
>
> **[人类已拍板 2026-07-27 · D-06]** Skill ＝ **声明式契约**——提示词模板 ＋ 输入输出 schema
> ＋ 数据范围声明。**phase-1 不做沙箱、不执行任意代码**；多文件可执行包、仓库导入、
> 外部社区导入均为 **phase-2 能力升级**。本文按此口径书写。

## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-3.1 / 上传并校验一个 Skill
- **Actor**：**能力维护者**（提交人）、**审核人**（方法论审核，新增角色见 R5）、**引导师**（使用方）
- **目标**：[Backlog] Skill 是能被 agent 调用的一段固定能力（读画布、缺口检测、生成便签…）。
  要能新建/导入、校验、经**双重门禁**发布、绑定到**议程环节**、按角色下发。
  （[原型] 已写实的是 Skill 库列表与**双重门禁**文案；「读画布 / 缺口检测 / 生成便签」
  三个能力例子在原型档案 0 命中。）
- **[人类已拍板] Skill 的物理形态**：一份**声明式契约**，含三个部分——
  1. **提示词模板**（可带变量占位符）；
  2. **输入输出 schema**（结构化字段定义，供 agent 与运行时校验）；
  3. **数据范围声明**（这个 skill 允许读到哪些数据；与 21-mcp 的授权范围求交）。
  phase-1 的 skill **不含可执行代码**，运行时只做「模板渲染 → 模型调用 → 输出按 schema 校验」。
- **本用例结果**：Skill 库中新增一条处于 `已启用` 状态的 skill，带完整契约、来源标记、
  可见性范围与最近一次试跑结果；未过门禁的停在 `待审核` 并对审核人可见。
- **系统边界**：Skill 库、契约校验（schema + 数据范围越权检查）、安全扫描、方法论审核、
  试跑、版本、可见性范围、议程环节绑定与运行时挂载。
- **核心数据对象**：Skill、Skill 版本、提示词模板、输入输出 schema、数据范围声明、
  来源标记、审核记录、试跑记录、可见性范围、调用与满意度统计。

## R2 前置条件 / 触发条件

- **前置条件**：
  - 用户已建立可校验的正式身份，且在本组织持有能力维护者权限（组织角色见 `uc-0-3`）。
  - 依赖能力「登录管理、项目模板（skill 要绑到**议程环节**上）」可用，
    或界面能明确显示其不可用状态。
  - 若 skill 的数据范围声明涉及原始转写、客户资料或跨范围读取，相应授权与留存策略已生效。
  - **[设计]** 若 skill 指定了模型，该模型必须已在 20-model 中处于「已启用（测试通过）」态；
    否则模型下拉里根本不出现（见 UC-20.2 硬约束）。
- **触发条件**（[原型] Skill 有**三种来源**，三条入口收敛到同一套门禁）：
  - **来源 ①「自建 / 上传」**：[原型] 维护者在后台 → AI 能力 → Skill 库点 `[＋ 新建 Skill]`
    （从空白开始）或 `[导入 Skill]` 上传一份契约定义。
  - **来源 ②「外部社区导入」**：[原型] 从 **Codex 社区**导入现成 skill（原型条目
    「高琳 18 分钟前从 Codex 社区导入 · 4 个文件」）。
    **[人类已拍板 D-06] phase-1 不实现**——社区市场对接、仓库导入、多文件包解析
    均为 **phase-2 能力升级**；phase-1 只保留数据模型上的 `source=community` 取值与
    「4 个文件」这类文件数字段，界面上入口置灰并标注 later。
  - **来源 ③「方法类知识晋升后自动生成」**：[原型] 大脑 → 晋升队列，方法类候选被
    `[批准并推给全员]` 后**自动在 Skill 库生成一条可调用的 skill**。
    这条链路单独成用例，见 **UC-3.5**；本用例负责接收它产出的 skill 并走同一套门禁。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

1. **能力维护者操作**：新建或导入 skill 定义，填写**名称、一句话职责、提示词模板、
   输入输出 schema、数据范围声明、可见性范围**。
   **系统响应**：校验当前身份与组织范围；把 skill 落为 `草稿` 状态（仅作者与能力维护者可见），
   自动打上**来源标记**（`自建` / `CC` / `画布` / `社区`，见 R7）。
2. **系统处理**：跑**静态契约校验**——必填字段齐全、输入输出 schema 可解析且自洽、
   数据范围声明**不越出提交人自身权限**、是否声明了失败兜底（输出不符合 schema 时怎么办）。
   校验失败列出逐条原因，不入库。
3. **系统处理**：跑**安全扫描（自动，门禁第一道）**——[原型]「安全扫描通过，等待方法论审核」。
   [设计] phase-1 的扫描对象是声明式内容本身：提示词注入模式、越权数据范围申请、
   敏感字段外泄倾向、对未授权 MCP 工具的引用。扫描结论以「通过 / 有风险项待确认 / 拒绝」三态呈现。
4. **能力维护者操作**：[Backlog] **试跑一次样例输入**，看返回内容、是否符合 schema、
   耗时与 token 消耗。
   **系统响应**：使用 skill 声明的模型执行一次真实调用，记录输入、输出、耗时、命中数据范围；
   [Backlog] **试跑失败不入库**，给出失败原因与日志。
   ⚠ **原型确认缺失**：Skill 库列表行的操作**只有 `[编辑]`**（待审核行另有
   `[批准发布] [查看内容]`），**没有 `[试跑]`**。原型里的 `[试跑]` 只出现在
   **Agent 管理**行与**画布模板**草稿行（`[发布][试跑]`）以及蓝本设计器（`[试跑一场]`）
   ——**不同对象，不可跨屏挪用**。skill 侧的试跑能力**需补画原型**。
5. **系统处理**：提交进入 **`待审核`** 状态，出现在审核人的待办里。
   [原型] 列表上呈现为「**待审核** —— 安全扫描通过，等待方法论审核」，附
   `[批准发布]` `[查看内容]` 两个动作。
6. **审核人操作**：做**方法论审核（人工，门禁第二道）**——判断这个 skill 的方法本身是否成立、
   提示词是否会诱导结论、数据范围是否最小必要、输出格式是否符合组织的产出规范。
   **系统响应**：`[批准发布]` 则转入 `已启用`；`[退回]` 则回到 `草稿` 并附退回理由。
7. **系统收口**：校验 AC1「库里每个 skill 都有可看的输入输出契约与最近一次试跑结果」、
   AC2「**未同时通过安全扫描与方法论审核的 skill 不得进入已启用状态**」；
   记录操作者、时间、对象、门禁两道结论与来源进审计，并刷新 Skill 库列表与元数据。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[设计] Skill 库为空或筛选无结果时展示真实空态、原因和下一步入口
    （`[＋ 新建 Skill]`），**不生成示例 skill 冒充真实结果**
    （原型每屏都填满样例数据，零空态）。
  - A2：[原型] **来源 ③ 晋升生成**的 skill 进入本流程时，跳过第 1 步的人工填写
    （契约由晋升流程预填），但**不跳过任何一道门禁**——安全扫描与方法论审核照跑。
    详见 UC-3.5。
  - A3：[设计] 安全扫描判为「有风险项待确认」时不直接拒绝，把风险项逐条列给审核人，
    由审核人在方法论审核时一并裁决；风险项的确认理由必须留痕。
  - A4：[设计] 审核人同时是提交人时，**不得自审自批**；系统要求指派另一名审核人，
    组织内无第二名审核人时明确阻断并提示（见 R7）。
- **异常流程**：
  - E1：[Backlog] **声明要读原始转写的 skill 需额外授权**——提交时即校验，未获授权的
    数据范围声明直接判为校验失败，不进入待审核队列。
  - E2：[Backlog] **试跑失败不入库**，给出失败原因与日志（含模型返回原文与 schema 校验差异）
    ——skill 侧无试跑入口，属**原型确认缺失**。
  - E3：[设计] skill 指定的模型在提交后被停用（20-model）时，该 skill 自动转为
    「依赖失败」态并停止被载入，提示维护者改选模型；**已启用状态不被静默撤销**，
    但运行时明确失败而非降级到别的模型。
  - E4：[设计] 请求超时、网络中断或依赖（模型、MCP）不可用时，保留用户当前输入与
    最后成功数据，明确失败原因并提供安全重试。失败不得被呈现为成功。
  - E5：[设计] 同一 skill 被并发修改时不得静默覆盖；提示版本已变化，允许刷新、对比或重新提交。
  - E6：[设计] 权限在操作过程中被撤回时立即终止后续写操作；已完成步骤按审计规则保留。

## R5 权限与可见性

- **能力维护者**（组织角色：管理员 / 被授予能力维护权的顾问）：可新建、导入、编辑、试跑、
  提交 skill；**不能自行批准发布**。范围限定在其有权访问的组织。
- **审核人**（**[设计] 新增角色**——现有五角色「引导师 / 组长 / 组员 / 观察者 / 项目负责人」
  中没有对应项）：
  - **[已裁决 O-21] 本用例的审核人 ＝ ① 方法论审核人**（看**方法对不对**）。
    职责：执行**方法论审核**，对 `待审核` 队列行使 `[批准发布]` / `[退回]`；
    同一职能亦负责 **UC-3.5 的知识晋升审批**。
  - **[已裁决 O-21] 与之并列的 ② 安全评审人**（看**权限给不给**）负责
    **MCP 放行（UC-21.1/21.2）与 agent 越权申请（UC-4.1）**，**不是同一职能，不得合并**——
    两者的判断依据、能力要求、失误后果完全不同，合成一种会让方法论专家去批权限。
  - **[已裁决 O-21] 授予方式**：两种职能**均由组织管理员指派**，
    是**组织级职能授权**（挂在组织角色上，不是项目角色），**可跨团队审**；
    一个组织可有多名。可由同一自然人兼任两个职能，
    但**同一事项上只能行使其中一种**。
  - **[已裁决 O-21] 硬约束**：**不得自审自批**（提交人 ≠ 审核人，见 A4）。
  - **[待确认]** 审核 **SLA 与超时后的默认行为**（建议 3 个工作日、超时自动升级给组织管理员，
    **数值无依据，需产品确认**）；以及是否需按 skill 的领域细分审核人
    （如财务类 skill 需财务口审核人）。
- **引导师**：可浏览已启用且可见性范围覆盖自己的 skill，可在蓝本里绑定（UC-3.2）、
  在对话里临时加减（UC-3.3）；**不能改契约、不能发布**。
- **组长 / 组员**：只能使用引导师下发的 skill，库本身不可见。
- **观察者**：默认不可见 Skill 库。
- **项目负责人**：可查看本组织已启用 skill 清单与审计摘要；写操作需显式授权。
- **可见性范围**（[原型] 后台资源统一二取值）：**全组织可用** / **仅某团队**
  （如「仅能源组」）。范围之外的用户在任何入口都看不到该 skill，且接口不得返回其存在性。
- 未登录、链接失效或未列出的角色：默认无权限；接口不得返回越权数据，不能只依赖前端隐藏。

## R6 后置条件 / 不包含

- **正常后置条件**：
  - Skill 处于 `已启用`，带完整契约、双门禁结论、最近一次试跑结果与可见性范围，
    可从 Skill 库再次打开。
  - **Skill 元数据面**（[原型] 列表列）齐备且可读：
    - **来源标记**：`CC`（平台内置） / `自建` / `画布`（由画布模板派生） / `社区`（phase-2）
      / `晋升生成`（[设计]，来源 ③ 需要一个可区分的取值，见 UC-3.5）；
    - **调用次数**（原型示例：4,120 / 2,884 / 1,930 / 742 / 508）；
    - **满意度百分比**（原型示例：94% / 91% / 88% / 86% / 90%，口径见 UC-3.6）；
    - **文件数**（原型示例「4 个文件」）——**[设计] phase-1 的声明式契约恒为单件**，
      本字段为 phase-2 多文件包预留，phase-1 显示为 1 或留空，不得据此实现打包解析；
    - **可见性范围**：全组织可用 / 仅某团队。
  - [Backlog验收] AC1：库里每个 skill 都有可看的输入输出契约与最近一次试跑结果。
    （[原型] 列表行只有来源标记 / 调用次数 / 满意度 / `[编辑]`；
    **输入输出契约与试跑结果两项行内均未渲染**——属原型确认缺失。）
  - [设计验收] AC2：**未同时通过安全扫描（自动）与方法论审核（人工）的 skill
    不得进入已启用状态**；直接改数据库状态的尝试被服务端拒绝并记审计。
  - [设计验收] AC3：可见性范围为「仅某团队」的 skill，对非该团队成员在列表、搜索、
    绑定面板、对话加技能四个入口全部不可见。
- **失败后置条件**：
  - 不创建「看似成功」的已启用 skill；未过门禁的内容保留为草稿/待审核，失败事件进可观测日志。
- **不包含**：
  - **[人类已拍板 D-06] 任意代码无沙箱执行**——phase-1 的 skill 是声明式契约，
    运行时不执行提交方提供的代码；沙箱与可执行包是 phase-2 议题。
  - **[phase-2 能力升级]** 从仓库导入 skill、多文件（如原型的「4 个文件」）包解析、
    **Codex 社区市场对接与社区导入**。
  - 组员自行扩大数据权限。
  - 不扩展到本 use case 未声明的跨组织、跨客户或公开发布能力。
  - Skill 的**改进反馈与版本触发**闭环（消息级 👎 → 改进 PR）——见 **UC-3.6**。
  - **方法类知识晋升生成 skill** 的判定与预填逻辑——见 **UC-3.5**。

## R7 业务规则（不随具体实现变化的硬性约束）

- **[人类已拍板 D-06]** Skill ＝ 提示词模板 ＋ 输入输出 schema ＋ 数据范围声明。
  **phase-1 不含任意代码、无沙箱执行**。
- **[原型] 双重门禁**：`安全扫描（自动）` ＋ `方法论审核（人工）`，**两道全过才能启用**。
- **[已裁决 O-11] skill 状态机 ＝ 四态**：
  ```
  草稿 ──提交──▶ 待审核 ──[批准]──▶ 已启用 ──[停用]──▶ 已停用
    ▲               │                   ▲                  │
    └──── [退回] ───┘                   └──── [恢复] ──────┘
  ```
  原问题（**保留原措辞**）：本文此前写三态机 `草稿 → 待审核 → 「已发布」`，但原型档案里
  **skill 只出现两个状态取值——`已启用`（86 个）与 `待审核`（3 个）**，
  **没有 `草稿`、也没有「已发布」这个词**；「草稿 → 待审核 → **运行中**」是
  **Agent 管理**的状态机（proto-03），不可混用到 skill。
  需裁决「已发布」与原型的 `已启用` 是同一态还是两态（另有 `已停用` / `已归档`，见 UC-3.4）。
  **裁决（O-11）**：**四态 `草稿 → 待审核 → 已启用 → 已停用`**；
  **`已归档` 作为 `已停用` 的终态子类不单列**；
  **「已发布」一词全仓废弃，统一用 `已启用`**（贴原型）。
  理由：原型只给了两个取值，新增的应是**最少**的必要补全——
  `草稿`（上传未提审）与 `已停用`（UC-3.4 明确需要）各有独立行为；
  「已发布」与 `已启用` 语义完全重合，属无谓分裂。
  ⚠ 由此，本文档全部原写「已发布」之处**一律改为 `已启用`**；
  状态字段的取值集合断言恰为 `{草稿, 待审核, 已启用, 已停用}`（**四个，不多不少**）。
- **[已裁决 O-21]** 提交人不得自审自批；审核动作必须记录审核人、时间、结论与理由。
  **裁决（O-21）**：本用例的「审核人」明确为 **① 方法论审核人**——
  职责是**看方法对不对**（skill 内容 + 知识晋升，后者见 UC-3.5）。
  与之并列的 **② 安全评审人**负责 **MCP 放行与 agent 越权申请**（看权限给不给，
  见 UC-21.1 / UC-21.2 / UC-4.1），**两者不是同一职能，不得合并**。
  两者**均由组织管理员指派**，**不得自审自批**；可由同一自然人兼任，
  但**同一事项上只能行使其中一种职能**。
- [Backlog] 声明要读原始转写的 skill 需额外授权。
- [Backlog] 试跑失败不入库，给出失败原因与日志（skill 侧试跑入口**原型确认缺失**）。
- **[设计]** skill 的**有效数据范围 ＝ 声明的数据范围 ∩ 调用方 agent 的工具白名单
  ∩ MCP 授权范围 ∩ 当次任务的权限包**（三层权限模型见 UC-4.1 R3 与 21-mcp）；
  声明本身不构成授权。
- **[设计]** skill 只能选择 20-model 中**测试通过并已启用**的模型；停用的模型不出现在下拉里。
- **[设计]** 来源标记不可由提交人自填——由系统按入口自动打标，防止「社区来的伪装成自建」。
- AC1：库里每个 skill 都有可看的输入输出契约与最近一次试跑结果。
- AI/Agent 生成的候选内容必须标识为机器产出，展示可追溯来源；来源不足时不得伪造结论。
- 所有权限判断必须在服务端执行；隐藏入口只是界面表现，不构成安全控制。
- 任何发布、停用、退回、覆盖动作都必须记录审计事件，并显示动作影响范围。

- **兼容与降级要求**：
  - 响应式 Web；后台管理以桌面端为主，移动端保证查看与审批两个动作可用。

## R10 已知约束 / 依赖

- **内部依赖**：
  - `uc-0-3` 角色本体与两层权限模型（能力维护者、审核人、可见性范围）；
  - **20-model**（UC-20.2）——**只有测试通过的模型才出现在 skill 的模型选择里**；
  - **21-mcp**（UC-21.1）——skill 数据范围声明中引用的 MCP 工具与授权范围；
  - 02-tpl 项目蓝本（skill 要绑到第 13 项「Skill 绑定」上）。
- **被依赖**：UC-3.2 议程环节绑定、UC-3.3 对话内临时加减、UC-3.4 版本与停用、
  UC-3.5 晋升生成、UC-3.6 改进反馈；**04-agent 全部用例**（agent 通过 skill 干活）。
- **跨模块契约**：Skill ID、版本、来源标记、可见性范围、审计事件必须与 04-agent、
  20-model、21-mcp、14-brain 使用统一标识。
- **[已裁决 O-21 · 部分]** 原问题：**审核人角色的授予方式与 SLA**——由谁指派、
  能否跨团队审、超时未审怎么办。这是本次新增角色最关键的未决项。
  **裁决（O-21）**：
  - **职能拆两种**：**① 方法论审核人**（skill 内容 + 知识晋升，看方法对不对，**即本用例**）；
    **② 安全评审人**（MCP 放行 + agent 越权申请，看权限给不给，见 21-mcp / UC-4.1）。
    两者**判断依据、能力要求、失误后果完全不同，不得合成一种**。
  - **授予方式**：**均由组织管理员指派**；是**组织级职能授权**，可跨团队审。
  - **硬约束**：**不得自审自批**（提交人 ≠ 审核人）。
  - **agent 越权申请**：须 **安全评审人 + 组织管理员会签**。
  - ⚠ **仍 [待确认]**：**审核 SLA 的具体数值与超时行为**（建议 3 个工作日、
    超时自动升级给组织管理员，**数值无依据，需产品确认**）；
    以及是否需按领域细分审核人（如财务类 skill 需财务口审核人）。
- **[设计 · 架构对齐] skill 执行只能通过 Context API 取上下文**：
  skill 的「数据范围声明」在运行时的兑现方式是——
  **向 Context Engine 的 Context API 请求一个 Context Pack**
  （`docs/architecture/context-engine.md` 第四节），
  **不得绕过 Context Engine 直查业务库、对象存储或向量库**。
  理由：Context Engine 是**唯一 AI 边界**——权限判定（`permissionDecisionId`）、
  引用锚点（`anchor`）、召回理由（`retrievalReasons`）与遗漏说明（`omissions`）
  都只在这条通路上产生；旁路取数会让 skill 的产出**无锚点、无权限凭据、不可引用**。
  由此推出两条可验收的约束：
  ① skill 运行时的**有效数据范围 ＝ 声明范围 ∩ Context Pack 实际返回项**；
  ② 每次 skill 调用**必须留下 `context_packs` 记录**，使「这次 skill 读到了什么」可重放
    （对应架构首批完成门槛第 ⑥ 条与 `uc-14-6` 检索可审查）。
- **[设计 · 架构对齐] 编排边界**：**LangGraph 只用于深度研究、人工确认（HITL）、多阶段生成**；
  **摄取流水线用持久任务系统**（PG outbox + worker），**两者不可混用**。
  单个 skill 的「模板渲染 → 模型调用 → schema 校验」是**一次同步调用**，
  **既不进 LangGraph 图，也不进摄取流水线**。
- **[待确认]** 安全扫描的具体规则集与「有风险项待确认」的判定阈值，需安全负责人给出。
- **[已裁决 O-37]** 原问题：满意度百分比的计算口径与最小样本量（与 UC-3.6 的 👎 聚合口径必须一致）。
  **裁决（O-37）**：**skill 满意度 ＝ 👍 / (👍+👎)**；**最小样本量 10**，
  低于 10 **显示「样本不足」而非百分比**；聚合浮现阈值 **3 条相似 👎**（与 UC-3.6 同一口径）。
  数值需产品确认，但「低于最小样本量不显示百分比」这条**无论数值如何都已定下**。
- **[待确认]** phase-2 社区导入的信任模型（Codex 社区是否可信、是否需签名校验）。

## R12 AI Ready 验收线索

- V1（成功态）：AC1 —— 任取一条已启用 skill，能看到其输入输出契约与最近一次试跑结果。
- V2（门禁态）：AC2 —— 只过安全扫描未过方法论审核的 skill 停在 `待审核`；
  直接调接口置为 `已启用` 被拒绝并记审计。
- V3（门禁态）：提交人尝试批准自己提交的 skill 被拒绝，提示需另一名审核人。
- V4（可见性态）：AC3 —— 标为「仅能源组」的 skill 对平台组成员在列表 / 搜索 / 蓝本绑定面板 /
  对话加技能四处均不可见，接口不返回其存在性。
- V5（权限态）：逐一使用 能力维护者 / 审核人 / 引导师 / 组员 / 观察者 / 未授权用户访问，
  可读数据与可执行动作严格符合 R5。
- V6（校验失败态）：提交一份声明读原始转写但未获授权的 skill，被判校验失败且不进待审核队列。
- V7（试跑失败态）：试跑返回不符合 schema 时不入库，界面给出失败原因与可复制日志。
- V8（依赖失败态）：把 skill 依赖的模型在 20-model 停用，该 skill 载入时明确失败，
  **不静默换模型**。
- V9（来源态）：三种来源各造一条，来源标记由系统自动打标且不可被提交人改写。
- V10（空态）：Skill 库为空时显示真实空态与 `[＋ 新建 Skill]`，不生成示例数据。
- V11（并发态）：两名维护者同时改同一 skill 不静默覆盖，可识别最终版本。
- V12（审计态）：发布、退回、停用可按操作者、时间、对象、门禁结论检索；越权尝试也有安全审计记录。
- V13（状态枚举 · O-11）：skill 状态字段的取值集合**恰为** `{草稿, 待审核, 已启用, 已停用}`；
  代码与数据中**不存在 `已发布` 这个取值或字面量**；`已归档` 不作为独立状态出现。
- V14（两种审核职能 · O-21）：以**方法论审核人**身份尝试裁决工具白名单的越权申请 → 被拒；
  以**安全评审人**身份尝试 `[批准发布]` skill → 被拒；
  两种职能的指派动作均只有**组织管理员**可执行；提交人以任一职能自审自批 → 被拒。
- V15（Context API 唯一通路 · 架构对齐）：执行一次 skill，
  断言其读取的全部上下文均来自 Context API 返回的 Context Pack；
  用架构测试/依赖规则断言 skill 运行时**不存在直连业务库或向量库的代码路径**。
- V16（Context Pack 可重放 · 架构对齐）：一次 skill 调用后，
  `context_packs` 中存在对应记录，可重放当时读到的条目与其 `anchor`、`omissions`。
