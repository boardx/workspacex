# 原始需求（细化）— UC-3.5 方法类知识晋升后自动生成 Skill

> 所属：阶段一 · 能跑完一场项目 / M3 上传 Skill（**跨模块：03-skill × 14-brain**）
> 来源：**运行态原型** 大脑 → **晋升队列**：
> 「候选 2 · 方法「工期承诺谈法：用交付时间替代 IRR 说服 CFO」
> `[批准并推给全员]` —— 晋升后会自动成为 Ava 在同类客户谈判场景下的默认方法，
> 并**在 Skill 库里生成一条可调用的 skill**」；
> 大脑「三层关系总览」节点类型「**方法/Skill 86**」与后台 Skill 库「**86 个已启用**」
> **数字一致**——两者是同一份资产的两个视图；
> 大脑「AI 读到了什么」的系统提示装配「**# 方法 ← Skill 库**」；
> 候选 3「Ava 提名·**需人工确认后才可入库（AI 不能自行晋升）**」；
> 晋升队列的「批准前必填（缺任一项都无法进入生效状态）：适用范围 / 有效期 / 复核负责人」，
> 有效期默认值「**方法 24 个月**」。
> **补写缘由**：原 4 份 03-skill 用例只覆盖「维护者手工上传」一条来源，
> 而原型明确存在第三条来源——**组织大脑的方法类知识被批准晋升后自动生成 skill**。
> 不写这条，「方法沉淀 → 可复用能力」这条组织学习闭环在系统里断掉。

> 口径（四标记）：**[原型]** ＝ `WorkspaceX Standalone.html` **运行态实际存在**的行为（有界面可查，依据 scratchpad 的 proto-01~10 抽取档案）；**[Backlog]** ＝ `Backlog Use Case.html` 的**文档要求**（原型未必实现）；**[设计]** ＝ 依据前两者反推补全，**需人类确认**；**[待确认]** ＝ 不应由实现者自行决定。
> 元数据：优先级 **P1**；估点 **5**；建议迭代 **迭代 5 · 收尾项**
> （**依赖 14-brain 的晋升队列**，若 14-brain 在 phase-3 则本用例需相应后置，见 R10）。
>
> **[人类已拍板 · D-32]** 知识晋升**严格准入**：**支撑过一个被签字的决策 ＋ 复盘中被验证**，
> 才够格晋升。本用例不放宽这条闸门。
> **[人类已拍板 · D-06]** 生成出来的 skill 同样是**声明式契约**，无沙箱、不含可执行代码。

## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-3.5 / 方法类知识晋升后自动生成 Skill
- **Actor**：**提名人**（顾问/引导师，把方法提到晋升队列）、**晋升审批人**（大脑侧，
  行使 `[批准并推给全员]`）、**审核人**（Skill 侧方法论审核，见 UC-3.1 R5）、
  **复核负责人**（晋升时必填，负责到期复核）
- **目标**：[原型] 把「某人在某个项目里验证有效的方法」**固化成全组织可调用的能力**——
  方法类知识被批准晋升到组织大脑的同时，**在 Skill 库里自动生成一条可调用的 skill**，
  并成为相关 agent 在对应场景下的默认方法。
- **本用例结果**：
  1. 组织大脑中新增一条 `生效` 态的方法类知识（带适用范围、有效期、复核负责人）；
  2. Skill 库中新增一条与之**双向关联**的 skill，来源标记为 `晋升生成`；
  3. [原型] 该方法成为指定 agent「在同类场景下的默认方法」。
- **系统边界**：晋升队列的方法类分支、方法 → skill 契约的转写、双向关联、
  自动打来源标记、进入 UC-3.1 的双重门禁、agent 默认方法绑定、
  源知识状态变化对 skill 的联动。
- **核心数据对象**：方法类知识条目、晋升记录（适用范围 / 有效期 / 复核负责人）、
  Skill（来源标记 `晋升生成`）、方法↔skill 双向关联、agent 默认方法绑定、审计事件。

## R2 前置条件 / 触发条件

- **前置条件**：
  - [原型 · D-32] 候选已满足**严格准入**：**支撑过一个已签字的决策**且**复盘结论判对**。
  - [原型] 候选的**资产类型为「方法」**（区别于「可复用判断」「客户档案」「客户机密」
    三类候选——只有方法类才会生成 skill）。
  - [原型] **批准前必填三项均已填写**，缺任一项都无法进入生效状态：
    - **适用范围**（原型示例：跨境并购 / 德国·荷兰 / 需持照经营行业；
      「范围外的项目仍可检索到，但会标『跨范围引用』并降权」）；
    - **有效期**（[原型] 按资产类型给默认值：行业事实 6 个月 / 监管 12 个月 /
      **方法 24 个月**）；
    - **复核负责人**（原型示例：高琳）。
  - Skill 库可写，且当前组织存在至少一名**审核人**（UC-3.1 R5）。
- **触发条件**：
  - [原型] 晋升审批人在**大脑 → 晋升队列**对一条**方法类**候选点 `[批准并推给全员]`。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

1. **提名人操作**：把某个方法提名到晋升队列（[原型] 队列条目形如
   「高琳提名·来自远洋项目·7/25 ｜ 状态 候选 ｜ 引用它的决策 1」）。
   **系统响应**：落为 `候选` 态；[原型] **AI 也可提名，但需人工确认后才可入库
   （AI 不能自行晋升）**。
2. **系统处理**：校验严格准入（D-32）——是否支撑过已签字决策、复盘是否判对。
   未达标的候选停在 `候选`，界面显示还差哪一条（原型示例「复盘结论：尚未复盘·8/08 到期」）。
3. **晋升审批人操作**：填齐三项必填（适用范围 / 有效期 / 复核负责人），
   点 `[批准并推给全员]`。
   **系统响应**：知识条目进入五态机的 `已批准 → 生效`。
4. **系统处理（本用例的核心）**：**自动生成一条 skill 草稿**——把方法条目转写为
   UC-3.1 定义的声明式契约三件套：
   - **提示词模板** ← 方法的执行步骤与话术（[原型] 大脑侧描述为
     「两个 skill 的**执行步骤与输出格式约束**」）；
   - **输入输出 schema** ← 方法的适用输入与产出形态；
     [设计] 转写不完整时**留空并标为待补**，**不得由系统臆造 schema**；
   - **数据范围声明** ← 默认取**最小必要**，不继承提名人的全部权限。
   同时：
   - **来源标记自动打为 `晋升生成`**（[设计] UC-3.1 R6 的来源取值需新增此项；
     来源标记不可由人改写）；
   - 建立**方法 ↔ skill 双向关联**（从 skill 能追回源知识条目与那个签字决策；
     从知识条目能看到它生成了哪条 skill）；
   - 继承源知识的**适用范围**作为 skill 的**可见性范围与使用范围提示**
     （[设计] 范围外使用不阻断，但标「跨范围引用」并降权，与知识侧口径一致）。
5. **系统处理**：生成的 skill **照走 UC-3.1 的双重门禁**——安全扫描（自动）
   ＋ 方法论审核（人工）。
   **[设计] 硬约束：自动生成不等于自动发布。** 它落在 `待审核`，
   由审核人 `[批准发布]` 后才进入 `已启用`。
6. **审核人操作**：审核转写质量（提示词是否忠实于原方法、schema 是否可用、
   数据范围是否最小必要），`[批准发布]` 或 `[退回]`。
   **系统响应**：发布后进入 Skill 库可选池，可被蓝本绑定（UC-3.2）与对话挂载（UC-3.3）。
7. **系统处理**：[原型] 把该方法设为**指定 agent 在同类场景下的默认方法**
   （原型：「晋升后会自动成为 **Ava** 在**同类客户谈判场景**下的默认方法」）。
   [设计] 这一步落为 agent 的默认 skill 绑定，**需在 04-agent 侧确认**；
   **[待确认]** 「同类场景」如何判定、由谁指定目标 agent。
8. **系统收口**：校验 AC1「方法类候选被 `[批准并推给全员]` 后，Skill 库里出现一条
   来源标记为 `晋升生成`、且与源知识双向可追溯的 skill」；
   记录晋升人、审核人、时间、源决策、生成的 skill ID 与版本进审计。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[原型] **非方法类候选**（可复用判断 / 客户档案 / 客户机密）晋升时**不生成 skill**，
    只入组织大脑；界面不出现 skill 相关提示。
  - A2：[原型] **客户机密类候选卡在脱敏闸门**——若某方法条目含客户机密，
    必须先走「AI 起草脱敏稿 → 人确认」（`[采纳脱敏稿并晋升]` / `[我自己改写]` /
    `[只留在项目层]`），脱敏稿通过后才允许生成 skill；
    [设计] **生成的 skill 只能引用脱敏稿，不得内含原文**。
  - A3：[设计] 晋升审批人可选择「**只晋升知识，不生成 skill**」——
    有些方法适合被检索但不适合被固化成可调用能力。默认勾选「生成 skill」，可取消。
  - A4：[设计] 转写结果不满意时，审核人可在 `[退回]` 的同时把 skill 草稿交给能力维护者
    手工完善，完善后仍走同一套门禁（此时来源标记**保持** `晋升生成`，不改为 `自建`）。
  - A5：[设计] 队列为空时展示真实空态，并保留反向数字
    （[原型] 晋升队列头部原文「4 条待审 · **同期 11 条降级或过期**」）；
    不生成示例候选。**空态本身是设计补全**——原型每屏都填满样例数据，零空态。
- **异常流程**：
  - E1：[原型 · D-32] 未满足严格准入（无签字决策 或 复盘未判对）时**拒绝晋升**，
    自然也不生成 skill；界面明确指出缺哪一条。
  - E2：[原型] **AI 提名的候选未经人工确认不得入库**——系统拒绝任何「AI 自行晋升」路径，
    尝试进安全审计。
  - E3：[设计] 三项必填缺任一项时**无法进入生效状态**，skill 生成一并阻断
    （不允许「知识生效了但 skill 没范围没期限」的半成品）。
  - E4：[设计] 同名/近似 skill 已存在时不静默创建重复项——
    提示「Skill 库已有相近条目 X」，出口二选一：**并入 X 成为新版本**（走 UC-3.4）
    或**新建独立条目**。
  - E5：[设计 · 联动 D-33] 源知识**到期转 `待复核`** 时：
    知识仍在检索范围内并在引用时提示已过期；对应的 skill [设计] **标为「源方法已过期」
    但不自动停用**，由复核负责人处置。**[待确认]** 是否应自动停用。
  - E6：[设计 · 联动] 源知识**被推翻 / 被撤销**时，对应 skill **自动转 `已停用`**
    （走 UC-3.4 的停用路径：列出引用清单、进行中项目不受影响）；
    [原型] 被撤销的知识「转为反例资产，不删除」，skill 亦不硬删。
  - E7：[设计] 源知识**被替代**（产生新版本）时，skill 侧对应发新版（UC-3.4），
    旧版自动归档，已建实例锁在自己的版本上。
  - E8：[设计] 请求超时或依赖不可用时保留输入与最后成功状态，明确失败并可安全重试；
    **不得出现「知识已晋升但 skill 没生成也没提示」的静默失败**。

## R5 权限与可见性

- **提名人**（顾问 / 引导师）：可提名候选；不可自行批准。
- **晋升审批人**：可 `[批准晋升]` / `[批准并推给全员]` / `[退回]`；必须填齐三项必填。
  原问题：晋升审批人与 UC-3.1 的**审核人**是否为同一职能（此前按两个独立职能书写）。
  **[已裁决 O-21]**：审核职能**共两种**——
  **① 方法论审核人**（**skill 内容 ＋ 知识晋升**，看**方法对不对**）；
  **② 安全评审人**（MCP 放行 + agent 越权申请，看**权限给不给**）。
  **知识晋升属于 ①**，因此**晋升审批人与 UC-3.1 的方法论审核人是同一职能**，
  不再单列第三种角色。
  **均由组织管理员指派**，**不得自审自批**（提名人 ≠ 审批人）。
  ⚠ 由此，本用例的「晋升审批」与「生成出的 skill 的方法论审核」由**同一职能**行使，
  但仍是**两道独立的门禁动作**（见 R3 第 5–6 步），**不得因同职能而合并跳过其一**；
  同一自然人在同一条晋升链上**只能行使一次裁决**——
  若他做了晋升审批，则生成 skill 的方法论审核须由另一名方法论审核人执行。
- **复核负责人**（[原型] 晋升必填字段）：源知识到期时的处置责任人；
  [设计] 对其名下的 skill 有「续期 / 停用 / 改版」的处置入口。
- **AI（Ava 等 agent）**：[原型] **可提名，不可晋升**；任何自动入库路径必须被服务端拒绝。
- **引导师 / 组长 / 组员**：只消费发布后的 skill；不可见晋升队列的处置动作。
- **观察者**：不可见。
- **可见性范围**：生成的 skill 继承源知识的适用范围；[原型] 范围外**仍可检索到**，
  但标「跨范围引用」并降权——**这是降权不是阻断**，与 UC-3.1 的
  「仅某团队 ＝ 完全不可见」是两套不同语义，实现时不得混同。
- 未登录、链接失效或未列出的角色：默认无权限；接口不得返回越权数据。

## R6 后置条件 / 不包含

- **正常后置条件**：
  - 组织大脑中该方法处于 `生效`，带适用范围、有效期、复核负责人。
  - Skill 库中存在一条来源标记 `晋升生成` 的 skill，已过双重门禁并 `已启用`。
  - 方法 ↔ skill **双向可追溯**，且能从 skill 追回**那个被签字的决策**。
  - [原型验收] AC1：方法类候选 `[批准并推给全员]` 后，Skill 库出现对应 skill，
    且能追回源知识与源决策。
  - [设计验收] AC2：**自动生成 ≠ 自动发布**——生成的 skill 必须停在 `待审核`，
    绕过门禁直接置为 `已启用` 被服务端拒绝。
  - [设计验收] AC3：源知识被推翻/撤销时，对应 skill 自动停用且不硬删；
    进行中的项目不受影响。
  - [设计验收] AC4：来源标记 `晋升生成` 由系统打标，任何人不可改写。
- **失败后置条件**：
  - **不允许「知识已晋升但 skill 静默未生成」**；失败必须显式提示并进可观测日志，
    且提供重试入口。
  - 不产生没有适用范围/有效期/复核负责人的生效知识或已启用 skill。
- **不包含**：
  - **[D-06] 任意代码无沙箱执行**。
  - 晋升队列本身的完整实现（五态机、脱敏闸门、健康度、降级与过期）——属 **14-brain**
    （D-24 的 MVP 三件：决策台账 + 五态机晋升 + 检索可审查）。
    本用例只承接「方法类被批准 → 生成 skill」这一条边。
  - Skill 的双重门禁实现——见 UC-3.1（本用例复用）。
  - Skill 版本与停用机制——见 UC-3.4（本用例的 E6/E7 走它的路径）。
  - **消息级 👎 驱动的 skill 改进**——见 UC-3.6（那是另一条反馈来源）。
  - 知识库健康度看板（D-24 已后置）。

## R7 业务规则（不随具体实现变化的硬性约束）

- **[原型]** 方法类知识被 `[批准并推给全员]` 后，**在 Skill 库里生成一条可调用的 skill**。
- **[人类已拍板 · D-32]** 严格准入：**支撑过一个被签字的决策 ＋ 复盘中被验证**。
- **[原型]** **AI 不能自行晋升**——AI 可提名，入库必须人工确认。
- **[原型]** 批准前三项必填（适用范围 / 有效期 / 复核负责人），**缺任一项都无法进入生效状态**；
  方法类有效期默认 **24 个月**。
- **[设计] 自动生成不等于自动发布**：生成的 skill 落 `待审核`，照走安全扫描 ＋ 方法论审核。
- **[设计]** 来源标记 `晋升生成` 由系统打标，不可改写（对照 UC-3.1 R7 的同类规则）。
- **[设计]** 生成的 skill 的数据范围取**最小必要**，**不继承提名人的全部权限**。
- **[原型 · D-16]** 含客户机密的方法必须先过**脱敏闸门**；生成的 skill 只能引用脱敏稿。
- **[设计 · D-33]** 源知识到期转 `待复核` 时仍在检索范围内，引用时提示已过期；
  skill 侧同步标注。
- **[设计]** 源知识被推翻/撤销 → skill 自动停用；被替代 → skill 发新版旧版归档（UC-3.4）。
- **[原型]** 「方法/Skill」在大脑图谱与 Skill 库是**同一份资产的两个视图**
  （原型两处数字均为 86），实现时**不得建两份互不关联的副本**。
- AI/Agent 生成的候选内容必须标识为机器产出，展示可追溯来源；来源不足时不得伪造结论。
- 所有权限判断必须在服务端执行；隐藏入口只是界面表现，不构成安全控制。
- 晋升、生成、发布、停用都必须记录审计事件，并显示动作影响范围。

## R9 非功能约束

- **性能/规模预期**：
  - [设计] 方法 → 契约的转写若使用模型，属后台任务：超过 10 秒转异步并保留进度，
    审批人可离开页面；完成后以通知回执告知。
  - [设计] 库规模量级参照原型「方法/Skill 86」，需支持按来源标记筛选出全部 `晋升生成` 条目。
- **安全/隐私/合规**：
  - **脱敏闸门是硬闸门**：含客户机密的方法未过脱敏不得生成 skill。
  - [D-16] 组织层内脱敏用可逆映射 ＋ 权限门控（支持审计回溯）；
    脱敏稿与原文双向关联，审计时可从脱敏稿追回原文与客户。
  - 生成的 skill 的数据范围为最小必要，且仍受三层权限（MCP 授权 × agent 工具白名单 ×
    任务权限包）约束。
  - 晋升与生成的留痕保留期不短于审计保留期（D-14）。
- **兼容与降级要求**：
  - 响应式 Web；大脑与后台以桌面端为主。
  - 转写用的模型不可用时**明确失败并保留候选的已填内容**，
    **不得静默跳过 skill 生成而只晋升知识**。

## R10 已知约束 / 依赖

- **内部依赖**：
  - **14-brain 晋升队列与知识五态机**（D-24 MVP 三件之一）——**这是本用例的触发源**；
  - **UC-3.1**——生成的 skill 复用其契约模型与双重门禁，并需新增来源取值 `晋升生成`；
  - **UC-3.4**——源知识变更时的改版/停用路径；
  - **04-agent（UC-4.1/4.2）**——「成为某 agent 在同类场景下的默认方法」；
  - `uc-0-3` 角色本体（晋升审批人 / 审核人 / 复核负责人三个职能）；
  - 决策台账（源决策签字是准入前提）。
- **被依赖**：UC-3.2（生成的 skill 可被蓝本绑定）、UC-3.3（可被对话临时挂载）、
  UC-3.6（生成的 skill 同样接受消息级评价与改进）。
- **跨模块契约**：知识条目 ID、Skill ID/版本、源决策 ID、适用范围、有效期、
  复核负责人、审计事件必须使用统一标识；
  **「方法/Skill」必须是同一份资产的两个视图，不得建互不关联的副本**。
- **[排期风险]** **14-brain 在裁决中属 phase-3**（D-24），而本用例挂在 phase-1 的 03-skill。
  **[待确认]** 两种处置二选一：
  ① 本用例随 14-brain 后置到 phase-3；
  ② phase-1 只做**接收端**——Skill 侧的 `晋升生成` 来源取值、双向关联字段、
     「自动生成不等于自动发布」的门禁路径先建好，触发端待 14-brain 就位后接通。
  本文按 ② 书写（估点 5 已按 ② 计），**需人类确认**。
- **[待确认]** 「同类客户谈判场景」这类**场景判定**如何形式化，由谁指定目标 agent。
- **[已裁决 O-21]** 原问题：晋升审批人与 skill 审核人是否可为同一人（此前按不得自审自批处理）。
  **裁决（O-21）**：**知识晋升与 skill 内容同属「① 方法论审核人」这一种职能**
  （与「② 安全评审人」并列，后者管 MCP 放行与 agent 越权申请）。

- **[待确认]** 一条方法知识能否生成多条 skill（如按适用范围拆分）。

- **[设计 · 架构对齐] skill 执行读上下文只能走 Context API**：
  skill 运行时若需读取项目材料、转写、知识或对话历史，

  （`docs/architecture/context-engine.md` 第四节），
  **不得绕过 Context Engine 直查业务库、对象存储或向量库**——
  Context Engine 是**唯一 AI 边界**，权限判定（`permissionDecisionId`）、
  引用锚点（`anchor`）、召回理由（`retrievalReasons`）与遗漏说明（`omissions`）
  只在这条通路上产生。每次调用须留下 `context_packs` 记录以便重放。
- **[设计 · 架构对齐] 编排边界**：**LangGraph 只用于深度研究、人工确认（HITL）、多阶段生成**；
  **摄取流水线用持久任务系统**（PG outbox + worker），**两者不可混用**。

## R12 AI Ready 验收线索

- V1（成功态）：AC1 —— 对一条满足准入的方法类候选点 `[批准并推给全员]`，
  Skill 库出现一条来源标记 `晋升生成` 的 skill，且能从它追回源知识条目与那个被签字的决策。
- V2（门禁态）：AC2 —— 生成的 skill 停在 `待审核`；直接调接口置为 `已启用` 被拒绝并记审计。
- V3（准入态）：对一条**无签字决策**或**复盘未判对**的候选发起晋升被拒绝，
  界面明确指出缺哪一条，且不生成 skill。
- V4（必填态）：三项必填缺任一项时无法进入生效状态，skill 生成一并阻断。
- V5（AI 边界态）：模拟 AI 提名并尝试自动入库，被服务端拒绝并写安全审计。
- V6（类型态）：对非方法类候选（可复用判断 / 客户档案）晋升，**不生成 skill**。
- V7（脱敏态）：含客户机密的方法未过脱敏闸门时不生成 skill；过闸门后生成的 skill
  内容只含脱敏稿，且可经权限门控回溯原文。
- V8（联动态）：AC3 —— 把源知识置为「被推翻」，对应 skill 自动转 `已停用` 且不硬删；
  进行中的项目继续用锁定版本跑完。
- V9（联动态）：把源知识置为「被替代」，skill 发新版、旧版自动归档，已建实例锁在旧版。
- V10（来源标记态）：AC4 —— 尝试把 `晋升生成` 改为 `自建` 被拒绝。
- V11（失败显式态）：模拟 Skill 库不可写，晋升操作明确失败并给出重试入口，
  **不出现「知识已生效但无 skill 也无提示」**。
- V12（权限态）：逐一使用 提名人 / 晋升审批人 / 审核人 / 复核负责人 / 引导师 /
  观察者 / 未授权用户访问，可读数据与可执行动作严格符合 R5。
- V13（审计态）：晋升、生成、发布、停用可按操作者、时间、源决策、skill 版本检索。
