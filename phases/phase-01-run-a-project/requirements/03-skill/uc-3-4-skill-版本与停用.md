# 原始需求（细化）— UC-3.4 Skill 版本与停用

> 所属：阶段一 · 能跑完一场项目 / M3 上传 Skill
> 来源：`Backlog Use Case.html` 的 UC-3.4；UI 线索来自 `WorkspaceX Standalone.html`；
> **运行态原型（版本语义的参照系）**：后台 → AI 能力 → **画布模板**——
> 「**发布新版本时旧版自动归档，但已经建出来的画布不会被改动——它们记着自己用的是哪个版本**。
> **归档只影响『还能不能新建』**。」；画布模板状态取值「已发布 / 草稿 / 已归档」，
> 已归档条目附 `[恢复]`；内置模板标「**内置不可删**」；
> 蓝本设计器「改动生成 v5，**已开过的项目锁在自己的版本上**」。

> 口径（四标记）：**[原型]** ＝ `WorkspaceX Standalone.html` **运行态实际存在**的行为（有界面可查，依据 scratchpad 的 proto-01~10 抽取档案）；**[Backlog]** ＝ `Backlog Use Case.html` 的**文档要求**（原型未必实现）；**[设计]** ＝ 依据前两者反推补全，**需人类确认**；**[待确认]** ＝ 不应由实现者自行决定。
> 元数据：优先级 **P1**；估点 **3**（原 2，因版本语义对齐画布模板 + 引用清单 + 快照绑定上调）；
> 建议迭代 **迭代 5 · 收尾项**。
>
> **[人类已拍板 · D-30]** 产出版本策略承认差异，**统一底线是「引用必须指向不可变快照」**。
> 本用例的版本语义**参照画布模板**，是该底线在 Skill 上的具体落法。

## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-3.4 / Skill 版本与停用
- **Actor**：**能力维护者**（发起改版/停用）、**审核人**（新版仍需过门禁）、**引导师**（受影响方）
- **目标**：[原型] 维护者能更新或下架 skill，且**不打断正在跑的项目**——
  「停用不影响进行中的项目，新项目不再看到它」。
- **[人类已拍板] 版本语义（参照画布模板）**：
  1. **发布新版本时旧版自动归档**；
  2. **已经建出来的实例不会被改动——它们记着自己用的是哪个版本**；
  3. **归档只影响「还能不能新建 / 还能不能新绑定」**，不影响已存在的引用。
- **本用例结果**：Skill 拥有一条清晰的版本链（v1 → v2 → …），每个历史版本可被历史项目
  继续解析；停用/归档后新蓝本与新项目不再可选，进行中的项目不受影响。
- **系统边界**：Skill 版本链、发布新版、旧版归档、引用清单（哪些蓝本/项目还在引用）、
  停用与恢复、硬删禁止、快照绑定。
- **核心数据对象**：Skill、Skill 版本（不可变快照）、版本状态、引用关系
  （蓝本绑定 / 项目绑定快照 / 对话临时挂载）、停用记录、审计事件。

## R2 前置条件 / 触发条件

- **前置条件**：
  - 目标 skill 存在且当前用户持有能力维护者权限。
  - 系统能够枚举该 skill 的**全部引用**：**后台工作流模板 / 蓝本第 13 项绑定**（UC-3.2）、
    **项目实例级编排与绑定快照**（[原型] `设置 → 工作流编排`）、
    进行中对话的临时挂载（UC-3.3）、agent 的 skill 挂载（UC-4.1）。
- **触发条件**：
  - [原型] 维护者更新或下架 skill（后台 → AI 能力 → Skill 库 → `[编辑]`）。
  - [设计] 或由 **UC-3.6 的改进闭环**触发——人工复核通过的改进被合入，生成新版本。
  - [设计] 或由 **UC-3.5 的晋升源知识变更**触发——方法类知识被更新/降级时，
    其自动生成的 skill 需跟随改版或停用。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

### 分支 A · 发布新版本

1. **能力维护者操作**：在 `[编辑]` 里修改契约（提示词模板 / 输入输出 schema / 数据范围声明），
   提交为新版本草稿。
   **系统响应**：**不覆盖**当前生效版本；把改动落为 `vN+1 · 草稿`，当前 `vN` 继续服务。
2. **系统处理**：新版本**照走 UC-3.1 的双重门禁**——安全扫描（自动）＋ 方法论审核（人工）。
   [设计] 改版不豁免门禁；数据范围扩大的改版应在审核时被显著标出。
3. **系统处理**：`vN+1` 发布成功后，**`vN` 自动归档**（参照画布模板语义）。
   归档只影响「还能不能被**新**绑定/**新**挂载」，**不影响任何已存在的引用**。
4. **系统处理**：**已建出来的实例记着自己用的是哪个版本**——
   - 进行中项目的绑定快照仍指向 `vN`，运行时按 `vN` 的契约执行；
   - 蓝本第 13 项的绑定条目**是否自动跟随到 `vN+1`**：[设计] 默认**不自动跟随**，
     在蓝本里显示「有新版本 vN+1 可用 `[升级到 vN+1]`」，由引导师显式升级。
     **[待确认]** 是否允许配置为自动跟随。
5. **系统收口**：校验 AC2「发布新版后，进行中的项目行为不变」；刷新版本链、引用清单与审计。

### 分支 B · 停用 / 归档

> **[已裁决 O-11 · 本分支的状态口径]** 原问题：本文此前把 `已停用` 与 `已归档` 当作**两个并列取值**，
> 而 UC-3.1 又写了 `已发布`，全模块出现三套措辞；原型档案里 skill 只有 `已启用` 与 `待审核` 两个取值。
> **裁决（O-11）**：skill 状态机为**四态 `草稿 → 待审核 → 已启用 → 已停用`**；
> **`已归档` 作为 `已停用` 的终态子类，不单列为状态取值**
> （数据模型上可用 `已停用` ＋ 一个 `archived` 标志或子类型表达，
> 但**状态字段的取值集合恰为四个**）；
> **`已发布` 一词全仓废弃，统一用 `已启用`**（贴原型）。
> 本分支下文的「归档」一律读作「`已停用` 的终态子类」，不构成第五个状态。

6. **能力维护者操作**：对某 skill 点「停用」。
   **系统响应**：[原型] **列出还在引用它的蓝本与项目**——分三类展示：
   - **进行中的项目**（不受影响，将继续用锁定版本跑完）；
   - **蓝本绑定**（停用后新项目套用时该条绑定失效，需处置）；
   - **agent 挂载**（04-agent，停用后相关 agent 的能力清单减少，可能触发「未配工具白名单」类校验）。
7. **能力维护者操作**：确认停用。
   **系统响应**：状态转为 `已停用`；**新蓝本/新项目/新对话不再能选到它**；
   进行中的项目与对话继续按锁定版本运行至结束。
8. **系统处理**：[原型] **有项目正在跑时不允许硬删，只能停用**。
   [设计] 进一步收紧：**只要存在任何历史引用（含已交付项目的产出溯源），就永久不允许硬删**——
   否则历史结论将失去可追溯的方法来源（对照 D-30「引用必须指向不可变快照」）。
9. **能力维护者操作**（可选）：对 `已停用`（含其归档子类）的 skill 点 `[恢复]`
   （参照画布模板的 `[恢复]`）。
   **系统响应**：恢复到 `已启用`，重新进入可绑定池；恢复动作记审计。
10. **系统收口**：校验 AC1「停用不影响进行中的项目，新项目不再看到它」；
    记录操作者、时间、对象、影响范围与结果进审计。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[设计] 引用清单为空时展示真实空态（大意：当前没有蓝本或项目引用它）与下一步入口，
    **不生成示例数据冒充真实结果**。
    ⚠ 括号内为**待定的设计文案，不是原型原文**——原型每屏都填满样例数据、**零空态**，
    此前给它加引号冒充原型原文是错的，已去掉引号。
  - A2：[设计] 停用前提供**影响预览**：列出受影响的蓝本条数、进行中项目数、agent 数，
    并对每类给出处置建议；预览不产生任何写操作。
  - A3：[设计] 提供「**停用并推荐替代**」——指定一个替代 skill，
    蓝本里的失效绑定可一键改指到它（改指仍需引导师确认，不自动执行）。
  - A4：[设计] 平台内置（来源标记 `CC`）的 skill 参照画布模板的「**内置不可删**」：
    可停用/可隐藏，**不可删除**。
- **异常流程**：
  - E1：[原型] **有项目正在跑时不允许硬删，只能停用**；硬删请求被服务端拒绝并给出正在跑的项目清单。
  - E2：[设计] 新版本未过门禁却尝试直接生效——被拒绝，`vN` 保持生效（对照 UC-3.1 AC2）。
  - E3：[设计] 历史版本 `vN` 的运行依赖（模型、MCP）已不可用时，
    进行中的项目**明确失败并提示**，**不静默回退到别的版本或别的模型**
    （对照 UC-20.3「无合格替代模型 → 明确失败」）。
  - E4：[设计] 请求超时、网络中断或依赖不可用时，保留用户当前输入与最后成功数据，
    明确失败原因并提供安全重试。
  - E5：[设计] 同一 skill 被并发改版/停用时不得静默覆盖；提示版本已变化，允许刷新、对比或重提。
  - E6：[设计] 权限在操作过程中被撤回时立即终止后续写操作；已完成步骤按审计规则保留。

## R5 权限与可见性

- **能力维护者**：可发起改版与停用/恢复，范围限定在其有权访问的组织；
  **不能自行批准新版本发布**（门禁由审核人把关，见 UC-3.1 R5）。
- **审核人**：对新版本行使方法论审核 `[批准发布]` / `[退回]`；
  [设计] **停用是否也需要审核人签字**：**[待确认]**——停用会影响进行中的方法一致性。
- **引导师**：可见「有新版本可用」提示与「引用了已停用 skill」告警；
  决定是否把蓝本绑定升级到新版；**不能改版、不能停用**。
- **组长 / 组员**：不可见版本管理面；只在运行时感知能力变化。
- **观察者**：不可见。
- **项目负责人**：可查看本组织 skill 的版本与停用记录、影响范围摘要；写操作需显式授权。
- **可见性范围**：版本与停用面的可见性继承 skill 自身的可见性范围（全组织可用 / 仅某团队）。
- 未登录、链接失效或未列出的角色：默认无权限；接口不得返回越权数据。

## R6 后置条件 / 不包含

- **正常后置条件**：
  - Skill 拥有完整版本链，每个版本是**不可变快照**，历史引用永远可解析。
  - [Backlog验收] AC1：**停用不影响进行中的项目，新项目不再看到它**
    （[原型] 同构证据在**画布模板**侧：「归档只影响『还能不能新建』」；
    skill 侧无停用/归档的界面呈现，属原型确认缺失）。
  - [设计验收] AC2（版本语义 · 参照画布模板）：**发布新版后旧版自动归档，
    但已经建出来的实例不会被改动——它们记着自己用的是哪个版本；
    归档只影响「还能不能新建/新绑定」**。
  - [设计验收] AC3：只要存在任何引用（含历史项目），**硬删被永久拒绝**。
  - [设计验收] AC4：停用操作前必须能列出完整引用清单（蓝本 / 项目 / agent 三类），
    清单为空亦需显式呈现空态。
- **失败后置条件**：
  - 不产生「以为停用了其实还在被新项目选到」或「以为改版了其实旧项目也变了」的状态；
    失败事件进可观测日志。
- **不包含**：
  - **[D-06] 任意代码无沙箱执行**、组员自行扩大数据权限。
  - Skill 的创建与首次发布——见 UC-3.1（新版本仍复用其双重门禁）。
  - 蓝本绑定的配置动作本身——见 UC-3.2。
  - **改进建议如何产生**（消息级 👎 → 聚合 → 改进 PR）——见 **UC-3.6**；
    本用例只承接「复核通过后合入生成新版本」这一步。
  - 组织级审计检索屏（D-34）。

## R7 业务规则（不随具体实现变化的硬性约束）

- **[已裁决 O-11] skill 状态机 ＝ 四态 `草稿 → 待审核 → 已启用 → 已停用`**；
  **`已归档` 是 `已停用` 的终态子类，不单列**；**`已发布` 一词全仓废弃，统一用 `已启用`**。
  状态字段的取值集合断言恰为 `{草稿, 待审核, 已启用, 已停用}`（**四个，不多不少**），
  与 UC-3.1 R7 的枚举断言**必须逐字一致**。
- [原型] **有项目正在跑时不允许硬删，只能停用**。
- **[人类已拍板 · 参照画布模板]** 发布新版本时**旧版自动归档**；
  **已建出来的实例记着自己用的是哪个版本**；**归档只影响「还能不能新建/新绑定」**。
- **[D-30 硬底线]** 引用必须指向**不可变快照**——Skill 版本一经发布即不可修改，
  只能发新版；历史项目的溯源永远能解析到当时的契约原文。
- [设计] **新版本不豁免门禁**：安全扫描 ＋ 方法论审核照走（UC-3.1 R7）。
- [设计] 停用必须先列出引用清单；**无清单不得停用**。
- [设计] 平台内置（`CC`）skill **不可删除**，只能停用/隐藏（参照画布模板「内置不可删」）。
- [设计] 历史版本的依赖不可用时**明确失败**，不静默回退。
- AC1：停用不影响进行中的项目，新项目不再看到它。
- AI/Agent 生成的候选内容必须标识为机器产出，展示可追溯来源。
- 所有权限判断必须在服务端执行；隐藏入口只是界面表现，不构成安全控制。
- 改版、发布、归档、停用、恢复、硬删尝试都必须记录审计事件，并显示动作影响范围。

## R8 界面线索

- **前端入口**：[原型] 后台 → AI 能力 → **Skill 库与市场** → 行内 `[编辑]`；
  参照画布模板行内的 `[编辑][归档]` 与已归档行的 `[恢复]`。
- **信息架构**：版本与停用是 skill 详情页的一个区块，与契约、门禁结论、
  元数据（调用次数 / 满意度 / 来源标记 / 可见性范围）同屏。
- **推荐交互**：
  - [设计] **版本链**竖向时间线：每版显示版本号、发布时间、发布人、门禁结论、当前状态
    （生效 / 已归档）、被多少引用锁定。
  - [设计] **停用确认对话框**必须明确对象、影响范围与后果，并把引用清单直接嵌进对话框
    （不是跳转），三类分栏：进行中项目 / 蓝本绑定 / agent 挂载。
  - [设计] 蓝本侧的「有新版本 vN+1 可用 `[升级到 vN+1]`」是**提示不阻断**。
  - [设计] 危险动作（停用/归档）与常规动作（编辑/试跑）在视觉上分离。
- **必须呈现的状态**：默认态、加载态、空态（无引用）、校验失败态、
  依赖失败态（历史版本依赖不可用）、无权限态、成功态；
  另加 **`已停用`（含其归档子类的呈现变体）** 一态及其 `[恢复]` 出口
  （**[已裁决 O-11]** 归档不是独立状态，原写「`已归档` 与 `已停用` 两态」已收敛为一态）。
  （七种必现状态按 D-36 统一规范实现。）
- **原型参考**：
  - `phases/requirements/WorkspaceX Standalone.html` — 后台 → AI 能力 → Skill 库与市场
  - 同上 — 后台 → AI 能力 → **画布模板**（版本语义的参照系：旧版自动归档 / 已建实例记版本 /
    归档只影响能否新建 / 内置不可删 / `[恢复]`）
- **UI sign-off**：
  - Skill 库列表与画布模板的版本语义文案**已存在，可直接签**。
  - **真·未探明**（按钮在行内，本轮未点开，补抽取即可）：
    `[编辑]` 打开后的版本区块——版本链布局、引用清单三栏、影响预览。
  - **原型确认缺失**（Skill 库列表行已逐字段渲染，本该有却没有，**需补画原型**）：
    - **skill 的停用/归档入口与确认对话框**——行内操作只有 `[编辑]`，
      无 `[归档]` / `[停用]` / `[恢复]`；这些出口只存在于**画布模板**行（`[编辑][归档]` / `[恢复]`），
      属**不同对象**，不可跨屏挪用；
    - **skill 的 `已停用` 状态取值与呈现**——原型 skill 只有 `已启用` 与 `待审核` 两态；
      **[已裁决 O-11]** 补齐的是 `草稿` 与 `已停用` 两态（`已归档` 不单列），
      这两态的界面呈现需补画原型。

## R9 非功能约束

- **性能/规模预期**：
  - [设计] 引用清单枚举需覆盖全组织蓝本与全部未归档项目，应在 3 秒内返回或转异步并给出进度。
  - [设计] 版本链需分页；历史版本的契约原文按需加载。
- **安全/隐私/合规**：
  - 版本快照与引用关系的保留期**不短于审计保留期**
    （D-14 五参数之一；**[已裁决 O-01]** 审计保留期默认 **1095 天（3 年）**，
    且**快照与绑定关系属不可删对象，不受留存期约束**，单独走 O-39 的法定留存清单）；
    历史项目在保留期内必须能解析其当时使用的 skill 契约。
  - 停用不等于删除；删除请求一律走合规删除流程（17-gov / UC-17.2），不在本用例范围。
- **兼容与降级要求**：
  - 响应式 Web；后台以桌面端为主，移动端保证查看版本与引用清单。
  - 历史版本依赖不可用时**明确失败**，不得静默降级或回退版本。

## R10 已知约束 / 依赖

- **内部依赖**：UC-3.1（门禁复用）、UC-3.2（蓝本绑定与项目快照是引用来源）、
  UC-3.3（对话临时挂载亦是引用）、UC-4.1（agent 的 skill 挂载）、
  20-model / 21-mcp（历史版本的运行依赖）、`uc-0-1`（工作版本可变、固定快照不可变）。
- **被依赖**：**UC-3.6**（改进复核通过后合入 → 触发本用例的发新版）；
  UC-3.5（晋升源知识变更 → 跟随改版/停用）；13-deliv 的产出溯源。
- **跨模块契约**：Skill ID、版本号、版本快照哈希、引用关系、审计事件必须使用统一标识；
  **任何模块记录「用了哪个 skill」都必须记到版本粒度，不能只记 skill ID**。
- **[待确认]** 蓝本绑定是否允许配置为**自动跟随新版本**（默认不跟随）。
- **[待确认]** **停用是否需要审核人签字**——停用会影响方法一致性，可能不宜由维护者单方决定。
- **[待确认]** 版本号语义（是否区分「兼容改动」与「破坏 schema 的改动」，
  后者是否强制不允许自动跟随）。
- **[已裁决 O-01]** 原问题：版本快照与引用关系的具体保留期（D-14 的五个留存参数尚待合规负责人给出）。
  **裁决（O-01）**：五参数取值 ＝ **材料 180 天 / 留痕 180 天 / 删除宽限 30 天 /
  知识有效期按资产类型 6·12·24 个月 / 审计保留期 1095 天（3 年）**；允许区间由合规负责人收窄。
  且 **快照、绑定关系、审计留痕属不可删对象，不受留存期约束**，
  单独走 O-39 的法定留存清单——因此**skill 版本快照与引用关系永久可解析**，
  不随材料保留期到期而失效。

- **[设计 · 架构对齐] skill 执行读上下文只能走 Context API**：
  skill 运行时若需读取项目材料、转写、知识或对话历史，
  **只能向 Context Engine 的 Context API 请求一个 Context Pack**
  （`docs/architecture/context-engine.md` 第四节），
  **不得绕过 Context Engine 直查业务库、对象存储或向量库**——
  Context Engine 是**唯一 AI 边界**，权限判定（`permissionDecisionId`）、
  引用锚点（`anchor`）、召回理由（`retrievalReasons`）与遗漏说明（`omissions`）
  只在这条通路上产生。每次调用须留下 `context_packs` 记录以便重放。
- **[设计 · 架构对齐] 编排边界**：**LangGraph 只用于深度研究、人工确认（HITL）、多阶段生成**；
  **摄取流水线用持久任务系统**（PG outbox + worker），**两者不可混用**。

## R11 切分提示（给 requirement-author）

- 建议拆分顺序：
  1. Skill 版本快照模型（不可变 + 版本链）
  2. 发布新版 → 旧版自动归档 + 已有引用锁定版本
  3. 引用枚举服务（蓝本 / 项目 / agent 三类）
  4. 停用 / 恢复 + 硬删拒绝
  5. 蓝本侧「有新版本可用」提示与显式升级
  6. 历史版本依赖失败的明确失败路径
  7. 审计 + 自动化验收
- 「已建实例记着自己用的是哪个版本」应单独成 feature 并有**改版后旧项目行为不变**的验收。
- **优先级 / 先后依赖**：P1；3 点；迭代 5；依赖 UC-3.1、UC-3.2。

## R12 AI Ready 验收线索

- V1（成功态）：AC1 —— 停用一个正被进行中项目使用的 skill：该项目行为不变直至结束；
  新建项目/新建蓝本绑定时它不出现在可选池。
- V2（版本态）：AC2 —— 项目 A 锁定 `v2` 后发布 `v3`：`v2` 自动归档，
  项目 A 运行时解析的仍是 `v2` 的契约原文；新项目只能选到 `v3`。
- V3（硬删态）：AC3 —— 对存在任何引用的 skill 发起硬删，服务端拒绝并返回引用清单。
- V4（引用清单态）：AC4 —— 停用前的引用清单包含蓝本 / 进行中项目 / agent 三类，
  且清单为空时呈现真实空态。
- V5（门禁态）：新版本未过方法论审核时不生效，`vN` 保持生效；直接置为生效的接口调用被拒绝。
- V6（依赖失败态）：把 `v2` 依赖的模型在 20-model 停用，进行中的项目明确失败并提示，
  **不静默回退到 `v3` 或换模型**。
- V7（内置态）：对来源标记为 `CC` 的内置 skill 发起删除被拒绝，停用允许。
- V8（恢复态）：已停用的 skill 恢复后重新进入可绑定池，且历史引用不受恢复影响。
- V9（权限态）：逐一使用 能力维护者 / 审核人 / 引导师 / 组员 / 观察者 / 未授权用户访问，
  可读数据与可执行动作严格符合 R5。
- V10（并发态）：两名维护者同时改版/停用同一 skill 不静默覆盖，可识别最终状态。
- V11（审计态）：改版、归档、停用、恢复、硬删尝试可按操作者、时间、对象、影响范围检索。
