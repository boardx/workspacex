# 原始需求（细化）— UC-7.5 画布模板编辑操作（updateTemplate）

> 所属：阶段一 · 能跑完一场项目 / M7 可视化模板
> 来源：人类 2026-08-15 看真实后台截图（`/admin/canvasadmin`，boardx 组织）后原话指出：
> 每张模板卡片上都标着「编辑入口待补（契约无更新操作，分区只能在新建时定）」——这是产品
> 自己在 `apps/web/components/canvas/template-admin.tsx:498` 标注的已知缺口，本次由人类
> 直接确认要补。

> 口径（四标记）：本 UC 无 `[原型]`（这是既有 `create-template.ts`/`publish-template.ts` 之后
> 缺失的第三个写操作，proto 档案里没有先例）。行为为 **[Backlog]**（人类直接指认缺口）+
> **[待设计]**（契约面全新，尚无签核参数）。**本文件不能直接开工**：`createTemplate` 契约面
> 本身已经签核（`contracts/canvas/design-signoff.md` 的 `scope_note: "本次签核范围含
> createTemplate"`，2026-07-31），但 `packages/contracts/src/canvas.ts:261` 的注释明确写着
> 「在补签之前，不得把它当作已签核事实去继续扩展（例如据此再造 updateTemplate）」——
> `updateTemplate` 是全新操作，即便 create 已签，也需要单独走一遍契约设计 + 束级签核，
> 不能因为"隔壁操作签过"就顺带默认这个也签了。

## 现状（先讲清楚，避免和已有能力重复）

- `POST /canvas/templates`（create，`create-template.ts`）——造一行 `draft`，`sections` 只能
  在这一步定，之后没有任何路径能改。
- `POST /canvas/templates/:key/publish`（publish，`publish-template.ts`）——draft→published
  的状态转移，不改内容。
- `archive`/`restore` 同理，都是**状态转移**，不是**内容编辑**。
- **完全没有**"改一个已存在模板的 `displayName`/`sections`/`visibility`"这条路径——
  这正是 UI 卡片上"编辑入口待补"提示的字面意思，`template-admin.tsx:498` 那句提示文案
  就是这个缺口在界面上的诚实呈现，不是 bug，是"故意还没做、如实告知"。

## R1 概览

- **Use Case ID / 名称**：UC-7.5 / 画布模板编辑操作
- **Actor**：组织 `admin`（与 create/publish/archive/restore 同一个门槛，`canMutateCapabilities`
  只放行 `orgRole === "admin"`）。
- **目标**：管理员在后台画布模板库里，能修改一个**已存在**模板的可编辑字段（至少
  `displayName`/`sections`/`visibility`），不需要靠"归档旧的、新建一个新 key"这种绕路方式。
- **本用例结果**：一次编辑操作 = 对既有模板行的一次**受控更新**（是否走版本递增、是否只能
  编辑 `draft` 状态还是任意状态都能编辑，是本 UC 待设计部分，见 R4）。
- **系统边界**：`apps/api/src/application/canvas/` 新增一个 `update-template.ts` 用例（或复用
  `publish-template.ts` 同款 `requireTemplateAdmin` 前置判定）；`template-ports.ts` 新增
  `update()` 端口方法；`canvas.ts` 契约新增 `updateTemplate` 操作定义；前端
  `template-admin.tsx` 补上真实的"编辑"按钮与表单（替换掉现在的提示文案）。

## R2 前置条件 / 触发条件

- **前置条件**：调用者是目标组织的 `admin`；目标 `key` 在该组织存在（不存在时的错误码
  参照 `publishTemplate.err` 里 `TEMPLATE_NOT_FOUND` 的既有先例，不新造语义相同的第二个码）。
- **触发条件**：管理员在模板库列表点击某条模板的"编辑"入口。

## R3 主流程（草案，供 requirement-author 细化，不是最终判据）

1. 管理员点击某条模板的"编辑"。
2. 系统展示当前 `displayName`/`sections`/`visibility` 可编辑表单（复用 create 表单的字段
   与校验逻辑，不新造第二套 `SectionDef` 校验）。
3. 管理员修改后提交，系统更新该行并返回更新后的模板。

## R4 待设计（本文件明确不预先裁定，留给契约签核）

1. **版本语义**：编辑是否触发 `version` 递增（像 publish 那样产生新版本行、归档旧版本），
   还是原地改写当前行？两种语义对"已被绑定到某个环节的模板被编辑后，正在使用它的绑定
   要不要感知变化"这件事的答案完全不同，**不能由实现者自行选**。
2. **状态范围**：只允许编辑 `draft` 状态（编辑完还要重新走一遍 publish），还是
   `published`/`archived` 状态也能编辑？如果 `published` 状态可编辑，需要重新过一遍
   `publish-template.ts` 里"发布新版本时旧版自动归档"（I-4 前半）那条不变量是否适用。
3. **`sections` 编辑的破坏性**：如果一个模板已经被某个议程环节绑定，编辑 `sections`
   （加/删分区）是否会影响已经基于旧分区结构生成的画布产物？这条不变量目前不存在，
   需要人类或契约设计阶段裁定是否需要一个"编辑不影响既有绑定/画布"的保证。
4. **`key` 是否可编辑**：`key` 是模板的稳定标识（内置模板与自定义模板共用同一份 key 语义），
   本 UC 默认 `key` 不可编辑（分区/展示名可改，标识不可改），但需人类在签核时明确写死这条
   边界，不留活口。
