## Q-1 六种资产是否都走三步向导（**集合部分已由人类截图确认，此问已缩小**）

> ✅ **2026-07-30 已确认「是哪六种」**：人类提供的后台左栏截图逐字六项
> `Agent 管理 14 / Skill 库与市场 86 / 模型 18 / MCP 服务器 6 / 画布模板 22 / 项目蓝本 7`，
> 与原型 `AN_META`（`[原型 @16.6511M]`）与 `AD_META`（`[原型 @16.6703M]`）**三份证据完全一致**，
> 连计数都逐个对得上。**这部分不再是待裁项。**
> 下面剩余的问题**只剩「流程是否也一样」**。

- [ ] **Q-1** 六个键里**只有五个有第 2 步的实现**（`anIsImport/anIsAgent/anIsMcp/anIsModel/anIsCv`），
      `blueprint` 在 `anOpenFn` 里被改道去了另一个编辑器（`bpOpen`），**不走三步向导**。

      **为什么不能自己定**：「六种资产完全一样」是本模块最核心的横切断言。
      如果实际只有五种走这条流程，那句话就是错的，不变量要按五写；
      如果六种都走，蓝本的第 2 步是原型缺屏、需要补设计。

      **候选**：A) 六种都走三步向导，蓝本第 2 步待补设计；
      B) 五种走向导，蓝本只共用第 3 步「治理与发布」；
      C) 六种共用第 3 步，第 1、2 步各类型可差异化。

      **推荐：C。** 理由：原型那句「六种资产完全一样」出现的位置在**第 3 步**页面上，
      它断言的就是第 3 步；第 1、2 步在原型里本来就每类不同（导入 Skill vs 组装 Agent
      vs 接入模型 vs 接入 MCP vs 搭画布）。C 是对原型的最小忠实读法。
      **风险**：若采 C，则「六道关」只属 skills（`AN_META.skills` 的副标题就是
      「外来资产要过落地检查六道关」），其余五类第 2 步各有自己的门——
      不变量必须按「第 3 步六类一致」写，**不能**写成「六道关六类一致」。

      裁决：____________  署名：__________  时间：__________

- [ ] **Q-1b（新增 2026-07-30）** 六种资产是否真的**共用同一套治理字段**
      （可见范围 / 谁能改 / 负责人 / 复核周期）？

      **核实结果——原型只对 Agent 画了第 3 步的完整实例**：
      第 3 步页面 `[原型 @16.611–16.616M]` 的「发布前检查」四条里，第一条逐字是
      「**四栏配置完整（人格 · 能力 · 模型 · 边界）**」——这是 **Agent 专属**的检查项。
      也就是说第 3 步**并非**六类逐字相同：三项治理配置（可见范围 / 谁能改 / 责任与复核）
      是共用的，但「发布前检查」的**清单内容按资产类型变化**。

      **已建成代码侧的证据更弱**：`apps/web/lib/mock/admin.ts` 只对
      **agent / skill / 画布模板** 三类登记了 `VisibilityScope`（第 74 行注释逐字如此）；
      MCP 走的是**另一套** `McpAuthScope = lead | team | all`（第 84 行），
      **模型与项目蓝本两类连可见性字段都没有**。
      ⇒ 「六种完全一样」目前**只有原型第 3 步那一句话作为依据，代码侧是 3 / 6**。

      **为什么不能自己定**：如果 MCP 的 `McpAuthScope`（三值）与其余资产的
      `VisibilityScope` 是两套东西，那「六种资产完全一样」是假的，
      本束的核心不变量要按「五种 + MCP 例外」写；如果它们该统一，

      **候选**：A) 六类统一到一套 `可见范围 / 可改集合 / 负责人 / 复核周期`，
      MCP 的 `McpAuthScope` 收敛进去；
      B) 三项治理配置六类统一，**发布前检查按类型可变**（原型实际形状）；
      C) 承认 MCP 是例外，不变量写「五种一致 + MCP 单列」。

      **推荐：B。** 理由：它是对原型的最小忠实读法——原型那句话印在
      「可见范围 / 谁能改 / 责任与复核」三块的正上方，而「发布前检查」在页面更下方、
      内容显然是 Agent 专属的。B 把不变量精确到「**这三项**六类一致」，
      而不是含糊的「这一步六类一致」。
      **风险**：B 仍要求 MCP 的 `McpAuthScope` 与 `VisibilityScope` 二选一收敛，
      而那是 `agent-runtime` 已签核的字段——采纳 B 需连带一条子裁决，
      且可能触发 `agent-runtime` 束重签。

## Q-3 「灰度发布」的语义

- [ ] **Q-3** 原型两处证据互相**不完全一致**：
      - 第 3 步页面底部：`发布方式` → 说明「灰度到能源组 5 人试用一周，无异常再全量——
        比一次性铺开更容易回滚」，两个按钮 `直接发布` / `灰度发布 · 5 人` `[原型 @16.616M]`。
      - 向导主按钮的 label 逻辑：`anNextLabel: s.anStep === 3 ? "灰度发布" : "下一步"`
        `[原型 @16.867M]`——即**第 3 步的主 CTA 就叫「灰度发布」**，`直接发布` 是次要出口。

      而 `contracts/skills/domain.md`（**已签核**）「四、这个域不负责什么」最后一条写：
      「软件反馈通道、**灰度发布**：phase-1 只做分流与跳转；**灰度列 phase-2**」。

      **为什么不能自己定**：灰度发布若是真的（一个资产同时对 5 人是新版、对其余人是旧版），
      它需要**按人分流的版本解析**，那是 `SkillBinding.versionId` 之外的一整套东西；
      若只是「发布但可见范围先设为 5 人」，那它压根不是灰度，只是可见范围的一个预设值。

      **候选**：A) 真灰度（按人分流的版本解析）；
      B) 伪灰度（＝ 可见范围先设小，无版本分流，一周后手动扩大）；
      C) 更伪（只是个待办提醒，一周后提示你去改可见范围）。

      **推荐：B。** 理由：原型的说明文字「灰度到能源组 5 人试用一周，无异常再全量」
      描述的**全部动作**都能由「可见范围 = 指定的 5 人」表达，没有一个字要求
      「同一时刻不同人看到不同版本」。B 也不与已签核的「灰度列 phase-2」冲突得那么硬
      （B 不引入新机制）。
      **风险**：B 下「无异常再全量」的「无异常」谁判、怎么判、一周后不管会怎样，
      三件都没有依据——若采 B，需追加裁决，否则会长出一个静默滞留的状态。

## Q-4 六道关第 06 关的显示自相矛盾

- [ ] **Q-4** 原型第 06 关 `[原型 @16.560M]` 的图标是 `✓`、状态标签是 **`通过`**，
      但正文写「**待第 3、4 关处理完后开放**」。同一屏顶部又写「`4 / 6` 已通过 · 1 项待处理」
      ——`4/6` 与「06 通过」相加得 5，对不上。

      **为什么不能自己定**：这决定第 06 关到底是不是一道**关**。
      如果它只是「前面处理完才开放的表单」，那六道关实际是「五道检查 + 一个发布表单」，
      「六道关全过才能发布」这条不变量要改写。

      **候选**：A) 原型是笔误，06 应为「未开始/锁定」态，六关都是关；
      B) 06 本来就不是检查而是第 3 步治理表单的前置摘要，六道关实为五道；
      C) 06 是关，但它的通过条件就是「第 3 步三项填完」，与第 3 步是同一件事的两个视图。

      **推荐：A + C**：显示按 A 修（锁定态），语义按 C（06 关的通过条件 ＝ 第 3 步三项齐全）。

      **风险**：若采 A+C，`06 发布范围与负责人` 与第 3 步必须共用同一份状态，

## Q-7 复核周期规则的**单一事实源**落在哪个束

      过期洞察不参与定题强度计算` `[原型 @15.270M]`；后台指标 `过期滞留 >30 天` `[原型 @16.226M]`）。

      第九次事故就在这里。
