# 原始需求（细化）— UC-23.7 社区源的连接与同步

> 所属：M23。口径见 `00-index.md`。优先级 **P1**；估点 **[待确认]**。
>
> ⚠ **Q-0**：外部社区导入被 D-06 推到 phase-2，本 UC 是它的基础设施。
> ⚠ **Q-2**：人类口头提到的 `open claw` 在原型与截图里**全部 0 命中**，本 UC **不发明它**。

## R1 概览

- **Use Case ID / 名称**：UC-23.7 / 社区源的连接与同步
- **Actor**：**平台组管理员**（维护源）；能力维护者是**消费方**（`uc-23-1`）
- **目标**：让组织能连上外部的资产生态，并且**连上不等于装上**——
  原型对这件事的核心约束逐字为「**同步只拉取清单，不自动安装任何东西**」`[原型 @16.555M]`。
- **系统边界**：社区源注册表、同步任务、凭据、源级健康状态。

## R2 前置条件 / 触发条件

**前置条件**
- 用户是平台组管理员（`[待确认]` 是否需要安全评审人联签，见 Q-2 推荐方案 C 的附带风险）。
- 网络可达（本 UC 是**唯一**必须出网的部分）。

**触发条件**
- 在 `uc-23-1` 第 1 步的「社区源 · 已连接 4 个」区点 `[＋ 添加源]` 或某行的 `[修复]`。
- 或系统按周期自动同步。

## R3 主流程

1. 系统展示源目录表，表头逐字 `来源 | 类型 | 可用 | 上次同步` `[原型 @16.555M]`，
   区标题「**社区源 · 已连接 4 个**」，副标题「**同步只拉取清单，不自动安装任何东西**」，
   右侧 `[＋ 添加源]`。
2. **原型实存的四个源**（这是市场源清单的**权威**，`[原型 @16.555–16.556M]`）：

   | 来源 | 类型 | 可用 | 上次同步 | 行内出口 |
   |---|---|---:|---|---|
   | **Claude Code 社区** | Skill · Agent | 1,842 | 2 小时前 | `[浏览]` |
   | **MCP Registry** | MCP 服务器 | 312 | 昨天 | `[浏览]` |
   | **咨询方法库 · 官方精选** | Skill · 蓝本 · 画布 | 96 | 3 天前 | `[浏览]` |
   | **Codex 社区** | Skill | 903 | **失败 · 凭据过期** | **`[修复]`** |

   ⚠ **`open claw` 不在其中**（三种写法全文 0 命中）。第五个及以后的源 → `[待确认]`（Q-2）。
   ⚠ 四个源的 `类型` 列各不相同 ⇒ **一个源只提供它声明的资产类型**，
     这是 `uc-23-1` 类型自动识别的一个约束条件（从 MCP Registry 拉来的不该被识别成 skill）。
3. 用户点 `[＋ 添加源]` → 填源信息（名称 / 地址 / 类型 / 凭据）。
   ⚠ **表单字段原型 0 命中**（按钮无 handler，Q-5）→ 全部 `[设计]`。
4. 系统连接并同步 → **只拉清单**：更新该源的 `可用` 计数与 `上次同步` 时间，
   **不在资产库里创建任何条目**。
5. 同步失败 → 该行显示失败原因（原型实例 `失败 · 凭据过期`）+ `[修复]` 出口。

### 两处计数口径不同，注意不要混

| 位置 | 措辞 | 含义 |
|---|---|---|
| 源目录表（本 UC）`[原型 @16.555M]` | `可用 1,842` | 该源**上游总共有多少个** |
| 「新建 Skill」页的市场三源 `[原型 @15.691M]` | `1,842 个 · **已同步 34**` | 上游总数 + **本组织已拉进清单的数量** |

⇒ **两个数是两件事**，且第二处的「已同步 34」**仍然不等于「库里有 34 个 skill」**（R7 规则 1）。
⚠ 咨询方法库在两处的数字不一致：源目录表写 `可用 96`，市场三源写 `官方精选 · 已同步 28`
——`96` 与 `28` 是上游总数与已同步数，**不矛盾**，但两处并列展示极易被误读 → `[设计]` 建议统一口径。

### 两处源清单的条目也不一致

| 「新建 Skill」页市场三源 `[原型 @15.691M]` | 源目录表四源 `[原型 @16.555M]` |
|---|---|
| Claude Code 社区 1,842 · 已同步 34 | Claude Code 社区 1,842 |
| Codex 社区 903 · 已同步 12 | Codex 社区 903（**失败**） |
| 咨询方法库 官方精选 · 已同步 28 | 咨询方法库 · 官方精选 96 |
| —（**无 MCP Registry**） | **MCP Registry 312** |

⇒ 差异是**可解释的**：市场三源在「新建 **Skill**」页，只列提供 Skill 的源；
MCP Registry 只提供 MCP 服务器，所以不出现。**这是一致的，不是 bug** —— 但要写成规则
（R7 规则 3），否则后来的人会「修」掉它。
⚠ 但 Codex 社区在市场三源里显示正常（`已同步 12`）、在源目录表里显示 `失败 · 凭据过期`
——**这两处状态不一致**，其中一处必然是过时的渲染 → `[待确认]`。

## R4 备选流程与异常流程

**备选流程**
- **A1 `[修复]` 凭据过期**：重新走认证。⚠ 认证方式原型 0 命中；
  MCP 侧的措辞是「OAuth · 凭据存密钥库，不入日志」`[原型 @16.584M]`，本 UC 类推 → `[设计]`。
- **A2 `[浏览]`**：⚠ **无 handler，市场目录屏不存在**（Q-5）。这是人类需求
  「导入市场上主流使用的 agents 和 skills」最直接的那一屏，而它没被设计。
- **A3 停用/删除一个源**：原型 0 命中 → `[待确认]`。已从该源导入的资产怎么办（保留？标记孤儿？）
  ——这条不问清楚会留下无法追溯来源的资产。

**异常流程**
- **E1 凭据过期**（原型实存）→ 该源在 `uc-23-1` 里**不可选**，行内给 `[修复]`。
- **E2 源不可达 / 上游 404 / 超时** → 与 E1 不同：凭据问题能修，源没了不能。
  区分显示 → `[设计]`。
- **E3 上游清单结构变了**（解析失败）→ 保留上次成功的清单，**不清空**；显式报解析失败。`[设计]`。
- **E4 同步返回的清单里某条目类型不在该源声明的类型里** → 拒收该条目并留痕
  （否则 MCP Registry 能塞进来一个 skill，绕过 `uc-23-1` 的类型约束）。`[设计]`。
- **E5 上游条目下架，而组织已导入它** → 已导入的资产**不受影响**
  （它已经是组织自己的东西了），但应能看到「上游已下架」→ `[设计]`。
  ⚠ 与 `uc-23-2` E8 相关（六关跑到一半来源被撤）。
- **E6 权限不足** → 非平台组管理员看不到 `[＋ 添加源]` 与 `[修复]`，但**能看到源目录表**
  （因为 `uc-23-1` 要用它选源）。⇒ **读写权限分离**，`[设计]`。

## R5 权限与可见性

- **平台组管理员**：增删改源、修复凭据、手动触发同步。
- **能力维护者**：**只读**源目录表（选源用）；不能改源。
- **安全评审人**：`[待确认]` 添加一个新的外部源是否需要他放行。
  ⚠ 强烈建议需要——添加源等于给组织开一个新的外部内容入口，
  这比放行单个 MCP 服务器（那件事已经要安全评审，`agent-runtime` F53）影响面更大。
- **其它角色**：看不到本屏（后台内）。
- **凭据**：任何角色都**不可读取**凭据明文（类推 MCP 的「凭据存密钥库，不入日志」）。

## R6 后置条件 / 不包含

**后置条件**
- 源注册表中新增/更新一条源：`{名称, 地址, 提供的资产类型集合, 凭据引用, 上次同步时间, 上次同步结果, 可用计数}`。
- 同步后：清单被更新，**资产库条目数不变**。

**不包含**
- **导入某个具体资产**（`uc-23-1`）。
- **市场目录的浏览/搜索**（不存在，Q-5）。
- **MCP 服务器的接入**（`agent-runtime` F52–F54）——注意区分：
  **MCP Registry 是一个「源」**（本 UC），**某台 MCP 服务器是一个「资产」**（那束）。
  ⚠ 这两件事都叫 MCP，是本模块最容易混的一处。
- **许可证/法务合规**（`uc-23-1` R6 已登记为不做 + `[待确认]`）。

## R7 业务规则

1. **同步只拉取清单，不自动安装任何东西**（原型原文）——本 UC 的核心不变量。
2. **凭据不入日志、不可读明文**（类推 MCP，`[设计]`）。
3. **一个源只提供它声明的资产类型**（由四个源各不相同的 `类型` 列证明）；
   越界条目在同步时被拒（E4）。
4. **按资产类型过滤源清单**：在「新建 Skill」页只列提供 Skill 的源
   ——两处清单不同是**规则**，不是不一致（见 R3 的对照表）。
5. **上游变化不回溯已导入资产**（E5）——导入是一次「把外来的东西放进我们的体系」
   的动作（`uc-23-2` R1 的定性），完成后它就是组织自己的资产。
6. `[待确认]` 同步周期（原型的 `2 小时前 / 昨天 / 3 天前` 看不出是自动周期还是手动）。

## R8 界面线索

- **屏**：源目录表（嵌在 `uc-23-1` 第 1 步内，`[原型 @16.555–16.556M]`）；
  另有一个精简版「市场三源」在「新建 Skill」页（`[原型 @15.691M]`）。
- **截图目录**：`ui-preview/asset-governance/`。
- ⚠ 缺屏（需补）：`[＋ 添加源]` 表单、`[修复]` 认证流程、源的停用/删除、
  **市场目录浏览屏**（Q-5，缺的是设计不是接线）。

## R9 非功能约束

- **安全**：本 UC 是**唯一出网**的部分。外部内容进入前不得被任何检索/embedding 消费
  （与 `uc-23-2` R9 同源）；同步必须服务端发起。
- **性能**：同步 1,842 个条目的清单要多久、清单存不存本地 → `[待确认]`。
- **可观测**：每个源的「上次同步时间 + 结果」必须可见（原型已有这一列，是好的）。
  ⚠ 但**没有「上次同步失败已持续多久」**——`失败 · 凭据过期` 可能是昨天开始的，
  也可能是三个月前 → `[设计]` 建议补。

## R10 已知约束 / 依赖

- 依赖密钥库（凭据存储）；与 `agent-runtime` 的 MCP 凭据存储**应共用**，不建第二套。
- ⚠ 依赖 **Q-0**（外部导入是否进 phase-1）、**Q-2**（源清单是固定四个还是可配置）。

## R11 切分提示

- 建议切两个 feature：① 源注册表 + 只拉清单的同步 + 健康状态；② 添加/修复源（含凭据）。
- ⚠ 「市场目录浏览屏」**不要塞进本 UC 的 feature**：它缺的是设计，
  一旦要做会连带出排序/筛选/评分/许可证/作者信誉一整套（Q-5 的风险条）。

## R12 AI Ready 验收线索

1. 源目录表列出**已连接的**源，表头为 `来源 / 类型 / 可用 / 上次同步`，
   区标题人数与实际源数一致（原型 `已连接 4 个` ↔ 4 行）。
2. 每行显示该源提供的资产类型集合，且四个源的类型集合互不相同（与原型一致）。
3. 触发一次同步 → 该源 `可用` 计数与 `上次同步` 更新，**资产库条目数不变**（规则 1 的直接断言）。
4. 同步返回的清单里塞一个不属于该源声明类型的条目 → 被拒并留痕（规则 3）。
5. 凭据过期的源：在 `uc-23-1` 的源选择里**不可选**，行内有 `[修复]`。
6. 在「新建 Skill」页只出现提供 Skill 的源（MCP Registry 不出现，规则 4）。
7. 修复凭据后，该源恢复可选，且下一次同步成功。
8. 凭据在任何接口响应、任何日志里 **0 命中明文**（规则 2）。
9. 非平台组管理员：看得到源目录表，看不到 `[＋ 添加源]` / `[修复]`（读写分离）。
10. 上游条目下架 → 已导入的同名资产**不受影响**，仍可用（规则 5）。
11. 上游清单解析失败 → 保留上次成功的清单（不清空）并显式报错。
12. 「可用 N」与「已同步 M」两个数在同一屏出现时口径可区分（不混用同一个标签）。
