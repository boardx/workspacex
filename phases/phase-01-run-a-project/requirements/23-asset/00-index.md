## 为什么单独成一个能力域（而不是塞进 `03-skill` / `04-agent`）

1. **原型自己说它是横切的**。第 3 步「治理与发布」的副标题逐字为
   「这一步**六种资产完全一样**：谁能用、出问题谁负责、什么时候重新检查」`[原型 @16.611M]`。
   把它放进 skills 或 agents，等于把一条横切六类资产的机制实现六遍。
2. **既有 21 条 skill/agent/model/mcp feature 一条都不覆盖它**。
   `六道关` / `落地检查` / `查重` / `灰度发布` / `复核周期` / `AGENT.md` / `Codex 社区`
   在 `feature_list.json` 与现有 `ui-preview/` 里全部 0 命中。
   F61「静态契约校验 + 安全扫描」校验的是**已在库中**的 skill，
   六道关治理的是**把外来的东西放进我们的权限与方法体系里**——原型这句话是第 04 关标题下的原文
   `[原型 @16.559M]`。两者不是同一件事。
3. **`skills` 与 `agent-runtime` 两束人类已签核**。往已签核的束里塞它没看过的设计，
   等于让一次签名替新设计背书。本仓已发生过一次同形事故，留痕在
   `phases/phase-00-shared-kernel/design-coherence.md` frontmatter 的署名例外。

## ⚠ 本束还领了一层没人认领的东西：**后台外壳与左栏 IA**

人类同日提问「**为什么在管理后台看不到项目蓝本**」。核实结果（可复现）：

| 事实 | 证据 |
|---|---|
| 后台壳存在 | `apps/web/app/admin/[module]/page.tsx` + `app/admin/page.tsx` |
| 左栏「AI 能力」组**只有 4 项**（agent / skill / model / mcp），**缺画布模板、缺项目蓝本** | `apps/web/lib/mock/admin.ts` 的 `ADMIN_NAV`，第 34–52 行 |
| 蓝本设计器被画在**独立路由 `/tpl`**，从未接进 `/admin` | `apps/web/app/tpl/`；`/admin/blueprint` 不存在 |
| 顶部组织额度条已建成且与人类截图逐字一致 | `ORG_HEADER = { 远洋咨询, org_8f21, 4820/6200 万, 78%, 剩 6 天 }` |

**根因**：十个契约束是**按能力**切的，后台是这些能力的**公共宿主**——
每个束都往里放东西，**没有任何一个束负责这个容器本身**。
于是「左栏该有几项」这个问题不属于任何人，缺两项也就没有任何门控会红。

⇒ 本束把这一层收编，见 `uc-23-8`。**边界必须可判定**，否则会与已签核的四个束重叠
（ADR-023 明确要红：一个 feature 被两个束声明 ＝ 归属不唯一）。判据写在下一节。

### 边界判据（可机械判定，写进 `contracts/asset-governance/domain.md` 与 `design-signoff.md`）

对任一候选 feature，问一句：**「把这条规则里的资产类型换成另一类，这条规则还成立吗？」**

- **还成立 ⇒ 归 `asset-governance`**（它是横切的公共机制）。
  例：「负责人到期不复核则降级为仅负责人可见」——换成 MCP、换成蓝本，仍成立。
- **不成立 ⇒ 归该资产自己的束**（它是那类资产的领域规则）。
  例：「带副作用的 MCP 工具永远不能设为『全体成员自动调用』」——换成 skill 就没有意义。

| 归属 | 内容 |
|---|---|
| **本束负责** | 后台外壳与左栏 IA（六项齐全）、组织额度条、数据总览；六种资产的**公共治理机制**——导入六道关（`uc-23-1/2`）、可见范围 · 谁能改 · 负责人 · 复核周期（`uc-23-4`）、目录文件树与编辑器（`uc-23-3`）、试跑台与回归用例（`uc-23-5`）、复核到期与降级（`uc-23-6`）、社区源（`uc-23-7`） |
| **本束不负责** | 六类资产**各自的领域模型与业务用例**：`skills`（Skill 契约三段、四态、双门禁）、`agent-runtime`（Agent 四栏、模型路由、**MCP 逐工具授权与 14 天隔离期 F52–F54**）、`canvas`（画布模板分区与围栏语法）、`templates`（蓝本 16 项配置与套用/提回）。**这四束已由人类签核，本束一条都不重新声明。** |

⚠ **MCP 特别说明**：人类同日也在 review MCP 的 feature/UI（接入 MCP 服务器、
逐工具授权 9 个、「带副作用的工具永远不能设为全体成员自动调用」、第三方源 14 天隔离期）。
按上面的判据，这些**全部归 `agent-runtime`（F52 / F53 / F54，已签核）**；
本束只负责左栏「MCP 服务器 6」这一项**在后台里的存在与位置**，
以及 MCP 作为六种资产之一时的**第 3 步治理配置**。
**本束不得引用、复述或重新声明 F52–F54 的任何规则。**

## 为什么切成 8 份而不是任务书建议的 6 份

任务书建议 6 份（`uc-23-1` 导入 / `23-2` 六道关 / `23-3` 编辑 / `23-4` 治理发布 / `23-5` 试跑 / `23-6` 复核到期）。
本模块**保留这 6 份，另加 `uc-23-7`**，两条理由：

- **Actor 不同**。添加/修复一个社区源是**平台组管理员**的组织级动作
  （原型把「Codex 社区 · 失败 · 凭据过期 · `[修复]`」放在源目录表里，不在导入向导里 `[原型 @16.556M]`）；
  导入某个资产是**能力维护者**的动作。R5 写不到一起。
- **失败模式不同**。源不可用（凭据过期 / 同步失败）与资产不合格（六道关阻断）
  是两类完全不同的异常，混在一份 UC 里会让 R4 的 E 条目互相污染。

**`uc-23-8` 是 2026-07-30 晚些时候追加的**，起因见上一节：后台外壳这一层不属于任何束。
它不与前七份合并，因为它的 Actor（组织管理员）、失败模式（左栏缺项）与后置条件
（IA 完整性）跟资产生命周期没有一条重合。

另外**没有**把「从实际用法沉淀」单独切一份，尽管它在原型里带独立数据
（`检测到 3 个候选` `[原型 @16.553M]`）：它是 `uc-23-1` 第 1 步四选一里的一支，
主流程完全汇入同一条；单独成 UC 会让 R3 重复三遍。它在 `uc-23-1` 的 A3 备选流程里展开。

## ⚠ 本模块与已拍板裁决 D-06 正面冲突

`03-skill/uc-3-1` 顶部逐字写着人类 2026-07-27 的拍板：

> **[人类已拍板 2026-07-27 · D-06]** …… **phase-1 不做沙箱、不执行任意代码**；
> **多文件可执行包、仓库导入、外部社区导入均为 phase-2 能力升级**。

本模块要求的 `uc-23-1`（仓库导入 / 上传 zip / 社区导入）、`uc-23-2` 第 05 关（沙箱试跑）、
`uc-23-3`（多文件目录与 `scripts/validate.py`）**恰好是 D-06 明确推到 phase-2 的三件**。
`contracts/skills/domain.md` 也据此把 `source = 社区` 标为「phase-1 入口置灰」、
把灰度发布标为「phase-1 只做分流与跳转；灰度列 phase-2」。

**这不是可以由 agent 顺手翻的案。** 登记为 `OPEN-QUESTIONS.md` 的 **Q-0**，
它是本模块**生成 feature 之前必须先有的裁决**。本模块的 UC 按「若 Q-0 裁为放行」书写，
并在每处受影响的地方标出 `⚠ Q-0`。
