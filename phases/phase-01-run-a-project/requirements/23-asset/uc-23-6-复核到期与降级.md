# 原始需求（细化）— UC-23.6 复核到期与降级

> 所属：M23。口径见 `00-index.md`。优先级 **P0**；估点 **[待确认]**。
>
> ⚠ **本 UC 是「同一事实不得声明在两处」的高危区**（本仓头号失败模式，已八次）。
> 原型自己逐字说这条规则「**与组织大脑里知识条目的规则一致**」——
> 即它**天生就有两个宿主**。单一事实源的落点未定 ⇒ `OPEN-QUESTIONS.md` **Q-7**。
> **本 UC 是这条规则的唯一文字定义处**；`uc-23-4` 只声明「有这三档、有这条规则」，不复述语义。

## R1 概览

- **Use Case ID / 名称**：UC-23.6 / 复核到期与降级
- **Actor**：**系统**（计时与自动转态）、**资产负责人**（复核动作）、**平台组管理员**（兜底）
- **目标**：让一个资产不会因为「当年发布过、之后没人管」而无声地继续被信任。
  规则原文（本 UC 全部内容的来源，`[原型 @16.613M]`）：
  > **到期后自动转「待复核」，仍可用但调用时会提示；30 天无人复核则降级为仅负责人可见。
  > 这与组织大脑里知识条目的规则一致。**
- **系统边界**：复核计时器、`待复核` 态、调用时提示、降级动作、复核动作。

## R2 前置条件 / 触发条件

**前置条件**
- 资产已发布，且带 `{负责人, 复核周期}`（`uc-23-4` 后置条件）。
- 复核到期时间 = 发布时间 + 复核周期。⚠ **重新发布是否重置计时** → `[待确认]`
  （直觉上应重置，但原型 0 命中，且「重新发布」与「复核」是不是同一件事也没依据）。

**触发条件**
- **T1** 系统时间到达复核到期时间 ⇒ 转 `待复核`。
- **T2** 进入 `待复核` 满 30 天且无人复核 ⇒ 降级为**仅负责人可见**。
- **T3** 负责人（或可改集合内的人？见 R5）执行复核 ⇒ 计时重置。

## R3 主流程（三段状态迁移）

```
已发布(生效) ──到期──▶ 待复核 ──30 天无人复核──▶ 降级：仅负责人可见
     ▲                    │                              │
     └────── 复核 ────────┘                              │
     └──────────────── 复核 ？（待确认，见 E4）───────────┘
```

1. **到期转态**：系统在到期时把资产转为 `待复核`。
   - **它仍然可用**（原型原文「仍可用」）——不停用、不从检索范围移出。
   - **调用时会提示**（原型原文）。⚠ 提示出现在**哪里、给谁看、长什么样**，原型 0 命中 → `[设计]`。
     旁证：组织大脑侧有同形提示的实例——消息头上直接标「**待复核 3**」`[原型 @16.310M]`，
     以及过期洞察卡明写「**不参与定题强度计算**」`[原型 @16.310M]`。
     ⚠ 但那是**知识条目**的表现；资产的「调用时提示」是不是同一形态 → `[待确认]`（并入 Q-7）。
2. **30 天倒计时**：进入 `待复核` 起算 30 天。
   ⚠ 这 30 天内是否有**提醒/催办**（给负责人发通知、进待办），原型 0 命中 → `[设计]`。
   没有催办的话，30 天倒计时的实际效果就是「大概率都会降级」。
3. **降级**：降级为**仅负责人可见**。
   - ⇒ 该资产从所有其他成员的检索、列表、绑定面板消失（复用 `identity` 束的可见性判定，X-1）。
   - ⚠ **已有的引用怎么办**：一个被降级的 skill，正被 5 个进行中的项目绑定着。
     按 `contracts/skills/domain.md` I-10 的既有形状（归档版本「不可被新绑定，但已有引用仍可解析」），
     **推测**降级也应是「不可新绑定、已有引用仍可解析」→ `[设计]`，**必须人类确认**。
     若不确认就实现成「立即失效」，会让进行中的项目在半夜炸掉。
4. **复核**：负责人执行复核 ⇒ 回到生效态，计时从复核时间重新起算。
   ⚠ 「复核」这个动作**具体做什么**（只是点一个「我看过了」，还是要重跑六道关 / 重跑回归用例），
   原型 0 命中 → **`[待确认]`，这是本 UC 最大的空白**。

## R4 备选流程与异常流程

**备选流程**
- **A1 到期前主动复核**：应当允许（提前复核并重置计时）。原型 0 命中 → `[设计]`。
- **A2 改复核周期**：把 24 个月改成 6 个月，已过 12 个月的资产**立即到期**吗？→ `[待确认]`。
- **A3 复核时决定停用**：复核的结论不一定是「继续用」。停用路径归 `03-skill/uc-3-4`（已签核），
  本 UC 只提供入口，不重定义停用语义。

**异常流程**
- **E1 负责人离职 / 账号停用**（与 `uc-23-4` E3 同源）→ **降级终态「仅负责人可见」会变成
  「谁都不可见」**，资产事实上消失且无人能恢复。
  ⚠ 这是本 UC 最严重的洞。必须有一个兜底接管人（候选：平台组管理员 / 组织管理员）→ `[待确认]`。
- **E2 资产在 `待复核` 期间被编辑并重新发布** → 算复核了吗？→ `[待确认]`（与 R2 的重置问题同源）。
- **E3 降级后又过了很久** → 有第三级降级吗（如自动停用）？原型只有两级 → **明确无第三级**，
  但要确认这是设计而非遗漏 → `[待确认]`。
- **E4 降级后能否复核回来** → 原型 0 命中。若不能，降级即不可逆；若能，由谁做
  （负责人是唯一还看得见它的人，所以只能是他，除非有 E1 的兜底人）→ `[待确认]`。
- **E5 六种资产的降级后果不同**：一个被降级的**项目蓝本**（已被 7 个项目套用）
  与一个被降级的**MCP 服务器**（正被 3 个 agent 调用），后果完全不是一回事。
  ⚠ 「六种资产完全一样」这句话在**治理配置**上成立（`uc-23-4`），
  在**降级后果**上是否成立，原型没说 → `[待确认]`。
- **E6 时钟/时区**：到期判定用什么时区、跨夏令时怎么算 → `[待确认]`（低危但会产生 off-by-one）。

## R5 权限与可见性

- **系统**：T1 / T2 两次自动转态。**没有人**可以手工把资产从 `待复核` 直接改回生效
  而不留一条复核记录。
- **资产负责人**：执行复核。降级后他是**唯一**仍可见该资产的人。
- **可改集合内的其他人**：能否代为复核 → `[待确认]`。
  ⚠ 与 **Q-9**（`负责人 ∈ 可改集合`）相关：若负责人不在可改集合，
  他可能能复核但不能改，那复核结论「需要修改」就无法执行。
- **平台组管理员 / 组织管理员**：E1 的兜底接管人候选 → `[待确认]`。
- **可见范围内的普通成员**：能看到该资产处于 `待复核`（因为「调用时会提示」意味着**使用者看得到**），
  但**不能**复核。

## R6 后置条件 / 不包含

**后置条件**
- 到期 ⇒ 资产状态含 `待复核` 标记，调用路径带提示，**可用性不变**。
- 30 天无人复核 ⇒ 可见范围收敛为 `{负责人}`，且该收敛**走与 `uc-23-4` 相同的可见性写入路径**
  （不是另一个绕过判定函数的后门）。
- 复核 ⇒ 一条复核记录 `{复核人, 时间, 结论}` + 计时重置。

**不包含**
- **停用/归档语义** —— `03-skill/uc-3-4`（已签核）。
- **组织大脑知识条目的到期规则** —— `14-brain`（phase-3）。⚠ 但它与本 UC 是**同一条规则**，
  见 Q-7：两处必须共用一个定义，不是「各自实现且刚好一样」。
- **MCP 的 14 天隔离期** —— `agent-runtime`（F52–F54，已签核）。
  与本 UC 的复核周期是两套计时器还是一套，见 **Q-6**。

## R7 业务规则（本 UC 是这些规则的**唯一**文字定义处）

1. **到期后自动转「待复核」**——自动，不需要任何人触发。
2. **`待复核` 仍可用**——不停用、不移出检索范围。
3. **`待复核` 调用时会提示**——提示是给**使用者**看的（否则「调用时」没有意义）。
4. **30 天无人复核则降级为仅负责人可见**。
5. **复核周期三档 `6 / 12 / 24 个月`**（取值集合的定义在 `uc-23-4` R3 第三项，
   本条只引用不复述数值来源）。
6. **本规则与组织大脑知识条目的规则一致** ⇒ **必须是同一个实现**，Q-7 决定它住哪。
7. **降级不是删除**：资产仍存在、负责人仍可见、可恢复（E4 待确认）。
8. `[待确认]` 「复核」这个动作的内容（R3 步骤 4）——**这是本 UC 最大的空白**，
   没有它这条规则只是一个会让资产慢慢消失的定时器。

## R9 非功能约束

- **性能/规模**：到期扫描是定时任务还是惰性判定 → `[设计]`。
  ⚠ 惰性判定（读的时候才算）会让「30 天无人复核」这个倒计时**永远不触发**
  （没人读的资产就没人算它）——而恰恰是没人读的资产最该降级。
  ⇒ **必须是主动扫描**，这一条建议写成不变量。
- **可观测**：每次自动转态与降级都必须写审计（谁都没做，是系统做的，所以更需要留痕）。
- **兼容与降级**：扫描任务挂掉时，不得出现「到期了但没转态」而无人知道 ⇒ 需要一个
  「最近一次扫描时间」的可观测指标。

## R10 已知约束 / 依赖

- 依赖 phase-00 `identity` 的可见性判定（降级要走同一条路径，X-1）。
- 依赖 `uc-23-4` 的 `{负责人, 复核周期}`。
- ⚠ 依赖 **Q-6**（与 MCP 隔离期的关系）、**Q-7**（单一事实源落点）、**Q-9**（负责人与可改集合）
  三条裁决，另有 R7 规则 8（复核动作的内容）必须先有答案。

## R11 切分提示

- 建议切三个 feature：① 计时器 + 到期转 `待复核` + 主动扫描；② 调用时提示；
  ③ 30 天降级 + 复核动作 + 记录。
- ① 是唯一能被机械验证的一件（造一个到期时间在过去的资产，跑扫描，断言转态）。
- ③ 在 R7 规则 8 有答案之前**不要开工**。

## R12 AI Ready 验收线索

1. 造一个 `复核到期时间` 在过去的已发布资产 → 跑扫描 → 状态含 `待复核`。
2. `待复核` 的资产**仍出现**在可见范围内成员的列表/检索/绑定面板（规则 2 的直接断言）。
3. 调用一个 `待复核` 资产 → 调用方看到提示（规则 3）。
4. 造一个进入 `待复核` 满 30 天的资产 → 跑扫描 → 可见范围收敛为 `{负责人}`；
   其他成员的列表/检索/绑定面板/Context Pack **四处 0 命中**。
5. 降级走的是与 `uc-23-4` 相同的可见性写入路径（可断言：同一函数被调用，无第二条写入路径）。
6. 降级后负责人仍能看到并打开该资产。
7. 复核 → 状态回生效、`复核到期时间` 从复核时间重新起算、留下一条复核记录。
8. **零调用**的到期资产也会被降级（R9 的主动扫描断言——这一条专门反证惰性判定）。
9. 每次自动转态与降级都有审计记录，且记录里的执行者是系统而不是某个人。
10. 「最近一次扫描时间」可观测；扫描停摆时该指标变旧（而不是静默）。
11. 复核周期取值只可能是 `6/12/24 个月`；构造其他值被拒。
12. 本规则的实现与组织大脑知识条目的到期规则**是同一段代码**
    （全仓 grep `30` 天与三档周期的定义处应恰好 1 处 —— 规则 6 的机械断言）。
13. 负责人被停用的资产 → 按 E1 裁决结果断言（未裁前不写验收，**但必须有一条**）。
