## 二、从 UC 读出来、但界面上**无法自洽**的点（sign-off 必须先裁的）

1. **🔴🔴 四视角是否被读成「第二套可见性规则」——这是本束最高风险（X-1）。**
   一致性复核 X-1 裁定「六条路径（检索 / Context Pack / embedding / 图遍历 / 文件浏览器 / 缓存）
   必须共用同一个判定函数，判定归 identity 束」。四视角界面天然会让人以为「界面这里在做可见性判断」。
   **我的处理**：在 `roles` 屏顶部放了一条常驻说明（`roles-single-source-note`），
   明写「四视角是服务端 `identity.authorize` 单一判定的界面投影，不是第二套规则」，
   且视角切换标注「预览手段 · 不可写入 · 留痕」。**但界面本身无法证明后端真的只有一处判定**——
   这条要靠契约 ③ 节（`identity.authorize` / `authorizeBatch`）与实现门控保证。
   ⚠ sign-off 必须确认：四视角的可见面（尤其观察者「已发布产出 + 脱敏聚合」）
   与文件浏览器 `denied` 态、Context Pack 的观察者面**逐项一致**，不是三处各写一套。

2. **一次性链接「使用者记录」的呈现位置未定（UC-1.3 R10 [待确认]）。**
   `invites` 屏我把 `used_by`（`郑好 · 今天 09:12`）放在**链接卡片下方**并显式标了
   `[待确认] 呈现位置：名单行内 / 链接卡片下 / 仅审计流水`（见 `uc-1-3-invites-default` 第 3 组）。
   规则本身（记录使用者）已由 O-06 落到 `invite_link.used_by`，**缺的只是界面落点**——三选一需产品定。

3. **激活链接「7 天」尚无单一事实源常量。**
   密码长度、邀请码位数、重发冷却都从契约 `AUTH_POLICY` 读（界面无写死）。
   但**组织成员激活链接有效期 7 天（O-28 ④）与「撤销后 5 秒失效」（AC2 · Backlog）
   目前不在 `AUTH_POLICY` 里**，我在 mock 里以 `ACTIVATION_CONTEXT.linkValidDays = 7` 承载并注了警。
   ⚠ 这正是 CLAUDE.md 反复警告的「第二份副本」温床：等这两个数进契约前，任何后端实现都会再写一份。
   建议契约束 ③ 节把 `activationLinkDays` / `revokeEffectiveSeconds` 补进 `AUTH_POLICY`。

4. **「资源可见性范围」字段只在 agent / 画布模板上确认存在（UC-1.4 R7 / R10 [设计]）。**
   `roles` 屏我把「组织角色决定资源准入」写进了角色说明条，但**没有单独画 skill 库 / 项目蓝本
   的可见性列**——因为原型里这两张表已探明且**行内没有可见性列**（原型确认缺失）。
   是否给它们补该字段，需人类裁决（同 UC-0.3 R7）。⚠ 且 MCP 的「授权范围」是另一套枚举
   （仅项目负责人 / 全体成员 / 待安全评审），**不得与团队可见性合并**——界面上我未混用，请核。

5. **组长 / 项目负责人是否有撤销权未定（UC-1.3 R5 留问号）。**
   `invites` 屏我取的默认是**组长不可撤销 / 重置**（`uc-1-3-invites-grouplead` 走无权限投影）。
   项目负责人的撤销权 R5 也留了问号——我未给项目负责人单独视角（预览器只有四个项目角色），
   这条需产品明确。

6. **临时提权是否同时支持「按时间失效」与「手动提前收回」（UC-1.4 R4 A2 [待确认]）。**
   `grant` 屏只画了**按流程节点失效**（选失效环节），未画时间失效与手动收回入口——
   因为原型只有「环节 3 结束自动失效」。若要加这两种补充失效方式，需补交互。

7. **低权角色本人是否能看到四视角切换器（UC-1.4 R4 A1 [待确认]）。**
   原型把切换器画在项目工作台顶部，未说明可见范围。我的 `roles` 屏对所有预览视角都渲染切换器
   （因为它是**预览工具**），但真实产品里「组员本人能否看到这个切换器」未定。

## 三、我替 UC 做的判断（UC 没写明、我在界面上定了的，逐条看）

1. **七屏收敛成一个 `/org-admin/preview` + `?screen=` 切换器**，左栏导航按 UC 分组标注载体
   （UC-1.3 载体一/二、UC-1.4 载体一/二/三、UC-1.6）。UC 没规定这些屏如何在一个原型里组织。
2. **单条撤销 / 重置全部 / 授予临时读权 / 移除成员的二次确认统一为「填理由（≥4 字）解锁 + 影响范围」**
   （复用 `components/admin/panel.tsx` 的 `ConfirmDialog`），不是孤零零的红按钮。R8 只要求「二次确认 +
   影响范围」，确认形式（原因门控）是我定的。
3. **撤销弹层里把 O-06 的两条裁决直接写进影响范围**：「已在场者不被踢出，保留至当前环节结束」
   「新访问 5 秒内失效」。UC 未规定它们在弹层的呈现，我放在影响面正文。
4. **`used_by` 放在链接卡片下**（见第二节 #2），并把「待确认呈现位置」做成界面上看得见的一条 badge。
5. **协同引导师在身份四选里保留为第四项**，选中时弹一句「＝ 以引导师身份加入（O-03，落库即 facilitator，
   不新增第五种角色）」。UC 要求文案写明这一点，具体措辞是我定的。
6. **管理员边界的「谁读过我的项目」做成项目负责人视图区**（`boundary-who-read`，标「需补原型」），
   D-18 ② 只说「对项目负责人可见」，其呈现位置与形态原型未画，我补成一条访问时间线。
7. **激活落地页做成免登独立居中卡片**（不套后台三栏），按 UC-1.6 R8「不复用后台」。
   新用户 / 已有账号用**两个分支按钮**切换，UC 未规定切换形式。
8. **配额硬阻断做在邀请弹层内**（用尽时按钮 disabled + 红条 + 直达「去调整配额」），
   而不是点了才报错。O-29 ⑤ 要求「阻断伴随可执行下一步」，具体位置是我定的。
9. **成员移除的「已离职」标记 vs 匿名化**：按 O-29 ② 取**保留署名 + 标已离职**，
   并在弹层里写明「与授权撤回 UC-17.2 是两条不同路径，不混用同一代码」。
10. **观察者视角在 `roster` 屏只显示脱敏聚合到场数**（不展开姓名 / 链接 / 二维码），
    R5 只说「脱敏聚合」，我定为「隐藏名单明细，保留 n/m 计数」。

## 四、R8 线索之间互相矛盾、我怎么处理的

1. **分组链接「带令牌」vs「裸组号链接」（UC-1.3 R10 O-06 记录的原型自相矛盾）。**
   proto-04 带 `?t=`＋24 小时，proto-08 四条分组链接无 `?t=`。已裁决 O-06 统一采信「带一次性令牌」。
   我在界面上**统一画成带令牌的链接**（`wsx.app/w/kickoff-8f21/g/2?t=9f21-b3`），
   并把「单条撤销作用于令牌」写进撤销弹层——与裁决一致，未两面下注。
2. **「观察者只读」两个入口（账号身份 vs 链接身份）是否放宽（UC-1.4 R7）。**
   R7 明写「不因入口不同而放宽」。我让 `roles` 观察者视角与 `roster` 观察者面、`invites` 观察者行
   **用同一套「已发布 + 脱敏聚合」口径**，不为链接单画一套过滤面。
3. **「邀请管理员双人复核」vs「组织仅一名管理员」（O-28 ⑥ 的边界）。**
   两者看似冲突（要复核却无人复核）。我在邀请弹层的管理员警告里直接写明「仅一名管理员时转待批队列
   （需平台运营方协助），不退化为单人可批」，把边界摆到界面上，而不是让它在实现里悄悄退化。

## 六、建议 sign-off 时重点核对的三处

1. **四视角是不是「单一判定的投影」（第二节 #1，X-1）**——本束最高风险。
   请核：观察者的可见面（已发布 + 脱敏聚合）在 `roles` / `roster` / 文件浏览器 / Context Pack 四处
   **是否逐项一致**；四视角界面有没有任何地方在**自己做**可见性判断。这条不定，
   F04/F07 的服务端断言会与界面漂移。

2. **两个未进契约的数值：激活链接 7 天 + 撤销 5 秒（第二节 #3）**——
   密码长度 / 邀请码位数 / 重发冷却已在 `AUTH_POLICY` 单源，这两个还没有。
   请拍板把它们补进契约常量，否则后端实现必产生第六/第七份副本（本项目已五次因此漂移）。

3. **一次性链接 `used_by` 的呈现位置 + 组长/项目负责人撤销权（第二节 #2、#5）**——
   直接决定 F15/F16 的验收锚点写在名单行内、链接卡片下、还是仅审计流水；
   以及撤销这个「链接外泄唯一止血手段」到底谁能按。这两条不定，F15/F16 的 verification 无处锚定。
