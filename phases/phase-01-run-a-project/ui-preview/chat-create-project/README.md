## 为什么入口只能在「个人对话」

真栈 chat 分两条线，实测：

| 屏 | 事实 | 能不能放 |
|---|---|---|
| 项目对话 `chat-read-screen.tsx` | **必须有 projectId**，没有就渲染 `chat-missing-project-context`，文案逐字「请先选择项目——**对话属于具体项目**」（第 379-385 行） | ❌ 你已经在项目里了 |
| 个人对话 `personal-chat-screen.tsx` | 无项目上下文；左栏那句「**不挂靠任何项目，仅自己可见**」 | ✅ |

⇒ 派工单原文只写「chat 对话侧」，未指定哪条线；按实测收敛到个人对话（coord-main 2026-08-13 裁）。

## 两个候选

### 候选 A —— 线程操作区（左栏）

- **支持**：常驻、好找；与「新建对话」并列，紧接着那句「不挂靠任何项目」——
  语义上这就是个人线程的**毕业路径**。
- **代价**：左栏是全局常驻区，多一个按钮就多一分永久占用；且与「新建对话」视觉权重接近，
  可能被误点（两者后果差别很大：一个建线程，一个建项目）。

### 候选 B —— 落地动作集（「选一条结论落地」）

- **支持**：**语义最准**。该区已有的动作是
  `存为洞察 / 加入报告 / 开一场深度研究`——「开一场深度研究」本身就是
  「把一段对话变成更大的东西」，**建项目是它的同族兄弟，不是新范式**。
  这对签核有利：它落在已签核材料的既有语义里，不新增交互范式。
- **代价**：只在落地页出现、不常驻；用户要先走到那一屏才看得到。

## 确认交互（两个候选共用同一个面板）

入口位置可以二选一，但**确认交互不该有两套**。面板只收一个字段：

- **项目名**：预填对话标题、可改；
- 其余按契约固定：`kind: "workshop"`、`blueprintVersionId: null`。

面板里逐条写明后果，不让用户猜：

1. 建为工作坊，**不套用蓝本**（蓝本服务尚未实现，见 #991）；
2. 这段对话**不会**被搬进新项目，**也不会记录来源关系**（本版范围）；
3. 建成后跳转到新项目。

## 这一版后端零新增

复用**已经真实存在**的 `POST /projects`（后端 F117 / 前端向导 F158，均已 passing）。
与 PJ-01 的新建向导**共用同一条创建路径**，符合 #991 裁决 ①「createProject 单门」。

⇒ 本 feature **不新增端点、不新增错误码、不新增字段、不碰 delta**。

## 一处刻意不做的事：不留溯源关系

「从这段对话建的项目」这条来源关系**本版不落库**（coord-main 2026-08-13 裁）。

理由：留关系需要新字段或新表 ⇒ 契约新增面 ⇒ 得走一轮 delta 签核。
本版先把闭环打通。**这不是「忘了做」，是明确排除**——所以确认面板里
对用户如实写了「也不会记录来源关系」，而不是默默不做。

将来要做，是一份独立的 delta（届时要回答：来源关系给谁看、能不能解绑、
对话删除后关系怎么办）。

## 签核后要做什么

人类选定 A 或 B 之后：

1. 把入口接进对应生产屏（`personal-chat-screen.tsx` 或 `landing-panel.tsx`）；
2. 接真实 `createProject`（复用 `lib/live-projects.ts` 既有封装）；
3. 补组件测试，**含反证**：打断接线后断言 fetch 的用例必须变红
   （同 F164/F172 两次的做法）；
4. 走 requirement-author 补 feature 条目 → claim → verify → PR。

⚠ 在签核之前**不做上面任何一步**——这正是 ADR-023 第 ① 件先行的意义：
界面跑得通不等于设计成立。
