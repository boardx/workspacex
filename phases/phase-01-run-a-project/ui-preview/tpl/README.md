### 预览怎么走
顶部「预览控制条」（仅 dev，生产 `NODE_ENV=production` 不渲染）三行：
- **屏** `?screen=`：list / designer / apply / prep / workflow / promote / versions
- **视角** `?as=`：facilitator / groupLead / member / observer（预览手段，真实权限在服务端 RLS）
- **七态** `?state=`：default / loading / empty / invalid / dep-failed / denied / success（走共享 `StateShell`）

每个可交互元素与关键展示区都带 `data-testid`（`tpl-*`，七态保留名 `loading/empty/err-*/denied/dep-failed/saved`），
供后续 verification 锚定。这是与旧原型（零 testid、零异常态）最大的差别。

## 二、从 UC 读出来、但界面上**无法自洽**的点（sign-off 必须先裁的）

1. **🔴🔴 议程环节的字段名：仓库里已有四个名字打架（第 7 次「同一事实两处」）。**
   `apply` 屏底部的「项目侧缺失概念」框把它画了出来：phase-00 **已落库 `stepId`**、**已实现动作词 `stage.*`**；
   而 `uc-2-2` **同一份文档**既命令写 `agenda_stage`（第 29 行）又自己写了 `agenda_segment_id`（第 394 行）。
   我在 mock 里统一用 `agenda_segment_id` 命名（跟随 templates 契约 domain.md），**但这是跨「已签契约 / 未签需求」两侧的分歧，
   改哪边都不是实现者能定的**。sign-off / 契约束必须先收敛成一个名字（依据 `00-project/DERIVED-FROM-CONTRACTS.md` D-14 / Q-3）。

2. **🔴 「必填项完成才能发布」与运行态原型直接冲突（缺 D-9）。**
   `designer-invalid` 与 `publish-confirm` 都把这条画成了阻断门槛，但原型里 `15/16`、`12/16`、`9/16` 的蓝本**均为「已发布」**。
   O-18⑤ 的和解是「那些缺项 `required=false`」——**这是推测性和解，需人类确认成立**。在确认前，`invalid` 态到底该不该拦发布，
   界面只能二选一地呈现（我选了「拦」），实际未定。

3. **🔴 矩阵格的内容粒度未定（缺 D-10）—— 直接决定 F27 的「恰好 9 条待办」断言。**
   `workflow` 屏的矩阵格里写着「写 ≥1 张便签 · 投票」。这**一格是一条待办还是两条**？
   「3 环节 × 3 角色 = 恰好 9 条待办」（AC7 / V9b / 不变量 I-23）在「一格多条」口径下就是错的。
   界面按「一格一条」画，但这条假设已被写进 feature 验收断言，sign-off 请优先看。

4. **🔴 满意度样本量阈值缺一个数（缺 D-5）。**
   `list` 屏满意度列按 O-37③ 显示「4.6（9 场）」或「样本不足（3 场）」，阈值 mock 里写死 `SATISFACTION_MIN_SAMPLE=5`。
   「低于阈值不显示分数」这条口径已定，但**具体数值待产品给**；现在 `组织诊断（3 场）` 显示「4.3」还是「样本不足」取决于这个数。

5. **🔴 「蓝本维护者」是谁未定（缺 D-1）—— 阻断提回屏的合并侧。**
   `promote` 屏的合并按钮我按「引导师不可合并、方法负责人可合并」演示，但「维护者是组织角色还是每份蓝本单独指定的 owner、
   能否多位」未裁。这条不定，F29 的 `mergePendingChange` 权限断言写不实。

6. **单场 3.5M / 90% 是否项目级可覆盖、与三级阈值如何取舍（缺 D-3）。**
   `designer` 配额区显示单场预算，但 proto-03 另有「组织 90% / 成员 85% / Agent 级」三级阈值（「最先触发的一条生效」）。
   两者的取舍未确认，界面只画了单场一层。

## 三、我替 UC 做的判断（UC 没写明、我在界面上定了的，逐条看）

1. **屏组织为「后台·项目蓝本」+「项目·筹备」两组左栏导航**：R8 各 UC 分别给了入口，但七个屏如何在一个原型面里并置、
   如何在它们之间跳转，UC 没说。我按数据归属分两组，沿用后台两栏 + 项目三栏的既有心智。
2. **完成度分母恒读 `CONFIG_ITEMS.length`（当前 15），界面绝不出现字面量 16/15**：这是 O-07/O-18⑤ 的实现方式（不变量 I-5），
   我把它做成 mock 里一张 `CONFIG_ITEMS` 表 + `configTotal()` 函数，第 16 项补出与否都不改界面。
3. **`required` 一栏此刻是占位示例**（我把基本配置 4 项 + 场地与形式标为必填），只为让「校验失败态」有东西演示。
   **哪几项真必填「清单本身无依据，仍需人类给出」（缺 D-2）**——sign-off 请把这份清单当作**未定**看。
4. **危险动作统一走一个 `ConfirmDialog`**（发布 / 删除 / 归档 / 换模板 / 回滚 / 合并）：R7 只要求「显式 + 影响范围」，
   确认形式我定为「影响范围列举 + 部分动作要填理由 ≥4 字才解锁」，不做孤零零红按钮。
5. **AI 产出统一用 `AiTag`（角标 + 来源计数）与人工内容视觉区分**：R7 要求机器产出标识 + 挂来源，但表现形式未规定；
   我用 `ai` 语义 token 的 Badge + 「来源：…」文字，未确认时不落为最终值（对象表里 AI 建议人选标「需人确认」）。
6. **组状态三态用固定色语义**（录音就绪=primary / 缺 N 人=warning / 需介入=danger），封闭三值（不变量 I-14），不自造第四态。
7. **回滚做成「新建等同旧版的新版本」并在确认框里写明 `rolled_back_from`**（O-18②）：原型无回滚屏，这是补画；
   我把「历史线性、版本号只增不减」直接写进影响说明，让人类核对语义。
8. **新建向导为两步**（选蓝本 → 选档位并预览六类初始化）：R8「推荐交互」建议两步，确认后才写入的细节、幂等去重的界面表达由我补。
9. **满意度、准备度等展示值我照原型示例填了具体数**，但准备度百分比口径未定（缺 D-13），本域不承诺它。

## 四、旗标含义与三态各不同的处置（PROTOTYPE-DIGEST「先分清要补什么」）

屏上的旗标颜色对应三种不同的 sign-off 处置，**不要一律当「已画好」看**：

- **未探明（橙 · Info）**：原型很可能有、只是本轮没点进去 → 不要重画，先补抽取。
  出现在：设计器 15 项**各配置项打开后的面板**（`designer` 每个「当前项面板」）、
  筹备页 `议程 / 材料准备 / 会前任务` 三子标签、提回屏**项目侧复盘屏**、第 16 项。
- **确认缺失 · 补画（蓝 · Warning）**：已探明区确认缺失 → 这才是我画的原创补充，需逐条 sign-off。
  出现在：提回屏**蓝本侧待审改动收件面**、版本历史屏 / 回滚入口 / 删除影响面、新建向导两步流。
- **与原型冲突 · 待裁（红 · ShieldAlert）**：文档要求与运行态原型直接打架 → sign-off 必须先裁。
  出现在：发布门槛「必填才能发布」（D-9）、换档位「可选/必留 + 压缩时间」（D-8）、矩阵格粒度（D-10）。

R8 线索之间的矛盾我怎么处理的：
- **「改动只影响那一场」vs「提交回蓝本」**（UC-2.2/2.3 同源规则的两处表述）：我在设计器一览底部、工作流「改动只影响这场」、
  提回屏「唯一沉淀通道」三处**用同一句口径**呈现，不让它们各写一版；`[另存为组织模板]` 与「提回蓝本」按 O-02 画成两条不同路径
  （横向复制投影 vs 纵向回灌定义层），不合并。
- **「设计环节」文案 vs D-03 正名「设计配置」**：R8 自己指出「原样呈现一个被改过的字符串是自相矛盾的」，我用「设计配置」正名，
  只保留完成度 `n/分母` 的**呈现形式**，分母读表。

4. **F28 的隔离不变量不可见**：「项目上下文不存在写蓝本/后台模板本体的旁路」（I-9）是后端接口面断言，界面只能承诺文案，防线本身未做。

## 六、建议 sign-off 时重点核对的三处

1. **议程环节字段名的四方打架（第二节 #1）**——这是会真漂的第 7 次候选，且跨「已签契约（stepId）/ 已实现动作词（stage.*）/
   未签需求（agenda_stage / agenda_segment_id）」三侧。**先定一个名字，再让 requirement-author 锚 testid 与字段**，
   否则 tpl 与 00-project 两个域会各锚一份。
2. **发布门槛 D-9 + 矩阵格粒度 D-10（第二节 #2、#3）**——两者都已被画进阻断态 / 写进 feature 验收断言（F22 的「拦发布」、F27 的「恰好 9 条」）。
   这两条不裁，`designer-invalid` 与 F27 的断言都可能是错的。
3. **必填清单 D-2 + 维护者归属 D-1（第二节 #5 与第三节 #3）**——前者决定「校验失败态」演示哪几项、后者决定提回屏合并权限。
   两者都是「缺数据/缺裁决」而非「缺实现」，人类给出后界面不返工，但**不给就无法把 F22 / F29 的权限与门槛断言写实**。
