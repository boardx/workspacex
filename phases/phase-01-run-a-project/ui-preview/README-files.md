# 项目文件浏览器（22-files）UI 预览 — sign-off 说明

> 路由：`/projects/[projectId]/files`（dev: http://localhost:3100/projects/demo/files）
> 代码：`apps/web/app/projects/[projectId]/files/page.tsx` + `apps/web/components/files/*` + `apps/web/lib/mock/files.ts`
> 自检：`apps/web` 下 `pnpm typecheck` 与 `./scripts/lint-design.sh` 均 exit 0。
>
> ⚠ **整个模块是原创设计**：原型只有四处计数钩子（材料准备 9 已入库 / 蓝本项目材料 9 件 /
> 分组打印素材 4 件 / 对话右栏 材料 12），没有浏览器本体。所以下面每一条设计决定都需人类逐条 sign-off。
> **我没有改任何 `ui-signoff.md` 的 status**——那是你的动作。

## 一、预览怎么走

顶部有一条「预览控制条」（仅 dev，生产不渲染），三行：
- **屏**：浏览器主屏 / 上传弹层 / 摄取进度抽屉 / 人工复核 / 版本列表 / 删除确认 / 待删除队列（`?screen=`）
- **视角**：引导师 / 组长 / 组员 / 观察者 / 合规负责人（`?as=`）——预览手段，真实权限在服务端 RLS
- **七态**：默认 / 加载 / 空 / 校验失败 / 依赖失败 / 无权限 / 成功（`?state=`，走 `StateShell`）

七态作用在**浏览器主屏的中列表区**。例：`?state=empty` 空态、`?state=dep-failed` 对象存储不可用
（预览与下载置灰并说明原因）、`?state=denied` 观察者只见已发布已脱敏、`?state=invalid` 导出超上限。

## 三、我替 UC 做的设计决定（sign-off 重点，逐条）

1. **来源树用「先展开箭头 + 再点节点名」的两段式**：箭头只管展开/折叠，节点名管筛选联动。
   UC-22.1 R8 只说「左树 = 来源类型 → agenda_segment」，没说展开与选中是否同一动作。我拆开了，
   避免「想筛却误折叠」。默认展开 `文件`/`访谈` 两类，其余折叠。
2. **系统产出 vs 上传原件用文字角标区分**（`OriginBadge`：上传原件 / 系统产出），不是靠颜色或图标。
   架构 file-first 第 1 条要求「一眼看出哪些是上传的、哪些是系统生成的」，但没规定表现形式。
3. **摄取九态用「阶梯进度条 + 每态含义一句话 + 每态出口」三件套**，刻意不做转圈圈。
   抽屉底部常驻一张「九态图例」，把「入库」这个词背后的九步全摊开（含义 / 是否可下载 / 是否已进检索）。
   这是我对「不要做成转圈圈」这条硬要求的具体兑现，请重点看它是否够清楚。
4. **`STORED` 之后即标「原件可下载」，与「已进检索」分成两个独立标记**。UC-22.2 R7 说这是两件事，
   但没给界面表达。我在每态角标旁用两个小字标（绿「原件可下载」/ 蓝「已进检索」）分别点亮。
5. **删除影响面弹窗把六类级联做成逐条清单**，并把第 ⑦ 条「已支撑已签字决策 → 通知拍板人复核」
   **单独高亮成 AI/人工色并配 `UserCheck` 图标**——沿用受访者撤回链第 04 步「通知拍板人复核而不是自动改结论」的做法。
   「确认删除」按钮在填写原因（≥4 字）前禁用；legal hold 时直接拒绝。UC-22.4 R7 要求「不是孤零零红按钮」，
   具体的版式是我定的。
6. **删除弹窗默认展示「已导出到组织外」警示**（回执须如实说明无法回收，UC-22.4 E2）。UC 要求回执如实，
   我把它前置到删除确认阶段就提示，让人删之前就知道「删了也收不回客户已下的 zip」。
7. **待删除队列的五步流程复用了受访者撤回链的五步文案**（entry mock 里 `WITHDRAWAL_FLOW` 的措辞），
   保持同一条数据流两处（受访者侧 / 合规侧）措辞一致。第 04 步（需人工）用 AI 色标出。
8. **「部分失败」态单独设计**（`files-trash-partial`）：红框 + 「未出回执」+「重试级联」按钮。
   UC-22.4 R8 明确要求这一态逐屏设计（不在七种必现态里）。请核对它是否够醒目——它是本 UC 最危险的态。
9. **上传弹层的机密勾选默认勾上并显示「继承自项目默认：是」**（O-17）；可见性四选一默认「全场」。
   预检**逐个列原因**并示范了两条被拒（`.svg` 脚本风险 / 解压炸弹），把 R10 的两个 `[待确认]`（白名单、上限数值）
   直接摆到界面上让你拍板。
10. **版本行把 SHA-256 做成可复制的等宽码 + 独立下载按钮**，每版都可下载（UC-22.4 R3.b 第 2 步「旧版仍可下载」）。
    派生物折叠在原件之下、带 `derived_from v?`、标生成器模型与版本；embedding 标「只登记不物化」。
11. **agent 上传者用 `Bot` 图标 + AI 色显示 agent 名，hover 出 `agent_run_id`**，绝不显示为某个人（UC-22.1 R7 / V10）。
12. **合规负责人视角**：由于 `identity.ts` 的项目角色枚举只有四种（引导师/组长/组员/观察者），
    合规负责人不是其中之一。我用 `?as=compliance` 这个**额外预览取值**来投影合规视角（仅前端预览层，
    不进 `resolvePreviewRole`）。待删除队列在 `facilitator` 或 `compliance` 视角可见，其余视角显示 `denied`。
    **这是我为「合规负责人」找的临时预览位，真实角色模型应由 UC-0.3 与合规确认**（见待确认清单）。

## 四、R8 线索之间的矛盾与处理

1. **入口矛盾**：UC-22.1 R8 说文件浏览器是「项目工作台新增第 8 个标签」，但 R10 又把
   「加第 8 标签 vs 并入项目筹备子标签」列为 `[待确认]` 的信息架构决策。
   → 我**不替你定标签归属**：本预览用独立路由 `/projects/[id]/files` 承载，不在导航里硬塞第 8 个图标。
   `lib/navigation.ts` 里已有的 `FILES_NAV` 指向本路由，作为入口候选，归属留给 sign-off。
2. **「不显示无权项」 vs 「空来源节点仍显示」**：R7 要求「不显示你有 N 项无权查看」（计数即泄露），
   但 R4 A5 又要求「来源节点为空也显示、标为空、不隐藏」。这两条不冲突但容易混：前者是**权限过滤后不留占位**，
   后者是**来源类型枚举恒显示**。→ 我按此实现：八类来源节点恒在（空的标「该来源存在，但还没有内容」），
   但**具体文件**被权限过滤掉时不占位、不计数提示。
3. **观察者可见性 vs 逐字记录**：UC-22.1 A2 说观察者只见已发布已脱敏；UC-22.3 R5 说 `messages.jsonl`/
   `transcript.jsonl` 默认不对观察者可见。→ 我把观察者的 `denied` 态文案写成「只见已发布且已脱敏，
   未发布/含机密/未脱敏不进结果集」，与两处一致。**但观察者是否有下载权是 R10 `[待确认]`，我没替你定**
   （下载按钮的可用性在观察者视角下仍按 happy path 显示，等你拍板后再收紧）。

## 五、建议 sign-off 时重点核对的 3 处

1. **摄取九态抽屉（`?screen=ingestion`）**——这是原型完全空白、且最容易做砸的地方。请确认：
   九态图例是否让非技术的项目负责人也能看懂「文件卡在哪、为什么、能做什么」；失败三段式（在哪步/为什么/能做什么）
   是否够用；`STORED 可下载` 与 `已进检索` 分离是否清楚。
2. **删除确认的影响面（`?screen=delete`）**——六类级联 + 第 ⑦ 条「通知拍板人复核」+「已导出无法回收」警示 +
   强制填原因。请确认影响面信息是否足够让人**在删之前就承担后果**，而不是删完才发现证据链断了。
   同时请拍板 R10 三个 `[待确认]`：能否删单个中间版本、宽限期内能否撤销、观察者/引导师的删除权。
3. **待删除队列的「部分失败」态（`?screen=trash`，看第 4 张卡）**——半完成的删除比不删更危险。
   请确认「未出回执 + 告警 + 重试」的表达是否足以阻止有人把部分失败误当完成；以及合规负责人这个角色
   在 `identity.ts` 里缺位、我用 `?as=compliance` 临时投影是否可接受，还是需要先补角色模型。
