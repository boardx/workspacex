# 第一组 · 阻塞迭代 1（不定就开不了工）

## 🔴 D-01 现场组员的身份模型

原型落地页是**手机号 + 验证码 + 名单校验**；UC-1.2 标题叫「**匿名**进场」，AC1 是「**不注册**就能发言、贴便签、投票」。两套数据模型不兼容。

| | 方案 | 优点 | 缺点 |
|---|---|---|---|
| **A** | **真匿名**：系统分配匿名名字，无手机号，一次性会话身份 | 合规最轻（不收个人信息）；现场进场最快；符合原文档 AC1 | 无法追责，产出无法归属到真人；引导师看不出谁没到；掉线换设备无法恢复身份；与原型不符 |
| **B** | **名单实名**：手机号验证 + 对照名单，但**不建账号**、展示层可用代称 | 可追责、可恢复现场、引导师能看签到；与原型一致 | 收集手机号触发个人信息合规（留存期、告知、删除）；名单需提前录入，临时加人要走申请流程 |

**我的推荐：B**。理由：产出要进决策链和组织大脑，来源必须可追溯到人；且原型已按 B 设计了「不在名单→申请加入」「换设备恢复」两条配套流程。代价是必须把手机号纳入 UC-17.2 的撤回与删除范围。

**选择：B**

## 🔴 D-03 「16 个环节」的术语两义

UC-2.1 的 AC1 是「16 个环节都能编辑并有完成度标记」；原型同时存在「**16/16 环节已配**」（设计维度完成度）和「**7 环节·3.5h / 28 环节·5d**」（运行议程环节数）。**那 16 项到底是哪 16 项，两边都没给。**

| | 方案 | 优点 | 缺点 |
|---|---|---|---|
| **A** | **术语拆开**：蓝本有固定的 **16 项设计配置**（主题句式/分组规则/组内能力/报告骨架…），议程环节数可变 | 消除歧义；AC1 的分母确定；与原型两个数字都能对上 | 必须**现在就列出那 16 项是什么**，否则 AC1 仍不可验收 |
| **B** | **取消 16 这个数**：改为「蓝本的必填配置项全部完成才能发布」，完成度按实际配置项数动态计算 | 不需要预先定义 16 项；灵活，将来加配置项不改需求 | 丢掉原型「16/16」这个明确的进度表达；不同蓝本完成度不可横向比较 |

**我的推荐：A + 立刻定义那 16 项**。我可以基于原型的「从主题句式、分组规则到组内能力与报告骨架」草拟一份 16 项清单供你增删。若你希望更快，选 B 也能开工。

**选择：B**

## 🟠 D-06 Skill 是「多文件可执行包」还是「声明式契约」

UC-3.1 写的是「上传定义（名称、输入输出、调用方式、数据范围）」且 R6 排除「任意代码无沙箱执行」；原型写的是「导入现成**仓库**」「**4 个文件**」「来源 **Codex 社区**」。**工程量差 3–5 倍。**

| | 方案 | 优点 | 缺点 |
|---|---|---|---|
| **A** | **声明式契约**：skill 是一份结构化定义（提示词模板 + 输入输出 schema + 数据范围），由平台执行 | 无需沙箱，安全面小；估点 5 点；安全扫描只需校验 schema | 表达力有限，复杂方法论（如 12 项尽调清单的逐条比对）可能写不出来；与原型的「仓库/4 个文件/社区导入」不符 |
| **B** | **多文件可执行包**：skill 是一个可运行的代码包，需沙箱隔离 | 表达力强，能承载任意方法论；与原型一致；可复用外部社区生态 | 必须做沙箱、资源限额、供应链安全；估点 13+；外部导入的可执行内容进客户环境是重大安全决策 |

**我的推荐：A 用于 phase-1，B 作为 phase-2 的能力升级**。理由：phase-1 的 6 个内置 agent（Ava/Scout/Echo/Ledger/Warden/Facilitator）用声明式足够；沙箱是独立的大工程，不该卡住迭代 2。

**选择：A**

# 第三组 · 合规（风险最高）

## ⚖️🔴 D-13 phase-1 会带着无法履行的合规承诺上线

原型的受访者同意书在 **phase-1** 就承诺「180 天后自动删除」「随时可撤回」「30 天内物理删除并回执」，但撤回执行引擎**全部在 phase-3 的 17-gov**。一旦真实受访者行使撤回权即构成违约。

| | 方案 | 优点 | 缺点 |
|---|---|---|---|
| **A** | **把 UC-17.2 的最小切片前置进 phase-1**：待删除队列 + 退出检索 + 报告段落标失效 + 回执 | 承诺与能力对齐；合规风险清零 | phase-1 +8 点；且需要 Context Engine（检索层）在 phase-1 就存在 |
| **B** | **phase-1 的同意书删掉撤回承诺**，只承诺「录音仅本场使用、180 天删除」 | 不增加 phase-1 工作量 | 削弱产品核心叙事（「被记录的人也要有一块屏」）；受访者信任度下降；且 GDPR 类法规下「撤回权」本身可能是法定权利，不是可选承诺 |

**我的推荐：A**。理由：B 在多数司法辖区可能站不住——数据主体的撤回权通常是法定的，不是产品可选项。这条建议请合规负责人拍板。

**选择：A**

## ⚖️ D-15 撤回 SLA

UC-17.2 写「24 小时内在所有位置生效」；原型是「前三步**即时**，物理删除 **30 天内**回执」。

| | 方案 | 优点 | 缺点 |
|---|---|---|---|
| **A** | **两级 SLA**：逻辑失效即时（≤5 分钟），物理删除 ≤30 天并出回执 | 用户体验好（立刻看到生效）；物理删除有操作余量；与原型一致 | 需要事件队列 + 定期清理两套机制 |
| **B** | **单一 SLA 24 小时** | 实现简单（一个批处理任务） | 撤回后 24 小时内该证据仍在检索范围，可能被 AI 引用进新结论——这是实质性的合规瑕疵 |

**我的推荐：A**。B 的 24 小时窗口期是真实风险。

**选择：A**

## ⚖️ D-16 脱敏是可逆映射还是不可逆改写

四处口径不一，且**互相矛盾**：晋升闸门要求脱敏稿与原文**双向关联可回溯原文**（原文仍在库），与「脱敏聚合」的不可逆语义直接冲突。

| | 方案 | 优点 | 缺点 |
|---|---|---|---|
| **A** | **可逆映射 + 权限门控**：原文保留，脱敏稿是视图，回溯需高权限且留痕 | 支持审计追溯；晋升闸门的「双向关联」可实现；纠错可回到原文 | 原文仍在库 = 泄露面仍在；跨客户复用时「脱敏」的法律保护力弱 |
| **B** | **不可逆改写**：脱敏时原文不进入组织层，只存脱敏稿 | 法律保护力强；跨客户复用安全 | 无法审计回溯「这条组织知识源自哪个客户」；与原型的晋升闸门设计冲突，需改原型 |

**我的推荐：A（组织层内）+ B（跨组织复用时）**——即两级：组织内部保留可逆映射，跨组织输出时做不可逆聚合，且需定义最小聚合样本量（对照 12-3 的「样本 <8 标不可推断」）。

**选择：A（组织层内）+ B（跨组织复用时）**
