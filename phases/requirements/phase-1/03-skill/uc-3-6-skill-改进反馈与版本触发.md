## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-3.6 / Skill 改进反馈与版本触发
- **Actor**：**评价人**（任何在对话里收到 AI 消息的人：引导师 / 组长 / 组员）、
  **能力维护者**（处置聚合建议、发起改进提案）、**审核人**（人工复核，见 UC-3.1 R5）
- **目标**：[原型] 让 skill 在使用中**被真实反馈驱动着变好**——
  单条消息上的 👎 汇聚成可执行的改进建议，一键生成契约变更提案，
  经**人工复核**后合入成为新版本上线，并用**满意度百分比**衡量效果。
- **本用例结果**：
  1. 每条 AI 消息可被 👍/👎 评价，评价与**产生它的 skill 版本**绑定；
  2. 后台「反馈与迭代」聚合出带计数的改进建议（原型：`打断时机过早 👎9`）与原始案例清单；
  3. `[生成 skill 改进 PR]` 产出一份契约 diff 提案；
  4. **人工复核通过后**触发 UC-3.4 的发新版流程上线；
  5. Skill 库的**满意度百分比**随之更新。
- **系统边界**：消息级评价采集、评价 → skill 版本归因、改进建议聚合与命名、
  原始案例回溯、改进提案生成与 diff 呈现、人工复核门禁、版本触发、满意度指标计算、迭代看板。
- **核心数据对象**：消息级评价（👍/👎 + 可选理由）、评价归因（消息 → agent → skill → 版本）、
  改进建议（聚合项）、原始案例集、改进提案（契约 diff）、复核记录、
  满意度指标、迭代闭环统计。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

### 阶段一 · 采集与归因

1. **评价人操作**：对一条 AI 消息点 👎（可选填一句理由）。
   **系统响应**：记录评价，并**绑定完整归因链**——消息 ID、agent、**skill 与其版本**、
   环节、项目、时间、评价人。
   [设计] 评价对同线程其他人**不公开署名**（对照 D-40「保留意见去掉署名」的同源原则）；
   **[待确认]** 评价是否对本人可见可撤销。
2. **系统处理**：把评价投影到两个消费者：
   - **Skill 库的满意度百分比**（[原型] 94% / 91% / 88% / 86% / 90%）；
   - **反馈与迭代的聚合队列**。

### 阶段二 · 聚合成改进建议

3. **系统处理**：把同一 skill 上语义相近的 👎 聚合成**一条命名建议**。
   [原型] 聚合项的呈现形态是四段：
   - **对象与问题名**：`FC Facilitator·打断时机过早`
   - **计数**：`👎9`
   - **人群与现象**：「9 位主持人反馈：在讨论未收敛时就提示投票。」
   - **可执行的改进建议**：「建议把「提议收敛」的触发阈值从 **3 次重复提及**提高到
     **5 次**，并**要求先征询主持人**。」
   [设计] 聚合与建议文案由 AI 生成，**必须标识为机器产出**并可展开原始案例核对；
   [原型] 附 `[看 12 个原始案例]`——**注意计数不等**（👎9 但 12 个案例），
   说明案例集包含未点 👎 但被判定为同类的实例，[设计] 两个数字必须分别标注口径，不得混用。
4. **系统处理**：对**已定位到实现层**的问题不生成 skill 改进提案。
   [原型] 反例：`SC Scout·引用页码偶发错位 👎4 —— PDF 双栏排版下页码定位偏移 1 页。
   **已定位到解析器，等待修复。**`——这类进的是**软件反馈**通道，不是 skill 契约变更。
   [设计] 因此聚合项需带**归类**字段：`skill 契约可解` / `实现层缺陷` / `模型能力所限`。

### 阶段三 · 生成改进提案

5. **能力维护者操作**：对一条 `skill 契约可解` 的聚合建议点 `[生成 skill 改进 PR]`。
   **系统响应**：基于建议内容与原始案例，产出一份**契约变更提案**——
   对现行版本 `vN` 的**提示词模板 / 输入输出 schema / 参数阈值**给出 **diff**
   （原型示例的改动即「阈值 3 → 5」＋「新增：先征询主持人」两处）。
   提案落为 `vN+1 · 草稿`，**不改动 `vN`**。
6. **能力维护者操作**：可在提案上手工编辑后再提交。
   **系统响应**：保留「AI 起草 / 人工修改」两段留痕，改动可逐条对照。

### 阶段四 · 人工复核与上线

7. **审核人操作**：**人工复核**（[原型]「开发 Agent 提交，**人工复核通过**，已灰度 100%」；
   「9 条已生成改进 PR → **6 条人工复核通过并上线**」）。
   **系统响应**：复核即 UC-3.1 的**方法论审核**——`[批准发布]` 则走 UC-3.4 的发新版流程：
   `vN+1` 上线、`vN` 自动归档、**已建实例锁在自己的版本上**；`[退回]` 则附理由回到草稿。
   [设计] **硬约束：AI 生成的改进提案不得自动上线**，与 UC-3.5 的
   「自动生成不等于自动发布」同源。
8. **系统处理**：上线后开始**效果观测**——
   [原型] 闭环指标：「本月 14 条反馈 → 9 条已生成改进 PR → 6 条人工复核通过并上线 →
   **相关 skill 满意度平均 ＋7 个百分点**」。
   [设计] 新版本上线后的评价单独统计，与旧版对比给出满意度变化。
9. **系统收口**：校验 AC1「每条 AI 消息可被评价，且评价能追到产生它的 skill 版本」、
   AC2「改进提案未经人工复核不得上线」；记录评价、聚合、提案、复核、上线全链路进审计。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[原型] 归类为 `实现层缺陷` 的反馈转入**软件反馈**通道（原型左栏的
    `[缺陷]` / `[需求]` / `[已修复]` 三态、票数、`[推送到开发 Agent]` `[查看附件]`），
    **不生成 skill 改进提案**。
    **[设计]** 软件反馈通道本身属产品运营范围，phase-1 只做**分流**与跳转，不做实现。
  - A2：[设计] 归类为 `模型能力所限` 的建议，出口是**换模型**（20-model）而非改契约；
    提示维护者到 skill 的模型选择里调整（可选池只含已启用模型，见 UC-9.2）。
  - A3：[设计] 队列为空或某 skill 无负向评价时展示真实空态（大意：暂无待处置建议），
    **不生成示例建议**。
    ⚠ 括号内为**待定的设计文案，不是原型原文**——原型每屏都填满样例数据、**零空态**，
    此前给它加引号冒充原型原文是错的，已去掉引号。
  - A4：[设计] 一条聚合建议可被**忽略/关闭**并填理由；关闭后同类新评价重新累计，
    达阈值再次浮现（避免被一次性关掉后永久沉默）。
  - A5：[设计] 同一 skill 同时存在多条待处置建议时，可合并为一次改版
    （一次 `vN+1` 解决多条），复核时逐条对照。
  - A6：[原型] `[打开迭代看板]` `[导出]` 提供闭环的看板视图与导出；
    **[设计]** phase-1 至少保证四个计数可读：反馈数 / 已生成提案数 / 复核通过并上线数 /
    满意度变化。
- **异常流程**：
  - E1：[设计] 评价无法归因（消息缺 skill 版本记录）时，该评价**只计入 agent 级**，
    不计入任何 skill 的满意度，并在数据质量报表中列出；
    **不得随意归给某个 skill**。
  - E2：[设计] 聚合建议的原始案例含**客户机密**时，案例视图按权限门控展示；
    无权者只见计数与脱敏摘要（对照 D-16、D-18）。
  - E3：[设计] 改进提案破坏了输入输出 schema 的兼容性时，必须在复核界面显著标出，
    并列出会受影响的蓝本绑定与进行中项目（复用 UC-3.4 的引用清单）。
  - E4：[设计] 提案生成用的模型不可用时明确失败并保留聚合建议，
    **不得产出半截 diff 当成提案**。
  - E5：[设计] 复核通过但发版失败（依赖不可用）时，`vN` 保持生效，
    提案回到「待上线」并可重试；**不得出现「已复核但没人知道没上线」的静默失败**。
  - E6：[设计] 同一 skill 被并发发起两份改进提案时不静默覆盖；
    提示已有待复核提案，出口为「合并」或「排队」。
  - E7：[设计] 评价被刷（同一人重复评价、异常集中评价）时按 UC-4.4 的异常检测口径处理，
    可疑评价标记后不计入满意度，处置留痕。

## R5 权限与可见性

- **评价人**（引导师 / 组长 / 组员，任何能看到该 AI 消息的人）：
  可对消息 👍/👎 并填理由；**只能评价自己看得到的消息**。
  [设计] 不可见他人的评价明细。
- **能力维护者**：可见聚合建议与原始案例（受机密门控）、可 `[生成 skill 改进 PR]`、
  可编辑提案；**不能自行复核上线**。
- **审核人**：行使人工复核 `[批准发布]` / `[退回]`；**提交人 ≠ 复核人**（沿用 UC-3.1 A4）。
- **观察者**：不可评价、不可见反馈与迭代面。
- **项目负责人**：可见本项目内的评价聚合摘要（不含个人署名）与相关 skill 的满意度；
  写操作需显式授权。
- **组织管理员**：可见全组织的反馈与迭代面与闭环指标；
  [D-18] 涉及个人层内容时只见计数，读项目内容需留痕且对项目负责人可见。
- **可见性范围**：某 skill 的反馈只对其可见性范围内的维护者可见
  （「仅能源组」的 skill，其反馈不对平台组维护者呈现）。
- 未登录、链接失效或未列出的角色：默认无权限；接口不得返回越权数据。

## R6 后置条件 / 不包含

- **正常后置条件**：
  - 每条 AI 消息的评价与其**skill 版本**绑定，可双向追溯。
  - 反馈与迭代面呈现带计数、带原始案例、带归类的聚合建议。
  - 改进提案以 **diff** 形式可读，AI 起草与人工修改分段留痕。
  - 复核通过后按 UC-3.4 发新版上线，旧版自动归档，已建实例锁版本。
  - [Backlog验收] AC1：每条 AI 消息可被评价，且评价能追到产生它的 skill 版本。
    （[原型] 已写实**消息级评价**的存在与聚合结果——「Agent / Skill 改进反馈（来自消息级评价）」
    `FC Facilitator·打断时机过早 👎9`；**「追到 skill 版本」的链路原型未渲染**。）
  - [设计验收] AC2：**改进提案未经人工复核不得上线**；绕过复核的接口调用被拒绝并记审计。
  - [设计验收] AC3：Skill 库的**满意度百分比**由真实评价计算，口径可解释、样本量可见；
    样本不足时显示「样本不足」而非一个漂亮数字。
  - [设计验收] AC4：`实现层缺陷` 类反馈**不生成 skill 改进提案**，分流到软件反馈通道。
- **失败后置条件**：
  - 不产生「已复核未上线且无人知晓」的静默失败；不产生无归因的满意度数字。
- **不包含**：
  - **[D-06] 任意代码无沙箱执行**；phase-1 的「改进 PR」不是代码 PR。
  - **软件反馈通道的完整实现**（缺陷/需求/已修复三态、票数、推送到开发 Agent、灰度发布）
    ——原型存在但属产品运营范围，phase-1 只做分流与跳转。
  - **灰度发布**（原型「已灰度 100%」）——[设计] phase-1 的 skill 上线是全量切版本，
    灰度能力**列为 phase-2**。
  - Skill 的创建与首次发布——见 UC-3.1；版本与停用机制——见 UC-3.4（本用例触发它）。
  - 晋升生成 skill——见 UC-3.5（另一条来源）。
  - **Agent 级**的改进（原型的聚合项同时覆盖 agent，如 `FC Facilitator`）——
    [设计] 本用例只处理**可由 skill 契约解决**的部分；
    agent 行为参数的改动走 04-agent。**[待确认]** 两者的边界需产品确认。
  - 组织级审计检索屏（D-34）。

## R7 业务规则（不随具体实现变化的硬性约束）

- **[原型]** 改进反馈的来源是**消息级评价**，不是问卷、不是工单。
- **[设计]** 评价必须记录到 **skill 版本粒度**；无法归因的评价不计入任何 skill 的满意度。
- **[原型]** 闭环形态固定为：**反馈 → 生成改进提案 → 人工复核 → 上线 → 满意度变化**。
- **[原型 · 硬约束]** **人工复核是必经环节**——「开发 Agent 提交，**人工复核通过**」；
  AI 生成的改进不得自动上线（与 UC-3.5 同源）。
- **[设计]** 提交人 ≠ 复核人。
- **[原型]** 已定位到实现层的问题（如解析器缺陷）**不走 skill 改进**，进软件反馈通道。
- **[设计]** 聚合建议与 diff 提案由 AI 产出，**必须标识为机器产出**并可展开原始案例核对；
  来源不足时不得伪造结论。
- **[设计]** 满意度百分比必须有可解释口径与最小样本量；样本不足显示「样本不足」。
- **[原型]** 👎 计数与原始案例数可以不等（👎9 / 12 个案例），两个口径必须分别标注。
- **[设计]** 破坏 schema 兼容性的改进必须在复核界面标出并列出受影响的引用。
- **[D-40 同源]** 评价不公开署名，聚合展示只给计数与人群描述（「9 位主持人反馈」）。
- 所有权限判断必须在服务端执行；隐藏入口只是界面表现，不构成安全控制。
- 评价、聚合处置、提案生成、复核、上线都必须记录审计事件，并显示动作影响范围。

## R8 界面线索

- **前端入口（采集侧）**：对话屏 AI 消息上的 👍/👎。

## R9 非功能约束

- **性能/规模预期**：
  - [设计] 评价写入必须轻量、不阻塞对话；聚合可按小时批处理。
  - [设计] 规模量级参照原型：本周 23 条软件反馈 + 14 条 agent/skill 改进建议，
    单条聚合下 12 个原始案例；案例列表需分页。
  - [设计] 提案生成属后台任务，超过 10 秒转异步并给出进度与通知回执。
- **安全/隐私/合规**：
  - 评价**不公开署名**；聚合只给计数与人群描述。
  - 原始案例含客户数据时按权限门控与脱敏策略展示（D-16、D-18）。
  - 评价与案例的保留期不短于审计保留期（D-14）。
  - 提案生成若把原始案例喂给模型，**含机密的案例只走自托管模型**（UC-9.3 硬路由）。
- **兼容与降级要求**：
  - 响应式 Web；**评价控件在移动端必须可用**（现场组员多用手机）。
  - 提案生成模型不可用时明确失败，不得产出半截 diff。

## R11 切分提示（给 requirement-author）

- 建议拆分顺序：
  1. 消息级评价采集 + 归因链（消息 → agent → skill → **版本**）
  2. 满意度指标计算（含最小样本量与「样本不足」态）
  3. 聚合成改进建议（计数 / 人群描述 / 建议文案 / **归类**）+ 原始案例回溯
  4. 分流：`实现层缺陷` → 软件反馈通道（只做跳转）
  5. `[生成 skill 改进 PR]` → 契约 diff 提案（AI 起草 + 人工编辑留痕）
  6. 人工复核门禁 + 提交人≠复核人 + 绕过被拒
  7. 触发 UC-3.4 发新版上线 + 「待上线」失败重试
  8. 闭环指标与迭代看板（四个计数）
  9. 审计 + 自动化验收
- 第 1、2 项是**其它一切的前提**（没有归因就没有满意度、没有聚合），应最先做。
- 「改进提案未经人工复核不得上线」应单独成 feature 并有**绕过尝试被拒绝**的验收。
- **优先级 / 先后依赖**：P1；5 点；迭代 5；依赖 UC-3.1、UC-3.3、UC-3.4。

## R12 AI Ready 验收线索

- V1（成功态）：AC1 —— 对一条 AI 消息点 👎，该评价可追到产生它的 agent、skill 与 **skill 版本**。
- V2（聚合态）：同一 skill 上 9 条同类 👎 聚合成一条带计数与建议文案的条目，
  `[看 N 个原始案例]` 能打开对应案例集，且 👎 计数与案例数的口径分别标注。
- V3（门禁态）：AC2 —— 生成的改进提案在未经人工复核时不上线；
  直接调接口置为生效被拒绝并记审计。
- V4（门禁态）：提交提案的人尝试自行复核被拒绝，提示需另一名审核人。
- V5（指标态）：AC3 —— Skill 库的满意度百分比可点开看口径与样本量；
  样本不足时显示「样本不足」而非数字。
- V6（分流态）：AC4 —— 归类为 `实现层缺陷` 的条目上**不出现** `[生成 skill 改进 PR]`，
  只提供软件反馈通道入口。
- V7（版本态）：复核通过后 `vN+1` 上线、`vN` 自动归档，进行中的项目仍按锁定版本运行。
- V8（兼容性态）：提交一个破坏 schema 的改进，复核界面显著标出并列出受影响的蓝本与项目。
- V9（归因失败态）：构造一条缺 skill 版本记录的消息评价，它只计入 agent 级，
  不计入任何 skill 的满意度，并出现在数据质量报表里。
- V10（机密态）：原始案例含客户机密时，无权者只见计数与脱敏摘要；
  提案生成把机密案例送模型时走自托管模型。
- V11（失败显式态）：模拟发版失败，提案停在「待上线」并可重试，且有明确通知。
- V12（权限态）：逐一使用 评价人 / 能力维护者 / 审核人 / 项目负责人 / 观察者 /
  未授权用户访问，可读数据与可执行动作严格符合 R5。
- V13（防刷态）：同一人对同一消息重复评价只计一次；异常集中评价被标记且不计入满意度。
- V14（审计态）：评价、聚合处置、提案生成、复核、上线可按操作者、时间、skill 版本检索。
