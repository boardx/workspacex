# 原始需求（细化）— UC-2.3 把一次项目的改动提回蓝本

> 所属：阶段一 · 能跑完一场项目 / M2 · 蓝本 项目模板  
> 来源：`Backlog Use Case.html` 的 UC-2.3；UI 线索来自 `WorkspaceX Standalone.html`。  
> **深层原型来源（本次修订依据）**：蓝本设计器「套用后会初始化什么」一览底部的硬规则
> （`proto-05-deep-layer.md` 第二节）——**「写入的是默认值。引导师在那一场里改，不会回写蓝本；
> 要沉淀就在复盘里『提交回蓝本』。」** 这一句把本用例的**入口路径**定死为「复盘 → 提交回蓝本」，
> 也确认了它是项目改动流回蓝本的**唯一合法通道**。
>
> **⚠ 证据边界（整份重标依据）**：上面那**一句话是本用例在原型里的全部证据**。
> 「勾选偏离项 → 写理由 → 生成待审改动 → 方法负责人合并」这条主流程，

> **原型运行态没有任何对应界面**。故本文除「入口路径 ＝ 复盘 →『提交回蓝本』」外，
> 主流程与规则一律标 **[Backlog]**，不得当作原型证据实现。  

> 口径（四标记）：**[原型]** ＝ `WorkspaceX Standalone.html` **运行态实际存在**的行为（有界面可查，依据 scratchpad 的 proto-01~10 抽取档案）；**[Backlog]** ＝ `Backlog Use Case.html` 的**文档要求**（原型未必实现）；**[设计]** ＝ 依据前两者反推补全，**需人类确认**；**[待确认]** ＝ 不应由实现者自行决定。

## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-2.3 / 把一次项目的改动提回蓝本
- **Actor**：**引导师**（提出回提）、**方法负责人**（蓝本维护者，唯一有权合并的人）
- **目标**：[Backlog] 把一场项目里被证明有效的偏离沉淀回蓝本，形成新版本的**待审改动**。
  [原型] 这是 UC-2.2 硬规则「改动不回写蓝本」的**唯一例外通道**——原型原话：
  **「写入的是默认值。引导师在那一场里改，不会回写蓝本；要沉淀就在复盘里『提交回蓝本』。」**
  （**只有这一句是原型证据；「待审改动」四字原型零命中**。）
- **本用例结果**：[Backlog] 引导师在**复盘**里勾选值得沉淀的偏离项并写明理由，
  生成挂在蓝本上的**待审改动**；方法负责人合并后进入蓝本下一版本（发布仍走 UC-2.1）。
- **系统边界**：项目侧的偏离清单与勾选提交、蓝本侧的待审改动收件与合并、来源追溯（哪一场、为什么）。
- **核心数据对象**：**偏离项**（项目实例值 vs 蓝本快照值的差）、**回提建议**（含理由与来源项目）、
  蓝本、蓝本版本、项目蓝本快照。

## R2 前置条件 / 触发条件

- **前置条件**：
  - 用户已建立可校验的正式或临时身份，且拥有目标组织、项目、小组或资源的访问权。
  - 目标资源存在且未被删除/冻结；依赖能力“登录管理（谁能编辑与发布蓝本）”可用，或界面能明确显示其不可用状态。
  - 若动作涉及个人数据、录音、原始材料或跨范围读取，相应授权与留存策略已生效。
- **触发条件**：
  - [原型] 项目复盘后，引导师认为某处调整值得沉淀。
  - [原型] 入口路径由蓝本设计器的说明句定死：**复盘 → 「提交回蓝本」**。
    这是产品对外承诺的唯一沉淀路径，实现**不得**改成「在项目筹备页直接编辑蓝本」
    或「系统自动合并高频偏离」。
  - 进入时携带：当前组织、项目 ID、**该项目绑定的蓝本 ID + 版本快照**、操作者角色。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

> **本节步骤 1–4 全部为 [Backlog] 口径**（Backlog UC-2.3 的 `flow` 三条 + `edge` 两条），
> 原型只提供了入口路径这一句。

1. [Backlog] **引导师操作**：在复盘里点「**提交回蓝本**」（**入口路径本身有原型依据**）。
   **系统响应**：把该项目的当前值与
   **绑定的蓝本版本快照**做 diff，**按配置项定义表逐项**列出偏离
   （议程环节的增删改归到第 2 项「流程 Agenda」名下），每条标明「蓝本原值 → 本场实际值」。
   （Backlog 原文只有「列出这场里所有偏离蓝本的改动」；diff 基准与呈现粒度为本文补全的 [设计]。）
2. [Backlog] **引导师操作**：勾选要沉淀的项，**每条写一句为什么**（Backlog 原文
   「勾选要沉淀的项，写一句为什么」）。**系统响应**：[设计] 理由为必填；
   校验身份与项目范围；未勾选的偏离项不产生任何蓝本侧记录。
3. [Backlog] **引导师操作**：提交，生成蓝本侧的**待审改动**（Backlog 原文
   「生成蓝本新版本的待审改动」）。**系统响应**：[设计] 待审改动挂到目标蓝本上，
   **不直接改蓝本内容、不生成新版本**；每条携带来源项目、时间、提出人、理由与原值/新值。
4. **方法负责人操作**：在蓝本侧审阅待审改动，逐条接受或拒绝。**系统响应**：
   [Backlog] **只有蓝本维护者能合并**（Backlog `edge` 原文）；
   [设计] 接受后改动进入蓝本草稿，发布仍走 **UC-2.1** 的门槛（必填完成 ∧ 已试跑）。
   [Backlog] 同一处被多场改过时**并排显示各自理由**（Backlog `edge` 原文）。
5. **系统收口**：校验 AC1「能看到某条蓝本规则是从哪一场、因为什么改的」——
   合并后的蓝本字段必须可反查到来源项目与理由；记录操作者、时间、对象、结果与来源。

> **[待确认] 本节步骤 1–3 的界面尚未探明**：复盘屏（含偏离清单的实际呈现）在本轮原型抽取中
> **未被点开**；步骤 4 的蓝本侧收件面（待审改动列表）在**已探明区域内确认缺失**——
> 蓝本设计器整屏与蓝本列表页均无「待审改动」入口。二者性质不同，见 R10。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[Backlog] **只有蓝本维护者能合并**。[设计] 非维护者提交后停在「待审」，
    可查看进度但不可合并；界面须明确告知「已提交，等待 <维护者> 审阅」，
    不得让提出人误以为已生效。
  - A2：[Backlog] **同一处被多场改过时并排显示各自理由**，[设计] 由维护者逐条判断；
    系统不做自动择一、不按时间覆盖。
  - A3：[设计] 偏离清单为空（本场完全照蓝本跑）时显示真实空态，不强行凑条目。
- **异常流程**：
  - E1：[设计] 请求超时、网络中断或依赖不可用时，保留用户当前输入与最后成功数据，明确失败原因，并提供安全重试。失败不得被呈现为成功，也不得产生无法追溯的半成品。
  - E2：[设计] 同一资源被并发修改时不得静默覆盖；系统提示版本已变化，并允许刷新、对比或重新提交。失败不得被呈现为成功，也不得产生无法追溯的半成品。
  - E3：[设计] 权限在操作过程中被撤回时立即终止后续写操作；已完成步骤按审计规则保留，未提交输入留在本地草稿并提示重新授权。

## R5 权限与可见性

- **引导师**：可发起、查看并管理本 use case，范围限定在其有权访问的组织、项目或小组。
- **方法负责人**：可在被授权范围内参与流程并查看与自身角色相关的结果。
- **观察者**：默认不能发起或修改；仅当内容已发布且授权范围允许时只读查看脱敏结果。
- **项目负责人**（组织角色，原文档写作「项目经理」；见 UC-0.3 角色本体：组织角色 × 项目角色两层正交）：
  可查看项目级状态与审计摘要；是否可代替业务 Actor 执行写操作需由角色模板显式授权。
- **未登录、链接失效或未列出的角色**：默认无权限；接口不得返回越权数据，不能只依赖前端隐藏。

## R7 业务规则（不随具体实现变化的硬性约束）

- [原型] **项目内改动不回写后台本体**——同一规则在原型有两处同义表述：
  「引导师在那一场里改，**不会回写蓝本**；要沉淀就在复盘里『提交回蓝本』」（蓝本设计器）
  ＋「改动**只影响这场项目，不会动后台的模板本体**」（项目设置 → 工作流编排，`proto-08`）。
- [原型] **沉淀回后台只有两条显式路径**，本用例是其中之一：
  ① **复盘 → 「提交回蓝本」**（本用例）：产生**已有蓝本的待审改动**，由维护者合并；
  ② 工作流编排 → **`[另存为组织模板]`**（属 UC-2.2）：产生**一份新的组织级模板**。
  两者**都不就地修改后台本体**；系统不得提供任何绕过这两条路径的旁路
  （含自动合并、批量同步、在项目筹备页直接编辑蓝本）。
  [待确认] 二者的分工边界与产物归属（另存出来的是工作流模板还是蓝本），见 UC-2.2 R10。
- [Backlog] **提交 ≠ 生效**：回提产生的是**待审改动**，不改变蓝本当前内容，也不生成新版本
  （Backlog 原文「生成蓝本新版本的待审改动」；「不生成新版本」是本文的 [设计] 补全）。
- [Backlog] **只有蓝本维护者能合并**（Backlog `edge` 原文；原型无合并界面、无维护者角色）。
- [Backlog] 同一处被多场改过时**并排显示各自理由**（Backlog `edge` 原文），
  [设计] 不做自动择一、不做后写覆盖。
- [设计] **理由必填**：没有「为什么」的偏离不允许提交——蓝本规则的可追溯性靠这一句支撑。
- [设计] 回提以**项目绑定的蓝本版本快照**为 diff 基准；若蓝本已发布到更新版本，
  待审改动仍记录其原始基准版本，合并时由维护者判断是否仍适用。
- AC1：能看到某条蓝本规则是从哪一场、因为什么改的。
- AI/Agent 生成的候选内容必须标识为机器产出，展示可追溯来源；来源不足时不得伪造结论。
- AI/Agent 的写回、覆盖、发布或高影响工具调用必须遵守原型中的批准点；未经确认只保留为草稿或候选。
- 所有权限判断必须在服务端执行；隐藏入口只是界面表现，不构成安全控制。
- 任何覆盖、删除、撤销、签署、发布、写回或停用动作都必须记录审计事件，并显示动作影响范围。

## R9 非功能约束

- **性能/规模预期**：
  - [设计] 普通读取与本地校验应在 1 秒内给出可感知反馈；超过 1 秒显示加载状态，超过 10 秒的任务转为可离开页面的后台任务。
  - [设计] 列表、图谱、转写和审计记录必须分页或增量加载，禁止一次加载整个项目历史。
- **安全/隐私/合规**：
  - 最小权限、组织/项目/小组隔离、传输与静态加密、敏感字段脱敏、导出与 AI 读取留痕。
  - 原始材料、录音、转写、私聊、个人身份与客户数据按授权和留存策略处理。
- **兼容与降级要求**：
  - 响应式 Web；桌面端提供完整能力，移动端保证加入、查看、输入、投票/确认等现场关键动作。
  - WebSocket/实时通道不可用时降级为轮询并显示“非实时”；断网允许保留未提交输入，但不得伪装已同步。

  若「蓝本 ＝ 工作流模板」（见 UC-2.2 R10 的待确认项）则两条路径可能需要合并。
- **[待确认]** 偏离 diff 是否覆盖**环节 × 三角色编排矩阵**的格级改动
  （`proto-08` 的矩阵是项目内可改的结构之一）；若覆盖，diff 粒度到「格」还是「环节行」。
- **[待确认]** 待审改动的生命周期：能否撤回、有无过期、被拒绝后是否通知提出人。
- **[待确认]** 同一处被多场改过时，并排显示的**排序与冲突判定规则**（按时间？按项目满意度？）。
- **跨模块契约**：身份与权限、来源引用、版本、任务状态、审计事件和通知必须使用统一标识，避免同一对象在各模块成为不可关联的副本。
- **技术约束**：[原型] 产品为响应式网页；完整离线模式、原生移动端、第三方 IM 与产品内自助计费在 backlog 中明确为范围外。
- **[待确认]** 单项目并发人数、组织数、材料量、音频时长和历史数据量尚未给出；容量与压测指标需在开发前定稿。
- **[待确认]** 通知渠道、消息模板、语言与时区策略未统一定义；本文仅承接原型明确写出的产品内/邮件行为。
- **[待确认]** 模型选择、提示词版本、质量阈值与人工复核责任人尚未指定。

## R11 切分提示（给 requirement-author）

- 建议先拆“领域数据与权限 → 主流程服务 → 页面与状态 → 跨模块回流 → 审计/通知 → 自动化验收”。
- 单个 feature 应能在一次会话内实现并验证，不应把本 use case 的全部前后端与所有异常态塞进一个 feature。
- **切分前置**：本用例两侧的屏一个**未探明**（项目侧复盘）、一个**确认缺失**（蓝本侧收件面），
  requirement-author 生成 feature 时**不得**为这两处编造 `data-testid` 锚点；
  建议先只切「偏离 diff 服务 + 待审改动数据模型 + 合并权限」三个不依赖具体屏的 feature，
  UI feature 留到补抽取/补画之后。
- **优先级 / 先后依赖**：P1；3 点；迭代 5 · 收尾项；**必须在 UC-2.2 之后**（依赖快照绑定）；
  先满足登录管理与「蓝本维护者」角色定义。
- 对 P1 能力可在主链路稳定后实现，但合入时仍需覆盖本文全部验收状态。

## R12 AI Ready 验收线索

以下行为应可由自动化测试、接口断言或可复现人工步骤验证：

- V1（成功态 · AC1）：合并后的蓝本字段可反查到**来源项目 + 提出人 + 时间 + 理由原文**，
  四者缺一即失败。
- V2（偏离清单）：在项目内改动 3 处（分属不同的设计配置项），断言偏离清单**恰好列出这 3 条**，
  每条含「蓝本原值 → 本场实际值」，未改动项不出现。
- V3（提交 ≠ 生效）：提交回提后断言**蓝本内容与版本号均未变**，只新增一条待审改动。
- V4（理由必填）：不填理由的提交被拒绝。
- V5（合并权限）：非蓝本维护者（含提出回提的引导师本人）调用合并接口被拒绝并写审计。
- V6（多场冲突）：两场项目对**同一处**提回不同改动，断言两条**并排显示各自理由**，
  不发生后写覆盖或自动择一。
- V7（唯一通道）：扫描接口面，断言**不存在**从项目上下文直接写蓝本的路径；
  在项目内的任何改动都不影响蓝本（与 UC-2.2/V4 互为镜像断言）。
- V8（权限态）：逐一使用 引导师、方法负责人、观察者、未授权用户访问；返回数据和可执行动作严格符合 R5。
- V3（空态）：无目标数据时显示真实空态与下一步，不生成伪数据。
- V4（依赖失败）：模拟网络/外部依赖失败，输入和最近成功数据保留，错误可解释且可重试。
- V5（并发态）：两名用户修改同一资源时不静默覆盖，并可识别最终版本。
- V6（审计态）：关键动作可按操作者、时间、对象和结果检索；越权尝试也有安全审计记录。
