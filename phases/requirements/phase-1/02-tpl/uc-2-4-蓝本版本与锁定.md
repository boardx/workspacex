## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-2.4 / 蓝本版本与锁定
- **Actor**：**方法负责人**（发布/归档/回滚）、**引导师**（读版本、按版本新建项目）
- **目标**：[原型] 让蓝本可以放心地改——**「改动生成 v5，已开过的项目锁在自己的版本上」**。
  改蓝本永远不会追溯性地改动任何已经开过的项目。
- **本用例结果**：[原型] 每次发布生成 v(n+1) 并记录改了哪几项设计配置；旧版自动归档但
  **已建实例记着自己用的是哪个版本**；每个项目页显示自己用的蓝本与版本（如 `蓝本 HMW 定题 v4`）。
- **系统边界**：**蓝本列表页**（版本、状态、元数据、行操作）、版本发布与归档、
  **快照绑定与锁定**、回滚、项目页的版本显示。
- **核心数据对象**：蓝本、**蓝本版本**（含版本差异：改了哪几项设计配置）、
  **项目蓝本快照**（项目 → 版本的不可变引用）、蓝本列表元数据（用过 N 次 / 满意度 /
  完成度 n/N / 议程环节数与时长）。

## R2 前置条件 / 触发条件

- **前置条件**：
  - 用户已建立可校验的正式或临时身份，且拥有目标组织、项目、小组或资源的访问权。
  - 目标资源存在且未被删除/冻结；依赖能力“登录管理（谁能编辑与发布蓝本）”可用，或界面能明确显示其不可用状态。
  - 若动作涉及个人数据、录音、原始材料或跨范围读取，相应授权与留存策略已生效。
- **触发条件**：
  - [原型] 蓝本被修改并发布。
  - 系统从 **蓝本列表** 进入本流程，并携带当前组织、项目、小组、角色和资源标识。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

1. **系统处理**：发布生成 **v(n+1)**，记录**改了哪几项设计配置**（不是「改了哪些环节」——
   见术语三分）。[原型] 设计器版本条同步为 `v5 已发布`，并始终呈现语义提示句
   **「改动生成 v5，已开过的项目锁在自己的版本上」**。
2. **系统处理**：**旧版自动归档**。[原型 · 类比证据待确认] 同一后台的画布模板对此有明确原话：
   「**发布新版本时旧版自动归档，但已经建出来的画布不会被改动——它们记着自己用的是哪个版本。
   归档只影响『还能不能新建』。**」→ 蓝本按同一规则：**归档只影响「还能不能用它新建项目」，
   不影响任何已建项目**（是否完全同规则见 R10 [待确认]）。
3. **引导师操作**：打开一个进行中的项目。**系统响应**：[原型] 项目仍按**自己绑定的版本快照**
   运行，结构不变；项目头部显示 `蓝本 HMW 定题 v4`（原型项目列表真实字段）。
4. **引导师操作**：新建项目。**系统响应**：默认用**最新已发布版本**；已归档版本不出现在可选列表。
5. **方法负责人操作**：在**蓝本列表页**查看与管理。**系统响应**：[原型] 每行呈现完整元数据与操作：

   | 字段 | 原型示例 | 说明 |
   |---|---|---|
   | 名称 | `HMW 定题项目` | — |
   | 状态与版本 | `已发布 v4` / `草稿` | 草稿态不显示版本号 |
   | **议程环节数 · 时长** | `7 环节·3.5h`、`28 环节·5d`、`4 环节·90m`、`16 环节·2d` | **随时长档位变，不是 16 项** |
   | **用过 N 次** | `用过 12 次` / `21 次` / `3 次` | 试跑不计入（见 UC-2.1 第 8 步） |
   | **满意度评分** | `满意度 4.6` / `4.1`（5 分制） | 来源见 R10 [待确认] |
   | **设计配置完成度** | `16/16 环节已配`、`15/16`、`13/16`、`12/16`、`9/16` | **＝ 设计配置项的完成度**；文案中的「环节」按 D-03 应正名为「项」。**分母取自配置项定义表**（原型标 16、实际枚举 15，见 UC-2.1 ⚠） |
   | 草稿态提示 | `试跑一场后才能发布`、`场地与打印素材两节待清空` | 发布门槛与待办说明 |
   | **行操作** | **`[编辑设计 →]` `[⧉ 复制]` `[× 删除]`** | 复制产生独立新蓝本；删除见 R10 [待确认] |

   页头统计：`项目蓝本（7 个 · 5 已发布 · 2 草稿）`。

6. **系统收口**：校验 AC1「每个项目页能显示自己用的是哪个蓝本版本」。
7. **系统收口**：校验 AC2「**已开过的项目锁在自己的版本上**」——发布新版后，
   存量项目的绑定版本与结构均不变。
8. **系统收口**：校验 AC3「归档只影响能不能新建，不影响已建项目」；
   记录操作者、时间、对象、结果与来源。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[原型] **回滚只允许回到未被任何进行中项目使用的版本**；不满足时明确列出
    「哪些进行中项目正用着该版本」，不得只给一句失败提示。
  - A2：[原型] **`[⧉ 复制]`**：产出一份独立的新蓝本草稿，不与源蓝本共享版本线。
  - A3：[待确认] **`[× 删除]`**：已被项目套用过的蓝本能否删除、快照如何处理尚未裁决，
    见 R10；裁决前该动作不得实现。
- **异常流程**：
  - E1：[设计] 请求超时、网络中断或依赖不可用时，保留用户当前输入与最后成功数据，明确失败原因，并提供安全重试。失败不得被呈现为成功，也不得产生无法追溯的半成品。
  - E2：[设计] 同一资源被并发修改时不得静默覆盖；系统提示版本已变化，并允许刷新、对比或重新提交。失败不得被呈现为成功，也不得产生无法追溯的半成品。
  - E3：[设计] 权限在操作过程中被撤回时立即终止后续写操作；已完成步骤按审计规则保留，未提交输入留在本地草稿并提示重新授权。

## R5 权限与可见性

- **引导师**：可发起、查看并管理本 use case，范围限定在其有权访问的组织、项目或小组。
- **方法负责人**：可在被授权范围内参与流程并查看与自身角色相关的结果。
- **观察者**：默认不能发起或修改；仅当内容已发布且授权范围允许时只读查看脱敏结果。
- **项目负责人**（组织角色，原文档写作「项目经理」；见 UC-0.3 角色本体：组织角色 × 项目角色两层正交）：
  可查看项目级状态与审计摘要；是否可代替业务 Actor 执行写操作需由角色模板显式授权。
- **未登录、链接失效或未列出的角色**：默认无权限；接口不得返回越权数据，不能只依赖前端隐藏。

## R7 业务规则（不随具体实现变化的硬性约束）

**快照绑定（本用例的核心）**
- [原型] **改动生成 v(n+1)，已开过的项目锁在自己的版本上。** 项目 → 蓝本版本的引用是
  **不可变快照**，一经绑定不随蓝本后续发布漂移（对齐 UC-0.1「固定快照不可变」与裁决 D-30）。
- [原型] **已建实例记着自己用的是哪个版本**——版本信息存在实例侧，不是运行时从蓝本反查。
- [原型] **归档只影响「还能不能新建」**，不影响已建项目的打开、编辑与运行。
- [设计] 版本号**单调递增、不复用、不缺号**；发布失败不占号（见 UC-2.1/E6）。
- [设计] 每个版本必须记录**版本差异（改了哪几项设计配置）**，供列表与项目页溯源。

**回滚**
- [Backlog] **回滚只允许回到未被任何进行中项目使用的版本。**——逐字出自 `Backlog Use Case.html` 的 UC-2.4；
  「回滚」二字在 proto-01~10 中**零命中**，原型既无回滚入口也无版本历史屏（见 R8 待补）。
- [设计] 回滚是**新建一个内容等同旧版的新版本**，还是把旧版重新置为当前版？——见 R10 [待确认]。

**列表与元数据**
- [原型] 「用过 N 次」统计**已套用该蓝本新建的项目数**；试跑实例不计入。
- [原型] 草稿态蓝本不显示版本号，只显示完成度与发布门槛提示。
- [设计] `[⧉ 复制]` 得到独立蓝本（草稿态、v 无、用过 0 次、满意度空），不与源蓝本共享版本线。

- AC1：每个项目页能显示自己用的是哪个蓝本版本。
- AI/Agent 生成的候选内容必须标识为机器产出，展示可追溯来源；来源不足时不得伪造结论。
- AI/Agent 的写回、覆盖、发布或高影响工具调用必须遵守原型中的批准点；未经确认只保留为草稿或候选。
- 所有权限判断必须在服务端执行；隐藏入口只是界面表现，不构成安全控制。
- 任何覆盖、删除、撤销、签署、发布、写回或停用动作都必须记录审计事件，并显示动作影响范围。

## R9 非功能约束

- **性能/规模预期**：
  - [设计] 普通读取与本地校验应在 1 秒内给出可感知反馈；超过 1 秒显示加载状态，超过 10 秒的任务转为可离开页面的后台任务。
  - [设计] 列表、图谱、转写和审计记录必须分页或增量加载，禁止一次加载整个项目历史。
- **安全/隐私/合规**：
  - 最小权限、组织/项目/小组隔离、传输与静态加密、敏感字段脱敏、导出与 AI 读取留痕。
  - 原始材料、录音、转写、私聊、个人身份与客户数据按授权和留存策略处理。
- **兼容与降级要求**：
  - 响应式 Web；桌面端提供完整能力，移动端保证加入、查看、输入、投票/确认等现场关键动作。
  - WebSocket/实时通道不可用时降级为轮询并显示“非实时”；断网允许保留未提交输入，但不得伪装已同步。

## R10 已知约束 / 依赖

- **内部依赖**：
  - **UC-2.1**（发布动作产生版本）、**UC-2.2**（套用时写入快照引用）。
  - **UC-0.1 版本与快照内核**：本用例是「固定快照不可变」在蓝本域的具体落地。
  - [原型] 登录管理与角色（谁能发布、归档、回滚、删除蓝本）。
- **[待确认 · 本用例最关键]** **已被项目套用过的蓝本能否删除**（列表行有 `[× 删除]` 按钮，
  但未探明其约束）。三种可能且后果差异很大，必须由人裁决，**不得由实现者自行选择**：
  ① 禁止删除（改为归档）；② 允许删除但**保留版本快照**，已套用项目继续可用；
  ③ 允许删除并级联失效已套用项目（**与「已开过的项目锁在自己的版本上」直接冲突，
  本文倾向排除**）。
- **[待确认]** 承上：**删除后已套用项目的快照如何处理**——快照数据是随蓝本删除、
  还是转为项目自持的独立副本？项目页的 `蓝本 … v4` 显示为「已删除的蓝本」还是保留原名？
  这决定快照到底是**引用**还是**深拷贝**，是数据模型的分叉点。
- **[待确认]** **归档规则是否与画布模板完全一致**——「发布新版本时旧版自动归档，
  归档只影响还能不能新建」这句原话出自**画布模板**章节；蓝本侧只有「已开过的项目锁在
  自己的版本上」。二者高度类似但**未在蓝本处逐字确认**，需人类拍板是否同规则。
- **[待确认]** **回滚的实现语义**：新建等同旧版内容的新版本（保留历史线性）vs
  把旧版重新置为当前版（版本号回退）。原型只给了约束「只能回到未被任何进行中项目使用的版本」，
  未给语义。
- **[待确认]** **满意度评分（4.6/4.1）的数据来源与算法**——是项目参与者反馈
  （对照项目「审计与反馈」的 `4.6 整体满意度/5`）的聚合，还是蓝本单独打分？
  样本量少时如何显示。
- **[待确认]** 是否需要**版本历史屏**（列出各版本及其改了哪几项设计配置）；
  若需要，属本用例还是独立 UC。
- **[待确认]** 蓝本的可见范围（原型 agent/画布模板有「全组织可用 / 仅能源组」的范围概念，
  蓝本侧未探明是否同样有团队级可见性）。
- **跨模块契约**：身份与权限、来源引用、版本、任务状态、审计事件和通知必须使用统一标识，避免同一对象在各模块成为不可关联的副本。
- **技术约束**：[原型] 产品为响应式网页；完整离线模式、原生移动端、第三方 IM 与产品内自助计费在 backlog 中明确为范围外。
- **[待确认]** 单项目并发人数、组织数、材料量、音频时长和历史数据量尚未给出；容量与压测指标需在开发前定稿。
- **[待确认]** 通知渠道、消息模板、语言与时区策略未统一定义；本文仅承接原型明确写出的产品内/邮件行为。
- **[待确认]** 模型选择、提示词版本、质量阈值与人工复核责任人尚未指定。

## R11 切分提示（给 requirement-author）

- 建议先拆“领域数据与权限 → 主流程服务 → 页面与状态 → 跨模块回流 → 审计/通知 → 自动化验收”。
- 单个 feature 应能在一次会话内实现并验证，不应把本 use case 的全部前后端与所有异常态塞进一个 feature。
- **建议切法**：① 版本模型与快照绑定（**与 UC-2.1/2.2 共用，宜前置到迭代 1**）
  ② 蓝本列表元数据与行操作（复制 / 删除 / 编辑设计）③ 归档与新建可选版本过滤
  ④ 回滚约束 ⑤ 项目侧版本显示 ⑥ 审计与自动化验收。
- **⚠ 排期提醒**：AC2「已开过的项目锁在自己的版本上」虽写在 P1 的本用例里，
  但它是 **UC-2.2 套用时就必须成立**的数据契约——**快照绑定不能等到迭代 5 才做**，
  否则迭代 1 建出的项目会缺版本引用。建议把①提到迭代 1 随 UC-2.2 一起交付。
- **优先级 / 先后依赖**：P1；3 点；迭代 5 · 收尾项（但见上方排期提醒）；
  先满足登录管理与角色；**「已被套用的蓝本能否删除」裁决前不得实现 `[× 删除]`**。
- 对 P1 能力可在主链路稳定后实现，但合入时仍需覆盖本文全部验收状态。

## R12 AI Ready 验收线索

以下行为应可由自动化测试、接口断言或可复现人工步骤验证：

- V1（成功态 · AC1）：项目页与项目列表行均显示 `蓝本 <名称> v<N>`，与该项目绑定的快照一致。
- V2（成功态 · AC2 · 核心）：用 v4 建项目 A → 蓝本发布 v5 → 断言 A 的绑定版本仍为 v4，
  且 A 的议程环节、分组、输出物等**逐项与 v4 快照一致**；再发布 v6，A 仍不变。
- V3（成功态 · AC3）：v4 归档后，新建项目的可选列表不含 v4；
  而项目 A 打开、编辑、运行**全部正常**。
- V4（成功态 · AC4）：构造一份 `已发布 v3 · 9 环节·1d · 用过 6 次 · 满意度 4.5 · 15/16` 的蓝本，
  断言列表行六个字段各就各位；特别断言 `9`（议程环节数）与 `15/16`（设计配置完成度）
  在接口与 UI 上是**两个独立字段**。
- V5（成功态 · AC5）：`[⧉ 复制]` 后新蓝本为草稿态、无版本号、用过 0 次、满意度空，
  且改动新蓝本不影响源蓝本。
- V6（版本差异）：发布 v5 时改了第 2、9、14 三项设计配置，
  断言版本记录里**恰好列出这三项**。
- V7（回滚约束）：尝试回滚到**正被进行中项目使用**的版本被拒绝并说明原因；
  回滚到未被使用的版本成功（语义按 R10 [待确认] 定稿后补断言）。
- V8（版本号完整性）：连续发布与失败混合执行后，版本号单调递增、无缺号、无复用。
- V9（新建默认版本）：新建项目默认选中**最新已发布版本**，非最新版需显式选择。
- V10（权限态）：逐一使用 引导师、方法负责人、观察者、未授权用户访问；返回数据和可执行动作严格符合 R5。
- V3（空态）：无目标数据时显示真实空态与下一步，不生成伪数据。
- V4（依赖失败）：模拟网络/外部依赖失败，输入和最近成功数据保留，错误可解释且可重试。
- V5（并发态）：两名用户修改同一资源时不静默覆盖，并可识别最终版本。
- V6（审计态）：关键动作可按操作者、时间、对象和结果检索；越权尝试也有安全审计记录。
