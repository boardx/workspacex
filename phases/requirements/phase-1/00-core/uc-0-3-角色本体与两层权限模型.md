# 原始需求（细化）— UC-0.3 角色本体与两层权限模型

> 所属：阶段零 · 共享内核 / M0 跨工具协议
> 来源：原型后台「成员与配额」的组织角色（管理员 / 项目负责人 / 顾问）＋团队列（能源组 / 平台组 /
> 供应链组）；组员入口的项目角色（引导师 / 组长 / 组员 / 受访者）；后台资源可见性
> 「全组织可用 / 仅能源组」；「你作为管理员看不到什么」硬约束。
> **补写缘由**：原文档只有一套四角色（引导师/项目经理/组员/观察者），且**自相矛盾**——
> UC-1.4 的 R5 角色列表没有「组长」，R3 第 1 步却写着「组长加上组员私聊」。
> 原型是两套正交角色。不统一则 8 份 UC 的 R5 段会集体返工，RBAC 表结构无法定稿。

> 口径（四标记）：**[原型]** ＝ `WorkspaceX Standalone.html` **运行态实际存在**的行为（有界面可查，依据 scratchpad 的 proto-01~10 抽取档案）；**[Backlog]** ＝ `Backlog Use Case.html` 的**文档要求**（原型未必实现）；**[设计]** ＝ 依据前两者反推补全，**需人类确认**；**[待确认]** ＝ 不应由实现者自行决定。
> 元数据：优先级 **P0**；估点 **13**（原 8，2026-07-28 上调）；建议迭代 **阶段零 · 共享内核**。
> **估点变更说明**：① 隔离下沉到 **PostgreSQL RLS**（策略编写、非 owner 运行角色、
> `FORCE ROW LEVEL SECURITY`、自动化断言 V9）；② 新增 `acl_bindings` 统一权限表与
> **权限沿 Segment / embedding / 图节点 / 缓存 / Context Pack 传播**（V10）；
> ③ O-12 落地的**顶部组织切换器 + 切换清空项目级上下文**（V11）。
> 反向减项：O-03 裁定协同引导师为引导师多实例，RBAC 表**不新增第五角色**，权限矩阵用例数不变。

## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-0.3 / 角色本体与两层权限模型
- **Actor**：**组织管理员**、**项目负责人**、**顾问**、**外部参与者**
- **目标**：[设计] 把「你在公司里是谁」和「你在这场项目里干什么」**彻底分开**——
  前者决定你能用什么资源、花多少额度；后者决定你在某场项目里能看到哪些内容、能做哪些动作。
- **本用例结果**：系统中每个人同时持有一个**组织角色**（可含团队归属）和零到多个**项目角色**；
  任何一次鉴权都是这两层的交集，且服务端可解释「为什么允许 / 为什么拒绝」。
- **系统边界**：角色定义、团队归属、资源可见性范围、两层交集鉴权、管理员边界。
- **核心数据对象**：组织角色、团队、组织成员、项目角色、小组、资源可见性范围、权限判定记录。

## R2 前置条件 / 触发条件

- **前置条件**：用户已有账号并归属某个组织（UC-1.5 / UC-1.6）。
- **触发条件**：任何一次受保护的读写操作；以及管理员在后台调整成员角色/团队时。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

1. **系统处理**：解析请求者的**组织身份**——所属组织、组织角色、团队归属。
   [原型] 组织角色三取值：**管理员** / **项目负责人** / **顾问**。
2. **系统处理**：解析请求者在**目标项目**中的项目角色。
   [设计] 项目角色四取值：**引导师** / **组长** / **组员** / **观察者**；
   外部受访者不是项目角色，走一次性令牌身份（UC-6.3）。
   [已裁决 O-03] **协同引导师是否为第五个项目角色**——proto-08「项目 → 设置 → 参与者与邀请」屏的
   **身份四选**原文是「组员 ｜ 组长 ｜ 观察者（只读）｜ **协同引导师**」，邀请链接的「进场身份」
   四选同样含它；proto-07 访谈的「本场角色」另有「周宁 **联合主持**」。原型**只证明该身份选项存在，
   从未给出它的任何权限**。它究竟是独立项目角色，还是「一场可有多名引导师」的实例，
   曾必须由人类裁决。
   **裁决（O-03）**：**协同引导师 = 引导师的多实例，不是第五种项目角色。**
   项目角色**恒为四种**；一场项目**可有多名引导师实例，权限完全相同**，
   其中一名标记为**主持人**，持**最终确认权**（对应 `uc-6-4` R5「联合主持同主持人，
   但最终确认权归主持人」——全仓唯一给出过权限语义的一处）。
   因此 RBAC 表**不新增行**，蓝本第 4 项「角色与权限」的「4 角色」分母不变。
   代价：邀请屏的身份四选需在**文案**上说明「协同引导师 ＝ 以引导师身份加入」，
   即它是**进场身份的展示别名**，落库时写入的项目角色是 `facilitator`。
   （同一裁决同步于 uc-1-3 / uc-1-4 / uc-2-1 / uc-2-2 / uc-3-2，本文为角色本体权威文件。）
3. **系统处理**：解析目标资源的**可见性范围**。
   [原型] 资源可标 **全组织可用** 或 **仅某团队**（如 Ledger「仅能源组」、
   画布模板「仅能源组」）；项目内资源另有 **本组 / 全场 / 私有** 三档。
4. **系统处理**：取两层交集判定。**组织层决定「能不能用这个资源」，项目层决定
   「在这场项目里能看到哪些内容、做哪些动作」**；两者任一不通过即拒绝。
5. **系统收口**：校验 AC1「组织角色与项目角色互不替代——组织管理员在他没有项目角色的项目里，
   不因管理员身份获得内容读取权」；拒绝时返回不泄露资源存在性的响应。
6. **系统收口**：记录权限判定所依据的两层角色与资源范围，供审计与「为什么被拒」解释使用。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[原型] **管理员出于审计目的读取项目内容**——允许，但**每次访问写入审计日志且对
    项目负责人可见**；管理员可在「看我的访问记录」查看自己的访问历史。
  - A2：[设计] **组长的项目角色由进场链接携带**——[原型]「组长的链接多一份主持权限」，
    即项目角色可由一次性链接授予，不必是组织成员。
  - A3：[设计] 同一人可在多个项目持有不同项目角色；项目角色变更立即生效。
  - A4：[已裁决 O-12] 同一人归属多个组织时是**两套完全独立的权限**（对照 UC-17.4），
    切换组织即切换全部上下文。
    **裁决（O-12）**：**① 一个账号 + 顶部组织切换器。**
    - `user` ↔ `organization` 是**一对多**：同一账号可**创建**并**归属多个组织**
      （否决「同邮箱注册多条账号」的方案，与 UC-1.1「同一人登录进的是同一账号」保持一致）。
    - 切换器在**顶部常驻**，会话内切换、**不需要重新登录**。
    - **切换时必须清空全部项目级上下文**——当前项目、当前环节、Context Pack、
      已缓存的鉴权判定、未提交的项目级草稿引用一律作废，**不得跨组织残留**。
    - 切换后**权限按当前组织重新求值**：组织角色、团队归属、资源可见性范围全部重取，
      不复用切换前的任何判定结果（对照 R9「角色变更后缓存失效」，组织切换等价于全量失效）。
    - **团队为单一归属**：组织内一人一队（见 R10）。
- **异常流程**：
  - E1：[设计] 用户有组织角色但无项目角色时，项目内资源一律不可见（管理员亦然，见 R7）。
  - E2：[设计] 用户的项目角色在操作过程中被撤回时，立即终止后续写操作；
    已完成步骤按审计规则保留。
  - E3：[设计] 资源标为「仅某团队」而用户不在该团队时，即使其项目角色足够也拒绝，
    并说明是组织层限制而非项目层。
  - E4：[设计] 角色数据不一致（如项目角色指向已停用组织成员）时，按**拒绝**处理并告警，
    不做宽松兜底。

## R5 权限与可见性

### 组织角色（[原型]）

| 角色 | 能力 |
|---|---|
| **管理员** | 后台全部配置（Agent / Skill / 模型 / MCP / 画布模板 / 项目蓝本 / 成员与配额 / 反馈）；邀请成员、分配角色与团队、设配额与降级策略。**不能读取任何人的个人层内容**（见 R7） |
| **项目负责人** | 创建与管理项目；可被授予对部分 MCP 的访问（[原型] 客户 CRM「仅项目负责人」）；不进后台配置 |
| **顾问** | 参与项目、使用被授权的能力；不进后台配置 |

**团队**（[原型] 能源组 / 平台组 / 供应链组）是与组织角色正交的归属维度，
用于资源可见性范围与配额池（[原型]「跑批类 agent 从团队池扣减而非个人」）。

### 项目角色（[设计]，统一原文档四角色并补入组长）

| 角色 | 能力 |
|---|---|
| **引导师** | 控场：推进环节、广播、计时、分组、批量确认；可见全场内容。**[已裁决 O-03] 一场可有多名引导师实例，权限完全相同**；其中一名标记为**主持人**，持**最终确认权**。原型的「协同引导师」与访谈侧的「联合主持」都是本行的实例，**不是独立角色**（`uc-6-4` 的「联合主持」与此同义） |
| **组长** | 主持本组：提交本组产出、确认本组节点；可见本组全部 + 全场已共享 |
| **组员** | 参与本组：贴便签、发言、投票；可见本组内容 + 全场已共享 |
| **观察者** | 只读已发布且已脱敏内容；不能输入、控场、读私聊或原始转写，单独授权除外且必须留痕 |

> **[已裁决 O-03] 关于「协同引导师」行**：早前稿本在此表保留一行「协同引导师 · 权限未定」。
> 裁决结论是**协同引导师 = 引导师的多实例**，故**该行已删除**，项目角色恒为上表四种。
> 原型的参与者身份四选与邀请链接进场身份四选里的「协同引导师」是**进场身份的展示别名**，
> 落库写入 `facilitator`；访谈侧的「联合主持」同义。
> 由此 RBAC 权限矩阵的测试用例仍按**四角色**枚举，蓝本第 4 项「4 角色」分母不变。

> **原文档的「项目经理」** 对应本模型的**组织角色「项目负责人」**，不是项目角色。
> 各 UC 的 R5 段需按此替换，避免同一名词跨层使用。

- **外部受访者**：不持项目角色，通过一次性令牌获得单场次的受限身份（UC-6.3）。
- **未登录、链接失效或未列出的角色**：默认无权限；接口不得返回越权数据，
  不能只依赖前端隐藏。

## R6 后置条件 / 不包含

- **正常后置条件**：
  - 每次鉴权可解释：返回依据的组织角色、项目角色、资源范围三项。
  - [设计验收] AC1：组织管理员在其无项目角色的项目中，内容读取一律被拒
    （审计目的访问走 A1 且必然留痕并通知）。
  - [原型验收] AC2：管理员对任何人的个人层只能看到条目**计数**，看不到内容。
  - [设计验收] AC3：标为「仅某团队」的资源对非该团队成员不可见，无论其项目角色为何。
- **失败后置条件**：拒绝时不泄露资源是否存在；判定失败进入可观测日志。
- **不包含**：
  - 自定义角色与细粒度权限编辑器（[原型] 后台无此屏；UC-17.4 的「角色模板可按组织定制」
    属 phase-3）。
  - 跨组织的统一身份与单点登录。

## R7 业务规则（不随具体实现变化的硬性约束）

- [设计] **两层正交**：组织角色决定资源准入，项目角色决定内容可见与动作许可，任一不通过即拒绝。
- [原型] **个人层对管理员封闭**：管理员只能看到他人个人层的**条目计数**，内容不可见。
  「要拿到某人的私有内容，只有一条路径：本人显式升到项目层。」
- [原型] **管理员读取项目内容必留痕**：每次访问写审计日志，且**对项目负责人可见**。
- [设计] **管理员不是超级用户**：不因管理员身份自动获得项目内容读取权。
- [原型] **资源可见性范围**为一等字段，但**只在两类资源上确认存在**：
  **agent**（Ava/Scout/Echo「全组织可用」、Ledger「仅能源组」）与
  **画布模板**（用户画像「全体成员」、采购比选旅程「仅能源组」）可标「全组织可用 / 仅某团队」。
  [原型确认缺失] **skill 库与项目蓝本两张列表已逐字段渲染，行内没有可见性列**——
  不是未探明，是已探明区内没有。它们是否也需要该字段，见下条。
- [设计] skill 与项目蓝本是否同样具备「全组织可用 / 仅某团队」可见性范围，
  由本文反推补全，**需人类确认**。
- [原型] **MCP 服务器用的是另一套枚举，不可与上一条混用**：其「授权范围」列取值为
  **仅项目负责人 / 全体成员 / 待安全评审**（见后台 MCP 服务器表）。它表达的是「谁能调这台服务器」，
  与团队可见性不是同一维度，**禁止合并成同一个字段**。
- [设计] **项目角色可由一次性链接授予**，不要求是组织成员（组长/组员的现场进场路径）。
- 所有权限判断必须在服务端执行；隐藏入口只是界面表现，不构成安全控制。
- 角色变更、团队变更、可见性范围变更都必须记录审计事件并显示影响范围。
- [设计] **租户与项目隔离必须在 PostgreSQL RLS 层强制**（`docs/architecture/context-engine.md`
  第五节）——**应用层过滤只是第二道防线，不是第一道**。
  理由：Context Engine 有多条数据出口（Context API、文件浏览器、检索、导出、
  ingestion worker、报表），任何一条忘了加 `WHERE tenant_id = ?` 就是一次跨租户泄漏；
  把隔离下沉到 RLS 后，**忘记过滤的默认结果是「查不到」而不是「全查到」**。
  上一条「所有权限判断必须在服务端执行」由此升级为「**必须在数据库层强制、在服务端复核**」。
- ⚠ [设计] **应用数据库连接不得使用表 owner 身份**——PostgreSQL 中**表 owner 默认不受 RLS 约束**
  （除非显式 `FORCE ROW LEVEL SECURITY`），用 owner 连接等于 **RLS 形同虚设**、
  策略写了也不生效且**不会报错**。硬性要求：
  ① 迁移/DDL 用 owner 角色，**运行时连接用受 RLS 约束的非 owner 角色**；
  ② 对所有含租户数据的表启用 `FORCE ROW LEVEL SECURITY` 兜底；
  ③ 把「运行时连接角色不是任何业务表的 owner」做成**可执行断言**（见 R12 V9），
  不依赖人工检查配置。
- [设计] **权限必须沿数据链路传播，不能只挂在源对象上**：Artifact 上的可见性范围
  必须传播到由它派生的 **Segment、embedding、图节点、缓存与 Context Pack**。
  否则会出现「原文看不到、但摘要/向量召回把内容洗白后送出去」的越权路径。
  推论：**交集生成内容取所有来源权限中最严格的一档**（不是最宽松，也不是取并集）。

## R8 界面线索

- **前端入口**：[原型] 后台「成员与配额」的成员表（成员 / 角色 / 团队 / 配额 / 调整）；
  [原型]「你作为管理员看不到什么」说明区与 `[看我的访问记录]`。
- **信息架构**：组织角色在后台管理；项目角色在项目的分组与邀请里管理（UC-1.3）。
- **推荐交互**：
  - [设计] 顶部常驻**角色说明条**（UC-1.4 R3 要求）需同时显示两层身份，
    形如「顾问 · 能源组 ｜ 本项目：组长 · 第 2 组」。
  - [设计] 被拒绝时给出可理解的原因（是组织层还是项目层限制），不要只显示「无权限」。
- **必须呈现的状态**：默认态、加载态、空态、校验失败态、依赖失败态、无权限态、成功态。
- **原型参考**：`phases/requirements/WorkspaceX Standalone.html` — 后台→成员与配额
- **UI sign-off**：**原型确认缺失**——后台「成员与配额」与项目四视角两处都已逐字段完整抽取，
  两层身份合并的**角色说明条**与「为什么被拒」的分层原因提示**在已探明区内没有**，
  不是「回去再抽一次就有」。需补画原型后确认。

## R9 非功能约束

- **性能/规模预期**：[设计] 鉴权判定应在毫秒级完成并可缓存；角色变更后缓存失效需在 1 分钟内生效。
- **安全/隐私/合规**：最小权限；越权尝试必须留安全审计；拒绝响应不泄露资源存在性。
- **兼容与降级要求**：鉴权服务不可用时**一律拒绝**，不得降级为放行。

## R10 已知约束 / 依赖

- **内部依赖**：UC-1.5 / UC-1.6（组织与成员）、UC-1.3（项目角色授予）。
- **被依赖**：**全部 68+ 份 UC 的 R5 段**。本用例是它们的共同底座。
- **[已裁决 O-03]** **协同引导师**（及访谈侧的「联合主持」）是第五个项目角色，还是引导师的多实例。
  见 R3 第 2 步与 R5 项目角色表。**这是本文作为角色本体权威文件必须挂出的裁决项**，
  不裁决则 RBAC 表无法定稿，uc-1-3 / uc-1-4 / uc-2-1 / uc-2-2 / uc-3-2 五份的同名条目也无法闭合。
  **裁决（O-03）**：**引导师的多实例**——项目角色恒为四种，一场可有多名引导师、权限相同，
  其中一名为主持人持最终确认权。RBAC 表不新增行，五份下游文档的同名条目随之闭合。
- **[已裁决 O-12]** 同一人归属多个组织时的切换模型（对照 UC-17.4）。
  **裁决（O-12）**：**一个账号 + 顶部组织切换器**；切换时清空全部项目级上下文，
  权限按当前组织重新求值；一人可创建 / 归属多个组织（`user` ↔ `organization` 一对多）。
  见 R4 A4。
- **[待确认]** 「项目负责人」与「引导师」在实践中是否总是同一人；若不是，
  项目创建者默认获得哪个项目角色。
- **[已裁决 O-12]** 团队是单一归属还是可多归属。
  **裁决（O-12）**：**单一归属——组织内一人一队。** 这是最小假设；
  多归属可在后续放开而不破坏数据模型（`org_member.team_id` 单列 → 关联表的迁移是加法）。
  跨组织不受此限：同一账号在 A 组织属能源组、在 B 组织属平台组，互不影响。
- [设计] **`acl_bindings` 表**（`docs/architecture/context-engine.md` 第二节核心表）是本用例
  两层权限模型的**落库载体**：一条绑定表达「**某主体（用户 / 组 / 团队）对某客体
  （项目 / Artifact / Segment）拥有何种访问范围**」。
  要点：① 组织角色、项目角色、团队可见性范围三者最终都归结为 `acl_bindings` 上的判定，
  **不另建三套权限表**；② 客体粒度必须**下探到 Segment**，否则 R7 的「权限沿链路传播」无处落地；
  ③ **文件浏览器（22-files）与检索共用同一套 `acl_bindings`**，文件浏览器不是权限旁路；
  ④ 每次判定产生一个 `permissionDecisionId`，写入 Context Pack 的 `items[]`
  （见 UC-0.2），使「为什么这条能给你看」可回溯。

## R12 AI Ready 验收线索

- V1（成功态）：AC1 —— 组织管理员访问其无项目角色的项目内容，接口拒绝；
  以审计目的访问时成功但产生审计记录且项目负责人可查询到。
- V2（成功态）：AC2 —— 管理员查询他人个人层，仅返回计数字段，内容字段不存在于响应体中。
- V3（成功态）：AC3 —— 非能源组成员请求标为「仅能源组」的 agent，被拒绝且原因标明为组织层限制。
- V4（权限态）：对引导师/组长/组员/观察者/未授权用户逐一调用同一批接口，
  返回数据与可执行动作严格符合 R5 表格。
- V5（空态）：无项目角色的用户打开项目，显示无权限态而非空列表。
- V6（依赖失败）：鉴权服务不可用时全部请求被拒绝，无任何放行。
- V7（并发态）：操作过程中角色被撤回，后续写操作立即失败，已完成步骤保留审计。
- V8（审计态）：角色变更、团队变更、管理员项目访问三类事件均可按操作者、时间、对象检索。
- V9（RLS 强制）：[设计] ① 用运行时数据库连接角色直接执行 `SELECT` 跨租户查询（**绕过应用层**），
  断言返回 0 行；② 断言运行时连接角色**不是任何业务表的 owner**
  （查 `pg_class.relowner` 与 `current_user` 比对）；③ 断言所有含租户数据的表
  已启用 `FORCE ROW LEVEL SECURITY`。**这三条必须是自动化断言，不接受人工核对配置。**
- V10（权限传播）：[设计] 对一份仅能源组可见的 Artifact，以非能源组成员身份分别经
  **检索、Context Pack、embedding 相似度查询、图节点遍历、文件浏览器、缓存命中**六条路径访问，
  断言六条全部不返回其内容——验证 R7「权限沿链路传播」。
- V11（组织切换）：[设计] 同一账号归属 A / B 两个组织，在 A 组织打开某项目后切到 B 组织，
  断言：① 项目级上下文（当前项目 / 环节 / Context Pack / 鉴权缓存）全部清空；
  ② 以 B 组织身份请求 A 组织的项目资源被拒且不泄露存在性；
  ③ 权限判定结果来自 B 组织的角色与团队，不复用切换前的任何缓存。
