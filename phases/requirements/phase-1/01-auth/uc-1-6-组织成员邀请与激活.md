# 原始需求（细化）— UC-1.6 组织成员邀请与激活

> 所属：阶段一 · 能跑完一场项目 / M1 登录管理
> 来源：原型**后台 → 成员与配额**（`proto-03-batch3-backend.md`）——
> 标签页「成员配额 ｜ 用量监控 ｜ 限额策略」＋ `[邀请成员]` `[导出]`；
> 成员表列「**成员 ｜ 角色 ｜ 团队 ｜ 本月配额使用 ｜ `[调整]`**」；
> 待激活行「**陈默 顾问(待激活) 供应链组 0/2.0M · 待接受邀请 · 已发送 2 天 `[重发]`**」；
> 说明页「已定下的四条规则」第 4 条：「**注册：邀请码或邀请链接**。只能被邀请入组织，
> 两种入口：14 位邀请码、**带组织与角色的一次性链接**」。
> **补写缘由**：**UC-1.5** 只解决「第一个组织和第一个人」；
> 从第二个人开始的入组路径（说明页规则 4 的第二种入口）**原 8 份 M1/M2 用例完全没有**。
> 没有本用例，一个组织永远只有一位管理员，`成员与配额` 屏没有数据来源，
> 项目也邀不到内部顾问。

> 口径（四标记）：**[原型]** ＝ `WorkspaceX Standalone.html` **运行态实际存在**的行为（有界面可查，依据 scratchpad 的 proto-01~10 抽取档案）；**[Backlog]** ＝ `Backlog Use Case.html` 的**文档要求**（原型未必实现）；**[设计]** ＝ 依据前两者反推补全，**需人类确认**；**[待确认]** ＝ 不应由实现者自行决定。
> 元数据：优先级 **P0**；估点 **5**；建议迭代 **迭代 1 · 能进场**。
>
> **[人类已拍板 2026-07-27]**
> - **0-3**：认证＝**邮箱 + 密码**，激活时做**邮箱验证链接**；**不做验证码（OTP）**。
> - **0-4**：本用例即裁决点名要补写的 **UC-1.6**（与已产出的 UC-1.5 配对）。
> - **UC-0.3**：**组织角色**（管理员 / 项目负责人 / 顾问）× **团队**（能源组 / 平台组 /
>   供应链组）是**组织层**身份；**项目角色**（引导师 / 组长 / 组员 / 观察者）由项目侧授予
>   （UC-1.3），**本用例不授予任何项目角色**。
> - **D-18**：管理员权力边界是硬约束——即使他能邀人、能改角色，也**看不到成员个人层的内容**。

## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-1.6 / 组织成员邀请与激活
- **Actor**：**组织管理员**（邀请方，[原型] 后台唯一有此权限的组织角色）、
  **受邀人**（激活后成为组织成员，组织角色为项目负责人或顾问）
- **目标**：[原型] 产品是**邀请制**的——「**只能被邀请入组织**」。
  管理员在后台把人请进组织，**入场即带好组织角色与团队**，并分到配额；
  受邀人用「带组织与角色的一次性链接」完成激活，成为可被拉进项目的正式成员。
- **本用例结果**：组织成员表中新增一条**已激活**记录（成员 / 角色 / 团队 / 本月配额使用），
  该成员可用 UC-1.1 的邮箱 + 密码登录，并可被 UC-1.3 邀请进具体项目。
- **系统边界**：邀请签发与送达、一次性激活链接、账号创建或已有账号加入、邮箱验证、
  组织角色与团队指派、配额初始化、待接受状态与重发、撤销邀请、成员停用/移除。
- **核心数据对象**：组织邀请、一次性激活令牌、账号、组织成员、组织角色、团队、配额、审计事件。

## R2 前置条件 / 触发条件

- **前置条件**：
  - 组织已存在且至少有一名管理员（由 **UC-1.5** 产生）。
  - 操作者的**组织角色为管理员**（[原型] `[邀请成员]` 只出现在后台「成员与配额」）。
  - [设计] 组织尚有可分配配额，或允许在未分配额度不足时先邀请、后调配（见 E5）。
- **触发条件**：
  - [原型] 管理员在**后台 → 成员与配额**点 `[邀请成员]`。
  - [原型] 受邀人点开收到的「**带组织与角色的一次性链接**」。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

1. **管理员操作**：[原型] 在后台「成员与配额」点 `[邀请成员]`，填写受邀人的**工作邮箱**，
   并指派 **①组织角色** 与 **②团队**。
   [原型] **组织角色三取值**：**管理员 / 项目负责人 / 顾问**。
   [原型] **团队取值**：**能源组 / 平台组 / 供应链组**（团队清单由组织维护，见 R10）。
   **系统响应**：校验操作者是管理员、邮箱格式与是否已在本组织、角色与团队合法；
   创建一条**待接受邀请**记录，**此时不创建可用账号**。
2. **系统处理**：[设计] 按角色的默认额度**预留配额**并写入该邀请
   （[原型] 「配额策略：**按角色设默认额度**，用满后可申请应急池」；
   待激活成员在成员表显示为 `0/2.0M`，即额度已分配、用量为零）。
3. **系统处理**：[原型] 发出**带组织与角色的一次性链接**到该邮箱。
   [设计] 链接一次性、有有效期；其中携带**组织 ID + 组织角色 + 团队**三项，
   受邀人无法自行改写这三项（须服务端校验，不信任链接参数的客户端回传）。
4. **系统处理**：[原型] 成员表立即出现该行，形如
   `陈默 顾问(待激活) 供应链组 0/2.0M —— 待接受邀请 · 已发送 2 天 [重发]`。
   **待激活成员计入名册但不计入活跃成员**（[原型] 数据总览「活跃成员 41/48」）。
5. **受邀人操作**：点开链接。**系统响应**：校验令牌有效性、是否已使用、是否被撤销；
   失败按 E1 处理。
6. **受邀人操作**：**分两种情况**——
   - **6a 新用户**：填写姓名、**设置密码**（[人类已拍板] 邮箱 + 密码，无 OTP）；
     系统创建账号并把该邮箱标为**已验证**（点击链接本身即证明邮箱所有权，
     [待确认] 是否仍需二次验证邮件，见 R10）。
   - **6b 已有账号**（此人已在别的组织有账号）：只需登录确认，
     **不新建账号**，把现有账号加入本组织（对照 UC-1.5 A2 的同款处理）。
7. **系统处理**：**核销**该一次性链接，创建**组织成员**记录并写入组织角色与团队，
   初始化配额；成员表状态由「待激活 / 待接受邀请」变为**已激活**。
   核销与成员创建必须在**同一事务**内完成。
8. **系统收口**：校验 AC1「**只能被邀请入组织**——不存在自助加入路径」；
   记录邀请人、受邀人、角色、团队、时间与结果进审计。
9. **系统收口**：校验 AC2「**入场即带好组织角色与团队**」；
   刷新成员表、活跃成员计数与配额总览（[原型] 「已分配 5,400 万（占组织额度 87%）｜
   未分配 800 万」）。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[原型] **重发邀请**——未接受的邀请显示已发送天数并给 `[重发]`；
    重发**签发新令牌并作废旧令牌**（不是把同一条链接再发一次），有频率限制。
  - A2：[原型] **另一条注册路径是 14 位邀请码创建新组织**（UC-1.5），
    与本用例互斥：**邀请码 → 新建组织当管理员**；**一次性链接 → 加入已有组织**。
    两者都不是自助注册。
  - A3：[设计] **管理员在邀请后、激活前修改角色或团队**——允许，
    以最后一次修改为准；已发出的链接携带的仍是服务端记录的最新值（见 R7 硬约束）。
  - A4：[设计] **撤销未接受的邀请**——立即作废令牌，成员表移除该行，写审计。
  - A5：[设计] **批量邀请**——[待确认] 后台是否支持一次填多个邮箱
    （项目侧的 UC-1.3 已有「邮箱或手机号，逗号分隔」的批量入口，后台侧未见同款）。
  - A6：[原型] **成员激活后的日常维护**在同一张成员表上进行：
    改角色、改团队、`[调整]` 配额、`[导出]`。本用例只覆盖**角色与团队的指派与变更**；
    配额调整与降级策略属后台配额用例。
- **异常流程**：
  - E1：[设计] **链接无效、过期、已使用或已撤销**——统一提示「该邀请已失效，请联系管理员重发」，
    **不区分具体原因**（防枚举），并**不泄露组织名称与成员信息**。
  - E2：[设计] **该邮箱已是本组织成员**——不重复创建，提示已在组织内，
    并把入口引导到「直接登录」。
  - E3：[设计] **该邮箱在别的组织已有账号**——走 6b，不新建账号；
    [待确认] 一人多组织的切换模型（对照 UC-17.4「同一人在两组织是两套权限」）。
  - E4：[设计] **并发**：两名管理员同时邀请同一邮箱，只产生一条有效邀请，
    另一方收到明确失败提示，不产生重复成员行。
  - E5：[设计] **配额不足**——[原型] 组织已分配 87%、未分配 800 万且「建议留作应急池」。
    邀请**不因此阻断**，但需明确提示剩余未分配额度，并允许以低于默认额度邀请。
    [待确认] 是否设硬上限（超过组织额度即拒绝邀请）。
  - E6：[原型] 邮件服务不可用时**明确失败**，保留已填信息与邀请记录（状态标为「发送失败」）
    并提供重试；**不得静默成功**，不得让管理员以为已发出。
  - E7：[设计] 激活过程中管理员撤销了邀请——受邀人当前步骤立即失败并说明原因，
    不产生半成品成员记录。
  - E8：[设计] **组织被停用**时，未接受的邀请一律不可激活；已激活成员按 UC-1.1 A1 只读登录。

## R5 权限与可见性

> 按 **UC-0.3 两层正交模型**：本用例**只授予组织层身份**（组织角色 + 团队），
> **不授予任何项目角色**。项目角色由 UC-1.3 在具体项目里单独授予。

### 谁能做本用例

| 组织角色 | 在本用例中的权限 |
|---|---|
| **管理员** | [原型] 唯一可进后台「成员与配额」者：`[邀请成员]`、指派角色与团队、`[重发]`、撤销邀请、`[调整]` 配额、`[导出]` |
| **项目负责人** | 不进后台配置；**不能邀请组织成员**。其在项目内邀请参与者走 UC-1.3，那是**项目角色**，不产生组织成员 |
| **顾问** | 同上，不进后台 |

### 被邀请者能获得什么

| 指派的组织角色 | 激活后获得 |
|---|---|
| **管理员** | 后台全部配置权；[设计] 邀请第二个管理员应有额外确认（见 R7） |
| **项目负责人** | 创建与管理项目；可被授予对部分 MCP 的访问（[原型] 客户 CRM「仅项目负责人」） |
| **顾问** | 参与项目、使用被授权的能力；不进后台 |

- **团队**（[原型] 能源组 / 平台组 / 供应链组）与组织角色**正交**，
  决定「全组织可用 / 仅某团队」资源的可见性（判定在 UC-1.4 / UC-0.3），
  并决定**配额池归属**（[原型]「跑批类 agent 从**团队池**扣减而非个人」）。
- **管理员边界（D-18）在本用例同样成立**：管理员能邀人、能改角色与配额，
  但**看不到任何成员个人层的内容**，只见条目计数；
  读取项目层内容须留痕且对项目负责人可见。**邀请权不等于阅读权。**
- **未登录访客**：仅能访问自己那条激活链接；除自己的激活进度外不可读取任何组织数据，
  **激活页不得回显组织成员名单或其它成员信息**。
- 所有校验必须在服务端执行；接口不得返回越权数据，不能只依赖前端隐藏。

## R6 后置条件 / 不包含

- **正常后置条件**：
  - 组织成员表新增一条**已激活**记录，含成员、角色、团队、本月配额使用四列；
    活跃成员计数与配额总览同步刷新。
  - 该成员可用邮箱 + 密码登录（UC-1.1），并可被拉进项目（UC-1.3）。
  - [原型验收] **AC1**：**只能被邀请入组织**——系统不存在任何自助加入已有组织的路径。
  - [原型验收] **AC2**：**入场即带好组织角色与团队**——激活完成时这两项已就位，
    不需要事后补配。
  - [设计验收] **AC3**：**一次性链接用过即失效**，重复使用被拒绝；`[重发]` 会作废旧链接。
  - [原型验收] **AC4**：未接受的邀请在成员表显示「**待接受邀请 · 已发送 N 天**」并可 `[重发]`；
    该成员**计入名册但不计入活跃成员**。
  - [设计验收] **AC5**：受邀人**无法自行改写**链接里的组织、角色或团队。
- **失败后置条件**：
  - 不创建「看似成功」的成员记录；未完成的邀请保留为待接受状态并可重发或撤销；
    失败事件进入可观测日志。
- **不包含**：
  - **自助注册 / 自助加入组织**——[原型] 明确「只能被邀请入组织」。
  - **创建新组织**（14 位邀请码路径）——见 **UC-1.5**。
  - **项目内的参与者邀请与进场身份**（组员/组长/观察者/协同引导师）——见 **UC-1.3 / UC-1.2**；
    那条路径**不产生组织成员**。
  - 配额策略本身（按角色默认额度、应急池、三级降级阈值、按任务类型分级）——
    属后台配额与限额策略用例；本用例只做**邀请时的初始额度写入**。
  - 用量监控与限额策略两个标签页的功能。
  - 企业 SSO、社交账号登录、计费与订阅。
  - 自定义组织角色（[原型] 后台只有三取值；「角色模板可按组织定制」属 phase-3 的 UC-17.4）。

## R7 业务规则（不随具体实现变化的硬性约束）

- [原型] **只能被邀请入组织**，两种入口且仅此两种：
  ① **14 位邀请码** → 创建新组织（UC-1.5）；② **带组织与角色的一次性链接** → 加入已有组织（本用例）。
- [原型] **组织角色三取值**：管理员 / 项目负责人 / 顾问。**不可自定义**。
- [原型] **团队是一等字段**，与组织角色正交；决定资源可见性范围与**团队配额池**。
- [人类已拍板] **认证为邮箱 + 密码**；**不做 OTP**。激活即完成邮箱所有权确认。
- [设计] **链接携带的组织、角色、团队以服务端记录为准**——
  客户端回传的这三项一律忽略；篡改链接参数不得改变实际授予的身份。
- [设计] **一次性且可撤销**：链接用过即失效；`[重发]` 作废旧令牌并签发新令牌；
  管理员可随时撤销未接受的邀请。
- [设计] **激活与成员创建原子**：核销令牌、创建组织成员、写入角色与团队、初始化配额，
  必须在同一事务内完成，不允许出现「令牌已核销但成员没建出来」。
- [设计] **失效原因不外泄**：链接无效/过期/已用/已撤销返回同一提示，且不泄露组织与成员信息。
- [设计] **邀请管理员需额外确认**——授予后台全部配置权是高影响动作，
  须二次确认并单独审计；[待确认] 是否要求现有管理员双人复核。
- [人类已拍板 **D-18**] **邀请权 ≠ 阅读权**：管理员即使掌握成员的角色与配额，
  也**不能读取任何人的个人层内容**（只见计数）；
  读取项目层内容须写审计日志且**对项目负责人可见**。
- **本用例不授予任何项目角色**；组织成员默认在任何项目中都**没有**内容读取权，
  须由 UC-1.3 单独授予。
- 邀请、重发、撤销、激活、角色变更、团队变更、配额调整、成员停用，
  都必须记录审计事件，并显示动作影响范围。

  两者是两层，**入口也必须分开**，不要在一个屏里混着改。
- **推荐交互**：
  - [设计] `[邀请成员]` 弹层三件事：**邮箱**、**角色**（三选一）、**团队**（下拉）；
    角色选「管理员」时给出高影响提示与二次确认。
  - [设计] 待激活行需与已激活行**视觉可辨**（原型用 `顾问(待激活)` 的括号后缀 +

- **必须呈现的状态**：
  - 默认态、加载态、空态（新组织只有创建者一人，承接 UC-1.5 V5 的真实空态）、

  - 邀请状态需可辨识：**待接受 / 已激活 / 发送失败 / 已撤销 / 已过期**。

## R9 非功能约束

- **性能/规模预期**：
  - [设计] 邀请提交应在 1 秒内给出可感知反馈；邮件发送异步但需明确回执状态。
  - [原型] 组织规模量级为**数十人**（48 位成员），成员表需支持筛选与分页，
    但不必按万人级设计。
- **安全/隐私/合规**：
  - 激活令牌为**高熵随机值**，不可预测；一次性且服务端可吊销。
  - 密码加盐哈希存储，永不明文记录或回显；传输强制 HTTPS。
  - 激活页在完成前**不得回显组织成员名单**或任何其它成员的信息。
  - 受邀人邮箱属个人数据，须纳入组织的留存与删除策略
    （对照 D-14 的五个可配置参数与 D-15 的两级 SLA）。
  - [待确认] 密码强度策略与是否强制 MFA——与 UC-1.1 / UC-1.5 同一条待确认项，需一并定稿。
- **兼容与降级要求**：
  - 响应式 Web；激活流程移动端可完整走完。
  - 邮件服务不可用时明确失败，不得让管理员以为邀请已发出。

## R10 已知约束 / 依赖

- **内部依赖**：**UC-1.5**（先有组织与首个管理员才谈得上邀请第二个人）、
  **UC-0.3**（组织角色与团队的本体定义）、**UC-1.1**（激活后用邮箱 + 密码登录）。
- **被依赖**：**UC-1.3**（项目侧只能从**已存在的组织成员**里挑内部参与者）、
  后台全部按角色/团队分权的模块（Agent / Skill / 模型 / MCP / 画布模板 / 蓝本的
  「全组织可用 / 仅某团队」可见性范围）、配额与降级策略。
- **跨模块契约**：账号、组织、组织成员、组织角色、团队必须与 UC-1.5 使用**同一套标识**；
  「团队」必须是可被资源可见性范围引用的一等实体，不能只是成员表上的一个字符串。

- **[待确认]** **团队清单由谁维护、能否增删改**——
  [原型] 只见三个固定值（能源组 / 平台组 / 供应链组），未见「新建团队」入口。
  **分两层看**：`成员与配额 → 成员配额`标签页已逐字段抽取，**其中确实没有团队维护入口
  （原型确认缺失）**；同屏的 `用量监控` 与 `限额策略` 两个标签页**尚未展开（未探明）**，
  团队维护是否落在那里需下一轮补抽取确认。
- **[待确认]** **一人能否归属多个团队**（对照 UC-0.3 同一条待确认项）。
- **[待确认]** **激活链接的有效期**与**重发频率限制**；
  与 UC-1.5 的「验证链接 24 小时」是否统一取值。
- **[待确认]** 点击一次性链接是否**已足以证明邮箱所有权**，还是仍需再发一封验证邮件
  （UC-1.5 走的是「先填资料 → 收验证链接」，本用例是「先收链接 → 再填资料」，顺序相反）。
- **[待确认]** **一人多组织**的切换模型（对照 UC-17.4「同一人在两组织是两套权限」）——

- **[待确认]** 后台是否支持**批量邀请**（项目侧 UC-1.3 已有「逗号分隔」批量入口）。

- **[待确认]** 组织配额用尽时是否硬阻断新邀请（R4-E5）。

## R11 切分提示（给 requirement-author）

- 建议先拆「组织邀请模型（邮箱 + 角色 + 团队 + 状态）→ `[邀请成员]` 与服务端校验 →
  **一次性激活链接签发与核销** → 新用户激活（设密码）与已有账号加入两条分支 →
  **组织成员创建与角色/团队写入（事务性）** → 待接受状态与 `[重发]` → 撤销邀请 →
  成员表的角色与团队两列 → 审计 → 自动化验收」。
- **「激活与成员创建的原子性」必须独立成 feature 并有并发验收**——
  与 UC-1.5 的「一码一组织」是同一类事务性风险。
- **「链接身份以服务端为准、篡改无效」（AC5）必须独立成 feature**，用接口断言验收；
  这是本用例最大的越权面：链接里明文写着角色，客户端可改。
- **「邀请权 ≠ 阅读权」（D-18）不在本用例实现**，但本用例的验收要能证明
  「新邀请的管理员没有自动获得任何项目内容读取权」——这条断言放在 V8。
- **优先级 / 先后依赖**：P0；**5 点**；迭代 1 · 能进场；
  **必须晚于 UC-1.5**（先有组织），**早于 UC-1.3**（项目侧要从组织成员里挑人）。
- 对 P0 必做链路优先实现成功态、权限态与数据闭环，异常态不得延期到上线后。

## R12 AI Ready 验收线索

以下行为应可由自动化测试、接口断言或可复现人工步骤验证：

- V1（成功态）：**AC1** —— 不存在任何自助加入已有组织的接口；
  未持有效激活链接的用户无法把自己加进任何组织（穷举组织 ID 亦不可）。
- V2（成功态）：**AC2** —— 管理员以「顾问 + 供应链组」邀请一个新邮箱，
  受邀人激活后，成员表出现该行且**角色为顾问、团队为供应链组**，
  该成员的会话上下文中这两项已就位（可被 UC-1.4 的鉴权中间件直接消费）。
- V3（成功态）：**AC3** —— 同一条激活链接连续用两次，第一次成功，第二次被拒绝；
  `[重发]` 后**旧链接立即失效**、新链接可用。
- V4（成功态）：**AC4 待接受状态** —— 邀请发出后成员表出现
  `顾问(待激活) · 待接受邀请 · 已发送 N 天 · [重发]`；
  该成员**计入名册总数但不计入活跃成员计数**；激活后两个计数同步更新。
- V5（安全态）：**AC5 篡改无效** —— 把链接中的角色参数由 `顾问` 改为 `管理员`
  （或改组织 ID、改团队）后激活，实际授予的仍是**服务端记录的原始值**；
  篡改尝试写安全审计。
- V6（成功态）：**已有账号加入** —— 用一个已在别的组织存在的邮箱激活，
  **不新建账号**，该账号同时归属两个组织，且两边的角色与团队互不影响。
- V7（权限态）：以**项目负责人**与**顾问**身份调用 `[邀请成员]` 接口均被拒绝；
  只有管理员成功。非管理员访问「成员与配额」显示无权限态。
- V8（权限态 · D-18）：新激活的**管理员**在其**无项目角色**的项目中，
  内容读取一律被拒绝；其查询他人个人层只返回**计数**，内容字段不存在于响应体中。
- V9（原子性/并发态）：两名管理员同时邀请同一邮箱，只产生**一条**有效邀请与**一条**成员行；
  激活过程中断（模拟事务失败）后，不残留「令牌已核销但成员不存在」的状态。
- V10（安全态）：激活链接无效 / 过期 / 已使用 / 已撤销四种情况返回**完全相同**的响应，
  且响应中不含组织名称或任何成员信息。
- V11（空态）：刚由 UC-1.5 创建的新组织，成员表只有创建者一人，
  显示真实空态与「邀请成员」下一步，不生成示例成员。
- V12（依赖失败）：模拟邮件服务不可用，界面明确失败、邀请记录标为「发送失败」并可重试，
  **不产生可激活的链接假象**。
- V13（撤销态）：撤销未接受的邀请后，该链接立即失效，成员表移除该行，事件可审计。
- V14（审计态）：邀请、重发、撤销、激活、角色变更、团队变更六类事件
  均可按操作者、时间、对象和结果检索；篡改链接与非管理员调用邀请接口也有安全审计记录。
