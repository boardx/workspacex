# 原始需求（细化）— UC-14.4 决策台账

> 所属：阶段三 · 跨项目与对外 / M14 组织大脑
> 来源：原型 `大脑 → 决策台账` 子标签（「42 个决策 · 2 个等我签字 · 9 个待复盘 ·
> **拍板栏只能是人名**」）；`大脑 → 三层关系总览` 的「枢纽：决策是三层之间唯一的搬运工」；
> `大脑 → 我的大脑` 的「我的判断记录：34 我拍板的决策 ｜ 21 复盘为对 ｜ 9 待验证 ｜ 4 被推翻」。
> **补写缘由**：原 M14 三份 UC 只覆盖「写回 / 调用 / 沉淀」，**没有决策这个对象**。
> 而原型把决策定义为三层记忆之间唯一的搬运工——没有决策台账，UC-14.5 的晋升准入
> （D-32「支撑过一个被签字的决策」）在数据上无法成立。本 UC 是 D-24 MVP 三件之第一件。

> 口径（四标记）：**[原型]** ＝ `WorkspaceX Standalone.html` **运行态实际存在**的行为（有界面可查，依据 scratchpad 的 proto-01~10 抽取档案）；**[Backlog]** ＝ `Backlog Use Case.html` 的**文档要求**（原型未必实现）；**[设计]** ＝ 依据前两者反推补全，**需人类确认**；**[待确认]** ＝ 不应由实现者自行决定。
> 元数据：优先级 **P0**；估点 **8**；建议迭代 **阶段三 · 迭代 11 · 跨项目复用**。
>
> **[裁决 D-24]** 14-brain 的 phase-3 范围收敛为 MVP 三件：**决策台账（本 UC）**、
> 五态机晋升（UC-14.5）、检索可审查（UC-14.6）。

## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-14.4 / 决策台账
- **Actor**：**拍板人**（持签署授权的人类，通常是项目负责人或合伙人）、**项目负责人**、
  **方法负责人**；**agent 为受限参与方**（可写建议/证据/复盘素材，不可拍板）。
- **目标**：[原型] 把所有项目的决策记在**一本账**上；每条决策必须有**拍板的人**、
  **当时的依据强度**、**复盘结论**——复盘为对且给了有效期，才有资格进入晋升队列。
- **本用例结果**：组织内任一决策都可被检索、可展开其支持/反对依据、可追到拍板人与签字时间；
  已签字的决策成为「可被引用的依据」，并自动进入复盘队列。
- **系统边界**：决策对象与状态机、签字动作与授权校验、「等我签字」一页视图、
  依据强度聚合、复盘四态、被推翻后的降级与级联打标。
- **核心数据对象**：决策、拍板人、支持/反对依据引用、依据强度、影响面、等待方（人与 agent）、
  复盘记录、引用关系、降级标记。

## R2 前置条件 / 触发条件

- **前置条件**：
  - 请求者持有效身份，且对目标项目有项目角色（观察者仅只读，见 R5）。
  - 候选决策已由人或 agent 从转写/推演/对话中提出，并携带可追溯来源。
  - [原型] 签字动作要求拍板人持**该类决策的签署授权且在有效期内**
    （对照项目工作台「你有此类决策签署授权 · 有效期至 8/31」）。
- **触发条件**：
  - [原型] 候选决策产生（转写抽取、推演链决策节点、项目成果沉淀的「结论与决策」）。
  - [原型] 拍板人打开 `大脑 → 决策台账` 的「等我签字」。
  - [设计] 复盘到期（复盘状态「待验证 · 8/08」的日期到达）。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

1. **系统处理**：把候选决策汇入台账，状态为**待签字**。系统同时聚合它的依据：
   [原型] 支持 N 条与其**最强置信度**、反对 N 条与其最强置信度（**反对必须留**，不得筛除）。
2. **拍板人操作**：打开「**等我签字**」一页视图。**系统响应**：[原型] 在**同一屏**给出四组信息，
   不要求用户翻页：
   ① 决策问句本身；
   ② **支持 N 条·最强 x.x ｜ 反对 N 条·最强 x.x**（各自可展开到原始证据）；
   ③ **如果错了**：影响面（成本结构重算 · 影响 N 个已发结论）；
   ④ **谁在等**：`<agent> 已停 N 分`（AI 停在审批点不会绕过人）与 `客户汇报 <日期>`。
3. **拍板人操作**：选择 `[签字并记入台账]` / `[要求补证据]` / `[看完整推演链]`。
   **系统响应**：校验签署授权与有效期；签字成功后**记录拍板人姓名、时间、当时依据快照**，
   决策转为 **已签字**。
4. **系统处理**：[原型]「签字后这条决策成为**可被引用的依据**，并**进入复盘队列**」——
   系统写入引用资格标记，并按 R7 生成复盘任务（默认复核日期见 R7）。
5. **拍板人/方法负责人操作**：到期后录入**复盘结论**。**系统响应**：复盘四态取值
   [原型] `待验证 · <日期>` / `已验证` / `已验证 · 已晋升` / `被推翻`；
   状态为「已验证」时，其支撑的知识条目才**够格进入 UC-14.5 的晋升队列**（D-32）。
6. **系统处理（被推翻分支）**：[原型]「**被推翻的决策最有价值**」——把该决策支撑过的
   组织层条目**降级**，并**给所有引用过它的项目打标**，同时把该负面结论转为反例/教训资产。
7. **系统收口**：校验 AC1「台账每一行都有人名拍板，无一行由 agent 拍板」；
   记录操作者、时间、对象、结果与来源，并刷新台账计数（待签字 / 待复盘 / 被推翻）。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[原型] **要求补证据**——`[要求补证据]` 是「等我签字」卡上的三个按钮之一。
    [设计] 点击后决策退回为待签字并生成一条任务派给指定 agent 或人，等待方写入「谁在等」——
    该行为原型未渲染；「[派 Scout 补第三个样本]」出自**组织大脑的冲突成对召回区**，属另一屏另一对象，
    只作类比、不构成本处证据。
  - A2：[原型] **疑似结论不进台账**——被 agent 判为「像结论但没人拍板」的语句单列展示，
    需人显式提升为候选决策才入账（对照项目工作台「另有 3 条被 Echo 判为『像结论但没人拍板』」）。
  - A3：[设计] 拍板人不具备该类决策的签署授权时，提供 `[请他签署]` 转派入口，
    转派动作本身留痕。
  - A4：[设计] 台账为空时展示真实空态与「从哪里产生第一条决策」的入口，
    不生成示例数据冒充真实结果。
- **异常流程**：
  - E1：[原型] **agent 尝试写入拍板栏**——服务端拒绝（不是前端隐藏），返回明确错误并记安全审计。
  - E2：[设计] 签署授权**已过有效期**时签字被拒，提示到期时间与续期路径；不得降级放行。
  - E3：[设计] 签字瞬间其依据发生变化（证据被撤回 / 版本更新）——**中止签字**并提示依据已变，
    要求重新确认当前依据快照。
  - E4：[设计] 两人同时对同一决策签字：只有一次成功，另一方收到明确失败并看到已生效的签字记录。
  - E5：[设计] 请求超时、网络中断或依赖不可用时保留输入与最后成功状态，明确失败原因并可安全重试；
    **不得产生「看起来签了但没入账」的半成品**。

## R5 权限与可见性

- **拍板人**：仅能对**其持有签署授权且在有效期内**的决策类型签字；签字不可代签、不可撤销
  （纠正走「被推翻」而非删除，见 R7）。
- **项目负责人**：可查看本项目全部决策与依据链，可发起「要求补证据」，可指派复盘负责人。
- **方法负责人**：可跨项目读台账（用于晋升评估），可录入复盘结论；不可签字（除非另持授权）。
- **组员 / 组长**：只看本项目内与自己相关的决策及其公开依据；不可签字。
- **观察者**：[原型] **纯只读**，仅可见已发布结论对应的决策条目与脱敏依据；
  不可展开原始转写、不可见「等我签字」视图。
- **agent**：可写建议、证据、复盘素材；**拍板栏、签字动作对 agent 永久关闭**（R7 硬约束）。
- **未登录、链接失效或未列出的角色**：默认无权限；接口不得返回越权数据，不能只依赖前端隐藏。

## R6 后置条件 / 不包含

- **正常后置条件**：
  - 决策以不可篡改的方式记入台账，含拍板人、签字时间、当时的依据快照。
  - [原型验收] AC1：**台账「拍板」列的取值恒为人名**；任何写入路径都无法让 agent 出现在该列。
  - [原型验收] AC2：「等我签字」一页视图在**单屏内**同时给出支持/反对条数与最强置信度、
    如果错了的影响面、谁在等（agent 已停时长 + 汇报日期）。
  - [原型验收] AC3：决策签字后即获得「可被引用」资格并出现在复盘队列。
  - [原型验收] AC4：一条决策被标为「被推翻」后，它支撑过的组织层条目被降级，
    且**所有引用过它的项目**都被打标。
- **失败后置条件**：不产生「看似已签」的记录；失败事件进入可观测日志与安全审计。
- **不包含**：
  - **推演链编辑器**（节点拖拽、边类型、模板偏离回写）——见本节末尾的模块级 backlog。
  - 决策的删除：台账**只增不删**，纠正通过「被推翻」状态与新决策实现。
  - 自动拍板、AI 代签、按规则自动通过——任何形式的自动签字都不在范围内。

## R7 业务规则（不随具体实现变化的硬性约束）

- [原型] **拍板栏只能是人名**：「agent 可以写建议、写证据、写复盘素材，但『拍板』这一栏只能是人名。」
  该约束必须在**服务端**强制，且对所有写入路径（API、批量导入、自动化规则）一致生效。
- [原型] **每条决策必须有三要素**：拍板人 + 依据强度 + 复盘结论。缺复盘结论的决策
  **不得进入晋升队列**（与 D-32 联动）。
- [原型] **反对证据必须保留**：依据强度聚合中反对条目不得被筛除或折叠隐藏，
  必须与支持条目同时可见（对照 UC-14.6 R7）。
- [原型] **签字后才成为可被引用的依据**——签字是引用资格的闸门。
- [设计] **签署授权有时效**：签字校验「决策类型 × 授权人 × 有效期」三元组，过期即拒。
- [原型] **被推翻触发级联**：降级其支撑的组织层条目 + 给所有引用过它的项目打标；
  被推翻的知识**不删除**，转为反例/教训资产。
- [设计] **台账只增不删**，签字记录与依据快照不可覆盖（对照 UC-17.1「审计日志不可删除」）。
- [待确认] 复盘默认到期天数（原型示例为签字后约两周，如「待验证 · 8/08」）与复盘负责人默认取值。
- 所有权限判断必须在服务端执行；隐藏入口只是界面表现，不构成安全控制。
- 签字、要求补证据、录入复盘、标记被推翻、级联打标，全部必须记审计事件并显示影响范围。

## R8 界面线索

- **前端入口**：[原型] `大脑 → 决策台账`；项目侧入口为 `项目 → 成果沉淀 → 结论与决策`
  （同一批数据的项目作用域视图）。
- **信息架构**：[原型] 头部计数条「42 个决策 · 2 个等我签字 · 9 个待复盘」→
  「等我签字」卡片区 → 台账表格。
- **推荐交互**：
  - [原型] **台账表格五列**：决策 ｜ 项目 ｜ 拍板 ｜ 依据强度 ｜ 复盘；每行有 `[支持链]`。
  - [原型] 「等我签字」卡片按钮组：`[签字并记入台账] [要求补证据] [看完整推演链]`。
  - [原型] 复盘列以状态标呈现四态：`待验证·<日期>` / `已验证` / `已验证·已晋升` / `被推翻`。
  - [设计] 签字为不可逆高影响动作，必须二次确认并明确列出「你正在把这条设为可被引用的依据」。
- **必须呈现的状态**：默认态、加载态、空态、校验失败态（授权过期/依据已变）、依赖失败态、
  无权限态、成功态。
- **原型参考**：`phases/requirements/WorkspaceX Standalone.html` — 大脑 → 决策台账
- **UI sign-off**：[原型] 台账列表与「等我签字」卡片**已存在，不必补画**；
  **原型待补**：`[看完整推演链]` `[支持链]` **两个按钮已渲染、目标屏未见**（按钮在、行为未接线；
  属推演链编辑器范围，见 backlog），实现前需就「点开后看到什么」补接线/补画。

## R9 非功能约束

- **性能/规模预期**：[设计] 台账按项目/拍板人/时间分页检索，1 秒内首屏可见；
  「等我签字」的依据聚合（支持/反对/最强置信度/影响面）应在 2 秒内完成，
  超时降级为「依据加载中」但**不得允许在依据未加载完成时签字**。
- **安全/隐私/合规**：签字记录、依据快照按审计保留期存储（见 UC-17.3）；
  跨项目读台账受组织角色与团队可见性范围约束（见 `uc-0-3`）。
- **兼容与降级要求**：响应式 Web；移动端至少保证「等我签字」可读并可执行签字/要求补证据。
  鉴权或授权校验服务不可用时**一律拒绝签字**，不得降级放行。

## R10 已知约束 / 依赖

- **内部依赖**：UC-0.3（两层角色）、UC-13.1/13.2（结论与决策、验收是引用资格闸门）、
  UC-9.x（知识图谱的证据与假设）、UC-17.1（审计事件）。
- **被依赖**：**UC-14.5**（晋升准入 D-32 直接读本 UC 的「已签字 + 复盘已验证」）、
  UC-14.6（检索时的「历史决策与复盘」注入段）、UC-14.1（写回来源）。
- **跨模块契约**：决策 ID、依据引用（指向不可变快照，见 D-30）、拍板人身份、
  复盘状态必须在项目侧与组织侧使用**同一套标识**，不得各存副本。
- **[待确认]** 签署授权的授予者与授予路径（谁能给谁签署授权、按决策类型还是按金额/影响面分级）。
- **[待确认]** 复盘负责人缺省规则与逾期未复盘的处置（是否阻断晋升、是否升级提醒）。

## R11 切分提示（给 requirement-author）

- 建议先拆「决策对象与状态机 → 依据聚合（支持/反对/最强置信度/影响面）→ 签字与授权校验 →
  『等我签字』一页视图 → 复盘四态与队列 → 被推翻的降级级联与打标 → 审计 → 自动化验收」。
- **「拍板栏只能是人名」必须独立成 feature 并有独立的服务端拒绝验收**，
  不得与签字 UI 合并；它是 MVP-1 的立身之本。
- **「被推翻的级联打标」独立成 feature**：它同时被 UC-14.5 的降级路径复用。
- **优先级 / 先后依赖**：P0；8 点；阶段三 · 迭代 11；**必须先于 UC-14.5**（晋升准入依赖它）。

## R12 AI Ready 验收线索

- V1（成功态）：AC1 —— 以 agent 身份（服务账号 / 自动化规则 / 批量导入三条路径）尝试写入
  `decision.decided_by`，**三次全部被服务端拒绝**；台账全表扫描，`拍板` 列无非人类主体。
- V2（成功态）：AC2 —— 请求「等我签字」接口，**单次响应**即包含
  支持条数与最强置信度、反对条数与最强置信度、影响面对象列表、等待方（agent 已停时长 + 汇报日期）。
- V3（成功态）：AC3 —— 决策签字后，其 `citable=true` 且出现在复盘队列；签字前引用它被拒绝。
- V4（成功态）：AC4 —— 把一条决策标为「被推翻」，断言：它支撑的组织层条目状态转为已降级，
  且引用过它的 N 个项目全部产生打标记录（N 与引用关系表一致）。
- V5（权限态）：逐一以拍板人（有授权/无授权/授权过期）、项目负责人、方法负责人、组长、组员、
  观察者、未授权用户调用签字与读取接口，返回严格符合 R5。
- V6（空态）：无决策时显示真实空态与产生第一条决策的入口，不生成伪数据。
- V7（校验失败态）：签字瞬间其依据证据被撤回，签字被中止并提示依据已变。
- V8（并发态）：两会话同时签同一决策，仅一次成功，另一方看到已生效签字，无双写。
- V9（审计态）：签字、要求补证据、复盘录入、被推翻级联四类事件均可按操作者、时间、对象检索；
  agent 越权写拍板栏的尝试有安全审计记录。
