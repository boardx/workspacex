# 原始需求（细化）— UC-15.2 客户反馈回流

> 所属：阶段三 · 跨项目与对外 / M15 客户侧门户
> 来源：`Backlog Use Case.html` 的 UC-15.2；**回流载体**取自原型
> `项目 → 待办`（项目内看板，四列：待办 / 进行中 / 待复核 / 已完成）的**来源徽标**机制——
> [原型] 卡片带来源徽标「**现场 / 会前任务 / 决策树 / 报告缺料 / 转写 / 研究**」，
> 且「**卡片来源自动同步 …… 状态改了会回写到原处**」。

> 口径（四标记）：**[原型]** ＝ `WorkspaceX Standalone.html` **运行态实际存在**的行为（有界面可查，依据 scratchpad 的 proto-01~10 抽取档案）；**[Backlog]** ＝ `Backlog Use Case.html` 的**文档要求**（原型未必实现）；**[设计]** ＝ 依据前两者反推补全，**需人类确认**；**[待确认]** ＝ 不应由实现者自行决定。
> 元数据：优先级 **P1**；估点 **5**（**不变**）；建议迭代 **阶段三 · 迭代 12 · 对外与预演**。
>
> **[2026-07-27 按 D-22 A 修订：5 点不变，理由须写清]**
> 15-portal 的另外两个 UC 都因「复用已有能力」而瘦身（15.1 5→3、15.3 3→2），
> **本 UC 不减点**，原因是：**[原型] 观察者是纯只读，「原始转写、私聊与任何操作按钮都关掉了」——
> 连评论入口都没有**。因此观察者视角**替代不了**反馈回流，这是**真正的新增能力**，
> 不是既有能力的投影。
> **实现上可蹭待办看板的来源徽标机制**：新增**第七类来源徽标「客户反馈」**，
> 复用其「自动汇入 + 状态回写到原处」的既有链路（见 R3 第 2 步与 R10）。

## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-15.2 / 客户反馈回流
- **Actor**：**客户方观察者**（唯一可写的场景）、**项目负责人**（处理与答复）、**引导师**
- **目标**：给客户**唯一的一个写入口**——对某条已发布结论提出疑问或补充材料——
  并让这条反馈**自动汇入项目待办看板**、被指派、被答复、且客户能看到闭环。
- **本用例结果**：每条客户反馈在项目内以一张带**「客户反馈」来源徽标**的卡片存在，
  状态变化回写到客户侧，客户能查到处理结果。
- **系统边界**：客户侧反馈提交入口（**观察者权限模型的唯一例外，须显式开孔**）、
  反馈对象与其锚点（挂到哪条结论/报告节）、汇入待办看板与**第七类来源徽标**、
  指派与答复、状态回写与客户侧闭环视图。
- **不属于本 UC 的边界**：只读链接与权限（UC-15.1）、进度投影（UC-15.3）、
  待办看板本身（UC-11.x / 项目内看板）。
- **核心数据对象**：客户反馈、反馈锚点（结论/报告节/产出物 + 版本）、待办卡片（来源＝客户反馈）、
  指派人、答复、处理状态、客户可见的闭环记录。

## R2 前置条件 / 触发条件

- **前置条件**：
  - 用户已建立可校验的正式或临时身份，且拥有目标组织、项目、小组或资源的访问权。
  - 目标资源存在且未被删除/冻结；依赖能力“成果沉淀、洞察报告、登录管理”可用，或界面能明确显示其不可用状态。
  - 若动作涉及个人数据、录音、原始材料或跨范围读取，相应授权与留存策略已生效。
- **触发条件**：
  - [Backlog] 客户在门户上评论。
  - 系统从 **客户门户 → 反馈** 进入本流程，并携带当前组织、项目、小组、角色和资源标识。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

1. **客户方观察者操作**：在某条**已发布**结论/报告节/产出物上提出疑问或补充材料。
   **系统响应**：校验身份与发布范围；**把反馈锚定到该内容的固定快照版本**
   （不是「当前最新版」，见 R7）；成功后生成一条客户反馈记录并给出提交回执。
   > ⚠ 这是**观察者只读模型的唯一显式开孔**：除本入口外，客户侧不得出现任何写控件（R7）。
2. **系统处理（汇入看板 · 复用来源徽标机制）**：[设计] 反馈**自动汇入项目待办看板**，
   生成一张卡片，带**第七类来源徽标「客户反馈」**——
   [原型] 现有**六类**徽标为 现场 / 会前任务 / 决策树 / 报告缺料 / 转写 / 研究；
   **第七类是本 UC 新增，原型中不存在**。
   [原型] 复用既有链路「卡片来源自动同步 …… **状态改了会回写到原处**」——
   本 UC**不新建一套反馈工单系统**。
   [裁决 D-39] 卡片**负责人恒为人**（默认指派给**项目负责人**）；若派 agent 起草答复，
   agent 记在独立的「执行者」字段。
3. **项目负责人操作**：处理并**答复**。**系统响应**：答复落库并**回写状态到原处**；
   [原型] 反馈**不改动已发布内容，只生成新版本建议**——
   若需修改已发布内容，走「已发布给客户的内容需人工确认后替换」流程（D-19）。
4. **系统处理（闭环可见）**：客户侧显示该条反馈的**处理状态与答复**；
   状态取值与看板列一致（待办 / 进行中 / 待复核 / 已完成），
   [设计] 客户侧以「已收到 / 处理中 / 已答复」三档呈现，不暴露内部列名。
5. **系统收口**：校验 AC1「每条客户反馈都有可查的处理结果」与
   AC2「反馈卡片带『客户反馈』来源徽标且状态回写到客户侧」；
   记录操作者、时间、对象、结果与来源，并刷新看板与通知状态。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[Backlog] 反馈不改动已发布内容，只生成新版本建议。系统不得丢失当前上下文，且需提示用户当前采用了哪条替代路径。
  - A2：[设计] **反馈附带材料**——客户可上传补充材料；材料进入项目材料库并**标来源为客户方**，
    受该项目的留存策略（UC-17.3）与「禁止用于训练」开关约束。
  - A3：[设计] **反馈转为正式行动项**——项目负责人可把反馈卡片升级为行动项，
    保留其「客户反馈」来源徽标与原始锚点，不断链。
  - A4：[设计] **反馈被判定为无需处理**——必须给出答复理由后才可关闭；
    **不允许静默关闭**，客户侧仍能看到「已答复：不予调整 · 理由 …」。
- **异常流程**：
  - E0：[设计] 反馈锚定的内容**已被新版本替代**时，反馈仍锚在**原快照**上，
    并在卡片上提示「该内容已更新至 vN」；**不得把反馈自动迁移到新版本**。
  - E0b：[设计] 客户的只读链接在反馈处理期间被撤销/过期 → 已提交的反馈**不受影响**，
    但客户无法再查看闭环；重新签发链接后可恢复查看。
  - E1：[设计] 请求超时、网络中断或依赖不可用时，保留用户当前输入与最后成功数据，明确失败原因，并提供安全重试。失败不得被呈现为成功，也不得产生无法追溯的半成品。
  - E2：[设计] 同一资源被并发修改时不得静默覆盖；系统提示版本已变化，并允许刷新、对比或重新提交。失败不得被呈现为成功，也不得产生无法追溯的半成品。
  - E3：[设计] 权限在操作过程中被撤回时立即终止后续写操作；已完成步骤按审计规则保留，未提交输入留在本地草稿并提示重新授权。

## R5 权限与可见性

> 权限内核复用 `phase-1/00-core/uc-0-3` 的项目角色「观察者」（见 UC-15.1）。
> **本 UC 是观察者只读模型的唯一显式例外**，该例外必须在权限模型里被明确定义为
> 「观察者对 `client_feedback` 对象有 create 权限」，**不得以「客户是另一种角色」的方式实现**。

- **客户方观察者**：只读已向其发布的结论、产出、报告、进度与脱敏聚合；
  **仅可创建客户反馈**，且只能对**在其发布范围内**的内容创建；
  可读自己提交的反馈及其答复；**不可**读他人的反馈、不可改动项目正式内容、
  不可看到内部处理讨论与指派细节。
- **项目负责人**（组织角色）：反馈的默认负责人；可指派、答复、关闭、升级为行动项。
- **引导师**（项目角色）：可参与处理并答复。
- **agent**：可起草答复、可归类反馈；**不得作为反馈卡片的负责人**（D-39），
  也**不得代替人关闭反馈**。
- **内部观察者**：与客户方观察者同权限，但其反馈在内部视图中**显示提出人**。
- **未登录、链接失效或未列出的角色**：默认无权限；接口不得返回越权数据，不能只依赖前端隐藏。

## R6 后置条件 / 不包含

- **正常后置条件**：
  - 形成与本 use case 对应的正式记录或明确状态，并可从来源页面再次打开。
  - 所有跨模块回流均携带来源资源、版本、操作者/触发者、时间和可见范围。
  - [Backlog验收] AC1：每条客户反馈都有可查的处理结果。
  - [设计验收] AC2：反馈自动生成的看板卡片带**第七类来源徽标「客户反馈」**，
    且**状态变化回写到客户侧**（复用既有的来源同步链路，不新建工单系统）。
  - [设计验收] AC3：反馈**锚定在提交时的固定快照版本**上，内容升版后锚点不迁移。
  - [设计验收] AC4：**除本反馈入口外，客户侧不存在任何写接口**——
    对客户身份枚举全部写接口，除 `client_feedback:create` 外一律被拒。
- **失败后置条件**：
  - 不创建“看似成功”的正式记录；可重试内容保留为草稿，失败事件进入可观测日志。
  - 反馈提交失败时明确告知，不产生「客户以为提了但项目侧没有」的静默丢失。
- **不包含**：
  - 客户读取私聊、草稿、原始材料或内部过程细节；**客户读取他人反馈**。
  - **客户直接编辑已发布内容**——反馈只生成新版本建议。
  - **新建一套独立的反馈/工单系统**——复用待办看板与来源徽标机制。
  - **只读链接与权限**（UC-15.1）、**进度投影**（UC-15.3）。
  - 不扩展到本 use case 未声明的跨组织、跨客户或公开发布能力。

## R7 业务规则（不随具体实现变化的硬性约束）

- [Backlog] 反馈不改动已发布内容，只生成新版本建议。
- [原型 · 本 UC 不减点的理由] **观察者是纯只读——原始转写、私聊与任何操作按钮都关掉了，
  连评论入口都没有**。因此客户反馈是**新增能力**，不能由观察者视角替代。
- [设计] **唯一开孔原则**：客户侧只允许 `client_feedback:create` 这一个写权限；
  该例外必须写在权限模型里并可被逐接口验收（AC4），**不得用「客户是另一种角色」绕过**。
- [设计] **反馈锚定固定快照**：反馈绑定提交时的产出版本（D-30），内容升版后锚点不迁移，
  只在卡片上提示已更新。
- [设计] **复用来源徽标机制**：新增第七类来源「客户反馈」，
  沿用「自动汇入 + 状态改了会回写到原处」的既有链路。
- [裁决 D-39] **反馈卡片的负责人恒为人**；agent 记在独立的「执行者」字段，
  且 agent 不得关闭反馈。
- [设计] **不允许静默关闭**：判定无需处理也必须给出答复理由，客户侧可见。
- [裁决 D-19] 因反馈而修改已发布内容时，走「已发布给客户的内容需人工确认后替换」流程。
- [设计] 客户上传的补充材料受该项目的留存策略与「禁止用于训练」开关约束（UC-17.3）。
- AC1：每条客户反馈都有可查的处理结果。
- AC2：反馈卡片带「客户反馈」来源徽标且状态回写客户侧。
- AC3：反馈锚定固定快照。
- AC4：客户侧除反馈提交外无任何写接口。
- AI/Agent 生成的候选内容必须标识为机器产出，展示可追溯来源；来源不足时不得伪造结论。
- AI/Agent 的写回、覆盖、发布或高影响工具调用必须遵守原型中的批准点；未经确认只保留为草稿或候选。
- 所有权限判断必须在服务端执行；隐藏入口只是界面表现，不构成安全控制。
- 任何覆盖、删除、撤销、签署、发布、写回或停用动作都必须记录审计事件，并显示动作影响范围。

## R8 界面线索

- **前端入口**（客户侧，**确认缺失**）：**客户门户 → 反馈**（见 UI sign-off）。
- **前端入口**（内部侧，**已存在**）：[原型] `项目 → 待办`（四列看板，卡片带来源徽标）；
  本 UC 只需在其徽标枚举中**新增第七类「客户反馈」**。
- **信息架构**：[设计] 客户门户三屏之一：首页（UC-15.3）/ 成果与报告 / **反馈（本 UC）**。
- **推荐交互**：
  - [设计] 反馈入口挂在**内容旁**（某条结论 / 报告节 / 产出物），而不是一个孤立的留言板——
    锚点是反馈可被处理的前提。
  - [设计] 内部侧卡片形如「**[客户反馈]** <到期> <标题> <负责人>」，与现有六类徽标同构。
  - [设计] 客户侧状态用三档（已收到 / 处理中 / 已答复），不暴露内部列名与指派细节。
  - [设计] 沿用原型的左侧导航 + 中部工作区 + 右侧上下文/执行栏结构。
- **必须呈现的状态**：
  - 默认态、加载态、空态、校验失败态、依赖失败态、无权限态、成功态。
  - 涉及后台任务时显示排队/运行/需批准/完成/失败/已取消，并允许查看最近一次成功结果。
  - 涉及版本或发布时同时显示草稿状态、当前版本、来源版本和最后修改人。
- **原型参考**：
  - `phases/requirements/WorkspaceX Standalone.html` — 项目 → 待办（四列看板 + 六类来源徽标）
  - `phases/requirements/WorkspaceX Standalone.html` — 项目工作台 → 视角切换 → 观察者

- **UI sign-off**：
  - [原型] 内部侧（待办看板与来源徽标）**已存在，不必补画**；本 UC 只加一类徽标。
  - ⚠ **客户侧反馈屏确认缺失**（同 UC-15.1）：原型只有 `[预览客户版]` 空按钮，

  - [待确认] 客户反馈是否需要通知（邮件/产品内）以及通知模板。

## R9 非功能约束

- **性能/规模预期**：
  - [设计] 普通读取与本地校验应在 1 秒内给出可感知反馈；超过 1 秒显示加载状态，超过 10 秒的任务转为可离开页面的后台任务。
  - [设计] 列表、图谱、转写和审计记录必须分页或增量加载，禁止一次加载整个项目历史。
- **安全/隐私/合规**：
  - 最小权限、组织/项目/小组隔离、传输与静态加密、敏感字段脱敏、导出与 AI 读取留痕。
  - 原始材料、录音、转写、私聊、个人身份与客户数据按授权和留存策略处理。
- **兼容与降级要求**：
  - 响应式 Web；桌面端提供完整能力，移动端保证加入、查看、输入、投票/确认等现场关键动作。
  - WebSocket/实时通道不可用时降级为轮询并显示“非实时”；断网允许保留未提交输入，但不得伪装已同步。

## R10 已知约束 / 依赖

- **内部依赖**：[原型] 成果沉淀、洞察报告、登录管理；**UC-15.1**（只读链接与观察者权限）、
  **项目内待办看板**（来源徽标与状态回写链路）、UC-13.x（发布快照）、
  UC-17.2 + D-19（已发布内容的替换流程）。
- **跨模块契约**：身份与权限、来源引用、版本、任务状态、审计事件和通知必须使用统一标识，避免同一对象在各模块成为不可关联的副本。
  **来源徽标枚举**必须集中定义（六类 + 新增「客户反馈」＝七类），不得在门户模块另建一份。
- **技术约束**：[Backlog] 产品为响应式网页；完整离线模式、原生移动端、第三方 IM 与产品内自助计费在 backlog 中明确为范围外。
- **[待确认]** 客户反馈的通知渠道与模板；反馈是否有 SLA。
- **[待确认]** 单项目并发人数、组织数、材料量、音频时长和历史数据量尚未给出；容量与压测指标需在开发前定稿。
- **[待确认]** 通知渠道、消息模板、语言与时区策略未统一定义；本文仅承接原型明确写出的产品内/邮件行为。
- **[待确认]** 模型选择、提示词版本、质量阈值与人工复核责任人尚未指定。
- **[待确认]** 数据驻留地区、加密密钥策略、法定留存和删除证明格式需由合规负责人确认。

## R11 切分提示（给 requirement-author）

- 建议先拆“**反馈对象与锚点（绑定固定快照）** → **观察者权限的唯一开孔** →
  **第七类来源徽标 + 汇入看板 + 状态回写** → 答复与闭环视图 → 审计/通知 → 自动化验收”。
- **「唯一开孔」必须独立成 feature 并有独立的接口枚举验收（AC4）**：
  它是客户门户安全性的关键面，靠人眼审查不可靠。
- **「第七类来源徽标」应作为对既有看板模块的小改动提交**，不要在门户模块复制一套卡片。
- 单个 feature 应能在一次会话内实现并验证，不应把本 use case 的全部前后端与所有异常态塞进一个 feature。
- **优先级 / 先后依赖**：P1；**5 点（不变）**；阶段三 · 迭代 12 · 对外与预演；
  先满足“成果沉淀、洞察报告、登录管理”、**UC-15.1** 与项目内待办看板；
  **且必须在客户门户 3 屏补画并由人类确认之后开工**（D-22 A + ADR-003）。
- 对 P1 能力可在主链路稳定后实现，但合入时仍需覆盖本文全部验收状态。

## R12 AI Ready 验收线索

以下行为应可由自动化测试、接口断言或可复现人工步骤验证：

- V1（成功态）：AC1：每条客户反馈都有可查的处理结果 —— 提交一条反馈，答复后以客户身份查询，
  返回处理状态与答复内容；判定「无需处理」时仍返回理由，无静默关闭。
- V1b（成功态）：AC2 —— 断言反馈自动生成的看板卡片 `source = client_feedback`
  且徽标枚举长度为 7；把卡片从「进行中」拖到「已完成」，断言客户侧状态同步变为「已答复」。
- V1c（成功态）：AC3 —— 提交反馈后把被锚定的报告升到新版本，
  断言反馈仍指向原快照版本号，且卡片显示「该内容已更新至 vN」。
- V1d（权限/安全态）：AC4 —— 以客户方观察者身份**逐一枚举全部写接口**，
  断言除 `client_feedback:create` 外**全部被服务端拒绝**；
  并断言客户读取他人反馈被拒。
- V2（权限态）：逐一使用 客户方观察者、项目负责人、引导师、内部观察者、agent、
  未授权用户访问；返回数据和可执行动作严格符合 R5；
  **agent 被指派为反馈负责人的请求被拒（D-39）**。
- V3（空态）：无目标数据时显示真实空态与下一步，不生成伪数据。
- V4（依赖失败）：模拟网络/外部依赖失败，输入和最近成功数据保留，错误可解释且可重试。
- V5（并发态）：两名用户修改同一资源时不静默覆盖，并可识别最终版本。
- V6（审计态）：关键动作可按操作者、时间、对象和结果检索；越权尝试也有安全审计记录。
