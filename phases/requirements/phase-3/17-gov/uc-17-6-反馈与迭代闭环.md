# 原始需求（细化）— UC-17.6 反馈与迭代闭环

> 所属：阶段三 · 跨项目与对外 / M17 审计、合规与数据治理
> 来源：原型 `后台` → **`反馈与迭代`**（本周 23 条软件反馈 · 14 条 Agent 改进建议）：
> ```
> [打开迭代看板] [导出]
> 软件反馈（本周 23 条 · 5 条待处理）
>   [缺陷] 多人同时说话时说话人识别错乱  7 票
>     周宁：项目里三个人抢话，转录把两个人合成了一个。附了 40 秒音频片段。
>     [推送到开发 Agent] [查看附件]
>   [需求] 画布希望支持离线导出为 PPT 母版  14 票
>     已进入下个迭代 · 开发 Agent 已生成技术方案草案
>   [已修复] 移动端线程列表滑动卡顿  v2.14
>     开发 Agent 提交，人工复核通过，已灰度 100%
> Agent / Skill 改进反馈（来自消息级评价）
>   FC Facilitator · 打断时机过早 👎9 —— 9 位主持人反馈：在讨论未收敛时就提示投票。
>      建议把「提议收敛」的触发阈值从 3 次重复提及提高到 5 次，并要求先征询主持人。
>      [生成 skill 改进 PR] [看 12 个原始案例]
>   SC Scout · 引用页码偶发错位 👎4 —— PDF 双栏排版下页码定位偏移 1 页。已定位到解析器，等待修复。
> 迭代闭环：本月 14 条反馈 → 9 条已生成改进 PR → 6 条人工复核通过并上线 →
>           相关 skill 满意度平均 ＋7 个百分点。
> ```
> 反馈的**采集端**见 `项目 → 成果沉淀 → 审计与反馈` 的参与者反馈区：
> 「4.6 整体满意度/5 ｜ 92% 认为目标已达成 ｜ 3.9 AI 主持有用性/5 ／
> "AI 提醒收敛那次很关键，但打断得稍早。" **已推送到后台 Skill 改进队列**」。
> **补写缘由**：原 17-gov 四份 UC 完全没有覆盖**反馈 → 开发 Agent → PR → 人工复核 → 灰度**
> 这条自迭代闭环，而它是原型后台九子模块中**独立的一个模块**，且与
> 03-skill / 04-agent 的质量治理直接相连。缺它，「Agent/Skill 越用越好」这一产品主张
> 在系统中没有任何承载。

> 口径（四标记）：**[原型]** ＝ `WorkspaceX Standalone.html` **运行态实际存在**的行为（有界面可查，依据 scratchpad 的 proto-01~10 抽取档案）；**[Backlog]** ＝ `Backlog Use Case.html` 的**文档要求**（原型未必实现）；**[设计]** ＝ 依据前两者反推补全，**需人类确认**；**[待确认]** ＝ 不应由实现者自行决定。
> 元数据：优先级 **P1**；估点 **8**；建议迭代 **阶段三 · 迭代 12 · 对外与预演**。

## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-17.6 / 反馈与迭代闭环
- **Actor**：**任意使用者**（提反馈 / 打消息级评价）、**组织管理员**（分诊与推送）、
  **人工复核人**（PR 复核与放行）、**开发 Agent**（起草方案与提交 PR）
- **目标**：[原型] 让「用得不好」变成**可追踪、可度量、可闭环**的改进——
  软件缺陷与需求进迭代看板；Agent/Skill 的问题由**消息级评价**聚合成改进建议，
  经**开发 Agent 起草 → 人工复核 → 灰度**回到产品里。
- **本用例结果**：每条反馈都有状态与去向；每条 Agent/Skill 改进建议都能追到
  **原始案例**与**具体的阈值/提示词改动**；闭环转化率与满意度变化可被度量
  （[原型]「14 条 → 9 条 PR → 6 条上线 → 满意度 ＋7 个百分点」）。
- **系统边界**：**两类反馈的采集**（软件反馈 / **消息级评价**）、投票与聚合、
  分诊与状态机、**推送到开发 Agent 并生成改进 PR**、**人工复核与灰度**、
  **闭环度量**、参与者反馈的采集与推送。
- **不属于本 UC 的边界**：**客户反馈**（→ UC-15.2，那是对项目成果的反馈，不是对产品的）、
  skill/agent 的上线门禁本身（→ 03-skill / 04-agent）、审计事件（→ UC-17.1）。
- **核心数据对象**：软件反馈（类型 / 票数 / 附件 / 状态）、**消息级评价**（👍/👎 + 原始案例）、
  Agent/Skill 改进建议（含具体参数改动）、改进 PR、复核记录、灰度状态与比例、
  闭环度量指标、参与者反馈（满意度 / 目标达成率 / AI 有用性 + 文字）。

## R2 前置条件 / 触发条件

- **前置条件**：请求者是本组织成员（或项目参与者，对参与者反馈而言）；
  被评价的消息/skill/agent 存在且可追溯。
- **触发条件**：
  - [原型] 用户提交**软件反馈**（缺陷 / 需求）或为他人的反馈**投票**。
  - [原型] 用户对某条 **AI 消息**打评价（👍/👎），系统聚合到对应 skill/agent。
  - [原型] 项目结束后参与者填写**参与者反馈**（满意度 / 目标达成 / AI 主持有用性 + 文字）。
  - [原型] 管理员点 `[推送到开发 Agent]` 或 `[生成 skill 改进 PR]`。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

### R3.a 软件反馈

1. **使用者操作**：提交反馈，选类型（[原型] **缺陷 / 需求**），可**附材料**
   （[原型]「附了 40 秒音频片段」）。**系统响应**：入库并进入待处理队列；
   反馈**自动携带上下文**（发生位置、版本、操作者）以便复现。
2. **使用者操作**：对已有反馈**投票**。**系统响应**：[原型] 票数聚合并作为排序依据
   （示例：缺陷 7 票 / 需求 14 票）。
3. **管理员操作**：分诊。**系统响应**：状态机流转——
   [原型] 状态取值至少包含 **待处理 → 已进入下个迭代 → 已修复（带版本号，如 v2.14）**；
   动作 `[推送到开发 Agent]` `[查看附件]`。
4. **系统处理**：[原型] 推送后**开发 Agent 生成技术方案草案**；
   [原型] 已修复项标注实现路径：「**开发 Agent 提交，人工复核通过，已灰度 100%**」。

### R3.b Agent / Skill 改进反馈（来自**消息级评价**）

5. **使用者操作**：对某条 AI 消息打 👍/👎（**消息级**，不是对整个 agent 打分）。
   **系统响应**：把评价挂到该消息所用的 **skill + agent + 上下文**上，保留**原始案例**。
6. **系统处理（聚合成可执行建议）**：[原型] 同类负评聚合后给出**具体的改动建议**，
   而不是一句「表现不好」。原型示例：
   > 「FC Facilitator · 打断时机过早 **👎9** —— 9 位主持人反馈：在讨论未收敛时就提示投票。
   > **建议把『提议收敛』的触发阈值从 3 次重复提及提高到 5 次，并要求先征询主持人。**」
   建议必须包含：**现象 / 负评数 / 归因 / 具体参数或提示词改动**，
   并提供 `[看 N 个原始案例]` 下钻。
7. **管理员 / 复核人操作**：点 `[生成 skill 改进 PR]`。**系统响应**：
   开发 Agent 生成改动 PR（提示词 / 阈值 / 输出约束），**进入人工复核**。
8. **系统处理（复核与灰度）**：[原型] **人工复核通过后灰度上线**，灰度比例可见
   （示例「已灰度 100%」）。**开发 Agent 不得直接上线**（见 R7）。
9. **系统处理（回归到门禁）**：skill 改动上线仍须走 03-skill 的
   **安全扫描（自动）+ 方法论审核（人工）** 门禁；本 UC 不绕过它。

### R3.c 参与者反馈与闭环度量

10. **系统处理**：[原型] 项目侧采集**参与者反馈**——
    「**4.6 整体满意度/5 ｜ 92% 认为目标已达成 ｜ 3.9 AI 主持有用性/5**」+ 文字反馈；
    文字反馈中涉及 AI 行为的**自动推送到后台 Skill 改进队列**
    （[原型]「已推送到后台 Skill 改进队列」）。
11. **系统处理（闭环度量）**：[原型] 计算并公开闭环指标：
    **本月 N 条反馈 → M 条已生成改进 PR → K 条人工复核通过并上线 →
    相关 skill 满意度平均 ±X 个百分点**。
12. **系统收口**：校验 AC1（每条反馈有状态与去向）、AC2（改进建议可追到原始案例与具体改动）、
    AC3（开发 Agent 不得直接上线，必须人工复核）；
    记录操作者、时间、对象、结果与来源。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[设计] **导出** —— `[导出]` 按钮存在，但**点击后无目标屏（原型待补）**；导出内容与格式无原型依据。
  - A2：[设计] **迭代看板** —— `[打开迭代看板]` 按钮存在，但**点击后无目标屏（原型待补）**；看板形态无原型依据。
  - A3：[设计] **建议被驳回** —— 复核人可驳回改进 PR，须附理由；理由归档不可覆盖，
    且原反馈**回到待处理**而非关闭。
  - A4：[设计] **灰度回滚** —— 灰度期间指标恶化时可回滚；回滚事件与原因留痕，
    对应反馈回到待处理。
  - A5：[设计] 无反馈时展示真实空态与提交入口，不生成示例反馈。
- **异常流程**：
  - E1：[设计] **开发 Agent 试图跳过人工复核直接上线** → 服务端拒绝并记安全审计
    （与 D-27「R2/R3 必须人接受」、UC-14.4「拍板栏只能是人名」同源）。
  - E2：[设计] **反馈附件含客户机密或 PII**（如原型的「40 秒音频片段」）→
    附件受该项目的留存策略与访问控制约束（UC-17.3）；
    推送到开发 Agent 时**必须先脱敏或降级为不含原始音频的描述**（D-16）。
  - E3：[设计] **消息级评价指向的消息已被删除或撤回** → 评价保留但标注「原始案例不可用」，
    **不得因此伪造案例**。
  - E4：[设计] **改进建议缺少具体改动**（只有「表现不好」）→ 不得生成 PR，
    退回并要求补充归因与参数。
  - E5：[设计] 请求超时或依赖不可用时保留用户输入，明确失败原因并可安全重试。

## R5 权限与可见性

- **任意使用者**：可提交软件反馈、投票、打消息级评价；可查看自己提交的反馈及其状态；
  [待确认] 是否可查看他人反馈的全文（本文按「可见标题与票数、不可见他人附件」书写）。
- **参与者（含现场组员）**：可提交项目侧的参与者反馈；
  [设计] 参与者反馈**默认匿名聚合**呈现（原型只给出聚合数字与引号内的文字）。
- **组织管理员**：可分诊、推送到开发 Agent、生成改进 PR、导出。
- **人工复核人**：**唯一**可放行改进 PR 上线的角色；可驳回（须附理由）、可回滚灰度。
- **开发 Agent**：可起草技术方案、生成 PR；**不得自行合并、不得自行上线、不得改灰度比例**。
- **观察者 / 客户**：**不可见**本模块（这是产品内部治理，不是项目成果）。
- **未登录、链接失效或未列出的角色**：默认无权限；接口不得返回越权数据，
  不能只依赖前端隐藏。

## R6 后置条件 / 不包含

- **正常后置条件**：
  - [原型验收] **AC1**：每条反馈都有**明确状态与去向**（待处理 / 已进入下个迭代 /
    已修复 + 版本号），且票数可聚合排序。
  - [原型验收] **AC2**：每条 Agent/Skill 改进建议都能追到 **N 个原始案例**，
    并包含**具体的参数或提示词改动**（如「阈值 3 → 5」），不接受空泛结论。
  - [原型验收] **AC3a**：**开发 Agent 提交 → 人工复核通过 → 灰度** 三步在原型条目中如实呈现
    （「开发 Agent 提交，人工复核通过，已灰度 100%」）。
  - [设计验收] **AC3b**：三步顺序**不可颠倒、不可跳过**（服务端强制）——
    原型只陈述了一次成功路径，未表明其它顺序被拒绝。
  - [原型验收] **AC4**：项目侧参与者反馈中涉及 AI 行为的文字**自动推送到 Skill 改进队列**。
  - [原型验收] **AC5**：闭环度量可见（反馈数 → PR 数 → 上线数 → 满意度变化）。
- **失败后置条件**：不产生「看似已上线」的改动；驳回与回滚的理由归档不可覆盖；
  失败事件进入可观测日志。
- **不包含**：
  - **客户对项目成果的反馈**（→ UC-15.2）。
  - **skill/agent 的上线门禁本身**（→ 03-skill / 04-agent）；本 UC 不绕过它。
  - 开发 Agent 的实现、代码仓库与 CI/CD 系统本身（本 UC 只定义产品侧的触发与状态）。
  - 面向外部的公开路线图。

## R7 业务规则（不随具体实现变化的硬性约束）

- **[原型] 改进建议必须具体**：聚合结论必须给出**现象 + 负评数 + 归因 + 具体改动**
  （原型示例：「触发阈值从 3 次重复提及提高到 5 次，并要求先征询主持人」），
  且必须能 `[看 N 个原始案例]`。**空泛结论不得生成 PR**（E4）。
- **[原型] 人工复核是上线的必经环节**：「开发 Agent 提交，**人工复核通过**，已灰度 100%」——
  **开发 Agent 不得自行上线**，服务端拒绝任何跳过复核的路径。
- **[原型] 评价是消息级的**：改进反馈来自**对具体消息的 👍/👎**，
  因此每条负评天然带着可复现的上下文；不接受脱离案例的整体评分作为改进依据。
- [设计] **反馈不因「已修复」而丢失溯源**：已修复项须保留其修复版本号与对应 PR。
- [设计] **驳回与回滚必须附理由，理由归档不可覆盖**（与 UC-17.1 的「退回理由不可覆盖」一致）。
- [设计] **反馈附件受留存与脱敏约束**：含客户数据的附件按 UC-17.3 存储，
  推送给开发 Agent 前须脱敏（D-16）。
- [设计] **闭环度量必须公开**：转化率与满意度变化对全组织可见——
  与 14-brain「知识库健康度必须公开」同源的产品主张
  （只涨不减、或没人复核，这一层很快就没人信）。
- 所有权限判断必须在服务端执行；隐藏入口只是界面表现，不构成安全控制。
- 反馈提交、投票、分诊、推送、PR 生成、复核放行、灰度变更、回滚，全部记审计事件。
- [待确认] 消息级评价是否对被评价内容的作者（人类）可见——
  agent 的评价无隐私问题，但人机混合线程中需明确边界。

## R8 界面线索

- **前端入口（已存在）**：
  - [原型] `后台` → **`反馈与迭代`**：软件反馈列表 + Agent/Skill 改进反馈列表 +
    迭代闭环统计；动作 `[打开迭代看板] [导出] [推送到开发 Agent] [查看附件]
    [生成 skill 改进 PR] [看 N 个原始案例]`。
  - [原型] `项目 → 成果沉淀 → 审计与反馈` 下半屏的**参与者反馈**区。
  - [设计] 消息级评价入口在对话消息上（👍/👎），属 08-chat 的界面元素。
- **信息架构**：[原型] 后台该模块分两大块 —— **软件反馈**（缺陷/需求，带票数与状态标签）
  与 **Agent / Skill 改进反馈**（带 👎 计数与建议正文）；底部是**迭代闭环**统计行。
- **推荐交互**：
  - [原型] 反馈行以 **`[类型标签] 标题 N 票`** 呈现，类型标签取值至少
    `[缺陷]` `[需求]` `[已修复]`；已修复项带版本号。
  - [原型] 改进建议正文应**直接可读为一条改动说明**，而不是链接到别处。
  - [设计] 「人工复核」环节必须是**显式的一步**，界面上不可与「生成 PR」合并成一个按钮。
  - [设计] 灰度比例可见且可调，回滚为一等动作。
  - [设计] 闭环统计行使用漏斗式呈现（N 条 → M 条 PR → K 条上线 → 满意度 ±X）。
- **必须呈现的状态**：默认态、加载态、空态、校验失败态（建议缺具体改动）、
  依赖失败态（开发 Agent 不可用）、无权限态、成功态；
  PR 与灰度需显示排队/运行/需复核/完成/失败/已回滚。
- **原型参考**：
  - `phases/requirements/WorkspaceX Standalone.html` — 后台 → 反馈与迭代
  - `phases/requirements/WorkspaceX Standalone.html` — 项目 → 成果沉淀 → 审计与反馈
- **UI sign-off**：
  - [原型] 后台 `反馈与迭代` 主屏与项目侧参与者反馈区**已存在，不必补画**。
  - ⚠ **原型待补 / 未探明（须分开）**：`[打开迭代看板]` `[生成 skill 改进 PR]` `[看 N 个原始案例]`
    三个动作的**按钮已见、目标屏未见——属「原型待补」（按钮在、行为未接线），不是「未探明」**；
    消息级评价的提交交互细节属 08-chat，**属「未探明」**。
    实现前需分别补接线与补抽取。

## R9 非功能约束

- **性能/规模预期**：[设计] 反馈量级为每周几十条，列表分页即可；
  消息级评价可能量级较大，聚合应为增量计算。
- **安全/隐私/合规**：
  - 反馈附件可能含**客户机密与 PII**（原型的音频片段即是），
    必须按 UC-17.3 的留存策略与访问控制处理，推送外部前脱敏（D-16）。
  - 参与者反馈默认匿名聚合，**不得**在后台反向定位到具体填写人
    （[待确认] 是否允许项目负责人看到具名反馈）。
  - 改进 PR 的内容属产品资产，不得包含客户原始数据。
- **兼容与降级要求**：开发 Agent 不可用时，反馈仍可提交与分诊，
  只是无法生成 PR——界面须明确显示该能力不可用，**不得让反馈静默积压**。

## R10 已知约束 / 依赖

- **内部依赖**：**03-skill / 04-agent**（改进的落点与上线门禁）、
  **08-chat**（消息级评价的采集点）、**UC-17.3**（附件留存与脱敏）、
  **UC-17.1**（全流程留痕）、**UC-14.5 / D-16**（脱敏规则）。
- **被依赖**：03-skill / 04-agent 的质量演进；`uc-17-1` 项目级审计屏的下半区
  （参与者反馈）与本 UC 共用同一份数据。
- **跨模块契约**：**消息级评价必须能同时定位到 message / skill / agent / 上下文四者**，
  否则聚合出的建议无法落到具体改动上。
- **技术约束**：[设计] 产品为响应式网页；本 UC 涉及的代码仓库与 CI/CD 属产品研发侧，
  在本产品内只保留状态镜像。
- **[待确认]** 「开发 Agent」是产品内的 agent 还是研发流程外部系统——
  影响本 UC 是「集成」还是「实现」。
- **[待确认]** 参与者反馈是否可具名、对谁可见。
- **[待确认]** 灰度的粒度（按组织 / 按用户 / 按项目）与回滚 SLA。
- **[待确认]** 消息级评价对人类作者的可见性（见 R7）。

## R11 切分提示（给 requirement-author）

- 建议先拆「**软件反馈对象 + 投票 + 状态机** → **消息级评价采集与聚合** →
  **改进建议生成（含具体改动的结构化校验）** → **推送到开发 Agent 与 PR 状态镜像** →
  **人工复核与灰度/回滚** → **参与者反馈采集与自动推送** → **闭环度量** → 审计 → 自动化验收」。
- **「人工复核是必经环节」独立成 feature 并有独立验收**：
  它与 D-27（AI 生成一律进 inbox 草稿态）、UC-14.4（拍板栏只能是人名）
  是同一条产品原则在三个场景的体现，实现上应共用同一套「AI 不能自我放行」的门禁。
- **「改进建议必须含具体改动」应做结构化校验**（现象/负评数/归因/改动四段齐备），
  否则会退化成一堆无法执行的抱怨。
- **优先级 / 先后依赖**：P1；**8 点**；阶段三 · 迭代 12 · 对外与预演；
  依赖 **03-skill / 04-agent** 与 **08-chat 的消息模型**先落地。

## R12 AI Ready 验收线索

- V1（成功态）：AC1 —— 提交一条缺陷反馈并由第二个账号投票，断言：
  ① 票数 +1 且列表按票数可排序；② 状态从待处理流转到已进入下个迭代、再到已修复
  并携带版本号；③ 每次状态变更都有审计。
- V2（成功态 · **主锚点**）：AC2 —— 对同一 skill 的多条消息打 👎，断言：
  ① 生成的改进建议包含**四段**（现象 / 负评数 / 归因 / **具体参数或提示词改动**）；
  ② `[看 N 个原始案例]` 返回的案例数与负评数一致且每条可跳到原消息；
  ③ 构造一条只有「表现不好」的建议，断言**无法生成 PR**（E4）。
- V3（成功态 · 安全）：AC3 —— 以开发 Agent 身份**直接调用上线/合并接口**，
  断言**被服务端拒绝**并记安全审计；只有人工复核人放行后才能进入灰度；
  三步顺序被强制（跳过任一步的请求被拒）。
- V4（成功态）：AC4 —— 在项目侧提交一条涉及 AI 行为的参与者文字反馈，
  断言它出现在后台的 Skill 改进队列中，且携带来源项目与时间。
- V5（成功态）：AC5 —— 请求闭环度量，断言返回反馈数 / PR 数 / 上线数 /
  相关 skill 满意度变化四项，且对全组织可见。
- V6（合规态）：上传含 PII 的反馈附件（如音频），断言：
  ① 附件按项目留存策略存储；② 推送到开发 Agent 时**已脱敏或降级为描述**，
  原始音频未离开受控范围。
- V7（权限态）：逐一以使用者、参与者、组织管理员、人工复核人、开发 Agent、
  观察者、未授权用户访问；返回数据和可执行动作严格符合 R5；
  **观察者/客户完全不可见本模块**。
- V8（空态）：无反馈时显示真实空态与提交入口，不生成示例反馈。
- V9（依赖失败）：开发 Agent 不可用时，断言反馈仍可提交与分诊、
  界面明确显示 PR 生成能力不可用，且反馈未静默积压（有可见的待处理计数）。
- V10（回滚态）：灰度中回滚一次改动，断言回滚理由归档、对应反馈回到待处理、
  灰度比例归零，全过程留痕。
- V11（审计态）：反馈提交、投票、分诊、推送、PR 生成、复核放行、灰度变更、回滚
  八类事件均可按操作者、时间、对象检索。
