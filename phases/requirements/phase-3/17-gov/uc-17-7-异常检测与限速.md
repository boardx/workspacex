# 原始需求（细化）— UC-17.7 异常检测与限速

> 所属：阶段三 · 跨项目与对外 / M17 审计、合规与数据治理
> 来源：原型 `后台` → **`成员与配额`**（48 位成员 · 本周 1,284 万 token · **7 次触发限额**）：
> ```
> 配额总览：已分配 5,400 万（占组织额度 87%）｜ 未分配 800 万（建议留作应急池）｜
>           超支预警 4 人（已用 >85%）
> 成员表：成员 ｜ 角色 ｜ 团队 ｜ 本月配额使用 ｜ [调整]
>   吴桐 顾问 能源组 3.9/4.0M   高琳 管理员 平台组 1.8/4.0M
> 配额策略：按角色设默认额度，用满后可申请应急池；跑批类 agent 从团队池扣减而非个人。
> 降级阈值 · 三级 ＋ 按任务分级（三级中最先触发的一条生效）
>   组织级：已用 90% → 降级到 sonnet-4.6
>   成员级：已用 85% → 「吴桐已达 98%，本周起降级运行」[给他单独提额]
>   Agent 级：Scout 1.5M/日·80% ｜ Ledger 800k/次·不降级 ｜ Ava 按组织级
>     「财务建模精度敏感，Ledger 设为不降级、超限直接请人批准」
>   按任务类型分级：
>     普通生成 → 自动降级＋消息标注
>     研究/财务/合规/决策辅助 → 先问人再降级（这些结论会进决策链，静默降级等于污染证据）
>     含客户机密 → 禁止降级
>     无合格替代模型 → 明确失败
> ```
> 另见 `proto-03-batch3-backend.md` 批次总结第 9 条：
> 「**异常检测与自动限速** —— 单人消耗超均值告警、越权调用拦截计数。需求文档零覆盖。」
> **补写缘由**：原 17-gov 四份 UC 没有任何**运行时防护**——
> 谁在异常消耗、谁在反复越权、什么时候该拦下来。而原型的
> 「7 次触发限额」「超支预警 4 人」「三级 × 四类的降级矩阵」都说明这套机制是**已设计的**。
> 缺它，配额与权限只有「事后可查」，没有「事中拦截」。

> 口径（四标记）：**[原型]** ＝ `WorkspaceX Standalone.html` **运行态实际存在**的行为（有界面可查，依据 scratchpad 的 proto-01~10 抽取档案）；**[Backlog]** ＝ `Backlog Use Case.html` 的**文档要求**（原型未必实现）；**[设计]** ＝ 依据前两者反推补全，**需人类确认**；**[待确认]** ＝ 不应由实现者自行决定。
> 元数据：优先级 **P1**；估点 **5**；建议迭代 **阶段三 · 迭代 12 · 对外与预演**。

## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-17.7 / 异常检测与限速
- **Actor**：**组织管理员**（配额与阈值配置、处置告警）、**合规负责人**（越权异常）、
  **被限速方**（成员或 agent）
- **目标**：[设计] 在**事中**发现并处置两类异常——**资源消耗异常**（超均值、超配额）
  与**权限异常**（反复越权调用）——并按**分级策略**执行降级、限速或拦截，
  **且绝不静默污染结论**。
- **本用例结果**：异常可被检测、可被告警、可被自动处置；
  处置方式严格遵循「按任务类型分级」的四档语义；每次触发都可查。
- **系统边界**：**消耗异常检测**（超均值 / 超配额阈值）、**越权异常检测**（拦截计数）、
  **三级降级阈值 × 四类任务的处置矩阵**、限速与拦截、告警与人工处置入口。
- **不属于本 UC 的边界**：配额的**分配与调整**（属后台成员与配额的配置面，
  与本 UC 同屏但不同职责）、审计事件模型（→ UC-17.1）、
  权限判定本身（→ `uc-0-3` / UC-17.4 / UC-17.5）、模型选择（→ 09-model）。
- **核心数据对象**：用量指标（组织 / 成员 / agent / 任务）、阈值配置（三级）、
  任务风险类型、**处置动作**（降级 / 先问人 / 禁止降级 / 明确失败 / 限速 / 拦截）、
  异常事件、告警、越权拦截计数。

## R2 前置条件 / 触发条件

- **前置条件**：配额与阈值已配置；用量与越权拦截的埋点可用（依赖 UC-17.1）。
- **触发条件**：
  - [原型] **用量越过阈值**：组织级 90% / 成员级 85% / agent 级（各自的日或单次上限）。
  - [设计] **单人消耗显著超过均值**（统计意义上的离群），即使未越配额线。
  - [设计] **越权调用达到计数阈值**（同一主体短时间内多次被拒）。
  - [原型] 任务发起时命中「**含客户机密**」或「**无合格替代模型**」两种硬策略。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

### R3.a 消耗异常：三级阈值 × 四类任务

1. **系统处理（三级阈值，最先触发者生效）**：[原型]
   | 级别 | 阈值 | 默认处置 |
   |---|---|---|
   | **组织级** | 已用 **90%** | 降级到较低成本模型（原型示例 `sonnet-4.6`） |
   | **成员级** | 已用 **85%** | 该成员降级运行（原型：「吴桐已达 98%，本周起降级运行」`[给他单独提额]`） |
   | **Agent 级** | 各 agent 独立（原型：Scout **1.5M/日 · 80%** ｜ Ledger **800k/次 · 不降级** ｜ Ava 按组织级） | 按该 agent 配置 |
   > [原型] **三级中最先触发的一条生效**——不叠加、不取最严，取**最先命中**。
2. **系统处理（按任务类型分级，四档语义，覆盖第 1 步的默认处置）**：[原型]
   | 任务类型 | 处置 | 理由（原型原文） |
   |---|---|---|
   | **普通生成** | **自动降级 ＋ 消息标注** | 质量损失可接受，中断成本更高 |
   | **研究 / 财务 / 合规 / 决策辅助** | **先问人再降级** | **「这些结论会进决策链，静默降级等于污染证据」** |
   | **含客户机密** | **禁止降级** | 替代模型不满足隐私与部署要求 |
   | **无合格替代模型** | **明确失败** | **「宁可报错，也不给低质量伪结果」** |
   > 该矩阵**优先于**第 1 步的默认处置：即使命中组织级 90%，
   > 含客户机密的任务**也不降级**（而是走批准或失败）。
3. **系统处理（消耗离群检测）**：[设计] 对单人/单 agent 的消耗做**相对均值的离群检测**，
   命中时**告警而不自动限速**（避免误伤正常的重活）；
   由管理员决定 `[给他单独提额]` 或限速。
4. **系统处理（降级必留痕）**：[原型] 自动降级时**在消息上标注**（「降级运行 · sonnet」——
   对照原型对话流中的「Scout · 主动补充 · **降级运行 · sonnet**」）；
   **降级事件写审计**，且被降级产出的下游引用可追到这一事实。

### R3.b 权限异常：越权拦截计数与限速

5. **系统处理**：统计**越权调用被拒**的次数（来自 `uc-0-3` 的拒绝、UC-17.4 的跨组织拒绝、
   UC-17.5 的管理员旁路尝试、UC-16.x 的虚拟产物写入尝试等）。
6. **系统处理（限速与拦截）**：同一主体短时间内越权次数达阈值时，
   [设计] 触发**限速**（降低请求频率）→ 再超则**临时拦截**并告警合规负责人；
   拦截**不影响**其正常权限内的操作（最小影响原则）。
7. **系统处理（告警）**：两类异常都产生告警，含**主体 / 类型 / 计数 / 时间窗 / 建议处置**；
   [原型] 后台头部呈现聚合数字（「**7 次触发限额**」「超支预警 **4 人**」）。
8. **管理员 / 合规负责人操作**：处置——提额、限速、解除拦截、上报。
   **系统响应**：处置动作留痕并显示影响范围。
9. **系统收口**：校验 AC1（三级最先触发生效）、AC2（四档任务语义严格执行）、
   AC3（降级必标注必留痕）、AC4（越权计数与限速生效）；
   记录操作者、时间、对象、结果与来源。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[原型] **应急池** —— 用满后可申请应急池；[原型] 组织保留未分配额度
    （「未分配 800 万（**建议留作应急池**）」）。申请与批准留痕。
  - A2：[原型] **单独提额** —— `[给他单独提额]` 对某成员临时提高额度，
    该动作记审计并显示对组织池的影响。
  - A3：[原型] **团队池扣减** —— **跑批类 agent 从团队池扣减而非个人**；
    因此 agent 的大额消耗不应触发个人级降级。
  - A4：[原型] **超限直接请人批准** —— Ledger 类「不降级」的 agent 超限时
    **转为请人批准**而不是降级或失败。
  - A5：[设计] 无异常时显示真实空态（文案待定），不生成示例告警。
- **异常流程**：
  - E1：[原型] **无合格替代模型 → 明确失败** —— 不做任何形式的兜底生成。
  - E2：[原型] **含客户机密 → 禁止降级** —— 即使这意味着任务失败或等待批准；
    与 UC-17.3 的「客户机密只走自托管」硬路由一致。
  - E3：[设计] **降级发生在任务执行中途** → 对「研究/财务/合规/决策辅助」类任务
    **必须暂停并问人**，不得中途静默切换模型；已产出部分须标注其模型来源。
  - E4：[设计] **误伤** —— 被限速方可申诉；申诉期间管理员可临时解除，解除留痕。
  - E5：[设计] **用量埋点不可用** → 无法判定阈值时，**对「含客户机密」与
    「决策辅助」类任务采取保守策略（拒绝或请人批准）**，对普通生成放行；
    并显式告警埋点故障。
  - E6：[设计] 请求超时或依赖不可用时明确失败并可重试，失败不得被呈现为成功。

## R5 权限与可见性

- **组织管理员**：可配置三级阈值与各 agent 的策略、可提额、可解除限速；
  可见全组织的用量与告警。
- **合规负责人**：**越权异常**的第一接收人；可查看越权拦截计数与详情；
  可要求提高拦截强度。
- **成员本人**：可见**自己的**用量与降级状态（[原型]「本周起降级运行」应对本人可见），
  可申请应急池与申诉。
- **团队负责人**：[设计] 可见本团队池的用量（[原型] 团队池是一等概念）。
- **agent**：受策略约束；**不可修改任何阈值、不可为自己提额、不可解除自身限速**。
- **观察者 / 客户**：不可见本模块。
- **未登录、链接失效或未列出的角色**：默认无权限；接口不得返回越权数据，
  不能只依赖前端隐藏。
- 用量数据属敏感运营数据：**管理员可见成员用量总量，但不得因此获得其内容读取权**
  （UC-17.5 的边界仍然成立）。

## R7 业务规则（不随具体实现变化的硬性约束）

- **[原型] 三级阈值取最先触发**：组织级 / 成员级 / Agent 级中，
  **最先命中的一条生效**——不是取最严，也不是叠加。
- **[原型] 按任务类型分级的四档是硬语义，且优先于三级默认处置**：
  - **普通生成** → 自动降级 **＋ 消息标注**（标注不可省）；
  - **研究 / 财务 / 合规 / 决策辅助** → **先问人再降级**——
    [原型 原文]「**这些结论会进决策链，静默降级等于污染证据**」；
  - **含客户机密** → **禁止降级**（替代模型不满足隐私与部署要求，与 UC-17.3 硬路由一致）；
  - **无合格替代模型** → **明确失败**——[原型 原文]「**宁可报错，也不给低质量伪结果**」。
- **[原型] 静默降级是被明确禁止的失败模式**：任何降级都必须**可见**（消息标注）
  且**可查**（审计），否则等于污染证据链（与 UC-14.6「未挂来源标灰」同源的透明性原则）。
- **[原型] 跑批类 agent 从团队池扣减而非个人**：agent 的大额消耗不得触发个人级降级。
- **[原型] 「不降级」的 agent 超限时转为请人批准**（如 Ledger），不是失败也不是降级。
- [设计] **限速与拦截遵循最小影响原则**：只影响触发异常的行为，不冻结主体的全部能力。
- [设计] **消耗离群只告警不自动限速**（避免误伤正常重活）；
  权限越权可自动限速（越权无正当性）。
- [设计] **埋点不可用时对高风险任务采取保守策略**，并显式告警——不得当作「未超限」放行。
- [设计] **用量可见不等于内容可见**：管理员看到用量不得推导出或获得内容访问权（UC-17.5）。
- 所有权限判断必须在服务端执行；隐藏入口只是界面表现，不构成安全控制。
- 阈值配置变更、降级发生、提额、限速、拦截、解除，全部记审计事件并显示影响范围。
- **[待确认]** 消耗离群的判定方法与阈值（几倍均值 / 什么时间窗）。
- **[待确认]** 越权计数的阈值与时间窗、限速与拦截的强度曲线。
- **[待确认]** 「任务类型」的判定方式：由任务模板声明、由风险分级 R1/R2/R3 推导（D-28），
  还是二者结合。

## R9 非功能约束

- **性能/规模预期**：[设计] 阈值判定必须在**请求路径上**完成且为毫秒级
  （事中拦截而非事后统计）；用量聚合可异步但阈值判定所需的计数须实时可读。
- **安全/隐私/合规**：越权拦截记录属安全审计，按 UC-17.3 的审计保留期存储；
  告警内容中**不得包含被拒请求的敏感载荷**。
- **兼容与降级要求**：本 UC 自身的检测服务不可用时，
  **对高风险任务（含客户机密 / 决策辅助）采取保守策略**，
  对普通生成放行并告警——**不得因检测不可用而全面阻断，也不得因此放行高风险操作**。

## R12 AI Ready 验收线索

- V1（成功态）：AC1 —— 构造组织级 90%、成员级 85%、agent 级 80% 三种越线场景，
  按**不同的命中顺序**各跑一次，断言**每次生效的都是最先触发的那一条**，
  且不出现叠加或取最严的行为。
- V2（成功态 · **主锚点**）：AC2 —— 在同一越线条件下，对四类任务各发一次请求，断言：
  ① **普通生成**：自动降级且响应/消息上**带降级标注**；
  ② **研究/财务/合规/决策辅助**：**任务暂停并产生一个「是否降级」的人工审批点**，
  未获批准前不执行；
  ③ **含客户机密**：**不降级**——要么请人批准、要么失败，断言未切换到不合规模型；
  ④ **无合格替代模型**：**明确失败**，响应为错误而非任何形式的兜底生成。
- V3（成功态）：AC3 —— 取一段降级产出的内容，断言：
  ① 消息上有降级标注且可点开看原因；② 审计中有降级事件；
  ③ 该内容被引用为证据时，**下游（UC-14.6 检索记录 / UC-14.4 决策依据）
  仍能看到它是降级产出的**。
- V4（成功态）：AC4 —— 同一主体在时间窗内连续触发 N 次越权拒绝，断言：
  ① 越权计数递增；② 达阈值后触发限速；③ 再超触发拦截并**告警合规负责人**；
  ④ 该主体**权限内的正常操作不受影响**（最小影响原则）。
- V5（成功态）：AC5 —— 后台返回聚合指标：触发限额次数、超支预警人数、
  配额总览（已分配 / 未分配）；跑批类 agent 的消耗断言**从团队池扣减而非个人**。
- V6（异常态）：把 Ledger 类 agent 配为「不降级」并使其超限，
  断言其**转为请人批准**，既不降级也不直接失败。
- V7（依赖失败态）：模拟用量埋点不可用，断言：
  ① 含客户机密与决策辅助类任务采取保守策略（拒绝或请人批准）；
  ② 普通生成放行；③ 产生埋点故障告警。
- V8（权限态）：逐一以组织管理员、合规负责人、成员本人、团队负责人、agent、
  观察者、未授权用户访问；返回数据和可执行动作严格符合 R5；
  **agent 修改阈值 / 为自己提额 / 解除自身限速三个请求均被拒**并记安全审计。
- V9（边界态）：断言管理员可见成员用量总量，但**对该成员个人层内容仍不可读**（UC-17.5）。
- V10（空态）：本周无触发时显示真实空态，不生成示例告警。
- V11（审计态）：阈值变更、降级发生、提额、限速、拦截、解除六类事件
  均可按操作者、时间、对象检索。
