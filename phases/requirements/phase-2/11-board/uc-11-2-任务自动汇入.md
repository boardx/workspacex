## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-11.2 / 任务自动汇入
- **Actor**：**来源模块**（会前任务 / 现场 / 决策树 / 报告 / 转写 / 研究，作为触发方）、
  **agent**（作为草稿建议的生成方，**不是接受方**）、**负责人 / 项目经理 / 引导师 / 组长**（接受方，恒为人）。
- **目标**：[原型] 把六类来源产生的行动项自动汇成任务卡，**每张卡都能追回它是从哪里来的**；
  AI 产出的卡先进收件箱等人接受，人接受后才进入工作流。
- **本用例结果**：来源模块产生一个行动项 → 系统建卡并写入来源引用 → 按建卡方与风险等级决定落
  `inbox`（AI 建卡）还是直接落工作列（人手工建卡）→ `inbox` 中 R1 卡自动晋升 `todo`、
  R2/R3 卡等人点「接受」。
- **系统边界**：六类来源的汇入适配、来源引用写入与跳回、**AI 建卡的 inbox 草稿态门禁**、
  **风险等级的服务端推导**、接受/忽略动作、重复汇入的合并（幂等）。
  状态机与列投影见 UC-11.1；权限包与授权流见 UC-11.6；模板覆盖见 UC-11.7。
- **核心数据对象**：
  - **任务卡**（同 UC-11.1）：新增关注 `status` 初值、`risk_level`（`R1`/`R2`/`R3`）、
    `created_by_kind`（`human` / `agent` / `rule`）、`accepted_by` / `accepted_at`。
  - **来源引用 `source_ref`**：来源模块 + 来源对象 ID + **资源版本** + **触发时间** + 触发者，
    四要素缺一不可。
  - **风险推导规则表**：操作类型 → 风险等级的映射，**存于服务端**，可被任务模板覆盖。
  - **汇入去重键**：来源模块 + 来源对象 ID（+ 归一化标题），用于同一件事被两处提出时的合并。

## R2 前置条件 / 触发条件

- **前置条件**：
  - 用户已建立可校验的正式或临时身份，且拥有目标组织、项目、小组或资源的访问权。
  - 目标资源存在且未被删除/冻结；依赖能力“各模块的任务产生点（图谱、报告、访谈、会前任务）”可用，或界面能明确显示其不可用状态。
  - 若动作涉及个人数据、录音、原始材料或跨范围读取，相应授权与留存策略已生效。
- **触发条件**（六类来源之一产生行动项）：
  - [原型] **会前任务**：蓝本/项目筹备派发的会前任务清单产生一条待办。
  - [原型] **现场**：现场协作中产生的行动项（如「追访两家本地 EPC」）。
  - [原型] **决策树**：决策节点的后续动作（如「查三国资质转移条文，判定收购分支存亡」）。
  - [原型] **报告缺料**：报告工作台底部缺料提示（如「保底条款成本测算·待财务确认折现率」）。
  - [原型] **转写**：转写产生的待处理项（如「第3组访谈转写的说话人指派」）。
  - [原型] **研究**：研究模块交付或建议（如「Scout 发现波兰无一手材料，建议先做桌面研究」）。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

1. **来源模块触发**：某个来源对象产生行动项，调用汇入接口，必须携带
   **来源模块 + 来源对象 ID + 资源版本 + 触发时间 + 触发者（人或 agent）** 五要素。
   **系统响应**：任一要素缺失直接拒绝建卡（见 E4）——**没有来源就不建卡**。
2. **系统推导风险等级 [D-28]**：按**操作类型**在服务端规则表中查出 `risk_level`。
   - 例：读公开资料 / 桌面检索 → **恒 R1**；写入项目数据、消耗预算的分析任务 → **R2**；
     **外发邮件、对客户方发送、不可逆动作 → 恒 R3**。
   - 若该任务套用了任务模板且模板声明了风险等级覆盖，则**以模板值为准**（唯一合法覆盖入口，见 UC-11.7）。
   - **推导与覆盖都在服务端完成，前端不参与判定**；前端只展示结果。
3. **系统决定初始 `status` [D-27]**：
   - `created_by_kind = agent`（AI 生成的卡，含自动化规则生成的卡）→ **初始 `status` 恒为 `inbox`**，
     标为草稿态。**不得直接写 `todo` 或任何工作列**，无论风险等级高低。
   - `created_by_kind = human`（人在看板上手工建卡、或人在来源模块显式派活）→ 可直接落 `todo`。
4. **系统写卡**：写入来源徽标（六类之一，与来源模块一一对应）、可点击跳回原处的来源引用、
   标题、到期日、**负责人（恒为人）**、**执行者**（可为 agent）。
   **系统响应**：负责人为空的 AI 建卡允许停在 `inbox`（由接受人在接受时指派），
   但**不得在负责人为空的情况下进入 `todo`**。
5. **系统处理接受门槛 [D-27]**：
   - **R1 卡**：可**自动接受**——系统自动把 `status` 从 `inbox` 晋升为 `todo`，
     记录 `accepted_by = system` 与推导依据。
   - **R2 / R3 卡**：**必须由人显式接受**。卡停在 `inbox`，界面提供 `[接受]` `[忽略]` 两个动作
     （原型原文：「AI 建议(未确认不会开跑)…[接受][忽略]」）。调用自动接受接口对 R2/R3 **必须返回拒绝**。
   - **用户操作 `[接受]`**：系统校验操作者有该项目/组的建卡权，写 `accepted_by`（人的账号）与
     `accepted_at`，`status` → `todo`，并要求补齐负责人。
   - **用户操作 `[忽略]`**：卡保留在库中标为已忽略，**不删除**，可检索可恢复；写审计。
6. **系统处理去重合并**：同一件事被两处提出时（去重键命中），**不新建第二张卡**，
   而是在既有卡上追加一条来源引用，卡片显示「2 个来源」并可分别跳回。
   合并后风险等级取**两者中更高的一级**（就高不就低）。
7. **系统收口**：校验 AC1「每张卡都能追回它是从哪里来的」；写审计事件
   （触发来源、建卡时间、`created_by_kind`、推导出的风险等级、初始 `status`、接受人与接受时间）。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[原型] 来源对象被删除时卡片标为**孤立**，停留在当前列等人处理，不自动删卡；
    卡上说明来源已不存在，回写目标失效（对齐 UC-11.1 E6）。
  - A2：[设计] 来源对象的**版本被更新**（如报告升到 v4、决策被改写）时，卡不重建，
    在卡上标「来源已更新到 vN」并提供查看差异入口，由人决定是否作废本卡。
  - A3：[设计] R1 卡自动接受后，负责人仍可把它退回 `inbox`（「我不认这条」），
    退回后重新按 R2 处理（需人再次显式接受），防止自动接受被滥用。
- **异常流程**：
  - E1：[设计] 汇入接口超时或来源模块不可用时，汇入进入重试队列并对来源侧回执明确失败；
    **不得产生没有来源引用的孤儿卡**，也不得静默丢弃行动项。
  - E2：[设计] 同一来源对象在短时间内重复触发汇入时按去重键幂等处理，**只保留一张卡**；
    重复触发写日志但不重复建卡、不重复计数。
  - E3：[设计] 风险推导规则表查不到该操作类型时，**默认按最高风险 R3 处理**（fail-safe），
    并在卡上标「风险等级待人工确认」，不允许 fallback 到 R1。
  - E4：[设计] 汇入请求缺少来源模块 / 来源对象 ID / 版本 / 时间任一要素时直接拒绝（400），
    错误信息指明缺哪一项；**绝不允许"先建卡后补来源"**。
  - E5：[设计] 有人试图对 R2/R3 卡调用自动接受接口时返回 403 并写安全审计；
    这不是界面隐藏问题，是服务端硬门禁。
  - E6：[设计] 接受动作的操作者在提交瞬间失去权限时终止晋升，卡回到 `inbox` 并提示重新授权。

## R5 权限与可见性

- **项目经理 / 引导师**：可接受或忽略本项目全部 `inbox` 卡，含 R2/R3。
- **组长**：可接受或忽略本组范围内的 `inbox` 卡；R3 卡的接受权 [待确认] 是否需上收到项目经理。
- **组员**：可见指派给自己的 `inbox` 卡并可接受 R1/R2；**R3 卡不可由组员接受**。
- **agent（执行者）**：只能**生成**草稿卡，**不能接受任何卡**——包括它自己生成的 R1 卡
  （R1 的自动接受由系统按规则执行并记为 `system`，不是由 agent 决定）。
- **观察者**：不可见 `inbox`，也不可见任何未接受的草稿卡。
- **未登录、链接失效或未列出的角色**：默认无权限；接口不得返回越权数据，不能只依赖前端隐藏。

## R6 后置条件 / 不包含

- **正常后置条件**：
  - 每张卡都带完整来源引用（来源模块 + 对象 ID + 版本 + 时间 + 触发者），点开可跳回原处。
  - AI 生成的卡的初始 `status` 恒为 `inbox`；R1 已自动晋升 `todo`，R2/R3 停在 `inbox` 待人接受。
  - 每张卡的 `risk_level` 已由服务端推导（或由模板覆盖）并记录推导依据。
  - [Backlog验收] AC1：每张卡都能追回它是从哪里来的（Backlog UC-11.2 `ac` 原文）。
  - [设计验收] AC2：任何由 agent 或自动化规则创建的卡，其创建时刻的 `status` 必为 `inbox`。
  - [设计验收] AC3：R2/R3 卡的 `accepted_by` 必为人的账号；不存在 `accepted_by = system` 的 R2/R3 卡。
  - [设计验收] AC4：同一来源对象重复触发汇入，库中卡数恒为 1。
  - [设计验收] AC5（**双向契约**）：每张卡的 `source_ref` 既能从卡跳回来源对象，
    也能被来源模块反向定位到这张卡——**两向都通**才算汇入成功。
  - [原型验收] AC6a（**环节结束自动归档**）：带 `stage_ref` 的现场型卡在环节结束事件后被归档
    （无论 `status` 为何）——原型原文「来自 Kickoff 项目·环节 3『假设风暴』· 9 项 ·
    **环节结束自动归档**」，属实。
  - [Backlog验收] AC6b（**done 满 7 天折叠**）：不带 `stage_ref` 的卡在 `done` 满 7 天后折叠
    ——出自 Backlog UC-11.1 `edge`，**原型确认缺失**。
    此前把两条拼成一条 AC6 并整体标 `[原型验收]`，是「真 + 假」拼接，已拆开。
    两种情况下卡都**仍可检索**，均非删除。
- **失败后置条件**：
  - 不产生无来源引用的孤儿卡；不产生「已接受但没有接受人」的卡；失败事件进入可观测日志与重试队列。
- **不包含**：
  - 状态机与列投影（属 UC-11.1）、筛选（UC-11.3）、提醒与催办（UC-11.4）、
    语义分区视图（UC-11.5）、**权限包与缺权限时的授权流**（UC-11.6）、
    **模板与自动化规则的编辑**（UC-11.7，本用例只消费模板已声明的覆盖值）。
  - 完整项目管理套件、第三方 IM 通知。
  - 不扩展到本 use case 未声明的跨组织、跨客户或公开发布能力。

## R7 业务规则（不随具体实现变化的硬性约束）

- **[D-27 · 硬约束] AI 建卡一律落 `inbox` 草稿态**：由 agent 或自动化规则创建的任务卡，
  初始 `status` **恒为 `inbox`**，不得直接进入 `todo` 或任何工作列。
  原型原文：「**AI 只能生成草稿进收件箱；R3 以上永远需要人接受后才成立**」。
- **[D-27 · 硬约束] 接受门槛按风险分级**：**R1 可自动接受**（系统自动 `inbox → todo`）；
  **R2 / R3 必须由人显式接受**，对 R2/R3 调用自动接受接口必须返回拒绝。
- **[D-27 · 硬约束] 未经人接受的 `inbox` 卡**：
  ① **不计入任何人的工作量**（不进个人任务数、不进负荷统计）；
  ② **不触发到期提醒**（UC-11.4 的提醒范围排除 `inbox`）；
  ③ **不进项目内四列视图的列计数**（只计入折叠入口的「收件箱 N」，见 UC-11.1 R7）。
- **[D-28 · 硬约束] 风险等级由操作类型自动推导**：`risk_level` 由服务端规则表按**操作类型**推导，
  **不由前端判定、不由 agent 自报**。例：读公开资料恒 R1、外发邮件恒 R3。
  **唯一合法的覆盖入口是任务模板**（UC-11.7）；规则表查不到时 fail-safe 到 R3。
- **[原型] 六类来源徽标**：`现场` / `会前任务` / `决策树` / `报告缺料` / `转写` / `研究`；
  每条汇入必须携带**来源资源 + 版本 + 时间**，缺一不建卡。
  **六类是封闭集合**——新增第七类来源必须先扩这张枚举表，不允许用「其他」兜底。
- **[原型 · 双向契约 · 硬约束] 汇入不是单向搬运**。原型底注原文：
  「**卡片来源自动同步：会前任务、现场行动项、报告缺料、决策的后续动作。
  状态改了会回写到原处。**」——本用例负责**来源 → 卡**这一向（建卡 + 写来源引用 + 保持可跳回），
  **卡 → 来源**的回写在 UC-11.1 R3.3 实现；两向读同一份 `source_ref` 绑定，
  **禁止两侧各存一份不可关联的副本**。因此汇入时写入的 `source_ref` 必须是**可反向定位**的
  （来源模块能按它找回自己那条对象），只能跳转、不能反查的引用视为不合格汇入。
- **[原型] 同一件事被两处提出时合并**：按去重键幂等，只保留一张卡并挂多条来源引用；
  合并后风险等级就高不就低。
- **[原型] 来源被删除时卡片标为孤立**，等人处理，不自动删卡。
- **两套归档机制并存，按任务类型二选一，不得互相顶替**（**两条口径不同，见各自标记**）：
  - **① [原型] 环节结束自动归档**（原型原文可证）——适用于**绑定到项目环节的现场型任务**
    （`source_kind = 现场`，且汇入时携带 `stage_ref` 环节引用）。原型原文：
    「来自 Kickoff 项目·环节 3『假设风暴』· 9 项 · **环节结束自动归档**」
    「项目环节产出（按角色拆）：一个环节自动生成引导师／组长／组员三套任务，**环节结束自动归档**」。
    触发条件是**环节结束事件**，**与卡是否 `done` 无关**：未完成的卡也一并归档，
    并保留其当时的 `status` 作为该环节的现场记录。归档=移出活跃看板并可检索，**不是删除**。
  - **② [Backlog] 已完成 7 天后折叠**（Backlog UC-11.1 `edge`；**原型确认缺失**，十份档案零命中）
    ——适用于**不绑定环节的常规任务**（其余五类来源与手工建卡）。
    [设计] 触发条件是 `status = done` 且已过 7 天，折叠进「已完成」列的收起区，仍可展开与检索
    （见 UC-11.1 E2），**不是删除**。
  - **判定优先级**：卡带 `stage_ref` 时走 ①，否则走 ②；**一张卡不得同时受两套机制处置**。
  - [待确认] 现场型任务在环节结束时若仍未完成，是否需要同时向负责人推一条「已随环节归档，
    未完成」的通知——需产品定稿。
- **[D-39] 负责人恒为人**：汇入时若只能确定 agent 执行者，负责人位留空并停在 `inbox`；
  **负责人为空的卡不得进入 `todo`**。
- **[原型] `[忽略]` 不等于删除**：被忽略的草稿卡保留可检索，可恢复，写审计。
- 所有门禁（inbox 初始态、接受权限、风险推导）必须在服务端执行；界面隐藏不构成安全控制。
- 建卡、接受、忽略、合并、风险等级覆盖都必须记录审计事件。

  - [原型] **全局视图的收件箱列**：`任务 → 项目看板 → 收件箱 3`（五列的第一列）。

    「全部 ｜ 我的 ｜ 现场 ｜ 逾期与今天」，**没有收件箱**；收件箱只存在于
    **全局**「任务 → 项目看板」的五列里。同一件事在 `uc-11-1` 已标 `[设计]`（D-b 取 `[设计]`）。

## R9 非功能约束

- **性能/规模预期**：
  - [设计] 汇入为异步但需对来源侧回执明确状态；来源模块产生行动项到卡出现在收件箱应在 5 秒内。
  - [设计] 去重合并的判定必须在写入事务内完成，不能靠事后清理任务补救。
  - [设计] 现场高频场景（四组并行产生行动项）下汇入需能承受突发批量，队列积压必须可观测。
- **安全/隐私/合规**：
  - 最小权限、组织/项目/小组隔离、传输与静态加密、敏感字段脱敏、导出与 AI 读取留痕。
  - 原始材料、录音、转写、私聊、个人身份与客户数据按授权和留存策略处理。
- **兼容与降级要求**：
  - 响应式 Web；桌面端提供完整能力，移动端保证加入、查看、输入、投票/确认等现场关键动作。
  - WebSocket/实时通道不可用时降级为轮询并显示“非实时”；断网允许保留未提交输入，但不得伪装已同步。

## R12 AI Ready 验收线索

以下行为应可由自动化测试、接口断言或可复现人工步骤验证：

- V1（inbox 门禁 · AC2）：以 agent 身份调 AI 建卡接口 20 次覆盖各类操作类型，
  断言**每次返回的 `status` 恒为 `inbox`**；直接在请求体里指定 `status: "todo"` 亦被覆写为 `inbox`
  或返回 400。
- V2（R2/R3 拒绝自动接受 · AC3）：对一张 R2 卡与一张 R3 卡分别调用自动接受接口，
  断言**均返回拒绝**（403）且卡的 `status` 仍为 `inbox`、`accepted_by` 仍为空。
- V3（R1 自动晋升）：造一张操作类型为「读公开资料」的 AI 卡，
  断言推导出 `risk_level = R1` 且系统在建卡后自动把 `status` 置为 `todo`，`accepted_by = system`。
- V4（人工接受）：以项目经理身份对 R3 卡点 `[接受]`，断言 `status → todo`、
  `accepted_by` 为该人的账号 ID、`accepted_at` 非空。
- V5（风险推导 · D-28）：对同一标题的任务分别以操作类型「读公开资料」与「外发邮件」建卡，
  断言前者 `risk_level = R1`、后者 `= R3`；**断言前端请求体中携带的 risk_level 被服务端忽略**。
- V6（模板覆盖 · D-28）：套用一个声明了风险覆盖的任务模板建卡，
  断言最终 `risk_level` 取模板值而非推导值，且记录中同时保留推导值与覆盖来源。
- V7（fail-safe）：用一个规则表中不存在的操作类型建卡，断言 `risk_level = R3` 且卡带
  「风险等级待人工确认」标记。
- V8（来源五要素 · AC1）：逐一省略来源模块/对象 ID/版本/时间任一要素调汇入接口，
  断言均返回 400 且库中未新增卡；正常汇入后断言 `source_ref` 四要素齐全且跳回链接可解析。
- V9（六类徽标）：分别从六个来源模块各触发一次汇入，断言产生的卡的 `source_kind` 依次为
  `现场 / 会前任务 / 决策树 / 报告缺料 / 转写 / 研究`。
- V10（去重 · AC4）：对同一来源对象连续触发 5 次汇入，断言库中该来源的卡数恒为 1
  且该卡挂了 1 条来源引用；再从第二个来源提出同一件事，断言仍为 1 张卡但来源引用变为 2 条、
  风险等级取两者中较高者。
- V11（inbox 不计入 · R7 三条）：造 3 张 `inbox` 卡，断言
  ① 负责人的个人任务计数不变；② 到期提醒任务扫描结果不含这 3 张；
  ③ 项目内视图四列的列计数之和不含这 3 张，而「收件箱 N」= 3。
- V12（忽略不删）：对一张卡点 `[忽略]`，断言卡仍可按 ID 查到、状态标为已忽略、可恢复，
  且审计中有忽略事件。
- V13（孤立态）：删除来源对象后断言卡仍存在并带孤立标记，回写调用不再发出。
- V14（agent 不能接受）：以 agent 身份调接受接口，断言返回 403 并写安全审计。
- V15（双向契约 · AC5）：汇入一张卡后，① 从卡的 `source_ref` 解析并 GET 来源对象成功；
  ② 以来源对象 ID 调「按来源查卡」接口，断言能查回同一张卡 ID。两向任一不通即判失败。
- V16（环节结束归档 · AC6）：造 3 张带 `stage_ref` 的现场型卡（状态分别为 `todo` /
  `in_progress` / `done`），触发该环节的结束事件，断言**三张全部**被标为已归档、
  各自的 `status` 值未被改写、且仍可按 ID 与检索接口取到。
- V17（7 天折叠 · AC6）：造一张不带 `stage_ref` 的卡置 `done`，把系统时间推进 8 天，
  断言其被折叠而非归档、亦未被删除；同一时刻断言 V16 中已归档的现场卡**没有被再折叠一次**
  （一张卡只被一套机制处置）。
- V18（审计态）：建卡、接受、忽略、合并、风险覆盖、归档/折叠六类事件均可按操作者、
  时间、卡 ID 检索。
