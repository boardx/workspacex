>
> **补写缘由**：原 11-board 四份用例把任务当成一张卡片，没有回答
> 「**agent 拿这张卡去干活时，它能读什么、不能读什么，缺权限了怎么办**」。
> 原型对这件事有明确设计：任务模板「生下来就带**权限包**」，
> agent 缺权限时任务**转「等待输入」并向人请求授权**（`[去授权]`）。
> 这是 AI 参与执行的**安全底座**，不写清楚会被实现成「agent 有什么权限就用什么权限」。
>
> **[裁决引用 · 权限三层]** 权限模型是三层：
> **MCP 授权范围 × agent 工具白名单 × 任务权限包（R1/R2/R3）**，**三层取交集**。
> **[D-28]** 权限包的风险等级由操作类型自动推导，任务模板可覆盖。
> **[D-39]** 授权人恒为人；**agent 不能给 agent 授权**。

## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-11.6 / 任务权限包与授权流
- **Actor**：**负责人**（授权人，恒为人）、**有权审批人**（项目经理 / 引导师，恒为人）、
  **agent**（权限的**使用方与请求方**，**不是授予方**）、**任务模板**（权限包的默认值来源）。
- **目标**：让每一张任务卡**自带一份数据访问范围声明（权限包）**，
  agent 只能在这份声明与另两层权限的交集内行动；
  一旦执行过程中缺权限，任务**停下来向人请求授权**，而不是失败、跳过或偷偷绕开。
- **本用例结果**：任务卡上可见其权限包（能读写哪些数据、有效期）；
  agent 执行中缺权限时任务转**「等待输入」**态并向负责人弹出**授权请求**；
  人**逐次、限范围、限时**地批准或拒绝；两种结果都写审计；
  拒绝或超时后任务转**「阻塞」**并说明原因。
- **系统边界**：权限包的数据结构与挂载、**三层权限求交的判定服务**、
  执行中缺权限的中断与「等待输入」态、授权请求的生成与呈现、
  授权的授予/拒绝/超时处理、授权有效期与自动失效、授权审计。
  **不含** MCP 注册与授权范围本身（属 10-mcp）、
  不含 agent 工具白名单的配置（属 04-agent）、不含风险规则表的维护（属 UC-11.2 / UC-11.7）。
- **核心数据对象**：
  - **任务权限包 `permission_pack`**（挂在任务卡上）：
    `scopes[]`（允许读写的数据范围：**项目 / 组 / 材料类别 / 外部来源**）、
    `mode`（读 / 写）、`risk_level`（R1/R2/R3，由 D-28 推导、模板可覆盖）、
    `expires_at`（有效期）、`granted_by`（授权人，恒为人）、`source`（模板默认 / 逐次授权）。
  - **授权请求 `authz_request`**：任务 ID、请求方 agent、**要读什么**、**为什么要读**、
    **授权后 agent 能做什么**、**请求范围**、**建议有效期**、生成时间、超时时限。
  - **授权决定 `authz_decision`**：批准 / 拒绝、实际授予范围（可小于请求范围）、
    实际有效期、决定人（恒为人）、决定时间、理由。
  - **三层权限判定输入**：MCP 授权范围（10-mcp）× agent 工具白名单（04-agent）×
    任务权限包（本用例）。
  - **任务执行态**：`waiting_input`（等待输入）、`blocked`（阻塞）——
    这两个是**标记，不是 `status` 列**（对齐原型「阻塞/等待输入/超期是标记，不是列」）。

## R2 前置条件 / 触发条件

- **前置条件**：
  - 任务卡已存在且已被人接受（`status ∉ {inbox}`，见 UC-11.2）——
    **未接受的草稿卡不会有 agent 去执行，也就不会触发授权流**。
  - 该任务已指定 `executor`（agent）并已开始执行。
  - 三层权限的另两层已就绪：MCP 已注册并配了授权范围；agent 已配工具白名单
    （[裁决] agent 未配工具白名单不得发布）。
- **触发条件**：
  - [原型] **agent 执行到一半发现缺权限**——原型实例：
    「等待输入 R2『核对客户方联系人与决策链』**阻塞：Echo 请求读取「客户 CRM」，
    权限包里没有** `[去授权]`」。
  - [原型] 或 agent 在开跑前预检权限包发现范围不足，直接请求授权
    （原型「我的今天」实例：`R1·授权 Echo 请求读取「客户 CRM」以核对联系人 ——
    是否把 CRM 读取权限加入这次任务的权限包？`）。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

1. **系统挂载权限包**：任务被创建时（手工建卡或汇入建卡，见 UC-11.2），
   系统从**任务模板**取默认权限包写入该任务（模板携带权限包，见 UC-11.7）；
   无模板时权限包为**空集**（不是「全项目可读」）。
   **系统响应**：权限包的 `scopes` 逐条声明该任务允许读写哪些
   **项目 / 组 / 材料类别 / 外部来源**；卡片详情页可查看。
   [原型] 实例：「资质尽调（默认 Scout）：完成标准 12 项·**权限包：项目文件＋组织清单 v3**·
   R3 前必须人批准·预算 ≤800k」。

2. **系统推导权限包的风险等级 [D-28]**：按**操作类型**在服务端规则表中推导 `risk_level`
   （读公开资料恒 R1、外发邮件恒 R3）；**任务模板可覆盖**推导结果（唯一合法覆盖入口）。
   **系统响应**：推导与覆盖都在服务端完成；风险等级决定该任务的审批门槛
   （R2/R3 需人批准，见 UC-11.2 D-27）。

3. **agent 请求访问某数据**：agent 执行中要读某个资源。
   **系统响应：三层权限求交判定**——
   ① 该资源是否在 **MCP 授权范围**内（10-mcp）；
   ② 该操作是否在 **agent 工具白名单**内（04-agent）；
   ③ 该资源是否在**本任务的权限包 `scopes`** 内（本用例）。
   **三层取交集：任一层不允许即不允许**，**默认拒绝**（未显式允许即拒绝）。
   判定必须在服务端执行，不由 agent 自我裁定。

4. **命中缺权限时任务转「等待输入」**：三层判定不通过时，
   **agent 立即停止该动作**，任务打上 **`waiting_input`（等待输入）** 标记。
   **硬约束**：**不失败、不静默跳过**——
   - **不失败**：任务不进入 `done`、不报错终止，已完成的部分保留；
   - **不静默跳过**：**不允许** agent「跳过这一步继续做别的」或「用替代数据源凑答案」，
     也不允许把缺失的部分当作「查无此项」写进结论。
   [原型印证]「进行中（**2 项等待输入**）」「AI 停在这里，不会绕过你继续」。

5. **系统生成并弹出授权请求给负责人**：请求必须说明**四件事 + 两个范围参数**：
   - **要读什么**：具体资源名与范围（如「客户 CRM 的联系人表」，不是「一些数据」）。
   - **为什么要读**：关联到当前任务的哪一步、不读会怎样
     （[原型] 「Echo 请求读取『客户 CRM』**以核对联系人**」）。
   - **授权后 agent 能做什么**：授权带来的具体能力边界（只读？可写？能否外发？）。
   - **授权范围**：项目 / 组 / 材料类别 / 外部来源的具体取值。
   - **有效期**：本次授权多久后自动失效。
   - [原型] 请求文案形态：「**是否把 CRM 读取权限加入这次任务的权限包？**」
   **系统响应**：该请求同时出现在负责人的「我的今天 → 等我判断」区（UC-11.5 ① 区）
   与项目看板该卡上的 `[去授权]` 入口。

6. **人做出授权决定**（**授权人恒为人**，[D-39]）：
   - **批准**：可**收窄**范围与有效期（授予 ≤ 请求）；写入本次任务的权限包，
     `granted_by` 记为该人，`expires_at` 记为实际有效期。
     **系统响应**：agent 从中断点继续执行；权限**只对本任务生效**，不外溢到其它任务。
   - **拒绝**：任务转 **`blocked`（阻塞）** 并**记录拒绝理由**（见第 8 步）。
   - **两种结果都写审计**（授权与拒绝同等留痕）。

7. **系统执行授权的三条边界**——**逐次、限范围、限时**：
   - **逐次**：一次授权只对**这一次任务**有效；同一 agent 下次做别的任务需重新授权。
     **不产生「以后都允许」的常设权限**。
   - **限范围**：授予的 `scopes` 不得超过请求范围，也不得超过 MCP 授权范围与工具白名单
     （仍受三层交集约束——**授权只能在交集内加，不能突破另两层**）。
   - **限时**：`expires_at` 到期后权限**自动失效**，无需人工回收；
     失效后 agent 再访问同一资源须重新走授权流。
   - **默认拒绝**：权限包中未显式列出的范围一律视为不允许。

8. **拒绝或超时后任务转「阻塞」**：
   - 人明确拒绝 → 任务标 `blocked`，卡上显示**阻塞原因**（「负责人拒绝授权读取客户 CRM」）。
   - 授权请求**超时未响应** → 同样标 `blocked`，原因为「授权请求超时未处理」。
   - **硬约束**：**不得伪装成已完成**——被阻塞的任务
     ① 不得进入 `done`；② 其部分产出不得作为完整交付物提交验收；
     ③ 结论中必须显式标注「因缺少 X 授权，Y 部分未完成」。
   - 阻塞后可由人补授权、改派人工执行、或显式关闭任务并说明原因。

9. **系统收口**：授权请求、授权决定（批准/拒绝/超时）、权限包变更、
   权限到期自动失效，四类事件全部写审计，可按任务、agent、授权人、资源检索。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[设计] 负责人不在线或无权批准该级别的请求时，
    请求上抛给**有权审批人**（项目经理），并在原负责人处保留可见；
    **上抛对象恒为人**。
  - A2：[设计] 人可选择**改派人工执行**而不是授权——
    任务的 `executor` 从 agent 改为人，`waiting_input` 解除，权限包不变更。
  - A3：[设计] 人可**部分批准**：只授予请求范围的一个子集
    （如只给「联系人表」不给整个 CRM），agent 在缩小的范围内继续，
    若仍不足则再次发起请求（可重复，但每次都要记录）。
  - A4：[设计] 同一任务在执行中多次缺权限时逐次请求，**不合并成一次大授权**——
    合并会让人失去逐项判断的机会。
- **异常流程**：
  - E1：[设计] 三层权限判定服务不可用时，**按默认拒绝处理**（fail-safe），
    任务转 `waiting_input` 并说明是系统原因，**不得因判定服务挂了就放行**。
  - E2：[设计] agent 试图绕过判定直接访问资源时，
    数据层必须再次拦截（**纵深防御，不止在调度层判定**），并写安全审计。
  - E3：[设计] 授权在 agent 执行中途到期时，当前动作立即中止并转 `waiting_input`，
    已读取的数据按留存策略处理；**不允许「已经开跑就跑完」**。
  - E4：[设计] 授权人在批准瞬间失去审批权限时，授权不生效并提示重新走流程。
  - E5：[设计] 授权请求的资源已被删除或撤回（如 UC-17.2 的待删除队列）时，
    请求自动作废并告知负责人，**不得授权一个已被撤回的资源**。
  - E6：[设计] agent 在被拒绝后重复发起同一请求时按冷却期限流，
    避免用重复弹窗逼人点同意（防授权疲劳）。

## R5 权限与可见性

- **负责人（默认授权人）**：可对自己负责的任务的授权请求做批准/拒绝；
  批准范围不得超过其本人在该项目中的可见范围——
  **人不能授权 agent 读自己都读不到的数据**（这是本用例最容易被漏掉的一条）。
- **项目经理 / 引导师（有权审批人）**：可处理上抛的请求；可查看全项目的授权记录。
- **组长**：可处理本组任务的 R1/R2 授权请求；**R3 授权 [待确认] 是否需上收**。
- **组员**：只能处理自己负责的任务的 R1 请求；R2/R3 上抛。
- **agent**：**只能请求，不能授予**——[D-39] **agent 不能给 agent 授权**，
  也不能给自己授权、不能代人点批准。接口层面必须拒绝任何以 agent 身份提交的授权决定。
- **观察者**：不参与任务，不可见授权请求与权限包。
- **未登录、链接失效或未列出的角色**：默认无权限；接口不得返回越权数据。

## R6 后置条件 / 不包含

- **正常后置条件**：
  - 每张已被接受的任务卡都有一份可查看的权限包（可能为空集）。
  - agent 的每次数据访问都经过三层交集判定，判定结果可追溯。
  - 缺权限时任务处于 `waiting_input` 且有一条待处理的授权请求。
  - 授权批准后权限**只对本任务生效**，且带明确有效期。
  - 授权与拒绝都已写审计。
  - [设计验收] AC1：任一 agent 数据访问被允许 ⟺ **三层同时允许**；任一层拒绝即整体拒绝。
  - [设计验收] AC2：缺权限时任务**既不是 `done` 也不是失败终止**，
    而是带 `waiting_input` 标记且原任务数据完整保留。
  - [设计验收] AC3：所有 `authz_decision` 的决定人**都是人的账号**；
    **不存在决定人为 agent 的授权记录**。
  - [设计验收] AC4：授权记录都带 `expires_at`；到期后同一访问被拒绝。
  - [设计验收] AC5：被拒绝或超时的任务标 `blocked` 且不得进入 `done`。
- **失败后置条件**：
  - 不产生「未经授权却已读取」的数据访问；不产生无授权人的授权记录；
    不产生「阻塞但显示为完成」的任务；失败事件进入可观测日志。
- **不包含**：
  - **MCP 注册与授权范围配置**（属 10-mcp，本用例只消费其判定结果）。
  - **agent 工具白名单的配置与上线门禁**（属 04-agent）。
  - **风险规则表的维护**（属 UC-11.2 的推导服务与 UC-11.7 的模板覆盖）。
  - 组织级的常设数据权限（那是身份权限内核的事，本用例只做**任务级的逐次授权**）。
  - 授权的批量管理界面、授权策略引擎（[待确认] 是否需要）。

## R7 业务规则（不随具体实现变化的硬性约束）

- **[裁决 · 硬约束] 权限模型三层，取交集**：
  **MCP 授权范围 × agent 工具白名单 × 任务权限包（R1/R2/R3）**。
  **任一层不允许即不允许。** 授权流只能在交集内**加**权限，**不能突破另外两层**。
- **[硬约束] 默认拒绝**：权限包中未显式列出的范围一律不允许；
  空权限包 ≠ 全部允许，空权限包 = 什么都不允许。
- **[原型 · 硬约束] 缺权限时任务转「等待输入」，不失败、不静默跳过**：
  agent 必须停在原地等人，**不得**跳过该步骤继续、不得换替代数据源蒙混、
  不得把缺失当作「无此数据」写进结论。
- **[硬约束] 授权是逐次、限范围、限时的**：
  ① **逐次**——只对本次任务有效，不产生常设权限；
  ② **限范围**——授予 ≤ 请求，且仍受三层交集约束；
  ③ **限时**——必须有 `expires_at`，到期自动失效。
- **[硬约束] 授权与拒绝都写审计**，同等留痕；到期自动失效也写审计。
- **[D-39 · 硬约束] 授权人恒为人**：只有负责人或有权审批人能授权；
  **agent 不能给 agent 授权**，不能给自己授权，不能代人确认。
- **[硬约束] 人不能授权超出自己可见范围的数据**——授权是**转授**，不是提权。
- **[D-28] 权限包的风险等级由操作类型自动推导，任务模板可覆盖**（唯一合法覆盖入口）。
- **[硬约束] 拒绝或超时后任务转「阻塞」并说明原因，不得伪装成已完成**：
  阻塞任务不得进入 `done`，其部分产出不得作为完整交付提交验收，
  结论中必须显式标注未完成的部分与原因。
- **[原型] 阻塞 / 等待输入 / 超期是标记，不是列**——不占 `status` enum 的取值位
  （与 UC-11.1 的五态 enum 不冲突）。
- **纵深防御**：三层判定在调度层执行，数据访问层必须再次校验，
  不能只靠一处拦截；绕过尝试写安全审计。

## R9 非功能约束

- **性能/规模预期**：
  - [设计] 三层权限判定必须是**同步、低延迟**的（p99 < 100ms），
    否则会拖慢每一次 agent 数据访问；判定结果可缓存但**授权变更必须立即失效缓存**。
  - [设计] 授权请求生成到出现在负责人界面应在 5 秒内（这是人在等的场景）。
- **安全/隐私/合规**：
  - **默认拒绝 + 最小权限**是本用例的底色；任何「为了方便先放开」的实现都不可接受。
  - 授权记录属审计范围，**不可删除**（对齐项目级审计「四类事件同一条时间线，不可删除」）。
  - 授权请求中展示的资源名称本身可能敏感——请求详情只对有权审批人可见。
  - 涉及客户机密材料的权限包必须与模型策略联动
    （[原型] 「机密材料 仅本地 qwen3」「客户机密材料只能由本地模型处理」）。
  - agent 读取的每一份数据都要留痕（导出与 AI 读取留痕），可与 UC-17.1 审计对齐。
- **兼容与降级要求**：
  - 响应式 Web；**移动端必须能完成授权决定**——人经常在现场，
    授权请求卡住的是整条 AI 执行链。
  - 判定服务降级时按默认拒绝，**绝不降级为默认允许**。

## R11 切分提示（给 requirement-author）

- 建议拆分：
  ① **权限包数据结构 + 挂载到任务对象**（含空集 = 默认拒绝的语义）；
  ② **三层权限求交判定服务**（MCP × 工具白名单 × 权限包，默认拒绝、fail-safe）——

## R12 AI Ready 验收线索

以下行为应可由自动化测试、接口断言或可复现人工步骤验证：

- V1（三层交集 · AC1）：构造判定矩阵——三层各取「允许 / 不允许」共 8 种组合，
  逐一调判定接口，断言**只有三层全允许时返回允许**，其余 7 种全部拒绝。
- V2（默认拒绝）：给任务挂一个空权限包，让 agent 请求读任意资源，断言拒绝；
  断言拒绝原因指向「不在权限包内」而非「资源不存在」。
- V3（授权不能突破另两层）：把某资源加入任务权限包，但该资源不在 MCP 授权范围内，
  断言判定仍为拒绝——**授权只能在交集内加**。
- V4（等待输入 · AC2）：让 agent 执行到一半请求一个权限包外的资源，断言
  ① 任务被打上 `waiting_input` 标记；② `status` **未变为 `done`**、未变为失败终止；
  ③ 已完成部分的产出数据完整保留；④ 生成了一条 `authz_request`。
- V5（不静默跳过）：同 V4 场景下断言 agent **未继续执行后续步骤**、
  **未使用替代数据源**、产出中不含「该项无数据」类结论；agent 的执行日志停在中断点。
- V6（请求内容完整性）：断言 `authz_request` 含且非空：要读什么（具体资源）、
  为什么要读（关联任务步骤）、授权后能做什么、请求范围、建议有效期、超时时限。
- V7（授权人恒为人 · AC3 · D-39）：以 agent 身份调授权决定接口，断言返回 403；
  断言库中所有 `authz_decision.granted_by` 都是人的账号 ID，
  查询「决定人为 agent 的授权记录」返回**空集**。
- V8（agent 不能给 agent 授权）：让 agent A 尝试为 agent B 的请求授权，断言拒绝并写安全审计。
- V9（不能授权超出自己可见范围）：以只能看第 2 组的组长身份，
  尝试授权 agent 读第 3 组的材料，断言拒绝。
- V10（逐次）：为任务 T1 授权读资源 R；让同一 agent 在任务 T2 中请求读 R，
  断言**仍需重新授权**（T1 的授权不外溢）。
- V11（限范围 · 部分批准）：agent 请求「整个客户 CRM」，人只批准「联系人表」，
  断言权限包中写入的是「联系人表」；agent 随后访问 CRM 其它表时被拒绝并再次发起请求。
- V12（限时 · AC4）：授权 `expires_at = T`，把系统时间推进到 `T+1`，
  断言同一访问被拒绝、任务转 `waiting_input`；断言有一条「权限到期自动失效」的审计事件。
- V13（执行中到期 · E3）：让授权在 agent 执行中途到期，
  断言当前动作立即中止、任务转 `waiting_input`，**未「跑完再说」**。
- V14（拒绝 → 阻塞 · AC5）：人拒绝授权，断言任务被标 `blocked`、
  卡上有具体拒绝原因、`status` **不为 `done`**；
  尝试把该任务提交验收，断言被拒绝并提示存在未完成部分。
- V15（超时 → 阻塞 · AC5）：授权请求超过时限未处理，
  断言任务同样标 `blocked` 且原因为「授权请求超时未处理」。
- V16（不伪装完成）：对一个 `blocked` 任务调完成接口，断言拒绝；
  断言其部分产出在被引用时带「因缺少 X 授权，Y 部分未完成」的标注。
- V17（fail-safe · E1）：mock 三层判定服务不可用，断言判定结果为**拒绝**（不是允许），
  任务转 `waiting_input` 并说明是系统原因。
- V18（纵深防御 · E2）：绕过调度层直接调数据访问接口读权限包外的资源，
  断言数据层拦截并写安全审计。
- V19（风险覆盖 · D-28）：套用一个覆盖了风险等级的任务模板，
  断言该任务权限包的 `risk_level` 取模板值，且审批门槛随之变化。
- V20（审计完整性）：授权请求、批准、拒绝、超时、到期失效五类事件均可按
  任务 ID / agent / 授权人 / 资源检索；断言审计记录**不可删除**。
