# 原始需求（细化）— UC-11.5 我的今天

> 所属：阶段二 · 让推演与成果可见 / M11 待办看板  
> 来源：原型 `任务 → 我的今天`（`proto-02-batch2.md`）；口径裁决 `DECISIONS-FINAL.md` D-29 / D-39。  

> 口径（四标记）：**[原型]** ＝ `WorkspaceX Standalone.html` **运行态实际存在**的行为（有界面可查，依据 scratchpad 的 proto-01~10 抽取档案）；**[Backlog]** ＝ `Backlog Use Case.html` 的**文档要求**（原型未必实现）；**[设计]** ＝ 依据前两者反推补全，**需人类确认**；**[待确认]** ＝ 不应由实现者自行决定。
> 元数据：优先级 **P1**；估点 **5**；建议迭代 **阶段二 · 迭代 9 · P1 补齐**；模块 11-board 合计 **39** 点 ＝ **存量 18**（11.1=3 / 11.2=5 / 11.3=5 / 11.4=5）＋ **新增 21**（11.5=5 / 11.6=8 / 11.7=8）；DECISIONS-DELTA 旧值 18 只算了存量，已陈旧；**phase-2 五模块合计 158 点**。
>
> **[人类已拍板 2026-07-27 · D-29]**「我的今天」**独立成 UC**，
> 四语义分区为：**等我判断 / 今天该我推进 / AI 正在替我跑 / 下一步轮到别人**。
> 它与 **UC-11.3 看板筛选并存**——同一批卡的**两种组织方式**，
> 状态源是同一套 `status` enum，**两者不互相取代**。
> **[D-39]** 分区按**负责人（人）**归属；「AI 正在替我跑」按**执行者**字段归属，负责人仍是我。
>
> **补写缘由**：原 11-board 四份用例只覆盖了「按状态列」这一种组织方式。
> 但看板回答的是「这件事在哪一步」，回答不了个人视角的「**现在轮到谁、什么在等我**」。
> 原型的这一屏页头原文就是：「**最重要的是什么 · 下一步轮到谁 · 什么在等我判断**」。

## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-11.5 / 我的今天
- **Actor**：**任一有任务的人**（项目经理 / 引导师 / 组长 / 组员 / 顾问），
  以**负责人本人视角**进入；agent 只作为「正在替我跑」的被观察对象，不是 Actor。
- **目标**：[原型] 把散在多个项目、多个看板列里的卡，按「**谁该动**」重新组织成四个语义分区，
  让人一眼看出：什么卡在等我拍板、今天我必须推进什么、AI 替我跑到哪了、我交出去的活卡在谁那。
- **本用例结果**：用户进入 `任务 → 我的今天`，看到四个分区各自的卡与计数，
  每个分区内的卡可**直接执行下一步动作**，动作回写同一套 `status` enum，
  看板视图（UC-11.1 / UC-11.3）立即反映同一变化。
- **系统边界**：四个语义分区的**判定规则与归属计算**、分区内卡的排序、
  分区级的下一步动作（接受 / 推进 / 查看 agent 运行 / 催办）、
  底注的当日汇总。**不含** `status` 状态机（UC-11.1）、不含看板筛选（UC-11.3）、
  不含提醒调度（UC-11.4）、不含授权流本身（UC-11.6，本视图只做入口）。
- **核心数据对象**：
  - **分区归属计算结果**：卡 → 四个分区之一（或不属于任何分区，则不在本视图出现）。
    这是**派生视图，不是新字段**——不在任务表上新增「分区」列，每次按规则实时计算。
  - **复用的既有字段**：`status`（五态 enum）、`owner`（负责人，恒为人）、
    `executor`（执行者，人或 agent）、`risk_level`（R1/R2/R3）、`due_at`、
    `waiting_on`（在等谁：人或事件）、agent 运行态（进度 / 已耗时 / token）。
  - **当日汇总**：今日 AI 完成项数与折算人时、停下等授权的项数
    （[原型] 底注原文：「今日 AI 完成 11 项、折算 6.5 人时；2 项停下等授权。」）。

## R2 前置条件 / 触发条件

- **前置条件**：
  - 用户已登录并至少归属一个组织；本视图**跨项目聚合**，不要求先进入某个项目。
  - UC-11.1 的统一五态 enum 已落地（分区规则读的就是它）。
  - UC-11.2 的 `inbox` 草稿态与风险分级已落地（「等我判断」区依赖它）。
- **触发条件**：
  - [原型] 用户点击一级导航 `任务 → 我的今天 6`（标签带待办计数徽标）。
  - [设计] 或从任意提醒/催办通知点进来，落在对应卡所在的分区并高亮该卡。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

1. **系统计算四个分区的归属**（跨用户有权访问的全部项目，实时计算，不落库）：

   | 分区 | 判定规则（服务端） |
   |---|---|
   | **① 等我判断** | 三类并入：<br>· **需要我接受的 `inbox` 卡**（AI 建的草稿，R2/R3 必须我接受，见 UC-11.2）<br>· **待我审批的 R2/R3 项**（agent 停在审批点等我批）<br>· **待我签署 / 待我验收的项**（`status = review` 且验收人是我） |
   | **② 今天该我推进** | `owner = 我` **且** (`due_at` = 今天 **或** `due_at` 已逾期) **且** `status ∈ {todo, in_progress}` |
   | **③ AI 正在替我跑** | `executor` 为 agent **且** 该 agent 运行中 **且** `owner = 我`；<br>卡上带**进度 / 已耗时 / 预算消耗** |
   | **④ 下一步轮到别人** | 我已交棒的卡：我曾是上一手（或我是发起人/负责人链上的一环）**且**当前 `waiting_on` 指向他人；<br>**必须显示在等谁**（人名 + 等待事项 + 是否逾期） |

   **系统响应**：一张卡**同一时刻只落一个分区**（按 ①→②→③→④ 的优先级取第一个命中的），
   避免同一张卡在四个区重复出现；不属于任何分区的卡不在本视图渲染。

2. **系统渲染分区 ①「等我判断」**：[原型] 每条显示**风险等级前缀 + 等待时长 + 到期**，
   并明写「AI 停在这里，不会绕过你继续」。原型实例：
   - `R3·需批准  Ledger 已暂停·等待 4 分钟 · 今天 18:00`
     「路径 B 是否承诺收益保底？这会改变整张商业模式画布的成本结构」`[提供判断][看依据]`
   - `R2·待验收  Scout 已交付·完成标准 3/3`——「**验收后才会成为可引用证据**」
   - `R1·授权    Echo 请求读取「客户 CRM」以核对联系人`（授权流详见 UC-11.6）
   **系统响应**：本区按「等待时长」倒序——等得越久越靠前，因为这一区是全局的阻塞点。

3. **系统渲染分区 ②「今天该我推进」**：[原型] 每条显示**执行模式**
   （人工 / AI / 人机协作）+ 完成标准进度 + 到期 + 来源项目/环节。原型实例：
   - `约访 2 家本地 EPC 负责人(人工·完成标准 1/3·8/04)`
   - `准备客户董事会汇报的一页纸摘要(人机协作·Ava 已备好初稿，等你定结论顺序·7/29)`
   - `决定是否给第 4 组延时 5 分钟(人工·来自 Kickoff 项目·环节 3·现在)`
   **系统响应**：已逾期的排在今天到期之前；来自进行中现场环节的卡置顶（时效最强）。

4. **系统渲染分区 ③「AI 正在替我跑」**：[原型] 每条显示 **agent + 当前步骤 + 进度**，
   例：`LG 三路径现金流对比(敏感性 2/3)`、`SC 资质可转让性尽调(已读 41 份)`。
   [原型] 明确的界面纪律：「**token、读取文件数、内部步骤都在任务详情的『执行』页，不占这一屏**」
   ——本屏只给一行摘要 + 进度，细节下钻到详情页。
   **[D-39] 系统响应**：这一区按 `executor` 归到我名下，但卡的 `owner` **仍然是我本人**；
   界面必须同时体现「Scout 在跑」与「我负责」两件事，**不得把负责人显示成 agent**。

5. **系统渲染分区 ④「下一步轮到别人」**：[原型] 每条显示**在等谁 + 等什么 + 是否逾期**：
   `周 签字确认资质尽调的结论(逾期 1 天)`、`高 提交第 2 组产出(今天)`、
   `陈 补齐供应链本地化率数据(8/02)`。
   **系统响应**：逾期项标红并提供**催办**入口（催办能力见 UC-11.4；
   本视图只是催办的入口之一）。

6. **用户操作：在分区内直接执行下一步动作**——**不需要跳到看板再操作**：
   - ① 区：`[接受]`（`inbox → todo`，走 UC-11.2 的接受门禁）、`[提供判断]`、`[签署]`、
     `[验收]`、`[要求补证据]`、`[看依据]`、`[去授权]`（走 UC-11.6）。
   - ② 区：`[推进]`（改 `status`）、`[改期]`、`[标记阻塞]`。
   - ③ 区：`[查看 agent 运行]`（跳任务详情的「执行」页）、`[暂停]`、`[追加预算]`。
   - ④ 区：`[催办]`、`[收回自己做]`（重新指派 `owner` 为我）。
   **系统响应**：**所有动作最终都写回同一套 `status` enum 与同一张任务表**；
   写入成功后本视图的分区归属实时重算（卡可能从 ① 移到 ②），
   同时 UC-11.1 / UC-11.3 的看板视图反映同一变化——**不存在两套数据**。

7. **系统渲染底注汇总**：[原型] 「今日 AI 完成 11 项、折算 6.5 人时；2 项停下等授权。」
   末尾附硬约束原文：「**责任人始终是人——AI 只拿到行动权，不承担验收。**」

8. **系统收口**：分区计算是读操作不写业务审计；
   第 6 步的每个动作按其所属用例的规则写审计（接受走 UC-11.2、状态变更走 UC-11.1、
   催办走 UC-11.4、授权走 UC-11.6）。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[设计] 某个分区为空时显示该区的真实空态（如「没有等你判断的事」），
    **不隐藏该区**——四个分区是固定骨架，空也要在，否则用户无法确认「确实没有」。
  - A2：[设计] 四个区全空时显示整屏空态与去看板的出口，不生成示例卡。
  - A3：[设计] 一张卡同时满足多个分区条件时按 ①→②→③→④ 优先级归入第一个命中的区，
    并在卡上标出它同时满足的其它条件（如「也已逾期」），**不重复渲染同一张卡**。
  - A4：[设计] 卡跨多个项目时按项目分组或在卡上标项目名——本视图是跨项目聚合，
    必须让人知道每张卡属于哪个项目。
- **异常流程**：
  - E1：[设计] 分区计算依赖的某个来源（如 agent 运行态服务）不可用时，
    该分区显示依赖失败态并说明影响范围，**其余三区照常渲染**，不整屏失败。
  - E2：[设计] 在分区内执行动作失败时，卡回到操作前的分区并显示失败原因，
    **不得因为界面已把卡移走就当作成功**。
  - E3：[设计] 用户对已被他人处理过的卡执行动作时（如别人已接受），
    提示「状态已变为 X」并刷新分区，不静默覆盖。
  - E4：[设计] 权限在浏览过程中被撤回时，相关卡从分区移除并说明原因。
  - E5：[设计] agent 运行中断或超预算时，卡从 ③ 区移入 ① 区（变成「等我判断」），
    **不得静默停在 ③ 区显示为还在跑**。

## R5 权限与可见性

- **本人**：本视图**只呈现与本人相关的卡**——`owner = 我`、待我审批/签署/验收、
  或我已交棒仍在等他人的卡。这是个人视角视图，不存在「看别人的今天」。
- **跨项目边界**：聚合范围严格限于用户有权访问的项目；
  失去某项目权限后该项目的卡立即从本视图消失。
- **组员 / 组长 / 引导师 / 项目经理**：均可使用本视图，
  可见内容由其在各项目中的角色分别裁定，**本视图不放大任何人的权限**。
- **观察者**：观察者不参与任务，**本视图对其不渲染**；接口直接拒绝。
- **agent**：不是本视图的使用者；agent 无法进入任何人的「我的今天」。
- **未登录、链接失效或未列出的角色**：默认无权限；接口不得返回越权数据。

## R6 后置条件 / 不包含

- **正常后置条件**：
  - 四个分区各自渲染（空区也在），每张卡只出现在一个分区。
  - 分区内执行的动作写回同一张任务表与同一套 `status` enum，看板视图同步反映。
  - 底注汇总反映当日 AI 完成量与等授权项数。
  - [原型验收] AC1（**UC-11.5 在 Backlog 中无对应条目，本 AC 为原型派生**）：
    「等我判断」区的每一条都对应一个**真实阻塞点**——
    AI 停在这里不会绕过人继续（`R3·需批准`、`R2·待验收`、`R1·授权` 三类）。
  - [设计验收] AC2：**同一张卡在本视图中只出现一次**（分区互斥）。
  - [设计验收] AC3：③ 区的每张卡 `executor` 为 agent 且 `owner` 为当前用户；
    **不存在 `owner` 是 agent 的卡**（D-39）。
  - [设计验收] AC4：本视图与 UC-11.3 看板筛选读同一套 `status` enum 与同一批卡；
    在本视图改状态，看板视图立即一致，反之亦然。
  - [设计验收] AC5：④ 区每张卡都能显示**在等谁**（具体人名，不是「等待中」这种含糊词）。
- **失败后置条件**：
  - 不产生「界面已移动卡但后端未写入」的状态；单个分区失败不导致整屏失败。
- **不包含**：
  - **UC-11.3 的看板筛选**——[D-29] **两者并存不互斥**：
    UC-11.3 是**看板内的筛选视图**（列结构不变、只收窄卡集合），
    本用例是**独立的语义分区视图**（换一套按「谁该动」的组织方式）。
    **本用例不取代看板筛选，看板筛选也不取代本用例。**
  - `status` 状态机与列投影（UC-11.1）、汇入与接受门禁的实现（UC-11.2）、
    提醒调度与催办记录（UC-11.4，本视图只提供入口）、
    授权流的弹窗与审批逻辑（UC-11.6，本视图只提供 `[去授权]` 入口）。
  - 原型中的 `收件箱` / `需要我处理` / `已委派` 三个子标签——
    [原型抽取结论] 这三个标签点开后内容与「我的今天」完全一致，**原型占位未设计**，
    不在本用例范围；是否保留为独立视图 [待确认]。
  - 工作量统计、个人绩效看板、跨人对比。

## R7 业务规则（不随具体实现变化的硬性约束）

- **[D-29 · 硬约束] 四语义分区是固定骨架**：
  **等我判断 / 今天该我推进 / AI 正在替我跑 / 下一步轮到别人**，四个区固定存在、
  顺序固定、空区也渲染。**不允许实现方增删或改名分区**。
- **[D-29 · 硬约束] 与看板筛选并存不互斥**：本视图与 UC-11.3 是**同一批卡的两种组织方式**，
  **状态源是同一套 `status` enum、同一张任务表**。
  **禁止**为本视图新建状态字段、新建分区列、或复制一份卡数据。
  分区归属是**每次实时计算的派生结果**，不落库。
- **[D-39 · 硬约束] 分区按负责人（人）归属**：四个分区的归属计算以 `owner`（人）为主键。
  **「AI 正在替我跑」按 `executor` 字段归属，但该卡的 `owner` 仍是我**——
  界面必须同时呈现执行者与负责人，**不得把 agent 显示为负责人**。
- **[原型 · 硬约束] AI 停在「等我判断」不会绕过人继续**：
  R2/R3 的审批点、验收点、授权点都会把任务停住并落入 ① 区；
  agent **不得**因为等待超时就自行继续（对齐 UC-11.6 的「等待输入」态）。
- **[原型 · 硬约束] 责任人始终是人**——原型底注原文：
  「**责任人始终是人——AI 只拿到行动权，不承担验收。**」
- **[原型] 验收是引用资格的闸门**：① 区的「待验收」项，
  **验收后其产出才会成为可被决策引用的证据**（与 UC-13.2 / UC-9.1 同一条约束）。
- **[原型] ③ 区只给摘要**：token、读取文件数、内部步骤放任务详情的「执行」页，
  **不占本屏**——本屏是决策屏，不是监控屏。
- **[D-27] 未接受的 `inbox` 卡只出现在 ① 区**（作为「需要我接受」的判断项），
  **不进 ② 区**、不计入「今天该我推进」的工作量。
- **[原型] ④ 区必须显示在等谁**：具体人名 + 等待事项 + 是否逾期，
  不允许只显示「等待中」。
- 分区计算与动作权限均在服务端执行；隐藏分区不构成安全控制。

## R8 界面线索

- **前端入口**：[原型] 一级导航 `任务` 的视图之一——`我的今天 6`（标签带计数徽标）。
  同级还有 `收件箱 3`、`需要我处理 3`、`AI 正在执行 5`、`已委派 4`、

## R9 非功能约束

- **性能/规模预期**：
  - [设计] 四个分区的归属计算须在一次服务端查询内完成并返回，
    **不允许前端拉全量卡再本地分区**（会同时破坏性能与权限裁剪）。
  - [设计] 本视图跨项目聚合，查询必须带用户维度索引；首屏 1 秒内可见。
  - [设计] ③ 区的 agent 运行进度可增量推送刷新，但**刷新失败不得让整屏卡住**。
- **安全/隐私/合规**：
  - 服务端先按各项目角色裁剪可见集合，再做分区归属计算。
  - ① 区展示的审批依据摘要须遵守原项目的可见性规则，不得因聚合到个人视图而绕过脱敏。
  - ③ 区展示的 agent 运行信息不得泄露该用户无权访问的材料名称与内容。
- **兼容与降级要求**：
  - 响应式 Web；移动端保证四分区可浏览、① 区动作可执行（这是最需要随时处理的一区）。
  - 实时通道不可用时降级为轮询并标「非实时」，进度值标注最后更新时间。
