## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-11.4 / 到期提醒
- **Actor**：**负责人**（被提醒方，恒为人）、**项目经理 / 引导师 / 组长**（催办方）、
  **系统调度器**（提醒的触发方）。
- **目标**：让「快到期 / 已逾期」这件事主动找到负责人，而不是等他自己去看板上翻；
  并让催办这件事**留痕、可查、不重复轰炸**。
- **本用例结果**：任务到期前一天与当天各推一次提醒；逾期后每天一次直到改状态或改期；
  催办方可按角色批量催办，每次催办写入催办记录并对被催方可见。
- **系统边界**：到期扫描与提醒调度、提醒去重与免打扰、催办动作与催办记录、
  提醒渠道分发（产品内 / 邮件）。**不含**到期日的设置（属 UC-11.1 建卡/编辑）、
  不含状态机（UC-11.1）、不含筛选（UC-11.3）。
- **核心数据对象**：
  - **提醒规则**：触发时点（到期前 1 天 / 当天 / 逾期后每天）、渠道、接收人（= 负责人）。
  - **提醒记录**：任务 ID、触发时点、渠道、发送结果、是否被去重抑制。
  - **催办记录**：催办人、被催人、任务 ID、时间、渠道、附言；用于「可查、避免重复轰炸」。
  - **复用的已有字段**：`due_at`、逾期标记、`status`（`done` 与 `inbox` 都不提醒）、`owner`。

## R2 前置条件 / 触发条件

- **前置条件**：
  - 用户已建立可校验的正式或临时身份，且拥有目标组织、项目、小组或资源的访问权。
  - 目标资源存在且未被删除/冻结；依赖能力“各模块的任务产生点（图谱、报告、访谈、会前任务）”可用，或界面能明确显示其不可用状态。
  - 若动作涉及个人数据、录音、原始材料或跨范围读取，相应授权与留存策略已生效。
- **触发条件**：
  - [原型] 任务的 `due_at` 临近或已超过（原型已呈现这两个状态：卡片到期日、「已逾期」标）。
  - [设计] 催办方在看板上对某人/某角色发起催办（**该入口在原型中确认缺失，需补**）。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

1. **系统扫描**：定时扫描任务表，取 `due_at` 非空且 `status ∉ {done, inbox}` 的卡。
   - **排除 `inbox`** 是硬约束（UC-11.2 R7）：**未经人接受的草稿卡不触发到期提醒**。
   - **排除 `done`**：已完成不再提醒。
   - 扫描口径与看板底注 `逾期 1 · 今天到期 2` 的统计口径**必须一致**——同一份判定逻辑，
     不允许提醒说逾期而看板显示不逾期。
2. **系统按时点推送提醒**：[Backlog]（Backlog UC-11.4 `flow` 原文
   「到期前一天与当天各提醒一次」「逾期后每天一次，直到改状态或改期」
   「可按角色批量催办」——**三时点的来源是 Backlog，不是原型**；
   **「催办」二字在 proto-01~10 十份档案中零命中**）
   - **到期前一天**推一次；**到期当天**推一次；
   - **逾期后每天一次**，直到该卡改状态（离开逾期条件）或改期（`due_at` 被推后）为止。
   - 接收人恒为**负责人 `owner`**（[D-39] 恒为人）；`executor` 为 agent 的卡也提醒负责人，
     **不向 agent 发提醒**。
3. **系统去重与抑制**：同一任务同一时点只发一次（幂等键 = 任务 ID + 触发时点 + 渠道）；
   若该任务在同一天已被人工催办过，则当天的自动提醒**合并为一条**，
   落实「AC1 催办记录可查，**避免重复轰炸**」。
4. **催办方操作**：在看板上选中若干逾期卡，或**按角色批量催办**（如「催 4 位组长交本组产出」），
   填可选附言后发出。**系统响应**：校验催办方对这些卡有管理权；
   逐条写**催办记录**（催办人 / 被催人 / 任务 / 时间 / 渠道 / 附言）；
   同一催办人对同一被催人同一任务在冷却期内重复催办被拒绝并提示上次催办时间。
5. **被催方响应**：被催方在产品内看到催办提示，可直接从提示跳到该卡并执行下一步动作
   （推进状态 / 改期 / 说明阻塞原因）。改期或改状态后，该卡的后续每日提醒立即停止。
6. **系统收口**：催办记录对**催办方与被催方双向可见**（谁在什么时候催过我、我催过谁），
   并写审计事件。

> **实现前提**：第 4、5 步依赖的催办按钮、催办浮层、催办记录列表、提醒设置面板
> **在已探明的两个看板屏中确认缺失**，需先补原型再实现（见 R8）。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[原型] **免注册进场的现场组员没有邮箱时只在产品内提醒**（名单实名参与者不建账号，
    见 D-01），不因为没有邮箱就跳过提醒。
  - A2：[设计] 负责人为空的卡（尚未指派）**不提醒任何人**，改为在看板上标「待指派」
    并计入项目经理的「需指派」计数——**不得把提醒发给建卡人当作兜底**。
  - A3：[设计] 卡改期后，已发出的提醒不撤回，但后续提醒按新的 `due_at` 重新计算。
- **异常流程**：
  - E1：[设计] 提醒渠道（邮件/推送）不可用时，**产品内提醒仍必须落地**，
    并在提醒记录中标明渠道失败；**不得因为一个渠道失败就整条提醒静默丢弃**。
  - E2：[设计] 调度器重启或补偿重跑时按幂等键去重，**同一任务同一时点不重复发**。
  - E3：[设计] 催办方在冷却期内重复催办时被拒绝，返回上次催办时间，避免重复轰炸。
  - E4：[设计] 被催人已离开项目/权限被撤时不再向其发提醒，转为提示项目经理重新指派。
  - E5：[设计] 大批量催办部分失败时逐条返回结果，成功的写记录、失败的可重试，
    **不得整批标为成功**。

## R5 权限与可见性

- **负责人（被提醒方）**：收到自己负责的卡的到期提醒与催办；可查看谁在什么时候催过自己。
- **项目经理 / 引导师**：可对本项目任意卡发起催办，可按角色批量催办；可查看全项目催办记录。
- **组长**：可对本组卡发起催办；可查看本组催办记录。
- **组员**：只能查看与自己相关的提醒与催办记录，**不能对他人发起催办**
  （[待确认] 是否允许组员催同组同伴）。
- **观察者**：不可见待办看板，**也不接收任何到期提醒与催办**。
- **agent（执行者）**：**不接收提醒**——[D-39] 提醒的接收人恒为人（负责人）。
- **未登录、链接失效或未列出的角色**：默认无权限；接口不得返回越权数据。

## R6 后置条件 / 不包含

- **正常后置条件**：
  - 到期前一天、到期当天、逾期后每天各产生且仅产生一条提醒记录（同渠道去重后）。
  - 每次催办都写入催办记录，对催办方与被催方双向可见。
  - 改状态或改期后，该卡的后续每日提醒立即停止。
  - [Backlog验收] AC1：催办记录可查，避免重复轰炸（Backlog UC-11.4 `ac` 原文）。
    ⚠ **原型确认缺失**：**「催办」二字在 proto-01~10 十份档案中零命中**，
    催办界面与催办记录在原型中均不存在（见 R8）。
  - [设计验收] AC2：`status = inbox` 与 `status = done` 的卡**永不触发到期提醒**。
  - [设计验收] AC3：提醒接收人恒为 `owner`（人）；不存在发给 agent 的提醒记录。
  - [设计验收] AC4：提醒的逾期判定与看板底注 `逾期 N · 今天到期 M` 使用同一套判定逻辑，
    两处结论恒一致。
- **失败后置条件**：
  - 渠道失败不吞提醒；提醒失败必须留记录可重试；催办部分失败逐条可见。
- **不包含**：
  - **到期日的设置与修改**（属 UC-11.1 的建卡/编辑）。
  - **第三方 IM 通知**（明确范围外）。
  - 复杂的提醒策略引擎（自定义提前量、按人配置节奏）——本用例只做原型口径的固定三时点。
  - 不扩展到本 use case 未声明的跨组织、跨客户或公开发布能力。

## R7 业务规则（不随具体实现变化的硬性约束）

- **[原型口径] 提醒时点固定三段**：到期前一天一次、到期当天一次、
  **逾期后每天一次直到改状态或改期**。
- **[D-27 · 硬约束] `inbox` 卡不触发到期提醒**：未经人接受的草稿卡不算任何人的活，
  自然不催任何人（与 UC-11.2 R7 同一条约束的另一面）。
- **[D-39 · 硬约束] 提醒接收人恒为负责人（人）**：`executor` 为 agent 的卡也提醒负责人，
  **不向 agent 发提醒、不把 agent 记为被催方**。
- **[Backlog] AC1：催办记录可查，避免重复轰炸**（Backlog UC-11.4 `ac` 原文）——
  [设计] 每次催办必须留记录；同一催办人对同一被催人同一任务在冷却期内不得重复发出。
  ⚠ **原型确认缺失**：催办界面与催办记录在原型中均不存在，见 R8。
- **[原型] 免注册进场的现场参与者没有邮箱时只在产品内提醒。**
- **判定口径唯一**：提醒扫描的「逾期 / 今天到期」判定必须与看板底注计数**共用同一份逻辑**，
  不允许两处各写一套。
- 提醒与催办都必须记录审计事件（谁催的、催了谁、催的哪张卡、什么时候）。
- 所有权限判断在服务端执行；隐藏催办按钮不构成安全控制。

## R9 非功能约束

- **性能/规模预期**：
  - [设计] 到期扫描为定时批处理，须能在单次扫描内覆盖全组织的活跃卡且不阻塞在线请求。
  - [设计] 批量催办按条异步发出，界面在 1 秒内返回受理回执，逐条结果异步回填。
  - [设计] 提醒与催办记录必须分页加载，禁止一次拉取全部历史。
- **安全/隐私/合规**：
  - 最小权限、组织/项目/小组隔离、传输与静态加密、敏感字段脱敏、导出与 AI 读取留痕。
  - 原始材料、录音、转写、私聊、个人身份与客户数据按授权和留存策略处理。
- **兼容与降级要求**：
  - 响应式 Web；桌面端提供完整能力，移动端保证加入、查看、输入、投票/确认等现场关键动作。
  - WebSocket/实时通道不可用时降级为轮询并显示“非实时”；断网允许保留未提交输入，但不得伪装已同步。

## R10 已知约束 / 依赖

- **内部依赖**：**UC-11.1**（`status` enum、`due_at`、逾期判定与底注计数逻辑）、
  **UC-11.2**（`inbox` 不提醒规则）、**phase-00 共享内核的通知能力**、身份与权限、审计。
- **跨模块契约**：提醒与催办事件必须使用统一的任务标识与人员标识；
  逾期判定逻辑与看板计数**共用同一实现**，不允许提醒服务另写一套。
- **前置阻塞**：**本用例的界面在已探明区域内确认缺失**，
  必须先补齐 R8 列出的四个界面（催办入口 / 提醒设置 / 催办记录 / 通知落地位置）
  才能进入实现，否则只能做无界面的后端调度部分。
- **技术约束**：[原型] 产品为响应式网页（原型含移动端对照屏）；[Backlog] 第三方 IM 通知明确为范围外。
- **[待确认] 通知渠道**：产品内通知是否为必选、邮件是否为默认开启、
  是否需要移动端推送——原型未给出通知中心界面，需产品定稿。
- **[待确认] 提醒时点策略**：「到期前一天」的具体发送时刻（当天几点）、
  逾期后每日提醒的发送时刻、是否随用户时区变化、是否有次数上限（连续逾期 30 天是否还发）。
- **[待确认] 免打扰规则**：工作时间外是否静默、周末是否发送、
  用户能否自行关闭某类提醒、关闭后逾期是否仍强制提醒。
- **[待确认]** 组员能否对同组同伴发起催办。
- **[待确认]** 催办冷却期时长（本文按「有冷却期」写，具体时长需产品给出）。

- **[设计] 架构对齐 · Context Engine**（`docs/architecture/context-engine.md`，2026-07-28 定稿）：
  - **AI 取上下文只能通过 Context API 领取 Context Pack**——任何 agent、副驾驶或生成动作
    都不得绕过服务平面直查 `claims` / `segments` / `artifact_versions` 等库表。
    绕过即丢失 `permissionDecisionId` 与引用锚点，`uc-14-6`「AI 读到了什么」将不可重放。
  - **编排边界**：**LangGraph 只用于深度研究、人工确认（HITL）与多阶段生成**；
    文件摄取、批量导入、定时与重试一律走**持久任务系统**（MVP 为 PG outbox + job table）。
    LangGraph 不得被当作通用任务队列；HITL 用动态 `interrupt()`，节点恢复时副作用必须幂等。
  - **权限**：**租户与项目隔离在 PostgreSQL RLS 层强制**，应用连接使用受 RLS 约束的
    **非 owner** 角色（PG 中表 owner 默认不受 RLS 限制）。本文 R5 的权限判定与 R12 的
    越权断言是**第二道**防线，不是唯一防线。Artifact 权限必须传播到 Segment、embedding、
    图边、缓存与 Context Pack；交集生成内容取所有来源权限的**最严格**结果。

## R12 AI Ready 验收线索

以下行为应可由自动化测试、接口断言或可复现人工步骤验证：

- V1（三时点 · 可复现）：造一张 `due_at = D` 的 `todo` 卡，把系统时间依次推进到
  `D-1`、`D`、`D+1`、`D+2`，断言提醒记录条数依次为 1、2、3、4，
  且每条记录的触发时点标记正确。
- V2（停止条件）：在 `D+2` 把该卡置为 `done`，再推进到 `D+3`，
  断言**不再新增提醒记录**；另造一张卡在 `D+2` 把 `due_at` 改为 `D+10`，
  断言 `D+3` 无提醒、`D+9` 恢复「到期前一天」提醒。
- V3（inbox 不提醒 · AC2）：造一张 `status = inbox` 且 `due_at` 已过期的卡，
  推进时间跨越三个时点，断言**提醒记录数恒为 0**。
- V4（done 不提醒 · AC2）：同上以 `status = done` 造卡，断言提醒记录数恒为 0。
- V5（接收人恒为人 · AC3）：造一张 `owner = 林可(人)`、`executor = Scout(agent)` 的逾期卡，
  断言提醒记录的接收人恰为林可、**不存在接收人为 Scout 的记录**。
- V6（判定口径一致 · AC4）：随机造 20 张不同 `due_at` 的卡，
  断言提醒扫描判定为「逾期」的集合 == 看板底注 `逾期 N` 统计出的集合（集合相等，不只是数量相等）。
- V7（去重 · AC1）：在同一时点重复触发调度器 3 次（模拟重启补偿），
  断言提醒记录仍为 1 条；断言幂等键为 `任务ID + 触发时点 + 渠道`。
- V8（催办记录 · AC1）：以项目经理身份对一张逾期卡催办，
  断言催办记录含催办人/被催人/任务/时间/渠道/附言六字段，
  且催办方与被催方**双向可查**到同一条记录。
- V9（冷却期 · AC1）：同一催办人对同一被催人同一任务在冷却期内二次催办，
  断言返回拒绝并携带上次催办时间，且**未新增第二条催办记录**。
- V10（批量催办）：对「4 位组长」发起按角色批量催办，
  断言产生 4 条催办记录、逐条返回结果；mock 其中 1 条渠道失败，
  断言该条标为失败可重试而其余 3 条成功，**整批不被标为成功**。
- V11（渠道降级）：mock 邮件服务不可用，断言产品内提醒仍落地、
  提醒记录中邮件渠道标为失败，**提醒未被整条丢弃**。
- V12（无邮箱参与者）：对一个免注册进场、无邮箱的现场参与者的卡触发提醒，
  断言只产生产品内提醒记录且未尝试发邮件。
- V13（负责人为空）：造一张 `owner` 为空的逾期卡，断言**无任何提醒记录产生**，
  且该卡出现在项目经理的「待指派」计数中。
- V14（权限态）：以组员身份对他人的卡调催办接口，断言 403；
  以观察者身份调提醒与催办接口，断言 403 且其收件箱无任何本模块提醒。
- V15（审计态）：提醒与催办事件可按操作者、被催人、任务 ID、时间检索；越权催办写安全审计。
