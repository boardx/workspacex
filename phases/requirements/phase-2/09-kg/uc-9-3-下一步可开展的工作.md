## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-9.3 / 下一步可开展的工作
- **Actor**：**引导师**（项目角色，主使用者与派发者）、**组长**（项目角色，可领本组的工作）、
  **项目负责人**（组织角色，原文档称「项目经理」，见 `phase-1/00-core/uc-0-3`）
- **目标**：[原型] 把决策树上「还缺什么才能拍板」翻译成**一组可以马上开工的具体工作**——
  页头一句话说明：「每条都指向树上的一个待决节点 · 点『开展』即派给对应模块或小组」。
- **本用例结果**：[原型] 决策树下方呈现**一组工作卡**（原型实例 5 条），每条卡片字段固定为：
  **执行模块 / 预计耗时或工作量 / 负责人（人或 agent）/ 收益标签 / 验证目标节点 / `[开展]`**；
  点 `[开展]` 后工作落到对应业务模块，并在 11-board 待办看板生成对应卡片，两处可互相追溯。
- **系统边界**：工作卡的生成与排序、五类收益标签、验证目标节点绑定、`[开展]` 派发链路与回滚、
  重复派发拦截；**不含**各业务模块内部如何执行这条工作、也不含看板本身的列与筛选（11-board）。
- **核心数据对象**：工作卡（建议任务）、执行模块、工作量估算、负责人与执行者、收益标签、
  验证目标节点引用、派发记录、看板卡片引用。

## R2 前置条件 / 触发条件

- **前置条件**：
  - 用户已建立可校验的正式或临时身份，且拥有目标组织、项目、小组或资源的访问权。
  - 目标资源存在且未被删除/冻结；依赖能力「可视化模板/画布便签（节点来源）、实时转录（证据来源）、研究模块与访谈模块（证据来源）」可用，或界面能明确显示其不可用状态。
  - 若动作涉及个人数据、录音、原始材料或跨范围读取，相应授权与留存策略已生效。
- **前置条件补充**：
  - [原型] **决策树（UC-9.2）上至少存在一个 `待决` 或 `待验证` 节点**——没有待决节点就没有可开展的工作。
  - [设计] 目标执行模块（研究 / 访谈 / 投票 / 原型 / 测算）可用，或界面明确显示其不可用状态。
- **触发条件**：
  - [原型] 引导师在 `知识图谱 → 决策树` 页向下滚动到「下一步可以开展的工作」分区。
  - [设计] 决策树节点状态变化（新增待决节点、某节点被验证关闭）触发工作卡列表增量重算。
  - 系统从 **决策树 → 下一步** 进入本流程，并携带当前组织、项目、小组、角色和资源标识。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

1. **系统处理**：遍历决策树上全部 `待决` / `待验证` 节点，为每个节点生成**至少一条**可执行工作卡；
   [原型] 卡片的**六个字段一个都不能少**：
   `执行模块` / `预计耗时或工作量` / `负责人（人或 agent）` / `收益标签` / `验证目标节点` / `[开展]` 按钮。
2. **系统处理**：为每条工作卡打上**收益标签**，取值来自五类：
   `关掉 N 节点` / `补 N 证据` / `定优先级` / `推进 1 层` / `补决策依据`。
   [原型] 原型的五条工作卡实例：

   | 工作 | 收益标签 | 执行模块 · 工作量 | 负责人 | 验证目标节点 |
   |---|---|---|---|---|
   | DR 查三国资质转移条文 | **关掉 4 节点** | 研究模块 · 约 8 分钟 | 派给 **Scout**（agent） | 资质可随股权转移？ |
   | IT 追访两家本地 EPC | **补 2 证据** | 访谈模块 · 2 场 | 第 2 组组长 | 合资对象选谁 |
   | VT 全场投票：先验哪条 | **定优先级** | 全场投票 · 60 秒 | 引导师 | 主决策 |
   | UX 做归因看板原型 | **推进 1 层** | 原型模块 · 3 屏 | 第 4 组 | 首单商业模式 |
   | LG 算两条路径的回本 | **补决策依据** | 测算 · 需财务确认折现率 | 派给 **Ledger**（agent） | 以什么模式进入欧洲 |

   每条还带一句**为什么值得做**的说明（如「把『资质可转』这条冲突判死或判活，直接决定收购分支存亡」）。
3. **系统处理**：为每条工作卡**强制绑定一个验证目标节点**（`验证 → <节点名>`），
   该节点必须是决策树上真实存在的 `待决` / `待验证` 节点。[原型]
   [设计] 绑定不上目标节点的工作**不生成、不入列**——「没有验证目标的工作不属于本列表」。
4. **系统处理**：按收益排序工作卡——能关掉的节点数多、成本低的排前面；
   [设计] 排序依据可展开（「为什么这条排第一」），不做黑箱排序。
5. **引导师操作**：点某条工作卡的 **`[开展]`**。
   **系统响应**：[原型] 校验权限与目标模块可用性后执行**派发链路**：
   ① 在**对应业务模块**内创建具体工作实例（研究任务 / 访谈排期 / 投票 / 原型任务 / 测算任务）；
   ② 在 **11-board 待办看板**生成对应卡片，卡片携带来源链接（回指本工作卡与验证目标节点）；
   ③ 按 **D-39** 写入责任字段：**`负责人` 恒为人**（引导师 / 组长 / 指定成员），
   　agent（Scout / Ledger 等）写入独立的 **`执行者`** 字段，agent 不得占用负责人位；
   ④ 按 **D-27** 处理卡片初始态：由 AI 生成的卡**一律落 `inbox` 草稿态**，
   　R1 风险可自动接受，R2/R3 必须由人接受后才进 `todo`。
6. **系统响应**：[设计] 派发成功后把该工作卡置为「**已开展**」态，显示对应看板卡片链接与
   **执行进度回填口**。
   [Backlog] 同一目标节点已有在跑的同类工作时**不重复派发**
   （Backlog UC-9.3 `edge` 原文「同一节点已有在跑的任务时不重复派发」），
   [设计] 改为提示「已有一条在跑」并直达那条。
   ⚠ **原型只有五张工作卡与 `[开展]` 按钮**：「点开展会在待办看板生成卡」由 Backlog `flow` 与
   原型看板卡片的【决策树】来源徽标共同印证；但**「已开展」后置态、执行进度回填口、
   不重复派发、失败回滚这四项在原型中零依据**，均为 `[设计]`/`[Backlog]`。
7. **系统处理**：[Backlog] 派发过程中任一步失败（目标模块不可用、看板写入失败）→ **整体回滚**
   （Backlog `edge` 原文「派发失败（如模块不可用）要回滚卡片」）：
   [设计] 撤销已创建的模块工作实例与看板卡片，工作卡回到未开展态，明确提示失败原因并可重试。
8. **系统处理**：目标节点被验证关闭后（如「资质可随股权转移？」判定为可转），
   指向它的工作卡自动从列表移除或标为「目标已关闭」，并在决策树上回写该节点状态。[设计]
9. **系统收口**：校验 AC1「从图谱派出的任务能在待办看板与来源模块里同时看到」；
   记录派发的操作者、时间、目标节点、目标模块、结果与来源进审计；
   刷新工作卡列表、看板与决策树的【待决的岔口】计数。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[设计] 决策树上**没有任何待决/待验证节点**时，列表显示真实空态
    「当前没有待决节点，所有分支都已有结论」并给出回到决策树的入口，**不生成示例工作卡**。
  - A2：[设计] 某条工作的**负责人未指定**时，卡片仍可展示但 `[开展]` 置灰，
    提示「先指定负责人（必须是人）」；agent 只能填 `执行者`，不能顶替负责人（D-39）。
  - A3：[设计] 工作卡由 AI 生成时必须带机器产出标识与生成依据（指向哪个待决节点、缺什么证据）；
    引导师可编辑卡片的工作量、负责人与执行模块后再派发，编辑留痕。
  - A4：[设计] 引导师可**手工新增**一条工作卡，但同样必须选定一个验证目标节点才能保存。
  - A5：[设计] 目标节点在派发过程中被他人关闭时，派发中止并提示「目标节点已关闭，这条工作不再必要」。
- **异常流程**：
  - E1：[Backlog] **同一目标节点已有在跑的同类工作时不重复派发**（Backlog `edge` 原文）——
    [设计] `[开展]` 改为「已有一条在跑」并直达那条工作，不产生第二张看板卡。
  - E2：[Backlog] **派发失败（如目标模块不可用）必须回滚卡片**（Backlog `edge` 原文）——
    [设计] 已创建的模块工作实例与看板卡片一并撤销，工作卡回到未开展态；
    不得留下「模块里有、看板里没有」的半成品。
  - E3：[设计] 派发是跨模块写入，必须保证**模块实例与看板卡片同生同灭**；
    若只成功一半，系统需要能检测并自动补偿或回滚，不得静默留下孤儿卡。
  - E4：[设计] 请求超时、网络中断或依赖不可用时，保留引导师对卡片的编辑内容与最后成功数据，
    明确失败原因并提供安全重试。
  - E5：[设计] 两个引导师同时对同一条工作卡点 `[开展]` 时不得双发；以先到者为准，
    后到者收到「已有一条在跑」的明确提示。
  - E6：[设计] 权限在操作过程中被撤回时立即终止后续写操作；已完成步骤按审计规则保留，
    未提交输入留在本地草稿并提示重新授权。

## R5 权限与可见性

- **引导师**：可查看全部工作卡、编辑卡片字段、指定负责人、对**任意**工作卡点 `[开展]` 派发。
- **组长**：可查看全部工作卡；可对**验证目标属本组**或**负责人为本人**的工作卡点 `[开展]`；
  不能改他组工作卡的负责人。
- **组员**：只读查看工作卡；不能派发。
- **项目负责人**（组织角色，原文档称「项目经理」）：在被授权项目内只读查看工作卡与派发结果。
- **观察者**：只读查看工作卡的标题与收益标签；**不可见**负责人姓名与内部工作量估算，
  不能派发、不能编辑。
- **agent（Scout / Ledger 等）**：只能作为 `执行者` 被指派，**永远不能作为负责人**（D-39）；
  agent 的执行结果回到看板仍需人接受（D-27）。
- **未登录、链接失效或未列出的角色**：默认无权限；接口不得返回越权数据，不能只依赖前端隐藏。

## R6 后置条件 / 不包含

- **正常后置条件**：
  - 每条工作卡都有完整六字段，且**都指向决策树上的一个真实待决/待验证节点**。
  - 点 `[开展]` 后：目标业务模块内有工作实例、11-board 看板有对应卡片、两者与本工作卡三向可追溯。
  - 看板卡片的 `负责人` 为人、`执行者` 可为 agent；AI 生成的卡落 `inbox` 草稿态待人接受（D-27/D-39）。
  - [Backlog验收] AC1：从图谱派出的任务能在待办看板与来源模块里**同时**看到
    （Backlog UC-9.3 `ac` 原文）；[设计] 且能互相跳转。
  - [设计验收] AC2：收益标签取值落在五值枚举内（**取值 [原型] 可证，闭合性属设计约束**）；
    [原型] 每条工作卡的 `验证目标节点` 非空（五条实例均带「验证 → …」行）。
  - [设计验收] AC3：同一目标节点不产生第二条在跑的同类工作。
  - [设计验收] AC4：派发失败后模块实例与看板卡片均不残留。
- **失败后置条件**：
  - 不创建“看似成功”的正式记录；派发失败整体回滚，失败事件进入可观测日志。
  - 不产生「有工作卡但没有验证目标」的孤儿记录。
- **不包含**：
  - 各业务模块内部如何执行这条工作（研究怎么查、访谈怎么排）——属各模块自身用例。
  - 看板本身的列语义、筛选与「我的今天」（属 11-board / D-26 / D-29）。
  - AI 无人确认自动派发高影响工作、自动替人接受卡片。
  - 不扩展到本 use case 未声明的跨组织、跨客户或公开发布能力。

## R7 业务规则（不随具体实现变化的硬性约束）

- [原型] **每条工作必须指向决策树上的一个待决/待验证节点**（`验证 → <节点名>`）。
  **没有验证目标的工作不得出现在此列表**——这条列表的存在理由就是「为拍板扫清障碍」，
  不是通用待办池。服务端在创建时强制校验目标节点存在且处于 `待决`/`待验证` 态。
- [原型] **工作卡六字段**：执行模块 / 预计耗时或工作量 / 负责人 / 收益标签 / 验证目标节点 / `[开展]`
  （原型「每条任务卡的字段」一行逐项列出，五条实例均齐备）。
  [设计] 六字段**必填**，任一字段缺失则卡片不可派发（必填性属实现约束）。
- [原型] **收益标签的五个取值**：
  `关掉 N 节点` / `补 N 证据` / `定优先级` / `推进 1 层` / `补决策依据`
  （原型「收益标签（关掉N节点·补N证据·定优先级·推进1层·补决策依据）」一行逐项列出）。
  [设计] 该枚举**封闭**、服务端校验；`关掉 N 节点` 与 `补 N 证据` 的 N 必须是可计算的整数，
  不得是文案里的形容词。
- [Backlog] **`[开展]` 是真实派发链路，不是标记**：点开展即派给对应模块或小组，
  **并在待办看板生成卡片**（Backlog UC-9.3 `flow` 原文）。
  [原型] 项目内待办看板的卡片确实带【决策树】来源徽标（「查三国资质转移条文，判定收购分支存亡」），
  可佐证这条链路。[设计] 「两处与本工作卡三向可追溯」。
- [Backlog] **同一目标节点已有在跑的同类工作时不重复派发**（Backlog `edge` 原文；原型无据）。
- [Backlog] **派发失败必须回滚卡片**（Backlog `edge` 原文）；
  [设计] 模块工作实例与看板卡片同生同灭，不留孤儿卡。
- [设计] **D-39 责任归属**：待办卡的 **`负责人` 恒为人**；agent 记在独立的 **`执行者`** 字段。
  与「AI 只拿行动权、不承担验收」一致——Scout / Ledger 可以执行，但验收责任落在人身上。
- [设计] **D-27 卡片初始态**：AI 生成的卡一律落 `inbox` 草稿态；R1 风险可自动接受，
  R2/R3 必须由人接受后才进 `todo`（风险分级按 D-28 由操作类型自动推导）。
- [设计] 工作卡的排序依据必须可展开说明，不做黑箱推荐。
- AI/Agent 生成的候选工作必须标识为机器产出，展示生成依据（指向哪个节点、缺什么证据）；
  依据不足时不得伪造工作卡。
- 所有权限判断必须在服务端执行；隐藏入口只是界面表现，不构成安全控制。
- 任何派发、回滚、撤销、指派动作都必须记录审计事件，并显示动作影响范围。

## R8 界面线索

- **前端入口**：[原型] `项目 → [进入项目] → 现场协作 → 全场视图 → 知识图谱 → 决策树`
  页面下方的「**下一步可以开展的工作**」分区。
- **信息架构**：[原型] 决策树页自上而下：树主体 →【待决的岔口 · N】→【图谱推演 · 如果现在拍板】→
  **【下一步可以开展的工作】（本用例）**。分区页头一句话：
  「每条都指向树上的一个待决节点 · 点『开展』即派给对应模块或小组」。
- **推荐交互**：
  - [原型] 工作卡三行式：`标题（带模块前缀 DR/IT/VT/UX/LG）` + `【收益标签】` /

## R9 非功能约束

- **性能/规模预期**：
  - [设计] 工作卡列表随决策树变化重算，重算延迟 ≤ 3 秒；卡片数量在单场现场规模下 ≤ 20 条，
    超出时按收益排序截断并提供「查看全部」。
  - [设计] `[开展]` 的跨模块派发（模块实例 + 看板卡片）应在 3 秒内给出成功/失败结论；
    超过 10 秒转为后台任务并在完成后通知，期间卡片显示「派发中」不可重复点击。
  - [设计] `关掉 N 节点`、`补 N 证据` 的 N 由服务端计算下发，前端不做二次统计。
- **安全/隐私/合规**：
  - 最小权限、组织/项目/小组隔离、传输与静态加密、敏感字段脱敏、导出与 AI 读取留痕。
  - 原始材料、录音、转写、私聊、个人身份与客户数据按授权和留存策略处理。
- **兼容与降级要求**：
  - 响应式 Web；桌面端提供完整能力，移动端保证加入、查看、输入、投票/确认等现场关键动作。
  - WebSocket/实时通道不可用时降级为轮询并显示“非实时”；断网允许保留未提交输入，但不得伪装已同步。

- **内部依赖**：**UC-9.2**（待决/待验证节点的唯一来源，工作卡必须挂到它的节点上）；
  **UC-9.1**（证据计数支撑「补 N 证据」）。
- **被依赖 / 派发目标模块**：**11-board 待办看板**（每次 `[开展]` 生成一张卡）、

  - **责任契约（D-39）**：`负责人` 字段只接受**人**的标识；agent 写入 `执行者` 字段。

- **[待确认]** 「同类工作」的判定口径——同一目标节点 + 同一执行模块算同类，还是要更细（同一负责人）？

## R12 AI Ready 验收线索

以下行为应可由自动化测试、接口断言或可复现人工步骤验证：

- V1（枚举断言）：AC2 —— 收益标签字段的可取值集合**恰为**
  `{关掉N节点, 补N证据, 定优先级, 推进1层, 补决策依据}`（5 类）；提交枚举外的值返回校验失败。
  以原型数据构造后断言五类**各出现一次**。
- V2（必填断言）：遍历工作卡列表，断言每条的六个字段
  `execution_module` / `effort` / `owner` / `benefit_label` / `target_node_ref` / 可派发标记
  **均非空**；任一为空时 `[开展]` 接口返回拒绝。
- V3（目标节点强制绑定）：AC —— 调用创建工作卡接口且 `target_node_ref` 为空 → 断言返回校验失败、
  库中无记录；`target_node_ref` 指向一个 `已否决` 节点 → 同样拒绝
  （只能指向 `待决`/`待验证`）。遍历列表断言**不存在** `target_node_ref` 为空的卡。
- V4（派发链路 · 成功）：AC1 —— 对「DR 查三国资质转移条文」点 `[开展]` →
  断言 ① 研究模块内新增一条工作实例；② 11-board 看板新增一张卡；
  ③ 看板卡的 `source_ref` 指回该工作卡、`target_node_ref` 指向「资质可随股权转移？」；
  ④ 从看板卡与从研究模块**都能跳回**本工作卡。
- V5（D-39 责任断言）：对「派给 Scout」的工作卡派发后，断言看板卡的
  `owner` 是**人**的标识、`executor` = `Scout`；把 agent 标识写入 `owner` 字段的请求返回**拒绝**。
- V6（D-27 草稿态）：AI 生成的工作卡派发后，断言看板卡初始 status = `inbox`；
  风险为 R2/R3 时断言未经人接受**不会**自动进 `todo`；R1 时可自动接受。
- V7（重复派发拦截）：AC3 —— 对同一目标节点 + 同一执行模块连续点两次 `[开展]` →
  断言看板卡片总数只 +1，第二次返回「已有一条在跑」并携带那条的引用。
- V8（失败回滚）：AC4 —— 令目标模块返回不可用后点 `[开展]` →
  断言看板卡片数**未变**、模块工作实例数**未变**、工作卡仍为未开展态、错误信息可解释且可重试。
- V9（半成功补偿）：令看板写入失败但模块实例已创建 → 断言系统检测到不一致并回滚模块实例，
  最终两边计数一致，无孤儿记录。
- V10（收益 N 可计算）：对 `关掉 N 节点` 的卡断言 N 为整数且等于该目标节点关闭后
  在决策树上会连带关闭的待验证节点数（原型：资质条文 → 4）；对 `补 N 证据` 同理（原型：EPC 追访 → 2）。
- V11（目标关闭后清理）：把「资质可随股权转移？」判为已解决 → 断言指向它的工作卡
  从列表移除或标为「目标已关闭」，且不再可派发。
- V12（权限态）：逐一以 引导师 / 组长（本组、他组）/ 组员 / 项目负责人 / 观察者 / 未授权用户 调接口；
  断言只有引导师可派发任意卡、组长仅可派发本组相关卡、观察者返回中不含负责人姓名与工作量估算。
- V13（空态）：决策树无待决/待验证节点时，断言接口返回空数组、页面显示真实空态，
  返回体中**不含**任何示例工作卡。
- V14（并发态）：两个会话同时对同一卡点 `[开展]` → 断言只产生一张看板卡，另一方收到明确提示。
- V15（审计态）：派发、回滚、指派负责人、忽略工作卡四类动作可按操作者、时间、对象、结果检索；
  越权派发尝试留安全审计记录。
