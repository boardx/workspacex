## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-10.3 / 缺料提示与补齐
- **Actor**：**引导师**、**项目经理**、**客户**
- **目标**：[原型] 报告生成后，系统自己把「还差什么」说清楚并**指到具体节号**，
  原型原话——**「还缺两块：第 2 组的供应商侧访谈（影响第 03 节）与保底条款成本测算
  （影响第 04 节）。补齐后可升到 v4 并对客户发布。」**——然后把每块缺料变成项目内看板上
  一张有主的卡，补齐后报告才允许升版与对外发布。
- **本用例结果**：报告右栏底部出现一条可执行的缺料清单（每条指向节号），项目内看板对应生成
  带 **`[报告缺料]` 徽标**的卡；卡片状态变化**回写**缺料清单；缺料清零后升版与对客户发布解锁。
- **系统边界**：缺料检测与清单、缺料 → 节号的影响面映射、缺料 → 看板卡的双向同步、
  **「缺料 → 升版 → 对外发布」三段门禁链**。
- **核心数据对象**：缺料项（missing_item：描述 / 影响节号 / 负责人 / 执行者 / 截止 / 状态）、
  报告版本、看板卡（含来源徽标）、门禁判定结果、审计事件。

## R2 前置条件 / 触发条件

- **前置条件**：
  - 用户已建立可校验的正式或临时身份，且拥有目标组织、项目、小组或资源的访问权。
  - 目标资源存在且未被删除/冻结；依赖能力“知识图谱、访谈、实时转录、成果沉淀”可用，或界面能明确显示其不可用状态。
  - 若动作涉及个人数据、录音、原始材料或跨范围读取，相应授权与留存策略已生效。
- **触发条件**：
  - [原型] **每次生成或重写后系统自检**（UC-10.2 第 5 步之后），在报告工作台右栏底部输出缺料提示。
  - [原型] 用户点某条缺料的「变成待办」，或直接在项目内看板上改动一张 `[报告缺料]` 卡的状态。
  - [设计] 用户尝试**升版**（v3 → v4）或**对客户发布**时，门禁链主动复核缺料状态。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

1. **系统处理（生成后自检）**：扫描本版报告，找出**证据不足以支撑的内容块**——典型来源是
   UC-10.2 中节状态为 `待补` 的节、以及标灰段落所需但项目里尚不存在的证据。
   把每一处归纳成一条**缺料项**，并**必须算出它影响哪一节**。
2. **系统响应（右栏底部渲染）**：[原型] 输出一条自然语言缺料提示，格式为
   「还缺 N 块：<缺料 1>（**影响第 XX 节**）与 <缺料 2>（**影响第 XX 节**）。
   补齐后可升到 v(N+1) 并对客户发布。」原型实例逐字为：

   > **「还缺两块：第 2 组的供应商侧访谈（影响第 03 节）与保底条款成本测算（影响第 04 节）。
   > 补齐后可升到 v4 并对客户发布。」**

   这条提示同时说清了三件事：**缺什么 · 影响哪节 · 补齐后解锁什么**——三者缺一不可。
3. **用户操作**：把缺料派出去（可一次全派，也可逐条派）。**系统响应**：
   [原型] 在**项目内看板**（项目 → 待办，四列：待办 / 进行中 / 待复核 / 已完成）生成卡片，
   卡片带 **`[报告缺料]` 来源徽标**。原型实例（「待复核」列）：

   > `[报告缺料] 明天　保底条款成本测算 · 待财务确认折现率　LG · Ledger · 测算`

   卡片必须携带：来源徽标 `[报告缺料]`、截止时间、缺料描述、**负责人（恒为人）**、
   **执行者（可为 agent，如 Ledger）**、所属范围；并**反向链接回本报告的具体节号**。
4. **用户操作**：在看板上推进这张卡（拖动改列 / 标记完成）。**系统响应**：[原型] 底注原话
   「卡片来源自动同步：会前任务、现场行动项、报告缺料、决策的后续动作。**状态改了会回写到原处**。」
   ——看板卡状态变化**回写到报告缺料清单**，右栏底部的「还缺 N 块」实时递减；
   反过来，在报告侧关闭一条缺料也同步更新看板卡。**这是双向的，不是单向派发。**
5. **用户操作**：缺料补齐后点升版（v3 → v4）。**系统响应**：门禁复核——
   仍有未完成缺料时**拒绝升版**并列出阻塞的缺料与其节号；全部完成时允许升版，
   新版本重新生成受影响节（第 03 / 04 节）并重算节状态。
6. **用户操作**：对客户发布（UC-10.4）。**系统响应**：门禁再次复核——
   **未补齐缺料时不得对客户发布**，即使用户手工改过正文；提示指向具体缺料项。
7. **系统收口**：校验 AC1「缺料清单与待办看板双向同步」——两侧条目一一对应、状态一致；
   刷新 UC-10.1 清单行的「待补 N 块」，并记录缺料生成、派发、状态回写、门禁拒绝
   四类事件进项目级审计。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[原型] **缺料不阻塞草稿，只阻塞升版与对外发布**——带缺料的报告可以继续编辑、继续生成、
    继续在内部查看；被卡住的只有「升到下一版本号」与「对客户发布」两个出口。
  - A2：[设计] **人工新增缺料**——引导师认为系统没识别出来的缺口，可手工加一条缺料项并指定节号，
    同样纳入门禁链。
  - A3：[设计] **人工豁免某条缺料**——有发布授权的人可显式豁免（如「该访谈已确认无法约到」），
    豁免必须填理由、留痕，并在报告正文对应节保留「该口径证据不足」的说明，
    **不得让豁免看起来像补齐**。
  - A4：[设计] 缺料被补齐但对应节尚未重新生成时，缺料标记为「已补齐 · 待重写」，
    升版门禁仍提示需重写受影响节。
- **异常流程**：
  - E1：[设计] **缺料项与节号失配**——受影响的节在后续重写中被删除或合并时，
    缺料项自动改挂到承接内容的新节；无法确定时标为「影响面待确认」并提示人工指认，
    **不得默默丢弃该缺料**。
  - E2：[设计] **看板卡被删除**——`[报告缺料]` 卡在看板侧被删除时，报告侧缺料项**不随之消失**，
    改为「已失去看板卡」状态并可重新派发；门禁仍视其为未补齐。
  - E3：[设计] **同步冲突**——报告侧与看板侧同时改同一条缺料状态时，以时间戳较晚者为准，
    并在两侧都留下一条同步记录，不静默覆盖。
  - E4：[设计] 请求超时、网络中断或依赖（看板服务）不可用时，保留用户当前输入与最后成功数据，
    明确失败原因，并提供安全重试；**看板不可用时缺料清单仍必须可见，门禁仍必须生效**
    ——不得因为同步失败就放行发布。
  - E5：[设计] 权限在操作过程中被撤回时立即终止后续写操作；已完成步骤按审计规则保留，
    未提交输入留在本地草稿并提示重新授权。

## R7 业务规则（不随具体实现变化的硬性约束）

- [原型] **「缺料 → 升版 → 对外发布」是同一条门禁链，三段耦合，不得分别放行。**
  这是本用例最核心的硬约束，展开为：
  1. 报告存在**未补齐的缺料项**时，**不能升到下一个版本号**（v3 无法变成 v4）。
  2. 报告存在**未补齐的缺料项**时，**不能对客户发布**（内部查看不受限）。
  3. 缺料全部补齐（或经授权豁免并留痕）后，升版与对外发布**同时**解锁。
  实现上必须是**同一个服务端门禁判定**被两个出口共用，**禁止**在升版接口与发布接口里
  各写一份独立校验——那会导致其中一个被绕过。
- [原型] **缺料不阻塞草稿**：带缺料的报告可继续编辑、生成、内部查看与内部分享。
- [原型] **每条缺料必须指向具体受影响的节号**（原型：「影响第 03 节」「影响第 04 节」）。
  没有节号的缺料项不合法，不得入库——否则用户无法判断补齐它有什么用。
- [原型] **缺料提示必须写明补齐后解锁什么**（原型：「补齐后可升到 v4 并对客户发布」），
  让门禁对用户是可预期的，而不是到发布时才被拒绝。
- [原型] **与项目内看板双向同步**：缺料自动建卡且卡上带 **`[报告缺料]` 来源徽标**；
  卡片状态变化**回写到报告缺料清单**（原型底注「状态改了会回写到原处」）。
  单向派发不满足本约束。
- [D-39] 看板卡的**负责人恒为人**；agent（如 Ledger）记在独立的**执行者**字段。
- [设计] **豁免必须留痕**：任何绕过缺料的放行都必须有操作者、理由、时间，
  并在报告正文对应节保留证据不足的说明。
- 所有权限判断必须在服务端执行；隐藏入口只是界面表现，不构成安全控制。
- 任何覆盖、删除、撤销、签署、发布、写回或停用动作都必须记录审计事件，并显示动作影响范围。

## R9 非功能约束

- **性能/规模预期**：
  - [设计] 缺料自检应在生成结束后 3 秒内给出清单；超过 10 秒转为后台任务，
    期间升版与发布按 fail-closed 保持关闭。
  - [设计] 缺料 ↔ 看板卡的双向同步延迟应 ≤ 5 秒；超时必须在两侧显示「同步中」，
    不得让任一侧显示过期状态却看起来是最新的。
- **安全/隐私/合规**：
  - 最小权限、组织/项目/小组隔离、传输与静态加密、敏感字段脱敏、导出与 AI 读取留痕。
  - 原始材料、录音、转写、私聊、个人身份与客户数据按授权和留存策略处理。
- **兼容与降级要求**：
  - 响应式 Web；桌面端提供完整能力，移动端保证加入、查看、输入、投票/确认等现场关键动作。
  - WebSocket/实时通道不可用时降级为轮询并显示“非实时”；断网允许保留未提交输入，但不得伪装已同步。

## R10 已知约束 / 依赖

  在 backlog 中明确为范围外。
- **[已裁决 O-32]** 缺料的**自动识别口径**——原问题：系统凭什么判定「缺一块」而不是「这节写得短」；
  是纯规则（节状态为 `待补` / 标灰段落数超阈值）还是含模型判断，阈值由谁定。
  **裁决（O-32 ①）**：**缺料 ＝ 报告骨架中标为「必需」的节没有挂任何来源。**
  一律采**结构化规则、不用统计比较、不含模型判断、不设长度阈值**：
  - 判定的唯一输入是「该节的 `source_refs` 是否为空」与「该节在报告骨架定义表里
    `required` 是否为真」，两者同时成立即判缺料；
  - **不看字数、不看段落长短、不与其他节横向比较**——「这节写得短」永远不构成缺料；
  - 「必需节」清单来自**报告骨架的配置项定义表**（与 O-07 / O-18 / O-32 ④ 的
    配置项定义表同源），清单变化不改代码；
  - **不引入模型判断**：模型判断没有可复现基线，写不出 verification，且误判会制造假缺料。
  理由与 D-11 对「六成」的处理同构：显示给人看的判断，用可复现的结构化规则比统计阈值更可验收。
- **[待确认]** 豁免权限归属：是否只有「有发布授权的人」（对齐 UC-10.4）可以豁免。
- **[待确认]** 缺料逾期后的升级路径（是否通知项目负责人、是否影响项目健康度）。
- **[已裁决 O-33]** 通知平面**单点定义在 `.harness/instructions/` 的通知规范**，各 UC 只引用不重复定义。默认：产品内通知**必选**；邮件**默认开启可关**；短信仅用于现场进场验证码；免打扰**默认关闭**（B 端工具，静默会误事）；到期提醒 **09:00 用户时区**；催办冷却 **4 小时**；组员**可以**催同组同伴；**「今天」一律按用户时区**

- **[设计] 架构对齐 · Context Engine**（`docs/architecture/context-engine.md`，2026-07-28 定稿）：
  - **AI 取上下文只能通过 Context API 领取 Context Pack**——任何 agent、副驾驶或生成动作
    都不得绕过服务平面直查 `claims` / `segments` / `artifact_versions` 等库表。
    绕过即丢失 `permissionDecisionId` 与引用锚点，`uc-14-6`「AI 读到了什么」将不可重放。
  - **编排边界**：**LangGraph 只用于深度研究、人工确认（HITL）与多阶段生成**；
    文件摄取、批量导入、定时与重试一律走**持久任务系统**（MVP 为 PG outbox + job table）。
    LangGraph 不得被当作通用任务队列；HITL 用动态 `interrupt()`，节点恢复时副作用必须幂等。
  - **权限**：**租户与项目隔离在 PostgreSQL RLS 层强制**，应用连接使用受 RLS 约束的
    **非 owner** 角色（PG 中表 owner 默认不受 RLS 限制）。本文 R5 的权限判定与 R12 的
    越权断言是**第二道**防线，不是唯一防线。Artifact 权限必须传播到 Segment、embedding、
    图边、缓存与 Context Pack；交集生成内容取所有来源权限的**最严格**结果。

## R11 切分提示（给 requirement-author）

- 建议拆「缺料项模型（含必填节号） → 生成后自检与清单渲染 → **统一门禁判定服务** →
  升版出口接入门禁 → 对外发布出口接入门禁 → 看板建卡 → 看板状态回写 → 豁免与留痕 →
  审计 → 自动化验收」。
- **「统一门禁判定服务」必须先于两个出口落地并单独成 feature**：升版与对外发布共用同一个判定，
  两处各写一份校验是本用例最可能出的实现缺陷。
- **「看板状态回写」不能与「建卡」合并成一个 feature**，否则容易只做单向派发就报完成。
- **优先级 / 先后依赖**：P0；**5 点**；阶段二 · 迭代 8 · 报告与问卷；
  依赖 UC-10.2（节状态）与 11-board（项目内看板）先可用。
- 对 P0 必做链路优先实现成功态、权限态与数据闭环，异常态不得延期到上线后。

## R12 AI Ready 验收线索

以下行为应可由自动化测试、接口断言或可复现人工步骤验证：

- V1（成功态 · AC2 节号必填）：缺料清单接口对每条缺料返回 `affected_section` 且非空；
  构造一条 `affected_section` 为空的缺料项写入，接口返回拒绝。
- V2（成功态 · 提示文案三要素）：缺料提示接口返回的文本同时含
  ① 缺料条数与描述 ② 每条的「影响第 XX 节」③ 「补齐后可升到 v(N+1) 并对客户发布」的解锁说明；
  三者缺一判失败。
- V3（硬约束 · 门禁链第 1 段）：存在 `status != resolved` 的缺料项时，
  调用**升版接口**返回拒绝，错误体列出阻塞缺料的 ID 与节号。
- V4（硬约束 · 门禁链第 2 段）：同一状态下调用**对客户发布接口**同样返回拒绝，
  错误体与 V3 指向同一批缺料项。
- V5（硬约束 · 门禁链同源）：把全部缺料置为 `resolved` 后，**升版与对客户发布两个接口同时成功**；
  代码层断言两个出口调用的是**同一个门禁判定函数/服务**（可用调用链埋点或契约测试验证），
  不存在两份独立校验。
- V6（硬约束 · 不阻塞草稿）：存在未补齐缺料时，编辑正文、重新生成、内部查看三个接口均返回成功
  ——门禁只作用于升版与对外发布两个出口。
- V7（双向同步 · 报告 → 看板）：新建一条缺料并派发后，项目内看板出现一张卡，断言该卡
  `source_badge == "报告缺料"`、`affected_section` 与缺料一致、`owner` 为人类用户、
  `executor` 可为 agent（如 Ledger）、且携带回指报告 ID + 节号的反链。
- V8（双向同步 · 看板 → 报告 · AC1）：把该卡从「待办」拖到「待复核」再到「已完成」，
  每次变更后读取报告缺料清单，断言缺料项状态同步变化，右栏「还缺 N 块」计数相应递减；
  **反向**：在报告侧关闭该缺料，看板卡状态同步更新。
- V9（异常 E2）：删除该看板卡，断言报告侧缺料项**仍存在**且状态为「已失去看板卡」，
  升版接口仍拒绝。
- V10（异常 E4 · fail-closed）：模拟看板服务不可用，断言缺料清单仍可读、升版与发布仍被拒绝，
  **不出现因同步失败而放行**的情况。
- V11（豁免留痕 A3）：以有发布授权的账号豁免一条缺料（填理由），断言
  ① 门禁放行 ② 审计中存在含操作者/理由/时间的豁免事件 ③ 报告对应节保留证据不足说明；
  无发布授权的账号执行豁免返回 403。
- V12（一致性）：缺料条数、UC-10.1 清单行的 `missing_block_count`、看板中该报告的
  `[报告缺料]` 卡数量三者相等。
- V13（权限态）：逐一使用 引导师、项目经理、组长、组员、观察者、客户、未授权用户访问；
  客户与观察者不可见缺料清单，组员只可见派给自己的缺料卡。
- V14（空态）：无缺料时缺料区显示「无缺料，可升版并发布」而非隐藏，且不生成伪缺料。
- V15（并发态 E3）：报告侧与看板侧同时改同一条缺料状态，最终状态以时间戳较晚者为准，
  两侧各留一条同步记录，无静默覆盖。
- V16（审计态）：缺料生成、派发、状态回写、门禁拒绝、豁免五类事件可按操作者、时间、
  报告 ID、缺料 ID 检索；越权尝试也有安全审计记录。
- V17（**缺料判定口径** · O-32）：构造三种节 →
  ① 必需节 + 零来源 → 断言判为**缺料**；
  ② 必需节 + 有来源但正文只有一句话 → 断言**不判缺料**（长度永不构成缺料）；
  ③ 非必需节 + 零来源 → 断言**不判缺料**。
  另断言「必需」标记读自**报告骨架配置项定义表**，改动该表即改变判定结果而无需改代码；
  断言判定链路中**不含任何模型调用**（纯结构化规则，可复现）。
