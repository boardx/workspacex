# 给合规 / 法务的问询清单

> 2026-07-29。这份文件列的是**产品与工程无权自行决定、必须由合规或法务给出**的输入。
>
> 为什么单独成文而不是塞进待决清单：前面 40+ 条裁决都是**产品可以拍板**的（A/B 权衡、
> 范围取舍、口径统一）。下面这几条不是——它们的答案取决于**法律要求与对外承诺**，
> 我们编一个「看起来合理」的值，风险不是「做错功能」，而是**对受访者作出做不到的承诺**。
>
> ⚠ 本项目已发生过一次相关失误：我曾把一个 SLA 判成「实现者编造的」并据此让人类改了决定，
> 后来才发现 `DECISIONS-FINAL.md` 的 D-15 早已裁定过那个数。**所以下面每一条都注明了
> 「我们查过哪些地方、确认它确实没有」**——请先核对这一点，如果某条其实已有出处，
> 直接指出来比重新裁决更省事。

# 🔴 Q-1 法定留存清单（最硬的一条，它在阻塞开工）

## 问题
**哪些数据类别属于法定留存，即使收到数据主体的删除/撤回请求也不得删除？**
请按类别给出，并注明依据的法规与留存年限。

## 为什么必须有
系统里有三条约束正面冲突，**这份清单是唯一的判据**：

| 约束 | 出处 | 内容 |
|---|---|---|
| 快照不可删 | `artifact` 契约 I-11 | 固定快照不可删、不可改、不可降级 |
| 撤回必须删 | D-15 | 逻辑失效 ≤5 分钟；物理删除 ≤30 天并出回执 |
| 不可删对象豁免留存期 | O-01 | 「不可删对象不受留存期约束，单独走法定留存清单」 |

O-01 把判据指向了「法定留存清单」，**而那份清单不存在**。

⇒ 在它给出之前，「收到撤回请求时，哪些快照必须删、哪些不得删」**没有判据**，
撤回删除相关的 feature 无法定稿（涉及 `22-files/uc-22-4`、`17-gov/uc-17-2`）。

## 我们查过
`DECISIONS-FINAL.md`（41 条）、`DECISIONS-OPEN.md`（40 条）、`DECISIONS-UI-ROUND.md`（12 条）
全文搜索，O-39 是唯一提及处，且它自己写着「⚪ 需合规/法务外部输入」。**确认没有。**

## 不给会怎样
撤回链的第 05 步（物理删除）无法实现——它必须先判断「这条能不能删」。
当前实现把这个判断标为 `legalHoldCategories: { known: false }`，
**取值时抛错而不是放行**（放行等于默认全都能删，那是更危险的默认）。

# 🟠 Q-2 留存期五参数的默认值与允许区间

## 问题
D-14 定了留存期是**五个独立可配置参数**，各有默认值且项目级可覆盖。请给出：

| # | 参数 | 我们需要的 | 当前状态 |
|---|---|---|---|
| ① | **材料保留期** | 默认值 + 允许区间 | 界面上曾写死 180 天，**已改为「按项目配置」的显式占位** |
| ② | **留痕保留期** | 默认值 + 允许区间 | 未定 |
| ③ | **删除宽限期** | 默认值 + 允许区间 | 界面写 30 天（O-01），需确认是否为合规值 |
| ④ | **知识有效期** | 默认值 + 允许区间 | 界面写「监管类 12 个月 / 市场数据 6 个月」，**来自原型，未经合规确认** |
| ⑤ | **审计保留期** | 默认值 + 允许区间 | UC-17.1 只写「不可删」，与留存期如何共存见 Q-1 |

## 为什么必须有：这是**对外承诺**不是内部配置
① 会**印在受访者同意书上**。D-14 明写「同意书文案必须按项目动态渲染」——
也就是说同一份同意书在不同项目下显示不同的天数。

⚠ 这条之前是**写死的**（所有项目都显示 180 天）。
只要有一个项目配了不同的保留期，同意书就会向受访者作出**与实际不符的承诺**。
已改为显式占位并加了机械门控（`pending-thresholds.test.ts` 会拦住任何重新写死的尝试）。

## 我们查过
D-14 原文即写「⚠ 各项默认值与允许区间**仍需合规负责人给出**」。**确认没有。**

# 🟡 Q-3 撤回 SLA 是否需要写进同意书

## 问题
D-15 已裁定撤回的两级 SLA（**逻辑失效 ≤5 分钟；物理删除 ≤30 天并出回执**）。
我们想确认两件事：

1. **这两个数是否要印在同意书上**（对受访者的明示承诺），还是只作为内部 SLA？
2. 若要印——**某些司法辖区是否强制要求**给出明确时限？

## 背景（这条有过一次反复，说明白免得重复）
实现期曾有人把 02/03 两步的时限判成「编造值」并改成「立即启动，进度可查」。
后来核实发现 **D-15 早已裁定过**，那两步都属「逻辑失效」，由 D-15 直接覆盖。已恢复。

⇒ 现在同意书上印的是 D-15 的数值。**我们要确认的是「该不该印」，不是「数值是多少」。**

## 我们查过
D-15 定了数值，但没说是否对外披露。**这是个未被回答的问题，不是缺失的裁决。**

# 附：这些值在代码里怎么存放的

全部登记在 `packages/contracts/src/thresholds.ts`，形态是：

```ts
legalHoldCategories: {
  known: false,                    // ← 类型上就拿不到值
  rule: "属法定留存的对象不得删除，即使收到合规撤回请求…",
  owner: "法务",
  blocksWhat: "🔴 真实阻塞：X-4 的冲突以此为判据…",
  ref: "design-coherence N-1 / X-4 / O-39",
}
```

三条机械保证（`packages/contracts/tests/pending-thresholds.test.ts`）：
1. **取未定的值会抛错，不会返回默认值** —— 静默默认是这类缺陷的温床
2. **业务代码里不得硬编码这些数值** —— 有人填了「看起来合理」的数字会被门控拦下
3. 抛出的错误里带得上「谁该给」与「不给会卡住什么」 —— 只说「未定」，读到的人不知道该找谁

## 数值到位后怎么填

把该项改成：

```ts
{ known: true, value: …, source: "2026-08-xx 合规 XXX 给出，依据《…》第 x 条", rule: "…" }
```

⚠ `source` 是必填的，测试会检查——**没有出处的数值等于没有依据**，
半年后没人记得那个数是谁定的、依据什么。
