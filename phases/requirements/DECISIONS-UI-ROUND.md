# 第一组 · 🔴 定不了就会把错的东西实现进后端

## 🔴 D-U1 批准卡：机密数据能否与云端模型并存

原型同时印着「gpt-5.2 ＋ **本地** qwen3-32b」和「含机密，**仅本地模型**」，字面矛盾。
**这条直接决定后端 gateway 的拦截规则**，不是文案问题。

| | 方案 | 优点 | 缺点 |
|---|---|---|---|
| **A** | **分流**：机密数据只路由到本地模型，**云端模型可并存**承接非机密部分 | 与原型那行字面一致；一轮里既能用强模型又守住机密；性价比高 | 需要在**片段级**判定哪些内容机密——判错一次就是泄漏；「这段算不算机密」的边界要有人定义并可审计 |
| **B** | **全程本地**：只要本轮上下文**含任何**机密条目，整轮所有模型调用都走本地 | 判定简单、边界清晰、不可能误分流；审计容易 | 一份材料里有一句机密，整轮都降级到本地小模型，效果明显下降；用户可能因此不标机密 |

**我的推荐：B**。理由：A 的安全性取决于「片段级机密判定」的准确率，而那是个**没有人能保证 100% 的分类问题**；一次误判的代价是不可逆的泄漏。B 的代价是性能，可以靠「把机密材料单独开一轮」来规避，且这个规避动作是用户可见可控的。
若选 A，必须同时回答：机密的**最小判定单位**是什么（Artifact / Segment / 句子）？谁来标？错标怎么追责？

**选择：B** — **全程本地**：本轮上下文含任何机密条目 ⇒ 整轮所有模型调用走本地。

**⇒ 执行**：改 `modelPolicyViolation()` 的语义：不再是「有机密且无本地模型才违规」，而是「有机密 ⇒ 云端模型在本轮不可用」。批准卡与 composer-settings 共用这一个纯函数，勾选机密材料时云端模型 chip 直接置灰并注明原因。**后端 gateway 按同一规则拦截。**

## ⚖️🔴 D-U2 受访者撤回五步的两个 SLA

D-13 撤回链只给了 01「即时」、04「需人工」、05「30 天内」。实现按 D-15 两级 SLA
**推断补了 02「≤5 分钟」、03「即时」**——这是编出来的数值。

| | 方案 | 优点 | 缺点 |
|---|---|---|---|
| **A** | **确认这两个推断值**（02 引述退出检索 ≤5 分钟；03 报告段落标失效 即时） | 立刻可开工；数值在技术上可达成 | 若与真实合规承诺不符，同意书上写的是对外承诺，改起来涉及已签署的文件 |
| **B** | **同意书上不写具体时限**，只承诺「收到撤回后立即启动，各环节完成时间见处理进度页」 | 不把自己锁死在一个数字上；进度页可以显示真实状态 | 受访者信任度略低；某些司法辖区可能要求给出明确时限 |

**我的推荐：先问合规，不要我们定。** 如果必须现在推进，选 **B** 更安全——
承诺一个做不到的时限比不承诺时限风险更大。**这条建议由合规负责人拍板，不是产品决定。**

**选择：B** — 同意书**不写具体时限**，只承诺「收到撤回后立即启动，各环节完成时间见处理进度页」。

**⇒ 执行**：改 `consent-form` 的撤回五步：删掉推断补的 02「≤5 分钟」/ 03「即时」两个 SLA，改为「立即启动 + 进度可查」。⚠ **本项仍需合规复核**——产品这边按 B 推进只是不把自己锁死在编出来的数字上，不代表合规不需要给出真实时限。

## 🔴 D-U3 角色本体是否需要「场景角色」这一层

O-03 裁定项目角色**恒为四种**（引导师/组长/组员/观察者）。但两处出现了枚举外的角色：
- 文件浏览器需要**合规负责人**视角
- 访谈/问卷需要**研究员 / 受访者 / 参与者**

实现临时用 `?as=compliance` 与另一根 `?view=` 预览轴绕过，**这动摇了 O-03**。

| | 方案 | 优点 | 缺点 |
|---|---|---|---|
| **A** | **加第三层「场景角色」**：组织角色 × 项目角色 × 场景角色（研究员/受访者/参与者/合规…） | 每个场景都能准确表达；不用把不相干的角色塞进四角色 | 鉴权从两层交集变三层交集，复杂度上升；UC-0.3 的 R5 表要重写；权限矩阵测试用例数翻倍 |
| **B** | **不加层**：合规负责人归**组织角色**（第四种组织角色）；受访者走**一次性令牌身份**（已有机制）；研究员/参与者是**引导师/组员在访谈场景下的别名**，不落库 | 保住 O-03「项目角色恒为四种」；鉴权仍是两层交集；改动最小 | 「别名」这个说法需要在界面文案上处理干净，否则用户会以为是不同角色 |

**我的推荐：B**。理由：受访者已经有一次性令牌机制（UC-6.3），不需要项目角色；
「研究员」实质就是引导师在访谈场景里的称呼；只有**合规负责人**是真的新东西，
而它是**组织级职能**（对整个组织的合规负责），本来就该在组织角色层。
加第三层会让权限矩阵从 4×3 变成 4×3×N，测试成本不成比例。

**选择：B** — **不加第三层**：合规负责人归**组织角色**；受访者走已有的一次性令牌身份；研究员/参与者是引导师/组员在访谈场景下的**展示别名**，不落库。

**⇒ 执行**：`identity.ts` 组织角色增加第四种 `compliance`；文件浏览器的 `?as=compliance` 改为组织角色维度；访谈/问卷的 `?view=` 保留为**场景别名预览**并在界面注明「别名，落库仍是项目角色」。**O-03「项目角色恒为四种」得以保住。**

## 🔴 D-U4 丢弃清单的原因分类（会成为 Context Pack 的枚举）

UC-0.2 只说「丢弃清单带原因」。实现发明了 7 类：
`已撤回 / 时效过期 / 低置信 / 无授权 / 预算截断 / 去重 / 越出范围`。
**这套词汇会成为 `omissions[].reason` 的枚举**，之后很难改。

| | 方案 | 优点 | 缺点 |
|---|---|---|---|
| **A** | **采纳这 7 类**，作为封闭枚举 | 立刻可开工；7 类覆盖了目前能想到的全部情形；封闭枚举便于统计与筛选 | 将来出现第 8 类要改 schema 与历史数据 |
| **B** | **改成开放结构**：`{ category: 枚举, detail: string }`，枚举先给这 7 类但允许扩展 | 不会被将来的情形卡住 | 容易退化成人人自定义 detail，统计与筛选失效 |

**我的推荐：A + 一条纪律**——采纳 7 类作为封闭枚举，
**新增类别必须走 ADR**（像 harness 自己那样），不允许临时加。
理由：丢弃原因是**给人看的可审查性**，不是日志。开放结构必然长出几十种说法，
到时「AI 为什么没读这条」就又变成不可回答的问题了。

**选择：A** — 采纳 7 类作为**封闭枚举**：`已撤回 / 时效过期 / 低置信 / 无授权 / 预算截断 / 去重 / 越出范围`；**新增类别必须走 ADR**，不允许临时加。

**⇒ 执行**：把这 7 类定义成 `lib/omission-reason.ts` 的 const 枚举（单一事实源），research 屏与brain 的「AI 读到了什么」共用；写进 UC-0.2 作为 `omissions[].reason` 的契约。

## 🔴 D-U5 管理员停用某能力时，正在用它的会话怎么办

（UC-0.5 R4 A3，是上一轮四问里唯一没答的）

| | 方案 | 优点 | 缺点 |
|---|---|---|---|
| **A** | **立即中断**：停用即刻生效，进行中的调用失败并提示「该能力已被管理员停用」 | 安全边界立刻收紧——停用往往是因为出了安全问题；语义无歧义 | 用户正在跑的活会丢；批量任务跑到一半中断，成本白花 |
| **B** | **允许跑完当前一轮**：已发起的调用跑完，新调用被拒 | 不丢用户的活；对误操作友好 | 「一轮」的边界要定义（一次 API 调用？一个 agent 任务？一条对话线程？）；出安全问题时仍有一个窗口期在继续访问 |

**我的推荐：A，但给管理员一个「立即中断 / 允许跑完」的二选一**，默认立即中断。
理由：停用能力的动机分两类——**安全事件**（必须立即断）与**版本下线**（可以跑完）。
只支持一种必然有一种场景很难受；把选择权给按下停用的那个人，并在确认弹窗里说清影响范围
（当前有 N 个进行中的调用会被中断）。

**选择：A+** — **默认立即中断**，但给按下停用的管理员一个「立即中断 / 允许跑完当前一轮」二选一，确认弹窗说清影响范围（当前有 N 个进行中的调用会被中断）。

**⇒ 执行**：写进 UC-0.5 R4 A3；后台各能力页的停用动作加二选一确认。理由：停用动机分**安全事件**（必须立即断）与**版本下线**（可跑完），只支持一种必然有一种很难受。

## 🟠 D-U6 「在场数」是否包含跑批中的 agent

原型同时有「团队 **4**」与「AI 团队 · **6**」。实现定义 `在场 = presence === "present"`（4 个），
**跑批中（Ledger）与空闲（Echo）不计入在场**。

| | 方案 | 优点 | 缺点 |
|---|---|---|---|
| **A** | **在场 = 能立刻响应的**（当前实现，4 个）；跑批中/空闲另计 | 「在场」这个词符合直觉——它回答「现在问一句谁会答」 | 跑批中的 agent 其实在替你干活却不算在场，用户可能困惑 |
| **B** | **在场 = 编入本线程的**（6 个）；用另一个词表达「可立刻响应」 | 与「AI 团队 · 6」一致，只有一个数字 | 丢失了「谁能马上答」这个信息，而那是对话屏最有用的一条 |

**我的推荐：A**，但把标签从「团队 4」改成「**在场 4 / 编制 6**」——
两个数字同时显示，就不需要用户猜哪个是哪个。UC-4.2 R6 本来就要求「两个口径分别标注」。

**选择：A+** — **在场 = 能立刻响应的**；标签改为「**在场 4 / 编制 6**」两个数同时显示。

**⇒ 执行**：改对话屏线程头与左栏计数。UC-4.2 R6 本来就要求两个口径分别标注，这次落实。

## 🟠 D-U7 人时折算的三个数值

任务屏的人时折算涉及三个 UC 明写「需产品给出」的数：
① 每项折算系数（几人时/项）② 最小样本量阈值 ③ token→金额单价与口径表版本号。
实现**拒绝编造**，界面显式标注「产品待定」（中途曾编过 `sampleSize=18`，已删）。

| | 方案 | 优点 | 缺点 |
|---|---|---|---|
| **A** | **现在给三个数**，界面显示真实折算值 | 任务屏的价值主张（「AI 替我省了多少」）立刻成立 | 拍脑袋定的系数会被当成真数据引用到对外汇报里，比不显示更危险 |
| **B** | **保持「产品待定」占位**，只显示原型演示值 + 「样本不足」闸门的形态 | 诚实；闸门形态可以先验收；等有真实数据再填 | 任务屏底部那段折算暂时没有说服力 |

**我的推荐：B**，且把它挂成一个**明确的待办**（谁来给这三个数、什么时候给）。
理由：折算系数是**对外可引用的数字**，一旦显示就会被截图进汇报。
在没有真实运行数据之前给一个数，比空着危险得多。

**选择：B** — **保持「产品待定」占位**，只显示原型演示值 + 「样本不足」闸门形态。

**⇒ 执行**：代码已经是这样（`minSampleKnown/coefficientKnown/ledgerVersionKnown: false`），无需改动。⇒ **挂成明确待办**：谁来给这三个数、什么时候给。

## 📦 D-U9 画布的写工具做到什么程度

实现把 `＋便签`/`＋节点`/`删除`/缩放都做成了**真的乐观交互**（点了真落一个、删了真消失），
超出了「静态壳」的最小实现。画布上仍有「非 mermaid 渲染」的角标。

| | 方案 | 优点 | 缺点 |

| **A** | **保留乐观交互** | sign-off 时能真正感受到画布的操作手感；发现交互问题更早 | 容易被误读成「布局引擎已经有了」，尽管有角标 |

误读的风险用角标 + README 的明确说明控制即可。

**选择：A** — **保留乐观交互**（点了真落便签、删了真消失），保留「非 mermaid 渲染」角标。

**⇒ 执行**：代码已经是这样，无需改动。误读风险由角标 + README 说明控制。

## 📦 D-U11 摄取复核的权威入口是哪个

复核处置出现在两处：**摄取抽屉**里的接受/拒绝，与**独立的人工复核屏**。
现在两处各自独立，点其一另一处不联动。

| | 方案 | 优点 | 缺点 |
|---|---|---|---|
| **A** | **独立复核屏是权威**，抽屉里只显示状态 + 「去复核」链接 | 复核是有批量属性的工作，独立屏更合适；单一入口不会分叉 | 从摄取抽屉里处理一条要跳一次 |
| **B** | **抽屉是权威**，独立复核屏只是同一动作的批量视图，两处共享状态 | 就地处理更顺手 | 两处要共享状态，实现复杂一点 |

**我的推荐：B**。理由：复核的触发点通常是「我刚传了一份东西，它卡在复核」——
就地能处理最自然。批量视图是同一动作的另一个入口，不是另一个动作。

**选择：B** — **摄取抽屉是权威入口**，独立复核屏是同一动作的批量视图，两处共享状态。

**⇒ 执行**：files 模块把两处的处置动作接到同一份状态上。

## 📦 D-U12 后台里编造的部分怎么处理
