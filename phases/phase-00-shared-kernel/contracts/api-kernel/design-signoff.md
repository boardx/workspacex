# 契约束 `api-kernel` 设计签核

覆盖 feature：**F18**（13 点，后端内核）
依据 UC：`uc-0-6 后端内核与运行时门控`

## 这个束为什么现在才出现

phase-00 原本四束（identity / artifact / context-pack / web-kernel）已于 2026-07-28 全部签核。
本束是 **2026-07-29 起第一个 sprint 时补出来的**，动因是一次核实：

> F01「两层角色落到 `acl_bindings`」估 **5 点**。但 `apps/api` 不存在、零 NestJS、
> 零迁移、零 PG 连接。F01 实际要交付的是「NestJS 骨架 + 洋葱四层 + 迁移体系 +
> RLS 策略 + `acl_bindings` 表 + 两层交集判定」——**估点失真三倍**，
> 且 F02~F13 十二个后端 feature 的共同前置会被埋进 F01 里，
> **下一个 feature 的人不知道它已经有了**。

这与 UC-0.4（前端内核）从 F01~F13 里拆出来的理由完全相同。**前端有内核，后端没有。**

## 签核前请确认

- [ ] **A-4：不引入 ORM，同意吗**（coverage 第四节第 1 条）——
      这条决定 F01~F13 全部持久化代码的写法，且很难回头。
      理由：ORM 把 RLS 需要的 `SET LOCAL` 会话语义藏进连接池行为，
      让「这条查询在哪个租户上下文里跑」变得不可读，而本束的全部价值正是让它可读可断言。
- [ ] **A-5：X-3（出网为零）的分工成立吗** —— 本束认领**落点**
      （`docker-compose.dev.yml` 与部署清单的网络策略位并署名），
      deny-all 的**断言**留给 F16。阶段一致性复核警告过它会「掉进前后端与运维的缝里」；
      若不认可这个分工，请指定另一个归属。
- [ ] **V5 的形状对吗** —— 「绕过应用层过滤后跨租户读 0 行」**且**
      「换成自己的租户能读得到自己的行」。⚠ 只写前半句的话，
      一个「一律拒绝」的坏策略也会全绿——**隔离与瘫痪必须能被区分**。
- [ ] **I-4 / I-5（应用角色非 owner、表 FORCE RLS）的分量对吗** ——
      PG 中表 owner 默认不受 RLS 约束。用 owner 身份连库 = RLS 写了但没生效，
      且**表面上一切正常**。这是「以为开了 RLS 其实没开」的头号成因。
- [ ] **A-1 / A-2：两处现存的门控空洞认可吗** ——
      ① `lint-arch-deps` 至今**从未扫过一个文件**（对空目录打印「跳过」并 exit 0），
      ADR-020 却称它「强制、与七道门控同级」；
      ② `lint-contract-source` **只覆盖前端侧**，后端抄一份 DTO 不会有任何东西报警。
- [ ] **A-7：本束在为尚不存在的东西立契约** —— 与另外四束（把既成事实固定成契约）
      性质相反，coverage 表「状态」列全是 ⬜。**签核对象是契约定得对不对，
      不是实现做完没有。**
- [ ] **A-3：凭证形态（JWT / session / mTLS）刻意不在本束决定** ——
      Guard 只断言「principal 非空」这条结构约束，凭证来源先用测试注入，
      真实认证属 phase-01 `01-auth`。请确认这个切法可接受。
