# 契约束 `auth` — ④ UC 覆盖证明

> 覆盖 feature：**F19 F20 F21 F22**（12 点）
> 验收线索来源：`uc-1-5` 与 `uc-1-1` 的 R12
>
> ⚠ 状态列全是 ⬜ —— 本束是**为尚不存在的东西立契约**（同 `api-kernel` 当初）。
> 签核对象是「契约定得对不对」，不是「实现做完没有」。

## 一、`uc-1-5` 用邀请码创建组织并注册（F19 / F22）

| R12 | 一句话 | API 操作 | 前端消费点 | 状态 |
|---|---|---|---|---|
| **V1** | 14 位邀请码可创建组织并注册 | `RedeemInviteAndCreateOrg` | `/signup?code=` | ⬜ |
| **V2** | **一码一组织**：同一码第二次核销失败 | 同上（条件 UPDATE，`rowCount===1`） | 同上 | ⬜ |
| **V3** | **并发核销恰好一个成功，且不留半个组织** | 同上（事务边界是契约的一部分） | — | ⬜ |
| **V4** | 邮箱验证未完成不能登录 | `Login` err `EMAIL_NOT_VERIFIED` | `/signin` | ⬜ |
| **V5** | 一账号可归属多组织 | `SwitchOrgAtLogin` → `identity.switchOrganization` | 顶部组织切换器 | ⬜ |
| **V6** | 组织停用后只读降级，仅管理员可导出 | ⚠ **契约缺口**，见第二节 A-2 | — | ⬜ |

## 二、`uc-1-1` 邮箱账号登录（F20 / F21）

| R12 | 一句话 | API 操作 | 前端消费点 | 状态 |

## 三、缺口清单

| # | 缺口 | 性质 | 补法 |
|---|---|---|---|
| **A-1** | **凭据形态未定** —— UC-0.6 A-3 刻意留到本束 | 需人类裁决 | domain 第三节①给了三个方案与推荐（不透明 token + Redis）。⚠ JWT 与 I-5「立即失效」**正面冲突** |
| **A-2** | **V6「组织停用只读降级」没有对应操作**。`identity` 束里没有停用组织的用例，本束也没有 | 契约缺口 | 需新增一个操作，或明确 V6 归 phase-03 治理。⚠ 不定的话 F22 会带着一条无法判定的验收 |
| **A-3** | **会话存储仍是进程内** | 已知且必须换 | `InMemorySessionStore` 不跨副本不跨重启。deploy compose 里 redis 已持久化就是为它准备的；不换的话**第一次重启就是「所有人被登出」** |
| **A-4** | **`Mailer` 是出网**（邮箱验证、密码重置） | X-3 交叉约束 | 本地组织路径**不得使用**。⚠ 那意味着本地组织里「忘记密码」走不通——需要裁决：本地组织是否允许密码登录，还是走别的凭据 |
| **A-5** | **F03（设备与会话列表）未迁入** | 刻意取舍 | 它带 `needs_ui_signoff`。于是 I-7「吊销是写标记不是删行」在本束**只有后端断言，没有界面**——用户看不到自己有哪些设备 |

## 四、反向检查：有没有多余的操作

| 操作 | 被哪条要求 | 结论 |
|---|---|---|
| `RedeemInviteAndCreateOrg` | V1 V2 V3 | ✅ |
| `Login` | V4 V7 V8 V9 | ✅ |

**无孤儿操作。**

## 五、签核时请重点看这四处

1. **凭据形态（A-1）** —— 三个方案见 domain 第三节。JWT 做不到 I-5，这是硬冲突不是偏好。
2. **A-2：V6 有验收无操作** —— 要么补操作，要么明确它归 phase-03。留着就是一条判不了的验收。
3. **A-4：本地组织的密码重置走不通** —— 发信是出网，而本地组织承诺零出网。
   这不是实现细节，是产品要回答的问题。
4. **I-1 的耗时半边** —— 「响应体一样」不够，两条路径的耗时差一个数量级时，秒表就是枚举器。
   ⇒ 未找到用户时也要跑等价开销的假哈希。这条容易在 code review 里被当成「多余的浪费」删掉。
