# 契约束 `auth` — ① 领域模型与不变量

> 洋葱最内层。**不依赖任何外层**。
> 覆盖 feature：**F19 F20 F21 F22**（12 点）
> 依据：`uc-1-5 用邀请码创建组织并注册`、`uc-1-1 邮箱账号登录`
> 关联：UC-0.6 A-3（凭据形态刻意留到这里定）· `identity` 束（本束产出 principal，identity 消费它）

---

## 零、这个束与 `identity` 的分界

**`auth` 回答「你是谁」，`identity` 回答「你能做什么」。**

F18 的 Guard 只断言一条结构约束——**handler 拿到的 principal 非空**——
并明确把凭据形态留给本束（UC-0.6 A-3）。所以：

| | 归谁 |
|---|---|
| 凭据校验、会话签发与吊销、邀请码核销 | **`auth`（本束）** |
| principal → 两层角色 → 判定 | `identity` |
| 强制 | PG RLS |

⚠ **本束不得自己做权限判定。** 一旦它开始判「这个人能不能看 X」，
就有了第二个判定源，而 X-1 的全部工作就是保证只有一个。

## 一、实体与值对象

### `Credential`（实体）

| 字段 | 说明 |
|---|---|
| `userId` | |
| `email` | **唯一**，小写规范化后比较 |
| `passwordHash` | ⚠ **算法与参数是契约的一部分**，见不变量 I-2 |
| `emailVerifiedAt` | null = 未验证 |

### `Session`（实体）

| 字段 | 说明 |
|---|---|
| `id` | 不可猜（同 A-1：UUID，不得是序列） |
| `userId` / `currentOrgId` | |
| `issuedAt` / `expiresAt` | 有效期 30 天（UC-1.3） |
| `revokedAt` | null = 有效。**吊销是写标记不是删行**——删了就查不出「谁在什么时候被踢的」 |

### `InviteCode`（实体）—— F19 最容易做错的地方

| 字段 | 说明 |
|---|---|
| `code` | **14 位**（UC-1.5） |
| `redeemedByUserId` / `redeemedAt` | null = 未核销 |
| `createdOrgId` | 核销后指向它建出来的那个组织 |

⚠ **一码一组织、事务性核销**（I-4）。两个人同时用同一个码，
必须**恰好一个成功**——而做错时的表现是**两个组织都建出来了**，
且两边都「登录正常」，没有任何东西会报。

### `LoginAttempt`（值对象）—— 限速与锁定的依据

`{ email, at, outcome: "ok" | "bad-credential" }`。
⚠ **按 email 计数而不是按 IP**：按 IP 会让共用出口的整间办公室互相锁死，
而攻击者换 IP 是免费的。

## 二、不变量

| # | 不变量 | 断言方式 |
|---|---|---|
| **I-1** | 登录失败的响应**不区分**「邮箱不存在」与「密码错误」——响应体、状态码、**以及耗时**都不得可分辨 | 两种失败逐字段比对；耗时差落在阈值内（防时序侧信道） |
| **I-2** | 口令只以**慢哈希**存储（argon2id 或 bcrypt cost ≥ 12），**任何地方不得出现明文或可逆编码** | 断言 `passwordHash` 形态；扫描代码与日志不得出现口令字段 |
| **I-3** | 连续失败达阈值即**锁定**，锁定期内即使口令正确也拒绝 | 双向：锁定后正确口令仍拒；解锁后可登录 |
| **I-4** | 一个邀请码**至多**核销一次；并发核销恰好一个成功，失败方**不留下半个组织** | 并发两路核销，断言组织数为 1、码状态为已核销 |
| **I-5** | 重置口令成功后，该账号**全部既有会话**立即失效（UC-1.1 R4） | 双向：旧会话下次请求即 401；新会话可用 |
| **I-6** | `Session.id` 不可猜（UUID，非序列） | 同 A-1 的断言形态 |
| **I-7** | 吊销是**写标记不是删行** | 断言吊销后行仍在且 `revokedAt` 非空 |
| **I-8** | 未验证邮箱的账号**不能登录**（UC-1.5） | 双向 |
| **I-9** | 本束**不产生任何权限判定**——principal 之外不返回角色 | 断言 `auth` 的响应体里没有 role/scope 字段 |

### 为什么 I-1 要连耗时一起断言

「邮箱不存在」走一条不做哈希校验的短路径，「密码错误」要跑一次慢哈希——
**两者耗时差一个数量级**。响应体一模一样也没用：攻击者拿秒表就能枚举。
⇒ 未找到用户时**也要跑一次等价开销的假哈希**。

## 三、需要人类裁决的两处（签核时定）

### ① 凭据形态

| 方案 | 优点 | 缺点 / 风险 |
|---|---|---|
| **不透明会话 token + Redis**（推荐） | 吊销是即时的（I-5 直接可做）；token 不含信息，泄漏面小 | 每次请求要查一次 Redis；Redis 挂了全站登出 |
| JWT | 无状态、可水平扩展 | **吊销要么做黑名单（等于回到有状态），要么等过期**——与 I-5「立即失效」正面冲突 |
| session cookie + PG | 少一个组件 | 每请求一次 PG 往返，且会与业务查询争连接 |

**推荐不透明 token + Redis**：I-5 是 UC 明写的硬要求，而 JWT 做不到「立即」。

### ② 会话存储换不换

现在是 `InMemorySessionStore`——**不跨副本、不跨重启**。
`docker-compose.deploy.yml` 里 redis 已经持久化，就是为它准备的。
⇒ 推荐本束一并换掉；不换的话第一次重启就是「所有人被登出」。

## 四、这个域不负责什么

- **权限判定** —— 属 `identity`（见第零节）
- **邀请链接 / 免注册进场 / 四视角裁剪** —— 留在 phase-01，且带 UI 签核
- **设备与会话列表界面** —— 原 phase-01 F03，带 UI 签核，未迁入
