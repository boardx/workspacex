# 原始需求（细化）— UC-0.5 组织配置平面与个人本地组织

> 所属：阶段零 · 共享内核 / M0 跨工具协议
> 来源：**人类新需求（2026-07-28）**「这个默认的列表只是我提出的例子，这个列表可以根据当前的
> 组织来调整，我们需要有一个组织的控制界面，每个组织可以根据自己的需要来做配置和调整，
> 然后所有的成员都跟住组织的配置。一个组员也可以不使用任何组织，使用本地来工作，
> 每个人有自己的默认的本地的一个组织，一个特殊的组织，可以使用本地模型来处理所有的最隐私的数据。」
> **补写缘由**：原型把六个 agent（Ava/Atlas/Scout/Ledger/Warden/Echo）画得像**产品内置**，
> 后台也把 18 台模型、6 台 MCP 画成既定清单。人类明确这些**只是示例**——
> 它们是**某个组织的配置**，不是产品常量。这一条不落地，会导致：
> ① agent/skill/模型/MCP 全被硬编码成产品常量，第二个客户进来就要改代码；
> ② 「每个人有一个本地组织」这条隐私底线**无处存放**——它既不是项目层也不是现有的组织层。
> 前者是架构错误，后者是产品承诺无法兑现。

> 口径（四标记）：**[原型]** ＝ `WorkspaceX Standalone.html` **运行态实际存在**的行为（有界面可查）；**[Backlog]** ＝ `Backlog Use Case.html` 的**文档要求**（原型未必实现）；**[设计]** ＝ 依据前两者反推补全，**需人类确认**；**[待确认]** ＝ 不应由实现者自行决定。
> 元数据：优先级 **P0**；估点 **13**；建议迭代 **阶段零 · 共享内核**。
> **本件不计入 699 点原始需求基线**（它是 2026-07-28 新增需求）。计入后 phase-00 为 81 点。

## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-0.5 / 组织配置平面与个人本地组织
- **Actor**：**组织管理员**、**组织成员**（顾问 / 项目负责人）、**独立工作者**（不属于任何组织的人）
- **目标**：[设计] 把「有哪些 agent、哪些 skill、哪些模型、哪些 MCP、哪些画布模板、哪些项目蓝本」
  从**产品常量**改为**组织配置**；并为每个人提供一个**默认的个人本地组织**，
  让最隐私的数据可以完全不出本地。
- **本用例结果**：
  ① 任何能力清单都挂在某个组织上，成员**跟随所属组织的配置**，不各自维护；
  ② 每个用户在注册时自动获得一个 `personal-local` 组织，**该组织内的一切处理只走本地模型**；
  ③ 顶部组织切换器在「若干个正式组织」与「我的本地」之间切换，切换即换掉整套配置。
- **系统边界**：组织类型、配置项归属、配置继承与覆盖规则、个人本地组织的隔离保证、切换语义。
- **核心数据对象**：组织、组织类型、能力配置项（agent / skill / model / mcp / canvas-template / blueprint）、
  配置版本、本地运行时端点。

## R2 前置条件 / 触发条件

- **前置条件**：用户已有账号（UC-1.1）。**个人本地组织在注册那一刻自动创建**，不需要任何前置。
- **触发条件**：
  - 管理员在后台调整本组织的能力清单；
  - 成员进入任一工作面（系统需按当前组织解析可用能力）；
  - 用户切换组织（含切到「我的本地」）。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

1. **系统处理**：注册成功时，**自动为该用户创建一个 `personal-local` 组织**。
   [设计] 它是一个**真实的组织记录**，不是特例分支——这样 `acl_bindings`、RLS 策略、
   Artifact 模型、Context Pack 全部机制**原样复用**，不需要为「本地模式」写第二套代码路径。
   命名默认「<用户名> 的本地」，成员恒为一人，**不可邀请、不可转让**。
2. **管理员操作**：在后台「组织配置」里维护本组织的六类能力清单：
   [原型] **agent**（原型示例 6 个）、**skill**、**模型**（原型示例 18 台）、
   **MCP**（原型示例 6 台）、**画布模板**、**项目蓝本**。
   ⚠ **这六类在原型里的具体条目都是示例，不是产品常量**（本用例的直接缘由）。
3. **系统处理**：成员进入任一工作面时，系统按**当前组织**解析可用能力清单。
   [设计] 成员**跟随组织配置，不能自行增删**（对照 R7 的覆盖规则）。
4. **系统处理**：解析能力时叠加 UC-0.3 的**可见性范围**——
   [原型] 组织内的能力还可标「全组织可用 / 仅某团队」，两层是**串联**关系：
   先看「本组织有没有这个能力」，再看「我在不在它的可见范围里」。
5. **用户操作**：通过顶部组织切换器切换组织（含「我的本地」）。
   [已裁决 O-12] 切换时**清空全部项目级上下文**并按新组织重新求值权限。
   [设计] **本用例追加**：切换时**整套能力配置一并换掉**——
   上一个组织的 agent、skill、模型、MCP 一个都不带过去。
6. **系统收口**：在 `personal-local` 组织内，**强制所有模型调用走本地/自托管端点**，
   且**禁止任何 MCP 出网调用**（见 R7 的硬约束）。违反时**拒绝并明确报错**，不静默降级。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[设计] **不属于任何正式组织的用户**——只有个人本地组织，照样能建项目、跑 Studio、
    用本地模型。这是「一个组员也可以不使用任何组织，使用本地来工作」的落点。
  - A2：[设计] 用户同时属于多个正式组织 + 一个本地组织（`user` ↔ `organization` 一对多，O-12）。
    本地组织**恒定存在且不可退出**。
  - A3：[设计] 管理员**停用**某个能力（如下线一台模型）时，正在使用它的会话
    [待确认] 是立即中断还是允许跑完当前一轮。
  - A4：[设计] 组织配置支持**从模板初始化**（新建组织时给一套推荐清单），
    但那只是初始值，**不是不可改的默认**。
- **异常流程**：
  - E1：[设计] 在个人本地组织内请求云端模型 → **拒绝**，提示「本地组织不出网」，
    并给出「若要用云端模型，请切换到某个正式组织」的出口。**不得静默改用云端**。
  - E2：[设计] 本地模型运行时不可用（未安装 / 未启动）→ 显示**依赖失败态**，
    给出如何启动本地运行时的指引。**不得回退到云端**——那会破坏隐私承诺。
  - E3：[设计] 组织被停用/删除时，其成员的**个人本地组织不受影响**（它不属于任何正式组织）。
  - E4：[设计] 配置引用了已不存在的能力（如 skill 被删）→ 该能力在清单里标为**失效**并停止解析，
    不静默跳过。

## R5 权限与可见性

| 谁 | 在正式组织 | 在个人本地组织 |
|---|---|---|
| **组织管理员** | 维护六类能力清单、可见性范围、配额 | —— |
| **项目负责人 / 顾问** | **只读**能力清单，跟随配置 | —— |
| **本人** | —— | 自己就是唯一成员，**自己配置**（无人可管他） |
| **他人（含平台/组织管理员）** | —— | **一律不可见、不可访问**，见 R7 |

- [设计] 个人本地组织**不出现在任何组织的成员列表、配额统计、审计报表里**。
- [设计] 它**不受组织管理员的审计目的访问**（UC-0.3 R5 A1 的管理员留痕访问权**不适用**于此）——
  那条权限的前提是「管理员对本组织的项目负责」，而本地组织不属于任何组织。

## R6 后置条件 / 不包含

- **正常后置条件**：
  - [设计验收] AC1：删掉产品代码里所有硬编码的 agent/skill/模型/MCP 清单后，
    系统仍能正常运行——清单**全部**来自组织配置。
  - [设计验收] AC2：两个不同组织的同一个用户，看到的能力清单不同，且互不泄漏。
  - [设计验收] AC3：在个人本地组织内发起任何 AI 调用，**出网流量为零**；
    请求云端模型被拒绝且给出可理解的原因。
  - [设计验收] AC4：新注册用户**立即**拥有一个可用的个人本地组织，无需任何配置动作。
- **失败后置条件**：本地运行时不可用时进入依赖失败态；**任何情况下都不得回退到云端**。
- **不包含**：
  - 本地模型的**安装与分发**（那是部署形态问题，见 `.harness/instructions/architecture.md` 的单机私有形态）。
  - 组织之间的配置共享 / 配置市场（phase-3 的能力市场另议）。
  - 成员对组织配置的**个人覆盖**（本用例明确：成员跟随，不覆盖。见 R7）。

## R7 业务规则（不随具体实现变化的硬性约束）

- [设计] **能力清单是组织配置，不是产品常量。** 六类：agent / skill / model / mcp /
  canvas-template / blueprint。产品代码里**不得存在硬编码的默认清单**（AC1 是它的可执行断言）。
- [设计] **成员跟随组织配置，不做个人覆盖。**
  理由：能力清单直接决定「AI 能读什么数据、能调什么工具」，个人覆盖等于绕过组织的安全边界。
  个性化只允许发生在**不涉及数据边界**的维度（如界面偏好），那不属于本用例。
- [设计] **组织类型是一等字段**：`organization`（正式组织）| `personal-local`（个人本地组织）。
  **两者共用同一张表与同一套 ACL / RLS 机制**——本地组织不是特例分支。
  这一条是为了避免出现「本地模式」的第二套代码路径，那种分支必然长期失修。
- ⚠ [设计] **个人本地组织的三条硬隔离**（这是产品承诺，不是配置项）：
  ① **模型调用只允许本地 / 自托管端点**，云端模型在此组织内**不可选**；
  ② **禁止任何 MCP 出网调用**；
  ③ **数据不出本地部署**——不进共享对象存储、不进跨组织索引。
  违反时**拒绝并显式报错**，**不得静默降级到云端**（与 `knowledge-ontology.md` 对 AGE 的立场一致：
  「不许假装没事」）。
- [设计] **个人本地组织对任何他人不可见**，包括平台运营与组织管理员。
  它比 UC-0.3 R7 的「个人层对管理员封闭」更强：那条是「看不到内容」，这条是「数据根本不离开本地」。
- [设计] **切换组织 = 换掉整套配置**。上一个组织的能力一个都不带过去
  （在 O-12「清空项目级上下文」之上追加「清空组织级能力解析」）。
- [设计] **能力清单变更必须留痕**（谁在什么时候增删了哪个能力），进 `provenance_events`。
- [设计] **可见性范围与组织配置是串联的两层**：先「本组织有没有」，再「我在不在可见范围里」。
  两层都通过才可用。
- [设计] **`personal-local` 组织恒定存在且不可删除、不可退出、不可转让、不可邀请他人**。

## R8 界面线索

- **前端入口**：
  - [原型] 后台的七个模块（总览 / Agent / Skill / 模型 / MCP / 成员配额 / 反馈）
    **就是组织配置平面本身**——需要把它从「产品设置」的读感改成「**本组织的配置**」的读感：
    页头显式标出「以下配置只对『远洋咨询』生效，成员跟随本配置」。
  - [设计] 顶部组织切换器（O-12）需把**个人本地组织**作为一个视觉上可区分的条目
    （建议加锁形图标 + 「本地」字样），并说明「本地组织内只用本地模型，数据不出本机」。
- **推荐交互**：
  - [设计] 切到本地组织时，**整个应用要有可感知的状态变化**（如顶栏换一种底色 + 常驻说明条），
    让人始终知道「我现在在本地模式」。隐私模式若不可见，等于不存在。
  - [设计] 后台模型页在本地组织下：**云端模型整行禁用**并注明原因，不是隐藏——
    隐藏会让人以为「没有这个能力」，禁用+原因才说明「有能力但本组织不允许」。
  - [设计] 空态要引导：新组织的能力清单为空时，提示「从推荐模板初始化」而不是一片空白。
- **必须呈现的状态**：默认态、加载态、空态、校验失败态、依赖失败态、无权限态、成功态。
  ⚠ **依赖失败态在本用例格外重要**：本地运行时没起来时必须明确说清，不能转圈也不能偷偷用云端。
- **原型参考**：`phases/requirements/WorkspaceX Standalone.html` — 后台七模块
- **UI sign-off**：**原型确认缺失**——原型的后台是「产品设置」读感，
  **组织归属说明、个人本地组织、本地模式的全局可感知状态**三者都不存在。需补画后确认。

## R9 非功能约束

- **性能/规模预期**：[设计] 能力清单解析应可缓存；配置变更后缓存失效需在 1 分钟内生效
  （与 UC-0.3 R9 的角色变更同一口径）。
- **安全/隐私/合规**：
  - 个人本地组织的三条硬隔离（R7）必须有**自动化断言**，不接受人工核对配置。
  - 组织之间的配置**互不可见**；跨组织读取配置视为越权。
- **兼容与降级要求**：**本地运行时不可用时一律失败，不得降级到云端。**
  这与「鉴权服务不可用时一律拒绝」（UC-0.3 R9）是同一条纪律。

## R10 已知约束 / 依赖

- **内部依赖**：UC-0.3（组织与角色本体、`acl_bindings`、RLS）、UC-1.1 / UC-1.5（注册时创建本地组织）、
  裁决 O-12（一账号多组织 + 顶部切换器）。
- **被依赖**：
  - `04-agent` 全模块（agent 清单来自组织配置，不是产品内置）
  - `03-skill`、`20-model`、`21-mcp`（同上）
  - `02-tpl` 项目蓝本、画布模板
  - `/admin` 全部七个模块的读感与归属说明
- **[待确认]** 管理员停用某能力时，**正在使用它的会话**是立即中断还是允许跑完当前一轮（R4 A3）。
- **[待确认]** 个人本地组织内是否允许**建项目并邀请他人**。
  按 R7「不可邀请他人」推断是**否**，但那样「本地」就只能单人用——
  是否需要一种「本地多人（同一局域网/同一部署）」的中间形态，需人类裁决。
- **[待确认]** 正式组织是否可以**整体配置成「只用自托管模型」**（即把本地组织的约束①
  作为正式组织的一个可选策略）。这对有强合规要求的客户很可能是刚需。
- **[待确认]** 个人本地组织的数据是否可以**导出并导入到某个正式组织**（「把我本地的成果贡献上去」）。
  若可以，需要一条明确的、有意识的出网动作，不能是自动同步。

## R11 切分提示（给 requirement-author）

- 建议拆两个 feature：
  - **F-a 组织配置平面**（8 点）：组织类型字段、六类能力清单挂到组织、成员跟随解析、
    切换即换配置、配置变更留痕。验收面是 AC1（删掉硬编码清单后系统仍能跑）与 AC2。
  - **F-b 个人本地组织**（5 点）：注册时自动创建、三条硬隔离、本地模式的全局可感知状态、
    本地运行时不可用时的依赖失败态。验收面是 AC3（出网流量为零）与 AC4。
- **F-b 依赖 F-a**：本地组织是组织类型的一个取值，必须先有类型字段。
- **优先级 / 先后依赖**：P0；两者合计 13 点；阶段零共享内核；
  **必须先于 `03-skill` / `04-agent` / `20-model` / `21-mcp` 四个模块的实现**——
  否则它们会先把清单硬编码进去，之后再拆一次。

## R12 AI Ready 验收线索

- V1（AC1 · 无硬编码清单）：[设计] 静态断言产品代码中**不存在**内置的 agent/skill/model/mcp 清单
  （如扫描源码中是否有固定数组）；并断言把某组织的清单清空后，
  该组织成员看到的可用能力为零、界面进入空态而不是显示默认值。
- V2（AC2 · 组织隔离）：[设计] 同一用户在 A / B 两个组织下请求能力清单，
  断言两次返回不同且互不包含对方的条目；以 A 组织身份请求 B 组织的配置被拒。
- V3（AC3 · 本地组织出网为零）：[设计] 在 `personal-local` 组织内发起一轮完整的 AI 调用，
  **在网络层断言出网请求数为 0**；并断言请求云端模型时接口返回明确拒绝（非静默改用本地）。
  ⚠ 这一条必须在**网络层**断言，不能只查应用日志——应用层可能自认为没出网。
- V4（AC4 · 注册即有本地组织）：[设计] 新建用户后立即查询其组织列表，
  断言恰好包含一个 `kind = personal-local` 的组织且立即可用。
- V5（本地不可用不降级）：[设计] 停掉本地模型运行时，断言请求**失败并返回依赖失败**，
  且**没有任何**云端调用发生。这是 R9 的核心断言。
- V6（切换换配置）：[设计] 从 A 组织切到本地组织，断言：
  ① 能力清单完全替换（无 A 组织残留）；② 项目级上下文清空（对照 O-12）；
  ③ 云端模型在新上下文中不可选。
- V7（本地组织不可见）：[设计] 以组织管理员身份查询成员列表、配额统计、审计报表，
  断言**任何位置都不出现**他人的个人本地组织及其内容。
