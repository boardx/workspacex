# 原始需求（细化）— UC-0.6 后端内核与运行时门控

> 所属：阶段零 · 共享内核 / M0 跨工具协议
> 来源：**无原始需求，亦无 Backlog 条目**——本用例是从 **`architecture.md`「三个必须建立的
> 机械门控（运行时）」、ADR-020（洋葱分层 + `lint-arch-deps` 强制）、UC-0.3 R7（RLS 强制隔离）
> 三项已有裁决反推出的执行前提**，与 UC-0.4 是对称的一件（前端内核 ↔ 后端内核）。
>
> **补写缘由（2026-07-29，机器核实）**：phase-00 的 F01 是「两层角色落到 `acl_bindings`」，
> 5 点。核实发现它的**前提完全不存在**：
> ① `apps/` 下**只有 `web`**，`apps/api` 不存在，全仓零 NestJS、零迁移文件、零 PG 连接；
> ② `lint-arch-deps.mjs` 已写好但**每次运行都打印「跳过 apps/api/src：尚未创建」并 exit 0**
>    ——ADR-020 声称「与既有七道门控同级的强制门控」，实际处于**永久空转**状态；
> ③ `architecture.md` 点名的**三个运行时门控**（Guard 全局注册 / ValidationPipe + zod /
>    ExceptionFilter 只回 `internal_error`）**一个都不存在**；
> ④ `packages/contracts` 的 zod 目前只有**前端**一个消费者，
>    ADR-020 的「后端 DTO ← 同一份 zod」这条链**未接通**。
>
> 若不补此件，F01 实际要交付的是「NestJS 骨架 + 洋葱四层 + 迁移体系 + RLS 策略 +
> `acl_bindings` 表 + 两层交集判定」——**5 点的估点会失真三倍**，而且 F02~F13 十二个
> 后端 feature 的共同前置会被埋进 F01 的实现里，**下一个 feature 的人不知道它已经有了**。
> 这与 UC-0.4 从 F01~F13 里拆出来的理由完全相同。

> 口径（四标记）：**[原型]** ＝ `WorkspaceX Standalone.html` **运行态实际存在**的行为；**[Backlog]** ＝ `Backlog Use Case.html` 的**文档要求**；**[设计]** ＝ 依据前两者反推补全，**需人类确认**；**[待确认]** ＝ 不应由实现者自行决定。
> 元数据：优先级 **P0**；估点 **13**；建议迭代 **阶段零 · 共享内核**。
> **本件不计入 699 点原始需求基线**（见 `phases/requirements/ESTIMATE-BASELINE.md`）——
> 它是流程前提而非产品范围。与 UC-0.4 一并计入后全项目为 725 点。

## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-0.6 / 后端内核与运行时门控
- **Actor**：**后端开发 agent**、**人类工程师（sign-off 执行者）**
- **目标**：[设计] 把 `architecture.md` 与 ADR-020 里**已裁决但只写没做**的后端约束
  ——洋葱依赖方向、RLS 强制隔离、三个运行时门控、契约单源直达后端 DTO——
  变成一套**可运行、可机器验证**的后端内核，使 F01~F13 十三个后端 feature 具备开工条件。
- **本用例结果**：`apps/api` 可启动；迁移可从零重建库且幂等；
  **RLS 的「强制」二字有反证**（去掉应用层过滤后跨租户读仍为 0 行）；
  三个运行时门控各有**双向断言**（合规输入放行 / 违规输入被拦）；
  `lint-arch-deps` 从「跳过」变为**真正在扫描**。
- **系统边界**：后端应用骨架、洋葱四层目录与依赖门控、显式 SQL 迁移体系、
  RLS 基线与非 owner 应用角色、鉴权/校验/错误边界三道运行时门控、
  契约 zod → 后端 DTO 的接线、本地依赖编排（PG + MinIO + Redis）。
- **核心数据对象**：**无业务数据对象**——本件不建任何业务表。
  它只建**迁移体系本身**与一张用于证明 RLS 生效的**探针表**（见 R7）。

- **前置条件**：`./init.sh` 的基础验证通过；本机可运行容器（PG 16 + pgvector）。
- **触发条件**：phase-00 任何**后端** feature（F01~F13）开工之前。
- **阻塞关系（本件存在的全部理由）**：

  | 已有裁决 / 文档 | 它要求什么 | 现状为何做不到 |
  |---|---|---|

  | **`architecture.md` 运行时门控 1** | Guard 全局注册；隔离在 **PG RLS 层强制**；应用连接**不得用表 owner 身份** | 无 API 进程、无迁移、无 PG 角色 |
  | **`architecture.md` 运行时门控 2** | 全局 ValidationPipe + zod。「校验层根本不存在」是最常见的静默缺陷 | 同上 |
  | **`architecture.md` 运行时门控 3** | ExceptionFilter 只回 `internal_error`；lint 拦响应体里的 `err.message` | 同上 |
  | **ADR-020 契约单源** | 同一份 zod 生成**后端 DTO** + 前端类型 + OpenAPI + mock | 目前只接通了前端与 mock，**后端一端悬空** |

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

1. **开发 agent 执行**：在 `apps/api` scaffold **NestJS + TypeScript 严格模式**应用，
   纳入 pnpm workspace 与 turbo pipeline（`typecheck` / `lint` / `test` 三个 task
   必须被 `turbo run --affected` 命中）。
2. **开发 agent 执行**：建立**洋葱四层目录** `domain/` `application/` `infrastructure/`
   `interface/`，并让 `lint-arch-deps.mjs` **真正扫描到文件**
   （当前它对不存在的目录打印「跳过」并 exit 0）。
   ⚠ 同时给它补**反证 fixture**：一个故意从 `domain/` import `infrastructure/` 的样例文件，
   断言门控 exit 1。**只验「脚本能跑」不验「脚本能抓到违规」等于没有门控**（同 UC-0.4 V5）。
3. **开发 agent 执行**：建立**显式 SQL 迁移体系**——`apps/api/migrations/NNNN-*.sql`，
   前向单向、可从空库重建、**幂等**（连跑两次结果一致）。提供 `pnpm --filter api run migrate`
   与 `migrate:check`。
   > 依据 `architecture.md` 不变量：「所有状态可从 **PG + 迁移 + 对象存储**重建」。
   > 迁移不可审计，这条不变量就无从谈起。
4. **开发 agent 执行**：建立 **RLS 基线**——
   - 创建**应用角色**（如 `app_rw`），**不是表 owner**、**不带 `BYPASSRLS`**；
   - 迁移里对启用 RLS 的表统一 `ENABLE ROW LEVEL SECURITY` + `FORCE ROW LEVEL SECURITY`；
   - 租户上下文经 `SET LOCAL app.current_org` 传入，策略据此过滤；
   - 建一张**探针表** `rls_probe`（两个租户各若干行）——它的唯一用途是**证明 RLS 生效**，
     不属任何业务域。
   ⚠ PG 中**表 owner 默认不受 RLS 约束**（`architecture.md` 明写）。
   这一条是本步最容易被静默做错的地方，故 R12 V4 单独断言应用角色不是 owner。
5. **开发 agent 执行**：实现**三个运行时门控**，全部落在 `interface` 层（协议适配，不是业务规则）：
   - **Guard**（全局注册）：handler 拿到的 principal **非空**；无凭证一律 401，
     **不得降级为匿名放行**（对齐 `identity` 束的 `AUTH_SERVICE_UNAVAILABLE`「一律拒绝不降级」）；
   - **ValidationPipe**（全局）：schema 来自 `packages/contracts` 的 **zod**，
     **不得在后端另写一份 DTO 定义**；
   - **ExceptionFilter**：响应体只含 `internal_error` 与 traceId，
     细节只进日志；配 lint 拦响应构造里的 `String(err)` / `err.message`。
6. **开发 agent 执行**：接通**契约 → 后端 DTO** 这一端。
   `packages/contracts/src/*.ts` 的 zod 成为后端校验与类型的**唯一来源**，
   由 `lint-contract-source.mjs` 门控（它已存在，此前只覆盖前端侧）。
7. **开发 agent 执行**：提供**本地依赖编排** `docker-compose.dev.yml`
   （PG 16 + pgvector · MinIO · Redis），使 `pnpm dev:api` 可从零跑通。
   ⚠ 编排文件里为**出网策略预留声明位**（X-3，见 R10）——本件不实现 deny-all，
   但必须让它有**明确落点**，否则它会在前后端与运维的缝里掉下去。
8. **系统收口**：`pnpm --filter api run typecheck` / `test` 通过；
   `lint-arch-deps` **报出实际扫描文件数**（不再是「跳过」）；
   RLS 反证脚本与运行时门控反证脚本各自通过；迁移幂等校验通过。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[设计] **不引入 ORM**。持久化用显式 SQL + 轻查询构建，理由与「显式 SQL 迁移」一致：
    ORM 会把 RLS 需要的 `SET LOCAL` 会话语义藏进连接池行为里，
    **让「这条查询在哪个租户上下文里跑」变得不可读**。
    ⚠ 这是一条会长期生效的选择，[待确认]。
  - A2：[设计] worker 进程（摄取/研究）与 API **同代码库不同入口**
    （`architecture.md` 已定），本件只建 API 入口，worker 入口留给 phase-01。
    但**领域层必须共用**，故洋葱目录从一开始就不得写成 API 专属。
- **异常流程**：
  - E1：`lint-arch-deps` 报「跳过：尚未创建」→ **判本件未完成**。
    「门控绿了」在本项目已五次是空转（见 web-kernel/coverage.md 末尾），
    故 R12 V2 断言的是**扫描文件数 > 0**，不是退出码为 0。
  - E2：RLS 反证脚本发现「去掉应用层过滤后仍能读到别的租户」→
    **不得在应用层补一个过滤了事**。必须回到策略与角色设置——
    应用层过滤是第二道，第一道漏了就是漏了。
  - E3：迁移连跑两次结果不一致 → 判失败。不得靠「重建库」绕过：
    生产不会给你重建库的机会。
  - E4：ValidationPipe 的 schema 与 `packages/contracts` 出现第二份定义 →
    以契约为准删掉后端副本（`lint-contract-source` 会报）。
    **这是本项目第七次漂移的最高风险点**：后端 DTO 与契约同形，最容易被顺手抄一份。

## R5 权限与可见性

- 本件**不产生任何业务权限判定**——判定逻辑属 `identity` 束（UC-0.3 / F01）。
  本件只提供**判定被强制执行的地方**：Guard（应用层第二道）与 RLS（数据层第一道）。
- ⚠ [设计] **「应用层过滤」与「RLS 强制」不是同一件事，也不能互相顶替。**
  `architecture.md` 明写「租户/项目隔离在 PG RLS 层强制，应用层过滤只是第二道」。
  本件的验收面刻意设计成**去掉应用层过滤后仍不泄漏**——
  这是区分「真的强制」与「看起来隔离了」的唯一手段。
- 健康检查端点**不得泄露**库连接串、迁移 SQL、角色名等部署细节。

## R7 业务规则（不随具体实现变化的硬性约束）

- [设计] **依赖方向只能指向内层**，且这条**必须被机器检查**。
  「洋葱架构的全部价值在这一条」（ADR-020 原文）——只分目录不查方向 = 四层文件夹 + 零收益。
- [设计] **应用数据库连接不得使用表 owner 身份**，且不得带 `BYPASSRLS`。
  PG 中表 owner 默认不受 RLS 约束——**这是「以为开了 RLS 其实没开」的头号成因**。
- [设计] **RLS 是第一道，应用层过滤是第二道**。验收必须能在**移除第二道**的前提下成立。
- [设计] **迁移显式、前向、幂等**，且所有状态可从「PG + 迁移 + 对象存储」重建。
- [设计] **校验 schema 单一事实源在 `packages/contracts` 的 zod**。
  后端不得另写 DTO 定义——这是「同一事实声明在两处」在后端的第一个高危面。
- [设计] **错误响应体只回 `internal_error` + traceId**。
  细节进日志，不进响应——`err.message` 常含 SQL 片段与表名。
- [设计] **探针表 `rls_probe` 是内核资产，不是临时脚手架**。
  它必须长期存在：将来任何人改动 RLS 策略或连接角色，反证脚本会立刻红。
  ⚠ 删掉它等于删掉「RLS 真的在强制」的唯一证据。
- [设计] **本件的每一条门控都必须有反证**（同 UC-0.4 R7 的纪律）。
  本项目已五次出现「门控全绿但在空转」，其中 `lint-arch-deps` **此刻就是**——
  它对不存在的目录打印「跳过」并返回 0。

## R8 界面线索

- **无界面**。本件零前端产出。
- 唯一对外可见面是**健康/就绪端点**（如 `GET /healthz`），返回：
  已应用的迁移版本、RLS 是否处于 FORCE、应用角色是否为非 owner。
  ⚠ 它是**运维可见**而非用户可见，且**不得泄露连接串与角色名**（R5）。
- **UI sign-off**：**不适用**（无界面）。
  本件与 UC-0.4 同样**以机器门控代替人类 sign-off**——R12 的 V1–V10 全部为可执行断言。

## R9 非功能约束

- **性能/规模预期**：[设计] `pnpm dev:api` 冷启动 < 20s；
  RLS 反证脚本全程 < 60s（超时会让 agent 倾向跳过门控，同 UC-0.4 R9 的理由）。
- **安全/隐私/合规**：
  - 应用角色最小权限，非 owner、无 `BYPASSRLS`、无 DDL 权限（DDL 只由迁移角色执行）。
  - 错误响应不泄露内部细节；健康端点不泄露部署细节。
  - **无凭证一律 401，不得降级为匿名放行**——降级放行是「鉴权层根本不存在」的常见伪装。
- **兼容与降级要求**：门控脚本不可执行时 **verify 判失败**，不得静默跳过。
- **可观测性**：Interceptor 统一 traceId，错误日志与响应体的 traceId 必须能对上
  ——否则「只回 `internal_error`」会让线上问题无法定位。

## R10 已知约束 / 依赖

- **内部依赖**：`packages/contracts`（已存在，4 束 27 操作）。**无 feature 级依赖，可立即开工。**
- **被依赖**：**F01~F13 全部十三个后端 feature**。
  其中 F01 与 F02 直接消费本件的 RLS 基线与洋葱骨架。
- **[设计] 与 `architecture.md` 的关系**：该文档已裁决 NestJS、洋葱、RLS、三道运行时门控，
  但**全部处于「只写没做」状态**。本件负责把它建出来。
  实现中若发现文档与本仓实际不符，**以文档意图为准、修正文档表述**，并在 evidence 里记录。
- **X-3（出网为零）的归属**：阶段一致性复核指出「这条如果没人认领，它会在前后端的缝里掉下去」。
  ⇒ **本件认领它的落点**（`docker-compose.dev.yml` 与部署清单的网络策略位），
  但**不实现 deny-all 断言**——那需要本地组织的完整形态（F16）。
  本件的义务是：让 X-3 有一个**明确的文件位置和负责人**，而不是继续悬空。
- **[待确认]** 是否引入 ORM（R4 A1 默认不引入）。这条一旦定下很难回头。
- **[待确认]** 认证凭证形态（JWT / session / mTLS）——本件不决定，
  只要求 Guard 拿到非空 principal。属 phase-01 `01-auth`。
- **[待确认]** 迁移工具选型（自研 runner / node-pg-migrate / dbmate）。
  硬约束只有「显式 SQL、前向、幂等、可从空库重建」四条，工具不限。

## R11 切分提示（给 requirement-author）

- 建议**合并为单个 feature**，不拆。理由与 UC-0.4 R11 相同：
  R3 的八步强耦合——没有迁移体系就没有 RLS 策略，没有 RLS 就没有反证，
  没有洋葱目录 `lint-arch-deps` 就仍在空转。拆开会产生一串「做完了但验不了」的中间态。
- 若必须拆，唯一合理的切线是 **①~④（骨架 + 洋葱 + 迁移 + RLS 基线）** 与
  **⑤~⑦（三道运行时门控 + 契约接线 + 本地编排）**，前者 8 点、后者 5 点，后者依赖前者。
- **优先级 / 先后依赖**：P0；13 点；阶段零共享内核；
  **必须先于 F01~F13 任何后端工作**，与 F14（前端内核）无依赖、可并行。

## R12 AI Ready 验收线索

  **扫描文件数 > 0**（断言的是这个数，**不是退出码**）。

  **不带 `BYPASSRLS`**、**无 DDL 权限**；断言启用 RLS 的表均为 `FORCE ROW LEVEL SECURITY`。

  **绕过应用层任何过滤**直接 `SELECT * FROM rls_probe`，断言**读到 0 行属于租户 B 的数据**；
  再把 `SET LOCAL app.current_org` 换成 B，断言只看得到 B 的行。
  ⚠ 对照 UC-0.4 V5：只验「RLS 语句写了」不验「跨租户真的读不到」等于没有隔离。

  **只含 `internal_error` 与 traceId**，**不含该敏感字符串、不含堆栈、不含表名**；
  断言同一 traceId 在日志里能找到详情。

  退出码 0 且**扫描范围包含 `apps/api`**（不能只扫前端就算过）。
