## 一、本阶段目标与为什么是这个顺序

**一句话**：先把**所有业务模块都要用、且各自实现就必然分叉**的三条横切契约钉死——
统一上下文模型（Artifact / Version / Segment / Anchor + 三模式保存）、
Context Pack 装配与引用完整性、两层角色本体与 RLS 强制隔离。

**为什么必须排在最前**：这三件事是**数据模型层的定义**，不是功能。
- 后面 95 份 UC 里，凡是「保存产出」「引用证据」「谁能看见」的段落，全部指向这三份 UC。
- 若让 phase-1 的模块各自定义，会出现多套 artifact 表、多套权限判定、多套引用格式，
  而 `context-engine.md` 第七节的六条首批门槛（100% 引用可定位 / 跨租户泄漏为零 /
  重复摄取不产生重复 Segment / 删除后可验证失效 / 检索覆盖五类 / Context Pack 可重放）
  **每一条都是跨模块断言**，分叉之后无法收敛。
- D-38 已裁定：以 `uc-0-1` / `uc-0-2` 反推的 Context Pack + Artifact 设计为**权威**，
  UML 文档若出现只作校对参照。也就是说本阶段的产出即是全项目的地基定义。

## 三、依赖关系

**前置阶段**：无。本阶段是根（`roadmap.yaml` 中 `depends_on: []`）。

**被依赖**：phase-01 / 02 / 03 全部模块。特别是——
`22-files` 全模块、`14-brain/uc-14-6` 检索可审查、`17-gov/uc-17-1` 全链路审计、
`09-kg` 事实关系、`13-deliv/uc-13-5` 快照绑定契约，都是本阶段三份 UC 的直接下游。

**阶段内先后**（有硬顺序，不可并行乱序）：

```
uc-0-3 角色本体 ──> uc-0-1 Artifact 与三模式 ──> uc-0-2 Context Pack
   (权限是                (Pack 的召回对象               (最后装配，
    存储的前提)            必须先存在)                    验收面在这里)
```

- **`uc-0-3` 必须最先**：`acl_bindings` 与 RLS 是 `artifacts` 建表时就要带上的列与策略，
  事后补 RLS 等于重做迁移。
- **`uc-0-1` 次之**：没有不可变版本与固定快照，`uc-0-2` 的「打开原始引用」无落点。
- **`uc-0-2` 最后**：它的 AC1（100% 引用可定位到页码 / 时间码 / 消息）是本阶段的**总验收面**，
  同时也是 `context-engine.md` 首批门槛第 ① 条。

对齐 `context-engine.md` 第七节：本阶段 ≈ **P1 证据底座 + P2 的 Context Pack API**。

## 四、口径说明（给 requirement-author 的读法约定）

### 4.1 四标记（出现在每份 UC 的头部与正文行内）

| 标记 | 含义 | 生成 feature 时怎么处理 |
|---|---|---|
| `[原型]` | `WorkspaceX Standalone.html` **运行态实际存在**的行为，有界面可查 | 可直接落成 feature 的 `user_visible_behavior`，**可写 UI 断言**（但见 4.3 的 testid 警告） |
| `[Backlog]` | `Backlog Use Case.html` 的**文档要求**，原型未必实现 | 可落 feature，但 **UI 部分需先补画原型**，`verification` 只写 API / 逻辑断言 |
| `[设计]` | 依据前两者反推补全，**需人类确认** | 可落 feature，但必须在 feature 上标注待确认；UI 阶段进不了 `new-sprint` |
| `[待确认]` | 不应由实现者决定（阈值 / 权限边界 / 合规口径） | **不得自行取默认值**。对应 `DECISIONS-OPEN.md` 的 O-nn 时取该条已填的裁决；找不到对应则 feature 需挂阻塞 |

### 4.2 缺失三态（三者成本差一个数量级，不要混为一谈）

| 状态 | 含义 | 补齐方式与成本 |
|---|---|---|
| **未探明** | 原型档案（`proto-01`…`proto-10`）**尚未点进那个屏**，不知道有没有 | **补抽取**。低成本，由抽取员 / ui-prototyper 完成，**不占人类裁决名额**（见 `DECISIONS-OPEN.md` 附录 B） |
| **原型待补** | 主屏存在，但**按钮已渲染、目标屏未见**（行为未接线）或下钻层缺失 | **补接线 / 局部补画**。中等成本 |
| **原型确认缺失** | **枚举完毕后确认不存在**——该层级所有标签页都已抽取，其中没有这个界面 | **必须补画整屏 + 产品/设计确认**。高成本，且**卡 `ui-signoff`** |

> **硬规则（`DECISIONS-FINAL.md` 通用规则第 2 条）**：不得把「未探明」写成「原型没做」。
> 前者只是没看，后者是确认不存在——把前者写成后者会凭空制造补画工作量。

### 4.3 本阶段特有的口径

- `uc-0-2` 头部已声明：原型说明页把本协议指向「UML 文档第 13 节」，**该文档不在仓库中**，
  故本文是**依据原型证据链反推的设计稿**。D-38 已裁定采纳其为权威——
  但这意味着 `uc-0-2` 的大量条款是 `[设计]` 而非 `[原型]`。
- 本阶段**无独立界面**（它是契约层），UI 落点寄生在 phase-1/2/3 的屏上
  （右侧上下文包与证据栏、底部保存到项目三模式、大脑「AI 读到了什么」屏）。

## 五、切分注意事项

### 5.1 横切关注点必须合并成共享 feature

本阶段**整体就是横切层**，所以规则反过来：**这三份 UC 内部不要再按调用方切**。

| 横切能力 | 正确切法 | 错误切法（禁止） |
|---|---|---|
| 权限判定 | 一个 `acl_bindings` + RLS 策略 feature，附一张**权限矩阵测试表**覆盖全部角色组合 | 每个下游模块各写一遍「XX 角色能否看 XX」 |
| 审计留痕 | 一个 `provenance_events` append-only 写入 feature | 每个写操作各自埋点 |
| Context Pack 装配 | 一个装配器 feature + 一个五路召回 feature + 一个 `omissions[]` 契约 feature | 每个 Studio 各装配一次 |
| 七种界面状态 | **不在本阶段**（无界面）。D-36 已裁定按统一规范实现、sign-off 豁免逐屏设计 | 在契约层写界面状态 |

### 5.2 已知的重复计点风险

- **本阶段 55 点与下游模块的边界**：`22-files` 的 47 点是 `artifacts / artifact_versions` 的
  **用户界面投影**，**不重复实现存储**。若 `requirement-author` 在 phase-1 又生成了一份
  artifact 建表 feature，即为重复计入。
- `uc-0-1` 的固定快照 与 `13-deliv/uc-13-5` 快照绑定契约（3 点）是**同一套不可变语义的两侧**：
  本阶段交付机制，13-deliv 交付业务规则。不要在两处各建一套快照表。

### 5.3 `verification` 优先级（D-35：A + B 并行）

```
① round-trip / 纯函数断言   ← 最优先
② API 断言（含 SQL / RLS 断言）
③ UI 断言                   ← 最后手段
```

本阶段应当**几乎全部落在 ①②**：
- `uc-0-1`：版本不可变 round-trip（写入 → 改 → 断言原版本 SHA-256 不变）。
- `uc-0-2`：Context Pack 可重放（同一 run id 重放得到同一 `items[]`）——
  对应首批门槛第 ⑥ 条，是纯函数断言。
- `uc-0-3`：跨租户泄漏测试为零（首批门槛 ②）——**用非 owner 数据库角色**跑 SQL 断言。
  注意 `FORCE ROW LEVEL SECURITY`：连接不得用表 owner，否则 RLS 被静默旁路，测试假通过。

> ⚠ **原型零 `data-testid`**。任何 UI 断言在 `uiux-standards` 的 `data-testid` 命名规范落地前
> 都写不出稳定选择器。本阶段无界面，不受影响；但**不要为本阶段的能力去 phase-1 的屏上写 UI 断言**。

## 六、UI sign-off 风险

**本阶段无 UI，`roadmap.yaml` 中未标 `has_ui`，不受 ADR-003 的 UI 先行关卡约束。**

但有一条间接风险需记录：

| 项 | 状态 | 说明 |
|---|---|---|
| `uc-0-2` 的「上下文包与证据」右栏 | **原型待补** | 说明页有描述，四段注入结构 / 五种筛选动作在大脑「AI 读到了什么」屏可见，但 Studio 内的右栏本体未探明 |
| `uc-0-1` 的「保存到项目三模式」底栏 | **原型确认缺失 / 部分** | 说明页文字提及三模式，实际交互屏未见 |
| `uc-0-3` 的组织切换器（O-12 落地物） | **原型确认缺失** | 顶部组织切换器 + 切换清空项目级上下文，是裁决后新增，原型无此控件 |

以上三项**不阻塞本阶段开工**（本阶段交付的是后端契约），
但**会阻塞 phase-1 中承载它们的那几块屏**的 sign-off。建议在本阶段并行发起补画。

40 条 O-nn 已全部填写裁决，本阶段残留的 `[待确认]` 属于**裁决已下、细则未落**的类型：

| 类别 | 涉及 | 对应开放项 |
|---|---|---|
| **留存与不可删的共存规则** | 快照 / 绑定关系 / 审计留痕「不可删」与「到期删除」如何共存（`uc-0-1`） | O-01 裁决已给五个默认值，并建议「不可删对象不受留存期约束、单独走 O-39 法定留存清单」——**O-39 的法定留存清单本身仍是信息缺口（⚪ 需合规/法务外部输入）** |
| **上下文预算数值** | Context Pack 的 token 预算上限、五路召回各路配额、rerank 截断位（`uc-0-2`） | O-36 一批可配置阈值 / O-34 容量基线 —— 🟡 可并行，实现可先按假设走 |
| **权限传播的性能边界** | 权限沿 embedding / 图节点传播时的判定时机（请求时 vs 预计算）（`uc-0-3`） | O-34 容量与压测指标基线 —— 🟡 |

**结论**：本阶段**无 🔴 阻塞开工级残留**。可以直接进入 `feature_list.json` 生成。
