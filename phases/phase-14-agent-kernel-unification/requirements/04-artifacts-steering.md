# 需求：产出物版本化与执行中途插话

## R1 概览
- **Use Case 名称**：把 agent 产出的文件变成可版本追溯的一等实体；允许用户在
  agent 执行过程中插话重新引导
- **Actor**：终端用户（查看/追加修改产出物；在任务执行中发送新指令）
- **目标**：用户生成一份文件（如 PDF）后能基于它继续迭代而不是每次重新生成；
  用户发现方向不对时能立刻纠正而不必等待或取消重来
- **系统边界**：网关新增 `Artifact` 领域模型与 API、`apps/deep-agent-service`
  的插话消息处理、`apps/web` 新增 artifacts 面板与运行中可交互输入框

## R2 前置条件 / 触发条件
- **前置条件**：`02-streaming-transport.md` 的真流式状态机已就绪。
- **触发条件**：
  - agent 工具调用产出了文件类结果（触发 Artifact 创建/更新）。
  - 用户在已有 Artifact 基础上发起"继续修改"请求。
  - 用户在 run 处于 `running` 状态时通过输入框发送新指令（插话）。

## R3 主流程（Artifacts 版本化）
1. agent 执行中某次工具调用产出一个文件（如 PDF），网关创建一个新的 `Artifact`
   实体（`id`/`version=1`/`producedByRunId`/`producedByStepId`），而不是仅仅作为
   一条聊天附件落库。
2. 前端 artifacts 面板展示该产出物的版本历史（当前只有 1 个版本）。
3. 用户点击"基于此版本继续修改"，输入新的修改指令（如"把第二页标题改成 X"）。
4. 网关调用 `POST /artifacts/:id/continue`，携带该 artifact 内容作为上下文触发
   一个新 run。
5. 新 run 执行完成后，同一 `Artifact` 的 `version` 递增（`version=2`），旧版本
   保留可查看/下载。
6. 用户可在版本历史中任意切换查看，或继续基于最新版本迭代。

## R3'（中途插话）
1. 用户在一个 run 处于 `running` 状态时，通过输入框发送新指令。
2. 前端调用 `POST /agent-runs/:id/interject`，携带该指令文本。
3. 内核（LangGraph 图）在下一次工具调用之间检查是否有新插话消息，若有则将其
   注入为最高优先级上下文，据此判断是否需要重新规划。
4. 若内核判断为方向性改变，触发新的 `plan_update`（是否需要走
   `03-plan-mode-permissions.md` 的重新确认由内核判断）；若为局部调整，直接
   在当前计划框架内继续执行。
5. 前端在插话发送后 1 秒内展示"已收到"确认反馈。

## R4 备选流程与异常流程
- **备选流程**：
  - A1：用户对同一 Artifact 连续发起多次"继续修改"，版本历史应正确递增且每次
    都可独立追溯到触发它的 run/step。
  - A2：用户插话内容与当前任务无关（如切换到完全不同的话题），内核应能识别并
    提示用户"这是否意味着要开始一个新任务"，而不是强行把无关内容并入当前计划
    （具体识别策略属于内核实现细节，本需求只要求有此边界处理，不规定算法）。
- **异常流程**：
  - E1：插话发送时机恰好与一次正在执行的工具调用重叠，插话不得打断该次调用的
    执行（必须等它跑完/超时），只影响"下一步是否按原计划继续"。
  - E2：Artifact 的"继续修改"请求所依赖的原始 run 已经是很久以前的历史记录
    （原始产出物内容可能已被后续版本大幅偏离用户预期），系统应保证"继续修改"
    使用的是明确指定版本的内容作为上下文，不能默默使用了错误版本。
  - E3：插话导致的重新规划如果使已批准的 L2 权限授权（"本 run 内都允许"）失效
    范围产生歧义（比如插话后任务性质完全变了），需要重新走一次授权确认，不能
    沿用旧授权范围执行不同性质的高风险操作。
  - E4：产出物生成失败（如 PDF 生成中途报错），不应创建一个内容为空/损坏的
    Artifact 版本，失败的尝试不计入版本历史，仅在错误处理层面呈现（见
    `05-error-observability.md`）。

## R5 权限与可见性
- Artifact 的版本历史默认仅创建者及同组织内有权限访问该 run 的用户可见，不做
  跨组织共享（沿用现有聊天附件的组织隔离范围）。
- 插话功能对 run 的发起者开放；本 phase 不支持"其他协作者插话"（多用户协作不在
  本 phase 范围）。

## R6 后置条件 / 不包含
- **后置条件**：
  - 产出文件类结果不再仅作为一次性聊天附件存在，而是有独立的 `Artifact` 实体与
    版本历史。
  - `running` 状态下用户输入框保持可交互（非 disabled），这是可直接断言的 UI
    状态。
- **不包含**：
  - 多用户协作编辑同一 Artifact。
  - Artifact 的差异对比可视化（版本间 diff 展示）视为增强项，本 phase 只要求
    版本历史可查看/可继续修改，不强制要求版本间的可视化 diff。

## R7 业务规则
- 每个 Artifact 版本必须能明确追溯到产生它的 `runId`/`stepId`，不允许出现
  "不知道哪次执行产生的版本"。
- 插话不等同于取消当前任务：除非用户明确表达"取消"，插话默认被当作对当前任务的
  调整，而非另起一个任务。

## R8 界面线索
- **中途插话入口**：`running` 状态下用户输入区域保持可交互，发送后有即时"已收到"
  反馈，不打断当前展示中的执行进度流。
- **产出物面板**：独立于聊天流的侧栏，展示当前产出物的版本历史缩略图，点击可
  查看某版本，可"基于此版本继续修改"。
- 参考截图：待 UI 先行阶段产出（`ui-preview/`）。

## R9 非功能约束
- 性能/规模预期：插话确认反馈 < 1 秒；Artifact 版本历史查询应支持分页（避免
  长期迭代后单次加载过多版本）。
- 安全/隐私/合规：Artifact 存储遵循与现有聊天附件相同的对象存储与访问控制策略。
- 兼容与降级要求：无。

## R10 已知约束 / 依赖
- 依赖 `01-kernel-unification.md` 的网关工具执行代理机制（产出文件的写入路径）。
- 依赖 `02-streaming-transport.md` 的事件模型（`plan_update` 等事件在插话触发
  重新规划时复用）。

## R11 切分提示
- 建议拆分为：(a) Artifact 领域模型 + API（版本化）；(b) 前端 artifacts 面板；
  (c) 中途插话后端接口 + 内核处理；(d) 前端插话交互（可交互输入框 + 即时反馈）。
  (a) 与 (c) 可并行，各自的前端 (b)/(d) 依赖对应后端先行。

## R12 AI Ready 验收线索
- 可验证：连续两次"继续修改"后版本历史长度正确递增，各版本可独立回看；具体
  用例（如"把 PDF 第二页标题改成 X"）断言仅目标部分变化而非从零重新生成；
  `running` 状态下输入框非 disabled；插话后下一步执行路径需体现新指令（用具体
  场景断言最终产出）；发送插话后 1 秒内显示"已收到"确认。
