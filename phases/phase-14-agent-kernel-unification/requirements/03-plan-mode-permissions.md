# 需求：Plan Mode 与分级权限确认

## R1 概览
- **Use Case 名称**：agent 执行前先出计划让用户确认，执行中按风险分级请求工具
  调用授权
- **Actor**：终端用户（发起任务并对计划/高风险操作做决策）
- **目标**：用户在 agent 真正动手（尤其是有副作用的操作）之前，能看到并调整
  计划，并对高风险操作有知情和否决权，而不是被动等待结果
- **系统边界**：`apps/deep-agent-service`（`write_todos`/`PlanFirstToolChoiceMiddleware`）、
  网关新增权限判断层、`apps/web` 新增计划确认卡片与权限确认弹层

## R2 前置条件 / 触发条件
- **前置条件**：`02-streaming-transport.md` 的真流式与状态机已就绪（本需求新增
  的 `awaiting_plan_confirmation`/`awaiting_tool_permission` 状态依赖该状态机
  框架）。
- **触发条件**：
  - 用户发起一个非平凡任务（涉及多步骤或有副作用操作）。
  - agent 在执行中需要调用一个 L2 分级（不可逆/高风险）的工具。

## R3 主流程
1. 用户发起任务，内核产出结构化 plan（复用 `write_todos`），推送 `plan_update`
   事件，run 状态迁移到 `awaiting_plan_confirmation`。
2. 前端渲染计划确认卡片，展示结构化 todo 列表，用户可编辑/删除某项。
3. 用户确认（直接确认 / 编辑后确认）：编辑后的 plan 以修订版本写回内核作为新的
   执行输入，run 状态回到 `running`。
4. 内核开始执行。遇到 L0（只读）操作自动执行，不打断；遇到 L1（可撤销副作用，
   如写文件/编辑文件）默认自动执行，但对应事件带完整 diff；遇到 L2（不可逆/
   高风险，如执行命令）且用户尚未对该类操作授权时，run 状态迁移到
   `awaiting_tool_permission`。
5. 前端渲染工具权限确认弹层，展示 agent 想做什么、为什么；用户三选一：
   仅本次允许 / 本次 run 内都允许 / 拒绝。
6. 用户批准后，网关代理该工具调用在沙箱执行，run 回到 `running` 继续；用户拒绝
   后，内核收到拒绝结果，需据此调整后续计划（不是直接判定整个 run 失败）。
7. 任务完成，run 到达终态。

## R4 备选流程与异常流程
- **备选流程**：
  - A1：用户在计划确认阶段选择"取消"，run 应立即终止（进入 `failed` 或专门的
    "用户取消"终态，不残留在任何非终态）。
  - A2：用户此前已对某类 L2 操作选择过"以后都允许"（组织级默认策略持久化生效），
    则同类操作不再触发 `awaiting_tool_permission`，直接执行并仍产生带完整信息
    的事件供用户事后查看。
- **异常流程**：
  - E1：计划确认或权限确认弹层长时间无用户响应（用户离开），run 应保持在对应
    非终态等待（不超时自动执行有副作用的操作），但需要有明确的"待你确认"入口
    提醒（如通知/角标），避免用户遗忘。
  - E2：用户编辑计划后引入了明显不合法的内容（如删除了必要前置步骤导致后续
    步骤无法执行），内核应能识别并给出提示，而不是静默执行到中途失败。
  - E3：中途插话（见 `04-artifacts-steering.md`）导致方向性改变时，是否需要
    重新触发计划确认由内核判断（不强制每次插话都重新确认）。
  - E4：单个 run 内，除首次规划和插话触发的重新规划外，不应出现额外的计划确认
    请求——避免退化为"每步都要点头"的不可用体验。

## R5 权限与可见性
- 权限分级表（按操作类型，不按用户角色）：
  | 分级 | 触发条件 | 行为 | 归属状态 |
  |---|---|---|---|
  | L0 只读 | grep/read_file/web_fetch 等无副作用 | 自动执行，不打断 | 保持 `running` |
  | L1 可撤销副作用 | write_file/edit_file（有版本历史，可回滚） | 默认自动执行，事件带完整 diff | 保持 `running` |
  | L2 不可逆/高风险 | bash_exec、外部系统写入 | 默认需用户确认（除非已授权同类） | 进入 `awaiting_tool_permission` |
- 授权粒度：单次 / 本次 run 内 / 该组织默认策略三档，存储在网关侧（内核只需知道
  调用被批准还是拒绝，不持有授权状态本身）。
- 组织管理员角色对"以后都允许"类授权的管理后台不在本 phase 范围（见 00-overview
  Out of Scope）。

## R6 后置条件 / 不包含
- **后置条件**：
  - AgentRunStatus 新增 `awaiting_plan_confirmation`、`awaiting_tool_permission`
    两个非终态，且均已被 `02-streaming-transport.md` 中的 `isTerminalRunStatus`
    体系覆盖。
  - 每次 L1/L2 操作的完整入参出参（diff/命令内容）通过事件传递给前端，供用户
    在确认或事后查看时使用完整信息判断，不是截断摘要。
- **不包含**：
  - 组织级默认权限策略的后台管理界面。
  - L0/L1/L2 分级规则本身的动态可配置化（本 phase 分级规则为固定的工具白名单
    映射，不支持组织自定义分级）。

## R7 业务规则
- L2 操作在用户未曾授权同类操作的情况下，绝不允许自动执行，没有例外（包括
  agent 自认为"这次风险很低"也不能绕过）。
- Plan Mode 的确认粒度必须限制在"首次规划"与"方向性重新规划"两种时机，逐步骤
  确认在设计上被禁止（会导致体验不可用）。

## R8 界面线索
- **计划确认卡片**：触发于 `awaiting_plan_confirmation` + `plan_update`；展示
  结构化 todo 列表可编辑/删除，底部"确认执行/取消"按钮；不需要设计逐步执行时的
  勾选动画。
- **工具权限确认弹层**：触发于 `awaiting_tool_permission`；展示"agent 想做什么、
  为什么"，三个操作按钮：仅本次/本 run 内都允许/拒绝；不需要设计组织级默认策略
  管理界面。
- 参考截图：待 UI 先行阶段产出（`ui-preview/`）。

## R9 非功能约束
- 性能/规模预期：计划产出到前端渲染确认卡片的延迟应低于常规事件延迟标准
  （< 500ms，继承 `02-streaming-transport.md`）。
- 安全/隐私/合规：L2 操作的确认记录（谁在何时批准了什么）需要可审计，纳入
  `05-error-observability.md` 的 transcript 范围。
- 兼容与降级要求：无。

## R10 已知约束 / 依赖
- 依赖 `write_todos`、`PlanFirstToolChoiceMiddleware`（`deep-agent-service` 已有
  代码，本需求要求其在默认部署下生效，而非新增算法）。
- 依赖网关侧新增的权限判断与授权粒度存储（见 `01-kernel-unification.md` 中
  "网关是唯一有权决定工具调用是否被允许执行的组件"这一原则）。

## R11 切分提示
- 建议拆分为：(a) 后端状态机+权限分级+授权存储；(b) 前端计划确认卡片；
  (c) 前端工具权限确认弹层。(a) 需先行，(b)/(c) 可并行。

## R12 AI Ready 验收线索
- 可验证：非平凡任务第一个可见状态必须是 `awaiting_plan_confirmation`；编辑
  todo 后确认，实际执行路径需反映编辑内容（非仅 UI 显示）；固定测试场景下计划
  确认次数不超过预期上限；纯只读任务全程不出现 `awaiting_tool_permission`；
  含 `bash_exec` 的任务未授权时必进入确认态，拒绝后不得继续执行；分别验证
  单次/本run/以后三档授权的生效范围。
