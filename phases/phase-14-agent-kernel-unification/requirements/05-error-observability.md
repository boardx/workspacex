# 需求：错误人性化处理与完整可观测性

## R1 概览
- **Use Case 名称**：修复错误分类误标问题，向用户呈现可读、可行动的错误信息，
  并保留完整可审计的执行 transcript
- **Actor**：终端用户（遇到失败时需要看懂并知道下一步做什么）、运维/开发（排障
  时需要完整审计信息）
- **目标**：用户遇到任务失败时不再看到原始技术错误码/堆栈，而是明确的原因说明
  和可执行的下一步建议；同时系统内部保留完整的执行记录供审计排障
- **系统边界**：`apps/api/src/application/agent-run/run-skill-script.ts`（错误
  分类）、网关新增错误人性化转换层、`packages/contracts/src/wave2-runtime.ts`
  的 `agent_run_steps` 存储结构、`apps/web` 错误状态卡片

## R2 前置条件 / 触发条件
- **前置条件**：无直接依赖，但与 `01`/`02` 的改造在同一批代码路径上，建议同批
  次推进。
- **触发条件**：
  - 任意工具调用/模型调用在执行中失败。
  - 用户或运维需要查看某次 run 的完整执行记录。

## R3 主流程（错误分类与人性化）
1. 内核或工具执行过程中发生异常（如模型调用失败、沙箱执行失败）。
2. 网关的错误分类逻辑（修复后的 `toFailure`）根据异常的真实类型准确归类
   （模型调用失败 → 模型类错误码；沙箱不可用/超时 → 沙箱类错误码；不得再有
   "任何未识别异常都归为 SANDBOX_UNAVAILABLE"的兜底误标）。
3. 网关的错误人性化转换层把内部错误码转换为 `{ message, suggestedAction }`
   结构，`suggestedAction` 至少覆盖：重试 / 简化任务重试 / 联系支持三种。
4. run 状态迁移到 `failed`，事件携带上述人性化结构推送给前端。
5. 前端渲染错误状态卡片：主展示区显示 `message` 和 `suggestedAction` 对应的
   可点击按钮；原始技术信息（错误码/堆栈）放入"查看详情"折叠区，默认收起。

## R3'（完整可观测性）
1. 每次 run 的每个执行步骤（模型调用、工具调用、计划变化、权限确认）都写入
   `agent_run_steps` 账本。
2. 与现状不同，账本存储**完整的 prompt/response 内容**（而非仅 digest + 截断
   摘要），通过字段级加密存储，隐私通过 RBAC 访问控制实现，而非从数据源头
   阉割内容。
3. 有权限的运维/开发角色可通过审计接口读取某次 run 的完整执行 transcript，
   完整回放"模型看到了什么、完整说了什么、每次工具调用的完整入参出参"。

## R4 备选流程与异常流程
- **备选流程**：
  - A1：用户点击"重试"，系统应基于原始 run 的输入重新发起一次新的执行尝试
    （而非要求用户重新输入任务描述）。
  - A2：用户点击"简化任务重试"，前端应引导用户对原始任务描述做简化（如提示
    "任务可能过于复杂，尝试拆分成更小的步骤"），不是系统自动做不可控的简化。
- **异常流程**：
  - E1（本 phase 的直接触发 bug 回归用例）：模拟模型调用失败注入
    （`ModelCallError: MODEL_CALL_FAILED`），断言最终错误分类不再是
    `SANDBOX_UNAVAILABLE`，而是准确的模型类错误码。
  - E2：某个错误码没有映射到任何 `suggestedAction`，应被视为契约不完整，需要
    在开发阶段通过测试拦截（遍历所有已定义错误码确认均有映射），不允许上线后
    才发现某类错误无可行动建议。
  - E3：完整 transcript 因字段级加密的密钥不可用而无法解密时，审计接口应明确
    报告"内容不可读"而非静默返回空值或报错崩溃。
  - E4：极端情况下单次执行的 prompt/response 内容体积过大（如长文档处理任务），
    存储机制需要有合理的大小上限与截断策略说明，不能无限增长拖垮存储层
    （具体阈值留待实现阶段技术设计，此处只要求明确定义策略而非默认无限制）。

## R5 权限与可见性
- 面向终端用户的错误卡片：仅本人可见自己发起的 run 的错误信息（沿用现有权限
  范围）。
- 完整 transcript 的审计访问：仅限运维/开发角色（具体角色定义复用现有组织内
  权限体系），普通终端用户不能访问其他用户 run 的完整 transcript，也不能访问
  超出"人性化错误卡片"之外的原始技术细节（除非该 run 本身是自己发起的，"查看
  详情"折叠区对 run 发起者本人开放）。

## R6 后置条件 / 不包含
- **后置条件**：
  - `run-skill-script.ts` 的 `toFailure` 兜底分支不再统一归类为
    `SANDBOX_UNAVAILABLE`。
  - `agent_run_steps` 存储结构从"digest + 截断摘要"改为"完整内容 + 字段级加密"。
  - 每种 `failureCode` 都有明确的 `suggestedAction` 映射，可通过契约测试遍历
    验证无遗漏。
- **不包含**：
  - Agent 自身质量评测/回归打分体系（本需求只保证"记录完整"，不涉及"评测记录
    质量的好坏"，那是 00-overview 中声明的 Out of Scope）。

## R7 业务规则
- 面向用户的错误展示，任何情况下都不得直接暴露未转换的内部错误码/堆栈信息在
  主展示区。
- 错误分类的准确性优先于"总能给出一个分类"——宁可标记为"未知执行错误"这类诚实
  的兜底类别，也不能张冠李戴地标成一个具体但错误的分类（如把模型故障标成沙箱
  故障）。

## R8 界面线索
- **错误状态卡片**：触发于 `failed` + 人性化错误结构；展示 `message` +
  `suggestedAction` 对应按钮，原始堆栈放折叠区。
- 参考截图：待 UI 先行阶段产出（`ui-preview/`）。

## R9 非功能约束
- 性能/规模预期：错误人性化转换应在 run 失败后的事件推送中同步完成，不需要
  用户额外等待或二次请求。
- 安全/隐私/合规：完整 transcript 的字段级加密方案需要满足现行隐私合规要求，
  这是需要人类明确签字确认的决策点（涉及数据合规变更，架构文档中已标注）。
- 兼容与降级要求：无。

## R10 已知约束 / 依赖
- 依赖 `01-kernel-unification.md` 的工具执行代理机制（错误来源的准确捕获点）。
- 依赖组织现有的 RBAC 权限体系用于审计接口的访问控制。

## R11 切分提示
- 建议拆分为：(a) 错误分类修复（`toFailure` 精确化）；(b) 错误人性化转换层 +
  前端错误卡片；(c) 完整 transcript 存储改造（含加密与 RBAC）。(a) 应最先做
  （直接修复本次故障的诱因之一），(b)/(c) 可并行。

## R12 AI Ready 验收线索
- 可验证：固化模型调用失败注入的回归测试，断言分类不再误标；遍历所有已定义
  错误码，确认均有 `suggestedAction` 映射；`failed` 展示区不得出现未转换错误码/
  堆栈，仅折叠区可见；有权限角色可读取到完整 prompt/response 内容，无权限角色
  被正确拒绝访问。
