## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-10.1 / 报告列表与版本
- **Actor**：**引导师**、**项目经理**、**客户**
- **目标**：[原型] 页面顶部原话——「洞察报告 —— **用对话把项目里的材料综合成一份可发布的文本 ·
  每份都能追到出处**」。本用例负责这些报告的**清单视图与版本身份**：一个项目里可以并存多份写给
  不同读者的报告，每份处在自己的版本与状态上。
- **本用例结果**：[原型] 用户在「成果沉淀 → 洞察报告」看到本项目全部报告，每行能一眼读出
  **读者对象 / 页数 / 取材类别数 / 引用数 / 待补块数 / 状态与版本号**，并能 `[＋ 新建报告]` 或
  `[打开]` 进入报告工作台。
- **系统边界**：报告清单、报告元信息聚合（取材类别数、引用数、缺料块数）、版本号与三态状态机、
  新建 / 改名 / 删除、已发布版本与固定快照的绑定关系。**对话式生成属 UC-10.2、缺料属 UC-10.3、
  导出分享属 UC-10.4，本用例只负责入口与版本身份。**
- **核心数据对象**：报告（report）、报告版本（vN）、报告状态、读者对象（audience）、
  取材类别集合、引用计数、缺料项计数、发布记录与其绑定的固定快照。

## R2 前置条件 / 触发条件

- **前置条件**：
  - 用户已建立可校验的正式或临时身份，且拥有目标组织、项目、小组或资源的访问权。
  - 目标资源存在且未被删除/冻结；依赖能力“知识图谱、访谈、实时转录、成果沉淀”可用，或界面能明确显示其不可用状态。
  - 若动作涉及个人数据、录音、原始材料或跨范围读取，相应授权与留存策略已生效。
- **触发条件**：
  - [原型] 用户进入 **项目 → [进入项目] → 成果沉淀 → 洞察报告**（成果沉淀的五个子标签之一：
    洞察报告·对话生成 ｜ 结论与决策 ｜ 产出物 ｜ 行动项 ｜ 审计与反馈）。
  - [原型] 用户点 `[＋ 新建报告]`，或点某一行的 `[打开]` 进入报告工作台。
  - [设计] 报告在工作台被升版、发布或缺料数变化后，列表行的聚合字段随之刷新。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

1. **用户操作**：进入「成果沉淀 → 洞察报告」。**系统响应**：[原型] 顶部渲染一行说明
   「用对话把项目里的材料综合成一份可发布的文本 · **每份都能追到出处**」与 `[＋ 新建报告]`；
   下方按更新时间倒序列出本项目全部报告，**每行渲染六组字段**（原型实例）：

   | 状态 · 时间 | 读者对象 · 风格 | 页数 | 取材类别数 | 引用数 | 待补 | 动作 |
   |---|---|---|---|---|---|---|
   | `v3 草稿` 13:42 | 写给客户董事会 · 结论先行 | 3 页 | 取材 5 类 | 14 处引用 | **待补 2 块** | `[打开]` |
   | `已完成` 昨天 | 写给自己 · 过程与分歧 | 6 页 | 取材 6 类 | 21 处引用 | — | `[打开]` |
   | `已发布` 前天 | 写给项目经理 | 1 页 | 取材 3 类 | 6 处引用 | — | `[打开]` |

   [原型] **状态三态**：`草稿`（**带版本号**，如 `v3 草稿`）/ `已完成`（**不带版本号**）/
   `已发布`（**不带版本号**）——原型三行的实际呈现即如此；[Backlog] 另有第四态 `空白`。
   [设计] 无缺料时不显示「待补」块。
2. **用户操作**：点 `[＋ 新建报告]`。**系统响应**：创建一份 `v1 草稿`、读者对象为空、
   取材 0 类 / 0 处引用的空报告，直接进入报告工作台（UC-10.2）；列表新增该行。
3. **用户操作**：对某份报告执行**改名**或**删除**。**系统响应**：改名即时生效；
   删除前二次确认并说明影响范围——**已发布的报告不可直接删除**，只能停止分享（UC-10.4），
   其已发布版本与所绑定的固定快照按审计规则保留。
4. **用户操作**：点某行 `[打开]`。**系统响应**：加载该报告的**当前工作版本**进入左右两栏工作台，
   携带项目、报告 ID、版本号与当前用户角色；无该报告读权限时返回无权限态而非空列表。
5. **系统收口**：报告在工作台被升版（v3 → v4）或发布后，**回写列表行**的状态、版本号、页数、
   取材类别数、引用数与待补块数；已发布的报告改动**生成新版本，旧版本保留可查**（版本历史下钻未探明）。
6. **系统收口**：校验 AC1「同一项目可并存客户版、内部版、一页纸三份」——三份互不覆盖、
   各自独立版本号；记录新建 / 改名 / 删除 / 升版 / 发布的操作者、时间、对象与结果进项目级审计
   （项目 → 成果沉淀 → 审计与反馈）。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[原型] **已发布的报告改动生成新版本，旧版本保留可查**——在已发布的 vN 上继续编辑时，
    系统开出 `v(N+1) 草稿`，vN 及其固定快照保持只读，列表行同时可见当前草稿版本与最近已发布版本。
  - A2：[设计] **从既有报告另存一份**——用「写给自己 · 内部版」另存为「写给客户董事会」，
    继承取材范围与引用，版本号从 v1 重新计数，两份互不影响（支撑 AC1 的三份并存）。
  - A3：[设计] 列表支持按**读者对象**与**状态**筛选；报告数为 0 时展示空态与 `[＋ 新建报告]` 引导，
    不生成示例报告。
- **异常流程**：
  - E1：[设计] 请求超时、网络中断或依赖不可用时，保留用户当前输入与最后成功数据，明确失败原因，
    并提供安全重试。失败不得被呈现为成功，也不得产生无法追溯的半成品。
  - E2：[设计] 聚合字段（取材类别数 / 引用数 / 待补块数）计算失败时，该行显示「统计不可用」占位，
    **不得显示 0 冒充真实值**，`[打开]` 仍可用。
  - E3：[设计] 同一报告被两人并发改名或升版时不得静默覆盖；系统提示版本已变化，
    并允许刷新、对比或重新提交。
  - E4：[设计] 用户尝试删除**已发布**的报告时阻断，提示「已发布版本不可删除，请先停止分享」，
    并给出 UC-10.4 的撤销分享入口。
  - E5：[设计] 权限在操作过程中被撤回时立即终止后续写操作；已完成步骤按审计规则保留，
    未提交输入留在本地草稿并提示重新授权。

## R5 权限与可见性

- **引导师**：可发起、查看并管理本 use case，范围限定在其有权访问的组织、项目或小组。
- **项目经理**：可在被授权范围内参与流程并查看与自身角色相关的结果。
- **客户**：只读已向其发布的结论、产出、报告、进度与脱敏聚合；只能通过反馈入口新增意见，不能改动项目正式内容。
- **观察者**：默认不能发起或修改；仅当内容已发布且授权范围允许时只读查看脱敏结果。
- **未登录、链接失效或未列出的角色**：默认无权限；接口不得返回越权数据，不能只依赖前端隐藏。

## R7 业务规则（不随具体实现变化的硬性约束）

- [Backlog] **状态取值**：`空白` / `草稿` / `已完成` / `已发布`
  （Backlog UC-10.1 `flow` 原文「卡片显示读者对象、状态（空白 / 草稿 / 已完成 / 已发布）」）；
  原型列表只渲染了后三种。
- [设计] **状态与版本号绑定**：**每种状态都挂在一个确定的版本号 vN 上**；不存在无版本号的状态，
  也不存在同一版本号同时处于两种状态。
  ⚠ **与档案正面冲突，须人类复核**：原型报告列表三行里**只有草稿行带版本号**——
  「**v3 草稿** 13:42」「**已完成 昨天**」「**已发布 前天**」，后两行**没有 vN**。
  因此「三态都绑版本号」是本文的设计推论，**不是原型实况**；
  V4 建立在这条断言之上，须随本条一同复核（见 R12·V4）。
- [Backlog] **已发布的报告改动生成新版本，旧版本保留可查**
  （Backlog UC-10.1 `edge` 原文）——[设计] 已发布版本只读，不可就地修改。
- [设计] **已发布版本对应一个固定快照**：报告发布时必须绑定一份不可变的固定快照，
  快照语义（不可变、不可删除、只能新增版本 + 标注被替代）**统一由
  `phase-1/00-core/uc-0-1`「把 Studio 产出保存回项目」定义，本文不重复定义**，只声明依赖。
- [设计] 版本号在同一报告内**单调递增、不复用**；另存为新报告时从 v1 重新计数。
- [Backlog] AC1：同一项目可并存客户版、内部版、一页纸三份。
- AI/Agent 生成的候选内容必须标识为机器产出，展示可追溯来源；来源不足时不得伪造结论。
- AI/Agent 的写回、覆盖、发布或高影响工具调用必须遵守原型中的批准点；未经确认只保留为草稿或候选。
- 所有权限判断必须在服务端执行；隐藏入口只是界面表现，不构成安全控制。
- 任何覆盖、删除、撤销、签署、发布、写回或停用动作都必须记录审计事件，并显示动作影响范围。

## R8 界面线索

- **前端入口**：[原型] **项目 → [进入项目] → 成果沉淀 → 洞察报告**（成果沉淀子标签
  「洞察报告·对话生成」）；本用例具体页面为**报告清单**，行尾 `[打开]` 通向报告工作台。
- **信息架构**：[原型] 顶部说明行 + `[＋ 新建报告]`，下方一行一份报告；
  行内字段顺序：**状态与时间 → 读者对象与风格 → 页数 → 取材类别数 → 引用数 → 待补 N 块 → `[打开]`**。
- **推荐交互**：
  - [设计] **状态徽标**用三种视觉区分 `v3 草稿` / `已完成` / `已发布`；
    **「待补 N 块」必须高亮**，因为它同时意味着不能升版、不能对客户发布（见 UC-10.3）。
    （原型只给了三行**纯文本**状态与「待补 2 块」字样，**未给任何配色或视觉分级**；
    「三种视觉区分」与「必须高亮」都是本文设计推论。）
  - [设计] 读者对象与风格作为一行副标题呈现（「写给客户董事会 · 结论先行」），
    读者对象是报告的一等字段而非标签。
  - [设计] 改名为行内编辑；删除为危险动作，需确认对话框并明确「已发布版本不可删除」。
  - [设计] 新建报告直接落进工作台，不弹配置向导——配置通过 UC-10.2 的对话完成。

## R9 非功能约束

- **性能/规模预期**：
  - [设计] 报告清单（含六组聚合字段）应在 1 秒内给出可感知反馈；聚合字段允许异步补齐，
    但补齐前显示骨架而非 0。
  - [设计] 清单必须分页或增量加载，禁止一次加载整个项目的报告历史与全部版本。
- **安全/隐私/合规**：
  - 最小权限、组织/项目/小组隔离、传输与静态加密、敏感字段脱敏、导出与 AI 读取留痕。
  - 原始材料、录音、转写、私聊、个人身份与客户数据按授权和留存策略处理。
- **兼容与降级要求**：
  - 响应式 Web；桌面端提供完整能力，移动端保证加入、查看、输入、投票/确认等现场关键动作。
  - WebSocket/实时通道不可用时降级为轮询并显示“非实时”；断网允许保留未提交输入，但不得伪装已同步。

## R10 已知约束 / 依赖

- **内部依赖**：
  - `phase-1/00-core/uc-0-1`（**固定快照语义的权威定义**，已发布版本必须绑定固定快照）。
  - UC-10.2 对话式生成（提供取材类别数与引用数）、UC-10.3 缺料（提供待补块数）、
    UC-10.4 导出与分享（提供已发布状态与撤销分享入口）。
  - 成果沉淀模块（承载入口）、项目级审计与反馈（承载新建/删除/升版/发布事件）。
- **跨模块契约**：报告、报告版本、引用、缺料项必须与其它模块使用统一标识；
  列表行的聚合字段是**投影**，权威值在各自的产出模块，不得在报告侧另存一份可漂移的副本。
- **[设计] file-first 契约（与 `22-files` 项目文件模块）**——
  架构侧硬约束「能保存成文件的数据一律保存成文件，且必须能在项目文件浏览器里看到、能下载」
  （`docs/architecture/context-engine.md` 第 2.0 节）在本模块的落点：
  - **报告的每一个版本都物化为对象存储里一个真实、可下载的文件**，
    对应 `artifacts`（一份报告）+ `artifact_versions`（v1 / v2 / v3 …），
    每个版本带 **SHA-256** 与 MIME；**不存在只活在数据库表里的报告版本**。
  - **导出版本同样是文件**（UC-10.4 的 PDF / Word / Markdown 各自一个
    `artifact_version`），带 `derived_from` 指回它所导出的那个报告版本，
    **不覆盖源版本**。「导出」不是一次性下载动作，是产生一件可归档的派生工件。
  - 报告随正文一并物化 **`provenance.json`**（生成用的 prompt / model / run /
    Context Pack ID / 取材范围），`sourceType` 标 **`synthesized`**（见 UC-10.2 R7）。
  - **文件浏览器不是权限旁路**：报告文件在 `22-files` 中的可见性沿用同一套 `acl_bindings`，
    与报告列表页的权限判定**必须同源**——不允许出现「列表里看不到、文件树里能下载」。
  - **目录结构与命名一旦对外可见就是契约**：报告文件的路径与命名规则改动须走迁移，
    不得随手重构（UC-10.4 的只读链接可能直接指向它）。
  - 删除与撤回时，`22-files` 里那份**必须真的消失**（第二级物理删除后），
    这是 UC-10.5 与 `17-gov` 撤回可被**演示**的前提。
- **未探明（不是「原型没做」）**：
  - **版本历史下钻**——从某份报告进入 v1/v2/v3 的历史列表与版本对比，原型中的这一层
    **本轮抽取未点进**，需补抽取后才能定该子屏范围（D-23 列出的三处未探明之一）。
- **技术约束**：[原型] 产品为响应式网页（原型含移动端对照屏）；[Backlog] 完整离线模式、原生移动端、第三方 IM 与产品内自助计费
  在 backlog 中明确为范围外。
- **[待确认]** 一个项目内报告数量上限、单份报告版本数上限与历史版本的保留期
  （与 D-14 的五项留存参数如何对齐）。
- **[待确认]** 「已完成」与「已发布」之间是否存在评审/签字环节，还是由发布动作直接跨越。
- **[已裁决 O-38/O-39]** ① **数据驻留地区**：实现按「**受控枚举字段，取值从配置读取**」写，枚举内容留空——**不阻塞编码**，等合规给出；② **PII 最小集**可先按 邮箱 / 手机号 / 身份证号 / 银行卡号 / 详细住址 五类实现；③ **手机号加密存储 + 界面只展示掩码**（此二者不会因合规结论返工，可先动工）；④ **加密密钥策略、法定留存清单、删除证明格式**⚠ **必须等合规负责人输入**

- **[设计] 架构对齐 · Context Engine**（`docs/architecture/context-engine.md`，2026-07-28 定稿）：
  - **AI 取上下文只能通过 Context API 领取 Context Pack**——任何 agent、副驾驶或生成动作
    都不得绕过服务平面直查 `claims` / `segments` / `artifact_versions` 等库表。
    绕过即丢失 `permissionDecisionId` 与引用锚点，`uc-14-6`「AI 读到了什么」将不可重放。
  - **编排边界**：**LangGraph 只用于深度研究、人工确认（HITL）与多阶段生成**；
    文件摄取、批量导入、定时与重试一律走**持久任务系统**（MVP 为 PG outbox + job table）。
    LangGraph 不得被当作通用任务队列；HITL 用动态 `interrupt()`，节点恢复时副作用必须幂等。
  - **权限**：**租户与项目隔离在 PostgreSQL RLS 层强制**，应用连接使用受 RLS 约束的
    **非 owner** 角色（PG 中表 owner 默认不受 RLS 限制）。本文 R5 的权限判定与 R12 的
    越权断言是**第二道**防线，不是唯一防线。Artifact 权限必须传播到 Segment、embedding、
    图边、缓存与 Context Pack；交集生成内容取所有来源权限的**最严格**结果。

## R11 切分提示（给 requirement-author）

- 建议拆「报告与版本数据模型（含三态×版本号约束） → 清单聚合接口（六组字段） →
  清单 UI 与状态徽标 → 新建/改名/删除 → 已发布不可删门禁 → 审计 → 自动化验收」。
- **「状态与版本号绑定」是本用例最容易被实现漏掉的约束**，应单独成 feature 并有状态机验收，
  不要混进列表渲染。**但它目前是 `[设计]` 且与原型呈现冲突（见 R7），
  须先拿到人类裁决再开这个 feature**，否则会照着一条未确认的断言写验收。
- **优先级 / 先后依赖**：P0；**3 点**；阶段二 · 迭代 7 · 成果可交付；
  **必须在 `uc-0-1` 固定快照协议之后**，与 UC-10.2 同迭代。
- 对 P0 必做链路优先实现成功态、权限态与数据闭环，异常态不得延期到上线后。

## R12 AI Ready 验收线索

以下行为应可由自动化测试、接口断言或可复现人工步骤验证：

- V1（成功态 · AC1）：在同一项目创建三份报告，`audience` 分别为「客户董事会 / 自己 / 项目经理」，
  清单接口返回 3 条记录，三者 `report_id` 与 `version` 互不相同；修改其中一份不改变另两份的
  `updated_at` 与 `version`。
- V2（成功态 · 字段完整）：清单接口对每行返回
  `audience` `page_count` `source_category_count` `citation_count` `missing_block_count`
  `status` `version` 七个字段，全部非 null；`status` ∈ `{draft, completed, published}`。
- V3（成功态 · AC2）：对 `status=published` 的 vN 报告发起编辑，接口返回新版本号 `v(N+1)` 且
  `status=draft`；再次读取 vN，内容字节与发布时一致。
- V4（**[待确认]** · 状态×版本号）：尝试构造 `status` 非空而 `version` 为 null 的报告记录，
  接口返回拒绝；尝试把同一 `report_id@vN` 同时置为 `draft` 与 `published`，接口返回拒绝。
  ⚠ **本条建立在 R7「状态与版本号绑定」这条 `[设计]` 断言之上，而该断言与原型列表冲突**
  （原型「已完成 昨天」「已发布 前天」两行不带 vN）。
  若人类裁定沿用原型呈现（非草稿态可不显示版本号），则 V4 的第一句断言必须撤回，
  只保留第二句（同一版本号不得同时处于两种状态）。**由人类裁决，实现者不得自行选择。**
- V5（硬约束 · 已发布不可删）：对 `status=published` 的报告调用删除接口，返回拒绝，
  错误信息指向「请先停止分享」；对 `draft` 报告调用删除接口成功。
- V6（一致性 · AC3）：对同一报告分别读取清单接口的 `missing_block_count` 与 UC-10.3 的缺料清单，
  两者条数相等。
- V7（权限态）：逐一使用 引导师、项目经理、组长、组员、观察者、客户、未授权用户调用清单接口；
  客户与观察者只返回 `status=published` 的报告，草稿报告返回 404 而非 403。
- V8（空态）：新项目调用清单接口返回空数组，界面显示空态与 `[＋ 新建报告]`，不返回示例报告。
- V9（依赖失败）：模拟聚合统计服务不可用，清单仍返回行与 `[打开]` 可用，
  三个计数字段返回 `null` 并在界面显示「统计不可用」，**不返回 0**。
- V10（并发态）：两名用户同时对同一报告升版，只产生一个新版本号，另一方收到版本已变化提示。
- V11（审计态）：新建、改名、删除、升版、发布五类事件均可按操作者、时间、报告 ID 检索；
  越权尝试也有安全审计记录。
