## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-13.3 / 行动项与责任人
- **Actor**：**引导师**、**项目经理**、**行动项负责人（必须是人）**、
  **agent 执行者**（如 `SC` Scout、`LG` Ledger——只执行，不担责）
- **目标**：[原型] 项目散场之后，每一条"下一步该干什么"都必须落到**一个具体的人**头上，
  带**截止日**与**完成态**，并汇进项目内看板持续被跟踪，而不是停在纪要里。
- **本用例结果**：[原型]「**行动项跟踪 · 11 项**」中每条行动项都有**责任人 + 截止日 + 完成态**；
  条目汇入 11-board 项目内看板并带来源徽标，状态在两侧任一处改动都回写到另一侧；
  成果沉淀首页的「成果去向：决策记录 3 ｜ 新增洞察 14 ｜ **行动项 11**」如实反映。
- **系统边界**：行动项创建与来源关联、**责任人（人）与执行者（agent）两个独立字段**、
  截止日与完成态、到期提醒与升级、与 11-board 项目内看板的双向同步、成果去向汇总。
- **核心数据对象**：行动项、**负责人（人）**、**执行者（agent，可空）**、截止日、完成态、
  来源徽标（现场 / 决策树 / 会前任务 / 报告缺料 / 转写 / 研究）、看板卡片映射、提醒与升级记录。

## R2 前置条件 / 触发条件

- **前置条件**：
  - 用户已建立可校验的正式身份，且拥有目标项目的访问权。
  - [原型] 项目成员名单存在——**责任人只能从真实的人里选**（组织成员或现场实名名单）。
  - [设计] 若行动项要挂 agent 执行者，该 agent 已在本项目可用（Agent 编排/Skill 绑定已生效）。
  - 依赖能力（11-board 项目内看板、通知）可用，或界面能明确显示其不可用状态。
- **触发条件**：
  - [原型] **决策产生后续动作**——UC-13.1 的已签决策落地为一条或多条行动项。
  - [原型] Ava 整理项目时生成行动项（「行动项与责任人均已生成」，见 UC-13.2 的 AI 整理条）；
    [D-27] AI 生成的卡**一律落草稿/收件箱态**，须人接受并**指定人类责任人**后才生效。
  - [原型] 用户进入 `项目 → [进入项目] → 成果沉淀 → 行动项`（子标签徽标「行动项 3/11」）。
  - [原型] 在项目内看板 `项目 → 待办` 侧新建或改动卡片，反向同步到本流程。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

1. **系统处理**：从已签决策、现场行动、报告缺料等来源汇集候选行动项。**系统响应**：为每条生成
   条目并挂**来源徽标**（【现场】/【决策树】/【会前任务】/【报告缺料】/【转写】/【研究】），
   保留可回跳的来源链接；AI 生成的条目标记为机器产出且**未指定人类责任人前不生效**。
2. **引导师/项目经理操作**：为每条行动项**指定责任人（人）与截止日**。**系统响应**：
   校验责任人是**真实的人**（不接受 agent 标识，见 R7 硬约束）、截止日不早于当天；
   写入后条目进入「**行动项跟踪 · 11 项**」列表，形如：
   - `核实收购标的资质可转让性` —— 执行者 **SC**（Scout）· 截止 **7/28**
   - `三路径现金流对比模型` —— 执行者 **LG**（Ledger）· 截止 **7/30**
   - `约访 2 家本地 EPC 负责人` —— 责任人 **林**（林可）· 截止 **8/04**
   - `✓ 整理欧洲工商储项目库` —— 执行者 **SC** · **完成**
3. **用户操作**：给某条行动项挂 **agent 执行者**（可选）。**系统响应**：写入**独立的「执行者」字段**，
   与责任人字段并存；界面同时显示两者，**不得用执行者顶替责任人显示**。
   [D-39] agent 只拿行动权、不承担验收，**不能作为责任人被追责**。
4. **系统处理**：把行动项汇入 **11-board 项目内看板**。**系统响应**：在项目内看板（四列：
   待办 / 进行中 / 待复核 / 已完成）生成对应卡片，卡片带来源徽标（原型实例
   `[现场]`、`[决策树]`），并显示责任人与执行者（原型卡片实例
   「[决策树] 今天15:00 查三国资质转移条文，判定收购分支存亡 **SC·Scout·研究模块**」）。
5. **用户操作**：在**任一侧**改状态（行动项列表勾完成，或看板拖动卡片）。**系统响应**：
   状态**双向同步**并**回写原处**（原型底注：「卡片来源自动同步：会前任务、现场行动项、
   报告缺料、决策的后续动作。**状态改了会回写到原处**。」），两侧计数同时刷新。
6. **系统处理**：截止日临近或逾期且状态未动时提醒责任人；持续未动升级提醒给项目经理/引导师。
   **系统响应**：记录触发原因，按幂等条件避免重复轰炸，向有权用户反馈结果；
   看板侧同步显示「逾期 1 · 今天到期 2」。
7. **系统收口**：刷新**成果去向汇总**——「决策记录 **3** ｜ 新增洞察 **14** ｜ **行动项 11**」，
   与**假设状态**「已验证 **5** ｜ 待验证 **9** ｜ 已推翻 **3**」；
   刷新子标签徽标「行动项 **3/11**」（已完成/总数），校验 AC1「行动项完成率在项目概览可见」；
   把创建、指派、改期、完成、升级事件写入审计。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[原型] **纯 agent 执行的行动项**——工作由 agent 跑（如 Scout 查条文、Ledger 建模型），
    仍必须指定一位**人类责任人**对结果负责；agent 只写入「执行者」字段。
  - A2：[D-27] **AI 建议的行动项**——一律落草稿/收件箱态，须人接受；接受时**必须补齐人类责任人**，
    否则不能生效。
  - A3：[设计] **责任人变更**——转派须保留原责任人与转派时间的痕迹，不得静默替换。
  - A4：[原型/补全] 尚无行动项时展示真实空态、原因与下一步入口，不生成示例数据冒充真实结果；
    不得丢失当前上下文。
- **异常流程**：
  - E1：[文档要求 · 原型确认缺失] **无责任人的动作不允许保存**——责任人为空即拒绝写入，
    失败不得被呈现为成功。**该校验的界面在原型中不存在**（行动项屏只有只读列表，
    无新建/编辑表单），要求保留但需补原型，见 R7。
  - E2：[D-39 硬约束] **把 agent 填进责任人字段**——请求被拒绝，错误信息明确「负责人必须是人，
    agent 请填执行者字段」；服务端校验，不依赖前端下拉限制。
  - E3：[设计] **无截止日**——截止日为空时拒绝保存（或按项目配置落"待定"并进入必须补齐的提醒队列，
    见 R10 待确认）；不得产生永不到期的行动项。
  - E4：[设计] **双向同步冲突**——行动项侧与看板侧同时改状态时不得静默覆盖；
    提示状态已变化并给出两侧当前值供人裁决。
  - E5：[设计] **来源已失效**——行动项来源的决策被更正、或依据证据被撤回时，
    **不自动关闭行动项**，在卡片上标注「来源已变更」并通知责任人复核（对齐 D-19）。
  - E6：[设计] 请求超时、网络中断或看板服务不可用时，保留用户当前输入与最后成功数据，
    明确失败原因并提供安全重试；同步失败必须显式提示，不得伪装"已同步"。
  - E7：[设计] 权限在操作过程中被撤回时立即终止后续写操作；已完成步骤按审计规则保留，
    未提交输入留在本地草稿并提示重新授权。

## R5 权限与可见性

- **引导师 / 项目经理**：可查看全场 11 项行动项，创建、指派责任人、挂执行者、改期、关闭。
- **组长**：可查看本组相关行动项，创建本组行动项并在本组成员内指派；不可跨组指派。
- **组员 / 行动项负责人**：可查看指派给自己的行动项并更新其状态；不可改责任人与截止日
  （[设计] 改期需项目经理或引导师确认）。
- **agent 执行者**：**没有任何验收权与状态终结权**——agent 可推进执行、写入进展，
  但「完成」必须由人确认（对齐「AI 只拿行动权、不承担验收」）。
- **观察者**：[原型] **只读**——仅可见已发布内容中包含的行动项摘要；
  不可见责任人的私有备注、私聊来源与未发布行动项。
- **未登录、链接失效或未列出的角色**：默认无权限；接口不得返回越权数据，不能只依赖前端隐藏。

## R7 业务规则（不随具体实现变化的硬性约束）

### 【D-39】负责人恒为人，agent 记在独立的「执行者」字段

- **行动项/待办卡的负责人字段只接受人**（组织成员或现场实名名单中的自然人）；
  任何把 agent 写入责任人字段的请求必须在**服务端**被拒绝。
- **agent 记在独立的「执行者」字段**。原型行动项里的 **`SC`（Scout）**、**`LG`（Ledger）**
  是 **agent 执行者**，其**负责人仍必须是具体的人**；界面同时展示两者，
  **执行者不得顶替责任人显示**，导出与接口同理。
- 与「**AI 只拿行动权、不承担验收**」一致——**AI 不能作为责任人被追责**；
  行动项的「完成」必须由人确认，agent 无状态终结权。
- [D-27] AI 生成的行动项一律落草稿/收件箱态；接受时必须补齐人类责任人才生效。

### 其它硬约束

- **[文档要求 · 原型确认缺失] 无责任人的动作不允许保存**；
  [设计] 无截止日的行动项同样不得进入正式跟踪列表。
  ⚠ **口径更正**：这条来自 `Backlog Use Case.html` 的 UC-13.3，**不是原型行为**。
  `proto-05-deep-layer.md`「行动项」屏**已被完整抽取**，只有一张 11 项的只读跟踪列表
  （`核实收购标的资质可转让性 SC 7/28`…），**没有新建/编辑表单，因而无从观察必填校验**——
  属**已探明区域内确认缺失**（校验界面不存在），**要求本身保留**，实现前需补原型。
- **[文档要求 · 原型确认缺失] 到期未动升级提醒给项目经理**：同上，来自文档而非原型。
  `proto-05` 行动项屏**没有**任何提醒、升级或催办入口；
  `proto-02` 的看板屏亦无（与 UC-11.4 R8 的判定一致）。**要求保留**，界面需补画。
  ⚠ 与之对照，本模块中确属「**未探明**」的是 `[审阅并交付]` 之后的逐项验收清单屏
  （UC-13.2 R10）——两种措辞不得混用。
- [原型] **状态改了会回写到原处**——行动项与 11-board 项目内看板是**同一条数据的两个视图**，
  不是两份副本；任一侧的状态变更必须回写另一侧。
- **来源徽标的作用域必须拆开写，两个视图不同**（此前一句话通标 `[原型]`，与本文 R8 直接冲突）：
  - [原型] **项目内待办看板的卡片带来源徽标**——六个取值
    `现场 / 会前任务 / 决策树 / 报告缺料 / 转写 / 研究`（proto-05 逐项列出并有八条实例）。
  - [设计] **「行动项跟踪 · 11 项」列表的每行也带来源徽标**——
    ⚠ **原型确认缺失**：该列表已完整抽取，每行**只有四要素**
    （事项 / 执行者或责任人缩写 / 截止日 / 完成勾），**没有来源徽标**（见本文 R8）。
  - [设计] **可回跳来源**——「回跳」在十份档案中无任何界面证据，属设计推论。
- [设计] 责任人转派保留原责任人痕迹，不得静默替换。
- [Backlog] AC1：行动项完成率在项目概览可见（Backlog UC-13.3 `ac` 原文；
  [原型] 子标签徽标「行动项 3/11」可佐证）。
- 所有权限判断必须在服务端执行；隐藏入口只是界面表现，不构成安全控制。
- 创建、指派、转派、改期、完成、升级、同步回写都必须记录审计事件，并显示动作影响范围。

## R9 非功能约束

- **性能/规模预期**：
  - [设计] 普通读取与本地校验应在 1 秒内给出可感知反馈；超过 1 秒显示加载状态，超过 10 秒的任务转为可离开页面的后台任务。
  - [设计] 行动项与看板的双向同步应在 2 秒内在另一侧可见；超时须显示"同步中"而非直接显示新状态。
  - [设计] 列表与审计记录必须分页或增量加载，禁止一次加载整个项目历史。
- **安全/隐私/合规**：
  - 最小权限、组织/项目/小组隔离、传输与静态加密、敏感字段脱敏、导出与 AI 读取留痕。
  - 原始材料、录音、转写、私聊、个人身份与客户数据按授权和留存策略处理。
- **兼容与降级要求**：
  - 响应式 Web；桌面端提供完整能力，移动端保证加入、查看、输入、投票/确认等现场关键动作。
  - WebSocket/实时通道不可用时降级为轮询并显示“非实时”；断网允许保留未提交输入，但不得伪装已同步。

- **[待确认]** 责任人是否允许多人（共同负责）——原型只出现单人缩写。
- **[待确认]** 现场实名名单中的人（不建账号）能否作为责任人，以及其通知触达方式（对齐 D-01）。
- **[已裁决 O-33]** 通知平面**单点定义在 `.harness/instructions/` 的通知规范**，各 UC 只引用不重复定义。默认：产品内通知**必选**；邮件**默认开启可关**；短信仅用于现场进场验证码；免打扰**默认关闭**（B 端工具，静默会误事）；到期提醒 **09:00 用户时区**；催办冷却 **4 小时**；组员**可以**催同组同伴；**「今天」一律按用户时区**

- **[设计] 架构对齐 · Context Engine**（`docs/architecture/context-engine.md`，2026-07-28 定稿）：
  - **AI 取上下文只能通过 Context API 领取 Context Pack**——任何 agent、副驾驶或生成动作
    都不得绕过服务平面直查 `claims` / `segments` / `artifact_versions` 等库表。
    绕过即丢失 `permissionDecisionId` 与引用锚点，`uc-14-6`「AI 读到了什么」将不可重放。
  - **编排边界**：**LangGraph 只用于深度研究、人工确认（HITL）与多阶段生成**；
    文件摄取、批量导入、定时与重试一律走**持久任务系统**（MVP 为 PG outbox + job table）。
    LangGraph 不得被当作通用任务队列；HITL 用动态 `interrupt()`，节点恢复时副作用必须幂等。
  - **权限**：**租户与项目隔离在 PostgreSQL RLS 层强制**，应用连接使用受 RLS 约束的
    **非 owner** 角色（PG 中表 owner 默认不受 RLS 限制）。本文 R5 的权限判定与 R12 的
    越权断言是**第二道**防线，不是唯一防线。Artifact 权限必须传播到 Segment、embedding、
    图边、缓存与 Context Pack；交集生成内容取所有来源权限的**最严格**结果。

## R12 AI Ready 验收线索

以下行为应可由自动化测试、接口断言或可复现人工步骤验证：

- V1（成功态 · AC1）：行动项列表接口返回 `total=11` 与 `done` 计数，项目概览/子标签徽标显示
  `3/11`；每条返回 `owner`（人）、`due_date`、`status` 三字段且非空。
- V2（D-39 核心）：用 **agent 标识**（如 Scout 的 agent id）调用创建/更新行动项接口并把它填入
  `owner` 字段，**返回拒绝**，错误信息指向「负责人必须是人」；服务端拒绝，绕过前端直接调用同样被拒。
- V3（D-39 双字段）：创建一条 `owner=周宁`、`executor=SC(Scout)` 的行动项，读取接口
  **同时返回 owner 与 executor 两个独立字段**；对全库做断言：**不存在任何 `owner` 指向 agent 的记录**。
- V4（AI 不担验收）：以 agent 身份调用「把行动项标记为完成」接口返回拒绝；
  由 `owner` 本人调用同一接口成功。
- V5（必填校验）：`owner` 为空时创建接口返回拒绝并指明缺失字段；`due_date` 缺失按 R7/R10 的
  定稿口径拒绝或落"待定"，两种结果都不得产出"看似已保存"的正式记录。
- V6（双向同步 · 回写）：在行动项侧把一条置为完成，2 秒内看板侧对应卡片进入「已完成」列；
  反向在看板侧拖动卡片改状态，行动项侧完成态同步变化；两侧计数同时更新。
- V7（来源徽标）：看板卡片接口对每张由行动项汇入的卡返回 `source ∈ {现场, 会前任务, 决策树,
  报告缺料, 转写, 研究}` 且带可回跳的来源 ID；点击可打开原来源。
- V8（成果去向汇总）：成果沉淀首页接口返回 `decisions=3`、`insights=14`、`actions=11`，
  以及假设状态 `verified=5`、`pending=9`、`refuted=3`，数值与各自明细列表条数一致。
- V9（AI 建卡 · D-27）：AI 生成的行动项创建后 `status=draft/inbox` 且 `owner` 为空；
  未补人类责任人前调用"接受"接口返回拒绝。
- V10（权限态）：逐一使用 引导师、项目经理、组长、组员/负责人、观察者、未授权用户访问；
  组长接口不返回别组行动项；组员不能修改 `owner` 与 `due_date`；观察者只读已发布摘要。
- V11（空态）：尚无行动项时显示真实空态与下一步，不生成伪数据。
- V12（依赖失败）：模拟看板同步不可用，界面显示"同步失败/同步中"并保留输入，
  **不显示为已同步**，可安全重试。
- V13（并发态）：两侧同时改同一条的状态时不静默覆盖，提示状态已变化并可识别最终值。
- V14（审计态）：创建、指派、转派、改期、完成、升级、同步回写七类事件可按操作者、时间、对象检索；
  转派事件保留原责任人；越权尝试也有安全审计记录。
