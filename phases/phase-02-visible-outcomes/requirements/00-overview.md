## 一、本阶段目标与为什么是这个顺序

**一句话**：把 phase-01 采集进来的材料**变成看得见、拿得走、签得了字的东西**——
知识图谱与决策树、洞察报告、待办看板、问卷与投票、成果交付验收。

**为什么排在 phase-01 之后而不是并行**：本阶段的每一个屏都是**投影**，不是数据源。
- 图谱的节点来自访谈 / 画布 / 对话的 Claim；报告的每一段必须挂得上 Segment；
  看板的卡来自 AI 从材料里读出的行动项；交付物必须绑定不可变快照。
- 若在没有真实材料的情况下先做这几个屏，就只能拿 mock 数据验收——
  而本阶段最关键的三条业务规则（「没有数据不能生成真实结论」「验收是引用资格的闸门」
  「引用必须指向不可变快照」）**恰恰只有在真材料上才可验证**。

**阶段内的顺序逻辑**：先立**图**（证据结构）→ 再出**成果**（报告与交付）→ 再补**采集与筛选**（问卷、看板筛选、P1 项）。

4. **`10-report/uc-10-5`（证据撤回与失效标注）依赖 22-files 的删除传播**：
   六类级联失效中「报告段落标记」这一类的接口由本 UC 提供，
   但触发方在 phase-1 的 `uc-22-4`。**接口须先于 22.4 上线**（见 22-files 索引第七节风险 2）。
5. **`12-survey` 的物化必须走 22-files 的摄取链路**：`responses.csv` + `schema.json`，
   且**必须保留题号 ↔ 报告章节双向映射所需字段**，否则 `uc-12-3` 交叉分析与
   `uc-10-2` 报告引用对不上。

## 四、口径说明（给 requirement-author 的读法约定）

### 4.1 四标记

| 标记 | 含义 | 生成 feature 时怎么处理 |
|---|---|---|
| `[原型]` | `WorkspaceX Standalone.html` **运行态实际存在**的行为，有界面可查（依据 `proto-01`…`proto-10` 抽取档案） | 可直接落 `user_visible_behavior`；本阶段 `10-report` 四屏与 `11-board` 六视图属此类，密度最高 |
| `[Backlog]` | `Backlog Use Case.html` 的**文档要求**，原型未必实现 | 可落 feature，UI 部分**须先补画**；`verification` 只写 API / 逻辑断言 |
| `[设计]` | 依据前两者反推补全，**需人类确认** | 落 feature 时标注待确认；`has_ui` 阶段进不了 `new-sprint` |
| `[待确认]` | 不应由实现者决定（阈值 / 权限边界 / 合规口径） | **不得自行取默认值**。查 `DECISIONS-OPEN.md` 对应 O-nn 取已填裁决；无对应则挂阻塞 |

### 4.2 缺失三态（成本差一个数量级，务必区分）

| 状态 | 含义 | 补齐方式与成本 | 本阶段典型 |
|---|---|---|---|
| **未探明** | 原型档案**尚未点进那个屏** | **补抽取**。低成本，**不占人类裁决名额**（`DECISIONS-OPEN.md` 附录 B） | `[审阅并交付]` 之后的验收清单、组长 `[提交本组产出]` 的提交表单（`uc-13-2`）；全局看板视图的 `scope` 切换器（`uc-11-3`） |
| **原型待补** | 主屏存在，但按钮已渲染、目标屏未见，或下钻层缺失 | **补接线 / 局部补画**。中等成本 | `10-report` 的三处下钻（D-23：引用展开层 / 版本历史 / 导出配置面板） |
| **原型确认缺失** | **枚举完毕后确认不存在** | **补画整屏 + 产品/设计确认**。高成本，**卡 `ui-signoff`** | `12-survey` 全部 4 份；`09-kg` 3/5；`11-board` 3/7 |

> **硬规则**（`DECISIONS-FINAL.md` 通用规则第 2 条）：**不得把「未探明」写成「原型没做」**。
> 本阶段尤其容易踩：`10-report` 与 `11-board` 主屏都很完整，缺的多是下钻层，
> 写成「确认缺失」会把 D-23「四屏已存在，不必补画」的裁决推翻。

### 4.3 本阶段必须遵守的术语与状态约定

- **D-03a 三字段消歧**：`09-kg` 同时引用 **`agenda_segment_id`**（现场环节）与
  **`method_stage_id`**（9 个方法环节 PESTEL→PRD，`uc-9-4` 推演流水线视图的横轴）。
  **这两者不是一回事，不得共用一个字段名。** `13-deliv` 引用 **`design_facet_id`** 第 14 项「输出物」。
- **D-26 看板五态 + 视图投影**：状态 enum 恒为 `inbox / todo / in_progress / review / done`（**五态**）；
  项目内视图默认**折叠** `inbox` 列（以筛选项或徽标呈现，**不得丢卡**），全局视图五列全显。
  ⚠ `uc-11-1` 标题写「四列看板」，**文档口径不必改**（D-26 明示）——
  `requirement-author` 须按「五态 enum + 四列投影」实现，不要按标题字面做四个状态。
- **D-39 负责人恒为人**：待办卡的「负责人」字段只能是人，agent 记在独立的「**执行者**」字段。
- **D-40 保留意见**：对客户可见，但**去掉署名**（显示「1 条保留意见」，不显示提出人）。
- **D-19 证据撤回**：对内可见；**对外不自动改写**，需人工确认后替换。
  ⚠ 「静默」在此指**不向客户主动推送变更提示**，**不是**指系统可自行改写内容——后者被明确禁止
  （见 `uc-10-5` R7「两个方向都禁止静默」）。

### 5.2 已知的重复计点风险（务必只计一次）

1. 🔴 **跨阶段**：D-13 前置的 `UC-17.2` 最小切片（+8 点，在 phase-1）与
   `22-files/uc-22-4`（8 点，在 phase-1）是**同一批实现**。本阶段的
   `10-report/uc-10-5`（8 点）只提供**报告段落标失效的接口与界面**，
   **不重复实现待删除队列与级联失效引擎**——那部分已计在 phase-1。切分时把 10-5 的范围收敛到
   「接收失效事件 → 标注段落 → 对外替换走人工确认流」。
2. `09-kg/uc-9-1`（8 点）与 `07-canvas/uc-7-4`（phase-1，5 点）是**同一条写入通道的两端**：
   7.4 负责画布侧的提取与投递，9.1 负责图侧的落库与去重。接口只定义一次。
3. `13-deliv/uc-13-5` 快照绑定（3 点）与 `00-core/uc-0-1` 的固定快照（phase-0，含在 21 点内）：
   **机制在 phase-0，业务规则在 13-5**。不要在 13-5 再建一套快照表。
4. `11-board/uc-11-3`（筛选与我的待办，5 点）与 `uc-11-5`（我的今天，5 点）：
   D-29 已裁定「我的今天」**独立成 UC**（四语义分区：等我判断 / 今天该我推进 /
   AI 正在替我跑 / 下一步轮到别人），与 11.3 的看板筛选**并存**——
   两者共用同一套查询层，但**语义分区逻辑只在 11.5 实现一次**。
5. `12-survey/uc-12-2`（发放与回收）与 `uc-12-4`（现场快速投票）共用同一套发放/回收管道，
   12.4 只是低延迟的现场变体，不建第二套。

### 5.3 `verification` 优先级（D-35：A + B 并行）

```
① round-trip / 纯函数断言        ← 最优先
② API 断言（含 SQL / RLS 断言）
③ UI 断言                        ← 最后手段
```

本阶段最佳落点：
- **`13-deliv/uc-13-5`**：快照 round-trip——绑定 v2 → 修改工作版本 → 断言已发布内容仍解析到 v2 的内容哈希。**纯函数级，最强验收**。
- **`10-report/uc-10-5`**：撤回一条证据 → 断言引用它的报告段落 `invalidated=true`（API），
  且**对外副本未被改写**（API 比对哈希）。
- **`09-kg/uc-9-1`**：「验收后才成为可引用证据」——未验收的产出物尝试被 Claim 引用应被**服务端拒绝**（API 断言，非视觉标记）。
- **`12-survey/uc-12-3`**：「样本 < 8 标不可推断」是纯函数断言（对照 D-16 的最小聚合样本量）。
- **`11-board`**：五态转移矩阵（O-27 已裁决合法转移矩阵）→ 纯函数状态机断言；
  R1/R2/R3 自动推导（D-28：外发邮件恒 R3、读公开资料恒 R1）→ 纯函数断言。
- **`10-report/uc-10-3` 缺料提示**：「没有数据时不能生成真实结论，只能生成框架或数据需求说明」→
  给空材料集断言输出类型为「框架/数据需求说明」（API 断言）。

> ⚠ **原型零 `data-testid`**。UI 断言在 `uiux-standards` 的 `data-testid` 命名规范落地前
> **写不出稳定选择器**。特别提醒：D-24 指定「报告工作台的来源角标 + 未挂来源标灰」
> 作为 phase-3 `uc-14-6` 的验收锚点——**这两个元素的 testid 必须在本阶段就按规范命名并固定下来**，
> 否则 phase-3 的验收会连带失效。
