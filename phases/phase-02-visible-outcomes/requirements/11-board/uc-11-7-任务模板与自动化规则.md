## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-11.7 / 任务模板与自动化规则
- **Actor**：**组织管理员 / 项目负责人**（模板与规则的维护者，恒为人）、
  **引导师**（在项目内套用模板）、**系统规则引擎**（自动化规则的执行方）、
  **agent**（规则产出的草稿卡的建议生成方，**不是接受方**）。
- **目标**：让一类任务**生下来就带齐完成标准、权限包、审批点、默认执行者、预算上限**，
  不靠每次手填；并让「什么时候该生出这条任务」由**明示的规则**决定，
  规则产出的卡**同样受 D-27 的 inbox 门禁约束**。
- **本用例结果**：维护者可定义任务模板与自动化规则；
  套用模板建卡时五项默认值自动写入；
  三条自动化规则按各自触发条件产出卡（或只提醒），产出的卡带来源徽标与规则引用可追溯。
- **系统边界**：任务模板的定义与套用、模板对风险等级的覆盖、
  自动化规则的定义与触发、规则产出卡的 inbox 门禁与可追溯性、预算上限与降级行为。
  **不含**风险推导规则表本身（属 UC-11.2 的服务端规则表）、
  不含权限包的判定与授权流（属 UC-11.6）、不含知识五态机（属 14-brain）。
- **核心数据对象**：
  - **任务模板 `task_template`**：`name`、**`completion_criteria`（完成标准）**、
    **`permission_pack`（权限包）**、**`approval_points`（审批点）**、
    **`default_executor`（默认执行者）**、**`budget_cap`（预算上限：token 或时长）**、
    `risk_level_override`（可选，D-28 的唯一合法覆盖入口）、`usage_count`。
  - **自动化规则 `automation_rule`**：`trigger`（触发条件）、`action`（建卡 / 仅提醒）、
    `target`（派给谁 / 提醒谁）、`enabled`、`template_ref`（产出卡套用哪个模板）。
  - **规则产出溯源**：产出卡上必须携带 `rule_ref`（触发它的规则）+
    `trigger_data_ref`（触发它的那条数据）+ 来源徽标（六类之一）。
  - **预算消耗态**：已耗 / 上限 / 是否已达阈值 / 降级记录。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

### 甲、任务模板

1. **维护者定义模板**：一个模板必须声明**五项**：
   **完成标准 / 权限包 / 审批点 / 默认执行者 / 预算上限**（token 或时长）。
   [原型] 实例：
   - `资质尽调（默认 Scout）`：**完成标准 12 项** · **权限包：项目文件＋组织清单 v3** ·
     **R3 前必须人批准** · **预算 ≤800k**
   - `客户邮件外发（R3 强制审批）`：「**AI 只能起草，发送动作永远需要人点确认**」
   - `项目环节产出（按角色拆）`：一个环节自动生成引导师／组长／组员三套任务，环节结束自动归档
   **系统响应**：五项缺任一项不允许保存模板——**不允许存在「什么都不带」的模板**，
   那等于没有模板。

2. **维护者可在模板上覆盖风险等级 [D-28]**：模板可声明 `risk_level_override`，
   覆盖 UC-11.2 按操作类型自动推导出的 R1/R2/R3。
   **系统响应**：这是**唯一合法的覆盖入口**——
   接口层面拒绝来自建卡请求、前端、agent 的任何风险等级指定；
   覆盖后**同时保留推导值与覆盖值**，审计中两者都可查。
   [原型印证] `客户邮件外发（R3 强制审批）`即典型的模板级强制升档。

3. **用户套用模板建卡**：建卡时选择模板，系统把五项写入新任务卡。
   **系统响应 · 硬约束**：写入的是**默认值**——
   **在具体任务上修改这些值不回写模板**。
   [原型印证（蓝本同源语义）]：「写入的是默认值。引导师在那一场里改，**不会回写蓝本**；
   要沉淀就在复盘里『提交回蓝本』。」
   模板的修改只影响**此后**套用它的新任务，**已建的卡锁在自己套用时的那份值上**。

4. **系统记录套用关系**：卡上记录 `template_ref` 与套用时的模板版本，
   便于日后判断「这张卡当时带的是哪套默认值」。

### 乙、自动化规则（三条，逐条定义）

5. **规则一：证据过期 → 自动建「复核任务」** [原型 + D-33]
   - **触发**：组织层知识条目到期，五态机把它转为「**待复核**」态（D-33：
     过期知识转「待复核」，**仍在检索范围内**，引用时提示已过期，但**不参与定题强度计算**）。
   - **动作**：给该条目的**复核负责人**建一条复核任务，[原型] **默认派 Scout 先取新数据**。
   - **系统响应**：这条卡由规则创建 → `created_by_kind = rule` →
     **按 D-27 落 `inbox` 草稿态**（见第 8 步）。
   - [原型] 「证据过期 → 建任务复核：组织层条目转「待复核」时，给复核负责人建一条任务，
     默认派 Scout 先取新数据」。

6. **规则二：致命假设未验证 → 只提醒，不自动派活** [原型 · 硬约束]
   - **触发**：距关键节点（如客户汇报）N 天，仍有**致命假设**未验证。
   - **动作**：**只向项目负责人发提醒，不建任务、不派 agent**。
   - **硬约束**：**提醒而非自动派活**。理由是致命假设的验证路径需要人判断，
     自动派活会把「该不该验、怎么验」这个判断偷偷替人做掉。
   - [原型原文] 「致命假设未验证 → 提醒：距客户汇报 3 天仍有致命假设未验证，
     **提醒项目负责人而不是自动派活**」。

7. **规则三：高影响任务不许静默创建** [原型 · 硬约束 · 对齐 D-27]
   - **触发**：任何自动化路径（规则、agent、对话转任务）产生高影响任务。
   - **动作**：**必须走 D-27 的 inbox 草稿态 + 人接受**，不得直接进工作列。
   - [原型原文] 「高影响任务不许静默创建：**AI 只能生成草稿进收件箱；
     R3 以上永远需要人接受后才成立**」。

### 丙、产出卡的共同约束

8. **系统对规则产出的卡施加 inbox 门禁 [D-27]**：
   `created_by_kind = rule` 的卡与 agent 建的卡**同等对待**——
   初始 `status` **恒为 `inbox`**；R1 可自动接受，R2/R3 必须人显式接受。
   **规则不是绕过 D-27 的后门。**

9. **系统写入产出卡的可追溯信息**：规则产出的卡必须带
   ① **来源徽标**（六类之一，如证据过期复核任务归 `研究` 或 `决策树`，按触发源判定）；
   ② **来源引用**（触发它的那条数据：哪个知识条目、哪条致命假设、版本与时间）；
   ③ **规则引用** `rule_ref`——**可追溯到是哪条规则、因为哪条数据把它生出来的**。
   **系统响应**：三者缺一不允许建卡（与 UC-11.2 的「没有来源就不建卡」同一条纪律）。

10. **系统处理预算上限**：任务执行中消耗（token 或时长）逼近模板声明的 `budget_cap` 时——
    [蓝本对齐] **达 90% 自动降级到更便宜的模型并在对话里提示，不硬停**
    （蓝本原文：「单场预算 3.5M token，达 90% 自动降级到便宜模型并在对话里提示，**不硬停**
    ——『现场卡住比多花钱贵。』」）。
    **系统响应**：降级动作写入任务执行记录并对负责人可见，不静默发生。
    **[已裁决 O-36 ⑥] 超限（达 100%）时的处置 ＝ 转「等待输入」求追加预算**——
    打 `waiting_input` 标记，向负责人弹「追加 / 改派人工 / 关闭任务」三选一；
    **不硬停、也不无限继续**；未获追加转 `blocked` 并标注未完成部分（详见 R10）。

11. **系统收口**：模板的创建/修改/风险覆盖、规则的启停与每次触发、
    产出卡的创建与接受，全部写审计。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[设计] 不套用任何模板直接建卡时，五项取系统默认——
    **权限包为空集**（默认拒绝，见 UC-11.6）、无预算上限则不允许指派 agent 执行。
  - A2：[设计] 模板被停用或删除后，已套用它的卡不受影响（值已写死在卡上），
    但不能再被新卡套用；卡上的 `template_ref` 标为「模板已停用」。
  - A3：[设计] 规则一触发时若该知识条目**没有复核负责人**，
    不建无主的卡，改为提醒项目负责人指定复核人。
  - A4：[设计] 同一触发数据在短时间内多次满足同一规则时按幂等去重，
    只产出一张卡（复用 UC-11.2 的去重键机制）。
- **异常流程**：
  - E1：[设计] 模板保存时五项缺任一项 → 拒绝保存并指明缺哪项，不允许存半成品模板。
  - E2：[设计] 规则触发时目标模板已被删除 → 规则暂停并提醒维护者，
    **不得用一个空模板凑合建卡**。
  - E3：[设计] 规则引擎不可用时，触发事件进入重放队列，恢复后按幂等补建；
    **不得静默丢失触发**。
  - E4：[设计] 有人试图通过规则配置绕过 inbox 门禁（如把产出卡的初始状态配成 `todo`）→
    接口拒绝，该字段不可配置。
  - E5：[设计] 规则产生卡的速率异常（如短时间内数百条）时触发限流并告警，
    避免规则把收件箱刷爆导致人失去审阅能力（这会实质性废掉 D-27 的门禁）。
  - E6：[设计] 预算降级失败（无可降级的更便宜模型）时，任务转「等待输入」请求人决策，
    **不得静默超支、也不得静默停止**。

## R5 权限与可见性

- **组织管理员**：可创建、修改、停用**组织级**任务模板与自动化规则；可查看全部触发记录。
- **项目负责人 / 引导师**：可在项目内套用模板；
  [待确认] 能否创建**项目级**模板（原型未区分组织级与项目级）。
- **组长 / 组员**：可套用模板建卡，**不能修改模板或规则**。
- **agent**：**不能创建、修改或启停任何模板与规则**；
  只能作为模板的 `default_executor` 被指派、作为规则产出卡的建议生成方。
- **观察者**：不可见模板与规则。
- **未登录、链接失效或未列出的角色**：默认无权限；接口不得返回越权数据。
- **风险覆盖权限收紧**：`risk_level_override`（尤其是**降档**，如把推导出的 R3 改成 R1）
  [待确认] 是否需要更高级别的审批——这是绕过安全门禁的潜在路径。

## R6 后置条件 / 不包含

- **正常后置条件**：
  - 每个已保存的模板都带齐五项：完成标准 / 权限包 / 审批点 / 默认执行者 / 预算上限。
  - 套用模板产生的卡带上述五项的默认值副本，且 `template_ref` 已记录。
  - 三条自动化规则各按其定义行为：规则一建卡、规则二**只提醒**、规则三强制走 inbox。
  - 规则产出的卡带来源徽标 + 来源引用 + 规则引用，可追溯到触发规则与触发数据。
  - [原型验收] AC1（**UC-11.7 在 Backlog 中无对应条目，本 AC 出自原型原文**
    「模板决定一类任务生下来就带什么…自动化决定它什么时候被生出来」）：
    模板决定一类任务生下来带什么，自动化决定它什么时候被生出来。
  - [设计验收] AC2：**在任务上修改模板带来的值不回写模板**——
    改完后模板本身的值不变，此后套用该模板的新卡仍取原值。
  - [设计验收] AC3：**模板是风险等级的唯一合法覆盖入口**——
    非模板路径指定风险等级一律被服务端拒绝。
  - [设计验收] AC4：**规则二永不产生任务卡**，只产生提醒。
  - [设计验收] AC5：任何 `created_by_kind = rule` 的卡，创建时 `status` 恒为 `inbox`。
- **失败后置条件**：
  - 不保存缺项的模板；不产生无溯源的规则卡；不静默丢失规则触发；
    不静默超支；失败事件进入可观测日志。
- **不包含**：
  - **风险推导规则表本身**（属 UC-11.2 服务端规则表；本用例只做**覆盖**）。
  - **权限包的判定与授权流**（属 UC-11.6；本用例只写**默认值**）。
  - **知识五态机与「待复核」态的实现**（属 14-brain / D-33；本用例只**消费其事件**）。
  - **致命假设的定义与验证流程**（属 14-brain；本用例只**读其状态发提醒**）。
  - 蓝本级的模板（`蓝本 → 会前任务 / Agent 编排 / Skill 绑定` 属 02-tpl，
    与本用例的任务模板是**不同层级的两种模板**，不得混为一谈）。
  - 复杂规则编排（多条件组合、规则链、自定义 DSL）——本用例只做原型的三条固定规则。

## R7 业务规则（不随具体实现变化的硬性约束）

- **[原型 · 定性] 模板管「带什么」，自动化管「什么时候生出来」**：
  「模板决定一类任务生下来就带什么：完成标准、权限包、审批点、默认执行者。
  自动化决定它什么时候被生出来。」
- **[原型 · 硬约束] 模板必带五项**：
  **完成标准 / 权限包 / 审批点 / 默认执行者 / 预算上限**（token 或时长），缺一不可保存。
- **[D-28 · 硬约束] 模板是风险等级的唯一合法覆盖入口**：
  风险等级由操作类型自动推导（UC-11.2），**只有任务模板可以覆盖**；
  建卡请求、前端、agent 一律不得指定或改写。覆盖后推导值与覆盖值都要留痕。
- **[硬约束] 模板写入的是默认值，在具体任务上修改不回写模板**：
  卡与模板解耦；模板改动只影响此后新建的卡，已建的卡锁在套用时的那份值上。
  （与蓝本「引导师在那一场里改，不会回写蓝本」同构。）
- **[原型 · 规则一] 证据过期 → 自动建「复核任务」**：
  组织层条目转「**待复核**」时（D-33），给复核负责人建复核任务，默认派 Scout 先取新数据。
- **[原型 · 规则二 · 硬约束] 致命假设未验证 → 只提醒，不自动派活**：
  **提醒项目负责人，而不是自动派活**。本规则**永不产生任务卡**——
  该不该验、怎么验，是人的判断，不能被自动化替代。
- **[原型 · 规则三 · 硬约束] 高影响任务不许静默创建**：
  必须走 **D-27** 的 inbox 草稿态 + 人接受；
  「AI 只能生成草稿进收件箱；R3 以上永远需要人接受后才成立」。
  **规则不是绕过 D-27 的后门**——`created_by_kind = rule` 与 `agent` 同等门禁。
- **[硬约束] 规则产出的卡必须可追溯**：带来源徽标（六类之一）+ 来源引用（触发数据 + 版本 + 时间）
  + **规则引用**（是哪条规则生出来的）；三者缺一不建卡。
- **[蓝本对齐] 预算达 90% 自动降级并提示，不硬停**——「现场卡住比多花钱贵」；
  降级动作必须对负责人可见，不静默发生。
- **[原型] 客户邮件外发类模板**：AI 只能起草，**发送动作永远需要人点确认**。
- 模板与规则的变更、每次规则触发都必须写审计。
- 所有门禁在服务端执行；隐藏配置项不构成安全控制。

## R9 非功能约束

- **性能/规模预期**：
  - [设计] 规则触发到卡出现在收件箱应在 1 分钟内（非现场场景，可容忍批处理延迟）。
  - [设计] 规则引擎必须有**限流与告警**：单位时间内某规则产出卡数超阈值即暂停并告警
    （见 E5——刷爆收件箱等于废掉 D-27 的门禁）。
  - [设计] 预算消耗的统计必须近实时，否则 90% 降级阈值形同虚设。
- **安全/隐私/合规**：
  - 模板中的权限包默认值受 UC-11.6 的三层交集约束——
    **模板不能授予超出 MCP 授权范围与 agent 工具白名单的权限**。
  - `risk_level_override` 的**降档**操作是安全敏感动作，必须写审计并可追溯到人。
  - 规则产出卡携带的触发数据引用不得泄露接收人无权访问的内容。
- **兼容与降级要求**：
  - 响应式 Web；模板与规则的编辑主要在桌面端，移动端保证只读查看。
  - 规则引擎不可用时触发事件进队列重放，**不静默丢失**。

## R10 已知约束 / 依赖

- **内部依赖**：
  - **UC-11.1**（任务对象与五态 enum）、**UC-11.2**（inbox 门禁 + 风险推导服务，
    本用例提供其唯一覆盖入口）、**UC-11.6**（权限包结构，模板往里写默认值）。
  - **14-brain**：知识五态机的「**待复核**」态（**D-33**）——规则一的触发源；
    **致命假设**的状态——规则二的触发源。
  - 通知内核（规则二只发提醒）、审计内核。
  - 模型策略与配额（蓝本的「模型策略」「配额与降级」）——预算上限与降级行为的落点。
- **跨模块契约**：
  - 规则一消费 14-brain 发出的「条目转待复核」事件，
    该事件必须携带条目 ID、复核负责人、有效期到期时间。
  - 模板写入的 `permission_pack` 必须使用 UC-11.6 定义的同一套 `scopes` 结构。
  - 产出卡的来源徽标必须取 UC-11.2 的六类封闭枚举，不新增第七类。
- **与蓝本模板的区分（易混淆，必须写清）**：
  **蓝本**（02-tpl）管的是**一场项目的骨架**（16 项设计配置，含「会前任务」「Agent 编排」）；
  **任务模板**（本用例）管的是**一类任务的默认值**。两者是不同层级，
  蓝本可以引用任务模板，但**不得把二者实现成同一张表**。
- **[已裁决 O-36 ⑥] 预算超限（达 100%）的处置**——原问题：硬停 / 继续但每步需人确认 /
  转「等待输入」求追加预算。蓝本只明确了 90% 降级不硬停，**100% 之后未定**。
  **裁决（O-36 ⑥）**：**转「等待输入」求追加预算**。
  达 100% 时任务打上 `waiting_input` 标记（与 UC-11.6 缺权限时同一套中断机制），
  向负责人弹出「预算已用尽，是否追加 N token / 改派人工 / 关闭任务」三选一，
  **不硬停、也不无限继续**。
  理由：**硬停会让现场卡死**（与蓝本「现场卡住比多花钱贵」的取向冲突），
  **无限继续会失控**；转「等待输入」是唯一同时避免两者的处置。
  追加预算的批准**恒为人**（D-39），批准动作与追加额度写审计；
  未获追加时任务转 `blocked` 并显式标注「因预算用尽，Y 部分未完成」，
  **不得伪装成已完成**（与 UC-11.6 R3 第 8 步同一硬约束）。
  三档预算行为完整口径：**90% 自动降级模型并提示（不硬停）→ 100% 转「等待输入」求追加 →
  未获追加则 `blocked`**。
- **[待确认]** 模板是否分组织级与项目级两层；项目负责人能否创建项目级模板。
- **[待确认]** `risk_level_override` 的**降档**是否需要额外审批（安全敏感）。
- **[待确认]** 自动化规则是否允许用户自定义新规则，还是只能启停这三条内置规则。
- **[待确认]** 规则一默认派 Scout——若组织未启用 Scout 或该 agent 被停用时的回退策略。

- **[设计] 架构对齐 · Context Engine**（`docs/architecture/context-engine.md`，2026-07-28 定稿）：
  - **AI 取上下文只能通过 Context API 领取 Context Pack**——任何 agent、副驾驶或生成动作
    都不得绕过服务平面直查 `claims` / `segments` / `artifact_versions` 等库表。
    绕过即丢失 `permissionDecisionId` 与引用锚点，`uc-14-6`「AI 读到了什么」将不可重放。
  - **编排边界**：**LangGraph 只用于深度研究、人工确认（HITL）与多阶段生成**；
    文件摄取、批量导入、定时与重试一律走**持久任务系统**（MVP 为 PG outbox + job table）。
    LangGraph 不得被当作通用任务队列；HITL 用动态 `interrupt()`，节点恢复时副作用必须幂等。
  - **权限**：**租户与项目隔离在 PostgreSQL RLS 层强制**，应用连接使用受 RLS 约束的
    **非 owner** 角色（PG 中表 owner 默认不受 RLS 限制）。本文 R5 的权限判定与 R12 的
    越权断言是**第二道**防线，不是唯一防线。Artifact 权限必须传播到 Segment、embedding、
    图边、缓存与 Context Pack；交集生成内容取所有来源权限的**最严格**结果。
