## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-11.1 / 四列看板与推进
- **Actor**：**项目经理**（组织角色「项目负责人」）、**引导师**、**组长**、**组员**
- **目标**：[原型] 把会前任务、现场行动项、报告缺料、决策后续动作汇到一块看板上，
  用拖动改状态，**状态改了回写到原处**。
- **本用例结果**：用户在 `项目 → [进入项目] → 待办` 打开项目内看板，看到
  `待办 / 进行中 / 待复核 / 已完成` 四列卡片（各带来源徽标、负责人、执行者、到期日），
  拖动卡片改列后来源模块的对应对象状态同步更新。
- **系统边界**：**统一五态 enum 的定义与状态机**、两种视图投影（项目内折叠 inbox / 全局五列全显）、
  卡片渲染与来源徽标、拖动改列、状态双向回写、列计数与底注计数。
  自动汇入见 UC-11.2，筛选见 UC-11.3，到期提醒见 UC-11.4，「我的今天」见 UC-11.5。
- **核心数据对象**：
  - **任务卡**：`id`、`title`、**`status`（enum：`inbox` / `todo` / `in_progress` / `review` / `done`）**、
    `source_kind`（来源徽标六类）、`source_ref`（来源资源 + 版本 + 时间）、
    **`owner`（负责人，恒为人）**、**`executor`（执行者，可为人或 agent）**、
    `due_at`、`scope`（项目 / 组）、`risk_level`（R1/R2/R3，见 UC-11.2）。
  - **视图投影配置**：视图作用域（项目内 / 全局）、该视图下 `inbox` 的呈现方式（折叠 / 独立列）。
  - **回写映射**：任务卡 ↔ 来源对象（会前任务 / 现场行动项 / 报告缺料 / 决策后续动作）的双向绑定。

## R2 前置条件 / 触发条件

- **前置条件**：
  - 用户已建立可校验的正式或临时身份，且拥有目标组织、项目、小组或资源的访问权。
  - 目标资源存在且未被删除/冻结；依赖能力“各模块的任务产生点（图谱、报告、访谈、会前任务）”可用，或界面能明确显示其不可用状态。
  - 若动作涉及个人数据、录音、原始材料或跨范围读取，相应授权与留存策略已生效。
- **触发条件**：
  - [原型] 用户在项目工作台点击标签 `待办 6`（路径 `项目 → [进入项目] → 待办`），进入**项目内视图**。
  - [原型] 或在一级导航点击 `任务 → 项目看板`，进入**全局视图**（五列全显）。
  - 进入时携带当前组织、项目、小组、角色标识；项目内视图额外携带项目 ID 作为过滤域。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

1. **系统渲染列**：按当前视图作用域投影同一份 `status` enum。
   - **项目内视图**：渲染 `待办(todo) / 进行中(in_progress) / 待复核(review) / 已完成(done)` 四列，
     横向滚动不换行；**`inbox` 列默认折叠**，其中的卡以顶部筛选项「收件箱 N」与卡数徽标呈现，
     点击即可展开审阅。[原型] 原型示例：`待办 2 张 → 进行中 2 张 → 待复核 2 张 → 已完成 2 张`。
   - **全局视图**：渲染 `收件箱 / 待开始 / 进行中 / 待验收 / 已完成` 五列全显。
   - 两个视图读同一张任务表、同一个 `status` 字段，**不存在只在某一视图里可见的卡**。
2. **系统渲染卡片**：每张卡显示
   **来源徽标（六类：现场 / 会前任务 / 决策树 / 报告缺料 / 转写 / 研究）** + 到期日 + 标题
   + **负责人（人）** + **执行者**。[原型] 原型实例：
   - `[现场] 今天18:00 追访两家本地 EPC，确认产能与排他条款  高·高琳·第2组`
   - `[决策树] 今天15:00 查三国资质转移条文，判定收购分支存亡  SC·Scout·研究模块`
   - `[报告缺料] 明天 保底条款成本测算·待财务确认折现率  LG·Ledger·测算`
   - 到期着色：[Backlog] **已逾期红、今天到期橙**
    （Backlog UC-11.1 `flow` 原文「卡片显示来源徽标、负责人、到期（逾期红、今天橙）」）。
    [原型] 卡片带到期文字（示例 `[会前任务] **已逾期** 补供应链侧 3 条本地化率约束`、
    底注「逾期 1 · 今天到期 2`」），但**原型是纯文本、未给任何配色**——红/橙是 Backlog 的要求，
    不是原型实况。
   - **[D-39]** `SC·Scout·研究模块`、`LG·Ledger·测算` 中的 agent 渲染在**执行者**位，
     负责人位必须是人；负责人为空的卡不允许进入 `todo` 及其后的任何工作列。
3. **用户操作**：拖动卡片到另一列，或用卡片上的箭头按钮前进/回退一列。
   **系统响应**：服务端按状态机校验该转移是否合法（见 R7）与当前用户是否有权改该卡；
   通过后写入新的 `status`，并**在同一事务内回写来源对象**
   （会前任务 → 完成状态；现场行动项 → 行动项进度；报告缺料 → 缺料补齐标记；决策后续动作 → 动作状态）。
   回写失败时卡片打「未同步」标记并可重试（见 E1），**不得只改本地状态就显示成功**。
4. **系统响应**：改列后**实时重算三处计数**——本视图各列卡数、标签 `待办 N` 的未完成数徽标、
   底注 `逾期 1 · 今天到期 2`；三者必须来自同一次查询结果，不允许各自独立统计。
5. **用户操作**：在任一列点 `[＋ 加一张]` 或右上 `[＋ 新建待办]` 手工建卡。
   **系统响应**：手工建卡直接落该列对应的 `status`（**人建的卡不经 inbox**，与 UC-11.2 的
   AI 建卡路径相反），必填负责人与标题，来源徽标记为手工创建。
6. **系统收口**：写审计事件（操作者、时间、卡 ID、`status` 前后值、回写目标与回写结果），
   并向该卡的负责人与来源模块的订阅者推送变更。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[设计] 某列为空时展示该列的真实空态与 `[＋ 加一张]` 入口，不生成示例卡冒充真实结果。
  - A2：[设计] 项目内视图的折叠 `inbox` 中有卡时，顶部必须显示「收件箱 N」入口且 N > 0；
    **不得因视图折叠而让这些卡无处可达**（防丢卡的界面兜底）。
  - A3：[设计] 卡的负责人不在当前项目成员表内（例如已被移出项目）时，卡仍显示但负责人位标
    「负责人已失效」并要求重新指派，不静默把负责人置空。
- **异常流程**：
  - E1：[原型] 回写来源模块失败时，卡片打「未同步」标记并提供重试；看板侧的 `status` 与来源侧
    不一致的窗口期必须对用户可见，**不得呈现为成功**。
  - E2：[Backlog] `done` 卡片 **7 天后折叠**（Backlog UC-11.1 `edge` 原文「已完成的卡片 7 天后折叠」）；
    [设计] 折叠进「已完成」列的收起区，仍可展开与检索，**不是删除**。
    ⚠ **原型确认缺失**：项目内看板与全局看板均已完整抽取，**「7 天折叠」在十份档案中零命中**
    （唯一的「7 天」是**邀请链接有效期档位**，属另一对象）；折叠交互原型未画。
  - E3：[设计] 请求超时、网络中断或依赖不可用时，保留拖动前的列位置并回滚界面，明确失败原因并可重试；
    禁止界面停在新列而后端未写入。
  - E4：[设计] 两人同时拖同一张卡时按乐观锁拒绝后到者，提示「状态已变为 X」并要求刷新后重试，
    不静默覆盖。
  - E5：[设计] 权限在拖动过程中被撤回时立即终止写操作，卡回到原列并提示重新授权；
    已写入的部分按审计规则保留。
  - E6：[设计] 来源对象被删除时卡片标为「孤立」（见 UC-11.2 A1），此时**允许改状态但不再回写**，
    并在卡上说明回写目标已不存在。

## R5 权限与可见性

- **项目经理 / 引导师**：可见本项目全部卡；可改任意卡状态、可改派负责人与执行者。
- **组长**：可见本组卡 + 分派给自己的卡；可改本组卡状态，不可改别组卡。
- **组员**：可见分派给自己的卡 + 本组共享卡；只能改自己是负责人的卡的状态。
- **观察者**：**不可见待办看板**（见 R7）；观察者视角下该标签不渲染，接口直接拒绝。
- **未登录、链接失效或未列出的角色**：默认无权限；接口不得返回越权数据，不能只依赖前端隐藏。
- 视图投影**不是权限机制**：折叠 `inbox` 只是渲染差异，能否读到某张卡完全由上述角色规则决定。

## R6 后置条件 / 不包含

- **正常后置条件**：
  - 卡的 `status` 更新为五态之一，且来源对象的对应状态已同步更新（或明确标为未同步待重试）。
  - 列计数、标签徽标计数、底注逾期/今天到期计数三者一致。
  - 审计事件已写入（含 `status` 前后值与回写结果）。
  - [Backlog验收] AC1：tab 徽标（`待办 N`）的未完成数与看板列计数实时一致
    （Backlog UC-11.1 `ac` 原文）。
  - [设计验收] AC2：同一批卡在项目内视图与全局视图中**总数相同**——项目内视图折叠 `inbox`
    只影响列的呈现，不影响卡的可达性。
  - [设计验收] AC3：任一卡的 `status` 值恒属于 `inbox / todo / in_progress / review / done`，
    不存在第六个取值，也不存在「项目内专用状态」。
  - [设计验收] AC4：`owner` 字段的取值恒为人的用户 ID；agent 只能出现在 `executor` 字段。
- **失败后置条件**：
  - 不产生「界面已改列但后端未写入」的状态；回写失败必须可见可重试；失败事件进入可观测日志。
- **不包含**：
  - **卡的自动汇入与 AI 建卡**（属 UC-11.2）、**筛选口径**（属 UC-11.3）、
    **到期提醒与催办**（属 UC-11.4）、**「我的今天」语义分区视图**（属 UC-11.5）、
    **任务权限包与授权流**（属 UC-11.6）、**任务模板与自动化规则**（属 UC-11.7）。
  - 完整项目管理套件（甘特、工时、依赖关系图）、第三方 IM 通知。
  - 不扩展到本 use case 未声明的跨组织、跨客户或公开发布能力。

## R7 业务规则（不随具体实现变化的硬性约束）

- **[D-26 · 硬约束] 唯一状态 enum**：任务状态只有一套，取值为
  `inbox / todo / in_progress / review / done`。项目内看板与全局看板是**同一 enum 的两种视图投影**，
  **禁止**为某个视图另建状态字段、映射表或影子状态机。
- **[D-26 · 硬约束] 视图投影不得丢卡**：项目内视图默认折叠 `inbox` 列，其中的卡必须通过
  **筛选项或徽标**保持可达；任何视图下都不允许出现「存在于库中但在所有视图里都不可见」的卡。
- **[D-26] 项目内视图的四列**（待办 / 进行中 / 待复核 / 已完成）即
  `todo / in_progress / review / done` 的投影；全局视图五列全显。
- **[D-26] `inbox` 卡不计入项目内四列的列计数**（未经人接受的卡不算工作量，见 UC-11.2 R7），
  但必须计入折叠入口的「收件箱 N」。
- **[原型 · 双向契约]** 原型底注原文：「**卡片来源自动同步：会前任务、现场行动项、报告缺料、
  决策的后续动作。状态改了会回写到原处。**」——回写是**契约**不是尽力而为：
  回写失败必须显式标记，不得静默丢弃。
- **[原型] 来源徽标恒为六类之一**：`现场` / `会前任务` / `决策树` / `报告缺料` / `转写` / `研究`；
  每张卡必须带且只带一个来源徽标，并携带可点击跳回的来源引用。
- **[D-39 · 硬约束] 负责人恒为人**：`owner` 只能是人的账号；agent 记在独立的 `executor` 字段。
  与「AI 只拿行动权、不承担验收」一致——**agent 不能被记为负责人，也不能承担验收责任**。
- [原型] 回写失败时卡片标记未同步并可重试。
- [Backlog] `done` 卡片 **7 天后折叠**（Backlog UC-11.1 `edge` 原文）；[设计] 收起，非删除。
  ⚠ **原型确认缺失**，见 R4·E2。
- [原型] 观察者不可见待办看板。
- 所有权限判断与状态机校验必须在服务端执行；拖动是界面手势，合法性由服务端裁定。
- 任何状态变更与回写都必须记录审计事件，并显示动作影响范围（改了哪张卡、回写到了哪个来源对象）。

## R9 非功能约束

- **性能/规模预期**：
  - [设计] 拖动改列应在 1 秒内给出服务端确认；超过 1 秒显示卡级加载态，失败则回滚到原列。
  - [设计] 三处计数（列计数 / 标签徽标 / 底注逾期计数）必须由同一次查询产出，避免各自轮询导致漂移。
  - [设计] 列表按列分页或增量加载，禁止一次加载整个项目的历史卡片。
- **安全/隐私/合规**：
  - 最小权限、组织/项目/小组隔离、传输与静态加密、敏感字段脱敏、导出与 AI 读取留痕。
  - 原始材料、录音、转写、私聊、个人身份与客户数据按授权和留存策略处理。
- **兼容与降级要求**：
  - 响应式 Web；桌面端提供完整能力，移动端保证加入、查看、输入、投票/确认等现场关键动作。
  - WebSocket/实时通道不可用时降级为轮询并显示“非实时”；断网允许保留未提交输入，但不得伪装已同步。

- **内部依赖**：phase-00 共享内核的**任务对象**（统一 `status` enum 定义在此，不由本模块私有）、
  身份与权限、来源引用与版本、审计事件。
- **被依赖**：UC-11.2（汇入写入同一 enum）、UC-11.3（筛选投影同一 enum）、UC-11.4（提醒读同一到期字段）、
  UC-11.5（「我的今天」按同一 enum 分区）、UC-11.6（权限包挂在同一任务对象上）、
  UC-11.7（模板写入同一任务对象的默认值）。
- **跨模块契约（双向）**：与**会前任务**（02-tpl）、**现场行动项**（06-live）、
  **报告缺料**（10-report）、**决策后续动作**（13-deliv）四个来源模块建立双向绑定：
  来源侧产生对象 → 汇入为卡（UC-11.2）；**卡的 `status` 变更 → 回写来源对象状态**（本用例 R3.3）。
  两侧必须使用同一份资源标识与版本号，禁止各存一份不可关联的副本。
- **技术约束**：[原型] 产品为响应式网页（原型含移动端对照屏）；[Backlog] 完整离线模式、原生移动端、第三方 IM 为范围外。
- **[已裁决 O-27]** 状态机的**合法转移矩阵**：原问题——是否允许跨列跳跃（如 `todo → done`）、
  是否允许回退（`done → in_progress`）、`review` 打回是否必须填理由——需产品定稿，不由实现者决定。
  **裁决（O-27）**：**允许任意前进跳跃；允许回退但须填理由并留痕；`inbox` 单向出**。
  在 D-26 五态 enum（`inbox / todo / in_progress / review / done`）上，转移矩阵如下
  （✅ ＝ 允许且无附加条件；📝 ＝ 允许但**必须填理由**并写审计；⛔ ＝ 拒绝）：

  | 从 ＼ 到 | `inbox` | `todo` | `in_progress` | `review` | `done` |
  |---|---|---|---|---|---|
  | **`inbox`** | — | ✅ 接受 | ✅ | ✅ | ✅ |
  | **`todo`** | ⛔ | — | ✅ | ✅ 跨列跳跃 | ✅ 跨列跳跃 |
  | **`in_progress`** | ⛔ | 📝 | — | ✅ | ✅ 跨列跳跃 |
  | **`review`** | ⛔ | 📝 | 📝 打回 | — | ✅ |
  | **`done`** | ⛔ | 📝 | 📝 | 📝 | — |

  三条规则，逐条对应上表：
  ① **允许任意前进跳跃**——`todo → done`、`todo → review`、`in_progress → done` 全部放行，
     不强制逐列推进；
  ② **允许回退，但每一次回退都必须填理由并留痕**（表中 📝），
     理由为必填非空，与操作者、时间一起进审计；`review → in_progress` 的「打回」是回退的一种，
     同样必须填理由（本条同时回答了原问题的第三问）；
  ③ **`inbox` 单向出**——一张卡被接受或忽略后**不可回退到 `inbox`**（整列 ⛔）。
     理由：`inbox` 是 AI 建议卡的收件区（D-27），回流会让「待处置建议」的计数失真。
  **为什么不设更严的矩阵**：过严的转移矩阵在真实工作坊里会被绕开（大家改成手写便签），
  **留痕比阻断更有效**——这是本条裁决的取向。
- **[已裁决 O-27]** `scope = global` 时**不允许跨项目拖动改列**（确认 UC-11.3 的现有保守处理）。
- **[已裁决 O-34]** 容量基线（保守值，来自一场线下工作坊的物理上限）：单项目在场 **60 人**（8–10 组 × 6 人 + 引导师团队）、组织并发项目 **20**、单场音频 **8 小时**、单项目材料 **5 GB**、历史 **3 年 × 200 项目**。⚠ **无本项目实测依据，需产品确认**；确认前各 UC **不写性能类 AC**，不阻塞开工

- **[设计] 架构对齐 · Context Engine**（`docs/architecture/context-engine.md`，2026-07-28 定稿）：
  - **AI 取上下文只能通过 Context API 领取 Context Pack**——任何 agent、副驾驶或生成动作
    都不得绕过服务平面直查 `claims` / `segments` / `artifact_versions` 等库表。
    绕过即丢失 `permissionDecisionId` 与引用锚点，`uc-14-6`「AI 读到了什么」将不可重放。
  - **编排边界**：**LangGraph 只用于深度研究、人工确认（HITL）与多阶段生成**；
    文件摄取、批量导入、定时与重试一律走**持久任务系统**（MVP 为 PG outbox + job table）。
    LangGraph 不得被当作通用任务队列；HITL 用动态 `interrupt()`，节点恢复时副作用必须幂等。
  - **权限**：**租户与项目隔离在 PostgreSQL RLS 层强制**，应用连接使用受 RLS 约束的
    **非 owner** 角色（PG 中表 owner 默认不受 RLS 限制）。本文 R5 的权限判定与 R12 的
    越权断言是**第二道**防线，不是唯一防线。Artifact 权限必须传播到 Segment、embedding、
    图边、缓存与 Context Pack；交集生成内容取所有来源权限的**最严格**结果。

## R12 AI Ready 验收线索

以下行为应可由自动化测试、接口断言或可复现人工步骤验证：

- V1（enum 断言）：读取任务表 `status` 列的取值域，断言恰为
  `{inbox, todo, in_progress, review, done}` 五个值；构造第六个值写入被服务端拒绝（400）。
- V2（投影一致 · AC2）：造 N 张卡覆盖五个状态，分别调项目内视图与全局视图的列表接口，
  断言**两次返回的卡 ID 集合完全相同**；断言项目内视图响应中 `inbox` 卡带 `collapsed: true` 标记
  而非被过滤掉。
- V3（不丢卡 · AC2）：在项目内视图下遍历四列 + 折叠入口，断言可达卡数 == 库中该项目卡总数。
- V4（计数一致 · AC1）：任意改一张卡的 `status`，断言标签徽标未完成数、列计数、
  底注 `逾期 N · 今天到期 M` 三者在同一次响应内自洽且与库中查询结果相等。
- V5（回写断言）：把一张 `[会前任务]` 来源的卡从 `todo` 拖到 `done`，
  断言来源模块该会前任务对象的状态同步变为已完成；反向在来源模块改状态，断言卡的 `status` 同步。
- V6（回写失败）：mock 来源模块接口返回 5xx，断言卡上出现「未同步」标记、`status` 与来源侧不一致
  的事实对用户可见、重试接口可再次触发回写。
- V7（负责人恒为人 · AC4）：调改派接口把 `owner` 设为 agent ID，断言返回拒绝；
  把同一 agent ID 设为 `executor` 断言成功。
- V8（来源徽标）：断言每张卡的 `source_kind` ∈
  `{现场, 会前任务, 决策树, 报告缺料, 转写, 研究}` 且 `source_ref` 非空可跳转。
- V9（权限态）：以项目经理 / 引导师 / 组长 / 组员 / 观察者 / 未授权用户逐一调看板接口，
  断言观察者与未授权用户收到 403（不是空列表），组员只拿到自己与本组的卡。
- V10（并发态）：两会话同时把同一张卡拖到不同列，断言只有一个成功，
  另一个收到「状态已变化」错误且卡未被静默覆盖。
- V11（折叠不删 · **[Backlog]**）：把一张卡置 `done` 并把系统时间推进 8 天，
  断言卡仍可通过展开与检索取到（未删除）。
  ⚠ 本条来自 Backlog `edge`，**原型无折叠交互**；落地前须先补画。
- V12（审计态）：状态变更事件可按操作者、时间、卡 ID 检索，且记录含 `status` 前后值与回写结果。
- V13（**转移矩阵** · O-27）：对五态 enum 的 20 个有序对逐一调用状态变更接口——
  ① 断言 `todo → done`、`todo → review`、`in_progress → done` 三条**前进跳跃全部放行**；
  ② 断言全部**回退**转移（表中 📝 格）在**理由为空**时返回校验失败、卡状态不变；
     补上非空理由后放行，且审计事件中含理由原文与 `status` 前后值；
  ③ 断言**任意态 → `inbox`** 一律拒绝（整列 ⛔），包括刚从 `inbox` 接受出来的卡；
  ④ 遍历完 20 个有序对后，断言实际放行集合与矩阵**逐格一致**，无第 21 种转移。
- V14（**跨项目拖动** · O-27）：在 `scope = global` 视图下，把 A 项目的卡拖到 B 项目的列 →
  断言接口拒绝并返回「请在项目看板内推进」，卡的 `status` 与 `project_id` 均未变。
