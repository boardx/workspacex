## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-9.5 / 批量确认与写回
- **Actor**：**引导师**（项目角色，主使用者，执行批量确认）、**组长**（项目角色，节点确认的唯一来源）、
  **项目负责人**（组织角色，原文档称「项目经理」，见 `phase-1/00-core/uc-0-3`）
- **目标**：[原型] 现场收尾前，把本场四个组产生的新节点**按组盘一遍**——
  该确认的一次性确认掉、该判的冲突当场判掉，然后**排队写回组织大脑**；
  并守住那条最强的闸门：**只有组长确认过的节点才会写回组织大脑**。
- **本用例结果**：[原型] 「事实关系」屏下半呈现三块：
  ① **【本场新增节点 · 按组】**——每组一行，写清**类型构成**与**小计**；
  ② **`[批量确认]`** 入口 + 常驻硬约束文案「只有组长确认过的节点才会写回组织大脑」；
  ③ **【冲突待判定 · N】**——列出互斥事实对与各自证据归属，带两个**现场版消解出口**
  `[上台讨论]` `[标为不确定]`。确认后节点进入成果沉淀并**排队写回组织大脑**。
- **系统边界**：按组待确认清单的聚合与计数、批量确认动作与写回队列、写回闸门校验、
  冲突待判定清单与两个现场出口、写回前后清单可查与责任人留痕；
  **不含**节点与关系的产生与入图（UC-9.1）、组织大脑侧的知识五态机与晋升（14-brain / D-32）、
  组织大脑侧的冲突三出口消解（那是大脑侧流程，不是现场版）。
- **核心数据对象**：本场新增节点（按组分桶、按类型计数）、组长确认标记、批量确认批次、
  写回队列条目、冲突对与消解记录、审计事件。
- **[设计] 写回在 Claim 模型上的语义**（见 `docs/architecture/context-engine.md` 第二节
  与 `uc-9-1` R1 的 `claims` 字段契约）：**写回不是新建一条记录，是推进同一条 Claim 的生命周期**——
  - `[批量确认]` ＝ 把该 Claim 的 `status` 由 `proposed`/`reviewed` 推进到 **`accepted`**，
    并写入 `reviewed_by`（确认人）与 `valid_from`（写回时刻）；
  - `[标为不确定]` ＝ 保持 `status` 不升为 `accepted`（停在 `reviewed`），
    不删除、不隐藏，仍在检索范围内；
  - **冲突对** ＝ 两条 Claim 双双置 **`contested`**，两条都写回、**都不丢**；
    组织大脑侧看到的是一对互斥 Claim，而不是被现场替人选过的单条结论；
  - **被新结论推翻的旧结论** ＝ 旧 Claim 置 **`superseded`** 并由新 Claim 的
    `supersedes_claim_id` 指回，**不物理删除**——这是「当时对、现在错」可表达的前提。
  - 写回**不覆盖任何证据**：`claim_evidence` 只增不改，
    `relation = contradicting` 的行在写回全过程中不可删除。

## R2 前置条件 / 触发条件

- **前置条件**：
  - 用户已建立可校验的正式或临时身份，且拥有目标组织、项目、小组或资源的访问权。
  - 目标资源存在且未被删除/冻结；依赖能力「可视化模板（节点来源）、实时转录（证据来源）、
    研究模块与访谈模块（证据来源）」可用，或界面能明确显示其不可用状态。
    （**档案中不存在名为「Chat」的上游模块**，原「Chat（结论来源）」提法系杜撰，已按档案改写。）
  - [原型] UC-9.1 已把本场节点入图，且各组组长已在本组画布上对节点做过确认动作
    ——**组长确认是写回资格的唯一来源**。
  - [设计] 组织大脑侧的写回接收端可用；不可用时批次只能停在「待写回」，不得标成已写回。
  - 若动作涉及个人数据、录音、原始材料或跨范围读取，相应授权与留存策略已生效。
- **触发条件**：
  - [原型] **现场结束前**，引导师在 `知识图谱 → 事实关系` 屏下半查看【本场新增节点 · 按组】。
  - [原型] 引导师点 `[批量确认]`。
  - [设计] 冲突节点数变化时，【冲突待判定 · N】的计数与清单增量刷新。
  - 系统从 **全场图谱 → 事实关系** 进入本流程，并携带当前组织、项目、小组、角色和资源标识。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

1. **引导师操作**：在 `知识图谱 → 事实关系` 屏向下看到【本场新增节点 · 按组】。
   **系统响应**：[原型] 按组列出本场新增节点，每行写清**组号 + 场景名 + 类型构成 + 小计**。
   原型实例（四组共 17 个）：
   - 第 1 组　业主首次评估　**假设 2 / 证据 3**　小计 **5**
   - 第 2 组　采购比选　　　**假设 3 / 证据 2**　小计 **5**
   - 第 3 组　并网审批　　　**假设 1 / 证据 3**　小计 **4**
   - 第 4 组　收益归因　　　**假设 1 / 概念 2**　小计 **3**
   [原型] 类型构成必须按 `假设 / 证据 / 概念` 分别计数，**不得**只给一个合计数字。
2. **系统处理**：[原型] 在该区块常驻硬约束文案
   **「只有组长确认过的节点才会写回组织大脑。」** 并把 `[批量确认]` 入口放在同一区块。
   [设计] 每组行可展开为该组的节点明细，逐条显示是否已被**本组组长**确认；
   未被组长确认的节点在明细中显式标出，且**不计入可写回数**。
3. **引导师操作**：点 `[批量确认]`。
   **系统响应**：[设计] 弹出确认层，明确列出「本次将写回 N 个节点，来自 M 个组」与**被排除的条目及原因**
   （未经组长确认 / 冲突未解 / 证据未验收），要求引导师二次确认。
4. **系统处理**：[原型] **写回闸门校验**——逐条校验「是否有本组组长的确认记录」，
   无确认记录的节点**一律不进写回队列**（服务端强制，不只是前端置灰）。
   [Backlog] 有**冲突未解**的节点不允许批量确认，必须先在【冲突待判定】里处置
   （Backlog UC-9.5 `edge` 原文「有冲突未解的节点不允许批量确认」）。
   ⚠ **原型确认缺失**：事实关系屏只显示【冲突待判定 · 2】与 `[上台讨论]` `[标为不确定]` 两个按钮，
   **从未表明冲突会阻断 `[批量确认]`**——两者在原型里是同屏并列的独立区块。
   这是本用例最强的拦截规则，落地前须补画该阻断态。
5. **系统处理**：确认通过的节点**进入成果沉淀并排队等写回组织大脑**。[原型]
   [设计] 写回是**异步排队**：批次状态为 `排队中 / 写回中 / 已写回 / 失败`，
   写回前后都能看到**这批节点的清单与责任人**（AC1）；失败可重试，重试不产生重复知识。
6. **引导师操作**：查看【冲突待判定 · N】（原型实例 N=2）。
   **系统响应**：[原型] 列出互斥事实对，写清**互斥内容 + 各方证据归属 + 为什么需要现场判**。
   原型实例：
   > 「『审批 6–9 个月』与『本地 EPC 可压到 4 个月』互斥；第 2、3 组各自挂了证据，需要现场判一次。」
   并给出**两个现场版消解出口**：`[上台讨论]`　`[标为不确定]`。
7. **引导师操作**：选一个出口。**系统响应**：
   - [原型] `[上台讨论]` —— 把该冲突推到主持台/大屏进入现场讨论，节点保持 `冲突` 态，
     [设计] 讨论产生结论后由**人**判定归属，系统不自动消解。
   - [原型] `[标为不确定]` —— 把该冲突标为不确定并**允许本批次继续**；
     [设计] 被标不确定的节点**可以写回**，但在组织大脑侧带「不确定」标记，
     **不参与定题强度计算**，也不作为决策依据被引用。
   [原型] **两个出口是现场版**，与组织大脑侧的三出口**不同**，不得互相替代或合并实现。
8. **系统处理**：[设计] 写回时逐条携带**溯源四元组**（来源组 + 来源模块 + 证据量 + 时间码，见 UC-9.1）
   与**确认责任人**（哪位组长确认、哪位引导师批量提交、各自时间）；
   写回目标遵循「引用必须指向不可变快照」。
9. **系统收口**：记录批量确认、冲突消解、写回成功/失败的操作者、时间、对象、结果与来源进审计；
   刷新【本场新增节点 · 按组】计数、【冲突待判定 · N】计数与成果沉淀列表。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[设计] 本场零新增节点时展示真实空态「本场还没有新增节点」+ 回到事实关系列表的入口，
    **不生成示例节点冒充真实结果**，`[批量确认]` 禁用。
  - A2：[设计] 某组全部节点都未经组长确认时，该组行仍然列出（显示构成与小计），
    但标注「本组组长尚未确认，0 个可写回」，并提供「提醒组长确认」的入口。
  - A3：[设计] 引导师可在批量确认前**逐条取消勾选**某些节点；被取消的节点留在待确认清单里，
    不被标记为已拒绝，下次仍可确认。
  - A4：[设计] 冲突节点走 `[标为不确定]` 后，本批次可继续；
    走 `[上台讨论]` 则该节点**留在本批次之外**，直到现场判完。
  - A5：[设计] 引用了 **D-33「待复核」态过期知识** 的节点仍可确认并写回，
    但必须在清单与写回记录上带「引用了已过期知识」提示。
- **异常流程**：
  - E1：[Backlog] **有冲突未解的节点不允许批量确认**（Backlog `edge` 原文）——
    [设计] 接口返回明确拒绝并指出是哪几条，失败不得被呈现为成功。
    （**原型确认缺失**：无任何阻断界面，见 R3 第 4 步的说明。）
  - E2：[设计] **未经组长确认的节点即使被勾选也不得写回**——服务端拒绝，
    （规则本体出自原型硬约束文案「只有组长确认过的节点才会写回组织大脑」；
    **服务端强制与拒绝流程**是实现约束，原型无据。）
    且不得产生「部分成功但无法追溯」的半成品批次。
  - E3：[设计] 组织大脑写回接收端不可用时，批次停在 `排队中` 并显示「等待组织大脑」，
    **不得**把未写回的批次标成 `已写回`。
  - E4：[设计] 写回部分失败时，批次进入 `部分失败` 并逐条列出失败项与原因，
    可对失败项单独重试；重试**幂等**，不产生重复知识节点。
  - E5：[设计] 请求超时、网络中断或依赖不可用时，保留用户当前勾选与最后成功数据，
    明确失败原因并提供安全重试。
  - E6：[设计] 同一批节点被并发确认（两位引导师同时点 `[批量确认]`）时不得静默覆盖或双写；
    以批次为粒度加锁，第二个请求返回「已有批次在处理」并可查看该批次。
  - E7：[设计] 权限在操作过程中被撤回时立即终止后续写操作；已完成步骤按审计规则保留，
    未提交输入留在本地草稿并提示重新授权。
  - E8：[设计] 节点在批量确认与实际写回之间被上游改动（合并/转冲突/证据撤回）时，
    该条从本批次中剔除并给出原因，**不得**把改动前的旧快照写进大脑。

## R5 权限与可见性

- **引导师**（主使用者）：可查看【本场新增节点 · 按组】全量、执行 `[批量确认]`、
  处置【冲突待判定】的两个出口、查看写回批次状态与清单。
  **不能**替组长确认组内节点——引导师的批量确认只是**提交**，不是**授权来源**。
- **组长**（项目角色）：**节点确认的唯一来源**——只能确认**本组**节点；
  可只读查看全场按组计数与冲突清单；不能执行批量写回。
- **组员**（项目角色）：只读查看本组新增节点计数；不能确认、不能写回。
- **项目负责人**（组织角色，原文档称「项目经理」）：在被授权项目内只读查看按组清单、
  冲突待判定与写回批次记录。
- **观察者**（一等项目角色，见 D-12）：只读查看**已写回**的结果；
  待确认清单、冲突明细与各方证据归属默认不对观察者展开，个人身份信息脱敏。
- **AI / Agent**：可产出候选节点（受 UC-9.1 约束），**不能**确认节点、不能执行批量写回、
  不能消解冲突。
- **未登录、链接失效或未列出的角色**：默认无权限；接口不得返回越权数据，不能只依赖前端隐藏。

## R6 后置条件 / 不包含

- **正常后置条件**：
  - 【本场新增节点 · 按组】计数与实际节点一致，且按 `假设 / 证据 / 概念` 分别可核。
  - 确认通过的节点进入成果沉淀并排队写回组织大脑，写回记录带溯源四元组与确认责任人。
  - 冲突已通过 `[上台讨论]` 或 `[标为不确定]` 之一处置，处置留痕。
  - [Backlog验收] AC1：**写回前后都能看到这批节点的清单与责任人**（Backlog UC-9.5 `ac` 原文）。
  - [原型验收] AC2：**只有组长确认过的节点才会写回组织大脑**（原型常驻硬约束文案原文）；
    [设计] 未确认节点在写回队列中不存在（写回队列本身原型未渲染）。
  - [原型验收] AC3：按组清单显示类型构成与小计（原型基线：5 / 5 / 4 / 3）。
  - [Backlog验收] AC4：有冲突未解的节点无法进入批量确认
    （Backlog `edge`；**原型确认缺失**，见 R3 第 4 步——此前标 `[原型验收]` 系造假，已降级）。
  - [原型验收] AC5：冲突待判定提供现场版两出口 `[上台讨论]` `[标为不确定]`（原型可见）；
    [设计] **恰提供两个、不得增删**（枚举闭合性属实现约束）。
  - [设计验收] AC6：**D-33** ——被标为「不确定」或引用了「待复核」过期知识的节点，
    写回后**仍在检索范围内**、引用时提示，但**不参与定题强度计算**。
- **失败后置条件**：
  - 不创建「看似成功」的正式记录；未真正写回的批次不得显示为 `已写回`；
    可重试内容保留为草稿，失败事件进入可观测日志。
- **不包含**：
  - AI 无人确认自动写成正式结论、自动消解冲突、代替组长确认。
  - 节点与关系的产生、入图与三态判定（属 UC-9.1）。
  - 决策树与岔口（UC-9.2）、工作卡派发（UC-9.3）、流水线矩阵（UC-9.4）。
  - **组织大脑侧的知识五态机、晋升准入（D-32）与大脑侧冲突三出口**——本用例只负责写到队列为止。
  - 不扩展到本 use case 未声明的跨组织、跨客户或公开发布能力。

## R7 业务规则（不随具体实现变化的硬性约束）

- **[D-e] 本用例「写回组织大脑」的闸门＝组长确认，作用对象是【现场图谱节点】**——
  与 `uc-13-2` 的「写回组织大脑」**不是同一条规则**：那一条的闸门是**验收通过**，
  作用对象是**项目产出物**。两者对象不同、闸门不同、时机不同，
  **不得合并实现成同一个校验入口**。
- [原型] **只有组长确认过的节点才会写回组织大脑。**（原型常驻硬约束文案原文）
  这是本模块最强的一条闸门。[设计] 服务端强制；引导师的 `[批量确认]` 是提交动作，
  **不能**替代组长的确认授权。
- [Backlog] **有冲突未解的节点不允许批量确认**（Backlog UC-9.5 `edge` 原文）；
  [设计] 必须先经 `[上台讨论]` 或 `[标为不确定]` 处置。
  ⚠ **原型确认缺失**——原型只有两个并列区块，没有任何「冲突阻断批量确认」的表达。
- [原型] **【本场新增节点 · 按组】必须按组分桶并给出类型构成**（`假设 / 证据 / 概念` 各自计数 + 小计），
  不得只呈现一个总数。
- [原型] **现场版冲突消解出口**：`[上台讨论]` / `[标为不确定]`（原型两个按钮）。
  [设计] 该枚举**封闭**（恰为两个，不得增删）；这与**组织大脑侧的三出口不同**，
  两套流程独立建模，不得合并或互相替代。
- [设计] **写回幂等**：同一节点重复写回不产生重复知识；批次可重试，重试不改变最终结果。
- [设计] **写回必须携带责任人链路**：哪位组长确认、哪位引导师提交、各自时间；AC1 的「责任人」即指此。
- [设计] **写回必须携带溯源四元组**（来源组 + 来源模块 + 证据量 + 时间码，见 UC-9.1），
  且引用指向不可变快照（`phase-1/00-core/uc-0-1`、D-30）。
- **[D-33] 过期知识规则**：知识超过有效期后转「**待复核**」态，**仍在检索范围内**、
  仍可被展示与引用，**引用时必须提示已过期**；但**不参与定题强度计算**——
  不计入证据量权重、不推动状态升级、不作为「已确认」的充分条件。
  本用例中：引用了「待复核」知识的节点**可以**确认与写回，但须带提示且其强度贡献计 0。
  被 `[标为不确定]` 的节点适用同一条强度规则。
- [设计] **AI 不得确认或写回**：agent 只能提出候选，确认与写回的操作者字段恒为自然人。
- 所有权限判断必须在服务端执行；隐藏入口只是界面表现，不构成安全控制。
- 任何覆盖、删除、撤销、签署、发布、写回或停用动作都必须记录审计事件，并显示动作影响范围。

## R12 AI Ready 验收线索

以下行为应可由自动化测试、接口断言或可复现人工步骤验证：

- V1（写回闸门 · 最关键）：AC2 —— 造一个**未经组长确认**的节点并把它塞进批量确认请求 →
  断言接口**拒绝该条**，写回队列中查不到它；由本组组长确认后再提交，断言它进入队列
  且带 `confirmed_by`（组长）与 `submitted_by`（引导师）两个责任人字段。
- V2（越权确认）：以**他组**组长身份确认某节点 → 断言拒绝；
  以引导师身份直接调「确认节点」接口 → 断言拒绝（引导师不能替组长确认）。
- V3（按组计数）：AC3 —— 以原型基线断言四行分别为
  `第1组 假设2/证据3 → 5`、`第2组 假设3/证据2 → 5`、`第3组 假设1/证据3 → 4`、`第4组 假设1/概念2 → 3`；
  断言每行的小计 = 各类型之和，全场合计 = 17。
- V4（冲突拦截）：AC4 —— 存在未解冲突节点时提交批量确认 → 断言接口拒绝，
  错误体中**逐条列出**是哪些冲突节点；断言无任何节点被写入队列（不产生部分成功）。
- V5（现场两出口）：AC5 —— 断言冲突消解出口集合**恰为** `{上台讨论, 标为不确定}` 两值；
  提交第三个值（组织大脑侧的出口名）时返回校验失败。
- V6（标为不确定后可继续）：对冲突走 `[标为不确定]` → 断言该节点**可以**进入本批次；
  走 `[上台讨论]` → 断言该节点**被排除**在本批次之外且节点仍为 `冲突` 态。
- V7（D-33 强度规则）：AC6 —— 把一条知识置为过期「待复核」，另造一条被 `[标为不确定]` 的节点，写回后断言：
  ① 两者**仍出现**在检索结果中；② 展示与引用时带「已过期 · 待复核」/「不确定」标记；
  ③ 引用它们**前后的定题强度数值相同**（强度贡献为 0），且不推动任何节点升为 `已确认`。
- V8（清单与责任人）：AC1 —— 在写回**前**查询批次，断言返回节点清单 + 每条的确认组长 + 提交引导师；
  写回**后**再查同一批次，断言清单与责任人字段不变且可按批次 ID 检索。
- V9（幂等）：对同一批次重复触发写回两次 → 断言组织大脑侧知识条数只增一份，无重复节点。
- V10（写回端不可用）：停掉组织大脑写回接收端 → 断言批次停在 `排队中` 并显示「等待组织大脑」，
  **断言批次状态不为 `已写回`**；恢复后自动或手动重试成功。
- V11（部分失败）：构造部分条目写回失败 → 断言批次为 `部分失败`、逐条列出失败原因、
  可对失败项单独重试，成功项不被重复写入。
- V12（写回中途上游变更）：批量确认后、写回前把某节点转为 `冲突` → 断言该条被剔除并给出原因，
  断言写进大脑的**不是**变更前的旧快照。
- V13（AI 不得确认/写回）：以 agent 身份调用确认接口与批量写回接口 → 断言均返回拒绝；
  断言所有 `confirmed_by` / `submitted_by` 字段的主体类型恒为自然人。
- V14（溯源随写回）：断言写回队列每条都带 `source_group` / `source_module` / `evidence_count` /
  `timestamp` 四个非空字段，且引用目标为不可变快照 ID + 版本号。
- V15（权限态）：逐一以 引导师 / 组长（本组、他组）/ 组员 / 项目负责人 / 观察者 / 未授权用户 调接口；
  断言仅引导师能提交批量确认、仅本组组长能确认本组节点；
  观察者返回中不含待确认清单与冲突明细。
- V16（空态）：本场零新增节点时断言返回空清单、页面显示真实空态、`[批量确认]` 禁用，
  断言返回体中不含任何示例节点。
- V17（并发态）：两位引导师同时点 `[批量确认]` → 断言只产生一个批次，第二个请求返回
  「已有批次在处理」，无双写。
- V18（依赖失败）：模拟网络/上游失败 → 断言用户勾选与最近成功数据保留、错误可解释、可安全重试。
- V19（审计态）：批量确认、冲突消解（两出口各一次）、写回成功与失败四类动作
  均可按操作者、时间、对象、结果检索；越权尝试也留安全审计记录。
- V20（来源撤回联动）：已写回的知识其来源材料被撤回 → 断言 ≤5 分钟退出检索、引用处标失效
  （对照 D-13 / D-15 的两级 SLA）。
