# 原始需求（细化）— UC-9.1 节点实时入图

> 所属：阶段二 · 让推演与成果可见 / M9 知识图谱与决策树  
> 来源：`WorkspaceX Standalone.html` → `项目 → [进入项目] → 现场协作 → 全场视图 → 知识图谱 → 事实关系`（原型档案 `proto-06-deep-layer2.md` 第 2.4 节「事实关系」）；对照 `Backlog Use Case.html` 的 UC-9.1。  

> 口径（四标记）：**[原型]** ＝ `WorkspaceX Standalone.html` **运行态实际存在**的行为（有界面可查，依据 scratchpad 的 proto-01~10 抽取档案）；**[Backlog]** ＝ `Backlog Use Case.html` 的**文档要求**（原型未必实现）；**[设计]** ＝ 依据前两者反推补全，**需人类确认**；**[待确认]** ＝ 不应由实现者自行决定。
> 元数据：优先级 **P0**；估点 **8**；建议迭代 **阶段二 · 迭代 6 · 图谱立起来**；模块 09-kg 合计 **32** 点（9.1=8 / 9.2=8 / 9.3=5 / 9.4=6 / 9.5=5；Backlog 原 29）；**phase-2 五模块合计 163 点**（09-kg 32 / 10-report 29 / 11-board 41 / 12-survey 24 / 13-deliv 37；原 158，因 O-27 与 O-30 各 +2/+3）。

## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-9.1 / 节点实时入图
- **Actor**：**引导师**（项目角色）、**组长**（项目角色）、**项目负责人**（组织角色，原文档称「项目经理」，见 `phase-1/00-core/uc-0-3`）
- **目标**：[原型] 现场四个组同时在推演，各自产生的假设、证据、概念要**实时**落成一张可读的事实关系图——
  「谁支持谁、谁阻碍谁、哪条是硬约束」，并且每一条都能点回原始便签或转写时间码。
- **本用例结果**：[原型] 全场视图的「知识图谱 → 事实关系」子视图上有一张**每 15 秒刷新**的
  【正在推演的关系】列表：每条关系带关系类型、两端节点、节点状态与溯源四元组
  （来源组 + 来源模块 + 证据量 + 时间码）。原型实例：
  「交付确定性 —被证据支持→ 并网审批时长 9.5 个月　【已确认】　第 3 组 · 研究模块 9 来源 · 12:05」。
- **系统边界**：节点建立与合并、关系（边）建立与语义分类、节点三态判定、溯源留痕、冲突标记与提醒；
  **不含**批量确认与写回组织大脑（UC-9.5）、决策树布局（UC-9.2）。
- **核心数据对象**：知识节点（假设 / 证据 / 概念）、关系边（五类语义）、来源引用、证据量计数、冲突对、审计事件。
- **[设计] 与 Context Engine 的对应**（见 `docs/architecture/context-engine.md` 第二节）：
  本屏的**节点**落在 `claims` 表，本屏的**关系（边）**落在两处——
  节点↔证据的支持/反驳关系落 `claim_evidence`（`relation ∈ {supporting, contradicting}`），
  节点↔节点的五类语义关系落 `ontology_edges`。溯源四元组来自 `provenance_events` 与
  `segments/anchors`（时间码 = anchor 的 `startMs`，来源模块 = artifact 的 `sourceType`）。
- **[设计] `claims` 必备字段**（架构侧强制，本模块不得少写）：
  `status`（`proposed` / `reviewed` / `accepted` / `contested` / `superseded`）、
  `confidence`（数值）、`valid_from`、`valid_to`（支持「过去成立、现在失效」）、
  `created_by`（`human` / `model` / `import`）、`reviewed_by`（审核人）、
  `supersedes_claim_id`（被本条取代的旧 Claim）。
  界面上的**三态徽标是 `status` 的展示投影**，不是另一套字段：
  `已确认` ← `accepted`；`冲突` ← `contested`；`待确认` ← `proposed` / `reviewed`。
  `superseded` 不在本屏渲染（已被取代的旧结论），但**不删除**，仍可从版本链回溯。

## R2 前置条件 / 触发条件

- **前置条件**：
  - 用户已建立可校验的正式或临时身份，且拥有目标组织、项目、小组或资源的访问权。
  - 目标资源存在且未被删除/冻结；依赖能力「可视化模板/画布便签（假设与概念来源）、实时转录（证据来源）、研究模块与访谈模块（证据来源）、概念卡与 Agent 产出（候选方案来源）」可用，或界面能明确显示其不可用状态。
  - 若动作涉及个人数据、录音、原始材料或跨范围读取，相应授权与留存策略已生效。
- **触发条件**（任一即触发，二者并行）：
  - [原型] **组长确认了画布上的一个节点** —— 该节点从「待确认」升为「已确认」，进入可写回候选集。
  - [原型] **引导师打开 `知识图谱 → 事实关系` 子视图** —— 拉起【正在推演的关系】列表并起 15 秒刷新周期。
  - 系统从 **全场视图 / 本组图谱** 进入本流程，并携带当前组织、项目、小组、角色和资源标识。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

1. **引导师操作**：进入 `现场协作 → 全场视图 → 知识图谱 → 事实关系`。
   **系统响应**：[原型] 渲染【正在推演的关系】列表，每行一条关系「起点节点 —关系类型→ 终点节点」，
   右侧挂**节点状态徽标**与**溯源行**；页头标注「每 15 秒刷新」，并启动 15 秒增量刷新周期。
2. **系统处理**：从上游通道持续吸收内容——[原型] 档案实际出现的来源模块为
   **画布便签 / 概念卡**（产假设、概念）、**实时转录**（产证据）、
   **研究模块**（「研究模块 9 来源」）、**访谈模块**（「访谈 2 段」）、
   **Agent**（「Warden · 补贴目录原文」）。
   （**此前写的「Chat（结论来源）」在 proto-01~10 十份档案中零命中，系杜撰，已按档案改写。**）
   [原型] 按内容类型建节点（假设 / 证据 / 概念），
   按语义建边；[原型] **关系类型的五个取值**：`被证据支持` / `可能缩短` / `阻碍` / `硬约束` / `候选方案`。
   [设计] 不属于这五类的语义不得入图，退回人工归类（枚举闭合性属实现约束）。
3. **系统处理**：为每条入图关系写入**溯源四元组**——`来源组` + `来源模块` + `证据量` + `时间码`，
   四项缺一不可，缺项的关系停在「待补来源」不进列表。[原型] 实例：
   - 「交付确定性 —被证据支持→ 并网审批时长 9.5 个月」　第 3 组 · 研究模块 9 来源 · 12:05
   - 「本地 EPC 合作 —可能缩短→ 并网审批时长」　第 2 组 · 访谈 2 段 · 12:31
   - 「责任归属缺口 —阻碍→ 采购签字」　第 1、2、4 组转录共 7 次 · 12:22
   - 「本地化率 40% —硬约束→ 进入模式选择」　Warden · 补贴目录原文 · 11:40
   - 「收益保底条款 —候选方案→ 运营期归因争议」　第 4 组 · 概念卡 · 12:12
4. **系统处理**：判定**节点三态**并渲染徽标——
   `已确认`（挂有已验收证据且无互斥事实）／`冲突`（存在互斥事实、双方各自挂证据）／
   `待确认`（未挂证据，或所挂证据尚未通过验收）。[原型] 三个取值来自原型「节点状态」一行；
   [设计] 三态之外无第四种取值（闭合性属实现约束）。
5. **系统处理**：[Backlog] **同一事实被多组提出时合并为一个节点**，来源逐条累加、证据量相加，
   不产生重复节点；跨组引用**标明谁给谁提供了证据**（Backlog UC-9.1 `edge` 原文
   「同一事实被多组提出时合并为一个节点，来源累加」「跨组引用画紫色虚线，标明谁给谁提供了证据」）。
   [设计] 用**紫色虚线**渲染跨组引用。
   ⚠ 事实关系屏**无任何线型/配色说明**；「紫线」在十份档案中只出现一次，且属**推演流水线**
   的图例（`虚线＝图谱建议的下一步；紫线＝跨场景互证`），与本屏不是同一对象。
   线型选择属**视觉设计**，须人类确认。
6. **组长操作**：在本组画布上点「确认」某个节点。
   **系统响应**：把该节点标为「组长已确认」，写入本组的【本场新增节点】待写回清单（交给 UC-9.5）。
   [原型] **未经组长确认的节点只在现场图谱内可见，绝不写回组织大脑**。
7. **系统处理**：检测到两条互斥事实时，自动把两端节点置 `冲突` 态、双向连边，并在主持台
   【冲突待判定】分区推提醒（如「『审批 6–9 个月』与『本地 EPC 可压到 4 个月』互斥」）。[原型]
   同时**支持证据与反对证据同等留存**：反对证据不可删除，也不可被任何筛选器/默认视图排除。[设计]
8. **引导师/组长操作**：点击任一节点或关系。**系统响应**：下钻到**原始便签**或**转写时间码**，
   跳转携带来源资源 ID 与版本号，可从来源页面反向回到本节点。[Backlog]
   （Backlog `ac`「任一节点都能点回原始便签或转写时间码」；
   ⚠ **未探明**：该下钻层本轮抽取未点进，与 R8 sign-off 的「①点击节点后的节点详情/来源展开层
   未探明」是同一件事——**未探明区内不得有 `[原型]` 断言**。）
9. **系统收口**：记录操作者、时间、对象、结果与来源进审计；刷新全场事实关系列表、
   决策树（UC-9.2）的节点状态与待写回清单（UC-9.5）的按组计数。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[设计] 本场尚无任何关系入图时，列表展示真实空态「还没有关系入图，等各组在画布上确认第一个节点」
    并给出跳转到本组画布的入口，**不生成示例关系冒充真实结果**。
  - A2：[Backlog] 同一事实被多组提出 → 合并为一个节点、来源累加、证据量相加，**不新建重复节点**；
    合并后的来源行按组分别列出，不得把多组来源压成一条。
  - A3：[设计] 某条证据被引用它的节点采纳时，其**来源模块**字段保留原始模块名（研究模块 / 访谈模块 /
    转录 / 概念卡 / Agent 名如 Warden），不得统一改写成「图谱」。
  - A4：[设计] 引用了**已过期知识**（D-33「待复核」态）的关系仍然显示在列表中，
    但带「已过期，需复核」提示，且该条不计入定题强度。
- **异常流程**：
  - E1：[原型] 检测到互斥事实 → 不做自动消解，两端置 `冲突` 态并进【冲突待判定】，等人判。
    系统**不得**擅自保留一方、丢弃另一方。
  - E2：[设计] 15 秒刷新所依赖的实时通道（WebSocket）不可用时，降级为轮询并在页头显示「非实时 ·
    最后更新 hh:mm」，**不得**用旧数据冒充最新态。
  - E3：[设计] 请求超时、网络中断或上游依赖（转录 / 画布 / 研究模块 / 访谈模块）不可用时，保留最后一次成功快照，
    明确标出哪条通道断了，并提供安全重试；断链期间新产生的节点补入后需重新计算证据量。
  - E4：[设计] 同一节点被并发修改（两个组同时改同一条合并节点）时不得静默覆盖；提示版本已变化，
    允许刷新、对比或重新提交。
  - E5：[设计] 权限在操作过程中被撤回时立即终止后续写操作；已完成步骤按审计规则保留，
    未提交输入留在本地草稿并提示重新授权。
  - E6：[设计] 关系语义无法归入五类枚举时，入图失败并明确提示「关系类型不在允许取值内」，
    **不得**静默降级为某个默认类型。

## R5 权限与可见性

- **引导师**：可查看**全场**事实关系列表、下钻任一来源、看到冲突提醒；**不能**替组长确认组内节点。
- **组长**：可确认**本组**画布上的节点（确认动作是写回资格的唯一来源），可查看全场事实关系（只读）。
- **组员**：可看到本组节点入图结果，**不能**确认节点。
- **项目负责人**（组织角色，原文档称「项目经理」）：可在被授权项目内只读查看全场图谱与溯源。
- **观察者**：只读查看**已确认**节点与关系；`冲突`/`待确认` 节点及其反对证据默认不对观察者展开，
  个人身份信息脱敏。
- **未登录、链接失效或未列出的角色**：默认无权限；接口不得返回越权数据，不能只依赖前端隐藏。

## R6 后置条件 / 不包含

- **正常后置条件**：
  - 事实关系列表反映现场真实状态，每条关系带完整溯源四元组，可从来源页面再次打开。
  - 组长确认过的节点进入 UC-9.5 的【本场新增节点 · 按组】清单，等待批量确认与写回。
  - 冲突节点已进入【冲突待判定】分区并可被引导师处置。
  - [Backlog验收] AC1：任一节点都能点回原始便签或转写时间码（Backlog UC-9.1 `ac` 原文）；
    [设计] 跳转带来源 ID + 版本。⚠ **未探明**：点击节点后的下钻层本轮未点进。
  - [Backlog验收] AC2：冲突节点在主持台有明确提醒（Backlog `ac` 原文；
    原型【冲突待判定 · 2】可佐证）；[设计] 互斥双方的证据都可展开（**未探明**）。
  - [设计验收] AC3：关系类型字段的取值集合恰为五值，节点状态字段的取值集合恰为三态
    （**取值本身 [原型] 可证，「恰为」这一闭合性是设计约束**）。
  - [设计验收] AC4：反对证据在任何视图、任何筛选条件下都不会被隐藏或删除。
  - [设计验收] AC5：**未经验收的证据不具备被决策引用的资格**——引用它的关系只能置 `待确认`，
    不得置 `已确认`（见 `phase-1/00-core/uc-0-1` 与 D-30：验收是引用资格的闸门）。
  - [设计验收] AC6：**D-33 过期知识**转「待复核」态后**仍在检索与展示范围内**，引用时提示已过期，
    但**不参与定题强度计算**——即该证据不计入节点的证据量权重、不推动节点从 `待确认` 升 `已确认`。
- **失败后置条件**：
  - 不创建“看似成功”的正式记录；可重试内容保留为草稿，失败事件进入可观测日志。
- **不包含**：
  - AI 无人确认自动写成正式结论、自动消解冲突。
  - 批量确认与写回组织大脑的动作本身（属 UC-9.5）。
  - 决策树布局、岔口清单与拍板预判（属 UC-9.2）。
  - 不扩展到本 use case 未声明的跨组织、跨客户或公开发布能力。

## R7 业务规则（不随具体实现变化的硬性约束）

- [原型] **只有组长确认过的节点才会写回组织大脑。** 未确认的节点只在现场图谱内存在，
  不进入写回队列、不进入组织级检索。这是本模块最强的一条闸门。
- [原型] **关系类型取值**：`被证据支持` / `可能缩短` / `阻碍` / `硬约束` / `候选方案`
  （原型「关系类型（边的语义）」一行逐项列出）。
  [设计] 该枚举**封闭**：服务端校验，不在枚举内一律拒绝入图，不得静默落成默认值。
  （闭合性与服务端拒绝属实现约束，原型只列出了取值。）
- [原型] **节点状态取值**：`已确认` / `冲突` / `待确认`（原型「节点状态」一行）。
  [设计] 该枚举**封闭**。
- [原型] **每条关系必须携带完整溯源四元组**：来源组 + 来源模块 + 证据量 + 时间码。缺任一项不得入图。
- [原型] 事实关系列表**每 15 秒刷新**一次；刷新是增量的，不得整表重绘丢失用户当前展开状态。
- [Backlog] 同一事实被多组提出 → 合并为一个节点，来源累加、证据量相加（Backlog `edge` 原文）。
- [Backlog] 跨组引用**标明谁给谁提供了证据**；[设计] 具体线型（紫色虚线）**原型无据**，
  见 R3 第 5 步的说明，须人类确认。
- [设计] **反对证据必须留存**：与主流结论相反的证据不可删除、不可被筛选器排除、
  不可被默认视图折叠隐藏。冲突节点必须能同时展开支持方与反对方的证据。
  **数据侧的落点**：这条约束等价于 **`claim_evidence` 中 `relation = contradicting` 的行不可删除**
  （只能随其所属 Claim 一起进 `superseded`，或随原始材料的合规删除走 `17-gov` 的级联失效流程）；
  删除接口对 contradicting 行一律返回拒绝，筛选器不得提供排除该 relation 的选项。
- [设计] **冲突成对召回**：两条互斥 Claim 一旦成对，**必须同时进入同一个 Context Pack**——
  引擎只负责把两边一起交出来（含各自的 `supportingSegmentIds` / `contradictingSegmentIds`），
  **不替人选边、不做加权合并、不按分数丢弃低分的一方**。选边是人的动作（R3 第 7 步的【冲突待判定】），
  不是检索层的动作。对应 `docs/architecture/context-engine.md` 第四节流程第 6 步「支持/反驳平衡」。
- [设计] **AI 取上下文只能走 Context API**：任何 agent / 副驾驶 / 生成动作要读本模块的节点与证据，
  一律通过 Context API 领取 Context Pack，**不得绕过服务平面直查 `claims` / `segments` 库表**。
  绕过即丢失权限判定（`permissionDecisionId`）与引用锚点，`uc-14-6` 的「AI 读到了什么」将不可重放。
- [设计] **验收是引用资格的闸门**：未通过验收的证据不能把节点推到 `已确认`，也不能作为决策依据被引用。
  与 `phase-1/00-core/uc-0-1`「引用必须指向不可变快照」及 D-30 一致。
- [设计] **D-33 过期知识规则**：知识超过有效期后转「**待复核**」态，**仍在检索范围内**、仍可被展示与引用，
  引用时必须提示「已过期」；但**不参与定题强度计算**——不计入证据量权重、不推动状态升级、
  不作为「已确认」的充分条件。
- [设计] AI/Agent（如 Warden、Scout）产出的节点与关系必须带机器产出标识与来源，
  且同样受「组长确认才写回」的闸门约束。
- 所有权限判断必须在服务端执行；隐藏入口只是界面表现，不构成安全控制。
- 任何覆盖、删除、撤销、签署、发布、写回或停用动作都必须记录审计事件，并显示动作影响范围。

  - 来源引用与版本遵循 `phase-1/00-core/uc-0-1`：**引用必须指向不可变快照**；

- **[设计] 检索策略**：本模块的节点/证据检索走 **query-planned hybrid**，不是 graph-first——
  **五路并行召回**（PostgreSQL FTS 精确匹配术语与原话 + pgvector 语义 + 图关系 +
  元数据（项目/来源/时间/组）+ 已审核 Claim）→ **RRF 或加权融合** → **rerank** →
  去重与支持/反驳平衡 → Context Pack Builder 按 token budget 压缩。
  理由（架构第四节）：现场新入图的节点尚未完成实体链接，纯图优先会**直接漏召回**刚产生的证据，
  而本屏的立身之本恰恰是「15 秒内看见最新的关系」。
- **[设计] 图投影：阶段一不启用 Apache AGE**。先用 **`ontology_edges` + recursive CTE** 做
  节点关系的多跳查询；确有复杂路径性能需求，再用真实性能数据决定是否上 AGE
  （见架构第六节与落地顺序 P3）。本模块的验收命令不得依赖 AGE 语法。
- **技术约束**：[原型] 产品为响应式网页（原型含移动端对照屏）；[Backlog] 完整离线模式、原生移动端、第三方 IM 与产品内自助计费为范围外。
- **[设计] 租户与项目隔离在 PostgreSQL RLS 层强制**：本模块的全部读写走受 RLS 约束的
  **非 owner** 数据库角色（PG 中表 owner 默认不受 RLS 限制，用 owner 连接等于 RLS 形同虚设）；
  R5 的权限判定与 V11 的越权断言是**第二道**防线，不是唯一防线。
- **[已裁决 O-25]** 「证据量」的计数口径：原问题为「是**证据条数**还是**来源条数**」（原型同时出现
  「9 来源」「2 段」「7 次」三种量词），需统一定义后才能做强度计算。
  **裁决（O-25）**：计数口径统一为「**独立来源条数**」——同一份材料被引用三次只计 1。
  与 O-16「独立受访者人数」同源思路（避免同一来源反复自证）。
  界面上的「9 来源 / 2 段 / 7 次」三种量词统一改为**独立来源条数**一种量纲；
  实现上 `evidence_count = COUNT(DISTINCT artifact_id)`，
  按 `claim_evidence.relation` 分别计支持数与反对数。
- **[已裁决 O-25]** 「定题强度」的具体计算公式（D-33 只裁决了过期知识不参与，未给算法本体）。
  **裁决（O-25）**：先落**最简可验收形式**——
  `定题强度 = 支持的独立来源数 − 反对的独立来源数`。
  分档阈值后续可调（属可配置参数，不硬编码）。该形式可立即写 verification，
  并天然承接 D-33「过期/不确定知识不参与计算」——过期证据从两侧计数中一并剔除。
- **[待确认]** 知识有效期默认值与允许区间（D-14 列为五个留存参数之一，仍待合规负责人给出）。
- **[已裁决 O-34]** 容量基线（保守值，来自一场线下工作坊的物理上限）：单项目在场 **60 人**（8–10 组 × 6 人 + 引导师团队）、组织并发项目 **20**、单场音频 **8 小时**、单项目材料 **5 GB**、历史 **3 年 × 200 项目**。⚠ **无本项目实测依据，需产品确认**；确认前各 UC **不写性能类 AC**，不阻塞开工

- **[设计] 架构对齐 · Context Engine**（`docs/architecture/context-engine.md`，2026-07-28 定稿）：
  - **AI 取上下文只能通过 Context API 领取 Context Pack**——任何 agent、副驾驶或生成动作
    都不得绕过服务平面直查 `claims` / `segments` / `artifact_versions` 等库表。
    绕过即丢失 `permissionDecisionId` 与引用锚点，`uc-14-6`「AI 读到了什么」将不可重放。
  - **编排边界**：**LangGraph 只用于深度研究、人工确认（HITL）与多阶段生成**；

    LangGraph 不得被当作通用任务队列；HITL 用动态 `interrupt()`，节点恢复时副作用必须幂等。
  - **权限**：**租户与项目隔离在 PostgreSQL RLS 层强制**，应用连接使用受 RLS 约束的

## R12 AI Ready 验收线索

以下行为应可由自动化测试、接口断言或可复现人工步骤验证：

- V1（枚举断言）：AC3 —— 关系类型字段的可取值集合**恰为** `{被证据支持, 可能缩短, 阻碍, 硬约束, 候选方案}`；
  提交第六个值（如 `相关`）时接口返回校验失败，且库中无该记录。
- V2（枚举断言）：AC3 —— 节点状态字段的可取值集合**恰为** `{已确认, 冲突, 待确认}`；
  接口返回的任一节点的 status 都落在该集合内。
- V3（溯源断言）：AC1 —— 对列表中每条关系断言 `source_group`、`source_module`、`evidence_count`、
  `timestamp` 四个字段**均非空**；点击后返回的下钻目标带原始便签 ID 或转写时间码 + 版本号。
  以原型数据构造：断言存在一条「第 3 组 / 研究模块 / 9 / 12:05」的关系。
- V4（刷新断言）：在 T0 于画布确认一个新节点，轮询全场事实关系接口；断言 **≤15 秒**内该关系出现在
  返回列表中；同时断言页面刷新后滚动位置与展开状态未重置。
- V5（写回闸门）：AC —— 创建一个**未经组长确认**的节点，调用写回队列查询接口，断言其**不在**队列中；
  组长确认后再查，断言其**在**队列中且带确认人与时间。
- V6（冲突态）：构造两条互斥事实 → 断言两端节点 status 变为 `冲突`、双向边存在、
  主持台【冲突待判定】计数 +1；断言系统**未**自动删除任一方。
- V7（反对证据不可删）：对冲突节点的反对方证据调用删除接口 → 断言返回拒绝；
  遍历全部筛选器组合，断言反对证据在任一组合下都仍可见。
- V8（验收闸门）：挂一条**未通过验收**的证据到节点 → 断言节点 status 仍为 `待确认`，
  且该证据不出现在「可被决策引用」的引用选择器候选中。
- V9（D-33 过期知识）：把一条证据的有效期改为已过期 → 断言：
  ① 它**仍出现**在检索结果与关系列表中；② 展示与引用时带「已过期 · 待复核」标记；
  ③ 该节点的**定题强度数值不变**（过期前后强度计算结果相同），且状态不因它升为 `已确认`。
- V10（合并去重）：让第 1 组与第 3 组分别提出同一事实 → 断言节点数只增 1，
  来源行有 2 条且分属两组，证据量为两组之和。
- V11（权限态）：逐一以 引导师 / 组长（本组、他组）/ 组员 / 项目负责人 / 观察者 / 未授权用户 调接口；
  断言仅本组组长能对本组节点执行确认；观察者返回中不含 `冲突`/`待确认` 节点的反对证据明细。
- V12（空态）：本场零关系时接口返回空数组、页面显示真实空态与「去本组画布」入口，
  断言返回体中不含任何示例/mock 关系。
- V13（依赖失败）：断开实时通道 → 断言页头显示「非实时 · 最后更新 hh:mm」，
  最后一次成功快照保留，恢复后能补齐断链期间产生的节点。
- V14（并发态）：两个会话同时修改同一合并节点 → 断言无静默覆盖，返回版本冲突提示并可对比。
- V15（审计态）：节点确认、冲突标记、来源合并三类动作均可按操作者、时间、对象、结果检索；
  越权尝试也留安全审计记录。
- V16（**Claim 字段契约** · [设计]）：对任一节点读 `claims` 行，断言七个必备字段均存在且类型正确：
  `status ∈ {proposed, reviewed, accepted, contested, superseded}`、`confidence`、`valid_from`、
  `valid_to`、`created_by ∈ {human, model, import}`、`reviewed_by`、`supersedes_claim_id`；
  断言界面三态徽标与 `status` 的映射恒成立（`accepted→已确认`、`contested→冲突`、
  `proposed|reviewed→待确认`），且 `superseded` 的节点不在本屏列表中但仍可按 ID 读到。
- V17（**定题强度公式** · O-25）：构造一个节点，挂 4 个不同来源的支持证据（其中 1 个来源被引用 3 次）
  与 1 个来源的反对证据 → 断言 `evidence_count`（支持）＝ **4**（不是 6，去重生效），
  定题强度 ＝ **4 − 1 = 3**；再把其中一条支持证据置为过期 → 断言强度变为 **3 − 1 = 2**（D-33 生效）。
- V18（**冲突成对召回** · [设计]）：对一对互斥 Claim 调 Context API 请求 Context Pack →
  断言返回的 `claims[]` 中**两条同时存在**，各自的 `supportingSegmentIds` 与
  `contradictingSegmentIds` 均非空；重复调用 10 次，断言**没有任何一次**只返回其中一方。
- V19（**contradicting 不可删** · [设计]）：直接对 `claim_evidence` 中 `relation = contradicting`
  的行调用删除接口 → 断言拒绝且行仍在；断言该行只能通过 Claim 的 `superseded` 或
