## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case ID / 名称**：UC-9.2 / 决策树与岔口
- **Actor**：**引导师**（项目角色，主使用者）、**组长**（项目角色）、
  **项目负责人**（组织角色，原文档称「项目经理」，见 `phase-1/00-core/uc-0-3`）
- **目标**：[原型] 把散在四组的判断收成一棵**从主题到可执行选择**的树——
  「节点＝一个决策或选项，边上写的是判定依据」，让引导师一眼看出**已经定了什么、还卡在哪个岔口、
  缺什么才能拍板**。
- **本用例结果**：[原型] 决策树子视图上呈现四块内容：
  ① **决策树主体**（节点带七态 + 支持/反对计数 + 归属组；边上带判定依据文案）；
  ② **【待决的岔口 · N】** 清单（每个岔口列选项，**每个选项显示已有证据数**，并写明成立/不成立的后果）；
  ③ **已否决分支**（保留但淡出，可回溯否决理由与判定时间）；
  ④ **【图谱推演 · 如果现在拍板】** 预判文本（选某分支会关掉几个待验证节点、省多少工作量、建议先验哪条）。
- **系统边界**：决策树的节点与边、七态判定、支持/反对计数、岔口抽取与选项证据数、否决留痕、拍板预判生成；
  **不含**事实关系入图（UC-9.1）、工作卡派发（UC-9.3）、流水线矩阵（UC-9.4）。
- **核心数据对象**：决策节点、候选选项、判定依据（边标签）、支持/反对证据计数、岔口、否决记录、预判文本。

## R2 前置条件 / 触发条件

- **前置条件**：
  - 用户已建立可校验的正式或临时身份，且拥有目标组织、项目、小组或资源的访问权。
  - 目标资源存在且未被删除/冻结；依赖能力「可视化模板/画布便签（节点来源）、实时转录（证据来源）、研究模块与访谈模块（证据来源）」可用，或界面能明确显示其不可用状态。
  - 若动作涉及个人数据、录音、原始材料或跨范围读取，相应授权与留存策略已生效。
- **触发条件**：
  - [原型] 引导师在全场视图打开 `知识图谱 → 决策树`（三子视图默认落在决策树）。
  - [设计] UC-9.1 的节点状态变化（新增/合并/转冲突/被确认）触发决策树增量重算。
  - 系统从 **决策树画布** 进入本流程，并携带当前组织、项目、小组、角色和资源标识。

## R3 主流程（编号步骤，写清楚谁做什么、系统怎么响应）

1. **引导师操作**：打开 `知识图谱 → 决策树`。
   **系统响应**：[原型] 以**主决策为根**渲染树——原型实例根节点「以什么模式进入欧洲」【在议】，
   副标题写清约束与参与面（「18 个月内交付首个并网项目 · 四组共同推演」），
   其下挂三条候选路径分支。页头写「节点＝一个决策或选项，边上写的是判定依据」，并给出七态图例。
2. **系统处理**：为每个节点计算并渲染**七态之一**——
   `领先` / `在议` / `待验证` / `待决` / `冲突` / `已否决` / `建议`。[原型] 原型实例：
   - 收购已备案主体　**【待验证】**「最快，但资质能否随主体转存疑」· 支持 3 · 反对 2
   - 与本地 EPC 合资　**【领先】**「时间与本地化率都能过」· 支持 7 · 第 2、4 组
   - 自建实体　　　　**【已否决】**「18 个月内做不完 · 时间约束 · 11:20 判定」
   - 资质可随股权转移？　**【冲突】**「决定收购分支是否还活着 · 两处来源互相矛盾」
   - 合资对象选谁　　**【待决】**「EPC / 电网侧顾问 / 分销商 · 第 2 组正在比选」
   - 首个 MVP 范围　**【建议】**「保底条款＋月度归因看板 · 图谱推演·尚未讨论」
3. **系统处理**：为每个节点渲染 **「支持 N · 反对 M」** 计数，计数来自 UC-9.1 的证据挂载；
   并标出该结论由哪几个组提出（「第 2、4 组」）。[原型]
   **`已否决` 节点必须同时带判定依据与判定时间码**，保留但淡出，可展开回溯为什么否决。
4. **系统处理**：为每条边写上**判定依据文案**。[原型] 六个取值：
   `最快路径` / `满足硬约束` / `时间不够` / `先验这条` / `选定后可谈条款` / `决定谈判筹码`。
   [设计] 该枚举**封闭**；无判定依据的边不得渲染——边必须解释「凭什么从父节点走到这个子节点」。
5. **系统处理**：抽取所有 `待决` / `冲突` 节点，汇成 **【待决的岔口 · N】** 分区（原型实例 N=3）。
   [原型] 每个岔口一块，含：**后果说明**（「成立则…不成立则…」）+ **选项行**，
   **每个选项后缀已有证据数**：
   - 资质可随股权转移吗　「成立则收购分支省 3 个月；不成立则整支关掉」
     　可转·走收购 **(证据 2)** ｜ 不可转·只剩合资 **(证据 3)**
   - 合资对象选谁　　　　「决定谈判筹码与本地化率算法」
     　本地 EPC **(访谈 2)** ｜ 电网侧顾问 **(证据 1)** ｜ 分销商 **(无)**
   - 首单是否给收益保底　「决定 MVP 范围与售后成本」
     　给保底＋归因看板 **(概念卡 1)** ｜ 纯 EPC 交付 **(证据 2)**
   证据数为 0 的选项显式显示「(无)」，**不得省略该选项**。
6. **系统处理**：生成 **【图谱推演 · 如果现在拍板】** 预判文本——对当前领先分支模拟拍板，
   算出：会**关掉几个待验证节点**、**省多少工作量（人日）**、以及**若某条冲突成立能省多少时间**，
   并给出行动建议。[原型] 原型实例：
   「选『本地 EPC 合资』会关掉收购分支下的 4 个待验证节点，工作量少 6 人日；
   　但『资质可转』这条如果成立，收购分支能省 3 个月。**先验资质，再拍板。**」
7. **系统处理**：把**图谱建议的未来节点**（`建议` 态）明确标注「**尚未讨论**」，
   与已讨论节点不可混淆。[原型]（原型节点行原文「首个 MVP 范围 【建议】…图谱推演·**尚未讨论**」）
   [设计] 用**虚线**渲染。
   ⚠ 决策树图例只有 `领先 ｜ 在议/待决 ｜ 冲突 ｜ 图谱建议` **四项文字，无任何线型说明**；
   「虚线」出自**推演流水线**的图例（`虚线＝图谱建议的下一步`），是另一屏的对象。
   线型选择属视觉设计，须人类确认。（Backlog UC-9.2 `edge` 亦写「图谱建议的未来节点用虚线，
   明确标注还没讨论」——即该规则来源是 **[Backlog]**，不是原型。）
8. **引导师操作**：点击任一节点或岔口选项。
   **系统响应**：下钻到支撑它的证据清单（回到 UC-9.1 的事实关系与原始来源），
   并给出「派一条工作去验它」的入口（转 UC-9.3）。
9. **系统收口**：记录查看、下钻、否决、拍板等动作的操作者、时间、对象、结果与来源进审计；
   决策树状态变化后同步刷新【待决的岔口】计数与【如果现在拍板】预判文本。

## R4 备选流程与异常流程

- **备选流程**：
  - A1：[Backlog] **被否决的分支保留但淡出，可回溯为什么否决**（Backlog `edge` 原文）；
    [原型] 否决理由与判定时间可见（「18 个月内做不完 · 时间约束 · 11:20 判定」）。
    [设计] 若后续证据推翻否决理由，该分支可被**复活**，复活动作留痕并保留原否决记录。
    ⚠ **「复活」在 proto-01~10 十份档案与 Backlog 中均不存在**——它是本文新造的能力，
    不是「原型未探明」（说它未探明等于预设它存在）。
  - A2：[设计] 主决策尚未确立（树只有零散节点、无根）时，显示「还没有形成主决策」的空态，
    并列出候选主决策供引导师指定为根，**不得**自动挑一个节点当根。
  - A3：[设计] 岔口的所有选项证据数均为 0 时，该岔口仍列出，并标注「三个选项都没有证据，
    建议先派研究/访谈」，直接链到 UC-9.3。
  - A4：[设计] `建议` 态节点（图谱推演产生、尚未讨论）不参与「支持 N · 反对 M」计数，
    也不计入【待决的岔口】数量。
- **异常流程**：
  - E1：[Backlog] 图谱建议的未来节点必须用**虚线**并标注「还没讨论」（Backlog `edge` 原文）；
    [设计] 实现上不得把 `建议` 态渲染成与已讨论节点相同的实线样式（会让人误以为已达成共识）。
    （「尚未讨论」标注 [原型] 可证；**线型 [Backlog]/[设计]**，原型图例无线型。）
  - E2：[设计] 【如果现在拍板】的预判依赖的数据不全（如某分支缺工作量估算）时，
    只输出能算出的部分并显式标注「工作量数据不足，未计入」，**不得**编造数字。
  - E3：[设计] 请求超时、网络中断或依赖不可用时，保留最后成功渲染的树，明确失败原因并提供安全重试；
    不得把过期的树伪装成实时态。
  - E4：[设计] 同一节点被并发改状态（两人同时把一个节点判为否决/在议）时不得静默覆盖；
    提示版本已变化，允许刷新、对比或重新提交。
  - E5：[设计] 权限在操作过程中被撤回时立即终止后续写操作；已完成步骤按审计规则保留，
    未提交输入留在本地草稿并提示重新授权。

## R5 权限与可见性

- **引导师**：可查看全场决策树、改节点状态、否决/复活分支、生成拍板预判、从岔口派工作（转 UC-9.3）。
- **组长**：可查看全场决策树；可为**本组**负责的节点补证据、提出状态变更建议；**不能**直接否决分支。
- **组员**：只读查看决策树；不能改状态、不能否决。
- **项目负责人**（组织角色，原文档称「项目经理」）：在被授权项目内只读查看全树与否决理由。
- **观察者**：只读查看 `领先` / `在议` / `已否决` 节点与结论；`冲突` 节点的双方证据明细、
  各组支持/反对的**具体归属人**默认不对观察者展开。
- **AI / Agent**：适用 **R7【决策节点 AI 不可写入】**（该规则的**唯一权威表述在 R7**，本处只引用不复述）：
  AI/Agent **只能**产出 `建议` 态候选节点与【图谱推演 · 如果现在拍板】预判文本；
  **不能**创建、修改或删除任何非 `建议` 态节点，**不能**改状态、否决、复活或拍板。
- **未登录、链接失效或未列出的角色**：默认无权限；接口不得返回越权数据，不能只依赖前端隐藏。

## R6 后置条件 / 不包含

- **正常后置条件**：
  - 决策树反映当前真实推演状态：每个节点有明确的七态之一，每条边有判定依据。
  - 【待决的岔口 · N】的 N 等于当前 `待决` + `冲突` 节点数；每个选项的证据数与 UC-9.1 的实际挂载一致。
  - 已否决分支可回溯理由与判定时间；被否决不等于被删除。
  - 【如果现在拍板】预判文本可生成，且随节点状态变化重新计算。
  - [Backlog验收] AC1：能一眼看出现在卡在哪个岔口、缺什么才能拍板（Backlog UC-9.2 `ac` 原文）；
    原型【待决的岔口 · 3】+ 每选项证据数可佐证。
  - [设计验收] AC2：节点状态枚举**恰为**七值（**取值 [原型] 可证，「恰为」属闭合性设计约束**）；
    [原型] `已否决` 节点携带理由与时间码（原型「自建实体 …时间约束 · 11:20 判定」）。
  - [原型验收] AC3：每个岔口选项显示已有证据数，0 证据显式显示「(无)」
    （原型「分销商 (无)」可证）。
  - [Backlog验收] AC4：`建议` 态节点以**虚线**呈现（Backlog `edge`）
    并标注「尚未讨论」（[原型] 可证），不与已讨论节点同样式。
  - [设计验收] AC5：**R7【决策节点 AI 不可写入】成立**——所有非 `建议` 态节点的创建与状态变更，
    其**操作者字段恒为自然人**（措辞以 R7 为准，本处不另行表述）。
- **失败后置条件**：
  - 不创建“看似成功”的正式记录；可重试内容保留为草稿，失败事件进入可观测日志。
  - 预判算不出时输出「数据不足」，不产出看似精确的编造数字。
- **不包含**：
  - AI 无人确认自动写成正式结论、自动消解冲突、自动替人拍板。
  - 事实关系入图与溯源（UC-9.1）、工作卡派发（UC-9.3）、流水线矩阵（UC-9.4）。
  - 不扩展到本 use case 未声明的跨组织、跨客户或公开发布能力。

## R7 业务规则（不随具体实现变化的硬性约束）

- [原型] **节点状态的七个取值**：
  `领先` / `在议` / `待验证` / `待决` / `冲突` / `已否决` / `建议`（原型七态图例与节点实例逐个可证）。
  [设计] 该枚举**封闭**：服务端校验，枚举外的值一律拒绝（闭合性与服务端拒绝属实现约束）。
  （**[Backlog]** UC-9.2 `flow` 只列五态「领先 / 在议 / 待验证 / 冲突 / 已否决」，
  原型多出 `待决` 与 `建议` 两态，本文以原型为准补齐。）
- [Backlog] **边上标判定依据**（Backlog `flow`「边上标判定依据（满足硬约束、时间不够…）」）；
  [原型] 判定依据的六个取值：
  `最快路径` / `满足硬约束` / `时间不够` / `先验这条` / `选定后可谈条款` / `决定谈判筹码`。
  [设计] 该枚举**封闭**，且无判定依据的边不得渲染。
- [原型] **每个节点带「支持 N · 反对 M」计数**，计数来源于 UC-9.1 挂载的证据，不得手工填写；
  反对计数不可被隐藏（与 UC-9.1「反对证据必须留存」同源）。
- [原型] **`已否决` 节点同时保留判定依据与判定时间码**，分支保留但淡出，可回溯；
  否决不等于删除，任何时候都能查到「谁在几点、凭什么否决了它」。
  [设计] **可复活**——「复活」是本文新造的能力，档案零命中，须人类确认是否纳入范围。
- [原型] **【待决的岔口】的每个选项必须显示已有证据数**；证据数为 0 的选项显示「(无)」，不得省略。
- [原型] **每个岔口必须带后果说明**（「成立则…不成立则…」），说明这个岔口决定了什么。
- [原型] **`建议` 态（图谱推演产生的未来节点）标注「尚未讨论」**（原型节点行原文）。
  [Backlog] 用**虚线**渲染（Backlog `edge`）；**原型图例无线型**，见 R3 第 7 步。
  [设计] 不参与支持/反对计数，不计入待决岔口数。
- [原型] **【图谱推演 · 如果现在拍板】必须给出可核对的量化项**：关掉几个待验证节点、省多少工作量、
  以及「先验哪条再拍板」的建议；量化项缺数据时标注「数据不足」而非编造。
- [设计] 决策树是 UC-9.1 事实关系的**投影**，节点与证据的唯一事实来源在 UC-9.1；
  决策树侧不得独立新建脱离证据的节点。
- [设计] 拍板本身是**人的动作**，系统只做预判与建议；不存在「系统自动选定分支」的路径。
- [设计] **【决策节点 AI 不可写入】**（本用例最强的一条治理闸门；**本条是该规则的唯一权威表述**，
  R5 与 AC5 只引用不复述。与 14-brain 决策台账
  「**拍板栏只能是人名**」是**同一条规则的两侧**，必须共用同一套服务端校验）：
  - AI/Agent **只能**产出 `建议` 态候选节点，以及【图谱推演 · 如果现在拍板】的预判文本；
  - AI/Agent **不能**创建、修改或删除任何 `领先` / `在议` / `待验证` / `待决` / `冲突` / `已否决`
    状态的节点，**不能**改变节点状态、不能否决分支、不能复活分支、不能拍板；
  - 所有非 `建议` 态节点的创建与状态变更事件，其**操作者字段恒为自然人**，服务端强制校验，
    把 agent 主体写进操作者位应当被**拒绝**；agent 的贡献只记在「来源 / 执行者」字段
    （与 D-39「负责人恒为人、agent 记在执行者字段」同源，见 UC-9.3）。
  - 这条闸门不因「AI 置信度高」「引导师事先授权」而放宽；预判文本再确定也只是建议。
- 所有权限判断必须在服务端执行；隐藏入口只是界面表现，不构成安全控制。
- 任何覆盖、删除、撤销、签署、发布、写回或停用动作都必须记录审计事件，并显示动作影响范围。

  - 节点状态口径：UC-9.1 的三态（已确认/冲突/待确认）是**证据视角**，本用例的七态是**决策视角**，
    二者是两套字段、不可互相顶替；映射规则见下方 **[已裁决 O-25]** 的显式映射表。
  - [设计] 两套状态的**共同底座**是 Context Engine 的 `claims.status`
    （`proposed` / `reviewed` / `accepted` / `contested` / `superseded`，见 `uc-9-1` R1）：
    证据视角三态是 `claims.status` 的直接投影，决策视角七态是「`claims.status` × 决策位置」
    的二维投影。**落库只有一份 `claims.status` + 一个独立的 `decision_state` 字段**，
    两个展示视角都从这两个字段推导，不得再造第三套状态词。
  - 证据引用遵循 `phase-1/00-core/uc-0-1`：引用必须指向不可变快照。
  - 身份与权限沿用 `phase-1/00-core/uc-0-3` 的两层角色模型。
- **技术约束**：[原型] 产品为响应式网页（原型含移动端对照屏）；[Backlog] 完整离线模式、原生移动端、第三方 IM 与自助计费为范围外。
- **[已裁决 O-25]** **UC-9.1 三态与本用例七态的映射规则**——原问题：例如 UC-9.1 的 `冲突`
  是否恒等于本树的 `冲突`，`待确认` 落到 `待验证` 还是 `待决`。不定则两屏会出现互相矛盾的状态。
  **裁决（O-25）**：**两套字段并存、不可互相顶替**（本文档原有声明确认有效），
  并由本模块在实现前给出**一张显式映射表，不得由实现者推断**。该表即为下表，**服务端校验**：

  | UC-9.1 证据视角三态 | `claims.status` | 本树决策视角七态（允许集） | 说明 |
  |---|---|---|---|
  | `已确认` | `accepted` | `领先` / `在议` / `已否决` | 证据已立住；落哪一态由**决策位置**决定，不由证据决定 |
  | `冲突` | `contested` | `冲突` | **恒等映射**，唯一的一对一：证据互斥 ⇒ 决策必为 `冲突` |
  | `待确认` | `proposed` / `reviewed` | `待验证` / `待决` / `建议` | 缺证据⇒`待验证`；有证据待人拍板⇒`待决`；系统建议⇒`建议` |

  **不变式（服务端强制，三条）**：
  ① `冲突` 双向恒等——证据态为 `冲突` 的节点在本树必为 `冲突`，反之亦然；
  ② `已确认` 的节点**不得**落 `待验证`（证据已立住却说"待验证"是自相矛盾）；
  ③ `待确认` 的节点**不得**落 `领先`（无立住的证据不得被标为领先方案）。
  违反任一不变式时接口拒绝写入，不得静默取某一侧为准。
- **[已裁决 O-25]** 「支持 N · 反对 M」的计数口径（原问题：证据条数 / 来源条数 / 组数），
  须与 UC-9.1 的证据量口径统一。
  **裁决（O-25）**：与 UC-9.1 同口径——**独立来源条数**（同一份材料引三次只计 1）。
  支持数 ＝ `claim_evidence` 中 `relation = supporting` 的 `COUNT(DISTINCT artifact_id)`，
  反对数同理取 `contradicting`；过期证据（D-33 待复核态）两侧均不计入。
  「组数」不作为计数量纲，只作为**来源行的分组展示维度**。
- **[待确认]** 【如果现在拍板】的**工作量估算来源**（人日数据从哪来：工作卡估时汇总？历史项目均值？）。
- **[待确认]** 「先验这条」建议的排序算法（按能关掉的节点数？按证据缺口？按时间收益？）。
- **[已裁决 O-34]** 容量基线（保守值，来自一场线下工作坊的物理上限）：单项目在场 **60 人**（8–10 组 × 6 人 + 引导师团队）、组织并发项目 **20**、单场音频 **8 小时**、单项目材料 **5 GB**、历史 **3 年 × 200 项目**。⚠ **无本项目实测依据，需产品确认**；确认前各 UC **不写性能类 AC**，不阻塞开工

- **[设计] 架构对齐 · Context Engine**（`docs/architecture/context-engine.md`，2026-07-28 定稿）：

## R12 AI Ready 验收线索

以下行为应可由自动化测试、接口断言或可复现人工步骤验证：

- V1（枚举断言）：AC2 —— 节点状态字段的可取值集合**恰为**
  `{领先, 在议, 待验证, 待决, 冲突, 已否决, 建议}`（7 个）；提交枚举外的值返回校验失败。
  以原型数据构造树后，断言这 7 个值**至少各出现一次**。
- V2（枚举断言）：边的判定依据字段取值落在
  `{最快路径, 满足硬约束, 时间不够, 先验这条, 选定后可谈条款, 决定谈判筹码}` 内；
  遍历全部边断言**无一条边的判定依据为空**。
- V3（计数断言）：对每个节点断言 `support_count` 与 `oppose_count` 均存在且为非负整数，
  且等于 UC-9.1 中挂到该节点的支持/反对证据数。以原型数据断言
  「收购已备案主体」= 支持 3 · 反对 2，「与本地 EPC 合资」= 支持 7。
- V4（否决可回溯）：AC2 —— 对 `已否决` 节点断言 `reject_reason` 与 `rejected_at` 非空
  （原型：「18 个月内做不完」/「时间约束」/`11:20`）；断言该节点**仍在**树查询返回结果中
  （保留但淡出，未被删除）。
- V5（岔口证据数）：AC3 —— 断言 `/decision-tree/forks` 返回的岔口数 = `待决` + `冲突` 节点数
  （原型 = 3）；每个岔口的每个选项都带 `evidence_count` 字段；
  断言「分销商」选项的 `evidence_count = 0` 且**该选项仍出现在返回列表中**（渲染为「(无)」）。
- V6（岔口后果）：断言每个岔口对象的 `consequence` 字段非空
  （原型：「成立则收购分支省 3 个月；不成立则整支关掉」）。
- V7（建议态虚线）：AC4 —— 断言 `建议` 态节点带 `is_suggested=true` 与 `discussed=false`，
  前端 DOM 上该节点携带虚线样式标记（`data-testid` 可断言），且**不计入**岔口数与支持/反对计数。
- V8（预判可生成）：调用预判接口 → 断言返回文本非空且包含三个结构化字段：
  `closed_nodes`（关掉的待验证节点数，原型 = 4）、`saved_effort`（省的工作量，原型 = 6 人日）、
  `recommendation`（建议先验哪条，原型 = 「先验资质，再拍板」）。
- V9（预判降级）：抽掉工作量数据后再调预判 → 断言 `saved_effort` 返回 null 且文本带
  「数据不足，未计入」，**不返回任何编造数字**。
- V10（预判重算）：把一个 `待验证` 节点改为 `已否决` → 断言预判的 `closed_nodes` 随之变化，
  且【待决的岔口】计数同步更新（≤3 秒）。
- V11（权限态）：逐一以 引导师 / 组长 / 组员 / 项目负责人 / 观察者 / 未授权用户 调接口；
  断言仅引导师可执行否决与状态变更；观察者返回中不含冲突节点的双方证据明细与个人归属。
- V12（**决策节点 AI 不可写入**）：AC5 —— 以 agent 身份（Scout / Warden / Ledger）逐一调用：
  ① 创建 `待决` 节点；② 把某节点由 `待验证` 改为 `领先`；③ 否决某分支；④ 复活已否决分支 ——
  断言**四项全部返回拒绝**，且库中无对应变更。以同一 agent 身份创建 `建议` 态节点则**允许**。
- V13（操作者主体断言）：遍历决策树的全部状态变更审计事件，
  断言每条的 `actor` 主体类型**恒为自然人**（无一条为 agent/system）；
  断言该校验与 14-brain 决策台账「拍板栏只能是人名」走**同一个服务端校验入口**
  （同一错误码 / 同一拒绝语义）。
