# design delta 签核 · 开工之前把上下文收集够（迭代 13）

⚠ `status`、`confirmed_by`、`confirmed_at` 只能由人类修改；agent 不代签
（ADR-023 / AGENTS.md「设计签核（三件、一处签）」）。**我把 `status` 留在 `draft`。**

规范唯一来源：[`contract.md`](./contract.md)。验收口径：[`verification.md`](./verification.md)。

## 这份 delta 为什么存在

人类 2026-09-08 交办六件事。前四件是同一个主题——**设计开工之前，把上下文收集够**：

1. 图片作为输入（拖拽 + 按钮）
2. 已有 chat session 作为上下文
3. 取消工作台顶部那三张模板卡片
4. **新建时先问问题、再进设计界面**

第 4 条是这里面最重要的。今天的「新建设计」是三个字段（类别 / 名称 / 背景可选），
背景那行占位符写着「想解决的问题、谁会用、现在怎么绕过去的」——**这已经是在提示
该收集哪些数据了，只是把它塞进一行灰字，而且可选**。结果是大多数项目带着一句话
甚至空背景就进了画布，模型只能靠猜，画出来自然不像。

第 3 条「取消三张模板卡片」不只是省地方：它让「挑一个模板」成了流程第一步——
用户还没说清要做什么，就先被要求选一个设备形态。而设备形态本该是**澄清完之后**的结论。

**另外两件（第 5、6 条）是不同主题**，见 contract §4：列表最新在前、卡片标签与过滤。

**再加三件（第 7–9 条，issue #3125）**，见 contract §5——人类实测后的原话是
「现在出来的页面很不专业」。核实下来是三件事：
① **`frontend-design` skill 就在仓库里，但设计对话的 prompt 完全没引用它**——
现用的 `DESIGN_PRINCIPLES` 八条全是布局结构，**一个字没讲视觉**；
② 原型不能独立切白天/黑夜（跟随后台主题）；
③ 属性面板只能改内容，不能调视觉。

并进同一个 delta 只是为了一次交付，评审时可以分开看。

**好消息是不用从零造**：视觉输入（`ModelCallInput.images` + `visionModelIds` 门控）、
图片上传（反馈附件那条路，按字节嗅探类型、限额、鉴权下载）、线程读取
（`listThreads` / `getThread`）**三条管线都已经在仓库里**。

**好消息是不用从零造**：视觉输入（`ModelCallInput.images` + `visionModelIds` 门控）、
图片上传（反馈附件那条路，按字节嗅探类型、限额、鉴权下载）、线程读取
（`listThreads` / `getThread`）**三条管线都已经在仓库里**。本 delta 主要是把它们接起来。

**先签后做**：新增两个操作、一张表、`appendProjectChat.in` 加一个字段——covers 追加
三条件一条都不满足，所以走 design-delta。

## ① UI

见 [contract.md](./contract.md) §1.4、§2.3。⚠ **这一件目前只有文字，没有截图**——
按 ADR-003「UI 先行」，签核前应由 ui-prototyper 把下面四屏做出来拍进
[`ui.md`](../../contracts/design-prototype/ui.md)：

1. **澄清问答流程**（写 brief → 问题列表 → 逐条回答 → 指导原则预览）；
2. 输入框上方的参考图条（缩略图 + 删除）、拖拽悬停高亮；
3. 线程选择器 + 导入预览；
4. 工作台新样子（没有三张模板卡片、有标签 chip 过滤条）。

**要你确认的：**
- 澄清问答是**一屏一题**还是**一次列出全部**？（我按一次列出——能一眼看到要答几题，
  也方便跳着答；一屏一题更专注但像问卷调查）
- 「类别」在澄清之后由模型建议、用户可改——**还是**干脆不问，由模型直接定？
- 拖拽的放置区是整个对话面板还是只有输入框？（我按整个面板，少一次瞄准）

## ② 用例

见 [verification.md](./verification.md) V51–V66。重点看**失败模式**：

- 澄清问题必须是**按这段 brief 生成的**，不是固定问卷念一遍（V61）；
- 模型不可用时**退回通用问卷并说明是兜底**，不是让整个新建流程失败（V62）；
- 跳过就是跳过，**后面不再拦**（V63）；
- 问答落地成既有的 `problem` / `criteria`，**不新增第四种事实源**（V64）；
- 排序与标签过滤都在**服务端**（V65/V66）——放前端的话，分页之后顺序和过滤都会不对；

- 参考图按**字节**判类型，不信 `Content-Type`（V51）；
- **模型看不了图时不发图，但必须在回复里说出来**（V54）——静默降级会让界面显示
  "图已上传"而模型根本没看过，这是本仓反复栽过的形态，**这条是本 delta 最重要的一条**；
- 导入是**一次性**的：线程后来变了，项目背景不跟着变（V57）；
- 导入**要确认才写**，不覆盖用户已写的 `problem`（V58）。

## ③ API 契约

见 [contract.md](./contract.md) §5。改动五处：

1. `appendProjectChat.in` **+1 可选字段** `refImageIds`（≤3）。
2. **新增两个操作**：上传参考图、导入线程。
3. **新增一张表** `design_project_ref_images`（RLS 同 `design_projects`）。
   **澄清问答不新增存储**：问题在前端内存里，答案随 `createProject` 交上来，落地就是
   `problem` / `criteria`。
4. 图片类型闭集**复用** `ModelCallImageMime`（V52 用集合相等钉住，不是"包含"）。
5. `DesignProject` **+1 字段** `refImages`（只有元信息，**不含字节**）。

**无新错误码**：上传复用附件那套既有闭集，导入线程复用 `DEPENDENCY_UNAVAILABLE`。

## 请人类拍板的三处取舍（`contract.md` §4）

| # | 取舍 | 建议 | 备选 |
|---|---|---|---|
| ① | 参考图张数上限 | **A** 3 张 | B 1 张 / C 6 张 |
| ② | 模型不支持视觉时 | **A** 不发图 + 回复里明说 | B 直接拒绝这次请求 |
| ③ | 导入线程的语义 | **A** 一次性摘要进 `problem`，可编辑 | B 长期挂靠该线程实时读 |
| ④ | 澄清问答能否整段跳过 | **A** 能，且跳过后不再拦 | B 至少答前两条才放行 |
| ⑤ | 属性面板的视觉调节 | **A** 只给设计系统的档位（枚举） | B 也给自由数值（px 输入框） |

签核时若与建议不同，把选择写在下面这行，agent 按它实现：

> 人类选择：① A ② A ③ A ④ A ⑤ A

**②③④值得你多花两分钟：**

- **②A** 让用户在看不了图的部署上仍能用文字推进（图白传了，但**他知道**）；B 更"诚实"
  但把人堵死。我建议 A，**前提是那句话必须说出来**。
- **③B（长期挂靠）听起来更强，但它让「这个设计是照什么做的」变成一个会变的东西**——
  线程后续改了，设计上下文就悄悄变了，而设计评审要的恰恰是一个定住的输入。
  B 也拿不出"当时导入的是什么"这个证据。
- **④A**：引导是帮忙，不是关卡。做成必答会让老手绕道，**而老手正是最可能带着完整
  上下文来的人**——把他们挡在问卷后面，收集到的反而更少。
