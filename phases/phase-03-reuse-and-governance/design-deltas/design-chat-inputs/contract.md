## §0 现状与要解决的事

人类 2026-09-08 交办**四件事**，它们是同一个主题的四个面——**设计开工之前，把上下文收集够**：

1. 「需要可以接受图片作为输入，可以拖拽，和按钮」
2. 「可以接受当前的某个 chatsession 作为上下文」
3. 「取消上面的三个按钮」（工作台顶部那排模板卡片）
4. 「在新建的时候列出一些需要收集的数据，来制定指导原则；可以让用户先输入一个问题或
   上下文，然后再生成一系列的问题要用户回答，然后再进入设计界面」

第 4 条是这四件里**最重要的**：它把「新建」从一次填表变成一次**澄清对话**。前三条都是
在给这次澄清补充输入渠道。

现在设计协作的输入**只有一句纯文本**（`appendProjectChat.in = { projectId, text, focusNodeId? }`）。
两个真实场景落不了地：

| 场景 | 今天只能怎么办 | 代价 |
|---|---|---|
| 「照着这张截图画」「风格参考这张」 | 用文字描述那张图 | 描述图片这件事本身就丢信息，且很费口舌 |
| 「我刚在 chat 里跟 AI 聊了半天需求，照那个做」 | 把聊天内容手动复制粘贴过来 | 几百上千字，粘完还占满输入框；粘漏了模型就画错 |

两者是同一类缺口：**上下文只能靠打字进来**。而更深一层的缺口是：**没人问用户该说什么**。

现在的「新建设计」对话框是三个字段：类别、名称、背景（可选）。「背景」的占位符写着
「想解决的问题、谁会用、现在怎么绕过去的」——**这已经是在提示该收集哪些数据了，
只是把它塞进了一行灰字，而且可选**。结果是大多数项目带着一句话甚至空背景就进了画布，
模型只能靠猜，画出来的东西自然不像。

## §1 参考图（输入其一）

### §1.1 接入点：复用既有的两条管线，不新造

- **上传**：反馈附件那条路已经有嗅探（`sniffDeclaredType`：按**字节**判类型，不信 `Content-Type`）、
  大小上限、存储与鉴权下载。设计项目的参考图复用同一套形状，**不另写一份上传实现**。
- **喂给模型**：`ModelCallInput.images` 与 `visionModelIds` 已经在端口上。设计对话此前从不传
  `images`，本 delta 开始传。

### §1.2 契约变化

```ts
// appendProjectChat.in 增加
refImageIds: z.array(z.string()).max(PROTOTYPE_MAX_REF_IMAGES).optional()
```

- 上限 **3 张**（`PROTOTYPE_MAX_REF_IMAGES`）：视觉输入按张计费且很贵，一次给三张已经足够
  说清「照这个画」；不设上限等于把成本敞口交给用户手滑。
- 单张 ≤ **4 MB**，类型闭集 `image/png | image/jpeg | image/webp`——与 `ModelCallImageMime`
  **同源**，不另立一个枚举。
- 图片**属于项目**（`design_project_ref_images`），不属于某一条消息：同一张参考图往往要在
  好几轮对话里反复被指着说。

### §1.3 模型侧

- 参考图随**每一轮**对话发给模型（骨架轮与每页轮都发）——不是只发第一轮。
  「照着这张画」在第 4 页仍然成立。
- ⚠ **模型不支持视觉时**：`visionModelIds` 不含当前 modelId ⇒ **不发** `images`，
  并在回复里**明说**「这个部署的模型看不了图，我按你的文字描述画的」。
  静默丢弃是本仓反复栽过的形态：界面显示图片已上传、模型根本没看过。

### §1.4 界面

- 输入框上方一条**参考图条**：缩略图 + 删除。
- **两种加图方式，同一条路径**：
  - 「＋ 参考图」按钮（`<input type="file" accept="image/*">`）
  - **拖拽**到对话面板任意位置——拖入时整个面板显示放置区高亮。
- 粘贴（⌘V）**也走同一条**——用户从截图工具复制过来是最常见的动作，不支持它等于逼人先存盘。

## §2 已有对话作为上下文（输入其二）

### §2.1 语义：一次性**导入摘要**，不是持续订阅

人类原话是「接受当前的某个 chatsession 作为上下文」。两种可能的读法，本 delta 取前者：

| | 做法 | 取舍 |
|---|---|---|
| **A（本 delta）** | 选一个线程 ⇒ 把它的内容**这一刻**抽成一段结构化摘要，写进项目的 `problem`，并作为一条系统备注进对话 | 一次性、可见、可编辑；用户能看到"导进来的是什么"并改它 |
| B | 项目**长期挂靠**某个线程，每轮对话都实时读它 | 线程后续变了会悄悄改变设计上下文；两个事实源随时间漂移 |

选 A 的理由：B 让「这个设计是照什么做的」变成一个会变的东西，而设计评审要的恰恰是一个
**定住的**输入。B 也拿不出"当时导入的是什么"这个证据。

### §2.2 契约变化

```
POST /pm-designs/:projectId/import-thread   { threadId }
  → { project: DesignProject, imported: { threadId, title, messageCount, at } }
```

- 只读**调用者自己有权读**的线程（复用 `getThread` 既有的鉴权，不新开一条读路径）。
- 导入产物写进 `problem`（用户可继续编辑），并在 `chat` 里追加一条
  `source: "system"` 的消息记录「从线程《X》导入了 N 条消息」——**留痕**，
  否则半年后没人知道这个项目的背景是从哪来的。
- 摘要由**同一个标准补全模型**做（与 `structure-feedback-draft` 同类元任务），
  不新配一套。线程太长时按最近 N 条截断，并在留痕里写明截断了。

### §2.3 界面

对话面板顶部一个「从对话导入」入口 ⇒ 弹出线程选择器（复用 `listThreads` / `listPersonalThreads`
的既有列表形态）⇒ 选中后显示**导入预览**（摘要正文，可编辑）⇒ 确认才写入。

**不确认不写**：直接写进去会覆盖用户已经写好的 `problem`。

## §3 引导式澄清：把「新建」从填表改成问答（人类交办第 4 条）

### §3.1 流程

```
① 用户写一段「想做什么」（一句话也行）
        ↓
② 模型据此生成 3–6 个**针对这个产品**的问题（不是固定问卷）
        ↓
③ 用户逐条回答，每条都可以跳过
        ↓
④ 汇成一份「设计指导原则」，用户可编辑
        ↓
⑤ 确认后创建项目，指导原则写进 problem / criteria，直接进画布
```

### §3.2 问题必须是**生成的**，不是固定问卷

固定问卷（「目标用户是谁 / 核心场景 / 竞品」）对每个产品都问同样的话，
用户答得敷衍，模型也没多拿到什么。生成的问题能问到点上——做牙膏电商会问
「会员的核心权益是什么」，做内部工具会问「谁审批」。

**兜底**：模型不可用时退回一份**固定问卷**（§3.5），并明说「AI 没能生成针对性的问题，
先按通用的问一遍」。不能因为模型挂了就把整个新建流程堵死。

### §3.3 每一步都能跳过，跳过就是跳过

- 单条问题可跳过；整个澄清阶段可「跳过，直接进画布」。
- ⚠ **跳过之后不许在后面再拦一次**。引导是帮忙，不是关卡；把它做成必答会让老手绕道，
  而老手正是最可能带着完整上下文来的人。

### §3.4 「指导原则」是什么、写到哪

它是一段人话，形如：

> 面向已有门店的会员，核心是让他们在线下单时省掉排队。首屏必须能直接下单；
> 会员等级与优惠要在下单前就看得见。不做社交分享。

- 写进 `problem`（用户随后仍可编辑）；
- 其中可验收的条目抽成 `criteria`；
- **不新增字段**——指导原则不是第四种事实源，它就是被问答填充好的 `problem` / `criteria`。

### §3.5 需要收集哪些数据（问题生成的骨架，也是模型不可用时的兜底问卷）

模型按这六个维度生成具体问题，**顺序即优先级**——只答得动前两条也够开工：

| # | 维度 | 为什么要它 |
|---|---|---|
| 1 | **谁会用**（角色、熟练度、使用场景） | 决定信息密度与用词 |
| 2 | **要解决什么**（现在怎么绕过去的） | 决定首屏放什么 |
| 3 | **主线任务**（用户来这儿最想完成的一件事） | 决定页面划分与跳转 |
| 4 | **关键约束**（必须有 / 一定没有 / 合规） | 决定边界，也决定不做什么 |
| 5 | **参考与风格**（像什么、不像什么） | 与 §1 的参考图同一维度 |
| 6 | **成功长什么样**（怎么算做对了） | 直接变成 `criteria` |

⚠ 这张表是**问题生成的骨架**，不是逐字问用户的话。把它原样念一遍就退化成固定问卷了。

### §3.6 顶部三张模板卡片：删（人类交办第 3 条）

工作台顶部那排「移动端设计 / UI 原型 / 线框图」卡片删掉。理由不是"占地方"：

- 「类别」在新建对话框里**已经是一个下拉**，两处入口做同一件事；
- 更要紧的是，**它让「挑一个模板」成了这条流程的第一步**——用户还没说清要做什么，
  就先被要求选一个设备形态。而设备形态本该是**澄清完之后**的结论
  （做门店会员下单 ⇒ 手机；做后台审批 ⇒ 桌面）。

删掉之后，工作台的主入口变成一个「新建设计」按钮，走 §3.1 的问答流程；
类别在澄清之后由模型**建议**、用户可改。

## §4 工作台列表：排序与标签（人类交办第 5、6 条）

> ⚠ 这一节与 §1–§3 **不是同一个主题**（那三节讲"开工前收集上下文"，这节讲"回来以后找得到"）。
> 并进同一个 delta 只是为了一次交付，**不是因为它们有内在关联**——评审时可以分开看。

### §4.1 最新的排在最上面

现在列表的顺序不是按时间倒序，用户刚建的项目要往下翻才找得到。改成 **`updatedAt` 倒序**
（不是 `createdAt`）：刚改过的项目排前面，比"刚建的排前面"更贴近"我在做什么"。

⚠ 排序在**服务端**定，不在前端 `sort()`：列表将来分页时，前端排序只能排出当前这一页，
表现是"翻页之后顺序乱了"。

### §4.2 卡片标签 + 顶部按标签过滤

- 每个设计项目可以打若干标签（自由文本，**每项目 ≤ 8 个，每个 ≤ 20 字**）。
- 卡片上显示标签；列表顶部一排标签 chip，点一下按它过滤，可多选（**取交集**）。
- 过滤在**服务端**做（`listMyProjects` 加 `tags?: string[]` 查询参数），理由同 §4.1。
- 标签集合从"这个人现有项目上出现过的标签"派生，**不另建一张标签表**——
  标签没有独立生命周期，建表只会带来"删了最后一个用它的项目，标签还留着"这类问题。

## §5 范围外（登记）

- **不做**图片生成/编辑，只做图片**理解**。
- **不做**把参考图存进原型或导出产物——它是给模型看的输入，不是设计的一部分。
- **不做**跨组织读线程；不做导入别人的线程。
- **不做** §2.1 的 B 方案（长期挂靠）。
- **不改**迭代 12 的分页生成编排——参考图只是多一个输入。

## §6 请人类拍板的四处取舍（实现按「建议」先做，签核时可改）

| # | 取舍 | 建议 | 备选 |
|---|---|---|---|
| ① | 参考图张数上限 | **A** 3 张 | B 1 张（更省）/ C 6 张（更灵活，贵一倍） |
| ② | 模型不支持视觉时 | **A** 不发图 + 回复里明说 | B 直接拒绝这次请求（"换个模型再来"） |
| ③ | 导入线程的语义 | **A** 一次性摘要进 `problem`，可编辑 | B 长期挂靠该线程实时读 |
| ④ | 澄清问答能否整段跳过 | **A** 能，且跳过后不再拦 | B 至少答前两条才放行 |

> 人类选择：① ＿ ② ＿ ③ ＿ ④ ＿

**②值得多看一眼**：A 让用户在一个看不了图的部署上仍能用文字推进（图白传了但**他知道**）；
B 更"诚实"但会把人堵死。我建议 A——前提是那句话**必须说出来**，静默降级是这个仓库
反复栽过的坑。

## §7 对既有契约的改动清单

1. `appendProjectChat.in` **+1 可选字段**：`refImageIds`。
2. **新增三个操作**：上传参考图、导入线程、**生成澄清问题**（`POST /pm-designs/intake-questions { brief } → { questions[] }`，不落库、不建项目）。
3. `createProject.in` **+1 可选字段** `intake: { question, answer }[]`——创建时把问答一起交上来，服务端汇成 `problem` / `criteria`。
4. **新增一张表** `design_project_ref_images`（项目级，RLS 同 `design_projects`）。
5. 图片类型闭集**复用** `ModelCallImageMime`，不新建枚举。
6. `DesignProject` **+2 字段**：`refImages`（元信息，不含字节）、`tags: string[]`。
7. `listMyProjects.in` **+1 可选字段** `tags`（取交集）；返回顺序改为 `updatedAt` 倒序。
8. `updateProject.in` **+1 可选字段** `tags`（给出即整体替换）。

**澄清问答不新增存储**：问题在前端内存里，答案随 `createProject` 一次交上来，
落地形态就是既有的 `problem` / `criteria`（§3.4）。

无新错误码：上传失败复用附件那套既有闭集；导入线程失败复用 `DEPENDENCY_UNAVAILABLE`。
