## 第二节 · 原型给了什么（逐条对齐）

来源：`WorkspaceX Standalone.html` 后台 → 反馈与迭代（UC-17.6 头部引用块）。

| 原型上的东西 | 现在的 mock 屏有没有 | 实现时的判据 |
|---|---|---|
| 软件反馈：类型徽标（缺陷/需求）+ 票数 + 提交人 + 附件 | 有 | 票数是**排序依据**（R3.a-2），不是装饰 |
| 状态三态：待处理 / 已进入下个迭代 / 已修复 **+ 版本号** | 有 | 「已修复」**必须**带版本号，否则溯源断了（R7） |
| `[推送到开发 Agent]` `[查看附件]` | 有（点了只出 toast） | 推送前必须过 E2 的脱敏闸 |
| Agent/Skill 改进建议：**现象 + 负评数 + 归因 + 具体改动** | 有 | **四件缺一不可**（AC2 / E4）——只有前两件时不得生成 PR |
| `[看 N 个原始案例]` 下钻 | 有（抽屉） | N 必须等于真实案例数；案例不可用时标注，**不得伪造**（E3） |
| `[生成 skill 改进 PR]` | 有（toast） | 生成 ≠ 上线（AC3b） |
| 闭环度量：N 条 → M 条 PR → K 条上线 → 满意度 ±X | 有 | 四个数必须同源可核对（AC5） |
| `[打开迭代看板]` | 有（抽屉是本地拼的） | ⚠ **原型点了没有目标屏**，见下方 K-1 |
| `[导出]` | 有（toast） | ⚠ 同上，见 K-2 |

## 第三节 · 缺口（请人类在签核时逐条裁）

- **K-1 `[打开迭代看板]` 无目标屏**（UC A1/A2 逐字：「按钮存在，但点击后无目标屏（原型待补）」）。
  现在 mock 用一个三列抽屉顶着，那个形态**没有原型依据**，是实现者定的。
  → 建议：**这一版不做看板**，把按钮去掉。留一个点了出现「实现者自己设计的看板」的按钮，
  比没有按钮更糟——它会被当成已确认的设计继续长。
- **K-2 `[导出]` 无目标屏**，导出内容与格式无原型依据。→ 同上建议。
- **K-3 参与者反馈的采集端不在这块屏上**（R3.c）：它在项目侧「成果沉淀 → 审计与反馈」。
  本束的 UI 里没有它，但 AC4（文字反馈自动推送到 Skill 改进队列）要靠它触发。
  → 请裁：AC4 算不算本束的验收（本文按「算」写，实现时需要那一侧配合）。
- **K-4 驳回与回滚在界面上没有位置**（A3/A4 是 [设计]）：复核人驳回要附理由、
  灰度回滚要留痕，但现在的屏上**没有复核人的视角**——整屏是管理员视角。
  → 请裁：复核人是另开一块屏，还是本屏加一个视角切换。
- **K-5 「谁能看到别人的反馈全文」未定**（R5 标着 [待确认]）。
  UC 按「可见标题与票数、不可见他人附件」书写，但那是 UC 作者的取向不是裁决。
  → 这条直接决定列表接口回不回 `body` 与 `attachments`，必须裁。

## 第四节 · 空态与失败态（A5 / E5）

- 无反馈时显示真实空态与提交入口，**不生成示例反馈**（A5）。
  ⚠ 现在的 mock 屏做不到这一条——它的「空态」也是一份写死的数据。
- 依赖不可用（埋点流水线）时保留用户输入、明说失败原因、可安全重试（E5）。
  现屏的 `depFailure` 文案已经写了这句话，实现时要让它由真实失败触发。
