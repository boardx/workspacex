# 契约束 `feedback-loop` 设计签核

**反馈与迭代闭环 —— 软件反馈 · 消息级评价聚合 · 开发 Agent 起草 · 人工复核 · 灰度**

依据 UC：`phases/phase-03-reuse-and-governance/requirements/17-gov/uc-17-6-反馈与迭代闭环.md`（313 行）。

## 这份束为什么现在才出现，以及它挡住了什么

2026-08-12：人类要求把后台「成员与配额」与「反馈与迭代」两屏的前后端都实现掉。
前一屏走已签核的 `org-admin` 束（+ delta 补签）已经做完；**后一屏在这里停下了**——
phase-03 此前**没有任何 contracts/ 目录**，`ui-signoff.md` 是 2026-07-30 已停用的旧门
（AGENTS.md 逐字：改它无效）。按 ADR-023，束级 `design-signoff.md` 未签 ⇒ 不得开工实现。

所以本目录下的四份材料是**给人类签的东西**，不是实现的一部分。
`apps/web/components/admin/feedback-screen.tsx`（178 行）保持现状：纯 mock + `NoBackendNotice`。

⚠ **coord-main 在 2026-08-12 夜间持有全权裁决，但那覆盖不到这一签**：
ADR-023 写的是「签核是**人的动作**，agent 不许改 status」。coord-main 也是 agent。

## 为什么切成这一个束（而不是拆成两个、或并进 org-admin）

判据是「不变量互相依赖吗」：

- **软件反馈的状态机**（待处理 → 已进入迭代 → 已修复+版本号）与
  **消息级评价的聚合**看起来是两件事，但它们汇入**同一条闭环度量**
  （AC5：N 条反馈 → M 条 PR → K 条上线 → 满意度 ±X）。拆开会出现两套「反馈计数」，
  而闭环度量恰恰是这个模块存在的理由。
- **人工复核是必经环节**（R7 / AC3b）这条硬约束同时约束两条来源产出的 PR。
  拆开就要写两遍，而写两遍的规则迟早会有一遍被改松。
- 与 `org-admin` 束**无共享不变量**：那束管的是「谁能看到什么、谁能花多少」，
  这束管的是「产品自己怎么变好」。并进去只会让一个已签的束被重新打开。

## ① UI —— 人看到的界面对不对

→ 详见 [`ui.md`](./ui.md)

`components/admin/feedback-screen.tsx`），但**它是 mock**：数据来自 `lib/mock/admin.ts`
的 `SW_FEEDBACK` / `AGENT_FEEDBACK` / `ITERATION_LOOP`，整屏挂着 `NoBackendNotice`。
原型（`WorkspaceX Standalone.html` 后台 → 反馈与迭代）给出的行为在 `ui.md` 第二节逐条对齐。

### 签核前请重点确认

- [ ] **⚠ 两个按钮点了没有目标屏**（UC 的 A1/A2 逐字写着「原型待补」）：
      `[打开迭代看板]` 与 `[导出]`。现在的 mock 屏用一个抽屉和一句 toast 顶着。
      请裁：**这一版是否就不做这两件**（我的建议：不做，把按钮去掉而不是留一个假的），
      还是要补原型再实现。
- [ ] **参与者反馈的采集端在项目侧**（R3.c / AC4：文字反馈里涉及 AI 行为的**自动推送**到
      后台 Skill 改进队列）。那一端属 `project` / `skills` 的屏，不在本束的 UI 里。
      请确认这条跨屏的推送**算在本束的验收里**（我按「算」写），还是拆去那一侧。

## ② 用例 —— 失败与边界对不对

→ 详见 [`usecases.md`](./usecases.md)

### 签核前请重点确认

- [ ] **E1 的强度**：开发 Agent 跳过人工复核直接上线 ⇒ 服务端拒绝 **+ 记安全审计**。
      我按「与 skill 双重门禁同款：写一条 `skill-gate-bypass-attempt` 审计」写。
- [ ] **E2 的脱敏**：反馈附件（原型里是「40 秒音频片段」）推给开发 Agent 前**必须脱敏或
      降级为不含原始音频的描述**。这条我**没有**给出实现方案，只把它写成一条阻断：
      未脱敏的附件不得进入推送 payload。真要做自动脱敏是另一个 UC 的量级。
- [ ] **E4**：改进建议缺具体改动（只有「表现不好」）⇒ **不得生成 PR**。
      这条是本束最容易被实现成「警告一下然后照样生成」的地方。

## ③ API 契约 —— 后端形状对不对

→ 详见 [`domain.md`](./domain.md)

### 签核前请重点确认

- [ ] **三步不可颠倒是用状态机枚举 + 服务端转移表强制的**，不是靠调用方自觉。
      `domain.md` §3 给的是一张显式的合法转移表；任何不在表里的转移一律拒绝并留痕。
- [ ] **消息级评价挂到什么上**：我按 UC R3.b 写成挂 `(messageId, skillVersionId, agentVersionId)`
      三元组——**版本 id 而不是 skill id**，否则 skill 发了新版之后旧负评会被算到新版头上。
      ⚠ 这一条与 phase-01 F68（已 passing 的「消息级评价归因到 skill 版本」）**是同一件事**，
      本束**不重新声明**它，只消费它。请确认这个边界。
- [ ] **灰度比例谁能改**：R5 说人工复核人「可回滚灰度」，没说谁能调比例。
      我把「调比例」也收在复核人手里（开发 Agent 明确不得改），属 [设计] 待裁。

## 与既有束/feature 的关系

- **不重复声明** phase-01 F68 的消息级评价归因（已 passing）；本束消费它的产出。
- **不绕过** 03-skill 的双重门禁（R3.b 第 9 步）：改进 PR 上线仍走那道门。
- **不含** 客户对项目成果的反馈（UC-15.2 / F39 / F40）——那是对项目的，不是对产品的。
  F39/F40 若要做，是另一个束。
