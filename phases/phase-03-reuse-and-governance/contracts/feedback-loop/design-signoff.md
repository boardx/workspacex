## 签核前请你确认的三件（这三条我做了决定，但它们是产品判断不是技术判断）

1. **`不做` 这个终态**。它不在原提案里，是我加的：没有它，「我们不打算做这条」的
   唯一表达方式是把它永远留在待处理里。它必须带理由，且提交人看得见那句理由。
   —— 你若认为「不答复好过一句被拒绝的理由」，那这一态要去掉。
2. **反馈类型只有 `缺陷` / `需求`，没有「其他」**。一个「其他」桶会装走一半的反馈，
   而分诊的人拿到「其他」时得到的信息量等于零。
   —— 你若确实需要第三类（如「体验」/「性能」），现在加比以后加便宜。
3. **状态流水没有查看界面**（coverage.md 缺口 1）。留痕在写，但今天只能直连库查。
   —— 你若认为「管理员要能在屏上看到这条反馈被怎么处理过」是第一版的一部分，
   那需要新增一条 `listFeedbackStatusEvents` 契约操作，本束要重签。

## 签核结果（2026-08-15）

`status: confirmed`。签核方式：**人类在会话里口头授权，由 agent 代转录**——
原话逐字是「以上的两个问题，同意，请继续」，指的是当时唯一挡着的两道门
（本文件 + `design-coherence.md`）。

⚠ **`confirmed_by` 的写法与其他束不同，是刻意的**：其余束的 `confirmed_by` 是人类
自己敲进去的名字，证据是 git 里那次人类提交；本文件的证据只是一句会话里的话，
所以它明写了「由 agent 代转录」。两者在审计上不是一回事，写成一样会让
「谁真的动手签的」不可分辨——ADR-023 那条「agent 不许改 status」挡的正是它。
人类若要把它升级成自己动手签的形态，改这两行即可。

### 上面「请你确认的三件」的处置

三件均按本文件提出的方案通过（人类给的是对整体的「同意」，未逐条另行给出不同意见）：

1. **`不做` 终态保留**，且必须带理由、提交人看得见那句理由。
2. **反馈类型只有 `缺陷` / `需求`**，不加「其他」桶。
3. **状态流水暂无查看界面**（`coverage.md` 缺口 1）——留痕在写，本版只能直连库查。

⚠ 第 3 条是**接受一个已知缺口**，不是「这件事已经做完」。它记在 `coverage.md` 的缺口栏里，
   不在任何一条 V 的「已覆盖」里。补 `listFeedbackStatusEvents` 是**新增契约操作**，
   届时本束需重签。

## D4 重开（2026-09-02，FB-5：语音 + 图片附件）

**这不是本文件顶部 `status` 那次正式签核仪式的重复**——`status: confirmed` 仍然只覆盖
2026-08-15 那次会话签下的 D1/D2/D3/D5 与「请你确认的三件」，本节记的是人类在**另一次
会话里**用直接聊天授权重开 D4 这一条单项决策，证据同样只是一句会话原话（同上面
`confirmed_by` 那条注一样的理由：这不是 git 里的一次人类提交，写法上必须诚实地区分
「谁真的动手签的」）。

人类原话（要点，非逐字）：「提交反馈时要允许用户用语音描述，AI 分析语音生成结构化
issue，并允许上传图片」；澄清轮里确认：语音交互是「说完自动填表单、人工再改」（不是
AI 直接代提交）；图片存储用**轻量级方案**（不接 F35 `uploadArtifact` 的九态流水线，
理由见 `apps/api/src/application/feedback/upload-feedback-attachment.ts` 头注）；
**「暂时不做脱敏处理，直接出功能」**——这一句话把此前在同一轮讨论里刚谈过的
「EXIF 剥离」方案也一并推翻了，最终裁决是**这一轮完全不做脱敏，直接出功能**。

### D4 从「不做」改为「做，且明确不带脱敏」

| 原决策（2026-08-15） | 新决策（2026-09-02） |
|---|---|
| 第一版不做附件，纯文字 + 自动上下文。理由：图片可能含客户数据，转发给开发 Agent（FB-4）前需要先有 E2 脱敏 | **本轮就做**（图片上传 + 展示），**且不等 E2**：FB-4「自动转发给开发 Agent」的链路今天依然没建，这一条本身没有变；变的是「附件功能本身」不再等那条未建的下游链路，理由是**没有任何自动转发路径存在时，先做脱敏是在为一个还不存在的收件人预防泄露，而人类判断这个顺序可以倒过来** |

**明确登记为已知限制，不是遗漏**：本轮上传的图片**不做任何脱敏处理**（连最基础的
EXIF 元数据剥离都没有做——讨论中间一度谈过"EXIF 剥离够用"这个折中方案，最终被
"暂时不做脱敏处理，直接出功能"这句话推翻）。这条限制的真正防线是**可见性门控**：
附件与反馈正文走**同一条 D3 规则**（管理员 + 提交人才能看到，见 `list-feedback.ts`
/ `download-feedback-attachment.ts` 头注），不是"所有人都能看到未脱敏的图片"。
**在 FB-4 那条"自动转发给开发 Agent"的下游链路真正建成之前，必须先在这里或那条链路
自己的入口补上脱敏这一步**——那一刻起，"谁能看见"不再是唯一的收件人，含 PII 的
截图会被原样转发给一个不受 D3 门控约束的下游消费者。

### 范围声明：本轮走的是 D4 单项重开，不是整束重新签核

沿用本文件「② 用例」一节已经承认过的同一种打破常规：ADR-023 的"先签后做"顺序在这里
第二次被打破——上一次是"人类先直接要求做，2026-08-15 才补签"，这一次是"人类直接授权
重开单项决策，本节只是如实转录"。这不是一个可以反复利用的口子：**它只对 D4 这一项
生效**，不代表本束此后可以绕过契约束签核直接改设计。后果与上一次相同：**代码在分支
上，feature 不得标 `passing`，直到人类明确确认本节的转录准确**——如果人类的原意与
本节的转录有出入，需要改的是转录，而不是让代码带着一份不准确的签核记录合入 `main`。
