# 原始需求（概览）— billing-payment（Phase 21）

估点 **4**（本文件 spec_ref 的 feature 合计；与 `../feature_list.json` 机械对账，改点必改此数）。

> 本文件夹是 Phase 21 的原始需求（**输入/上下文，不是权威**；权威是 `../feature_list.json`）。
> 行为基线：`boardx-backend` 的 `src/payment/**`（Stripe 订阅）与 `src/credits/**`（微信 Native 扫码充值），
> 以及 `boardx-web` 的收银台交互（`CreditPurchaseDialog` / `PersonalScanPaymentPanel` / `UpgradePlanDialog`）。
> 本阶段目标是**全量对齐**这两个仓库的支付能力（人类 2026-10-01 对话确认）。
> 参考实现里的已知缺陷**不视为需求**，见 R2。

## R1 阶段范围

- **要做的（本阶段交付）**：
  1. **微信 Native 扫码充值**：套餐浏览 → 创建订单 → 二维码 → 扫码支付 → 服务端回调到账 → 钱包/流水可查。
  2. **订单生命周期与回调安全**：状态机、15 分钟过期关闭、幂等入账、验签/解密、重复回调、失败留痕；非生产环境的 mock 支付测试通道。
  3. **Stripe 订阅**：升级跳转、订阅管理页、订阅状态同步（含 webhook）。
  4. **前端收银台**：购买弹窗（套餐 / 二维码 / 轮询 / 全部终态）、订阅升级弹窗、用户菜单与组织管理入口。
  5. **计费管理端（最小）**：查钱包与流水、手工发额度、组织计费开关。
- **明确不做的（后续阶段）**：AI 用量扣费与额度门控（额度只入不耗）、欠款/透支、退款、支付宝与微信 JSAPI 渠道、发票与税务、主动查单对账、多币种结算。

## R2 明确不照搬的参考缺陷

以下行为在参照仓库真实存在，**禁止照抄**：

1. **回调验签不得跳过**——boardx-backend 的微信回调验签代码被整段注释掉，伪造回调即可触发到账；本阶段回调必须完整验签。
2. **"有枚举、无写入路径"的状态不许出现**——如参考里的 `CLOSED`/`REFUNDED` 状态有枚举但没有任何代码会写入；本阶段每个状态的每条迁移边都必须有触发者与验证手段。
3. **未启用的渠道不得卡启动**——参考实现里 Stripe 4 个环境变量即使在 credits 模式也强制必填、缺失即启动失败；本阶段未启用渠道的配置缺失不应阻塞服务启动。

## R3 角色定义（Actor）

- **终端用户**：个人额度购买者、订阅购买者。
- **组织管理员**（owner/admin）：为组织购买额度、管理组织计费开关、查看组织钱包。
- **平台管理员**：查任意用户/组织钱包、手工发额度。
- **外部系统**：微信支付（服务端回调）、Stripe（webhook、托管支付页与账单门户）。
- **运维/开发**：配置渠道参数、使用 mock 通道做本地与 CI 验证。

## R4 术语与全局约定

- **额度（credits）**：系统内可充值、可查询余额的计费单位；本阶段**只入账不消耗**。
- **套餐（package）**：一次充值的商品，含金额、基础额度、赠送额度/赠送率、合计额度。
- **订单（order）**：一次充值意图，含订单号、状态、金额、二维码、各阶段时间戳。
- **订阅（subscription）**：Stripe 侧的周期性计划（如 Pro）；系统保存其状态快照。
- **支付渠道（provider）**：微信 / Stripe；按部署配置启用，具体开关形态由契约设计定。
- **回调（notify/webhook）**：支付方 → 系统的服务端通知；**到账只认服务端回调，不认前端轮询结果**。
- **金额**：微信侧人民币（展示用元、计算用分）；**服务端是唯一计算源，前端不上传任何金额字段**。

## R6 假设与待澄清

- 购买主体沿用参考实现的"个人 / 组织"两类 owner；组织模型映射到 workspacex 现有组织体系（`auth-org` 域），由契约设计统一。
- 渠道启用方式的具体形态（配置项名、能否同部署并存）由契约设计定，需求只要求"按部署配置启停，未启用时入口不可用且不阻塞启动"。
- 需要真实商户号/真实 Stripe 账号的验收场景，以"沙箱/mock + 人工抽验"替代，并在证据里写明边界（参考实现本身即如此：`mock-paid` 生产禁用）。

## R9 非功能约束（全局）

- **回调应答**：微信回调必须在微信要求的超时内应答（<5s）；处理与应答分离（先占单再入账，异常置失败）。
- **轮询节流**：前端订单轮询间隔 3 秒，不允许更密；同一订单并发轮询不放大后端压力。
- **密钥安全**：API v3 密钥、商户私钥、平台公钥、Stripe 密钥一律只从部署配置/环境变量读取，不进代码库、不进日志明文。
- **审计**：资金相关操作（入账、发额度、订单状态迁移）必须有可追溯留痕（谁/何时/多少/依据）。
- **金额精度**：计算与存储用"分"（整数），展示层转"元"；不得用浮点数参与金额运算。

## R10 已知约束 / 依赖

- **依赖**：workspacex 登录体系（auth）、组织体系（org）；微信商户平台、Stripe 账号（运维提供；测试期用 mock）。
- **技术栈差异**：参考仓库是 NestJS + Mongoose（Mongo）；本仓是 NestJS + Postgres。**语义对齐、实现按本仓技术栈重做**，不得照搬集合/字段结构。
- **已存在的未跟踪骨架**：`apps/api/src/infrastructure/payment/payment-config.ts`、`apps/api/src/interface/controllers/payment.controller.ts`、`packages/contracts/src/payment.ts`、`apps/api/tests/payment/`（约 55 行，region `cn/en` 模型，未挂路由）。契约设计阶段裁决**并入或重写**，不许形成第二事实源。
