# 04 — 计费管理端（钱包 / 发额度 / 组织开关）

估点 **24**（= 钱包流水查询 4 + 人工发放 5 + 组织开关 4 + 管理端 UI 6 + 组织区块 UI 5；与 `../feature_list.json` 机械对账，改点必改此数）。

## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case 名称**：计费管理操作（可查、可控、可审计）
- **Actor**：平台管理员、组织管理员（owner/admin）
- **目标**：让"钱与额度"的每一次变化都可查询、可追溯、可追责。
- **系统边界**：`apps/web` 管理端入口 → `apps/api` 计费域。

## R2 前置条件 / 触发条件

- **前置条件**：已登录且具备对应管理权限（平台管理员由平台角色判定；组织管理员为该组织 owner/admin）。
- **触发条件**：管理端打开用户/组织计费页、执行发放或开关操作；或直接调用对应管理接口。

## R3 主流程

1. **查钱包**：平台管理员查看指定用户/组织的钱包——余额、累计获得（充值/赠送/发放），以及流水明细（类型、数量、时间、来源）。
2. **手工发额度**：平台管理员填写目标主体、额度数、**原因（必填）** → 系统入账：钱包累加 + 写一笔"人工发放"流水（记录操作者与原因）。
3. **组织自助查看**：组织 owner/admin 查看本组织钱包与流水。
4. **组织计费开关**：组织 owner/admin 开启/关闭「组织计费」——关闭后组织维度的**新购买入口**不可用；已购余额仍可查看（只影响新购买，不追缴已购）。

## R4 备选流程与异常流程

- **E1 无权限调用**：403，且响应不泄露目标资源是否存在（沿用 workspacex 既有权限错误惯例）。
- **E2 发放参数非法**：额度 ≤ 0、缺原因、目标主体不存在 → 拒绝并给出原因。
- **E3 并发发放**：每笔独立流水、独立操作者留痕；余额累加结果正确（不得丢笔）。
- **E4 组织不存在/已解散**：拒绝操作。
- **E5 平台管理员查看不存在主体**：明确 404 语义，不返回空壳数据。

## R5 权限与可见性

- **平台管理员**：可查任意用户/组织的钱包与流水；可手工发放额度。
- **组织 owner/admin**：仅可查**本组织**钱包与流水；可开关本组织计费；**不可**手工发放（发放是平台动作）。
- **普通成员**：看不到任何管理端入口；直接调管理接口返回 403。
- **未登录**：全部管理接口不可用。

## R6 后置条件 / 不包含

- **后置条件**：每次发放有一笔流水与操作者留痕；组织开关状态持久化并被购买入口正确消费。
- **不包含**：退款/冲正、批量发放、额度消耗与欠款管理、计费报表/BI、自定义发放审批流。

## R7 业务规则（硬性约束）

1. 任何余额变更（含人工发放）**必须**有流水记录，且流水必须带操作者与原因（人工发放时）。
2. 管理接口的权限判定以服务端为准，前端隐藏入口只是体验优化。
3. 组织开关只影响**新购买入口**的可用性，不改变任何历史数据。

## R8 界面线索（has_ui 阶段必填）

- **前端入口**：平台管理端的用户/组织计费页；组织管理页的计费设置区块。
- **构成**：钱包余额卡（余额 + 累计）、流水列表（类型筛选/分页）、发放表单（主体 + 额度 + 原因）、组织开关键。
- **参考实现（竞品路径，供 UI 先行对照）**：
  - `boardx-web/src/components/credits/CreditRecordsDialog.tsx`（流水/余额展示）
  - `boardx-web/src/components/credits/TeamCreditManagement.tsx`（组织管理）
  - 截图待 UI 先行阶段产出到 `ui-preview/`。

## R11 切分提示（给 requirement-author）

- 建议粒度：钱包与流水查询、手工发放、组织开关，可拆 2–3 个 feature。
- 先后依赖：依赖 01/02 的钱包模型先定型；管理端 UI 依赖契约束签核。

## R12 AI Ready 验收线索（收尾自检）

- 成功态：发放后余额与流水一致、操作者与原因可查；组织开关生效于购买入口；
- 异常态：无权 403、非法参数拒绝、并发发放不丢笔、不存在主体 404；
- 权限态：组织管理员看不到他人组织、普通成员看不到入口、发放仅平台管理员。
