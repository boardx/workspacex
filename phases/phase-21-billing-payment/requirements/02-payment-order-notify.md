# 02 — 订单生命周期与微信回调

估点 **19**（= 建表 5 + 回调入账 8 + 关单任务 3 + mock 通道 3；与 `../feature_list.json` 机械对账，改点必改此数）。

## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case 名称**：订单状态机与其服务端保证（**钱到账必记、记录不重复**）
- **Actor**：外部系统（微信支付回调）、终端用户（查询状态）、运维/开发（mock 通道与排障）
- **目标**：任何一次真实支付都有且仅有一次入账；任何异常都有明确状态与可追溯留痕。
- **系统边界**：`apps/api` 订单/账务域；微信支付服务端 → 系统回调端点。

## R2 前置条件 / 触发条件

- **前置条件**：订单已创建（见 01）；微信商户参数与平台公钥/证书配置完整。
- **触发条件**：
  - 微信支付服务端发起回调 HTTP 请求；
  - 前端轮询订单状态；
  - 非生产环境：测试人员调用 mock 支付接口。

## R3 主流程（回调处理）

1. 系统收到回调 → **先验签**（平台公钥/证书）；验签失败直接拒绝，**不得进入后续任何步骤**，并记录安全事件。
2. 验签通过 → 用 API v3 密钥解密回调资源，取出：商户订单号、交易状态、微信交易号、金额。
3. **一致性校验**：订单存在、金额一致、商户号一致；不一致 → 拒绝入账，按 E2 处理。
4. **幂等**：若订单已是「成功」→ 直接按成功应答（不重复入账）；若为「处理中」→ 应答失败让微信稍后重试。
5. **原子抢占**：订单从「待支付」→「处理中」（条件更新，防并发双入账）。
6. **入账**：钱包余额增加（基础额度、赠送额度分别记流水）；写支付时间、通知时间；订单置「成功」。
7. 应答微信「成功」；若入账过程异常 → 订单置「失败」并留痕（见 E3）。

## R4 备选流程与异常流程

- **E1 验签失败 / 解密失败**：拒绝应答 + 记录安全事件；**不得入账**。
- **E2 一致性校验失败**（金额不符 / 订单不存在 / 商户号不符）：拒绝 + 告警级留痕（可能为篡改或配置错误）。
- **E3 入账过程异常**（数据库错误等）：订单置「失败」，错误信息留痕；资金已在微信侧收取的情况由平台管理员按 04 手工发额度救济，并保留补单记录。
- **E4 重复回调 / 微信重试**：幂等保证同一订单至多入账一次；应答语义符合微信协议（成功才停止重试）。
- **E5 已关闭订单收到成功回调**：**资金真实性优先**——校验通过则执行入账、订单转「成功」，同时留痕告警（用于发现"过期后仍完成支付"的异常流量）。
- **E6 非生产环境调用 mock 接口**：直接推进订单到成功（走与回调相同的入账函数）；**生产环境硬拒绝（403）**且不得改变任何订单状态。
- **E7 处理进程崩溃/重启**：微信重试到达后按幂等规则继续；幂等键 = 订单号 + 回调唯一 id；系统不得因重启丢单或双记。
- **E8 回调延迟**（超过 15 分钟才到）：同 E5 规则（订单可能已被关闭）。

## R5 权限与可见性

- **回调端点**：无用户鉴权，但**必须验签**；对外仅按微信协议应答，不泄露内部细节。
- **订单查询**：登录用户 + 归属校验（个人本人 / 组织 owner-admin）。
- **mock 端点**：仅非生产环境可用；生产环境硬拒绝。
- **错误细节**：用户可见自己的订单状态与用户可读的失败原因；内部错误明细仅管理端与日志可见。

## R6 订单状态机与不包含

- **状态集合**：待支付 `PENDING` / 处理中 `PROCESSING` / 成功 `SUCCESS` / 失败 `FAILED` / 已关闭 `CLOSED`。
  （参考仓库里的 `REFUNDED` 不在本阶段，不引入。）
- **合法迁移（每条边都必须有触发者与验证手段）**：

| 迁移 | 触发者 |
|---|---|
| 待支付 → 处理中 | 回调验签通过后的原子抢占（R3.5） |
| 待支付 → 已关闭 | **服务端定时关单任务**（超过 15 分钟未支付；参考实现没有这个任务，本阶段必须实现） |
| 处理中 → 成功 | 入账完成（R3.6） |
| 处理中 → 失败 | 入账异常（E3） |
| 已关闭 → 成功 | 成功回调兜底（E5，资金真实性优先） |

- **不包含**：主动向微信查单/对账补偿；退款流；订单修改/撤销。
- **可观察字段**（用户与运维可见）：订单号、状态、金额、基础/赠送/合计额度、二维码链接、创建/支付/通知/过期时间、用户可读失败原因。

## R7 业务规则（硬性约束）

1. 回调处理与 HTTP 应答分离：先完成状态抢占，再入账；应答必须快（<5s）。
2. **没有验签就没有入账**——验签是入账的必要条件，不允许任何"开发期跳过"的分支进入生产。
3. 所有状态迁移必须持久化时间戳，任何"状态变了但没有迁移记录"都视为缺陷。
4. 幂等键、抢占条件必须抗并发（同一订单并发回调只产生一次入账）。

## R8 界面线索（has_ui 阶段必填）

- 本域**无独立界面**；状态通过 01 的收银台（用户视角）与 04 的管理端（运维视角）间接呈现。
- 运维可见性要求：订单的关键字段（R6 可观察字段）必须能在管理端/诊断入口查到（形态由契约设计定，最低限度为结构化日志可检索）。

## R11 切分提示（给 requirement-author）

- 建议粒度：订单模型与状态机（契约先行）、微信回调验签/解密/幂等、定时关单、mock 通道，各成 1 个 feature。
- 先后依赖：本文件先于 01 的 UI 部分；定时关单可与回调并行。

## R12 AI Ready 验收线索（收尾自检）

- 成功态：合法回调 → 订单成功 + 钱包增加 + 流水两条（基础/赠送）+ 各时间戳齐全；
- 异常态：验签失败不入账、金额不符拒绝、重复回调不双记、并发回调只入账一次、崩溃重启不丢单；
- 状态机：五状态的每条合法边都有可复现触发路径；`CLOSED` 有真实关单任务驱动；
- 生产禁用：mock 接口在生产返回 403 且订单不变。
