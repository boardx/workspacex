# 01 — 用户购买额度（微信 Native 扫码）

估点 **15**（= 订单主链路 7 + 收银台 UI 8；与 `../feature_list.json` 机械对账，改点必改此数）。

## R1 概览（Use Case 名称 / Actor / 目标 / 系统边界）

- **Use Case 名称**：扫码充值额度（收银台全流程）
- **Actor**：终端用户（个人主体）、组织管理员（组织主体）
- **目标**：用户在收银台选择套餐，用微信扫码完成支付，让额度**可靠**到账并可随时查询。
- **系统边界**：`apps/web` 收银台弹窗 → `apps/api` 订单/账务域 → 微信支付 Native 下单与回调（回调细节见 `02-payment-order-notify.md`）。

## R2 前置条件 / 触发条件

- **前置条件**：
  - 用户已登录且会话有效；
  - 部署已启用微信扫码渠道且商户配置完整（未启用时见 E1）；
  - 组织主体订单：操作者是该组织的 owner/admin。
- **触发条件**：
  - 用户在用户菜单点「购买额度」；或组织管理页点「为组织购买」。

## R3 主流程

1. 用户打开收银台 → 系统展示套餐列表：套餐名、价格（元）、基础额度、赠送额度（赠送率）、合计额度。列表为空时展示空态说明（不编造套餐）。
2. 用户选择套餐；支付方式默认微信；未启用的渠道（如支付宝）不展示或置灰不可点。
3. 用户点「生成二维码」→ 系统创建订单：
   - 金额、基础额度、赠送额度**以服务端套餐为准**（前端不传金额）；
   - 订单号全局唯一；初始状态「待支付」；有效期 15 分钟；
   - 系统向微信下 Native 单，取得二维码链接（失败见 E2）。
4. 前端把二维码链接**本地渲染**成二维码图片（不依赖第三方二维码图床），提示「请用微信扫码支付」。
5. 前端每 3 秒轮询订单状态；用户也可手动点「刷新支付状态」。
6. 用户扫码完成支付 → 微信服务端通知系统（详见 02）→ 订单转「成功」→ 钱包入账（基础额度 + 赠送额度）并生成流水。
7. 前端轮询到「成功」→ 展示支付成功提示；余额与流水**无需整页刷新**即更新。
8. 用户可随时在钱包/流水入口查看余额与本次充值记录。

## R4 备选流程与异常流程

### 备选流程

- **A1 用户重复点「生成二维码」**：每次点击生成一个新订单；旧订单若未支付，到期自动关闭；允许并存多个待支付订单，但**每个订单至多入账一次**。
- **A2 用户关闭弹窗后回来**：重新打开收银台按新建订单流程走；不包含"历史订单列表续看"（见 R6）。
- **A3 同一用户快速连续下单同一套餐**：视为 A1，多订单互不影响。

### 异常流程

- **E1 渠道未配置**：购买入口不可用或明确报错（示例错误码 `PAYMENT_PROVIDER_NOT_CONFIGURED`）；**不得展示一个永远扫不成功的二维码**。
- **E2 微信下单失败**（网络/签名/参数错误）：订单不得进入「待支付且持有有效二维码」的假态；前端收到**可重试**的失败提示；失败原因后端留痕。
- **E3 订单超时（15 分钟未支付）**：订单转「已关闭」；前端提示「二维码已过期」并提供重新生成按钮。
- **E4 用户支付成功后立刻离开/断网**：到账不依赖前端在线（服务端回调驱动）；用户之后回来查询余额可见。
- **E5 轮询接口暂时失败**：前端保持当前提示，**不得误报**「支付成功/失败」；恢复后继续轮询。
- **E6 已关闭订单收到支付成功回调**：按 02 的兜底规则处理（资金真实性优先）并留痕告警。
- **E7 组织主体权限不足**（非 owner/admin）：入口拒绝并说明原因；直接调接口返回无权限。
- **E8 套餐被下架/禁用后用户仍打开了旧页面**：下单时服务端校验套餐可用性，拒绝并提示刷新。

## R5 权限与可见性

- **个人用户**：只能创建/查询自己的订单与钱包。
- **组织 owner/admin**：可为组织创建/查询组织订单与钱包；普通成员**不可见**组织购买入口。
- **任何用户**：不能查询他人订单（按订单号查询也必须做归属校验）。
- **未登录**：收银台与全部订单接口不可用。
- **平台管理员**：不代替用户下单（管理能力见 04）。

## R6 后置条件 / 不包含

- **后置条件**：订单「成功」；钱包余额 = 原余额 + 基础额度 + 赠送额度；流水可查（充值与赠送分别入账，或按契约设计合并但明细可辨）。
- **不包含**：
  - 额度消耗（AI 计费）与额度门控；
  - 退款、发票、税务；
  - 订单列表页与历史订单管理（仅支持按订单号查询状态）；
  - 支付宝、微信 JSAPI 渠道。

## R7 业务规则（硬性约束）

1. **金额与额度只能由服务端套餐决定**；任何来自前端的金额字段一律忽略并记录可疑请求。
2. **到账只认服务端回调**；前端轮询只是展示层，不得驱动入账。
3. 一个订单**至多入账一次**（含重复回调、并发场景）。
4. 订单必须有过期路径：超过有效期未支付必须可关闭（由服务端定时任务保证，而非惰性判断）。

## R8 界面线索（has_ui 阶段必填）

- **前端入口**：用户菜单「购买额度」；组织管理页「为组织购买」；AI 额度不足场景的引导入口（若现有产品有对应事件位，按现有机制接入；没有则不新造）。
- **收银台弹窗构成**：套餐卡片列表（选中态）→ 支付方式选择 → 「生成二维码」按钮 → 二维码展示区 → 状态提示区（待支付 / 支付成功 / 已过期 / 失败）→ 「刷新支付状态」按钮。
- **参考实现（竞品路径，供 UI 先行对照）**：
  - `boardx-web/src/components/credits/CreditPurchaseDialog.tsx`（主力弹窗，含 3s 轮询与错误文案映射）
  - `boardx-web/src/components/ui-user/PersonalScanPaymentPanel.tsx`（扫码面板形态）
  - 截图待 UI 先行阶段产出到 `ui-preview/`。
- **提醒**：feature 清单可先生成，但**开工前 UI 必须随契约束一起经人类签核**（束级 `design-signoff.md` 第 ① 节）。

## R11 切分提示（给 requirement-author）

- 建议粒度：套餐展示与下单、二维码与轮询交互、过期与重试、钱包/流水展示，可拆成 2–3 个 feature。
- 先后依赖：01 依赖 02 的订单模型先定型（契约先行）；UI 部分依赖契约束签核。

## R12 AI Ready 验收线索（收尾自检）

读完 R1–R11，零先验的 agent 应能推导出这些可验证行为：

- 成功态：选套餐 → 生成二维码 → （回调）→ 轮询显示成功 → 余额与流水更新；
- E1 渠道未配置时入口/接口的明确失败；E2 下单失败可重试且无假二维码；E3 超时关单与提示；E5 轮询失败不误报；E7 越权拒绝；
- 权限态：他人订单不可查、组织入口对普通成员不可见、未登录全部不可用。
