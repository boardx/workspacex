# 原始需求 — 全站终验收官

估点 **3**

> 来源：2026-08-23《WorkspaceX 十分制评估》+《十分冲刺 Backlog》IT-10。

## R1 概览
- **Use Case 名称**：本阶段收官的全站机械门控与回归验证
- **Actor**：负责收官的开发 agent；最终对结果负责的人类
- **目标**：汇总前 9 个 feature 的成果，跑一遍全套机械门控（lint-design、对比度检查、axe-core、关键路径键盘走查），确认没有新增回归，并对照本阶段评估报告的十维评分重新打分，出最终分数。不允许出现"标了 passing 但实际观感没到位"的假 10 分。
- **系统边界**：全仓 `apps/web`，`.harness/` 下相关验证脚本，`init.sh` 基础验证

## R2 前置条件 / 触发条件
- **前置条件**：本阶段前 9 个 feature（01-09）均已达到 passing
- **触发条件**：前序全部完成后触发本 feature

## R3 主流程
1. 全量跑通 `lint-design.sh`（含本阶段新增的 U9 第三方组件规则、扩展后的 U7a 图片规则）
2. 跑 `apps/web/scripts/check-token-contrast.mjs`，确认对比度门控无回归
3. 跑 axe-core 对关键页面（chat/profile/org-admin/canvas）做全站扫描
4. 重跑「03-keyboard-accessibility」产出的核心任务键盘走查自动化用例，确认无回归
5. 对照《WorkspaceX 十分制评估》的十维评分表，逐维重新评估并贴出证据（对应本阶段各 feature 的产出物）
6. `./init.sh` 基础验证通过；`pnpm harness doctor` 三条检查通过
7. 若仍有未闭合的缺口（如某个维度受限于产品功能缺口，无法在本阶段单靠 UI 修复解决），如实记录为下一阶段待办，不允许虚报为已达标

## R4 备选流程与异常流程
- **备选流程**：
  - A1：某个 feature 在验证过程中发现遗留的小问题——评估是否属于阻塞级，阻塞级需要打回对应 feature 修复，非阻塞级记录为已知问题
- **异常流程**：
  - E1：全站扫描发现前序 feature 未覆盖到的遗漏点（如某个页面漏了 focus trap）——不能因为不在原计划里就忽略，需要补一个小修复或明确记录为下一阶段待办
  - E2：终验分数没有达到 10 分——如实报告实际分数与差距，说明差距具体在哪个维度、为什么，而不是调整评分标准来凑分（参照仓库既有原则：判据的收窄必须有真实理由，如数据不支撑，而不是为了让分数好看）

## R5 权限与可见性
- 无业务权限差异，本 feature 是治理性质，验证全站已有的权限展示是否符合各角色预期（作为回归检查的一部分，不新增权限逻辑）

## R6 后置条件 / 不包含
- **后置条件**：终验报告产出；十维评分重新计算并附证据；`init.sh` 与 `harness doctor` 均通过
- **不包含**：本 feature 不修复评审中发现的所有问题（篇幅大的问题应打回对应 feature 或转为下一阶段待办），只做验证与如实报告

## R7 业务规则
- 终验分数必须有可复现的证据链（命令输出/截图/日志），不能凭印象打分

## R8 界面线域
- 前端入口：全站，作为验证对象而非新增开发对象
- 提醒：本 feature 本身不产出新的可见 UI 改动（除非验证中发现的小修复），一般不需要新的设计签核，但需确认阶段级的 `design-coherence.md`（一致性复核）已完成

## R9 非功能约束
- 性能/规模预期：全站扫描需要在合理时间内完成（作为 CI/本地验证的一部分，不应过长阻塞流程）
- 安全/隐私/合规：无障碍合规相关的最终确认

## R10 已知约束 / 依赖
- 依赖：本阶段全部前序 feature（01-09）均已 passing
- 技术约束：无

## R11 切分提示
- 期望粒度：单个 feature（工作量评估 M，3-5 天，含如实修复遗漏点的时间）
- 优先级：本阶段最后一项，无后续依赖

## R12 AI Ready 验收线索
- 可验证行为：`lint-design.sh`、`check-token-contrast.mjs`、axe-core、键盘走查自动化用例全部通过；`./init.sh` 与 `pnpm harness doctor` 通过；终验报告逐维贴出证据，若有未达标项如实记录而非隐藏
