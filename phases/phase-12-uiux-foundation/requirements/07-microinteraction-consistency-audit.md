# 原始需求 — 微交互一致性稽核

估点 **5**

> 来源：2026-08-23《WorkspaceX 十分制评估》缺口「视觉打磨精细度」+《十分冲刺 Backlog》IT-07。

## R1 概览
- **Use Case 名称**：统一 hover/focus/active 微交互反馈
- **Actor**：全站用户
- **目标**：`components/ui/button.tsx` 是微交互的标杆实现（内置 hover/focus/active，token 化），但业务组件里手写的可点击元素交互态可能各自为政。目标是对 chat / profile / org-admin / canvas 四个域做一次全站稽核，把偏离 `uiux-standards.md` §5 的案例收敛到统一模式。
- **系统边界**：`apps/web/components/chat/**`、`profile/**`、`org-admin/**`、`canvas/**` 下所有可点击元素

## R2 前置条件 / 触发条件
- **前置条件**：`uiux-standards.md` §5（微交互规范）与 `lint-design.sh` 的 U4 规则（hover 必有 transition）已存在
- **触发条件**：本 feature 开工时逐域抽查

## R3 主流程
1. 逐一列出四个域下所有可点击元素（按钮、卡片、列表项、图标按钮等）
2. 对照 `uiux-standards.md` §5 检查每个元素的 hover/focus/active 是否有一致的视觉反馈（过渡时长、颜色变化幅度、是否有 `active:scale` 类的点击反馈）
3. 记录偏离案例，按"完全没有反馈"→"反馈存在但不一致"→"反馈存在且一致但可以更好"三档分类整改优先级
4. 修复偏离案例，优先修"完全没有反馈"的（可能是可访问性问题，不只是美观问题）
5. 修复 PR 按域拆分，避免单 PR 改动面过大

## R4 备选流程与异常流程
- **备选流程**：
  - A1：某个元素在特定状态下（如已选中）需要与默认态不同的 hover 反馈——需要设计说明为什么不同，不能是遗漏
- **异常流程**：
  - E1：某个第三方组件（如 CopilotKit 渲染的消息内容里的可点击链接）的微交互不受本仓库样式控制——记录为已知限制
  - E2：稽核过程中发现某处交互反馈的缺失实际上是更严重的可访问性问题（如整个元素没有 `:focus-visible` 状态，键盘用户完全看不到焦点在哪）——优先级提升，可能需要与「03-keyboard-accessibility」协同

## R5 权限与可见性
- 无业务权限差异

## R6 后置条件 / 不包含
- **后置条件**：四个域的微交互一致性稽核报告；修复 PR 落地
- **不包含**：不扩展到四个域之外的页面（属于后续迭代范围）；不改变元素本身的功能逻辑，只调整交互反馈的视觉呈现

## R7 业务规则
- 任何可点击元素必须有可见的 hover 或 focus 反馈之一（纯装饰性、不可点击的元素除外）

## R8 界面线索
- 前端入口：四个域下的所有可点击元素
- 提醒：本 feature 是既有视觉的一致性修复，改动幅度通常较小，是否需要签核取决于具体修复是否改变了显著的视觉呈现，建议由所属契约束负责人判断

## R9 非功能约束
- 兼容与降级要求：验证 `prefers-reduced-motion` 下微交互仍保留必要的状态提示（如颜色变化），只是去掉动画过渡本身

## R10 已知约束 / 依赖
- 依赖：`uiux-standards.md` §5、`lint-design.sh` U4 规则
- 无强依赖其他 feature，但建议在「01/06」组件收口之后进行，减少重复劳动

## R11 切分提示
- 期望粒度：按域拆分为最多 4 个小 feature，或合并为一个中等 feature（工作量评估 M，3-5 天）
- 优先级：排在组件收口类 feature 之后

## R12 AI Ready 验收线索
- 可验证行为：`lint-design.sh` U4 覆盖率达标；四个域的人工截图抽样对比交互反馈观感一致；稽核报告列出发现的偏离案例总数与修复状态
