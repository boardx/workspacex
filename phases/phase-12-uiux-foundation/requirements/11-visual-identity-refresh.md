# 原始需求 — 视觉系统 token 升级（品牌锚点 + 分级圆角/阴影 + 字重层级）

估点 **3**

> 来源：2026-08-24/25 人类会话反馈——"整体上来说，这个 UI 给人感觉很平庸，没有什么印象，不专业"，
> 对照真实截图诊断出结构性问题（非单屏个案），已出具对比方案 artifact 并经人类确认（选项 1：
> 按提案方向全站落地，不换主色相，保守处理）。

## R1 概览
- **Use Case 名称**：把现有 design token 从"单一色阶铺满"升级为分层视觉系统
- **Actor**：全站所有页面的终端用户（视觉观感），开发 agent（token 消费方）
- **目标**：现有 `--accent`（青绿）同时承担背景色/按钮色/选中态三种角色，视觉权重被拉平，
  没有强调；`--radius` 单值 7px 一刀切用于所有控件/卡片/容器；导航栏无品牌锚点（纯图标）；
  全仓字重集中在 400/500，无真实的标题/正文/元信息台阶。目标是在**不改动任何交互逻辑、
  不改动主色相**的前提下，通过 token 层的分级与克制使用，把观感从"平庸"提升到"专业"。
- **系统边界**：`apps/web/app/globals.css`（token 定义）、`apps/web/tailwind.config.ts`
  （radius/shadow/字重消费层）、`apps/web/components/shell/**`（导航栏 wordmark）、
  `apps/web/components/chat/**`（气泡不对称圆角，仅样式非交互）

## R2 前置条件 / 触发条件
- **前置条件**：F01-F13 已落地的组件原语（dialog/dropdown/select/table/menu/pagination 等）
  均通过 token 消费颜色/圆角/阴影，本次只改 token 定义层，理论上级联生效，不需要逐个组件改
- **触发条件**：人类确认对比方案（artifact `theme-direction.html`）后触发本 feature 开工

## R3 主流程
1. **色彩分层**：把 `--accent` 的三重角色拆开——
   - surface 层（卡片/面板背景）：改用接近无色的浅中性色，不再用 accent 色调背景
   - emphasis 层（选中态/hover）：用描边 + 极浅底色表达，不用大面积色块
   - action 层（唯一实心色块）：只保留给主按钮/发送按钮这类真正的"动作"元素
   - 主色相（青绿）本身不变，只调整**使用范围**
2. **圆角分级**：`--radius` 从单值拆成三档语义 token（控件 6px / 卡片 10px / 容器弹层 14px），
   参照现有 F03 动效 token 的"三档 + 唯一事实源 + lint 拦截裸值"模式实现，避免重蹈"同一事实
   两处声明"的覆辙。
3. **阴影分级**：现有 `--shadow-sm/md/lg` 已存在，检查是否被实际消费；确保卡片/弹层根据层级
   使用对应阴影，制造前后深度。
4. **品牌锚点**：导航栏顶部加一个 wordmark（衬线体，如 Bitter Semibold，纯视觉不涉及路由/
   交互变化），替代当前"纯图标无锚点"的空白。
5. **字重层级**：建立标题（700）/正文（400）/元信息（500 + 等宽数字）的真实台阶，
   Noto Sans SC 保留不变（中文场景下是合理选择，问题在于用法不是选型）。
6. **气泡不对称圆角**（可选，视工作量决定是否本轮做）：chat 消息气泡按方向（用户/agent）
   使用不对称圆角，纯样式改动，不涉及消息渲染逻辑或状态机。
7. **数字等宽**：agent 计数、时间戳、未读数等数字信息统一使用等宽字体 + tabular-nums。

## R4 备选流程与异常流程
- **备选流程**：
  - A1：如果某个已上线页面的视觉回归测试（截图快照）因 token 改动而"合理地"变化（不是
    bug，是预期的视觉升级），更新快照基线而不是回退 token 改动，但需在 PR 里逐张说明
    "为什么变了、变得对不对"。
- **异常流程**：
  - E1：某个组件曾经手写字面量颜色/圆角值（违反现有 token 单源约束）而不是消费 token，
    这类点在本次改动中会"级联失效"（视觉没跟着变）——发现即修，改成消费 token，不是
    本 feature 范围外的事（本来就该消费 token，只是之前没做对）。
  - E2：字面量残留可能触发 `lint-design.sh` 已有的 U5a/U5b 规则报红——这是正确的红，
    顺手修掉，不是本 feature 引入的新问题。

## R5 权限与可见性
- 无业务权限差异，全站所有角色看到同一套视觉系统。

## R6 后置条件 / 不包含
- **后置条件**：`globals.css`/`tailwind.config.ts` 的 token 定义完成分层与分级；导航栏有
  wordmark；关键页面（chat/profile/org-admin/kitchen-sink）实测视觉层次改善。
- **不包含**：
  - 不换主色相（品牌色相关的更大决策，明确排除在本次范围外）
  - 不改任何交互逻辑、状态机、路由
  - 不要求本轮把全站所有历史手写字面量值都清零（发现即修，但不做地毯式全仓扫描当作
    本 feature 的验收线，那是更大范围的存量迁移工作）

## R7 业务规则
- token 改动必须是**唯一事实源**——圆角/阴影新分级值只在 `tailwind.config.ts` 定义一次，
  `globals.css` 的注释只记选值依据，不重复写数值（沿用 F03 已确立的模式）。
- 主色相（青绿）的色值本身不得因为本次改动而漂移；只调整该色的**使用范围**。

## R8 界面线索
- 前端入口：全站视觉系统，直接影响面最大的是 `apps/web/components/shell/**`（导航栏/
  wordmark）、`apps/web/components/ui/**`（圆角/阴影消费）、`apps/web/components/chat/**`
  （气泡样式，如果本轮做）。
- 参考：artifact `theme-direction.html`（人类已确认的对比方案，含具体 hex/px 数值）。
- 提醒：本 feature 是纯视觉 token 改动，不引入新交互面，是否需要走契约束级设计签核由
  束负责人评估——鉴于已经过人类在会话中直接确认（截图对比 + 明确选择"1"），可视为
  已完成签核性质的确认，签核形式（是否需要补一份束级 design-signoff）留给人类决定。

## R9 非功能约束
- 兼容与降级要求：深色模式（`.dark` class）token 需要同步定义分层版本，不能只改浅色。
- 视觉回归：改动前后需要真实截图对比证据（沿用 F14/F15 已建立的截图取证方式）。

## R10 已知约束 / 依赖
- 依赖 F01-F13 已完成的组件原语（token 消费方），F03 的动效 token 分层模式（参照实现方式）。

## R11 切分提示
- 期望粒度：单个中等 feature（工作量评估 M，3-5 天），气泡不对称圆角如果时间不够可以
  拆成独立后续 feature。
- 优先级：人类直接指定的高优先级项，插入到常规排期之外。

## R12 AI Ready 验收线索
- 可验证行为：`pnpm --filter web run lint:design` 全过（含新增圆角分级规则）；kitchen-sink
  页面截图对比新旧视觉层次；chat/profile/org-admin 关键页面截图证据；深色模式同步验证；
  全仓 vitest/tsc 无回归。
