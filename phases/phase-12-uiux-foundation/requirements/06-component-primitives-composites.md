# 原始需求 — 复合组件收口二期（Table / Menu / Breadcrumb / Pagination）

估点 **5**

> 来源：2026-08-23《WorkspaceX 十分制评估》P0 缺口「组件覆盖面」+《十分冲刺 Backlog》IT-06。

## R1 概览
- **Use Case 名称**：收口高频复合组件模式
- **Actor**：全站用户；开发 agent
- **目标**：「01-component-primitives-overlays」解决了四个最高频的弹层类原语，本 feature 把 table、command palette/menu、breadcrumb、pagination 等在 3 个以上业务目录重复出现的复合组件模式也收口进 `components/ui/`，消除业务目录里的二次实现。
- **系统边界**：`apps/web/components/ui/`（新增文件）、org-admin/profile/canvas 等含列表/表格/分页场景的业务目录

## R2 前置条件 / 触发条件
- **前置条件**：「01-component-primitives-overlays」已完成（本 feature 的 menu 组件很可能复用 dropdown 的底层实现）
- **触发条件**：本 feature 开工时先做重复模式盘点

## R3 主流程
1. 盘点 `components/ui/` 之外、在 3 个以上业务目录重复出现的组件模式，候选包括：数据表格（表头/排序/空态一致性）、command palette 或右键菜单、面包屑导航、分页控件
2. 从盘点结果里选出实际满足"3 个以上重复"门槛的 3-5 个模式，收口为新的 `ui/` 原语
3. 逐一替换业务目录里的重复实现，保留迁移映射表（沿用 IT-01 的做法）
4. 在 kitchen-sink 页面新增对应展示区块

## R4 备选流程与异常流程
- **备选流程**：
  - A1：盘点后发现候选模式的重复实例不足 3 个——降级为不收口，记录原因，避免为了凑数过度抽象
- **异常流程**：
  - E1：某个业务目录的"表格"实际语义差异很大（如一个是数据表格、一个是设置项列表），强行收口成同一组件会导致 API 过度复杂——需要拆成 2 个更聚焦的原语而不是 1 个万能组件
  - E2：pagination 组件涉及的分页逻辑（如游标分页 vs 页码分页）在不同业务场景不一致——组件层只负责展示与交互，不强行统一底层分页策略

## R5 权限与可见性
- 无业务权限差异

## R6 后置条件 / 不包含
- **后置条件**：3-5 个新复合组件原语落地；对应业务目录的重复实现清零或降到 0-1（允许特例但需注释说明）
- **不包含**：不强行收口重复次数不足 3 次的模式；不改变具体业务页面的信息架构，只统一展示层组件

## R7 业务规则
- 新原语的视觉语言必须与 IT-01 产出的弹层组件保持一致（同一套圆角/阴影/间距 token）

## R8 界面线索
- 前端入口：org-admin 成员列表、profile 历史记录、canvas 相关的列表/分页场景（具体候选需盘点后确认）
- 提醒：本 feature 涉及可见 UI 改动，属于 has_ui 阶段，开工前需人类签核

## R9 非功能约束
- 性能/规模预期：table 类组件需验证大数据量（如百行以上）渲染性能不明显劣化于现有实现
- 兼容与降级要求：375/768/1280 三档视口无横向溢出

## R10 已知约束 / 依赖
- 依赖：「01-component-primitives-overlays」的 dropdown 实现（menu 组件复用）
- 技术约束：与 IT-01 一致，Tailwind + CVA + `cn()`

## R11 切分提示
- 期望粒度：可按组件类型拆分为多个小 feature，也可合并（工作量评估 L，1-2 周）
- 优先级：依赖 IT-01，建议排在 IT-02/03/04/05 之后、IT-07 之前

## R12 AI Ready 验收线索
- 可验证行为：`lint-design.sh` 全绿；grep 验证目标模式在业务目录的重复实现数量降到 0-1；kitchen-sink 能看到新组件展示
