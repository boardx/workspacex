# 原始需求 — 评审证据结构化归档

估点 **2**

> 来源：2026-08-23《WorkspaceX 十分制评估》缺口「验收成熟度」+《十分冲刺 Backlog》IT-08。

## R1 概览
- **Use Case 名称**：把 rev-uiux 评审结果结构化落盘
- **Actor**：负责 rev-uiux 评审的 agent；后续做趋势分析/规则制定的开发 agent
- **目标**：`rev-uiux` 的评分历史目前散落在 git log / issue 评论 / rubric 文件的裁决注记里，没有一处能离线聚合"过去 N 次评审的分数分布 / 最常见扣分维度"。目标是建立结构化日志，并回填可找到的历史记录，为后续把"反复扣分的维度"前移成 lint 规则提供数据基础。
- **系统边界**：`.harness/state/`（新增文件）、既有 rev-uiux 评审产出的 git log / issue 记录

## R2 前置条件 / 触发条件
- **前置条件**：`.harness/rubrics/chat-main-fidelity-rubric.md`、`uiux-screenshot-review-profile-org.md` 等评分卡已存在
- **触发条件**：本 feature 开工时先建结构 + 回填历史；此后每次 rev-uiux 评审完成后追加一条记录（流程约定，非本 feature 直接控制运行时行为）

## R3 主流程
1. 在 `.harness/state/` 下新增 `uiux-review-log.jsonl`（或等价结构化格式），字段包括：评审对象（页面/域）、评审日期、使用的评分卡、十维/十项各自得分、总分、扣分项说明、对应的 issue/PR 链接
2. 写一个脚本，从历史 git log（关键词如 "uiux" "fidelity" "保真度" "D2" "D3" 等）里尽力提取可识别的评审记录，回填进日志（回填数据的完整度取决于历史记录本身的可解析程度，无法解析的部分明确记录为"未能回填"而不是编造）
3. 写一个统计脚本/命令，跑出"最常反复扣分的维度"Top 5
4. 更新流程文档（如 `uiux-standards.md` 或 rubric 文件本身），约定以后每次 rev-uiux 评审后追加一条记录到日志

## R4 备选流程与异常流程
- **备选流程**：
  - A1：某次评审使用了自定义评分维度（不完全对应现有 rubric）——日志结构需要能容纳非标准维度，不强行套用固定 schema
- **异常流程**：
  - E1：历史 git log 里的评审记录格式不统一，脚本无法可靠解析——明确标注哪些记录无法自动回填，列出人工可选择性补充的清单，不能为了完整度伪造数据
  - E2：Top 5 扣分维度统计结果样本量过小（历史评审次数不足）——如实报告样本量，不能用小样本冒充趋势结论

## R5 权限与可见性
- 无业务权限差异，这是内部治理数据

## R6 后置条件 / 不包含
- **后置条件**：`.harness/state/uiux-review-log.jsonl` 建立并回填历史数据；统计脚本可用；Top 5 扣分维度报告产出，且至少 1 条能对应到一个新的 lint 规则或组件修复建议
- **不包含**：不要求追溯所有历史记录（早期可能确实缺失可解析数据），不建独立的可视化 dashboard（本 feature 只做数据结构与统计脚本）

## R7 业务规则
- 日志一旦写入不应被追溯性篡改评分本身（如需要修正错误记录，应追加更正记录而不是静默改写历史值），保持审计可追溯性

## R8 界面线索
- 前端入口：无，本 feature 是纯后台治理数据结构，不涉及 apps/web 前端 UI
- 提醒：本 feature 不涉及可见 UI，不需要契约束级设计签核

## R9 非功能约束
- 性能/规模预期：无特殊要求（数据量小）
- 安全/隐私/合规：无特殊要求

## R10 已知约束 / 依赖
- 依赖：现有 rubric 文件的评分维度定义
- 技术约束：无

## R11 切分提示
- 期望粒度：单个 feature 可完成（工作量评估 S，1-2 天）
- 优先级：建议在「09-screenshot-fidelity-review」之前完成，为其提供落盘结构
