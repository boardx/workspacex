## M7 Delivery 落地与度量

### M7-01 Strategy Roadmap · 战略路线图
- **来源**：通用设计实践
- **目的**：把已选定的方案排成分阶段的推出顺序，讲清先做什么、后做什么、为什么。
- **何时用**：方案已收敛，需要向决策层说明多期投入节奏；**不适用**：方案还没定，或只是单次小改版。
- **输入**：收敛后的方案清单（M6-11 的方案路线图更佳）、资源与时间约束、关键依赖。
- **步骤**：
  1. 列出所有方案要素，标注依赖关系和前置能力。
  2. 定 3–4 个时间段（如 近期 / 中期 / 远期），为每段写一句阶段目标。
  3. 把方案要素放进时间段，依赖在前、验证风险大的尽早试点。
  4. 每段写明进入下一段的判断条件（要看到什么信号才继续）。
  5. 与相关方走一遍，记录分歧并修订。
- **产出**：路线图表：阶段 / 时间窗 / 阶段目标 / 包含方案 / 依赖 / 进入下一段条件。
- **耗时 / 人数**：半天到 2 天；2–6 人（含决策人）。
- **AI 协作**：agent 可根据方案与依赖起草分段结构、指出依赖冲突；时间、预算、优先取舍必须由用户和决策人确认，不替用户承诺日期。
- **衔接**：上游 M6-11 → 下游 M7-02、M7-05

### M7-02 Platform Plan · 平台计划
- **来源**：通用设计实践
- **目的**：找出多个产品/服务可共享的底层能力，规划平台与其上的产品线。
- **何时用**：多个方案重复依赖同类能力（数据、账号、agent 运行时等）；**不适用**：只有单一产品且短期不扩展。
- **输入**：战略路线图、各方案的能力需求、现有系统清单。
- **步骤**：
  1. 为每个方案列出所需的底层能力。
  2. 找出被 2 个以上方案复用的能力，候选为平台层。
  3. 分出平台层 / 产品层 / 渠道层，画分层图。
  4. 为平台能力定接口边界和负责人。
  5. 按路线图排出平台先建、产品后接的顺序。
- **产出**：分层平台图 + 能力清单（能力 / 复用方 / 负责人 / 上线阶段）。
- **耗时 / 人数**：1–3 天；产品 + 技术负责人 3–5 人。
- **AI 协作**：agent 可做能力矩阵、识别复用与重复建设；现有系统能力、团队归属必须由用户提供。
- **衔接**：上游 M7-01 → 下游 M7-06、M7-11

### M7-03 Strategy Plan Workshop · 战略规划工作坊
- **来源**：通用设计实践
- **目的**：让关键相关方在一场工作坊里对落地战略达成共识。
- **何时用**：路线图草案已有，但各方目标或优先级不一致；**不适用**：决策权集中在一人且已拍板。
- **输入**：路线图草案、平台计划、关键洞察摘要；决策人与执行负责人到场。
- **步骤**：
  1. 会前发阅读包，统一背景。
  2. 开场复述愿景与目标，确认评判标准。
  3. 分组审视各阶段：风险、依赖、资源缺口。
  4. 集中讨论分歧点，用投票或决策人裁决收敛。
  5. 当场写下决定、负责人、下一步，会后 24 小时内发纪要。
- **产出**：共识战略计划：决定清单 / 未决问题 / 负责人 / 时间点。
- **耗时 / 人数**：半天到 1 天；6–15 人。
- **AI 协作**：agent 可准备议程、阅读包、分组问题和纪要模板，会后整理纪要；会上的决定只记录用户提供的真实结论，不补写。
- **衔接**：上游 M7-01 → 下游 M7-05、M7-09

### M7-04 Pilot Development and Testing · 试点开发与测试
- **来源**：通用设计实践
- **目的**：在真实但受控的范围里运行方案，验证它在实际情境中是否成立。
- **何时用**：原型测试已通过，要在真实用户和流程里跑一段时间；**不适用**：还没做过任何原型验证，或无法限定试点范围。
- **输入**：可运行的方案版本、试点对象（团队/地区/用户群）、成功标准、回退方案。
- **步骤**：
  1. 写试点假设与成功/失败标准（先写好再开始）。
  2. 选定试点范围和时长，准备回退方式。
  3. 部署并定期收集行为数据与反馈。
  4. 中期检查，只修阻断性问题，避免边跑边改变量。
  5. 结束时对照标准判定：推广 / 修改后再试 / 停止。
- **产出**：试点报告：假设 / 范围 / 数据 / 反馈摘要 / 判定与理由。
- **耗时 / 人数**：2–8 周；小团队 + 试点用户。
- **AI 协作**：agent 可起草试点计划、成功标准和反馈问卷，整理用户提供的数据；试点结果与指标必须来自真实运行，绝不编造。
- **衔接**：上游 M6-09、M6-10 → 下游 M7-05、M7-20

### M7-05 Implementation Plan · 实施计划
- **来源**：通用设计实践
- **目的**：把方案拆成可执行的工作包、里程碑和负责人。
- **何时用**：决定推进后，需要落到具体排期；**不适用**：方案仍在探索阶段。
- **输入**：战略路线图、试点结论、团队与预算约束。
- **步骤**：
  1. 按路线图第一阶段拆工作包（交付物粒度）。
  2. 为每个工作包写负责人、依赖、验收标准。
  3. 排里程碑，标关键路径。
  4. 列主要风险与应对。
  5. 定沟通与复查节奏。
- **产出**：实施计划表：工作包 / 负责人 / 依赖 / 验收标准 / 里程碑 / 风险。
- **耗时 / 人数**：1–2 天；项目负责人 + 各职能代表。
- **AI 协作**：agent 可拆解工作包、找依赖与关键路径、生成风险清单；人员、工期估算必须由用户确认。
- **衔接**：上游 M7-01、M7-04 → 下游 M7-07、M7-10

### M7-06 Competencies Plan · 能力计划
- **来源**：通用设计实践
- **目的**：对比方案需要的能力与组织现有能力，给出补齐方式。
- **何时用**：方案需要组织目前不具备的技能或资源；**不适用**：现有团队已完全覆盖。
- **输入**：平台计划/实施计划中的能力需求、现有团队能力盘点。
- **步骤**：
  1. 列出方案所需能力（技术、设计、运营、合规等）。
  2. 为每项标现状：已具备 / 部分 / 缺失。
  3. 对缺口选补齐方式：培养 / 招聘 / 合作 / 外购 / 工具化。
  4. 估算补齐所需时间，与路线图对齐。
- **产出**：能力缺口表：能力 / 现状 / 补齐方式 / 时间 / 负责人。
- **耗时 / 人数**：半天到 1 天；2–4 人。
- **AI 协作**：agent 可根据方案推导能力需求、列补齐选项；团队现状只能由用户提供，不推断个人能力。
- **衔接**：上游 M7-02 → 下游 M7-07

### M7-07 Team Formation Plan · 团队组建计划
- **来源**：通用设计实践
- **目的**：确定执行方案的团队结构、角色和协作方式。
- **何时用**：要为新方案组建或重组团队；**不适用**：沿用现有团队且职责无变化。
- **输入**：实施计划、能力计划、可用人员。
- **步骤**：
  1. 从工作包推导需要的角色。
  2. 定团队结构（跨职能小队 / 平台组 / 虚拟团队）。
  3. 写每个角色的职责与决策权。
  4. 定协作接口：与哪些团队、以什么节奏对接。
  5. 标出空缺及到位时间。
- **产出**：团队结构图 + 角色表（角色 / 职责 / 决策权 / 人员 / 到位时间）。
- **耗时 / 人数**：半天；负责人 + HR/管理者。
- **AI 协作**：agent 可起草角色与职责、对照工作包查漏；具体人选与编制由用户决定。
- **衔接**：上游 M7-05、M7-06 → 下游 M7-20

### M7-08 Vision Statement · 愿景陈述
- **来源**：通用设计实践
- **目的**：用简短文字讲清方案要为谁创造什么改变，统一团队方向。
- **何时用**：项目启动或进入落地前，需要一句大家都能复述的方向；**不适用**：代替具体目标和指标。
- **输入**：意图陈述、关键洞察、设计原则。
- **步骤**：
  1. 回答三问：为谁？带来什么改变？为什么是我们？
  2. 各自写一版，汇总比较。
  3. 合并成 1–3 句，去掉空话和行业黑话。
  4. 用"新成员能否据此做判断"检验，修订定稿。
- **产出**：愿景陈述（1–3 句）+ 一段解释 + 不做什么。
- **耗时 / 人数**：1–3 小时；3–8 人。
- **AI 协作**：agent 可基于洞察起草多个版本、指出空泛措辞；最终选择由团队定。
- **衔接**：上游 M1-14、M4-18 → 下游 M7-09、M7-01

### M7-09 Innovation Brief · 创新简报
- **来源**：通用设计实践
- **目的**：把整个项目的洞察、方案、计划浓缩成一份可以交接和传播的简报。
- **何时用**：向管理层汇报、交给执行团队或外部合作方；**不适用**：研究还没有结论。
- **输入**：愿景、关键洞察、方案、路线图、实施计划。
- **步骤**：
  1. 定读者和他们要做的决定。
  2. 按"问题 → 洞察 → 方案 → 价值 → 计划 → 所需支持"组织。
  3. 每部分只保留最有力的证据，附来源。
  4. 控制在 1–3 页，另附附录。
  5. 请一位未参与者读一遍，改掉看不懂的地方。
- **产出**：创新简报（1–3 页）+ 附录（证据与来源）。
- **耗时 / 人数**：半天到 1 天；1–2 人撰写。
- **AI 协作**：agent 可汇编已有材料并起草简报；数据与引文只用用户提供并可定位的来源，不补数字。
- **衔接**：上游 M7-08、M7-03 → 下游 M7-05

### M7-10 User Story Mapping · 用户故事地图
- **来源**：Jeff Patton
- **目的**：沿用户活动主线排列用户故事，切出可逐步发布的版本。
- **何时用**：从设计交给开发，需要确定首个发布范围；**不适用**：纯技术改造、没有用户流程。
- **输入**：旅程地图或任务地图、方案功能清单、产品与开发代表。
- **步骤**：
  1. 横向写用户活动主干（按时间顺序的大步骤）。
  2. 每个活动下纵向列用户任务和故事，越重要越靠上。
  3. 走一遍主干，补漏掉的步骤。
  4. 横切：第一刀切出能端到端走通的最小版本，再切后续版本。
  5. 为每个切片写发布目标。
- **产出**：故事地图：活动主干 / 故事 / 发布切片（含每片目标）。
- **耗时 / 人数**：2–4 小时；产品、设计、开发 3–7 人。
- **AI 协作**：agent 可从旅程和功能清单生成主干与故事草稿、检查切片是否端到端；优先级与切法由团队定。
- **衔接**：上游 M4-16、M4-22 → 下游 M7-11、M7-14

### M7-11 Event Storming · 事件风暴
- **来源**：Brandolini / DDD
- **目的**：用领域事件把业务流程摊开，找出边界、命令和聚合，给系统设计打底。
- **何时用**：业务流程复杂、涉及多团队或多系统；**不适用**：简单 CRUD 或纯界面调整。
- **输入**：领域专家 + 开发 + 产品到场；长墙或在线白板；不同颜色便签。
- **步骤**：
  1. 所有人自由写"已发生的业务事件"（过去式），贴在时间线上。
  2. 排序、去重，标出热点（疑问、冲突）。
  3. 为事件补触发它的命令、执行者、读取的信息和外部系统。
  4. 聚合相关事件，划出限界上下文。
  5. 记录热点和待决问题，指定负责人。
- **产出**：事件时间线 + 命令/聚合/上下文边界图 + 热点清单。
- **耗时 / 人数**：半天到 2 天；5–15 人。
- **AI 协作**：agent 可从需求或文字流程里提取候选事件和命令、整理白板结果；领域规则以专家当场说明为准。
- **衔接**：上游 M7-10、M6-13 → 下游 M7-05

### M7-12 Impact Mapping · 影响地图
- **来源**：Gojko Adzic
- **目的**：从业务目标倒推"影响谁、让他们如何改变、我们交付什么"，防止做与目标无关的功能。
- **何时用**：功能清单很长但说不清和目标的关系；**不适用**：目标本身还没定。
- **输入**：可度量的业务目标、相关角色。
- **步骤**：
  1. 写目标（为什么）：一个可度量的结果。
  2. 列角色（谁）：能促成或阻碍目标的人。
  3. 列影响（怎样）：希望这些角色的行为如何改变。
  4. 列交付物（做什么）：能促成该影响的功能或活动。
  5. 选一条最短路径先做，定度量方式。
- **产出**：四层树：目标 → 角色 → 影响 → 交付物，标出优先路径。
- **耗时 / 人数**：1–2 小时；3–6 人。
- **AI 协作**：agent 可展开角色和影响、检查交付物是否挂在某条影响下；目标数值由用户给。
- **衔接**：上游 M6-16、M7-08 → 下游 M7-10、M7-17

### M7-13 Design System / Design Tokens · 设计系统
- **来源**：设计系统实践
- **目的**：把视觉与交互决定沉淀成可复用的组件和 token，保证设计与代码一致。
- **何时用**：多个界面或团队需要统一风格、实现开始重复；**不适用**：一次性原型或极早期探索。
- **输入**：现有界面截图/代码、品牌规范、组件使用情况。
- **步骤**：
  1. 盘点现有界面，收集颜色、字号、间距、组件变体。
  2. 合并重复，定 token 层级（基础值 → 语义 token → 组件 token）。
  3. 定义核心组件：用途、状态、变体、可访问性要求。
  4. token 只在一处声明，由代码和设计工具共同引用。
  5. 定贡献与变更流程。
- **产出**：token 表（名称 / 值 / 语义 / 使用场景）+ 组件规范 + 变更流程。
- **耗时 / 人数**：初版 1–4 周；设计 + 前端。
- **AI 协作**：agent 可从样式代码中盘点重复值、起草 token 命名和组件文档；品牌取值与最终规范由用户确认。
- **衔接**：上游 M6-09 → 下游 X2-02、M7-10

### M7-14 MVP / Build-Measure-Learn · 最小可行产品
- **来源**：Lean Startup
- **目的**：用最小投入做出能验证关键假设的版本，按 构建 → 度量 → 学习 迭代。
- **何时用**：核心价值假设未经市场验证；**不适用**：合规或安全要求决定了不能"先粗后细"的场景。
- **输入**：价值假设、要验证的最危险假设、度量方式。
- **步骤**：
  1. 选出最危险、一旦错了全盘皆输的假设。
  2. 定验证标准：看到什么数据算成立 / 不成立（先写）。
  3. 选最小形式（落地页、人工服务、单一功能）。
  4. 上线收集行为数据，不只看口头反馈。
  5. 对照标准判定：坚持 / 调整 / 放弃，进入下一轮。
- **产出**：假设卡：假设 / 最小形式 / 标准 / 实际数据 / 结论；对话中用 canvas 模板交付（见 references/templates.md T-09）。
- **耗时 / 人数**：每轮 1–4 周；小团队。
- **AI 协作**：agent 可梳理假设、设计最小形式和判定标准；数据与结论只来自真实运行，不编造指标。
- **衔接**：上游 M5-02、M6-16 → 下游 M7-15、M7-18

### M7-15 Fake Door Test · 假门测试
- **来源**：Lean 实践
- **目的**：放一个尚未实现的功能入口，看有多少人点，获取真实需求信号。
- **何时用**：在投入开发前判断需求强度；**不适用**：会损害用户信任的关键流程（支付、安全）。
- **输入**：功能描述、放置位置、流量、点击后的告知文案。
- **步骤**：
  1. 定判定阈值（如点击率高于多少才开发）。
  2. 设计入口，与真实功能入口同等醒目。
  3. 点击后如实告知"正在开发"，可让用户留联系方式。
  4. 运行到样本足够，记录曝光与点击。
  5. 对照阈值决策，并通知留下联系方式的用户结果。
- **产出**：需求信号记录：曝光 / 点击 / 留资 / 与阈值对比 / 决策。
- **耗时 / 人数**：1–2 周；1–2 人。
- **AI 协作**：agent 可设计入口文案、告知文案和阈值；点击数据必须来自真实埋点。要诚实告知用户，不做诱导。
- **衔接**：上游 M7-14 → 下游 M7-16、M7-05

### M7-16 A/B Testing · A/B 测试
- **来源**：实验设计
- **目的**：随机分流对比两个版本，判断差异是否超出随机波动。
- **何时用**：有足够流量、改动可量化、需要因果证据；**不适用**：流量太小、效果要很久才显现、或伦理上不能对部分用户隐瞒。
- **输入**：假设、主指标与护栏指标、最小可检测效应、流量估计。
- **步骤**：
  1. 写假设和主指标，事先定显著性水平与样本量。
  2. 设护栏指标（如错误率、流失），防止局部优化伤整体。
  3. 随机分流，检查两组基线一致。
  4. 跑满预定样本再看结果，不中途偷看就停。
  5. 报告效应大小、置信区间与护栏结果，再做决策。
- **产出**：实验报告：假设 / 指标 / 样本 / 效应与区间 / 显著性 / 护栏 / 决策。
- **耗时 / 人数**：1–4 周；产品 + 数据分析。
- **AI 协作**：agent 可设计实验、估算样本量、解释用户提供的结果；绝不编造转化率、p 值或显著性结论。
- **衔接**：上游 M7-15、M7-14 → 下游 M7-17

### M7-17 HEART Metrics · 体验指标
- **来源**：Google（名称及原版素材归权利人所有，此处仅作出处说明；本卡为自写说明，未复制原版素材）
- **目的**：从愉悦、参与、采纳、留存、任务成功五个维度建立体验指标体系。
- **何时用**：要为新功能或产品定义"体验好不好"的度量；**不适用**：只关心单一业务指标。
- **输入**：产品目标、可采集的行为数据与问卷渠道。
- **步骤**：
  1. 对五个维度（Happiness / Engagement / Adoption / Retention / Task success）逐一判断是否适用。
  2. 每个适用维度写目标（Goal）。
  3. 为目标找行为信号（Signal）。
  4. 把信号转成可计算的指标（Metric），定口径。
  5. 确认埋点与数据来源，定期回看。
- **产出**：目标-信号-指标表（维度 / 目标 / 信号 / 指标 / 口径 / 数据源）。
- **耗时 / 人数**：半天；产品、设计、数据 3–5 人。
- **AI 协作**：agent 可起草 目标-信号-指标 表、检查口径歧义；基线与目标值由用户提供，不假设数字。
- **衔接**：上游 M7-12 → 下游 M7-18、M7-19

### M7-18 Funnel / Cohort Analysis · 漏斗与留存分析
- **来源**：产品分析
- **目的**：找出流程中流失最多的步骤，以及不同批次用户的留存差异。
- **何时用**：已上线且有行为数据，要定位问题环节；**不适用**：没有可靠埋点或样本极少。
- **输入**：事件数据、漏斗步骤定义、分组口径（按注册周/渠道等）。
- **步骤**：
  1. 定义漏斗步骤和时间窗口。
  2. 计算每步转化与流失，找最大的掉落点。
  3. 按批次（cohort）画留存曲线，比较版本或渠道差异。
  4. 对异常点提出假设，用访谈或录屏找原因。
  5. 把假设转成下一轮改进或实验。
- **产出**：漏斗图 + 留存曲线 + 流失点假设清单。
- **耗时 / 人数**：半天到 2 天；1–2 人。
- **AI 协作**：agent 可写查询思路、定义口径、解读用户给出的数据；不在没有数据时给出转化率或留存数字。
- **衔接**：上游 M7-17、M2-17 → 下游 M7-16、M3-07

### M7-19 Feedback Loop / NPS · 反馈闭环
- **来源**：通用
- **目的**：持续收集用户反馈，分诊、处理，并把结果告诉提出反馈的人。
- **何时用**：产品已上线，需要稳定的用户声音通道；**不适用**：只做一次性调查（用 M3-23）。
- **输入**：反馈渠道、分诊规则、负责人、NPS 或满意度问卷（可选）。
- **步骤**：
  1. 统一反馈入口，记录来源和上下文。
  2. 按类型（缺陷/需求/困惑）和严重度分诊，指派负责人。
  3. 定处理时限，关联到 issue 或需求。
  4. 处理后回复反馈者，说明结果或不做的理由。
  5. 定期汇总趋势；NPS 只看趋势并必须配开放题原因。
- **产出**：反馈台账：来源 / 类型 / 严重度 / 负责人 / 状态 / 回复记录 + 周期趋势。
- **耗时 / 人数**：持续运营；1 人主责。
- **AI 协作**：agent 可对真实反馈分类、去重、起草回复；NPS 分数和满意度数字只能来自真实问卷，不估算。
- **衔接**：上游 M7-17 → 下游 M7-20、M4-20

### M7-20 Retrospective · 复盘
- **来源**：敏捷实践
- **目的**：回看一个周期，找出做得好的、要改的，形成具体行动项。
- **何时用**：迭代、试点、项目阶段结束；**不适用**：用作追责会。
- **输入**：该周期的目标、事实时间线、数据与反馈；全体参与者。
- **步骤**：
  1. 重申安全前提：对事不对人。
  2. 先还原事实时间线，再谈感受和判断。
  3. 用"保持 / 改进 / 尝试"等格式收集意见。
  4. 聚类、投票选出 1–3 个最值得改的点。
  5. 每项写成有负责人和期限的行动，下次复盘先检查。
- **产出**：复盘记录：时间线 / 要点 / 行动项（内容 / 负责人 / 期限）。
- **耗时 / 人数**：45–90 分钟；全团队。
- **AI 协作**：agent 可整理时间线、引导提问、归类意见；事实与感受由参与者提供，不替人写结论。
- **衔接**：上游 M7-04、M7-19 → 下游 M7-05

## X1 AI 产品设计

### X1-01 People + AI Guidebook · 人与 AI 指南
- **来源**：Google PAIR（名称及原版素材归权利人所有，此处仅作出处说明；本卡为自写说明，未复制原版素材）
- **目的**：按 AI 产品的关键设计问题逐项自查：用户需求、心智模型、数据、可解释、反馈、出错与兜底。
- **何时用**：设计或评审任何 agent / AI 功能；**不适用**：功能里没有模型决策。
- **输入**：功能描述、目标用户、模型能力与局限说明。
- **步骤**：
  1. 先问"这件事真的该用 AI 吗"：确定性规则能否更好解决。
  2. 定自动化程度：agent 直接执行、给建议、还是只辅助。
  3. 设计入门：怎样告诉用户 agent 能做什么、不能做什么。
  4. 设计解释与置信：何时展示依据来源、何时说"我不确定"。
  5. 设计反馈与纠错：用户如何改正结果，改正如何影响后续。
  6. 设计出错兜底：失败时的替代路径和人工接管。
- **产出**：AI 体验检查表：问题 / 当前设计 / 缺口 / 改进项。
- **耗时 / 人数**：2–4 小时；产品、设计、算法。
- **AI 协作**：agent 可逐项提问并起草检查表；模型实际能力与局限需用户用真实测试确认。
- **衔接**：上游 M6-09 → 下游 X1-06、X1-07

### X1-02 HAX Guidelines · 人机交互 18 条准则
- **来源**：Microsoft（名称及原版素材归权利人所有，此处仅作出处说明；本卡为自写说明，未复制原版素材）
- **目的**：用一组覆盖 初次接触 / 交互中 / 出错时 / 长期使用 四个时段的准则，评估 AI 功能的交互质量。
- **何时用**：对已有原型或上线功能做系统性审查；**不适用**：还没有任何交互形态。
- **输入**：可操作原型或产品、典型任务。
- **步骤**：
  1. 按四个时段分组准则，逐条对照（不确定条目原文时以原则描述为准）。
  2. 初次接触：是否说清能做什么、做得多好。
  3. 交互中：是否结合上下文、时机合适、不打断。
  4. 出错时：是否易于撤销、纠正、说明原因。
  5. 长期：是否从用户行为学习、变化时告知、允许全局调节。
  6. 每条标 符合 / 部分 / 违反，附证据截图。
- **产出**：准则符合度表：准则 / 判定 / 证据 / 改进建议。
- **耗时 / 人数**：半天；2–3 人。
- **AI 协作**：agent 可引导逐条评审、归纳问题；判定证据必须来自用户实际操作或截图。
- **衔接**：上游 X1-01 → 下游 X1-06、M6-20

### X1-03 Wizard of Oz for AI · AI 绿野仙踪原型
- **来源**：交互设计
- **目的**：由人在幕后扮演 agent，先验证交互方式和价值，再决定是否投入模型开发。
- **何时用**：agent 能力尚未实现，想知道用户如何提问、期待什么回答；**不适用**：已有可用模型，直接做提示词原型更快。
- **输入**：场景脚本、扮演者、回复规范（模拟模型可能的局限）、知情同意说明。
- **步骤**：
  1. 写任务场景和 agent 应有的能力边界。
  2. 给扮演者回复规范：响应时延、会犯的典型错误、何时说"不确定"。
  3. 用户按场景与"agent"交互，记录输入、期待、反应。
  4. 故意插入错误回复，观察用户能否发现并纠正。
  5. 结束后说明是人工扮演，访谈期待与信任感。
- **产出**：会话记录 + 用户意图分类 + 对错误的反应 + 需要的能力清单。
- **耗时 / 人数**：3–5 天；扮演者 1、主持 1、用户 5–8。
- **AI 协作**：agent 可写脚本和回复规范、分析会话记录；不能替代真实用户参与，不编造用户反应。
- **衔接**：上游 M5-25 → 下游 X1-04、X1-05

### X1-04 Prompt Prototyping · 提示词原型
- **来源**：AI 产品实践
- **目的**：用提示词和少量样例快速做出可对话的 agent / skill 原型，检验输出是否可用。
- **何时用**：要判断一个 skill 的输出质量是否达到可用门槛；**不适用**：问题本质上需要确定性规则或精确计算。
- **输入**：任务定义、10–30 条真实代表性输入、期望输出样例、可用工具清单。
- **步骤**：
  1. 写任务说明：角色、输入、输出格式、禁止事项、何时拒绝或追问。
  2. 用代表性输入跑一轮，逐条记录输出。
  3. 标注问题类型：事实错误、格式偏离、过度自信、漏追问。
  4. 按问题改提示词或补工具，一次改一处，重跑对比。
  5. 把稳定的样例沉淀为评测集种子。
- **产出**：提示词版本 + 样例输入输出对照 + 问题标注表。
- **耗时 / 人数**：半天到数天；1–2 人。
- **AI 协作**：agent 可起草和改写提示词、批量标注问题类别；样例输入应来自用户授权的真实数据，质量判断需用户确认。
- **衔接**：上游 X1-03 → 下游 X1-05、X1-06

### X1-05 Eval-driven Design · 评测驱动设计
- **来源**：AI 产品实践
- **目的**：先定义"什么算好"的评测集和通过标准，再迭代 agent，让每次改动可比较。
- **何时用**：agent / skill 进入持续迭代，需要防止改一处坏一处；**不适用**：还在判断方向是否成立的最早期。
- **输入**：真实用例、失败案例、质量维度定义、评审人。
- **步骤**：
  1. 定质量维度：正确性、依据可追溯、格式、拒答/追问得当、安全。
  2. 收集用例：常见、边界、对抗、历史失败，各类都要有。
  3. 为每条用例写期望行为和判定方式（规则检查 / 人工评分 / 模型评分并抽样人工核对）。
  4. 定通过标准和不可回退的红线用例。
  5. 每次改提示词、模型或工具后全量重跑，记录对比。
  6. 线上新失败回流进评测集。
- **产出**：评测集（用例 / 类别 / 期望 / 判定方式）+ 通过标准 + 版本对比记录。
- **耗时 / 人数**：初版 2–5 天，之后持续；1–3 人。
- **AI 协作**：agent 可设计维度、生成候选边界用例、执行规则检查；分数只来自真实运行结果，期望答案需用户或领域专家确认。
- **衔接**：上游 X1-04 → 下游 X1-06、M7-14

### X1-06 AI Failure Mode Mapping · AI 出错模式地图
- **来源**：AI 产品实践
- **目的**：系统列出 agent 会怎样出错、用户会怎样受影响，并为每种出错设计兜底。
- **何时用**：agent 会执行动作、写入数据或给出建议前；**不适用**：无（任何 AI 功能都应做）。
- **输入**：用户任务流程、agent 能力与工具权限、已知失败案例。
- **步骤**：
  1. 沿任务流程逐步问"这里 agent 可能怎么错"：误解意图、编造、遗漏、越权、过期信息、无法完成。
  2. 对每种出错标：发生可能性、用户能否察觉、后果严重度。
  3. 高严重或难察觉的项优先设计兜底：确认步骤、展示来源、可撤销、降级为建议。
  4. 设计用户纠正方式：直接编辑结果、指出错误、回退版本。
  5. 把出错模式转成评测用例。
- **产出**：出错模式表：步骤 / 出错类型 / 可察觉性 / 严重度 / 兜底 / 纠正方式。
- **耗时 / 人数**：2–4 小时；产品、设计、工程。
- **AI 协作**：agent 可枚举候选出错模式和兜底方案；实际发生频率只能用真实日志或测试结果，不估造比例。
- **衔接**：上游 X1-01、X1-04 → 下游 X1-05、X1-07

### X1-07 Trust Calibration · 信任校准设计
- **来源**：人因工程
- **目的**：让用户对 agent 的信任与它的实际可靠程度相匹配，既不盲信也不弃用。
- **何时用**：用户过度依赖或完全不信任 agent 输出；**不适用**：输出可被机械验证、无需判断的场景。
- **输入**：agent 在各类任务上的真实表现（来自评测）、用户对 agent 的信任反馈。
- **步骤**：
  1. 按任务类型区分可靠区与不可靠区（依据评测结果）。
  2. 设计信任信号：引用来源、标出推断与事实、说明缺什么信息。
  3. 在不确定时明确表达（追问、给多个选项、建议人工核对），而不是给看似确定的答案。
  4. 高风险动作前要求确认，展示将发生的变化。
  5. 用访谈或任务测试检查用户是否正确判断何时该核对。
- **产出**：信任信号设计表：场景 / 可靠度依据 / 显示方式 / 确认要求。
- **耗时 / 人数**：1–2 天；设计 + 研究。
- **AI 协作**：agent 可提出信号与文案方案；可靠度必须来自真实评测，不自报置信度数字。
- **衔接**：上游 X1-05、X1-06 → 下游 M6-22

## X2 包容与伦理

### X2-01 Inclusive Design Toolkit / Persona Spectrum · 包容性设计
- **来源**：Microsoft（名称及原版素材归权利人所有，此处仅作出处说明；本卡为自写说明，未复制原版素材）
- **目的**：从永久、暂时、情境三类能力受限出发，找出被排除的人并改进方案。
- **何时用**：方案进入细化，想扩大可用人群；**不适用**：替代正式无障碍合规审计（用 X2-02）。
- **输入**：方案或原型、关键任务、目标人群。
- **步骤**：
  1. 对关键任务列出所需能力（看、听、说、触控、认知、语言等）。
  2. 为每种能力画谱系：永久（如失明）、暂时（如眼部受伤）、情境（如强光下看屏）。
  3. 找出谱系中会被排除的人和场景。
  4. 为每个排除点提出调整，优先那些对所有人都有益的。
  5. 请相关用户参与测试。
- **产出**：能力谱表：任务 / 能力 / 永久-暂时-情境 例子 / 排除点 / 调整。
- **耗时 / 人数**：半天；2–4 人 + 受影响用户。
- **AI 协作**：agent 可展开能力谱、提出调整建议；受影响人群的真实体验需由用户组织研究获取。
- **衔接**：上游 M5-03 → 下游 X2-02、M6-22

### X2-02 Accessibility Audit (WCAG) · 无障碍审计
- **来源**：W3C
- **目的**：按 WCAG 的可感知、可操作、可理解、健壮四原则检查产品，列出无障碍问题。
- **何时用**：上线前或设计系统定稿时；**不适用**：只看自动工具报告就当审计完成。
- **输入**：可访问的界面、目标一致性等级（如 AA）、自动检测工具、键盘与读屏软件。
- **步骤**：
  1. 定范围：关键页面和任务流程。
  2. 跑自动检测，记录对比度、替代文本、标签等问题。
  3. 人工检查：纯键盘走完流程、焦点顺序、读屏朗读内容。
  4. 检查动态内容：错误提示、实时更新、agent 流式输出是否能被读屏感知。
  5. 按四原则归类，标严重度与修复建议。
- **产出**：问题清单：页面 / 问题 / 对应原则 / 严重度 / 修复建议 / 验证方式。
- **耗时 / 人数**：1–3 天；1–2 人。
- **AI 协作**：agent 可审查代码或截图中的常见问题、给修复建议；读屏和键盘实际表现必须真实测试，不推断通过。
- **衔接**：上游 M7-13、X2-01 → 下游 M7-05

### X2-03 Consequence Scanning · 后果扫描
- **来源**：Doteveryone
- **目的**：在开发节奏里定期问"这个功能会带来哪些预期和非预期后果"，并决定如何应对。
- **何时用**：功能规划或迭代开始时；涉及数据、自动化决策、行为引导时必做；**不适用**：替代法律合规审查。
- **输入**：功能描述、相关方清单、团队成员。
- **步骤**：
  1. 列功能的预期后果（对用户、团队、社会）。
  2. 列非预期后果：正面、负面各想一轮，考虑弱势人群和滥用者。
  3. 把后果分为：要做的（行动）、要影响的（缓解）、要监测的。
  4. 为负面后果写对策和负责人。
  5. 下次迭代回看，检查监测项。
- **产出**：后果表：后果 / 预期或非预期 / 正负 / 处理方式（行动/缓解/监测）/ 负责人。
- **耗时 / 人数**：45–90 分钟；全功能团队。
- **AI 协作**：agent 可提出容易被忽视的后果与滥用场景；取舍决定由团队负责。
- **⚠ 注意**：行为塑造类方法不得用于设计违背用户利益的操纵性或成瘾性模式；本方法正是用来发现并阻止这类设计的。
- **衔接**：上游 M6-10 → 下游 X2-04、M7-05

### X2-04 Tarot Cards of Tech · 科技塔罗牌
- **来源**：Artefact（名称及原版素材归权利人所有，此处仅作出处说明；本卡为自写说明，未复制原版素材）
- **目的**：用一组提问卡引发团队反思技术可能带来的长期和规模化影响。
- **何时用**：概念阶段想拓宽伦理视角，或团队讨论陷入只看好处；**不适用**：需要结构化结论时单独使用（配合 X2-03）。
- **输入**：概念描述、一组影响类提问卡（可自拟：规模化后会怎样、谁被排除、被滥用会怎样、十年后会怎样）。
- **步骤**：
  1. 每人或每组抽 1–2 张卡。
  2. 围绕卡上的问题讨论 10–15 分钟，写下具体情景。
  3. 汇总各组情景，挑出最令人担忧的。
  4. 把担忧转成设计调整或监测项。
- **产出**：反思问题与情景清单 + 转化后的设计调整。
- **耗时 / 人数**：1 小时；4–10 人。
- **AI 协作**：agent 可自拟提问卡、主持讨论、扩写情景；不复制原版卡片文字。
- **衔接**：上游 M5-16 → 下游 X2-03

## X3 行为设计

### X3-01 Fogg Behavior Model · 福格行为模型
- **来源**：BJ Fogg
- **目的**：用"行为 = 动机 × 能力 × 提示同时到位"诊断用户为什么没做某个行为。
- **何时用**：用户"想做却没做"或流程中途放弃；**不适用**：行为本身不符合用户利益。
- **输入**：目标行为（具体到一个动作）、行为数据或访谈记录。
- **步骤**：
  1. 把目标行为写成一个具体动作。
  2. 检查提示：用户在正确时机收到提示了吗？
  3. 检查能力：时间、精力、认知、步骤是否太多？优先降低难度。
  4. 检查动机：用户是否真的在乎结果？
  5. 针对缺失项提出调整，并用真实行为验证。
- **产出**：诊断表：行为 / 动机 / 能力 / 提示 各自状态 / 调整方案。
- **耗时 / 人数**：1–2 小时；2–4 人。
- **AI 协作**：agent 可引导诊断、提出降低难度的方案；诊断依据需来自真实行为数据或访谈。
- **衔接**：上游 M7-18、M3-07 → 下游 M6-22、X2-03

### X3-02 Hook Model · 上瘾模型
- **来源**：Nir Eyal（名称及原版素材归权利人所有，此处仅作出处说明；本卡为自写说明，未复制原版素材）
- **目的**：拆解一个产品的 触发 → 行动 → 多变奖励 → 投入 循环，理解习惯是如何形成的。
- **何时用**：分析现有产品或竞品的使用习惯机制，检查自家产品是否存在不健康的依赖；**不适用**：作为提升使用时长的操纵手段。
- **输入**：产品使用流程、使用数据或访谈、竞品样本。
- **步骤**：
  1. 找触发：外部提示（通知、消息）和内部触发（情绪、需要）。
  2. 找行动：用户为获得回报做的最简动作。
  3. 找奖励：回报是什么，是否可预期。
  4. 找投入：用户留下了什么（数据、内容、设置）使下次更有价值。
  5. 逐环判断：这个循环服务于用户的目标，还是在消耗用户？
- **产出**：循环拆解图 + 每环的健康度判断与改进建议。
- **耗时 / 人数**：1–2 小时；2–4 人。
- **AI 协作**：agent 可拆解循环、指出操纵风险；使用数据须来自真实来源。
- **⚠ 注意**：只用于诊断和批判，不得用来设计违背用户利益的操纵性或成瘾性模式；使用时必须配合 X2-03 做后果扫描。
- **衔接**：上游 X3-01 → 下游 X2-03

### X3-03 COM-B · 行为改变模型
- **来源**：Michie 等
- **目的**：从能力（Capability）、机会（Opportunity）、动机（Motivation）三方面诊断行为障碍，选择干预方式。
- **何时用**：推动组织内采用新工具或新流程（如团队采用 agent 协作）；**不适用**：只需改一个界面细节。
- **输入**：目标行为、目标人群、访谈或观察资料。
- **步骤**：
  1. 精确定义目标行为：谁、在什么时候、做什么。
  2. 能力：身体与心理上会不会做（技能、知识）。
  3. 机会：物理环境与社会环境是否允许（工具、时间、团队规范）。
  4. 动机：反思性（认为值得）与自动性（习惯、情绪）是否到位。
  5. 针对主要障碍选干预：培训、环境改造、示范、激励等，并定验证方式。
- **产出**：诊断表：C / O / M 各子项现状与证据 / 干预方案 / 验证方式。
- **耗时 / 人数**：半天；2–5 人。
- **AI 协作**：agent 可组织诊断框架、提出干预选项；障碍判断需基于真实访谈或观察。
- **衔接**：上游 M3-07、M4-01 → 下游 M7-05、X2-03
