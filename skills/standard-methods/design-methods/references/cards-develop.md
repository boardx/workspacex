# 发展阶段方法卡片（M5–M6）

> 编号与 references/method-index.md 一致。每张卡片是本项目自写的操作说明，不是任何书籍原文。

## M5 Ideation 概念发散

### M5-01 Opportunity Mind Map · 机会思维导图
- **来源**：通用设计实践
- **目的**：把洞察和设计原则发散成一张机会导图，看清可以往哪些方向出概念。
- **何时用**：已有洞察/原则，要从问题转向机会；**不适用**：还没有任何研究输入，或方向已定只差细化。
- **输入**：洞察陈述、设计原则或 HMW 问题；1–3 名熟悉研究的人。
- **步骤**：
  1. 中心写项目意图或核心 HMW 问题。
  2. 第一层挂设计原则或关键洞察，每条一个主枝。
  3. 每个主枝下发散具体机会领域（服务什么人、在什么场景、解决什么阻碍）。
  4. 标出主枝之间的交叉点，交叉处往往是复合机会。
  5. 圈出 3–7 个最值得出概念的机会区。
- **产出**：机会导图 + 重点机会区清单（名称、依据的洞察、目标用户、场景）。
- **耗时 / 人数**：1–3 小时 · 1–3 人
- **AI 协作**：agent 可按洞察生成导图结构、补全分支、提示遗漏的交叉点；重点机会区的圈选由用户决定。
- **衔接**：上游 M4-18、M4-24 → 下游 M5-04、M5-05

### M5-02 Value Hypothesis · 价值假设
- **来源**：通用设计实践
- **目的**：把机会写成「谁、在什么情境、会因什么获得什么价值」的可检验假设。
- **何时用**：出概念前要明确价值主张、或要决定先验证什么；**不适用**：纯探索性发散阶段，过早收敛会限制点子。
- **输入**：机会区、目标用户群、已有洞察证据。
- **步骤**：
  1. 为每个机会写一句假设：对【用户】，在【情境】，【方案方向】能带来【价值】，因为【洞察】。
  2. 标出假设中最没把握的部分（用户是否存在、痛点是否够痛、价值是否被认可）。
  3. 为每条假设定一个验证信号与判定阈值（看到什么算成立）。
  4. 按风险 × 影响排序，决定先验证哪几条。
- **产出**：价值假设清单（假设句、依据、关键不确定点、验证信号、阈值、优先级）。
- **耗时 / 人数**：1–2 小时 · 1–3 人
- **AI 协作**：agent 可起草假设句、拆出隐含前提、建议验证信号；阈值和优先级需用户确认，假设未经真实验证前一律标为「待验证」。
- **衔接**：上游 M5-01、M4-23 → 下游 M5-25、M7-14、M6-16

### M5-03 Persona Definition · 用户画像
- **来源**：通用设计实践
- **目的**：把用户分群凝练成少量有名字、有目标、有行为的原型人物，供出概念时代入。
- **何时用**：团队对「为谁设计」理解不一致；**不适用**：没有研究数据支撑时——凭空编的画像只会固化偏见。
- **输入**：用户分群结果、访谈/观察证据。
- **步骤**：
  1. 从分群中选出 3–5 个在行为/目标上差异最大的群体。
  2. 每个写：目标、典型行为、痛点、情境约束、关键引文（引自真实研究，注明出处）。
  3. 标出主画像（首要服务对象）与次画像。
  4. 与团队核对：每条特征能否追溯到数据，不能的删或标假设。
- **产出**：Persona 卡（名称、目标、行为、痛点、情境、引文与来源、主/次标记）。
- **耗时 / 人数**：2–4 小时 · 1–3 人
- **AI 协作**：agent 可按用户提供的研究材料起草画像、标注每条的证据来源；不得补写研究中没有的人口特征或引文，缺证据处标「待验证」由用户确认。
- **衔接**：上游 M4-14、M4-21 → 下游 M5-07、M5-13、X2-01

### M5-04 Ideation Session · 创意会
- **来源**：通用设计实践
- **目的**：围绕明确的问题，在有规则的会上快速产出大量点子。
- **何时用**：机会区已明确、需要数量；**不适用**：问题本身没定义清楚，会只会跑题。
- **输入**：2–4 个 HMW 或机会区、画像、设计原则；4–8 名跨背景参与者、一名主持人。
- **步骤**：
  1. 开场重申问题与规则（先求量、不评判、借题发挥、一张卡一个点子）。
  2. 每个问题限时发散 10–15 分钟，个人先写再分享。
  3. 主持人在点子枯竭时用提示（换用户、换约束、极端化）刺激。
  4. 当场粗略归类，标出令人兴奋的点子。
- **产出**：点子池（点子、针对的问题、提出人、初步分类）。
- **耗时 / 人数**：1–2 小时 · 4–8 人
- **AI 协作**：agent 可在会前生成暖场提示与刺激问题、会中补充点子、会后去重归类；点子的取舍与兴奋度由参与者决定。
- **衔接**：上游 M4-24、M5-01 → 下游 M5-14、M5-28

### M5-05 Concept-Generating Matrix · 概念生成矩阵
- **来源**：通用设计实践
- **目的**：用两个维度交叉（如用户需求 × 技术/手段），系统地在每个格子里填出概念。
- **何时用**：想覆盖整个设计空间、避免只盯显而易见的点子；**不适用**：维度选不出来或只有一两个选项。
- **输入**：两组清单（如用户活动、需求、画像 与 技术、渠道、商业手段）。
- **步骤**：
  1. 选两个对问题最关键的维度，各列 4–8 项。
  2. 画矩阵，逐格问「这两者结合会是什么概念」。
  3. 每格至少写一个概念，空格也要尝试，写不出标原因。
  4. 标出最有潜力的格子和意外组合。
- **产出**：矩阵表（行项、列项、格内概念），以及优选概念清单。
- **耗时 / 人数**：1–3 小时 · 1–4 人
- **AI 协作**：agent 可快速填满全部格子作为草案，并解释组合逻辑；哪些格子有价值由用户判断。
- **衔接**：上游 M5-01、M4-14 → 下游 M5-16、M6-01

### M5-06 Concept Metaphors and Analogies · 概念隐喻与类比
- **来源**：通用设计实践
- **目的**：借用其他领域的成熟模式（隐喻/类比）激发新概念。
- **何时用**：点子陷入行业惯性；**不适用**：需要严格满足法规或技术约束的细化阶段。
- **输入**：目标问题的本质描述（抽象成动作/关系）、类比模型清单。
- **步骤**：
  1. 把问题抽象成一句通用描述（如「让陌生人快速建立信任」）。
  2. 列出面对同样本质问题的其他领域及其做法。
  3. 逐个提炼可迁移的机制，而不是表面形式。
  4. 把机制翻译回本领域，写成概念。
- **产出**：类比来源 → 机制 → 本领域概念 的对照表。
- **耗时 / 人数**：1–2 小时 · 1–4 人
- **AI 协作**：agent 擅长跨领域联想，可大量提供类比与机制拆解；类比是否贴切、概念是否可行由用户判断。
- **衔接**：上游 M2-06、M4-24 → 下游 M5-12、M5-16

### M5-07 Role-Play Ideation · 角色扮演构思
- **来源**：通用设计实践
- **目的**：让团队扮演用户及相关角色走一遍情境，从亲身代入中冒出点子。
- **何时用**：体验涉及人际互动或服务接触点；**不适用**：纯后台或算法类问题。
- **输入**：画像、情境描述、简单道具；3–6 人。
- **步骤**：
  1. 分配角色（用户、服务人员、旁观者等），交代情境与目标。
  2. 先按现状演一遍，旁观者记录卡点与情绪。
  3. 针对卡点即兴尝试新做法，再演。
  4. 复盘：把演出中有效的做法写成概念。
- **产出**：卡点记录 + 扮演中涌现的概念清单。
- **耗时 / 人数**：1–2 小时 · 3–6 人
- **AI 协作**：agent 可写情境脚本、角色卡和复盘提问，也可在对话中扮演某一方陪用户推演；推演只是构思手段，不能当作用户真实反应。
- **衔接**：上游 M5-03、M4-16 → 下游 M5-13、M5-23

### M5-08 Ideation Game · 构思游戏
- **来源**：通用设计实践
- **目的**：用游戏规则（抽卡、回合、组合、计分）降低门槛，让非设计人员也能产出点子。
- **何时用**：参与者多元、气氛拘谨或需要引入利益相关方；**不适用**：时间极短或需要深度专业推演。
- **输入**：卡牌素材（用户、场景、技术、约束等）、规则说明；4–12 人。
- **步骤**：
  1. 设计卡组与规则（如每轮抽一张用户卡 + 一张场景卡 + 一张手段卡）。
  2. 分组按回合出概念，限时。
  3. 组间互评或加分，鼓励组合他人点子。
  4. 汇总所有回合的点子并去重。
- **产出**：游戏化产出的点子清单（卡组组合、点子、组别）。
- **耗时 / 人数**：1–2 小时 · 4–12 人
- **AI 协作**：agent 可设计卡组和规则、充当发牌员并记录；得分和选择由真人参与者给出。
- **衔接**：上游 M5-01、M5-03 → 下游 M5-14、M5-28

### M5-09 Tabletop Scenario · 桌面情景演绎
- **来源**：通用设计实践
- **目的**：用小人偶/纸偶在桌面上演绎情景，低成本地试不同概念如何展开。
- **何时用**：想快速比较多个情景、或参与者不适合真人扮演；**不适用**：需要真实操作手感的细节验证。
- **输入**：简易人偶与场景道具、概念清单、情景大纲。
- **步骤**：
  1. 用道具搭出场景（地点、角色、关键物件）。
  2. 按大纲演绎概念的使用过程，拍照或录像。
  3. 观众随时叫停提问、替换一步再演。
  4. 记录每个情景中暴露的问题与新点子。
- **产出**：情景演绎记录（分镜照片、问题点、改进点子）。
- **耗时 / 人数**：1–2 小时 · 2–6 人
- **AI 协作**：agent 可写情景大纲和分镜清单、整理演绎记录；演绎本身由用户完成。
- **衔接**：上游 M5-13 → 下游 M6-07、M5-11

### M5-10 Behavioral Prototype · 行为原型
- **来源**：通用设计实践
- **目的**：在真实环境中放一个粗糙的替身，观察人们实际会怎么做，而不是问他们会怎么做。
- **何时用**：概念依赖一个关键行为假设（会不会用、会不会停下）；**不适用**：无法在真实场景中安全、合规地放置原型。
- **输入**：关键行为假设、简易原型、观察地点与知情安排。
- **步骤**：
  1. 写下要检验的行为和成立标准。
  2. 做一个只够引发该行为的最简替身。
  3. 在真实场景放置，按计划观察并记录（遵守知情同意与隐私要求）。
  4. 对比标准，总结行为模式与意外。
- **产出**：行为观察记录（场景、次数、行为、与假设的对比、结论）。
- **耗时 / 人数**：半天–数天 · 1–3 人
- **AI 协作**：agent 可帮忙写假设、观察表和成立标准、整理记录；观察数据必须来自真实现场，agent 不得模拟。
- **衔接**：上游 M5-02 → 下游 M5-11、M6-02

### M5-11 Concept Prototype · 概念原型
- **来源**：通用设计实践
- **目的**：把概念做成可以被看、被摸、被讨论的低保真形态，用于沟通和早期反馈。
- **何时用**：概念停留在文字、团队理解不一；**不适用**：已进入细节交互验证（改用方案原型）。
- **输入**：选中的概念、纸板/线框/图片等快速材料。
- **步骤**：
  1. 确定这个原型要回答的一个问题。
  2. 只做回答该问题所需的部分，其余省略。
  3. 拿给团队和少量用户看，记录反应与疑问。
  4. 决定：保留、修改还是放弃该概念。
- **产出**：低保真原型 + 反馈记录（问题、反应、决定）。
- **耗时 / 人数**：2 小时–2 天 · 1–3 人
- **AI 协作**：agent 可生成线框描述、界面文案、流程草图文本；用户反馈需来自真实展示，agent 只能汇总不能代答。
- **衔接**：上游 M5-12、M5-16 → 下游 M6-02、M6-09

### M5-12 Concept Sketch · 概念草图
- **来源**：通用设计实践
- **目的**：用快速草图把一个概念的核心画出来，方便比较和讨论。
- **何时用**：点子多、需要统一呈现；**不适用**：需要精确尺寸或交互细节。
- **输入**：点子清单、统一的草图模板（标题、图、一句话说明）。
- **步骤**：
  1. 每个概念一张纸：起名字、画核心画面、写一句话价值。
  2. 补充关键使用步骤或组成部分（3–5 个标注）。
  3. 贴墙展示，大家补充问题便签。
- **产出**：概念草图集（名称、画面、一句话价值、标注、疑问）。
- **耗时 / 人数**：每张 5–15 分钟 · 1–6 人
- **AI 协作**：agent 可为每个概念写标题、一句话价值和画面描述，或生成示意图提示词；草图是否表达准确由用户确认。
- **衔接**：上游 M5-04、M5-18 → 下游 M5-14、M5-16

### M5-13 Concept Scenarios · 概念情景
- **来源**：通用设计实践
- **目的**：用叙事描述画像在具体情境中如何使用概念，检验概念是否讲得通。
- **何时用**：概念需要放进真实生活检验逻辑；**不适用**：尚未确定目标用户。
- **输入**：画像、概念、使用情境。
- **步骤**：
  1. 选画像和触发情境（何时、何地、为什么想起来用）。
  2. 按「之前 → 使用中 → 之后」写叙事。
  3. 标出情景中概念必须成立的前提。
  4. 写一个出错/例外情景。
- **产出**：情景故事（画像、触发、过程、结果、前提、例外）。
- **耗时 / 人数**：每个 20–40 分钟 · 1–2 人
- **AI 协作**：agent 可快速写多版情景与例外情景；情景是推演不是证据，是否符合真实用户需向用户或研究核对。
- **衔接**：上游 M5-03、M5-12 → 下游 M6-07、M5-09

### M5-14 Concept Sorting · 概念分类
- **来源**：通用设计实践
- **目的**：把大量概念按相似性归组，看清概念空间的结构和重复。
- **何时用**：点子池超过几十个；**不适用**：概念很少、直接评估即可。
- **输入**：概念卡（草图或一句话）。
- **步骤**：
  1. 逐张阅读，合并明显重复。
  2. 自下而上按相似性分组，不预设类别。
  3. 为每组命名，写出组的共同主题。
  4. 标出空白区和孤立概念。
- **产出**：概念分组（组名、主题、成员概念、孤立概念、空白区）。
- **耗时 / 人数**：1–2 小时 · 1–4 人
- **AI 协作**：agent 可给出初始分组和命名草案；分组逻辑需用户过目调整。
- **衔接**：上游 M5-04、M5-12 → 下游 M5-15、M5-16

### M5-15 Concept Grouping Matrix · 概念分组矩阵
- **来源**：通用设计实践
- **目的**：把概念放到按两个维度划分的矩阵里，看各维度组合下的概念分布与空缺。
- **何时用**：想比较概念覆盖了哪些需求/场景；**不适用**：维度无法清楚定义。
- **输入**：概念清单、两个评估维度（如用户需求 × 场景，短期 × 长期）。
- **步骤**：
  1. 定义行列维度及各自取值。
  2. 把每个概念放进对应格子（可跨格）。
  3. 看密集格与空格，讨论原因。
  4. 针对重要空格补充概念或标记放弃。
- **产出**：概念 × 维度矩阵，附分布说明与补充动作。
- **耗时 / 人数**：1–2 小时 · 1–4 人
- **AI 协作**：agent 可完成初次归位并指出空缺；维度选择与空缺是否重要由用户决定。
- **衔接**：上游 M5-14 → 下游 M5-16、M6-04

### M5-16 Concept Catalog · 概念目录
- **来源**：通用设计实践
- **目的**：把所有概念整理成统一格式的可检索目录，便于后续评估和复用。
- **何时用**：发散结束、准备收敛；**不适用**：只有一两个概念。
- **输入**：概念草图、分组结果、相关洞察。
- **步骤**：
  1. 定统一字段：编号、名称、一句话描述、目标用户、解决的洞察、分组、状态。
  2. 逐条录入，补全依据。
  3. 标记状态（待评估 / 入选 / 搁置）与搁置原因。
- **产出**：概念库表格（上述字段）。
- **耗时 / 人数**：1–3 小时 · 1–2 人
- **AI 协作**：agent 可把散落的点子整理成统一字段表并补关联洞察；状态变更由用户确认。
- **衔接**：上游 M5-14、M5-15 → 下游 M6-02、M6-04

### M5-17 SCAMPER · 奔驰法
- **来源**：Eberle
- **目的**：用七个改造动作系统地从现有产品/流程衍生变体点子。
- **何时用**：有现成方案要改进；**不适用**：从零开始、没有可改造的对象。
- **输入**：一个现有产品、服务或流程的清晰描述。
- **步骤**：
  1. 依次用 替代 / 合并 / 调适 / 修改（放大缩小）/ 他用 / 去除 / 反转重排 七个问题追问对象。
  2. 每个动作至少写 2–3 个变体。
  3. 挑出最有意思的变体，写成概念。
- **产出**：变体点子表（动作、变体描述、初步评价）。
- **耗时 / 人数**：30–60 分钟 · 1–5 人
- **AI 协作**：agent 可逐个动作快速生成大量变体；可行性和吸引力由用户筛选。
- **衔接**：上游 M2-16 → 下游 M5-16、M5-28

### M5-18 Crazy 8s · 8 分钟 8 方案
- **来源**：GV Sprint（名称及原版素材归权利人所有，此处仅作出处说明；本卡为自写说明，未复制原版素材）
- **目的**：强迫个人在 8 分钟内画 8 个草图变体，突破第一个想法。
- **何时用**：需要快速把一个方向画出多种形态；**不适用**：参与者还没理解问题。
- **输入**：纸（折成 8 格）、笔、计时器、已明确的问题或目标画面。
- **步骤**：
  1. 每人把纸折成 8 格。
  2. 计时 8 分钟，每格约 1 分钟画一个变体，不求美观。
  3. 轮流快速讲解，其他人记下喜欢的元素。
  4. 各自挑最好的一格作为后续细化起点。
- **产出**：每人一张 8 格草图，及被选中的变体。
- **耗时 / 人数**：15–30 分钟 · 2–8 人
- **AI 协作**：agent 可提供 8 个变体方向作为提示；画草图是用户的个人行为，agent 不代替。
- **衔接**：上游 M4-24 → 下游 M5-12、M5-28

### M5-19 Brainwriting 6-3-5 · 书面头脑风暴
- **来源**：Rohrbach
- **目的**：6 人、每人每轮 3 个点子、每轮 5 分钟、传递 6 轮，以书面方式在他人基础上迭代。
- **何时用**：团队中有人不善发言、或讨论常被强势者主导；**不适用**：人数远少于 4 人。
- **输入**：清晰的问题、每人一张 3 列 × 6 行表格、计时器。
- **步骤**：
  1. 每人在第一行写 3 个点子，限时 5 分钟。
  2. 表格传给下一人，他在下一行延伸或新写 3 个。
  3. 重复直到表格填满（理论上最多 108 个点子）。
  4. 收集所有表格，去重与分组。
- **产出**：点子表格（理论上限 108 条），去重后的点子清单。
- **耗时 / 人数**：约 30–45 分钟 · 6 人（可按人数调整）
- **AI 协作**：agent 可作为「虚拟一席」补写一行、会后去重归类；不能用 agent 冒充缺席的真人参与者。
- **衔接**：上游 M4-24 → 下游 M5-14、M5-28

### M5-20 Parallel Perspectives · 六视角平行思考
- **来源**：de Bono
- **目的**：让团队在同一时间用同一种视角思考（事实、情感、风险、收益、创意、流程），避免争吵。
- **何时用**：讨论一个概念时意见冲突或只看一面；**不适用**：只需要快速发散数量。
- **输入**：待讨论的概念或决策、主持人。
- **步骤**：
  1. 主持人（蓝帽）说明议题和帽子顺序。
  2. 全员依次戴白（事实）、红（直觉感受）、黑（风险）、黄（收益）、绿（新点子）帽，每顶限时。
  3. 记录每顶帽下的发言。
  4. 最后蓝帽总结结论与下一步。
- **产出**：按帽子分栏的多视角评估记录与结论。
- **耗时 / 人数**：30–60 分钟 · 3–8 人
- **AI 协作**：agent 可按六个视角各写一版分析作为讨论起点；情感与最终结论须来自真人团队。
- **衔接**：上游 M5-16 → 下游 M6-02、M6-10

### M5-21 Worst Possible Idea · 最烂点子反推
- **来源**：创意实践
- **目的**：先故意想最糟糕的点子，再反转成好点子，打破心理防御。
- **何时用**：团队拘谨、点子保守；**不适用**：严肃的风险评审场合。
- **输入**：问题陈述、便签。
- **步骤**：
  1. 限时 5–10 分钟，大家比赛写最烂的方案。
  2. 挑几条，分析「它为什么烂」。
  3. 把烂的原因反转，得到新点子。
- **产出**：烂点子 → 原因 → 反转点子 对照表。
- **耗时 / 人数**：20–40 分钟 · 3–10 人
- **AI 协作**：agent 可生成烂点子和反转方向，活跃气氛；反转后点子的价值由用户判断。
- **衔接**：上游 M4-24 → 下游 M5-04、M5-28

### M5-22 TRIZ · 发明问题解决理论
- **来源**：Altshuller
- **目的**：把问题表述为矛盾（改善一项就恶化另一项），借用通用发明原理找突破口。
- **何时用**：遇到「既要又要」的技术或系统矛盾；**不适用**：问题是用户需求不明而非矛盾。
- **输入**：清晰的系统描述、要改善的参数与因此恶化的参数。
- **步骤**：
  1. 写出矛盾：想提升 A，但会导致 B 变差。
  2. 描述理想结果（不付代价就获得 A）。
  3. 查阅发明原理（如分割、预先作用、反向、动态化等），挑适用的几条。
  4. 把原理落到本问题，写出候选方案。
- **产出**：矛盾陈述、选用的原理、候选方案。
- **耗时 / 人数**：1–3 小时 · 1–3 人
- **AI 协作**：agent 可帮助精确表述矛盾、提示可能适用的原理并举例；原理映射只是启发，技术可行性由用户或专家确认。
- **衔接**：上游 M4-25、M4-27 → 下游 M5-16、M6-01

### M5-23 Bodystorming · 身体演练
- **来源**：交互设计
- **目的**：在真实或近似的物理空间里用身体走一遍体验，发现纸面想不到的问题。
- **何时用**：体验与空间、动作、多人协作相关；**不适用**：纯数字界面细节。
- **输入**：场地、简易道具、概念与情景。
- **步骤**：
  1. 布置空间，分配角色。
  2. 按情景完整走一遍，边走边说出感受。
  3. 记录身体层面的摩擦（距离、姿势、等待、注意力）。
  4. 即兴调整并再走，记录改进。
- **产出**：演练发现清单（位置、问题、调整）。
- **耗时 / 人数**：1–2 小时 · 3–6 人
- **AI 协作**：agent 可写情景和观察清单、整理发现；演练必须由用户在现场进行。
- **衔接**：上游 M5-07、M5-13 → 下游 M6-08、M6-13

### M5-24 Paper Prototype · 纸面原型
- **来源**：UX 实践
- **目的**：用纸画界面，由人工「切换页面」，在编码前测试流程和信息架构。
- **何时用**：界面流程初具形态，要快速找可用性问题；**不适用**：要测视觉细节、动效或性能。
- **输入**：关键任务、纸笔、便签；一名操作「电脑」的人、一名主持人。
- **步骤**：
  1. 确定 2–4 个关键任务。
  2. 画出完成任务需要的所有页面和状态。
  3. 让测试者用手指「点击」，操作者换纸响应。
  4. 记录卡住、误解的位置，当场修改纸面。
- **产出**：可测纸面界面 + 问题清单（任务、位置、问题、修改）。
- **耗时 / 人数**：半天–1 天 · 2–3 人 + 3–5 名测试者
- **AI 协作**：agent 可列出页面与状态清单、写界面文案和测试任务；测试结果只能来自真人测试者。
- **衔接**：上游 M5-11、M5-12 → 下游 M6-22、M6-09

### M5-25 Wizard of Oz · 绿野仙踪原型
- **来源**：Lean UX
- **目的**：前台看起来是自动化服务，后台由人手工完成，在不开发的情况下验证需求与体验。
- **何时用**：实现成本高、需先确认用户是否需要；**不适用**：无法向参与者做事后说明，或涉及敏感操作。
- **输入**：前台界面或入口、后台人工流程、事后告知方案。
- **步骤**：
  1. 定义要验证的假设与成功指标。
  2. 搭最小前台，设计后台人工处理流程与响应时限。
  3. 招募真实用户使用，人工在后台响应并记录。
  4. 结束后告知参与者真相，汇总数据与反馈。
- **产出**：人工模拟的服务体验记录（请求量、完成情况、用户反馈、成本估算）。
- **耗时 / 人数**：数天–数周 · 2–4 人
- **AI 协作**：agent 可设计流程、话术和记录表；验证结论只能来自真实用户参与的数据。AI/agent 功能优先看 X1-03。
- **衔接**：上游 M5-02 → 下游 M7-14、X1-03

### M5-26 Co-design Workshop · 共创工作坊
- **来源**：参与式设计
- **目的**：邀请用户和相关方作为共同设计者参与出概念，而不只是被研究对象。
- **何时用**：用户专业知识关键、或需要相关方认同；**不适用**：无法兑现参与者对结果的期待。
- **输入**：参与者（用户、一线人员等）、生成式工具包（卡片、模板、拼贴材料）、主持人。
- **步骤**：
  1. 用暖场活动建立信任，说明参与方式与数据使用。
  2. 让参与者用工具包表达现状与理想（拼贴、画、排序）。
  3. 分组共创概念，并让他们讲解。
  4. 共同挑选和改进，记录他们的理由。
- **产出**：与用户共创的概念 + 参与者的理由和语言。
- **耗时 / 人数**：2–4 小时 · 6–15 人
- **AI 协作**：agent 可设计议程、工具包和记录模板，会后整理产出；不得把 agent 生成的概念标成用户共创的成果。
- **衔接**：上游 M3-12、M5-03 → 下游 M5-16、M6-02

### M5-27 Speculative Design · 思辨设计
- **来源**：Dunne & Raby
- **目的**：设计来自可能未来的物件或叙事，引发对价值与后果的讨论，而非直接解决问题。
- **何时用**：探索长期方向、伦理议题、激发战略对话；**不适用**：需要短期可落地方案。
- **输入**：趋势与弱信号、未来情景、讨论对象（团队或公众）。
- **步骤**：
  1. 选一个趋势，推到可信但令人不安或惊讶的未来。
  2. 设计该未来中的一个日常物件或服务片段。
  3. 用叙事/图像呈现，刻意留下可争议的空间。
  4. 拿给受众讨论，记录他们的价值判断。
- **产出**：思辨物件 / 叙事 + 讨论中暴露的价值取向。
- **耗时 / 人数**：1–5 天 · 1–4 人
- **AI 协作**：agent 可推演未来情景、写叙事和物件描述；受众反应必须真实收集。
- **衔接**：上游 M1-16、M1-18 → 下游 X2-03、M6-05

### M5-28 Dot Voting · 贴点投票
- **来源**：引导实践
- **目的**：用有限票数快速看出团队对一批选项的偏好分布。
- **何时用**：点子太多、需要快速缩小范围；**不适用**：需要严谨评估或利害关系重大——投票只反映偏好。
- **输入**：可见的选项墙、每人固定票数（通常 3–5 票）、投票标准。
- **步骤**：
  1. 说明投什么标准（最有潜力？最想先验证？）。
  2. 每人先安静看一遍，再同时投票，避免从众。
  3. 统计票数，讨论高票和意外的低票。
  4. 决定进入下一步的选项，保留落选理由。
- **产出**：优先概念清单（得票、讨论要点、决定）。
- **耗时 / 人数**：15–30 分钟 · 3–15 人
- **AI 协作**：agent 可整理选项、统计票数；票必须由真人投，agent 不代投、不把自己的偏好算作票。
- **衔接**：上游 M5-04、M5-16 → 下游 M6-02、M6-18

## M6 Solutions 方案收敛与验证

### M6-01 Morphological Analysis · 形态分析法
- **来源**：Zwicky 形态分析
- **目的**：把方案拆成若干功能维度，每维列出可选方式，再组合成完整方案。
- **何时用**：方案由多个可独立选择的部分构成；**不适用**：部分之间强耦合、无法拆分。
- **输入**：方案需要的功能维度、每个维度的备选概念。
- **步骤**：
  1. 列出方案的关键维度（如触达方式、交互形式、商业模式）。
  2. 每个维度列 3–5 种备选。
  3. 从每行各选一个，组成 2–4 套一致的组合方案。
  4. 检查组合内部是否矛盾，命名每套方案。
- **产出**：形态表 + 组合方案（每套选了什么、为什么搭配）。
- **耗时 / 人数**：1–3 小时 · 1–4 人
- **AI 协作**：agent 可列维度和备选、生成组合并检查冲突；选哪几套组合由用户决定。
- **衔接**：上游 M5-16、M5-05 → 下游 M6-02、M6-06

### M6-02 Concept Evaluation · 概念评估
- **来源**：通用设计实践
- **目的**：用明确的标准对概念打分比较，选出值得深化的少数。
- **何时用**：有一批候选概念要收敛；**不适用**：标准尚未达成共识。
- **输入**：概念目录、评估标准（用户价值、可行性、业务价值等）及权重、评审人。
- **步骤**：
  1. 与决策者确认 3–6 条标准和权重。
  2. 每个概念按标准打分（如 1–5），写简短理由。
  3. 计算加权分，画出如价值 × 可行性散点图。
  4. 讨论分数与直觉不一致之处，决定入选。
- **产出**：概念评分表（标准、权重、分数、理由、总分、决定）。
- **耗时 / 人数**：1–3 小时 · 2–6 人
- **AI 协作**：agent 可起草评分与理由作为讨论草案，必须标明「agent 草拟分」；正式分数与入选决定由用户及评审人给出。
- **衔接**：上游 M5-16、M5-28 → 下游 M6-04、M6-09

### M6-03 Future-State Value Network · 目标价值网络
- **来源**：通用设计实践
- **目的**：画出方案落地后各方之间理想的价值流（钱、信息、服务、信任），检验各方是否都有动力参与。
- **何时用**：方案涉及多方协作或平台；**不适用**：单一用户、单一产品的小改动。
- **输入**：现状价值网、相关方清单、选定方案。
- **步骤**：
  1. 列出方案中的所有参与方。
  2. 画出方案实施后各方之间的价值流动，标类型与方向。
  3. 对比现状价值网，标出新增、消失、改变的流。
  4. 检查每方「付出 vs 得到」，找出缺乏动力的一方。
- **产出**：目标价值流网 + 各方得失表与风险点。
- **耗时 / 人数**：2–4 小时 · 2–4 人
- **AI 协作**：agent 可根据描述画出价值网结构、指出失衡点；各方真实利益需用户或相关方确认。
- **衔接**：上游 M4-05、M2-14 → 下游 M6-15、M6-04

### M6-04 Concept-Linking Map · 概念关联图
- **来源**：通用设计实践
- **目的**：找出概念之间的依赖、增强、互斥关系，把分散概念组织成系统方案。
- **何时用**：多个概念入选、需要判断如何组合；**不适用**：只有一个独立概念。
- **输入**：入选概念、它们的简述。
- **步骤**：
  1. 把概念作为节点摆开。
  2. 逐对判断关系：依赖、互相增强、互斥、无关，画线并标注。
  3. 找出核心节点（连接最多）和天然成组的簇。
  4. 把簇定义为方案系统，写出组成与关系。
- **产出**：概念关联系统图 + 方案系统定义。
- **耗时 / 人数**：1–3 小时 · 1–4 人
- **AI 协作**：agent 可逐对推断关系并出图草案；关系判断需用户核对。
- **衔接**：上游 M6-02、M5-15 → 下游 M6-06、M6-11

### M6-05 Scenario Planning · 情景规划
- **来源**：通用设计实践
- **目的**：在几种可能的未来情景下检验方案表现，找出稳健性与脆弱点。
- **何时用**：方案周期长、外部不确定性高；**不适用**：短期迭代的小功能。
- **输入**：两个关键不确定因素（构成 2×2 情景）、候选方案。
- **步骤**：
  1. 选出影响最大、最不确定的两个因素，组成四个情景并命名。
  2. 为每个情景写简短描述。
  3. 把方案放进每个情景，评估表现与需要的调整。
  4. 总结在所有情景下都成立的部分和需要预案的部分。
- **产出**：情景 × 方案表现矩阵、稳健要素、预案。
- **耗时 / 人数**：半天 · 3–6 人
- **AI 协作**：agent 可起草情景叙事与方案推演；情景是假设性推演，不是预测，因素选择由用户确认。
- **衔接**：上游 M1-17、M1-18 → 下游 M6-11、M6-23

### M6-06 Solution Diagramming · 方案图解
- **来源**：通用设计实践
- **目的**：用结构图表达方案的组成部分、关系和运作方式。
- **何时用**：方案复杂、需要对团队或决策者讲清楚；**不适用**：方案简单到一句话能说明。
- **输入**：方案系统定义、概念关联图。
- **步骤**：
  1. 选择图的形式（系统图、流程图、层级图）。
  2. 画出组成部分与关系，标出用户触点。
  3. 用图走一遍关键使用路径，检查缺失环节。
  4. 精简到非专业人员也能读懂。
- **产出**：方案结构图 + 图例和关键路径说明。
- **耗时 / 人数**：1–3 小时 · 1–2 人
- **AI 协作**：agent 可直接生成 Mermaid 等结构图并检查缺失环节；图是否准确反映意图由用户确认。
- **衔接**：上游 M6-04、M6-01 → 下游 M6-07、M6-13

### M6-07 Solution Storyboard · 方案故事板
- **来源**：通用设计实践
- **目的**：用一格一格的画面讲述用户使用方案的完整过程。
- **何时用**：要向他人传达方案体验、或为原型确定范围；**不适用**：需要交互细节时。
- **输入**：画像、方案、关键情景。
- **步骤**：
  1. 定起点（触发）和终点（价值达成）。
  2. 分成 6–12 格，每格一个动作或时刻。
  3. 每格配画面和一句话，标出情绪变化。
  4. 标记哪几格是原型必须覆盖的。
- **产出**：故事板（格序、画面、说明、情绪、原型范围标记）。
- **耗时 / 人数**：1–3 小时 · 1–3 人
- **AI 协作**：agent 可写分镜脚本和每格文案、生成配图提示词；故事是否贴合用户由用户判断。
- **衔接**：上游 M5-13、M6-06 → 下游 M6-09、M6-08

### M6-08 Solution Enactment · 方案演绎
- **来源**：通用设计实践
- **目的**：由团队或用户实际演出方案的使用过程，发现流程和交接中的问题。
- **何时用**：方案包含服务流程或多人协作；**不适用**：纯界面层问题。
- **输入**：故事板或服务流程、道具、角色。
- **步骤**：
  1. 按故事板分配角色和道具。
  2. 完整演出一遍，观察员记录断点。
  3. 替换或加入异常情况再演（如出错、排队）。
  4. 汇总发现并修订方案。
- **产出**：演绎发现清单（环节、问题、修订）。
- **耗时 / 人数**：1–3 小时 · 3–8 人
- **AI 协作**：agent 可准备角色卡、异常情况清单、整理发现；演出由用户进行。
- **衔接**：上游 M6-07、M5-23 → 下游 M6-13、M6-09

### M6-09 Solution Prototype · 方案原型
- **来源**：通用设计实践
- **目的**：做出足够逼真的原型，让用户像使用真产品一样体验方案。
- **何时用**：方案已收敛，需要真实用户验证；**不适用**：还在多方案比较阶段——过早高保真浪费。
- **输入**：故事板、原型范围、设计资源或原型工具。
- **步骤**：
  1. 明确原型要验证的问题与关键路径。
  2. 只高保真实现关键路径，其余用占位。
  3. 内部走查修掉阻碍测试的问题。
  4. 准备测试脚本。
- **产出**：高保真原型 + 覆盖范围说明 + 测试脚本。
- **耗时 / 人数**：1–5 天 · 1–3 人
- **AI 协作**：agent 可生成原型代码/文案、内部走查；原型好不好用只能由真实用户测试说明。
- **衔接**：上游 M6-07、M6-02 → 下游 M6-22、M6-10

### M6-10 Solution Evaluation · 方案评估
- **来源**：通用设计实践
- **目的**：综合用户反馈、业务目标、可行性，对方案给出是否推进的评估。
- **何时用**：原型测试后、决定投入前；**不适用**：尚无任何验证数据。
- **输入**：测试结果、评估标准、成本与风险估算。
- **步骤**：
  1. 汇总用户测试证据，区分已验证与未验证的部分。
  2. 按用户价值、业务价值、可行性、风险逐项评估。
  3. 列出需要修改的点和剩余不确定性。
  4. 给出建议：推进 / 修改后推进 / 放弃，并附理由。
- **产出**：方案评估报告（证据、评分、问题、建议）。
- **耗时 / 人数**：半天–1 天 · 2–5 人
- **AI 协作**：agent 可整理证据、起草报告，标清证据来源；不得把推演或自评写成测试结果，最终建议由用户决定。
- **衔接**：上游 M6-22、M6-09 → 下游 M6-11、M7-04

### M6-11 Solution Roadmap · 方案路线图
- **来源**：通用设计实践
- **目的**：把方案拆成可分阶段交付的部分，排出先后与依赖。
- **何时用**：方案大、不能一次交付；**不适用**：一次就能完整交付的小方案。
- **输入**：方案结构、组件依赖、资源约束。
- **步骤**：
  1. 把方案拆成可独立交付价值的模块。
  2. 标出依赖与前提能力。
  3. 按价值和依赖排成 3 阶段左右（近期 / 中期 / 远期）。
  4. 每阶段写目标、交付物、成功指标。
- **产出**：分阶段方案路线图（阶段、模块、依赖、指标）。
- **耗时 / 人数**：2–4 小时 · 2–5 人
- **AI 协作**：agent 可拆模块、排依赖、起草路线；阶段划分与时间承诺由用户确认。
- **衔接**：上游 M6-04、M6-10 → 下游 M7-01、M7-10

### M6-12 Synthesis Workshop · 综合工作坊
- **来源**：通用设计实践
- **目的**：召集团队和决策者，基于前期成果收敛成共识方案。
- **何时用**：多个方案或多方意见需要对齐；**不适用**：决策者无法到场。
- **输入**：概念评估、方案图、原型、测试结果；决策者与核心团队。
- **步骤**：
  1. 展示前期证据墙，快速对齐背景。
  2. 讨论各方案的优劣与证据强弱。
  3. 组合或取舍，形成一个收敛方案。
  4. 记录决定、理由、未决问题与负责人。
- **产出**：收敛方案 + 决策记录（决定、理由、未决、负责人）。
- **耗时 / 人数**：半天 · 4–10 人
- **AI 协作**：agent 可准备证据摘要、议程与决策记录模板，会中整理；决定由人作出。
- **衔接**：上游 M6-02、M6-10 → 下游 M6-11、M7-03

### M6-13 Service Blueprint · 服务蓝图
- **来源**：Shostack
- **目的**：把用户旅程与前台、后台、支撑系统对齐画出，找出服务交付中的断点与依赖。
- **何时用**：服务涉及多角色、多系统协作；**不适用**：单一界面、无后台流程的问题。
- **输入**：用户旅程、对内部流程与系统的了解（最好有一线人员参与）。
- **步骤**：
  1. 顶行写用户行为，按阶段排列。
  2. 下方依次画前台接触（可见互动）、后台动作（不可见）、支撑流程与系统。
  3. 用可见线、内部互动线分隔各层，连出依赖。
  4. 标出失败点、等待点和证据（用户看到的实物/界面）。
- **产出**：分层服务蓝图（用户行为 / 前台 / 后台 / 支撑 / 失败点）。
- **耗时 / 人数**：半天–1 天 · 3–6 人
- **AI 协作**：agent 可按描述起草蓝图表格并追问缺失层；内部流程事实需一线人员确认。
- **衔接**：上游 M4-16、M6-06 → 下游 M7-05、M6-11

### M6-14 Value Proposition Canvas · 价值主张画布
- **来源**：Strategyzer（名称及原版素材归权利人所有，此处仅作出处说明；本卡为自写说明，未复制原版素材）
- **目的**：检查方案提供的价值是否对准用户要完成的任务、痛点和收益期待。
- **何时用**：要说清方案为什么对某类用户有价值；**不适用**：尚未有明确的目标用户群。
- **输入**：目标用户研究、方案描述。
- **步骤**：
  1. 用户侧：列出其任务、痛点、期望收益，并排序。
  2. 方案侧：列出产品/服务、痛点缓解方式、收益创造方式。
  3. 逐条连线，检查哪些重要痛点/收益被覆盖，哪些没有。
  4. 把未验证的匹配写成假设。
- **产出**：用户-价值匹配表 + 缺口与待验证假设。
- **耗时 / 人数**：1–2 小时 · 2–4 人
- **AI 协作**：agent 可按研究材料起草两侧内容并指出缺口；用户侧必须有研究依据，否则标「待验证」。
- **衔接**：上游 M4-22、M5-03 → 下游 M6-15、M5-02

### M6-15 Business Model Canvas · 商业模式画布
- **来源**：Strategyzer（名称及原版素材归权利人所有，此处仅作出处说明；本卡为自写说明，未复制原版素材）
- **目的**：在一页上检查方案的商业逻辑：为谁创造什么价值、怎么交付、怎么赚钱、成本在哪。
- **何时用**：方案需要商业可行性判断；**不适用**：内部工具或非营利场景中只关心体验的讨论（可简化使用）。
- **输入**：价值主张、目标客户、渠道与资源估计。
- **步骤**：
  1. 从客户细分和价值主张开始填写。
  2. 补充渠道、客户关系、收入来源。
  3. 补充关键资源、关键活动、关键伙伴、成本结构。
  4. 检查各格之间是否自洽，标出最大假设。
- **产出**：九格商业模式 + 关键假设清单。
- **耗时 / 人数**：1–3 小时 · 2–5 人
- **AI 协作**：agent 可起草各格与自洽性检查；数字和商业判断由用户确认，未经验证的收入/成本标为假设。
- **衔接**：上游 M6-14、M6-03 → 下游 M7-01、M7-14

### M6-16 Opportunity Solution Tree · 机会-方案树
- **来源**：Teresa Torres
- **目的**：从一个期望结果出发，展开机会（用户需求/痛点）、方案和验证实验，让决策可追溯。
- **何时用**：持续发现的产品团队要决定做什么、先验证什么；**不适用**：没有明确的结果指标。
- **输入**：目标结果（产品指标）、用户研究中的机会。
- **步骤**：
  1. 顶层写一个可衡量的目标结果。
  2. 下层挂由研究得出的机会，可再细分子机会。
  3. 选定一个目标机会，展开多个候选方案。
  4. 为方案背后的关键假设设计小实验。
- **产出**：结果-机会-方案-实验树。
- **耗时 / 人数**：1–3 小时起，持续更新 · 2–4 人
- **AI 协作**：agent 可整理树结构、提议方案与假设实验；机会需来自真实研究，目标结果和选择由用户定。
- **衔接**：上游 M4-22、M5-02 → 下游 M7-14、M7-15

### M6-17 Kano Model · 卡诺模型
- **来源**：狩野纪昭
- **目的**：区分需求是基本型、期望型、兴奋型还是无差异/反向型，指导取舍。
- **何时用**：功能候选多、要判断哪些是底线、哪些是加分；**不适用**：用户群太小，无法收集有代表性的回答。
- **输入**：功能清单、目标用户样本。
- **步骤**：
  1. 为每个功能设计成对问题：有这个功能时感觉如何 / 没有时感觉如何。
  2. 向真实用户收集回答。
  3. 按评价表归类每个功能。
  4. 基本型保底、期望型按投入做、兴奋型择优做。
- **产出**：功能需求分类表（功能、类型、样本量、说明）。
- **耗时 / 人数**：数天（含问卷） · 1–2 人 + 用户样本
- **AI 协作**：agent 可设计问卷、计算分类；分类必须基于真实回答，agent 可给「预判」但须标注为非数据。
- **衔接**：上游 M3-23、M5-16 → 下游 M6-19、M6-18

### M6-18 Impact / Effort Matrix · 影响-投入矩阵
- **来源**：通用
- **目的**：按预期影响和所需投入把候选项放进四象限，快速排序。
- **何时用**：候选项多、需要快速决定先做什么；**不适用**：影响或投入完全无法估计。
- **输入**：候选清单、对影响和投入的估算依据。
- **步骤**：
  1. 定义「影响」「投入」的含义与尺度。
  2. 逐项估计并放入四象限（速赢 / 大项目 / 填充 / 不做）。
  3. 讨论位置有争议的项，补充依据。
  4. 输出排序与决定。
- **产出**：四象限优先级图 + 排序清单。
- **耗时 / 人数**：30–90 分钟 · 2–6 人
- **AI 协作**：agent 可给出初始定位与理由草案；投入估算需实现方确认，最终排序由用户决定。
- **衔接**：上游 M5-28、M6-02 → 下游 M6-19、M6-11

### M6-19 MoSCoW · 优先级
- **来源**：DSDM
- **目的**：在固定时间或资源下，把需求分成必须 / 应该 / 可以 / 这次不做。
- **何时用**：范围需要与时间盒对齐；**不适用**：没有明确交付边界。
- **输入**：需求清单、时间与资源约束、决策者。
- **步骤**：
  1. 先定「必须」的判定标准（没有它这次交付就无意义）。
  2. 逐项归类，控制「必须」占比（常见做法是不超过总工作量的约六成）。
  3. 明确列出「这次不做」，避免隐性范围。
  4. 与相关方确认并记录。
- **产出**：必须 / 应该 / 可以 / 不做 四类清单。
- **耗时 / 人数**：30–90 分钟 · 2–6 人
- **AI 协作**：agent 可起草分类并提示「必须」过多；归类由决策者确认。
- **衔接**：上游 M6-17、M6-18 → 下游 M7-10、M6-11

### M6-20 Heuristic Evaluation · 启发式评估
- **来源**：Nielsen
- **目的**：由评估者对照可用性启发式原则检查界面，低成本找出可用性问题。
- **何时用**：有原型或产品界面、需要快速体检；**不适用**：代替真实用户测试——它找不到只有用户才会暴露的问题。
- **输入**：界面或原型、启发式清单（如 Nielsen 十条）、3–5 名评估者。
- **步骤**：
  1. 评估者各自独立走查界面，对照每条原则记录问题。
  2. 每个问题标位置、违反的原则、严重度。
  3. 合并去重，统一严重度。
  4. 按严重度排序给出修改建议。
- **产出**：可用性问题清单（位置、原则、严重度、建议）。
- **耗时 / 人数**：半天–1 天 · 3–5 名评估者
- **AI 协作**：agent 可作为一名评估者对截图/描述做走查草案，标明「agent 评估」；不能替代其余评估者，也不能写成用户测试结果。
- **衔接**：上游 M6-09、M5-24 → 下游 M6-22、X2-02

### M6-21 Cognitive Walkthrough · 认知走查
- **来源**：Wharton 等
- **目的**：站在新手用户视角，逐步检查每一步是否易于理解和操作。
- **何时用**：关注首次使用和易学性；**不适用**：面向熟练专家的高效操作评估。
- **输入**：目标用户描述、任务、每一步的正确操作序列、界面。
- **步骤**：
  1. 为任务写出正确操作步骤。
  2. 每一步问：用户会想做这件事吗？能看到可操作的控件吗？能把控件和目标联系起来吗？操作后能看懂反馈吗？
  3. 任一答案为否，记录为问题与原因。
  4. 汇总并提出修改。
- **产出**：逐步易学性问题表（步骤、失败问题、原因、建议）。
- **耗时 / 人数**：2–4 小时 · 1–3 人
- **AI 协作**：agent 可列步骤并逐步提问、起草问题表；这是专家推演，结论需用真实用户测试补证。
- **衔接**：上游 M6-09、M5-03 → 下游 M6-22

### M6-22 Usability Testing / Think-aloud · 可用性测试
- **来源**：UX 实践
- **目的**：观察真实用户边完成任务边说出想法，找出可用性问题及其严重度。
- **何时用**：有可操作的原型或产品；**不适用**：没有可以真实操作的东西，或无法招募目标用户。
- **输入**：原型、任务脚本、5 名左右目标用户、主持人与记录员、知情同意。
- **步骤**：
  1. 写任务（真实目标，不透露操作路径）与成功标准。
  2. 每场说明规则，请参与者出声思考，主持人少引导。
  3. 记录完成情况、耗时、卡点、原话。
  4. 汇总跨参与者的问题，按频次和影响定严重度。
  5. 输出修改建议与复测计划。
- **产出**：问题清单（问题、出现人数、严重度、证据引文、建议）。
- **耗时 / 人数**：2–5 天 · 1–2 人 + 约 5 名参与者/轮
- **AI 协作**：agent 可写测试脚本、记录表，整理用户提供的记录；测试必须由真实用户完成，agent 模拟的用户反应不能当测试结果。
- **衔接**：上游 M6-09、M5-24 → 下游 M6-10、M7-04

### M6-23 Backcasting · 逆推
- **来源**：未来学
- **目的**：先描绘期望的未来状态，再从终点倒推需要依次发生的关键步骤。
- **何时用**：目标长期且与现状差距大；**不适用**：目标模糊或只是短期优化。
- **输入**：期望未来状态的描述、时间跨度、现状。
- **步骤**：
  1. 具体描述目标年份的理想状态（可观察的特征）。
  2. 问「在此之前必须已经成立什么」，一步步往回写里程碑。
  3. 倒推到今天，找出第一步行动。
  4. 标出每个里程碑的前提与风险。
- **产出**：从目标倒推的路径（里程碑、时间点、前提、第一步）。
- **耗时 / 人数**：半天 · 2–6 人
- **AI 协作**：agent 可推演里程碑链并检查逻辑缺口；目标状态和时间判断由用户确定。
- **衔接**：上游 M1-17、M6-05 → 下游 M6-11、M7-01

### M6-24 Design Sprint · 5 天设计冲刺
- **来源**：GV（名称及原版素材归权利人所有，此处仅作出处说明；本卡为自写说明，未复制原版素材）
- **目的**：用约 5 天把一个关键问题从理解推进到可测原型，并拿到真实用户反馈。
- **何时用**：有重要且紧迫的问题、决策者能参与；**不适用**：问题太小（杀鸡用牛刀）或太大（需分拆）。
- **输入**：明确的挑战、决策者、4–7 人跨职能小组、专家访谈安排、5 名测试用户。
- **步骤**：
  1. 理解：定长期目标与冲刺问题，画流程图，访谈专家，选定目标环节。
  2. 发散：借鉴已有方案，每人独立画方案草图（可用 Crazy 8s）。
  3. 决策：静默评审、投票，由决策者拍板，画故事板。
  4. 原型：一天内做出看起来真实的原型。
  5. 测试：与约 5 名目标用户一对一测试，总结规律。
- **产出**：验证过的原型 + 用户测试发现 + 下一步决定。
- **耗时 / 人数**：约 5 天（有压缩版） · 4–7 人
- **AI 协作**：agent 可准备议程、整理专家访谈、生成草图提示与原型素材、汇总测试记录；投票、拍板与用户测试必须由真人完成。完整流程见 F-05。
- **衔接**：上游 M4-24 → 下游 M7-14、F-05
