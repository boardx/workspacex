# 定义阶段方法卡片（M4）

> 编号与 references/method-index.md 一致。每张卡片是本项目自写的操作说明，不是任何书籍原文。

## M4 Synthesis 洞察综合

### M4-01 Observations to Insights · 观察转洞察
- **来源**：通用设计实践
- **目的**：把零散的观察事实提炼成「为什么会这样」的洞察陈述。
- **何时用**：研究结束、手里有观察笔记 / 访谈要点时；**不适用**：还没有一手材料，只有主观猜测。
- **输入**：观察记录（M3-14 数据库、访谈要点、照片注释）；1–2 名参与过研究的人。
- **步骤**：
  1. 逐条列出观察，每条只写看到/听到的事实，附来源定位。
  2. 对每条追问「为什么这很重要 / 背后是什么原因」，写成一句解释。
  3. 合并指向同一解释的观察，把解释改写为「用户……，因为……，所以……」的洞察句。
  4. 标注每条洞察的支持观察数与反例；只有单条支撑的标为待验证。
- **产出**：洞察表：洞察 ID、洞察陈述、支持观察（定位）、反例、置信度。
- **耗时 / 人数**：2–4 小时 · 1–3 人
- **AI 协作**：agent 可对用户提供的观察做归并、改写洞察句、查缺反例；观察本身必须来自用户材料，每条洞察回指原始定位，不得编造观察或引文。
- **衔接**：上游 M3-14 → 下游 M4-02、M4-23

### M4-02 Insights Sorting · 洞察分类
- **来源**：通用设计实践
- **目的**：把大量洞察按主题归组，看清哪些方向证据最厚、哪些是孤例。
- **何时用**：洞察超过约 20 条、需要收敛时；**不适用**：洞察少于 10 条，直接逐条讨论即可。
- **输入**：M4-01 产出的洞察清单；团队成员若干。
- **步骤**：
  1. 每条洞察一张卡，先不预设类别。
  2. 团队默读并把相似卡放在一起，逐步形成组。
  3. 为每组写一个概括性标题（一句判断，不是名词）。
  4. 检查组间是否重叠，合并或拆分；留出「未归类」组。
  5. 按证据量与对项目意图的相关度给组排序。
- **产出**：洞察分组表：组名、组内洞察 ID、证据量、优先级；可用 markdown 表格交付。
- **耗时 / 人数**：1–2 小时 · 2–6 人
- **AI 协作**：agent 可提出初始分组与组名草案供用户修改；分组依据只能是用户给出的洞察原文，归组最终由用户确认。
- **衔接**：上游 M4-01 → 下游 M4-12、M4-17

### M4-03 User Response Analysis · 用户反应分析
- **来源**：通用设计实践
- **目的**：系统整理用户对刺激物（概念、原型、图片、问题）的反应，找出一致和分歧的模式。
- **何时用**：做过图片分类、概念测试、问卷开放题后；**不适用**：没有统一刺激物、反应无法横向比较。
- **输入**：每位用户对每个刺激物的反应记录（原话、评分、选择）。
- **步骤**：
  1. 建矩阵：行为用户（匿名代码），列为刺激物或问题。
  2. 在格内填反应摘要，并编码为正面 / 负面 / 中立 / 困惑等类别。
  3. 按列看：哪些刺激物反应一致、哪些两极分化。
  4. 按行看：是否存在反应相似的用户子群。
  5. 为每个模式写一句解读并附代表原话定位。
- **产出**：用户 × 刺激物反应矩阵 + 模式清单（模式、涉及用户、代表原话定位）；用 markdown 表格交付。
- **耗时 / 人数**：2–4 小时 · 1–2 人
- **AI 协作**：agent 可建矩阵、做编码草稿、指出分化点；反应数据与原话只来自用户提供的记录，不得补填空格或推算比例。
- **衔接**：上游 M3-10、M3-23 → 下游 M4-14

### M4-04 System Elements Diagram · 系统要素关系图
- **来源**：通用设计实践
- **目的**：把一个系统拆成实体（Entities）、关系（Relations）、属性（Attributes）、流（Flows），看清结构与交换。
- **何时用**：问题涉及多方、多物、多流程交织时；**不适用**：单一用户单一界面的局部问题。
- **输入**：研究中识别出的人、组织、物品、场所、信息清单；相关方地图（如有）。
- **步骤**：
  1. 列出系统内所有实体，并定边界（哪些在系统外）。
  2. 为关键实体写属性（规模、角色、约束）。
  3. 画出实体之间的关系（归属、依赖、竞争等）。
  4. 标出流：信息、金钱、物品、服务的流向。
  5. 圈出断点、瓶颈、重复流，作为洞察候选。
- **产出**：系统要素关系图 + 实体/属性表 + 断点清单；对话中可用 mermaid `flowchart` 代码块（节点=实体，带标签连线=关系/流）或 markdown 表格交付。
- **耗时 / 人数**：2–4 小时 · 1–4 人
- **AI 协作**：agent 可把用户列出的要素整理成图和表、提示遗漏的流类型；实体和流必须来自用户或研究材料，不确定的标「待确认」。
- **衔接**：上游 M2-13、M2-14 → 下游 M4-05、M4-27

### M4-05 Current-State Value Network · 现状价值网络
- **来源**：通用设计实践
- **目的**：描绘现状下各参与方之间交换的价值（钱、产品、服务、信息、信任），找出失衡与缺口。
- **何时用**：商业 / 服务生态问题、需要理解「谁从谁那得到什么」时；**不适用**：纯交互细节问题。
- **输入**：参与方清单、已知交易与合作关系；M4-04 系统图（如有）。
- **步骤**：
  1. 把参与方作为节点排布，用户放中心。
  2. 画出每对参与方之间的价值流，标明价值类型与方向。
  3. 检查每个参与方的「付出 / 获得」是否平衡。
  4. 标记失衡、单向依赖、缺失的回流，写成洞察。
- **产出**：现状价值网图 + 价值流清单（从、到、价值类型、备注）；对话中可用 mermaid `flowchart` 或 markdown 表格交付。
- **耗时 / 人数**：2–3 小时 · 2–4 人
- **AI 协作**：agent 可整理价值流、做平衡检查；价值流与金额等事实来自用户或其资料，agent 不得臆造财务数字。
- **衔接**：上游 M4-04 → 下游 M6-03

### M4-06 Positioning Map · 定位图
- **来源**：通用设计实践
- **目的**：在两个关键维度上摆放实体（竞品、产品、用户群等），找到空白区和聚集区。
- **何时用**：需要比较多个同类实体的相对位置时；**不适用**：找不到有区分力的维度。
- **输入**：待比较的实体清单；候选维度及每个实体在维度上的依据。
- **步骤**：
  1. 选两个对项目有意义、彼此独立的维度作为坐标轴，写清两端含义。
  2. 为每个实体在两轴上定位，并记录定位依据。
  3. 观察聚集区（红海）与空白区（潜在机会）。
  4. 换一组维度再画一次，对比结论是否稳健。
- **产出**：二维定位图 + 定位依据表；对话中可用 mermaid `quadrantChart` 或 markdown 表格（实体、X 值、Y 值、依据）交付。
- **耗时 / 人数**：1–2 小时 · 1–3 人
- **AI 协作**：agent 可建议维度、生成图；实体定位依据来自用户提供的资料，缺依据的点标「估计」并请用户确认。
- **衔接**：上游 M2-07、M2-16 → 下游 M4-07

### M4-07 Venn Diagramming · 维恩图
- **来源**：通用设计实践
- **目的**：用集合重叠看清几类需求 / 能力 / 群体的交集，交集常是机会点。
- **何时用**：要找「同时满足 A、B、C」的切入点时；**不适用**：集合超过 4 个，图会不可读。
- **输入**：2–4 个集合的定义及其成员（需求、特征、用户群等）。
- **步骤**：
  1. 定义每个集合及成员判定标准。
  2. 把成员逐一放入对应区域（独有 / 两两交集 / 全交集）。
  3. 重点讨论交集区：为什么重叠、意味着什么。
  4. 也看空交集：本该重叠却没有的，可能是缺口。
- **产出**：维恩图 + 各区成员表 + 交集机会描述；对话中可用 markdown 表格（区域、成员）交付，简单两集合可用 mermaid 近似表达。
- **耗时 / 人数**：0.5–1 小时 · 1–3 人
- **AI 协作**：agent 可做集合运算与分区；集合成员来自用户材料，agent 不补造成员。
- **衔接**：上游 M4-06 → 下游 M5-01

### M4-08 Tree / Semi-Lattice Diagramming · 树 / 半格图
- **来源**：通用设计实践
- **目的**：把要素组织成层级（树）或允许多重归属的层级（半格），暴露结构与共享节点。
- **何时用**：梳理需求层级、信息架构、问题分解时；**不适用**：要素间主要是循环因果关系（用 M4-27）。
- **输入**：要素清单（需求、功能、问题、洞察）。
- **步骤**：
  1. 确定根节点（总目标或总问题）。
  2. 自上而下拆分，或自下而上归并，逐层建立父子关系。
  3. 检查是否有节点同时属于多个父节点——如有，改用半格表达。
  4. 审视层级是否平衡、有无缺层或同层粒度不一。
- **产出**：层级结构图 + 节点清单；对话中可用 mermaid `flowchart TD`（半格允许多条入边）或缩进列表交付。
- **耗时 / 人数**：1–2 小时 · 1–2 人
- **AI 协作**：agent 可自动整理层级、发现多重归属；要素内容来自用户，层级取舍由用户确认。
- **衔接**：上游 M4-02 → 下游 M4-17

### M4-09 Symmetric Clustering Matrix · 对称聚类矩阵
- **来源**：通用设计实践
- **目的**：对同一类元素两两评估相关度，据此聚类，发现自然分组。
- **何时用**：元素 10–40 个、分组不直观时；**不适用**：元素过多（两两评估成本爆炸）或过少。
- **输入**：一类元素清单（如需求、活动、功能）；相关度评分规则。
- **步骤**：
  1. 元素同时作为行和列，建 N × N 矩阵。
  2. 按规则给每对元素打相关度（如 0/1/2），矩阵对称只填一半。
  3. 调整行列顺序，让高分格聚到对角线附近。
  4. 圈出高相关块，命名为聚类。
- **产出**：对称矩阵 + 聚类清单（聚类名、成员、依据）；用 markdown 表格交付。
- **耗时 / 人数**：2–3 小时 · 1–3 人
- **AI 协作**：agent 可做矩阵排序与聚类计算；两两相关度的判断需用户给出或确认，agent 的初评必须标为草案并说明依据。
- **衔接**：上游 M4-02 → 下游 M4-11

### M4-10 Asymmetric Clustering Matrix · 非对称聚类矩阵
- **来源**：通用设计实践
- **目的**：评估两类不同元素（如用户需求 × 功能、活动 × 用户群）之间的关联，找出紧密对应的组合。
- **何时用**：要把需求映射到方案要素或用户群时；**不适用**：只有一类元素（用 M4-09）。
- **输入**：两类元素清单；关联评分规则。
- **步骤**：
  1. A 类作行、B 类作列，建矩阵。
  2. 逐格评估关联强度。
  3. 重排行列，使高关联格聚成块。
  4. 为每个块命名，并记录无人对应的行 / 列（缺口或冗余）。
- **产出**：A × B 关联矩阵 + 聚类块清单 + 缺口清单；用 markdown 表格交付。
- **耗时 / 人数**：2–3 小时 · 1–3 人
- **AI 协作**：agent 可排序矩阵、识别块和空行空列；关联判断由用户提供或确认，不得凭空填分。
- **衔接**：上游 M4-14 → 下游 M5-05

### M4-11 Activity Network · 活动网络
- **来源**：通用设计实践
- **目的**：把用户活动按先后、依赖、共现关系连成网络，看出核心活动与关键路径。
- **何时用**：用户行为不是线性流程、而是多活动交织时；**不适用**：流程已高度线性（用 M4-16）。
- **输入**：观察到的活动清单及活动间关系（来自 M3 研究）。
- **步骤**：
  1. 列出活动，每项一个节点。
  2. 标出活动间关系：先后、依赖、常一起发生。
  3. 找出连接最多的中心活动和常见路径。
  4. 标注痛点发生在哪些节点或连线上。
- **产出**：活动网络图 + 活动表（活动、关联活动、痛点）；对话中可用 mermaid `flowchart` 或 markdown 表格交付。
- **耗时 / 人数**：1–3 小时 · 1–3 人
- **AI 协作**：agent 可建网、计算连接度；活动与关系来自用户研究记录，缺证据的关系不画。
- **衔接**：上游 M3-17、M4-09 → 下游 M4-16

### M4-12 Insight Clustering Matrix · 洞察聚类矩阵
- **来源**：通用设计实践
- **目的**：把洞察放到一组维度（用户群、旅程阶段、人因等）上交叉查看，找出集中区和盲区。
- **何时用**：洞察已分组、需要看分布与覆盖时；**不适用**：洞察尚未提炼。
- **输入**：洞察清单（M4-01/M4-02）；2 个或以上分析维度。
- **步骤**：
  1. 选维度作列（如旅程阶段），洞察作行，或维度 × 维度交叉。
  2. 在相关格打标记或写要点。
  3. 看哪些格密集（高关注区）、哪些格空白（研究盲区或机会）。
  4. 把发现写成 2–5 条跨洞察结论。
- **产出**：洞察 × 维度矩阵 + 结论清单；用 markdown 表格交付。
- **耗时 / 人数**：1–2 小时 · 1–3 人
- **AI 协作**：agent 可排布矩阵、指出空白；空白只能解读为「当前材料未覆盖」，不得臆测填补。
- **衔接**：上游 M4-02 → 下游 M4-17、M4-18

### M4-13 Semantic Differential Profile · 语义差异剖面
- **来源**：Osgood 语义差异法
- **目的**：用成对的形容词量表（语义差异法）刻画产品 / 品牌 / 体验给人的感受，并对比现状与目标。
- **何时用**：需要量化或对比感知特质时；**不适用**：功能性问题，与感受无关。
- **输入**：一组对项目有意义的反义词对；评估对象；评分者（用户或团队）。
- **步骤**：
  1. 选 6–12 对反义形容词（如 冷漠—温暖），用 5 或 7 级量表。
  2. 让评分者对每个对象逐项打分。
  3. 汇总每对的分布（注明样本数，不外推为总体）。
  4. 把各对象的剖面线叠在一起比较，标出差距最大的维度。
- **产出**：语义剖面表（词对、各对象得分、样本数）+ 差距结论；用 markdown 表格交付。
- **耗时 / 人数**：1–3 小时 · 1–2 人 + 评分者
- **AI 协作**：agent 可建议词对、汇总计算、画剖面；评分必须来自真实评分者，agent 不得代为打分冒充用户。
- **衔接**：上游 M3-10 → 下游 M4-18

### M4-14 User Groups Definition · 用户群定义
- **来源**：通用设计实践
- **目的**：依据行为和需求差异（而非仅人口属性）把研究对象分成若干用户群。
- **何时用**：研究样本中出现明显不同的行为模式时；**不适用**：样本太少，无法区分模式。
- **输入**：研究对象记录；M4-03 的反应模式或行为变量。
- **步骤**：
  1. 选出 2–4 个区分力强的行为 / 态度变量。
  2. 把每位研究对象在变量上定位。
  3. 找出聚在一起的对象，形成候选群。
  4. 为每群写名称、核心特征、关键需求，并注明包含的研究对象代码。
- **产出**：用户群表（群名、区分特征、需求、成员代码、人数）；用 markdown 表格交付。
- **耗时 / 人数**：2–3 小时 · 1–3 人
- **AI 协作**：agent 可建议变量、做聚类草案；群成员与特征来自用户数据，不得推断未提供的人口属性，人数只报样本内计数。
- **衔接**：上游 M4-03 → 下游 M5-03、M4-10

### M4-15 Ideal Experience Map · 理想体验地图
- **来源**：通用设计实践
- **目的**：按体验阶段描绘「理想中」用户该有的体验，作为方案要追求的目标。
- **何时用**：已理解现状，需要为方案设定体验目标时；**不适用**：尚未理解现状旅程。
- **输入**：现状旅程（M4-16）、洞察、设计原则草案。
- **步骤**：
  1. 沿用现状旅程的阶段划分（如 吸引—进入—投入—离开—延续）。
  2. 每阶段写出理想体验：用户做什么、感受什么、得到什么。
  3. 对照现状标出差距最大的阶段。
  4. 把差距转成机会陈述。
- **产出**：理想体验阶段图（阶段、理想体验、现状差距、机会）；对话中可用 markdown 表格或 mermaid `journey` 交付。
- **耗时 / 人数**：2–3 小时 · 2–5 人
- **AI 协作**：agent 可起草理想体验描述供讨论；「理想」是设计假设，须标明不是用户原话，差距判断回指现状材料。
- **衔接**：上游 M4-16 → 下游 M4-24、M6-13

### M4-16 User Journey Map · 用户旅程地图
- **来源**：通用设计实践
- **目的**：按时间顺序呈现用户完成一个目标的全过程：阶段、行为、触点、想法、情绪、痛点。
- **何时用**：要看体验全貌、定位痛点阶段时；**不适用**：没有真实用户行为数据（只能画假设旅程并明确标注）。
- **输入**：访谈 / 观察记录；目标用户群；要覆盖的场景与起止点。
- **步骤**：
  1. 定角色（一个用户群）、场景、起点与终点。
  2. 划阶段，每阶段填：行为、触点、想法（引原话）、情绪高低。
  3. 标出痛点与「真相时刻」。
  4. 在痛点旁写机会点。
  5. 每个格子注明证据来源；无证据格标「假设」。
- **产出**：旅程地图（阶段 × 行为/触点/想法/情绪/痛点/机会）；对话中可用 markdown 表格或 mermaid `journey`（情绪分值）交付。
- **耗时 / 人数**：3–6 小时 · 2–5 人
- **AI 协作**：agent 可从用户提供的记录抽取行为与原话填表、画图；情绪分与原话必须回指材料，不得编造引文。
- **衔接**：上游 M3-07、M4-11 → 下游 M4-15、M6-13

### M4-17 Summary Framework · 总结框架
- **来源**：通用设计实践
- **目的**：把分散的分析结果浓缩成一页可讲清楚的框架（模型、矩阵或图），作为团队共同语言。
- **何时用**：分析结束、需要对外沟通或进入构思前；**不适用**：洞察还未收敛。
- **输入**：洞察分组、矩阵、层级图等分析产物。
- **步骤**：
  1. 找出最能解释全部发现的 2–4 个核心维度或主题。
  2. 选框架形式（2×2、层级、流程、同心圆等）。
  3. 把关键洞察放进框架，删掉不能解释任何发现的部分。
  4. 用一段话讲述框架，测试他人能否复述。
- **产出**：一页总结框架（图 + 一段说明 + 各部分对应的洞察 ID）；对话中可用 mermaid 或 markdown 表格交付。
- **耗时 / 人数**：2–4 小时 · 1–3 人
- **AI 协作**：agent 可提出多个框架备选、起草说明；每个框架元素须回指洞察 ID，由用户选定。
- **衔接**：上游 M4-12、M4-08 → 下游 M4-18、M5-01

### M4-18 Design Principles Generation · 设计原则生成
- **来源**：通用设计实践
- **目的**：把洞察转成指导后续方案取舍的少数几条原则。
- **何时用**：进入构思前，需要统一判断标准时；**不适用**：尚无可靠洞察。
- **输入**：洞察清单、总结框架。
- **步骤**：
  1. 对每条关键洞察问「那么方案应当……」。
  2. 把结果写成可执行的原则句（动词开头，有取舍含义）。
  3. 合并重复，控制在 3–7 条。
  4. 用反例测试：一个违反该原则的方案是否明显更差？不是则删改。
- **产出**：设计原则清单（原则、说明、来源洞察 ID、反例）；用 markdown 表格交付。
- **耗时 / 人数**：1–2 小时 · 2–5 人
- **AI 协作**：agent 可起草原则并做反例测试；每条原则必须回指用户材料中的洞察，不写空泛口号。
- **衔接**：上游 M4-17 → 下游 M5-04、M6-02

### M4-19 Analysis Workshop · 分析工作坊
- **来源**：通用设计实践
- **目的**：让团队和相关方一起过研究材料，形成共识洞察与优先级。
- **何时用**：多人参与研究、需要对齐理解时；**不适用**：只有一个研究者且无需对齐。
- **输入**：研究材料摘要、洞察草案；主持人；4–10 名参与者；议程。
- **步骤**：
  1. 会前分发材料，明确要回答的问题。
  2. 各自分享最意外的发现（讲事实、附来源）。
  3. 小组内做亲和归类（可用 M4-20）并提炼洞察。
  4. 全体讨论、投票确定优先洞察。
  5. 记录共识、分歧与后续待验证问题。
- **产出**：共识洞察清单 + 分歧记录 + 待验证问题。
- **耗时 / 人数**：半天 · 4–10 人
- **AI 协作**：agent 可设计议程、会前整理材料、会后整理纪要；会上讨论与投票由真人完成，纪要只记录实际发生的内容。
- **衔接**：上游 M4-01 → 下游 M4-20、M4-18

### M4-20 Affinity Diagram / KJ 法 · 亲和图
- **来源**：川喜田二郎
- **目的**：自下而上把大量零散数据按相似性聚类，从数据中「长出」主题。
- **何时用**：手里有大量访谈 / 观察片段，还没有分类框架时；**不适用**：已有成熟分类且只需归档。
- **输入**：一条一事实的数据卡（原话、观察），每张附来源定位。
- **步骤**：
  1. 每条数据写一张卡，语言保持原意。
  2. 不预设类别，逐张把「感觉相近」的卡放一起。
  3. 为每组写一句概括性标题（表达组内共同意思）。
  4. 把组再归并为更高层主题，形成 2–3 层结构。
  5. 检查组间关系，写出主题间的关联或矛盾。
- **产出**：亲和分组（主题 → 子组 → 数据卡 ID）；对话中可用缩进列表、markdown 表格或 mermaid `mindmap` 交付。
- **耗时 / 人数**：2–4 小时 · 1–6 人
- **AI 协作**：agent 可对用户提供的片段做首轮归组和命名，并保留每张卡的来源定位；不得添加材料中没有的卡片，归组由用户复核。
- **衔接**：上游 M3-07、M3-14 → 下游 M4-01、M4-24

### M4-21 Empathy Map · 同理心地图
- **来源**：XPLANE
- **目的**：围绕一个用户，把他「说、想、做、感」汇在一张图上，建立共同的用户理解。
- **何时用**：访谈后快速对齐对某类用户的理解时；**不适用**：想用它替代研究（没有数据时只能画假设版并标注）。
- **输入**：某一用户或用户群的访谈 / 观察记录。
- **步骤**：
  1. 在中心写明对象（用户群名）和场景。
  2. 分四格填写：说（原话）、想（推断的想法）、做（行为）、感（情绪）。
  3. 区分可观察（说、做）与推断（想、感），推断需注明依据。
  4. 找出格间矛盾（如说的与做的不一致），写成洞察。
  5. 可补充痛点（Pains）与收获（Gains）。
- **产出**：说 / 想 / 做 / 感 四格 + 矛盾洞察；对话中用 2×2 的 markdown 表格交付。
- **耗时 / 人数**：0.5–1.5 小时 · 1–5 人
- **AI 协作**：agent 可从用户提供的记录中抽取并分格；「说」格只放逐字原话并附定位，不得编造引文，推断格标明是推断。
- **衔接**：上游 M3-07 → 下游 M4-23、M5-03

### M4-22 Job Map / Job Story · 任务地图
- **来源**：Jobs to be Done
- **目的**：把用户要完成的「任务」拆成通用步骤，并用 Job Story 描述情境、动机与期望结果。
- **何时用**：要从用户目标而非功能出发找机会时；**不适用**：尚不知道用户的核心任务。
- **输入**：JTBD 访谈（M3-21）或其他研究材料；核心任务陈述。
- **步骤**：
  1. 写出核心任务（动词 + 对象 + 情境），不含方案。
  2. 按「定义—定位—准备—确认—执行—监控—调整—结束」等通用阶段拆步骤。
  3. 每步找出用户在速度、准确、稳定上的期望与难点。
  4. 把关键时刻写成 Job Story：「当……（情境），我想要……（动机），以便……（结果）」。
- **产出**：任务步骤表（步骤、期望、难点、证据）+ Job Story 清单；可用 markdown 表格或 mermaid `flowchart LR` 交付。
- **耗时 / 人数**：2–4 小时 · 1–3 人
- **AI 协作**：agent 可搭步骤框架、改写 Job Story；情境与难点来自用户研究，缺证据的步骤标「待研究」。
- **衔接**：上游 M3-21 → 下游 M4-24、M5-02

### M4-23 Point of View / Problem Statement · 问题陈述
- **来源**：d.school
- **目的**：用一句话锁定「为谁、要解决什么需要、基于什么洞察」，作为构思的起点。
- **何时用**：洞察已形成、要进入构思前；**不适用**：还在广泛探索、没有明确用户与洞察。
- **输入**：目标用户群、关键洞察、同理心地图。
- **步骤**：
  1. 按格式起草：「[用户] 需要 [需要，用动词]，因为 [洞察]」。
  2. 检查需要是否写成了方案（如「需要一个 App」），是则改成需要本身。
  3. 检查洞察是否有材料支撑、是否令人意外。
  4. 写 2–3 个版本，与用户 / 团队挑选最能激发构思的一个。
- **产出**：POV 陈述 1–3 条，每条附来源洞察 ID。
- **耗时 / 人数**：0.5–1 小时 · 1–4 人
- **AI 协作**：agent 可起草多个版本并检查是否夹带方案；用户与洞察必须来自用户材料，最终版本由用户选定。
- **衔接**：上游 M4-01、M4-21 → 下游 M4-24

### M4-24 How Might We · 「我们可以怎样…」
- **来源**：IDEO
- **目的**：把问题陈述或痛点转成开放、可构思的问题，为发散做准备。
- **何时用**：从定义进入构思的过渡；**不适用**：问题本身还没搞清楚。
- **输入**：POV 陈述、痛点、洞察。
- **步骤**：
  1. 以「我们可以怎样……」开头改写每个痛点或 POV。
  2. 调整范围：太宽（无从下手）就收窄，太窄（已暗含方案）就放宽。
  3. 用多种角度各写几条：放大好的、去掉坏的、反转、类比、拆分。
  4. 聚类并挑选 3–5 条进入构思。
- **产出**：HMW 问题清单（问题、来源痛点 / POV、是否入选）。
- **耗时 / 人数**：0.5–1 小时 · 1–6 人
- **AI 协作**：agent 可批量生成与调范围，适合在对话中直接产出；每条 HMW 回指来源痛点，入选由用户决定。
- **衔接**：上游 M4-23、M4-20 → 下游 M5-04、M5-18

### M4-25 5 Whys · 五问法
- **来源**：丰田
- **目的**：对一个问题连续追问「为什么」，从表面症状追到可行动的根因。
- **何时用**：问题相对明确、因果链较单一时；**不适用**：多因多果的系统问题（用 M4-27）。
- **输入**：清晰描述的问题现象；了解情况的人或相关数据。
- **步骤**：
  1. 用事实写出问题（何时、何处、什么现象）。
  2. 问「为什么发生」，写出答案并注明依据。
  3. 对答案继续问为什么，通常 3–5 层，到可行动的原因为止。
  4. 若一层有多个原因，分叉成多条链。
  5. 对根因提出对策，并确认对策能阻断链条。
- **产出**：根因链（问题 → 为什么 1…n → 根因 → 对策），每层附依据；对话中可用 mermaid `flowchart TD` 或编号列表交付。
- **耗时 / 人数**：0.5–1 小时 · 1–4 人
- **AI 协作**：agent 可引导追问、记录链条；每层答案须来自用户或数据，agent 提出的原因只能作为待核实假设。
- **衔接**：上游 M2-17 → 下游 M4-26、M4-23

### M4-26 Iceberg Model · 冰山模型
- **来源**：系统思考
- **目的**：从可见事件往下挖：事件 → 模式 → 结构 → 心智模式，找到更深的干预点。
- **何时用**：问题反复出现、表层修补无效时；**不适用**：一次性偶发事件。
- **输入**：反复出现的事件记录；相关方与流程信息。
- **步骤**：
  1. 事件层：列出最近发生了什么（事实）。
  2. 模式层：这类事件随时间有什么规律。
  3. 结构层：哪些规则、流程、激励、资源配置导致了这种模式。
  4. 心智层：哪些信念与假设在维持这些结构。
  5. 在每层标出可干预点，越往下杠杆越大。
- **产出**：事件-模式-结构-心智 四层表（层、内容、证据、干预点）；用 markdown 表格交付。
- **耗时 / 人数**：1–2 小时 · 2–5 人
- **AI 协作**：agent 可引导逐层提问、整理表格；事件与模式来自用户材料，结构与心智层的推断须标为假设并请用户确认。
- **衔接**：上游 M4-25 → 下游 M4-27

### M4-27 Causal Loop Diagram · 因果回路图
- **来源**：系统思考
- **目的**：画出变量间的因果关系与反馈回路，解释系统为何自我强化或自我抑制，找到杠杆点。
- **何时用**：「按下葫芦浮起瓢」的系统性问题；**不适用**：单向简单因果（用 M4-25）。
- **输入**：关键变量清单（可度量的量，不是事件）；变量间关系的依据。
- **步骤**：
  1. 列出 5–15 个关键变量，用名词短语表示可增减的量。
  2. 画变量间的因果箭头，标极性：同向（+）或反向（−）。
  3. 找出闭合回路，判断是增强回路（R）还是调节回路（B）。
  4. 标注明显的延迟。
  5. 讨论哪里是杠杆点：改变哪个变量或连线能改变系统行为。
- **产出**：回路图 + 回路清单（回路名、类型 R/B、变量链、解读）+ 杠杆点；对话中可用 mermaid `flowchart`（连线标 +/−）配 markdown 表格交付。
- **耗时 / 人数**：2–4 小时 · 2–5 人
- **AI 协作**：agent 可整理变量、画图、识别回路类型；因果关系须有用户材料或用户确认支撑，agent 提出的连线标为假设。
- **衔接**：上游 M4-26、M4-04 → 下游 M6-16
