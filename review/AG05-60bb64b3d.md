## Findings

1. **major (blocking): the new recovery short-circuit is not truthful.** `apps/api/src/infrastructure/agent-run/pg-run-recovery.ts:56`. Recovery now auto-approves any `start_workflow` interrupt it finds, and the evidence file and test title claim that the tool body then "如实回复「流程未发起、未创建任何实例」". Two cases break that claim:
   - **(a) Crash after start.** `handleWorkflowStartCall` calls WF03 `start` and writes the ledger note "已创建实例 X" *before* `requeueToolCallWithResult` (`workflow-start-gate.ts:31-48`). If the executor dies or loses its lease in that window, recovery reads the checkpoint, which is still parked on `start_workflow`, and approves it. The Agent is then told no instance exists while one is running. If the user asks again, the Agent issues a new tool call with a new `toolCallId`, so a second instance is created. This is the scenario round-1 ⑤ asked to be exercised. Before this round it went to a human; now it is automatic, and it is wrong.
   - **(b) Forged outcome via approve.** Approve executes the model's *original* args. The `outcome` parameter is part of the model-visible tool schema (`tools.py` `start_workflow(..., outcome)`), so a model or prompt injection that fills `outcome: {status:"started", message:"已发起流程…"}` gets that text echoed back verbatim. The gate path is safe because it rebuilds the args from `parseWorkflowStartArgs` and drops any model `outcome`. The recovery approve bypasses that. The human approve in `decideAgentRun` (`decide-agent-run.ts:82`, where approve is still allowed) has the same problem.

   **Fix:** in recovery, handle `start_workflow` the same way the gate does: `requeueToolCallWithResult` with a *server-computed* outcome, never approve.
   - Derive `requestId` the same way the gate does, from `run.id` and `result.toolCallId`. The reconciler returns `toolCallId` at runtime; add it to the `ReconciledRemoteRun` approval type.
   - Look it up **read-only**, with no fresh submission, per the recovery doctrine. Use either the WF03 receipt `start:<requestId>` (`pg-workflow-receipt-store.ts`) or this run's ledger `planningNote`.
   - If an instance exists, return `started` with that instanceId. Otherwise return `refused("workflow_runtime_unavailable")`.

   In `decideAgentRun`, either refuse `approve` for `start_workflow` as well, or rewrite it server-side to an edit with the refused outcome. Also consider hiding `outcome` from the model schema, for example with an injected / non-model arg, so the model cannot author it at all.

   **Test:** add a case where the instance was created before the crash. Recovery must hand back `started` with the same instanceId, and the instance count must be unchanged. Also add a case where the model-supplied `outcome` is ignored on the recovery and approve paths.

2. **minor: evidence and comments overstate the guarantee.** `phases/phase-20-work-stack-foundation/evidence/AG05-workflow-allowlist-enforce.md` (§评审) and the comment at `pg-run-recovery.ts:54-55` say the approve path is truthful and fail-closed. Once finding 1 is fixed, update both to describe the real guarantee.

3. **minor: WF03 start runs before the capability check.** `apps/api/src/application/agent-run/workflow-start-gate.ts:31-47`. The `requeueToolCallWithResult` capability check comes *after* `requestAgentWorkflowStart`. On a store without the method, a real instance is created and then the run is failed with `MODEL_CALL_FAILED`, so the Agent never learns the instance exists. **Fix:** move the capability check before the WF03 start, and fail or refuse without starting. Separately, `MODEL_CALL_FAILED` misattributes the cause; prefer an existing more accurate stable code if one fits.

4. **nit: the 409 copy does not fit this refusal.** A generic-path edit on `start_workflow` now gets 409 `AGENT_RUN_NOT_AWAITING_TOOL_PERMISSION`. The web copy for that code is "这次执行当前不处于等待审批状态", which is inaccurate for this case: the run *is* awaiting. It is acceptable because it reuses existing surface without adding contract surface. Better still, stop the approval card from offering "edit" for `start_workflow` at all.
