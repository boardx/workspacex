Findings:

1. **major (spec deviation, documentation only)**: `apps/api/tests/agent/workflow-allowlist-enforce.test.ts:227-231`. The feature notes say "E3 断言：D002 请求 W027 被拒、W001 成功", but the test asserts that W001 comes back `workflow_not_found`. Research-line W001 has no runtime graph or definition: `builtInWorkflowDefinitions()` / `defaultWorkflowGraphs()` only cover demo, W027–W032 and W002. So the allowlist-hit path passes, but "W001 成功" cannot happen on today's runtime. The positive path is proven with D003→W027 instead, which is reasonable, but the gap is not recorded where the gate looks. **Fix expected:** before `harness verify`, post a comment on the AG05 issue stating the deviation, with a link to the CT03 / W001-runtime-definition follow-up issue. Also add a line to the evidence file. When a W001 definition lands, change this assertion to `status: "started"`.

2. **minor**: `apps/api/migrations/20260929140000_ag05_tool_result_requeue.sql:38`. The new `running → queued (edit)` edge is allowed for any tool, not just `start_workflow`. The header comment calls it "同样收窄", but the DB does not enforce any tool restriction. **Fix:** add `AND NEW.pending_tool_name = 'start_workflow'` to the edge, in a new forward migration or in this one before merge, so that no other server path can use it silently.

3. **minor**: `apps/api/src/application/agent/request-agent-workflow-start.ts:139`. When `toolCallId` is missing, the `requestId` falls back to `runId + workflowId`. Two legitimate `start_workflow` calls for the same W in one run then collide under WF03 A1. The second call gets either the first call's cached result (A1 also caches business refusals, so an earlier "not published" would stick) or a 409 that maps to the generic copy. **Fix:** fall back to `interrupted.toolArgsDigest` plus a per-run counter or seq. Alternatively, refuse with `workflow_runtime_unavailable` and no start when `toolCallId` is absent.

4. **minor**: `apps/api/src/application/agent-run/workflow-start-gate.ts:42-49`. `requeueToolCallWithResult` is optional (`?.`). If a store does not implement it, `requeued` is `undefined`, but the gate still returns `{autoApproved: true}`. The run then stays in `running` with no resume, and nothing tells the user. **Fix:** make the method required on `AgentRunStore`, or treat a missing method as a failure: fail the run with a stable code, or park it in `awaiting_tool_permission`. Only log "lost the race" when the method returned `false`.

5. **minor (test coverage)**: `workflow-allowlist-enforce.test.ts:306`. The crash-recovery replay is proven by calling `requestAgentWorkflowStart` directly. The real takeover path is not exercised: lease expiry, then a checkpoint re-interrupt with the same `toolCallId`, then the gate again. **Fix (optional):** add one case that expires the run lease after `start` but before requeue, re-executes the run, and asserts one instance plus an edit resume.

6. **minor (test coverage)**: native runtime. The API test only drives a `deep-agent`-profile run. On the native side, only `interactions_only` membership, the `INTERRUPT_ONLY` dispatch list and `PgNativeSessionOwner` binding migration are covered. No test resumes `start_workflow` with `edit` through the native entry. **Fix (optional):** add a pytest case like `test_start_workflow.py` that builds the native graph (`build_tools(..., interactions_only=True)` + native interrupt_on) and resumes with `edit` + `outcome`.

7. **nit**: `apps/api/src/application/agent/request-agent-workflow-start.ts:32`. The tool name `"start_workflow"` is declared in the TS application layer and again as a literal in `tools.py`/`harness.py`. The generated admission JSON keeps the list in sync, but not the name itself. AG06 keeps `ESCALATE_TOOL_NAME` in contracts. Leaving it out of contracts is acceptable here given the "no new contract surface" constraint. When the bundle is next re-signed, move it to `@repo/contracts/agent-role`.

8. **nit**: `apps/api/src/application/workflow/workflow-runtime-service.ts:29`. The workflow module now imports `../agent-run/run-lease`. This is a cross-module dependency, although arch-deps lint passes. Consider exposing `withoutRunLease` from a shared port or context module so that workflow does not depend on agent-run internals.
