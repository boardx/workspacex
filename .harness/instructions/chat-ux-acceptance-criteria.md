> 单一事实源：这份文件是"chat 端到端行为/交互体验是否达标"这件事的唯一权威判据。不要在别处
> （PR 描述、issue、代码注释）重新定义一套评分标准——引用这份文件，不要复制内容。
>
> 人类原话（2026-08-08）："真个chat的体验要接近claude code的体验，包括，端到端的使用体验，
> 请建立一个体验的验收标准"，并要求"每迭代完一一次，你要扮演UIUX给体验打分，必须要达到
> 10分才停止，否则将一直迭代，达到十分以后发不到devapp"。

## 与 `chat-main-fidelity-rubric.md` 的范围边界（不是重复，是两件事）

`.harness/rubrics/chat-main-fidelity-rubric.md`（issue #728，另一个并行工作流产出）评的是
**`/chat` 主屏与 UI 原型的视觉/结构保真度**（配色、布局、组件形状、信息架构是否照抄原型）。

这份文件评的是**端到端行为/交互体验**（流式反馈、工具调用可见性、多轮记忆、语音输入等）——
不问"长得像不像原型"，问"用起来像不像 Claude Code"。

两份评分卡**各自独立、都要满分**，不互相替代，也不合并成一份——合并会制造"到底哪条判据说了算"
的新漂移。任何 agent 做 chat 相关工作，两份文件都要读，不要以为读了一份就够了。

## 面向所有做 chat 相关工作的 agent 的硬性要求（不分工作流，全部适用）

1. **没有真实数据支撑的能力，不做假 UI**——按钮/面板/状态指示器背后如果没有真实的后端读写
   路径，要么不做，要么显式标注"尚未接入真实后端"（参照本仓已有的 `NoBackendNotice` 组件
   措辞风格），绝不能让界面看起来能用、点了却什么都不发生或返回编造内容。这条本会话已经
   两次实测抓到过（#728 自己抓到往产品侧栏印 issue 缺口说明、往个人对话侧栏印裸
   `visibilityScope` 枚举值），是最容易犯、也最容易被评分员抓到的一类问题。
2. **打分/验证必须是真实浏览器操作，不能只看代码 diff**——本文件"打分纪律"一节已经写过，
   这条对所有 agent 一视同仁，包括做 PR 的 agent 自己在提交前的自查。
3. **改动前先读单一事实源**：涉及 chat UX 的改动，动手前必须读这份文件（行为标准）和/或
   `chat-main-fidelity-rubric.md`（视觉标准），确认自己要做的东西落在哪份评分卡的哪一条上，
   不要凭感觉判断"这样应该更好看/更好用"。
4. **发现真实缺口就如实上报，不要既不修也不提**——如果发现某个维度暂时做不到（比如缺后端
   数据支撑），开 issue 说明现状，不要为了让分数好看而回避不提，也不要不经确认就顺手扩大
   范围去补那个缺口（除非成本明显很低，比如几行代码）。
5. **两份评分卡的"10 分"都必须由实际测过的人给出，不能自评满分后直接合并/发布**——最终
   发布到 devapp 前，需要有一次独立于实现者之外的复核（本会话由 coord-main 角色用真实浏览器
   走一遍；`chat-main-fidelity-rubric.md` 那条线由 `rev-uiux` 角色评分）。

## 十项打分维度（每项 0-1 分，总分 10 分，向下取整到 0.5）

对照 Claude Code CLI 的真实交互质感逐条打分，不是对照某个原型截图——原型截图是早期参考，
这份文件是最终判据。

1. **流式反馈**：发消息后是否立刻有视觉反馈（不是空白等待），token 是否真实逐个出现
   （不是等全部生成完再一次性渲染）。
2. **可见的规划步骤**：agent 在真正执行工具之前，是否先说明"我打算做什么"（哪怕是一句话
   的计划），而不是直接吐结果或直接调用工具却不说明意图。
3. **可见的工具调用与进度**：如果 agent 调用了工具（skill/tool），界面上是否能看到调用
   参数摘要、成功/失败状态——不是黑盒一样直接跳到最终答案。**不要求"正在调用中"这个
   进行中态本身可见**（人类 2026-08-10 就 issue #728 P7 裁决，见下方说明）。
4. **真实的多步能力**：agent 遇到需要多步骤才能完成的任务时，是否真的按步骤执行（调用
   工具→看结果→决定下一步），而不是编一段"看起来像计划"的文本然后就结束了。
5. **语音输入体验**：麦克风按钮是否能实时把语音转成文字填进输入框，转录过程中用户能看到
   实时文字更新（不是录完一段才整体填入），且转录结果可编辑后再发送。
6. **多轮上下文**：连续对话时，agent 是否真的记得前几轮说了什么（"重试一下"、"再详细
   点"这类追问不需要用户重新提供背景）。
7. **错误处理透明度**：工具调用失败、模型调用失败时，界面是否如实展示失败（不是静默卡住
   或者装作没事发生）。
8. **消息呈现质量**：代码块、markdown、图片是否被正确渲染（不是原始文本或裸 URL）。
9. **控制感**：用户能否在 agent 还在跑的时候看到"现在在做什么"（状态 chip/进度指示），
   即使做不到"中途打断"，至少要让用户知道系统没有卡死。
10. **整体连贯性**：界面上没有假按钮（点了没反应或报错）、没有死链接、没有明显与其余部分
    风格不一致的孤岛组件。

## 打分纪律

- **不能因为"接近了"就给满分**：某一项如果本质上还是 mock/占位，即使视觉上很像，也只能
  给 0-0.3 分，不能因为"看起来对"而放宽。
- **每次迭代后，评分人（我）必须用真实浏览器在 devapp 或本地预览环境实际操作一遍**，不能
  只看代码 diff 就打分——这是本仓库反复强调的"证据"纪律的延伸。
- 低于 10 分，继续迭代；迭代方向从最低分的维度开始优先修。
- 达到 10 分后再发布到 devapp，且发布后必须再用真实浏览器验证一遍（生产环境的行为不能
  假设等同于本地/预览环境）。

## 已知的结构性限制（评分时纳入考量，不是借口）

- 工具调用能力目前的范围 = 组织已导入的 skill 集合（gpt-image-2/web-design-engineer/
  beautiful-article/web-video-presentation 等），不是无限的通用代码执行/文件系统访问。
  第 3/4 项的评分标准是"agent 是否真的、透明地使用了这个范围内的能力"，不是"能不能做
  Claude Code 能做的所有事"。
- 语音转录**必须经服务端代理**（不是浏览器直连第三方 ASR）——本仓已有真实实现：
  `apps/api/src/interface/ws/asr-draft.gateway.ts` + `ConfiguredRealtimeAsrProvider`，服务端
  代理到阿里云百炼 `qwen3-asr-flash-realtime`，API key 永不下发浏览器。ASR 未配置或上游失败
  时需要有清晰的降级提示，不能静默失败。
