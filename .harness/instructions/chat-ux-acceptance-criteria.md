# Chat 体验验收标准（对标 Claude Code）

> 单一事实源：这份文件是"chat 体验是否达标"这件事的唯一权威判据。不要在别处（PR 描述、issue、
> 代码注释）重新定义一套评分标准——引用这份文件，不要复制内容。
>
> 人类原话（2026-08-08）："真个chat的体验要接近claude code的体验，包括，端到端的使用体验，
> 请建立一个体验的验收标准"，并要求"每迭代完一一次，你要扮演UIUX给体验打分，必须要达到
> 10分才停止，否则将一直迭代，达到十分以后发不到devapp"。

## 十项打分维度（每项 0-1 分，总分 10 分，向下取整到 0.5）

对照 Claude Code CLI 的真实交互质感逐条打分，不是对照某个原型截图——原型截图是早期参考，
这份文件是最终判据。

1. **流式反馈**：发消息后是否立刻有视觉反馈（不是空白等待），token 是否真实逐个出现
   （不是等全部生成完再一次性渲染）。
2. **可见的规划步骤**：agent 在真正执行工具之前，是否先说明"我打算做什么"（哪怕是一句话
   的计划），而不是直接吐结果或直接调用工具却不说明意图。
3. **可见的工具调用与进度**：如果 agent 调用了工具（skill/tool），界面上是否能看到"正在
   调用 XX"、调用参数摘要、成功/失败状态——不是黑盒一样直接跳到最终答案。
4. **真实的多步能力**：agent 遇到需要多步骤才能完成的任务时，是否真的按步骤执行（调用
   工具→看结果→决定下一步），而不是编一段"看起来像计划"的文本然后就结束了。
5. **语音输入体验**：麦克风按钮是否能实时把语音转成文字填进输入框，转录过程中用户能看到
   实时文字更新（不是录完一段才整体填入），且转录结果可编辑后再发送。
6. **多轮上下文**：连续对话时，agent 是否真的记得前几轮说了什么（"重试一下"、"再详细
   点"这类追问不需要用户重新提供背景）。
7. **错误处理透明度**：工具调用失败、模型调用失败时，界面是否如实展示失败（不是静默卡住
   或者装作没事发生）。
8. **消息呈现质量**：代码块、markdown、图片是否被正确渲染（不是原始文本或裸 URL）。
9. **控制感**：用户能否在 agent 还在跑的时候看到"现在在做什么"（状态 chip/进度指示），
   即使做不到"中途打断"，至少要让用户知道系统没有卡死。
10. **整体连贯性**：界面上没有假按钮（点了没反应或报错）、没有死链接、没有明显与其余部分
    风格不一致的孤岛组件。

## 打分纪律

- **不能因为"接近了"就给满分**：某一项如果本质上还是 mock/占位，即使视觉上很像，也只能
  给 0-0.3 分，不能因为"看起来对"而放宽。
- **每次迭代后，评分人（我）必须用真实浏览器在 devapp 或本地预览环境实际操作一遍**，不能
  只看代码 diff 就打分——这是本仓库反复强调的"证据"纪律的延伸。
- 低于 10 分，继续迭代；迭代方向从最低分的维度开始优先修。
- 达到 10 分后再发布到 devapp，且发布后必须再用真实浏览器验证一遍（生产环境的行为不能
  假设等同于本地/预览环境）。

## 已知的结构性限制（评分时纳入考量，不是借口）

- 工具调用能力目前的范围 = 组织已导入的 skill 集合（gpt-image-2/web-design-engineer/
  beautiful-article/web-video-presentation 等），不是无限的通用代码执行/文件系统访问。
  第 3/4 项的评分标准是"agent 是否真的、透明地使用了这个范围内的能力"，不是"能不能做
  Claude Code 能做的所有事"。
- 语音转录用浏览器原生能力（如 Web Speech API）实现，不需要额外的后端 ASR 服务——如果
  浏览器/网络环境不支持，需要有清晰的降级提示，不能静默失败。
