# 静态痕迹 ≠ 动态事实

> 2026-08-09，本仓在**一天之内**因为同一个错误栽了四次。四次表面上毫无关系，
> 直到 rev-uiux 在一条跨会话消息里把它们归并成一句话：
>
> > **用一个静态痕迹（worktree / 代码注释 / 分支存在）去推断一个动态事实
> > （谁还活着 / 现状如何）。**
>
> 这份文件记录那四次，以及为什么这个错误特别难自己发现。

## 那一天的四次

| # | 读了什么静态痕迹 | 推断出的"事实" | 真相 |
|---|---|---|---|
| 1 | `core-loop.spec.ts` 的注释「今天没有任何产品路径造得出一个议程环节」 | 该能力对用户不可达 | 早已修复（#627/PR #645）。同一批还有两条（#552、#652），**三条全部过期** |
| 2 | `chat-main-fidelity-rubric.md` 文件存在（在某条分支上） | 判据是可用的权威 | 它**不在 main 上**。引用它的 CLR 标准在 main 上 ⇒ 从 main 出发的人读不到判据 |
| 3 | `/private/tmp/wsx-660` worktree 还在 | 这些 docker 栈有主 | 拥有它的 subagent 早已被 `TaskStop` 杀掉。`sweep-docker` 因此报「0 个孤儿」，而当时有 17 个栈在跑 |
| 4 | 评分记录里写了 `scored_sha` | 分数量的是这棵树 | 那些 SHA **无一是 `origin/main` 的祖先**。十轮迭代、十次评分，全部发生在 main 上不存在的树里 |

## 为什么这个错误特别难发现

### 1. 痕迹越诚实，越像权威

第 1 次里那三条注释写得**极其诚实、极其具体**——点名了表、点名了缺什么、还写了
"缺口随 #493 上报"。正因为具体，读的人（coord-main）没有产生任何怀疑，直接把它们当证据
写进了标准文档、issue 正文、PR 描述、以及派给评分员的任务书——**一天之内把一个早已修好的
缺口复述成"现状"四次**，差点让评分员据此把三个可用的维度打成 0 分。

**诚实的过期陈述比含糊的陈述更危险。**

### 2. 没有任何门控会因为它过期而变红

注释不参与断言，测试照样绿。worktree 存在性是真的。文件在分支上是真的。SHA 字段填了是真的。
**每一处静态痕迹本身都没说谎——它们只是在描述一个已经过去的时刻。**

本仓的「同一事实不得声明在两处」防的是**两份副本互相漂移**，那还有得比对。
这一类错误连第二份副本都没有，无从比对。

### 3. 同一个文件可以自相矛盾而无人察觉

`fullstack-smoke-fixture.ts` 第 82 行已经改对了（「#552 补的就是那条路径」），
而 121/148/199 三处仍是旧断言。**同一个文件里，一半更新了一半没有。** 读到哪一半，
取决于你先 grep 到哪一行。

## 纪律

### 判断"现在是什么状况"，读会随状况改变的信号

| 你想知道 | ❌ 不要读 | ✅ 要读 |
|---|---|---|
| 某条产品路径存不存在 | 代码注释、issue 正文的叙述 | grep 真实 controller/路由/契约实现；`gh issue view N` 看是否 CLOSED；`gh pr list --search N --state merged` |
| 某个缺口还在不在 | 「已知缺口」清单、TODO | 同上三步。清单只用来找线索，不用来下结论 |
| 某段代码在不在 main | 文件在你的工作区里存在 | `git ls-tree origin/main -- <path>`；`git show origin/main:<path>` |
| 某次测量量的是哪棵树 | 记录里的 SHA 字段 | `git merge-base --is-ancestor <sha> origin/main` |
| 某个 agent / 栈还活不活 | worktree 或进程痕迹还在 | 心跳、lease、owner label —— **痕迹不是心跳** |

### 三条可操作的习惯

1. **引用别人的结论时，标注它是转述还是自己核的。** rev-uiux 在报告里主动写「这条是转述
   coord-main 的 grep 结论，我没亲自 grep，请下一轮评分员复核，别让它变成下一条过期断言」
   ——这一句挡住了第五次。
2. **活的数字要带时间戳。** 「14 个栈」和「17 个栈」都是对的，只是差 14 分钟。
   引用一个会变的量却不写观测时刻，等于制造下一条过期断言。
3. **写「当前缺口」类断言时，旁边写上它依据的 issue 号。** 这样 issue 关闭时有一条可追的
   线索。（不能自动同步，但至少可查。）

## 已落地的机械门（能覆盖的部分）

- **CLR G2**：评分后 watch 路径有改动 ⇒ 分数过期记 0
- **CLR G5**：`scored_sha` 不是 `origin/main` 的祖先 ⇒ 记 0（对应第 4 次）
- **CLR G6**：证据必须结构上可解析 ⇒ 挡住手写假锚点
- **CLR 队列门**：`blocking_issues` 里出现已 CLOSED 的 issue ⇒ 当场红（对应第 1 次的下游后果）

⚠ **覆盖不到的部分要诚实**：散文里的过期断言（issue 正文、代码注释）没有门能自动抓，
只能靠上面那三条习惯。`sweep-docker` 的归属推断问题登记在 #841，修法方向是**让归属可证明
（label + lease）而不是可推断**——不要用启发式（"超过 N 小时算孤儿"），那会误伤长任务，
且违反 `agent-resource-cleanup-sop.md` 已有的硬规矩。

## 第 5 次（2026-09-06）：`git log` 说改动在 main 上，说明不了跑着的容器是哪一版

`docker compose up -d` 对带 `build:` 的服务**只在镜像不存在时**才构建。于是
`apps/skill-sandbox` 的镜像自 2026-08-21 首次部署起就冻在那一版，之后所有源码改动
（预装库、CJK 字体……）一次都没上过 devapp——而每一轮部署都是绿的，healthz 一直 200。

骗人的痕迹是**最有说服力的那种**：`git log` / `merge-base --is-ancestor` 都如实显示
改动在 main 上；PR 全绿；部署脚本跑完没报错。这些都是真的，它们只是**都不回答**
「此刻那个容器里跑的是哪一版代码」。用户侧的症状因此与代码完全对不上：API 是新的、
按新 SKILL.md 教模型 `require('@pdf-lib/fontkit')`，沙箱是旧的、根本没这个包。

**该读的动态信号**：问跑着的容器本身——`docker exec <容器> node -e "require.resolve('X')"`、
`stat` 那个该在的文件。部署脚本现在每轮都这么问一次，缺了就红退
（`.harness/scripts/vm/deploy.sh` 第 3 步，门控见 `deploy-image-freshness.test.ts`）。

⚠ 一并记住这条的下游形态：**排障时先确认"跑着的是哪一版"，再怀疑代码**。这次先花了
一轮去查字体/编码，而根因是那份代码压根没上线。
