# 反馈闭环验收手册（前端用户 × 后台管理员）

> **这份文档给谁**：要亲手走一遍「用户提了意见 → 最后用户收到回音」全过程的人。
> 需要**两个角色配合**：一个普通用户（前台），一个平台管理员（后台）。
> 一次完整走查约 **25–40 分钟**（不含等 GitHub 对账的 2 分钟轮询）。
>
> 这不是设计文档，是**验收清单**：每一步都有「你应该看到什么」，看不到就是没通过。

## 0. 这条链路到底是什么

```
① 用户在产品里提反馈
        ↓
② 管理员在后台分诊 ——转「已进入迭代」时自动建 GitHub issue
        ↓                                   ↘
③ 管理员把它深化成设计方案（PM 设计工作台）   ④ 研发在 GitHub 上做完、关掉 issue
        ↓                                   ↙
⑤ 推送到收件箱 → 用户收到「已生成设计方案」邮件
        ↓
⑥ 定时对账（每 2 分钟）发现 issue 关了 → 状态自动转终态 → 用户收到「状态已更新」邮件
```

**闭环的定义**：用户不需要追问，就能通过**邮件**和**「我的反馈」列表**知道自己那条意见的下落。
中间任何一步断了，用户端的表现都是同一个——石沉大海。所以这份验收是**端到端**的，
不能只验单点。

## 1. 开始之前

### 1.1 两个账号

| 角色 | 需要什么 | 在哪 |
|---|---|---|
| **前台用户** | 一个能登录产品的普通账号，**邮箱必须是你收得到信的真实地址** | 产品任意页面 |
| **平台管理员** | 平台后台权限 | `/platform-admin` |

⚠ 用户账号的邮箱如果是假的，第 5、6 步的邮件你永远等不到，而界面上**不会报错**
（发信是 best-effort，失败只进服务端日志）。这是本手册最容易踩的坑，放在最前面。

### 1.2 先确认这个部署真的能发信（管理员做，2 分钟）

别等走到第 5 步才发现发不出去。

1. 管理员进 **`/platform-admin/ops-status`（运营状态）**。
2. 找到「测试邮件」一栏，填**你自己的收件地址**，点发送。
3. 期望：界面显示已发送，**并且你的邮箱真的收到了**。

> 只看界面显示「已发送」不算通过——那只说明请求发出去了。**以收件箱为准。**

收不到就先解决投递问题（发信通道配置、域名、垃圾邮件箱），再往下走。

### 1.3 确认 GitHub 集成配好了

第 2 步会真的去建 issue。没配好会**分诊失败**（这是刻意的 fail-closed：
宁可分诊报错，也不让「状态改了但 issue 没建」这种没人会去核实的假象留在系统里）。

---

## 2. 逐步走查

### 步骤 1 · 用户提一条反馈

**谁做**：前台用户

1. 在产品里点反馈入口，打开反馈对话框。
2. 填：
   - **类型**：选「缺陷」或「需求」。建议**选「需求」**——它后面能被深化成设计方案，走得通全程。
   - **标题**：写成你能一眼认出来的，比如 `验收走查-0907-导出PDF`。
     ⚠ 标题会**原样出现在邮件主题里**，这是你后面在收件箱里认出它的唯一线索。
   - **详情**：随便写，但写具体点，第 3 步 AI 深化时吃的就是这段。
   - **附件**（可选）：传一张图。传了的话第 2 步要额外验证它有没有跟到 GitHub 上。
3. 提交。

**你应该看到**：提交成功的回执，且这条出现在「我的反馈」列表里，状态是 **`待处理`**。

**记下**：这条反馈的标题。后面每一步都靠它对账。

---

### 步骤 2 · 管理员分诊，并建 GitHub issue

**谁做**：平台管理员

1. 进 **`/platform-admin/inbox`（运营收件箱）**。
2. 找到刚才那条反馈（来源是「反馈」）。
3. 把状态转到 **`已进入迭代`**。

**你应该看到**：
- 状态变成 `已进入迭代`；
- 这条反馈上出现 **GitHub issue 链接**，点开是真实存在的 issue；
- issue 正文里有反馈的标题和详情；
- 如果第 1 步传了图，**图片也在 issue 正文里**
  （图是重新上传到 GitHub 的——产品内部的附件 URL 需要鉴权，GitHub 抓图是匿名的，抓不到）。

**同时，用户那边应该收到一封邮件**：
> 主题：`你的反馈《验收走查-0907-导出PDF》状态已更新为「已进入迭代」`

⚠ **这封邮件是 best-effort**：状态已经落库之后才发，发失败只记日志、不回滚状态。
所以「状态变了但没收到邮件」是**发信问题**，不是分诊问题——回到 §1.2 查投递。

#### 这一步的几个边界，值得顺手验

| 试什么 | 应该发生什么 |
|---|---|
| 把状态从 `已进入迭代` 退回 `待处理`，再转回 `已进入迭代` | **不会再建第二张 issue**（已经有 issue 了就不建） |
| 状态转到 `已修复` / `不做` | GitHub 上那张 issue 跟着**关闭** |
| 再转回 `待处理` / `已进入迭代` | issue 跟着**重新打开** |

> 后三条是 best-effort：GitHub 调用失败只记日志，反馈状态照样生效
> （issue 的开关从属于反馈状态这个已落库的事实，不是反过来）。

---

### 步骤 3 · 管理员把反馈深化成设计方案

**谁做**：平台管理员

1. 在收件箱里选中这条反馈，点 **「深化」**。
2. 系统用 AI 把这段用户原话结构化成设计草稿。
3. 到 **`/platform-admin/feedback-drafts`（反馈草稿）** 看结果，可以继续改。

**你应该看到**：草稿里保留了用户原话的意图，字段被拆开了（背景 / 目标 / 验收标准之类）。

⚠ 这一步依赖 AI 模型。**没配模型的部署走不到这里**——界面会明确告诉你是模型没配置，
不会假装成功。

---

### 步骤 4 · 管理员在 PM 设计工作台把方案做出来

**谁做**：平台管理员

1. 进 **`/platform-admin/design-workbench`（PM 设计工作台）**。
2. 打开由这条反馈生成的设计项目。
3. 在「设计协作」对话里描述你要的界面，AI 生成原型画布。
4. 满意之后，可以导出设计文档（`.md`）、原型规格（`.json`）、当前页 PNG。

**你应该看到**：画布上出现多页原型，页与页之间有跳转关系；切到「预览」点按钮真的换页。

> 这一节是设计台本身的能力，不是闭环的必经环节——但它是**用户那条意见变成具体东西**
> 的地方，验收时值得看一眼「用户说的和画出来的是不是一回事」。

---

### 步骤 5 · 推送到收件箱 → 用户收到「已生成设计方案」邮件

**谁做**：平台管理员

1. 在设计工作台里，把这个设计项目**推送到收件箱**。
2. 系统会给它一个**收件箱编号**，形如 `D-2`。

**你应该看到**：
- 收件箱里多了一条「设计方案」来源的条目，编号就是那个 `D-x`；
- 原来那条反馈上出现关联标记「已生成 D-x」。

**用户那边应该收到第二封邮件**：
> 主题：`你的反馈《验收走查-0907-导出PDF》已生成设计方案 D-2`
> 正文里有设计方案名字和收件箱编号。

**用户侧验证**：让用户按邮件里的编号 `D-2` 去收件箱找，**要能找到**。
编号对不上，或者找不到，这一步就是没通过。

⚠ 重复推送**不会重复发邮件**：只有反馈第一次关联上设计方案时才通知。
反复点推送只会更新那条收件箱条目的时间，这是刻意的（幂等）。

---

### 步骤 6 · 研发关掉 GitHub issue → 状态自动回流 → 用户收到终态邮件

**谁做**：研发（或你自己在 GitHub 上手动关）

1. 到步骤 2 建的那张 GitHub issue，**关闭它**。
   - 用 **`completed`**（正常完成）关 → 反馈应转 **`已修复`**
   - 用 **`not planned`**（不做）关 → 反馈应转 **`不做`**
2. **等最多 2 分钟**（后台每 2 分钟轮询一次 GitHub）。

**你应该看到**：
- 后台里那条反馈的状态**自己变了**，操作人显示为系统对账（不是某个具体的人）；
- **用户收到第三封邮件**：`你的反馈《…》状态已更新为「已修复」`；
- 用户在「我的反馈」列表里看到的也是新状态。

#### 这一步有一条重要的并发保护，值得专门验一次

**试**：在 issue 关闭之后、2 分钟轮询到之前，管理员手动把这条反馈改成 **`不做`**。

**应该发生**：轮询**不会覆盖**你这次手动判断，也**不会**多发一封邮件。

> 为什么专门验它：这是真实存在过的 bug 形态——轮询先读一次快照，中间隔着一次 GitHub API
> 调用，写回时用旧快照覆盖掉更晚发生的人工判断，还会留下一行 `fromStatus` 与数据库对不上的
> 假历史。现在「当前状态必须仍是读到的那个」被焊进了同一条 UPDATE 语句里。
> **这个窗口不是理论上的**，值得你亲手试一次。

## 3. 验收判定表

全部打勾才算闭环通过。**任何一条没勾，写清楚卡在哪一步**，不要"大致跑通了"。

| # | 验收项 | 谁验 | 通过标准 |
|---|---|---|---|
| 1 | 测试邮件收得到 | 管理员 | 真实收件箱收到，不是界面显示已发送 |
| 2 | 反馈提交成功 | 用户 | 「我的反馈」里状态 `待处理` |
| 3 | 分诊建了 issue | 管理员 | issue 链接可点开，正文有标题和详情 |
| 4 | 附件跟到了 GitHub | 管理员 | issue 正文里图片能显示（若第 1 步传了图） |
| 5 | 状态变更邮件 | **用户** | 收到，主题里有**自己填的标题** |
| 6 | 不重复建 issue | 管理员 | 来回切状态只有一张 issue |
| 7 | issue 开关跟随状态 | 管理员 | 转终态 issue 关；转回去 issue 开 |
| 8 | 深化出草稿 | 管理员 | 草稿保留了用户原意 |
| 9 | 设计方案推送 | 管理员 | 收件箱有 `D-x`，反馈上有关联标记 |
| 10 | 设计生成邮件 | **用户** | 收到，编号与收件箱里的一致 |
| 11 | 用户按编号找得到 | **用户** | 在收件箱里按 `D-x` 找到那条 |
| 12 | 关 issue 后状态回流 | 管理员 | ≤2 分钟自动转终态，操作人是系统 |
| 13 | 终态邮件 | **用户** | 收到第三封 |
| 14 | 并发不覆盖人工判断 | 管理员 | 手动改判后轮询不覆盖、不多发邮件 |

> 注意第 5、10、11、13 这四条**必须由用户角色本人验**，管理员代看不算——
> 闭环的定义就是"用户不追问也知道下落"，验收人替他看了，那就没验到这件事。

## 4. 常见"看起来坏了其实没坏"

| 现象 | 多半是什么 | 怎么区分 |
|---|---|---|
| 状态变了但没收到邮件 | **发信通道**，不是状态机 | 后台看得到新状态 ⇒ 状态机是好的；回 §1.2 发测试邮件 |
| 分诊直接报错 | GitHub 集成没配好 | 这是**刻意的 fail-closed**，不是 bug——见步骤 2 |
| 关了 issue 状态没变 | 还没轮到（≤2 分钟）／这条反馈没有 issue | 先等满 2 分钟；再确认步骤 2 真的建了 issue |
| 深化没反应 | 这个部署没配 AI 模型 | 界面会明说是模型没配置 |
| 反复推送没再发邮件 | **正常**，幂等 | 只有首次关联才通知 |

---

## 5. 这份手册没覆盖的（登记，别当成已验）

- **发信失败没有重试**：邮件是 best-effort，失败只进日志，没有持久 outbox。
  用户那边的表现就是"没收到"，且系统不会自己补发。（已登记为已知限制）
- **GitHub 同步失败没有重试调度**：反馈状态与 issue 开关可能短暂不一致。（同上）
- **多语言 / 邮件外观**：本手册只验内容对不对，不验排版。
- **权限边界**：本手册假设两个角色的权限都是配好的，不验越权。

---

## 6. 走完之后

把第 3 节那张表填好——**打勾的写"通过"，没打勾的写清楚卡在第几步、看到了什么**。
"基本能跑"不是验收结论；每一条要么通过，要么有一个具体的卡点。
