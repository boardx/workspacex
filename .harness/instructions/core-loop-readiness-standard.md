# 核心闭环就绪度 CLR —— 全仓统一衡量标准

> 人类 2026-08-09 指令："你要代表我有一个全面的解决方案，你要统一所有的 agent 的工作，
> 要有一个统一的衡量的标准"。issue #814。
>
> **这份文件是"我们离交付还差多少"这件事的唯一权威判据，也是所有 agent 的唯一取活口。**
> 做任何 chat / agent / skill / 录音相关的活之前，先跑一次 `pnpm harness readiness`。

## 它不是第四套评分卡

本仓已经有三套尺子在量 chat，而 `chat-ux-acceptance-criteria.md` 自己就逐字禁止过合并
评分卡（合并会制造"到底哪条判据说了算"的新漂移）。**这条禁令保留**。

本文件**一个既有判据都不复制**。它采用本仓已有的
`feature_list.json`（权威）→ `active-features.json`（脚本派生只读视图）同一模式：

| 层 | 放什么 | 谁写 |
|---|---|---|
| **判据** | 各 rubric 文件自己的维度定义 | 人类 / 评分卡作者 |
| **分数记录** | `.harness/state/core-loop-readiness.json`（分数 + 实测 SHA + 评分人 + 证据） | 该 track 的授权评分人 |
| **总分盘** | `pnpm harness readiness` 输出 | **脚本派生，禁止手写** |

## 四条 track

| track | 问的问题 | 判据权威 | 授权评分人 |
|---|---|---|---|
| **R** 可达性 | 一个真实新用户，**不靠种子脚本**，能不能走到这个能力？ | 本文件下方 R1-R10（**唯一新增的判据**） | `rev-e2e` |
| **B** 行为体验 | 用起来像不像 Claude Code？ | `.harness/instructions/chat-ux-acceptance-criteria.md` 十项 | `rev-e2e` |
| **V-D** 项目对话保真 | 长得像不像原型？ | `.harness/rubrics/chat-main-fidelity-rubric.md` D1-D10 | `rev-uiux` |
| **V-P** 个人对话 | 同上（个人对话侧） | 同文件 P1-P10 | `rev-uiux` |

## 合格门槛：CLR ≥ 9（人类 2026-08-09 裁决，#831）

**不再要求 = 10。** 原本的 10 分门在结构上不可达：`chat-main-fidelity-rubric.md` 的 D3/D4
各有一条子要求（线程「负责 agent」、面包屑「项目阶段/周次」）指向**产品域里根本不存在的
概念**——满足它们得先做一次产品设计并建模，而它们服务的只是一行副行和一行面包屑。

同一次裁决已把那两条子要求从判据中移除，"满分"因此重新可达；门槛降到 9 是**额外**的一分
容错。两者叠加**不是双重放宽**——四条 track 每条都是 0/1 逐维判定 + 硬门 H1-H4，
要求四条同时 ≥9 依然很硬。

> ⚠ 一个**不可能达到**的满分比一个略低但可达的门槛更危险：所有人会默认"反正到不了"，
> 门就废了。这条推理记在这里，是为了让后来改门槛的人知道它当初为什么不是 10。

门槛的单一事实源是 `core-loop-readiness.ts` 的 `PASS_THRESHOLD` 常量，不是本文件这段话。

## 聚合规则：R 是天花板，不是加数

```
CLR = min( R , mean(B, V-D, V-P) )     达标 ⟺ CLR ≥ PASS_THRESHOLD(=9)
```

**用户走不到的地方，做得再好也等于 0。** 可达性 3/10 时，哪怕体验和视觉都满分，总分
也只能是 3/10。

这条规则的唯一目的是让**"刷分"和"修对的东西"变成同一件事**。四项平均会让"一个漂亮
但走不到的功能"拿高分——那正是今天的处境。

> ⚠ 诚实标注：这条公式是 #814 引入的**设计决定**，不是从既有文档推导出来的（既有三份
> rubric 都没规定彼此如何合成，这正是它们各说各话的原因）。要改权重或改合成方式，改
> `.harness/scripts/lib/core-loop-readiness.ts`，不要在别处再写一份。

## 为什么必须有 track R —— "12/12 全绿"与"用户说不能用"同时为真

`core-loop.spec.ts` 12/12 绿，同一天人类在 devapp 实测录音不可用。**两者都不假**：
八步闭环是在"种子脚本已替用户创建好前置数据"的世界里绿的。规格自己的注释逐字承认过
这些让步（引用为证，不是推测）：

### ⚠ 本节初版引用的三条"证据"全部是过期的（#823，2026-08-09 当天发现并更正）

本标准初版在这里列了三条 `core-loop.spec.ts` 注释作为「用户走不到」的硬证据。
**核实后：三条全部已失效**——它们写的时候是真的，之后都被修了，注释没跟着改：

| 初版引用的注释 | 真实情况 |
|---|---|
| 「今天没有任何产品路径造得出一个议程环节」 | ❌ 已失效。`POST /workshops/:workshopId/agenda-segments`（`project.controller.ts`）；#627 已关闭，PR #645 已合并 |
| 「被挂的那个 skill 由夹具种成『已启用』」（暗示无产品路径） | ❌ 已失效。`POST /skill-versions/:versionId/review`（`skill-review.controller.ts`）；#552 已关闭，PR #584 已合并 |
| 「契约里没有写授权格子的操作」 | ❌ 已失效。`setConsentDecision` / `POST /recording/consent/decisions`，登记在 `KNOWN_CONTRACT_GAPS.C_REC_6`；#652 已补 |

**track R 这个概念仍然成立**——种子预置确实会掩盖不可达性，这一点没有变。
错的是初版拿来支撑它的那三个例子，以及据此播下的 `blocking_issues`。

### 由此得出的一条纪律（比上面那三个例子重要）

> **判断「某条产品路径存不存在」，不得以代码注释为准。**
> 必须：① grep 真实的 controller / 路由 / 契约实现；② `gh issue view N` 确认相关 issue
> 是否已 CLOSED；③ `gh pr list --search N` 确认有没有已合并的修复。
> 三样都做完才算数。

为什么这条要写进标准：注释描述的是**写它那一刻**的世界，而且它没有第二份副本可比对、
也没有任何门控会因为它过期而变红（测试照样绿，注释不参与断言）。它写得越诚实越具体，
读起来就越像权威——2026-08-09 当天，三条早已修好的缺口就是这样被复述成"现状"四次的
（写进本文件、写进 #814 正文、写进 PR #819 描述、写进派给评分员的任务书）。

**更可靠的证据源**：`packages/contracts/src/*.ts` 里的 `KNOWN_CONTRACT_GAPS` 常量
（如 `C_REC_1`…`C_REC_6`）——它有稳定 ID、与契约同处、被补上时会同步更新，
比散落的注释可信得多。

### 原本要说的事（依然成立）

`core-loop.spec.ts` 12/12 绿，同一天人类在 devapp 实测录音不可用。八步闭环跑在
"种子脚本已替用户创建好前置数据"的世界里，而**没有任何东西把这些让步汇总成一个
看得见的数字**，于是"绿"持续掩盖"用户走不到"。track R 的全部作用就是让这些让步
**可计数**——由评分员按 R1-R10 实测，不是从注释里读。

### track R 真实用户可达性

判据：**把种子脚本给的前置数据全部拿掉，一个刚注册的真实用户能不能靠产品自己的界面
走到这一步。** 每维 0 或 1 分，没有 0.5。

| # | 维度 | 给 1 分的判据 |
|---|---|---|
| R1 | 注册成为管理员 | 空库注册第一个用户 → 自动成为管理员，无需任何种子 |
| R2 | 新增 Agent | 管理员在界面上新增 agent，刷新后仍在 |
| R3 | 新增 Skill | 界面上新建 skill 草稿 → 列表可见 → 详情可读 |
| R4 | 新增 canvas 模板 | 界面上新建模板 → 刷新仍在 |
| R5 | 登录 / 登出 / 会话恢复 | 无种子依赖 |
| R6 | 会话 CRUD + 发消息 | 新建 / 改名 / 删除 / 发消息，刷新后一致 |
| R7 | 录音 → 转录归属会话 | **用户自己新建的线程**能录音（不是种子预置的那条）——含授权矩阵有产品写入路径 |
| R8 | 挂载并真正使用**自己建的** skill | 自建 skill 能走到"已启用"并在会话里挂上生效（不是种子种成 enabled 的那个） |
| R9 | **自己建的** agent 真的执行并回复 | 自建 agent 能发布 → 在会话里发消息 → 产出恰好一条回复（不是种子种的可运行 agent） |
| R10 | 真正**使用**一个 canvas 模板 | 含"用户能造出一个议程环节"——今天这条完全没有产品路径 |

评分方法：**跑 `core-loop.spec.ts` 的 `core-loop-empty-db` project（不吃种子那个），
或在 devapp 上用一个全新注册的账号手工走一遍。** 用吃种子的 `seeded` project 打出来的
分不作数——那正是这条 track 存在的原因。

## 四道机械门

分数记录是手写的，所以每一条都必须被机械检查。四道门的实现在
`.harness/scripts/lib/core-loop-readiness.ts`，**每一道在 `.test.ts` 里都配了反证**
（实测过"把这道门拆掉，测试会红"）：

| 门 | 规则 | 为什么 |
|---|---|---|
| **G1** | 未评分记 0，不记"未知" | 空着不等于满分 |
| **G2** | 评分 SHA 之后该 track 的 `watch` 路径有改动 ⇒ 分数过期 ⇒ 记 0 | 「grep 不会告诉你树是旧的」——6 轮前测出的分在今天的 main 上没有证明力 |
| **G3** | `scored_by` 必须 ∈ `allowed_scorers` 且 ≠ `implemented_by` | 自评的分数在语义上自相矛盾（同 `review-decision-model.ts` 对 `reviewer === producer` 的判法） |
| **G4** | `evidence` 为空 ⇒ 记 0 | 「没有证据 = 没有完成」在体验层的延伸 |

### `--strict` 只对结构问题退非 0，分数低不退

```bash
pnpm harness readiness            # 渲染看板（人看的）
pnpm harness readiness --strict   # doctor / CI 用
```

**CLR = 0 是事实，不是故障，不该把 CI 打红**——红了就会有人为了让 CI 绿而去改分数，
那正是这套机制要防的。`--strict` 只在**记录本身自相矛盾**时退非 0（自评、越权评分人、
分数越界），因为那让 CLR 这个数字失去意义。

## 统一队列 —— 所有 agent 的唯一取活口

每条 track 在 JSON 里声明 `blocking_issues`。`pnpm harness readiness` 把它们排成一条队：

```
R（天花板）的阻塞项  →  其余 track 按实际得分升序  →  去重
```

**R 的阻塞项永远在最前**，因为其余 track 修到满分也抬不动总分。

### 对所有 agent 的硬性要求

1. **开工前先跑 `pnpm harness readiness`，从队列顶部取活。** 不在队列上的活不占工时
   （沿用 `core-loop-commitments.json` 已有的 `scope_rule` 精神）。
2. **例外要说出口**：确有理由做队列外的活（安全修复、阻塞别人的基建、人类直接指派），
   在对应 issue 里写一句为什么，不要默默做。
3. **不要给自己打分。** 实现者改不了自己被评那条的分数字段，G3 会当场红。
4. **改了别人 track 的 `watch` 路径 = 让那条分数过期**，这是正常的，不是你的错，但
   要知道下一轮评分员得重跑。别为了保住分数而回避改代码。
5. **一条 track 的判据有异议**，去改它自己的 rubric 文件并说明，**不要**在这里加第二套。

## 这套标准的第一个输出很难看，这是对的

首次运行结果：**CLR = 0 / 10**。四条 track：B 与 R 从未评分（G1）；V-D/V-P 最近一次
评分在 SHA `d53c84ca`，其后 chat 组件改过 5 个文件（G2 过期）。

含义**不是**"产品一无是处"，而是：**我们其实不知道自己在哪，因为没有人在当前 main 上
量过。** 把"不知道"从隐性变成显性，是这套机制的第一个交付物——第一个行动项因此自动
成为：**四条 track 在同一个 SHA 上做一次基线评分**。
