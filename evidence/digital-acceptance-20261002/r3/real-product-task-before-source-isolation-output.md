# 团队协作工具下一迭代 PRD 草稿（合成验收输入）

## 1. 用户问题与目标定义

### 1.1 用户问题陈述
*   **邀请障碍**：首次用户在新手阶段难以找到邀请队友的入口，导致协作流转受阻。[来源：P1]
*   **信任顾虑**：部分首次用户对资料权限存在担忧，可能影响其使用意愿。[来源：P1]

### 1.2 业务/产品目标
在 8 人日的资源约束下，通过改善新手引导体验，降低首次用户在“邀请队友”和“理解权限”环节的摩擦。
*注：受限于现有数据，本次目标不包含任何留存率或付费转化率的改善承诺。* [来源：P2, P3]

---

## 2. 事实、假设与未知

| 类别 | 描述 | 来源 |
| :--- | :--- | :--- |
| **事实** | 8 名首次用户中 6 名找不到邀请入口，3 名担心权限。 | P1 |
| **事实** | 100 个新账号中，42 个建项目，18 个邀请队友。 | P2 |
| **事实** | 本迭代最多 8 人日。A(3人日)、B(3人日)、C(8人日)。工时为初步估计。 | P3 |
| **事实** | 只有 2 名管理员提出批量导入需求。 | P3 |
| **事实** | 权限文案须由安全负责人审阅。 | P3 |

| **假设** | 解决权限担忧能提升用户建项目后的安全感。 | P1 推断 |
| **未知** | 样本外用户的实际痛点分布（P1为自愿报名样本，不能代表全体）。 | P1 |

## 3. 方案比较与优先级建议（含 RICE 缺失说明）

### 3.1 候选方案评估
*   **方案 A：改善邀请入口**（估计 3 人日）。针对 6/8 用户找不到的痛点，且行为日志显示 100 个账号中仅 18 个完成邀请，存在明显漏斗流失。[P1, P2, P3]
*   **方案 B：资料权限说明**（估计 3 人日）。针对 3/8 用户的信任顾虑。需跨部门依赖（安全负责人审阅）。[P1, P3]
*   **方案 C：管理员批量导入**（估计 8 人日）。仅 2 名管理员提出，且耗满全部迭代预算。[P3]

### 3.2 RICE 框架应用限制声明
由于缺乏总体触达数据（Reach）、缺乏证明改善幅度的基线数据（Impact），以及 P1 样本不具备统计代表性（Confidence），**严禁编造 RICE 分数**。以下采用定性逻辑进行优先级排序。

### 3.3 优先级建议与取舍
*   **建议纳入范围：方案 A + 方案 B**。总估计工时 6 人日，低于 8 人日上限，留有 2 人日缓冲以应对安全审阅等不确定性。
*   **建议排除（非目标）：方案 C**。理由：1) 仅 2 名管理员提出，受众极窄；2) 估计耗时 8 人日，占满全部预算，无任何容错空间；3) 无法同时解决更广泛的首次用户引导问题。
*   *注：此为建议优先级，最终是否采纳需由团队及审批者决定，我不代为批准。*

## 4. 范围与非目标

*   **范围内 (In Scope)**：优化新用户界面的邀请队友入口可见性；增加资料权限的清晰说明文案。
*   **非目标 (Out of Scope / Non-goals)**：管理员批量导入功能（方案 C）；提升留存率或付费转化率（无数据支持，不作承诺）；重写底层权限架构。

---

## 5. 用户故事

*   **US-1 (对应方案 A)**：作为一名首次使用的用户，我希望能在显眼的位置找到“邀请队友”的按钮，以便我能快速开始团队协作。
*   **US-2 (对应方案 B)**：作为一名担心数据安全的用户，我希望在上传或共享资料前能看到清晰的权限说明，以便我知道谁能访问我的内容。

---

## 6. Given/When/Then 验收标准

### 6.1 US-1 验收标准（邀请入口）
*   **Given** 首次用户登录并进入新建项目页面，
*   **When** 用户寻找邀请队友的操作点时，
*   **Then** 页面上应存在符合设计规范的高亮/主操作级别的“邀请队友”入口，且点击后成功跳转至邀请流程。

### 6.2 US-2 验收标准（权限说明）
*   **Given** 用户在资料库或项目设置界面，
*   **When** 用户查看或更改资料共享状态时，
*   **Then** 界面应展示经安全负责人审阅通过的权限说明文案，清晰解释当前资料的可见范围。

---

## 7. 权限失败场景

*   **场景 1：文案未通过审阅**。若安全负责人在迭代结束前未批准权限说明文案，则方案 B 不得上线，相关 UI 保持原样，释放的 3 人日转入技术债清理或测试。
*   **场景 2：越权访问**。如果权限说明 UI 的变更意外导致前端鉴权逻辑被绕过（如错误提示暴露了无权限项目的元数据），必须立即阻断发布。

---

## 8. 依赖与风险

*   **依赖**：方案 B 强依赖于“安全负责人”的排期与审阅通过。[P3]
*   **风险 1（样本偏差）**：P1 数据来自 8 名自愿报名用户，不代表全体。改善入口后，实际大盘转化率提升幅度可能低于预期。[P1]
*   **风险 2（工时溢出）**：A 和 B 的 3 人日均为“初步估计”，若遇技术阻碍可能突破 8 人日总预算。[P3]
*   **风险 3（行为归因错误）**：P2 中 82 个未邀请账号的原因未知，可能并非因为“找不到入口”，而是“不需要邀请”。[P2]

## 9. 成功指标的定义及待测基线

*声明：由于 P2 明确指出无留存、付费数据，以下指标仅限行为漏斗，绝不宣称留存或付费改善。*

| 指标名称 | 定义 | 当前基线 (Baseline) | 目标值 |
| :--- | :--- | :--- | :--- |
| **新账号邀请转化率** | (发出邀请的新账号数 / 新建项目的新账号数) * 100% | 42.8% (18/42，依据P2) | 待上线后测量（建议提升，但不设虚假硬指标） |
| **邀请入口点击率** | 看到新入口的用户中点击的比例 | 未知（需埋点） | 待测 |
| **权限说明阅读/交互率** | 展开或悬停查看权限说明的用户比例 | 未知（需埋点） | 待测 |

*注：所有基线中标记为“未知”的项，必须在开发阶段补齐埋点，不能在发布后声称“已有提升”。*

## 10. 回滚方案

*   **触发条件**：上线后 48 小时内，若监控发现邀请流程报错率 > 5%，或权限说明引发大量客诉/安全漏洞。
*   **执行动作**：通过 Feature Flag（功能开关）一键关闭方案 A 和 B 的新 UI，恢复至上一版本状态。
*   **时限要求**：回滚操作需在触发条件满足后 30 分钟内完成。
*   **数据隔离**：回滚前产生的新版邀请记录需保留在数据库中，但前端不再展示新入口，确保数据不丢失。
