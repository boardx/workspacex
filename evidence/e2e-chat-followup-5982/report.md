## 诊断与修复

1. **刷新失败的主要延迟发生在脚本加载。** 原 trace 中聊天布局脚本约 27 秒，身份请求在 30 秒消息断言截止前才启动，200 响应晚于截止。不能据此判为会话锁死。登录与会话客户端从契约总入口导入 auth，带入无关注册表；现仅改为已有 `@repo/contracts/auth` 子路径，契约、会话锁、权限规则均保持。真实打包依赖图回归在旧实现红、新实现绿。
   开发根布局生成脚本从 12,061,746 降至 1,722,229 字节，契约模块 119 → 3。见 [体积证据](bundle-footprint.json)。这不是生产网络速度基准，也不承诺任意主机都能在同一时间内完成加载。
2. **“running 90秒”原报告归因不成立。** 原 trace 显示同一主 frame 途中离开本地站点，进入外站 nginx 欢迎页；导航发起者未确定，后续无应用权威状态，不能判 run 卡死。等待 helper 现在只接受同源页面中实际存在的 `ready/disabled` 状态，缺失属性不能成功，失败信息带当前 origin/path。
3. **多轮截图验证绑定真实两轮。** 用独立新线程，分别确认两轮 SSE `RUN_FINISHED`、权威 run 为 succeeded 且有结果消息，两次 run ID 不同；随后保留界面落定断言，确认第二轮 Markdown 标题和代码块可见，避免第一轮旧正文提前满足等待。见 [两次 run 的脱敏证据](two-run-evidence.json)。

原样独立诊断在修复前也曾 3/3 通过，故没有将重跑绿灯等同于修复。最终改动的独立审查未发现可操作问题。
