# Board Iteration 09 — AI/API/Chat/meeting-room evidence

Scope implemented in this branch:

- `@repo/contracts/whiteboard-operation` is the single versioned schema for human, service and AI actors, idempotent operations, revisions, audit events, event cursors, AI proposals, click-time rendered layouts, presenter state and pointer/room capability.
- `@repo/whiteboard-core` provides the shared operation kernel, preview/cancel/confirm proposal lifecycle, SHA-256 click-time layout verification, Chat artifact conversion and the presenter/follow/handoff state machine. Confirmed AI batches use one `WhiteboardCommandOrigin` transaction and one undo entry.
- `/v1/whiteboards/:boardId/operations` persists the collaboration update, receipt and event in one tenant transaction. `/events` exposes cursor-based subscriptions. Actor identity, delegated authority, tenant, role, revision and idempotency are checked fail closed.
- Non-human actors resolve from the server-owned `whiteboard_actor_identities` registry. Client-supplied role, scopes, model and skill are ignored; collaboration writes, operation receipts and events use the same resolved actor. The application role has read-only registry access. The controlled E2E owner seed creates the immutable test identity.
- PostgreSQL operation/event audit tables, AI proposals, room identities and presentation sessions are tenant-RLS forced. Proposal owner, request digest, expiry, base object digests and current revision are checked before an atomic confirm. Authorization runs before idempotent replay.
- Web adapters and reviewable UI cover proposal before/after preview, provenance, confirm/cancel, presentation/follow/free browse, meeting display reconnect/handoff and Chat artifact insertion. The handoff UI selects a target Board and world position; the server verifies artifact ACL/revision and recomputes the click-time Fabric layout hash.
- The full-stack Playwright spec named `AI clustering <=2 actions · chat fabric layout handoff · meeting room follow` uses separate owner, viewer and meeting-display principals. It is present for the main session to run against real API/PG/ObjectStore/browser services.
- `examples/board-api` contains a self-hosted curl payload and event subscription example.
