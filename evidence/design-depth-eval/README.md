# 设计工作台深度评测

人类 2026-09-24：「迭代十次全部做完，每次迭代完需要评测一次，找出十个问题解决修复。」

## 为什么要第二把尺子

对标评测（`evidence/design-parity-eval/`，42 条）在 R10 已经全部通过：它量的是「这项能力有没有」。
R10 收尾时自己登记了几处「有了，但不够用」的短板：批注只存在本机、导出的代码是静态骨架、编辑器里
看不到代码、原型里放不进一张真图片、幻灯片不能演示也导不出 PPT、变体没法提要求、详情页文件逼近 2000 行上限。
这把尺子把它们量出来。

- 检查：`apps/web/e2e/parity-eval/design-depth.eval.ts`（标题以 `[Vx.cy]` 开头）
- API 替身：`apps/web/e2e/parity-eval/depth-api.ts`（批注——语义对齐真实接口要的样子）
- 维度定义与打分：`apps/web/e2e/parity-eval/score.mjs` 的 `DEPTH_DIMENSIONS`（`--suite depth`）

## 它不量什么

1. **生成质量**（AI 画得好不好）。本容器没有真实模型凭据。要在真实模型车道上做同题盲评。
2. V9 是唯一不看界面的一维：它量代码规模，理由写在检查旁边——后面几轮都要往详情页上加功能，
   线划在 1500 行是给每一轮留余量，而不是等撞上仓库的 2000 行上限再拆。

## 规则

与对标评测相同：S0 冻结，之后只修评测自身的 bug 并在下面记账；实现某个目标 testid 的那一轮删掉
它的 `testid-gate: absent` 标注。每轮修掉的差距另写回归 e2e 进 `playwright.design-loop.config.ts` 车道。
每一轮两套评测一起跑：对标评测必须保持 10.0（不许为新功能拆掉旧能力）。

## 跑法

```bash
cd apps/web
PW_EXECUTABLE=/opt/pw-browsers/chromium-1194/chrome-linux/chrome npx playwright test -c playwright.parity-eval.config.ts
node e2e/parity-eval/score.mjs --suite depth --round S1   # → evidence/design-depth-eval/S1.md / S1.json
node e2e/parity-eval/score.mjs --round S1                  # 对标评测回归（应为 10.0）
```
