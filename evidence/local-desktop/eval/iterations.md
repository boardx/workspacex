# 本地版效率与质量迭代（#3749 续，2026-09-22 夜）

人类指令：一晚十轮，每轮实现→验证→评测→据数字找出下一轮的 10 个候选。交付一个效率与质量都更高的本地版。

## 度量
`scripts/local-bundle/eval-local.mjs`。速度指标：wall 中位、首块延迟、块/s、系统提示长度。

## 第 1 轮（模型预热 + 工具预算）

**取证**：记录代理拦在模型前，一次画布请求 25 519 字符 = 工具 schema 17 347（15 个工具）+ deepagents 基座 3 845 + 我们的提示 4 304 + 用户 23。
服务端：4 098 token，预填充 14.6 s。工具是最大单项（68%），不是我们的提示。
冷加载实测 11.7 s——用户的第一条消息在付这笔钱。

**改动**
1. `warmModel`：起栈后不 await 地发一次 1-token 请求，模型在用户看启动页时就位。
2. `tool_budget.py` + `DEEP_AGENT_EXCLUDED_TOOLS`：末位中间件按名剥掉工具（deepagents 的 FilesystemMiddleware/SubAgentMiddleware 是必需脚手架不能摘，只能从请求里过滤）。本地排除 grep / glob / delete / edit_file / task / spawn_async_task。未设环境变量 ⇒ 中间件根本不挂载，云端逐字节不变。

**数字**（canvas 套件，同机同模型）
| | 第 0 轮 | 第 1 轮 |
|---|---|---|
| wall 中位 | 67 s | **52 s** |
| 首块中位 | 12.9 s | 18.9 s（见下）|
| 围栏 | 5/5 | 4/5 |

**本轮暴露的更大问题**：31 次模型调用里 **15 次 `cached n_tokens = 0`**——前缀缓存完全没命中，整段提示重算（一次 6 653 token 的调用光预填充 18.3 s）。首块变差与围栏 4/5 都指向它和「工具仍可见导致模型绕 call_skill」。

## 第 2 轮（逐请求工具预算 + 评测口径换成低噪指标）

**取证**（记录代理，一次画像请求的真实轨迹）：
1. 模型臆造 skill 名 `create_user_profile_canvas` → 「未知技能」
2. 调 `list_org_skills` 查目录
3. 把画布委托给 `diagram-and-canvas` skill（整轮子调用，独立 system prompt）
4. 该 skill 回了一张 **markdown 表格，一个围栏都没有** → 这就是围栏 4/5 的那次
5. 收尾还有一次 grader 调用（`You are a grader…`，user 4 534 字符）

即：一张画布 = 5 次模型调用，其中两次纯绕路。而且子调用穿插在主对话之间，**把单槽 KV 缓存冲掉**，主对话下一次调用只能整段重算（`cached n_tokens = 0`）。

**改动**
- `configurable.excluded_tools`：API 逐请求告诉远端哪些工具本轮不挂。画布请求排除 `call_skill / list_org_skills / web_search / fetch_url`——画布是写围栏写出来的，没有 skill 能代劳，也不需要联网。
- `ToolBudgetMiddleware` 改为恒挂载，按「部署级 env ∪ 本轮 config」过滤；两者都空 ⇒ 请求原样透传。
- 评测加 `modelCalls` 列。理由：同一类提示的墙钟在这台机上从 26 s 摆到 149 s，用它判优劣是自欺；模型调用次数不受 CPU 负载影响。

**数字**：画布 5 次里 4 次实现零工具调用（第 1 轮是混合）。墙钟受 Laya 权重下载与 torch 推理争用，本轮不作数——第 3 轮空闲机器重测。
## 第 3 轮（不宣传不存在的工具 + 画布请求零工具）

**取证**：捕获的 system[0] 里有约 1 700 字符在教模型用 `confirm_task_intent` / `fill_run_params` / `choose_execution_option` / `browser_*`——**本地一个都没挂载**，末尾再补一句「这三个工具不可用」。自相矛盾的提示是 4B 乱走的主因之一。

**改动**
- `prompt_pruning.py`：按**句**剔除提到「本部署不存在的工具」的句子（句粒度不是段粒度：有一段把 `browser_navigate`（无）和 `fetch_url`（有）混在一起）。存活文本逐字节不变，不重写。deep-agent 提示 2 776 → 1 751 字符（−37%），矛盾消失。
- 工具预算支持 `"*"`：画布请求一个工具都不挂。画布是写围栏写出来的，工具只会带来绕路。

## 第 4–10 轮

**第 4 轮｜账本有界 + 匹配口径**
- `prune_events`：终态且超保留期的 run 删掉每 token 一行的流式块（一夜测试 38 557 行 / 47 MB），审计用的 values/updates/metadata 保留。
- 「提到模板名 ≠ 要画布」：`解释一下什么是用户画像` 此前白背 3 600 字符指引。

**第 5 轮｜网页正文进上下文的限额**
契约允许 `fetch_url` 返回 60 000 字符（约 24 000 token），是本地 8 192 上下文的三倍——一次抓取就把它自己所服务的对话挤掉。本地限 6 000 字符，API 返回与 contentHash 仍覆盖全文。工具结果驱逐阈值 8 000 → 2 500 token。

**第 6 轮｜评测抓到我自己的回归**
R4 的产出动词表只认「做一张/做个」，漏了裸「做」：`做商业模式画布` 因此没拿到指引，模型跑去 `write_todos + web_search`。改为「有产出动词且不是提问句式」。

**第 7 轮｜从「有没有围栏」到「画布完不完整」**
新判据：每个分区必须有 `##` 且至少一条要点，每个表头字段必须有值。一量就发现围栏 5/5、完整只有 1–2/5。两个真缺陷，都确定性修掉：
- 4B 把指引里的占位符 `字段名: 字段值` 逐字抄了九行——与 2026-09-10「（最多4条）」同一类：**指引本身是陷阱**。只注入一个模板时，示例改用该模板的真 key / 真字段 / 真分区，照抄即正确。
- 模型把分区写成 `用户描述：一整段内容` 或 `情境触发:` + 要点，内容全在但渲染端找不到分区。写回前提升为 `## 分区名`，一行形式的内容保留为首条要点，表头字段永不提升。

**第 8 轮｜CI 红的归属**
两条 streaming 契约测试报 `SocketError: other side closed`，没有任何信号指向根因。真因：真实账本长出 `append_events` / `events(after)` 之后，TS 契约测试的 Python 替身还停在旧签名，流式端点在响应生成器里抛异常、socket 中途断开。补齐替身 + 用 ast 逐方法比对签名的门控（反证：删掉 `after` 参数立刻红）。

**第 9 轮｜MLX 运行器**
同机同题实测（暖态）：`qwen3.5:4b` 首 token 3 984 ms、`qwen3.5:4b-mlx` 2 106 ms；生成两者都 ~30 tok/s。本地每个请求都由预填充主导。`preferredChatModel` 先按内存选尺寸、再按平台选运行器。

**第 10 轮｜MLX 的安全线与随包瘦身**
「库里有这个标签」≠「这台机器能跑它」：预热即验证，失败就回落非 MLX 版。Mac 随包改为 MLX 4B + GGUF 4B（回落）+ 嵌入，去掉 2B（16 GB 上它与聊天模型互相换入换出）。
