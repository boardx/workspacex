# R16：剪掉 1.5 GB 打包垃圾，并补上「包完整吗」这道发布门

实测机器：Apple Silicon / 16 GB / macOS 26.5。产物由 `apps/desktop` 本地构建。

## 剪了什么，以及判据

判据不是「看着像开发依赖」，是逐条核过运行时到底加不加载：

| 包 | 大小 | 为什么运行时不需要 |
| --- | --- | --- |
| `electron@33.4.11` | **708 MB** | 应用本身就是 Electron（`Contents/Frameworks` 里那份）；bundle 里的运行时代码对 electron **零 import** |
| `app-builder-bin` | 207 MB | electron-builder 自己的二进制，打完包就没用了 |
| `workerd` ×3 个版本 | 303 MB | wrangler 的运行时，给 `apps/coord-gateway` 用 |
| `@cloudflare/workerd-darwin-arm64` ×3 | 289 MB | 同上（平台二进制，三个版本各一份） |
| `typescript@4.9.5` | 64 MB | 运行时用 tsx（esbuild），不做类型检查 |

`up()` 启动的是 api / web / skill-sandbox / asr-gateway / deep-agent / ollama（外加延后的
model 装载）——**没有 coord-gateway**，而 `packages/local-runtime` 对 wrangler/workerd 零引用。

## 结果

| | 剪之前 | 剪之后 | 省下 |
| --- | --- | --- | --- |
| `.app` | 12,706 MB | **11,204 MB** | 1,502 MB |
| `bundle/` | 3,712 MB | **2,209 MB** | 1,503 MB |

没剪的（下一轮单独验）：`@next+swc-darwin-arm64` 110 MB、`monaco-editor` 98 MB、
`mermaid` 83 MB、`echarts` 54 MB、`lucide-react` 43 MB。生产构建之后它们**看起来**已经
进了 `.next`，但「看起来」不是判据。

## 反证：剪包是危险操作，判据必须是「包还能用」

`check-bundle-lean.mjs` 只查「不该在的在不在」，头注里写明它**证明不了包能用**。
真正的反证是把应用跑起来——**全新 userData 的完整首次运行**，这条路径碰的代码最多：

| | |
| --- | --- |
| 从 `open` 到首行日志 | 38.7s（重新打包后的首次启动，见下） |
| 模型导入 100% | +20.3s |
| 模型就绪 | +23.8s（延后，不挡界面） |
| 沙箱 / 语音 / API / deep-agent / Web ready | +26.3 / +28.7 / +30.5 / +34.2 / **+35.2s** |
| 界面可访问 | 75.3s |
| **登录 → 发消息 → 标题自动生成 → 真实模型答案** | **37 秒后出字** ✅ |

标题被自动生成成「存储相似内容查找的数据库」——这一条顺带证明元模型链路也通。

## 反证过程中抓到的真缺陷（不是剪包造成的）

日志里有一条 `⚠ skill 沙箱没有预装模块目录：pptx / docx / xlsx / pdf 生成类 skill 会以
MODULE_NOT_FOUND 失败`。我先误判成自己剪坏了——查下来不是：

- `apps/skill-sandbox/preinstalled` 由 `scripts/local-bundle/prepare-sandbox-modules.sh`
  生成、**不入仓库**，而 `dist:mac` **不跑那个脚本**。我的新 worktree 从没跑过它。
- 这和 R15 的 web 产物是**同一个家族**：发布脚本依赖「开发者手工跑过某些脚本」，
  漏了就发布一个少能力的包，而**唯一的症状要等用户真去生成一个文档才出现**。

⚠ 我一开始的 grep 判据也错了一次：我搜 `MODULE_NOT_FOUND`，命中的是一条**文案里含
这几个字**的告警，不是真的缺模块。差点把一条正常的能力提示报成剪包事故。

### 修法：接进「能不能发布」那道门

`releasable.ts` 加 `missingPreparedDirs`，`check-releasable.mjs` 检查五个由准备脚本
产出的目录（`skill-sandbox/preinstalled`、`apps/web/.next`、`Resources/python`、
`Resources/bin`、`Resources/models`）。对当前产物实跑，它把缺失的那个报成**第 1 条阻塞**，
且只报了那一个——同时反证了我的剪包没有碰到另外四个。

反证：删掉这段阻塞逻辑 → 13 条里红 3。

## 顺带确认的一件事

那 38 秒的首次启动税**与包体积同方向但不成比例**：12.7 GB 时 37.4s，11.2 GB 时 38.7s。
所以剪掉 1.5 GB **没有**明显缩短它（在噪声内）。我先前说「剪包会同时缩短它」，
按这两个数据点**不成立**——要么它主要由文件**个数**而不是字节数决定，
要么还有别的主导因素。这条以后要么拿更多数据点说清，要么别再声称。

# R17：文件数实验——**我的预测错了**，剪包不是那 38 秒的杠杆

## 先说方向上的一个修正

原计划是「开 asar 把 bundle 收成归档」。**查过才知道 asar 在这里不适用**：它只打包
`files`（`Resources/app`，431 个文件 / 27 MB），而 bundle 走 `extraResources`，
asar 一个文件都不碰。没查就动手会花半天做一件无效的事。

## 实验

按文件数剪（判据是运行时用不用，不是体积）：

| 类别 | 文件数 | 为什么运行时不需要 |
| --- | --- | --- |
| `*.map` | 28,864 | source map 只给调试 |
| `*.d.ts` | 21,225 | 运行时 tsx 不做类型检查 |
| `*.md` | 3,024 | 文档 |
| `test`/`tests`/`__tests__` 目录 | 1,366 | 依赖自己的测试 |

刻意**不删**两类，理由不是体积：
- `LICENSE*`（1,599 个）——再分发 MIT/BSD 依赖要保留版权声明，这是**许可证要求**
- `__pycache__`（4,105 个）——应用目录只读，删了 Python 每次启动重新编译，可能更慢

删 `*.md` 前查过一个险点：技能定义会不会是 markdown。`skills/starter-packs` 里是
**28 个 JSON、零 markdown**（SKILL.md 正文内嵌在 JSON 里），所以安全。

结果：**158,721 → 104,308 个文件（−34.3%）**，11,113 → 10,532 MB（−581 MB）。

## 判决：预测失败

落地前写下的预测是「若由文件数主导，应降到 **25 秒**上下」。

| 实验 | 变化 | 38 秒税 |
| --- | --- | --- |
| R16 减字节 | −12%（1,503 MB） | 37.4 → 38.7s（**没动**，在噪声内） |
| R17 减文件数 | **−34.3%**（54,413 个） | 38.7 → **33.7s**（−13%） |

**文件数是弱因素，不是主导**：减三分之一文件只换来八分之一时间。25 秒的预测**错了**。

⚠ 一个要说明的混淆：这次测量时 1 分钟负载 2.45（过了我的门），但 5 分钟负载 5.18、
15 分钟 7.42——机器不是完全空闲。33.7s 这个数可能偏大，但不足以把 −13% 解释成 −34%。

**结论：剪包不是那 38 秒的杠杆。这条路到此为止。**

剩下最可信的假设是签名：产物是 ad-hoc，且 `spctl` 报
`code has no resources but signature indicates they must be present`——
**没有公证票据，macOS 只能把整个包哈希一遍**。它同时解释了为什么字节几乎不影响、
文件数只弱影响。这个假设**预测签名+公证会直接解决 38 秒**，但没有证书验不了。

## 剪包本身的反证（危险操作，判据是「包还能用」）

| | |
| --- | --- |
| 缺模块 / 启动失败 | **0 条** |
| 六个服务 | 全起（pglite / ollama / api / deep-agent / skill-sandbox / asr-gateway / web） |
| 六个端口 | 全通（3100 / 3200 / 3310 / 3320 / 11435 / 55432） |
| 真实聊天 | 「什么是哈希表」→ **20 秒**拿到真实答案，标题自动生成 |

## R16 + R17 合计

| | 原始 | 现在 | 省下 |
| --- | --- | --- | --- |
| `.app` | 12,706 MB | **10,532 MB** | **2,174 MB（17%）** |
| 文件数 | 158,721 | **104,308** | **54,413（34%）** |

这些对下载体积和磁盘是真收益，只是**对那 38 秒不是**。

# R18：再剪 217 MB 构建期 web 依赖，并修掉我自己 R15 钉错的那道门

## 剪了什么（每条都实测，不是「看着像」）

| 包 | 判据 |
| --- | --- |
| `monaco-editor` | `next.config.mjs` 在求值期把 `min/vs` 拷到 `public/monaco-editor`，**拷贝两侧都有 `existsSync` 护栏**（源没了跳过、目标在了跳过），而那份拷贝（24 MB）已在包里。实测剪后 `/monaco-editor/vs/loader.js` → **HTTP 200** |
| `@next+swc-darwin-arm64` | **实测**：把它移开后 `next start` 照样起得来（生产产物不再编译） |
| `mermaid` / `echarts` / `lucide-react` | 客户端库，生产构建已打进 `.next/static`；`.next/server` 里对这几个包**零引用**（grep 实测） |

## ⚠ 我报的 388 MB 是重复计算的，真实边际值 217 MB

那个 388 MB 量的是**未剪过的源树**，而 R17 已经先把这些包里的 `.map`/`.d.ts`/`.md`
剪掉了：mermaid 84 → 24 MB、echarts 54 → 22 MB、lucide 33 → 9 MB——它们的体积
**主要就是 source map**。剪过之后的边际值合计约 260 MB，实测包体减少 **217 MB**。

## 反证（判据是「包还能用」）

| | |
| --- | --- |
| 六个端口 | 全通（3100 / 3200 / 3310 / 3320 / 11435 / 55432） |
| 缺模块 / 启动失败 | **0 条** |
| monaco 静态资源 | `/monaco-editor/vs/loader.js` **HTTP 200** |
| 真实聊天 | 「什么是 B 树」→ 流式出字，内容正确 |

## 撤回一条上一轮的建议：不要按平台只发 MLX

我建议过「mac-arm64 只发 `-mlx`，省 3.16 GB」。查代码后**撤回**：`up.ts` 那段注释写明

> MLX 构建更快，但「库里有这个标签」不等于「这台机器能跑它」。预热就是那次验证：
> 预热不过就换回非 MLX 版，宁可慢也不能让用户的第一条消息撞上起不来的运行器。

**GGUF 不是冗余，是刻意留的退路。** 删掉它，MLX 起不来的机器就彻底没有聊天。
要省那 3.16 GB，得先决定接不接受这个风险（或者反过来只发 GGUF：省 0.54 GB，
但丢掉实测的首 token 3984 → 2106 ms）。这是产品取舍，不是技术清理。

## 修掉我自己 R15 钉错的那道门

R15 我把 `probeChatModel` 挪出关键路径，并断言它只有一个调用点——那条断言是真的，
但它**管不着真正挡首屏的那一次**：`await warmModel(ollamaUrl, chosen)` 才是把 4 GB
权重装进内存的调用，而它**一直在关键路径上**。

后果有两层：
1. R15 那几条测试给人的印象是「模型装载已经不挡首屏了」，而**实测冷机仍约 18 秒**。
2. 我当时报的「26.1s → 9.8s 里分不清多少是页缓存」，现在有了更确定的答案：
   **很可能大部分都是页缓存**，因为真正的阻塞点一直没动。

新门要求三件（那个 `await` **不**挪走，它有正当理由）：
- 关键路径上**只剩一处**模型装载（多一处就是又把时间加回来）
- 它旁边必须写明为什么必须阻塞（否则下一个人会当成漏改）
- **MLX 回落分支必须还在**（删了它，那类机器彻底没有聊天）

反证：删回落分支 → 红；再加一处 `await warmModel` → 红。

D1 冷路径的正确修法因此是「**首屏就是应用 + 模型还在装的状态**」，不是去掉这次验证。

# R19：去掉重复模型省 3.2 GB —— 而它差点变成「每台机器下载 3.2 GB」

人类决策 2026-09-24：**体积优先，接受没有 GGUF 退路**。据此 mac-arm64 只带
`qwen3.5:4b-mlx` + embedding。产物 **10,242 → 7,009 MB**。

## 先记一条决策前没有、决策后才拿到的证据

那条 GGUF 退路**不是理论，是已验证有效的**。把 `bin/mlx_metal_v*` 真正移出 `bin/` 之后：

```
[ollama] failed to create server model=qwen3.5:4b-mlx error="MLX runtime is not available"
[ollama] qwen3.5:4b-mlx failed to load on this machine; falling back to qwen3.5:4b
载入的模型: ['qwen3-embedding:0.6b', 'qwen3.5:4b']
web HTTP 307 / api HTTP 200
```

所以去掉它，那类机器拿到的不是「慢一点」而是**完全没有聊天**。已把那条失败文案从
一行内部术语改成三段式（发生了什么／还有什么能用／三条恢复途径）。

⚠ 这个实验**前三次都失败，而且没有一次是因为 MLX 真的起不来**：
1. 我把目录改名为 `.hidden` —— ollama 按目录枚举、不看名字，`lsof` 显示它照样从
   `mlx_metal_v4.hidden/libmlx.dylib` 加载。**操作没造出条件。**
2. 磁盘掉到 12 GB，正好等于 `MIN_FREE_DISK_GB`，应用卡在 doctor 的模态框上。
3. 同上。

如果我没去查 `lsof`，就会拿第一次的无效实验得出「MLX 藏起来也照样跑」——
而那个结论**恰好支持刚做出的决定**。顺着决定的错误结论是最危险的那种。

## 然后：去掉 GGUF 让应用开始从网上下载 3.2 GB

```
[ollama] 拉取 qwen3.5:4b 10%（0.3/3.2 GB）
```

省下的 3.16 GB 包体，变成**每台新机器 3.2 GB 的下载**——而「零网络首次运行」
正是「模型随包」这个决策存在的唯一理由。代码改完、测试通过、体积数字漂亮，
**只有真跑一次首次运行才看得见它**。

### 根因：同一件事声明在两处，而这一类已经发生过一次

`up.ts` 的拉取步骤自己维护一份「需要哪些模型」（`c.chatModel`），而知道 `-mlx`
变体能满足需求的 `preferredChatModel` 在它**之后**才跑。

那段代码上面的注释逐字记着第一次（2026-09-22）：元模型从 Mac 包里去掉之后，
每次首启拉 **2.6 GB** 去换一个机器随后会拒绝使用的东西（用户实测：卡在
「检查本地模型」7 分钟）。**当时的修法是把它从清单里删掉——症状治了，根因没治。**

修法：拉取清单从 `preferredChatModel` 派生，两份判断合成一处。

### 一条被我删掉的断言，以及为什么那不是削弱门控

老测试 `model-choice.test.ts` 断言拉取那一行**必须含 `c.chatModel`** ——
它钉住的正是这次的缺陷本身，修法会被它判成违规。我删了那句，并在测试里写明
为什么删、以及「清单必须从选型派生」由哪条新测试接管。
顺手把它的判据从「那一行」放宽到**整个拉取段**（原来把 `c.metaModel`
挪到下一行就能绕过）。

## 验证（前后对照，判据精确）

| | 有 bug 那次 | 修后 |
| --- | --- | --- |
| 真正的拉取进度行（`拉取 qwen… NN%`） | **17** | **0** |
| 日志里的关键行 | `拉取 qwen3.5:4b 10%（0.3/3.2 GB）` | `qwen3.5:4b-mlx 已随包，不再拉取 qwen3.5:4b` |
| 六个服务 | — | 全起 |
| 载入的模型 | — | `qwen3.5:4b-mlx` |

⚠ 我第一版判据 grep `拉取 qwen` 得到 **1**，那 1 是我自己新写的「**不再**拉取」
那句话匹配上了。这次错在偏「像失败」的安全方向，但判据仍然是糙的——
改成匹配带百分比的进度行才准。

「外部地址命中 2」也是误报：一条是 ollama 打印自己的空 `HTTPS_PROXY`，
另一条是**本地存储路径**（`manifests/registry.ollama.ai/library/` 就是 Ollama 的目录结构）。
