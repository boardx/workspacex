# 结果呈现对标 Claude Code / Codex —— 十轮 UIUX 迭代

人类交办（2026-09-23）：聊天与 Claude Code / Codex 差距巨大，**特别是呈现结果的时候**；
要「在右边可以打开结果、浏览网页」，「可以拖拽边界」，review 整个 UIUX，每轮找出 10 个问题再迭代。

## 第 1 轮：找出的 10 个问题

1. **右栏宽度写死 288px，不能拖**——人类点名的第一件。
2. 宽度不记忆：每次回来都回到 288px。
3. 拖拽若只做鼠标，键盘用户拿不到这件能力。
4. 结果在**模态对话框**里打开，不能边看结果边追问（Claude Code / Codex 的核心差距）。
5. 没有网页查看：`fetch_url` 抓回来的只有文字，原网页打不开。
6. 一次只能看一个结果，没有多结果并列/切换。
7. 产物列表只有一种打开方式，没有「在右栏打开 / 新窗口打开」之分。
8. 全局壳左右栏同样写死，右栏 `hidden xl:block`——1280 以下整条消失。
9. 折叠态 40px 图标条与展开态之间没有中间档，窄屏上要么占 288px 要么只剩图标。
10. 结果视图缺常驻操作条（复制 / 下载 / 在浏览器打开）。

### 本轮交付（问题 1 / 2 / 3）

- `lib/chat-workbench/panel-width.ts`：**判据单源**的纯函数层——夹取（含「不超过半屏」的
  相对上限）、指针→宽度（把方向写进函数，左右栏复用时不会把符号搞反）、按键→宽度、
  读写持久值。放纯函数是因为 jsdom 模拟真实拖拽不可靠，判据落在测不动的那一层就是空转。
- `components/shell/panel-resize-handle.tsx`：WAI-ARIA **window splitter**
  （`role="separator"` + `aria-valuenow/min/max`），鼠标拖、键盘 ←→（Shift 大步）、
  Home/End 到两端、双击或 Enter/Space 回默认宽度。命中区 6px——1px 的把手谁也抓不住。
- `chat-task-inspector.tsx`：展开态宽度改由状态驱动并持久化（`shell.panelWidth.chat-inspector`）。
  默认值 288px 与被它取代的 `w-72` **逐字相等**，不改默认观感，只是让它可动。

边界：折叠态（40px）与移动态**不给**把手——那两档不是「更窄的同一档」，是另一种形态。
初值不在 `useState` 里读 localStorage（SSR 首帧必须两端一致），同 `app-shell` 折叠态的既有做法。

验证：`panel-width` 15 条、把手 5 条、接线 4 条；`apps/web` ui 全量 **3150 passed / 0 failed**。

### R2 复盘找到的下一批 10 件

1. **产物详情没有动作条**——复制 / 下载 / 在新窗口打开都没有；看完只能返回。
2. **抓回来的网页只有正文文本**（`fetch_url`），没有原始地址、没有「在浏览器里打开」。
3. **一次只能看一个结果**，没有多开/并排；追问时要反复返回列表。
4. 右栏在 1280 以下 `hidden xl:block` 整条消失——笔记本常见宽度上结果无处可看。
5. 全局左右栏宽度仍写死（272 / 316），R1 的拖拽只覆盖了 chat 右栏。
6. 折叠（40px）与展开之间没有中间档，窄屏上只能全有或全无。
7. 产物列表没有「最近打开」，长列表里找回刚看过的那份要靠记标题。
8. 详情态标题只有一行截断，没有类型/版本/大小等可判断「这是不是我要的那份」的信息。
9. 消息气泡里的产物引用不能直接送进右栏，只能去产物页签里找同名的。
10. 右栏拖到很窄时详情正文不重排（表格/代码块横向溢出），没有最小可读宽度的守卫。

# 第二批十轮：评测集驱动（2026-09-24 起）

人类交办：「做一个评测集，每次迭代要有一个 e2e 的测试，然后找出 10 个问题，
目标是 10 轮做完还要达到九分」。

判据的唯一权威仍是 `.harness/instructions/chat-ux-acceptance-criteria.md`（十项，各 0–1 分）。
评测集不是第二份标准，是它的**机械落地**：`apps/web/e2e/chat-ux-eval.spec.ts`
+ `e2e/support/chat-ux-rubric.ts`，跑 `pnpm run eval:chat-ux`（真栈 + loopback 替身，约 3 分钟）。

## E1（第 1 轮）——建评测集，拿到可信基线 **7.0 / 10**

| # | 维度 | 分 | 关键证据 |
|---|---|---|---|
| 1 | 流式反馈 | 0.50 | 首次反馈 67ms；**正文长度样本只有 2 个**（40→80），判据要 ≥4 |
| 2 | 可见的规划步骤 | 0.50 | **计划条目 0 条**，只有 1 段进展摘要 |
| 3 | 工具调用可见 | 1.00 | 4 行 + 4 个终态图标，首行「已执行 · 制定执行计划」 |
| 4 | 真实多步 | 1.00 | 4 种不同执行行 |
| 5 | 语音输入 | **未量** | 本轮没有探针（按 0 计入总分，但不等于已验证为 0） |
| 6 | 多轮上下文 | 0.60 | 链路通（5→7 条）；上限 0.6，语义记忆要真实模型才判得了 |
| 7 | 错误透明 | 1.00 | 失败可见 + 有下一步 + 屏上无内部错误码 |
| 8 | 消息呈现 | 1.00 | 渲染出结构标签，正文无残留 markdown 记号 |
| 9 | 控制感 | 0.50 | 状态条在，但**2.5 秒内文案一字不变**（「正在推进任务」→「正在推进任务」） |
| 10 | 整体连贯性 | 1.00 | 0 pageerror / 0 console.error / 0 个无可访问名的可点按钮 |

### 这一轮最重要的事：前两次测出来的分都是假的

- 第一次 6.5 分里，②⑨ 两项的低分是**我的探针瞎了**——我写的
  `chat-task-workbench-plan-item` / `chat-task-workbench-live-strip` **两个 testid 都不存在**，
  真实的是 `agent-plan-item-N` / `run-trace-live-strip`。
- 改对 testid 后 ⑨ 仍是 0，但那**还是**探针的问题：`RunTraceLiveStrip` 在 `!active` 时返回
  null，它所在的 trace 面板要等 journal 有事件才挂载——「运行中」与「状态条已挂载」之间有
  一个窗口，我取早了且不再重试。改成轮询后才看到它其实是在的（0.5）。

两次都是同一个形状：**0 分要先证明探针不瞎**。这也正是为什么记分卡区分「量到 0 分」与
「未量」——没跑过的探针给出的不是分。

### E1 找出的 10 个问题（下一轮起按顺序打）

1. **⑨ 实时状态条文案不变**：跑 2.5 秒「正在推进任务」一字不动，等于一个会转的圈。
2. **② 计划条目 0 条**：多步剧本的「计划」是一次工具调用（`制定执行计划`），不是结构化计划面。
3. **① 流式样本只有 2 个**：判据要 ≥4 个不同长度；要么真的不够细，要么采样间隔不对——先分清。
4. **⑤ 语音没有探针**：这一项占满分 1 分，现在按 0 算，必须先量到。
5. **⑥ 天花板 0.6**：语义记忆判不了。要么接真实模型车道，要么改判据（需人类裁决）。
6. 评测没有纳入任何 CI 车道，只能本地手跑。
7. 没有量「一次任务的成功率」——人类最痛的那项（工具调用永不返回）仍然没有数。
8. 没有量端到端耗时分布（p50/p95），`chat-agent-performance-acceptance.md` 那张 SLO 表还没有机械落地。
9. ⑩ 的「假按钮」判据只查了「可点但无可访问名」，查不到「点了什么都不发生」。
10. 记分卡只有总分与逐项分，没有趋势（每轮一份快照，看不出是哪一轮掉的）。
